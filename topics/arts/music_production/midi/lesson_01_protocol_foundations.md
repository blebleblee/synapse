# Lesson 1: Protocol Foundations

## 1. First-Principles Intuition & Invariants

The Musical Instrument Digital Interface emerged in 1983 as a radical compression of musical performance into the narrowest possible datastream. Before MIDI, electronic instruments spoke mutually incomprehensible analog control voltages—Moog's 1-volt-per-octave standard clashed with Yamaha's proprietary schemes, and every synthesizer manufacturer erected walls around their ecosystems. Dave Smith and Ikutaro Kakehashi recognized that musical performance could be distilled to a discrete event stream: a note begins, a note ends, a controller moves. This insight produced a protocol so lean it could traverse 31.25 kilobaud serial connections, yet so architecturally sound it remains the lingua franca of digital music four decades later.

MIDI's philosophical foundation rests on event-driven sparsity. Unlike audio, which demands continuous sample streams at 44,100 or 96,000 measurements per second, MIDI transmits only state transitions. A pianist holding a chord generates exactly three bytes when the key depresses and three more when it releases—seconds of silence produce zero protocol traffic. This elegance emerges from treating music as discrete control messages rather than acoustic waveforms. The protocol makes no assumptions about synthesis engines, recording media, or acoustic output; it merely describes performance gestures in a machine-readable notation.

The specification enforces strict invariants that pervade every layer. Messages consist of status bytes followed by zero to two data bytes, with the most significant bit serving as a type discriminator: status bytes always set bit 7 high (`0x80–0xFF`), while data bytes always clear it (`0x00–0x7F`). This single-bit sentinel allows receivers to resynchronize after transmission errors or detect framing mistakes without out-of-band signaling. The protocol operates as a unidirectional broadcast bus—there exists no acknowledgment mechanism, no flow control, no retransmission layer. Senders fire messages into the void and trust that receivers decode them correctly. This radical simplicity emerged from hardware constraints: early synthesizers could afford neither the memory nor the processing cycles for stateful connection management.

Channel voice messages, the protocol's workhorse category, embed a 4-bit channel identifier directly into the status byte's lower nibble. The original specification carved the namespace into sixteen logical channels multiplexed onto a single physical wire. A status byte of `0x92` decodes as "Note On, Channel 3" (`0x90` base + 2 offset, where channels index from zero in the wire protocol but label from 1 in human interfaces). This design allowed sixteen instruments to share one cable without crosstalk, though it created immediate namespace exhaustion as studios daisy-chained multiple synthesizers. The industry responded by multiplying physical ports—modern interfaces expose sixteen ports of sixteen channels each for 256 total channels—but the per-port protocol remains unchanged.

Data bytes encode musical parameters across a 7-bit range, yielding 128 discrete values. Note numbers map to equal-tempered pitches, with middle C canonically assigned to 60, following the equation

$$f = 440 \cdot 2^{(n - 69)/12} \text{ Hz}$$

where $n$ represents the MIDI note number. Velocity values span 1 to 127, where 0 carries special semantics in Note On messages to encode Note Off, an optimization that conserves bandwidth by eliminating redundant status bytes. Controller values occupy the same 0–127 range, though continuous controllers like modulation wheels often require 14-bit resolution by pairing coarse (CC 1) and fine (CC 33) messages. This resolution split reflects the era's 7-bit data bus constraints—modern implementations frequently ignore the fine controller layer, accepting the quantization noise of 128 steps rather than implementing paired message parsing.

The specification distinguishes three message categories by scope. Channel voice messages target specific instruments: Note On, Note Off, Control Change, Program Change, Pitch Bend, and Polyphonic and Channel Aftertouch. Channel mode messages reconfigure receiver behavior: All Notes Off, Reset All Controllers, Local Control On/Off, and the Omni/Poly/Mono mode selectors that determined whether 1980s synthesizers would respond to all channels or just one. System messages operate globally, subdivided into System Common (Song Position Pointer, Song Select, Tune Request), System Real-Time (Timing Clock, Start, Continue, Stop, Active Sensing), and System Exclusive (manufacturer-specific bulk dumps and parameter editing). This taxonomy reflects the protocol's evolution from single-instrument control to studio-wide synchronization infrastructure.

Running status, a bandwidth optimization introduced in MIDI 1.0, allows transmitters to omit repeated status bytes when sending consecutive messages of the same type to the same channel. After transmitting `0x92 3C 64` (Note On, Channel 3, middle C, velocity 100), the sender may issue `3E 64` directly for the next note, implicitly reusing the `0x92` status. This compression roughly halves bandwidth for dense polyphonic passages, but introduces state machine complexity: receivers must latch the last channel voice status byte and clear it upon receiving any system message, which cannot participate in running status. The optimization becomes treacherous in error conditions—a dropped byte transforms subsequent data bytes into phantom status bytes, cascading into protocol desynchronization until a fresh status byte or system reset restores framing.

Timing resolution represents the protocol's most contentious architectural constraint. MIDI operates in musical time, not absolute time. System Real-Time messages broadcast at 24 pulses per quarter note (PPQN), a resolution chosen to factor cleanly into common subdivisions: quarter notes, eighth notes, triplets, and sixteenth notes all align to pulse boundaries. However, 24 PPQN proves insufficient for expressive timing—human performers deviate by microseconds, while 24 PPQN quantizes to 20.83 milliseconds at 120 BPM. The specification addresses this with MIDI Time Code (MTC), which synchronizes to SMPTE timecode at frame granularity, and with high-resolution extensions like MIDI Clock with Song Position Pointer interpolation. Modern digital audio workstations internally operate at 960 or 1920 PPQN, downsampling to 24 PPQN only when transmitting to external hardware.

The protocol's most profound invariant is its separation of control and synthesis. MIDI describes performance gestures—key depressions, knob rotations, pedal movements—but specifies nothing about sound generation. A Note On message at velocity 100 might trigger a sampled piano, a frequency-modulated bell, or a granular synthesis cloud, depending entirely on the receiver's implementation. This abstraction liberated manufacturers to innovate in synthesis engines while maintaining interoperability, but also fragmented the ecosystem. Two synthesizers receiving identical MIDI streams may produce entirely different sonic results, a design choice that prioritized extensibility over deterministic reproduction. The protocol assumes intelligent receivers capable of mapping abstract control gestures to domain-specific synthesis parameters, deferring all timbral decisions to the endpoint.
