# Lesson 3: Graphics Rendering Pipelines

## 1. First-Principles Intuition & Invariants

The cathode ray tube television receiving analog composite video from a retro game console operates under physical constraints that shape every pixel rendered by the system. The electron beam sweeps horizontally across phosphor-coated glass at approximately 15.7 kHz for NTSC or 15.6 kHz for PAL, retracing to the left edge during horizontal blank, then descending one scanline to repeat the process. After completing all active scanlines—262.5 for NTSC, 312.5 for PAL—the beam retraces vertically during the much longer vertical blank interval. This raster scan discipline imposes an iron law: the graphics hardware must deliver pixel data synchronously with beam position, or the display shows garbage, tearing, or nothing at all.

Early console designers confronted a brutal arithmetic problem. A single frame of 256×240 pixels at 60 Hz demands 3,686,400 pixel decisions per second. The 6502 processor in the NES runs at 1.79 MHz, executing perhaps 500,000 useful instructions per second after accounting for memory wait states. Even if the CPU did nothing but write pixel data, it would fall short by an order of magnitude. The Z80 in the Master System or Game Boy fares no better. The solution lies in offloading raster generation to dedicated silicon that operates in parallel with the CPU, converting compact symbolic descriptions—tilemap indices, sprite coordinates, palette entries—into the analog voltage waveforms representing color intensity.

The Picture Processing Unit in the NES, the Video Display Processor in the Genesis, and similar chips in every console from the Atari 2600 to the Super Nintendo all implement variations on a layered compositing model. Background layers are constructed from rectangular tiles, typically 8×8 pixels, arranged in a grid according to indices stored in video RAM. Sprite layers overlay these backgrounds, each sprite defined by positional coordinates, tile references, and attribute flags controlling flip, priority, and palette selection. The hardware rasterizes these layers in fixed priority order, merging them into a single composite scanline delivered to the video encoder precisely when the electron beam demands it.

Palette indirection constitutes the second foundational invariant. Storing full RGB triplets for every pixel would exhaust the meager kilobytes of video RAM available in these systems. Instead, tile and sprite pixel data hold small indices—typically 2 to 4 bits—into palette RAM, which maps these indices to actual color values. The NES supports 64 colors in its master palette but allows only 25 simultaneous on-screen colors, divided into background and sprite palettes with 16 entries each. The Genesis expands this to 64 simultaneous colors from a master palette of 512. Palette RAM can be modified during vertical blank or, with careful timing, during horizontal blank, enabling effects like parallax scrolling layers with distinct color schemes or mid-frame gradient skies.

Timing synchronization between the CPU and graphics hardware determines what graphical effects are possible. The CPU must not write to video RAM while the PPU or VDP is actively reading it during scanline rendering, or visual corruption results. Vertical blank provides a safe window of approximately 1.3 milliseconds on NTSC hardware, during which the CPU can update tilemap data, sprite attribute tables, and palette entries without conflict. Scanline interrupts—triggered when the raster reaches a specific vertical position—allow mid-frame register changes, enabling split-screen status bars, parallax scrolling, or scanline-based sprite multiplexing to exceed hardware sprite limits.

The boundary between "background" and "sprite" reflects hardware optimization rather than conceptual necessity. Backgrounds are stored as tile indices in a contiguous two-dimensional array, minimizing VRAM reads through spatial locality. The hardware fetches each tile's pixel data once per scanline, shifting it out serially as the beam sweeps. Sprites, in contrast, are stored as discrete objects with arbitrary screen coordinates. The hardware must search the Object Attribute Memory table each scanline to identify which sprites intersect that line, fetch their tile data, and composite them over the background at the correct horizontal positions. This search-and-composite process is expensive; the NES limits sprite rendering to 8 per scanline, while the Genesis allows 20 but with a 320-pixel-per-scanline budget that overdraws consume rapidly.

Rasterization proceeds through a multi-stage pipeline that balances parallelism against chip area and power constraints. During the horizontal blank preceding a scanline, the hardware prefetches the next row of background tile indices from the nametable, looks up tile pattern data in character RAM, and loads shift registers with pixel values. Simultaneously, it scans the sprite table to identify sprites intersecting the upcoming scanline, fetching their tile data into line buffers. As the active scanline begins, background pixel shift registers clock out data synchronously with the dot clock—approximately 5.37 MHz for NTSC NES—while sprite compositors merge overlaying sprite pixels according to priority flags. The final pixel value indexes into palette RAM, which outputs RGB or YUV levels to the video encoder, which modulates the composite or RGB analog signal sent to the display.

Priority resolution between layers follows deterministic rules encoded in hardware. On the NES, sprites in lower OAM indices have priority over higher indices, with sprite zero reserved for collision detection. Background pixels can be flagged as high-priority to appear in front of sprites, enabling effects like the maze walls in Pac-Man obscuring characters. The Genesis implements four-bit priority per tile and per sprite, allowing finer-grained depth sorting. Transparency is defined by reserved palette index zero; any pixel with index zero allows the layer beneath to show through. This simple rule enables clouds drifting over mountains, characters walking behind fences, and explosions compositing over both sprites and backgrounds without CPU intervention.

## 2. Core Architecture & Mechanics

The NES Picture Processing Unit architecture exemplifies the elegance and constraints of tile-and-sprite rendering. The PPU contains 2 KB of internal video RAM divided into nametables and attribute tables, plus 256 bytes of Object Attribute Memory for sprites. External cartridge CHR ROM or RAM provides pattern tables—the actual pixel bitmap data for tiles—totaling 8 KB in the standard configuration. Nametable memory at addresses $2000–$2FFF holds four 1024-byte regions, each encoding a 32×30 grid of 8×8 tiles. Games typically use two nametables for scrolling, arranging them horizontally for side-scrollers or vertically for vertically-scrolling shooters, with mirroring mapping the other two nametable regions to the active pair.

Each nametable byte is an 8-bit tile index pointing into the pattern table. The PPU fetches pattern data in two planes: the low bit plane followed by the high bit plane, interleaving these to form 2-bit pixel values per tile. Attribute tables provide the upper two palette bits, stored with 4×4 tile granularity to conserve space. This means each attribute byte encodes palette selection for a 2×2 cluster of tiles through bit packing: bits 0–1 control the top-left tile pair, bits 2–3 control the top-right, bits 4–5 control the bottom-left, and bits 6–7 control the bottom-right. Consequently, adjacent tiles sharing an attribute byte boundary must coordinate palette choices, a constraint that shapes level art design and tile reuse strategies.

The PPU renders backgrounds through a carefully orchestrated fetch sequence occupying 256 dot clocks per scanline. During dots 0–255, the hardware performs 32 tile fetches, each consuming 8 dots divided into four 2-dot memory accesses: nametable byte fetch, attribute byte fetch, pattern low byte fetch, pattern high byte fetch. The nametable and attribute fetches use the current scroll position to compute VRAM addresses. The pattern fetches use the tile index and the current fine Y scroll (which row within the tile) to address CHR memory. Fetched pattern data loads into two 16-bit shift registers that clock out pixel data at the dot rate, while latched attribute bits select the palette. Fine X scrolling is implemented by starting the shift register output at an offset within the 16-bit buffer, delaying pixel emission by 0–7 dots.

Sprite rendering operates through a two-stage pipeline: sprite evaluation and sprite fetching. During dots 64–256 of the visible scanline, secondary OAM is populated with up to eight sprites intersecting the next scanline. The hardware scans all 64 sprite entries in primary OAM, comparing each sprite's Y coordinate against the upcoming scanline number. If a sprite intersects, its OAM data—Y position, tile index, attribute byte, and X position—is copied to secondary OAM. If more than eight sprites intersect, the overflow flag is set, and additional sprites are ignored, producing the classic sprite flickering when too many objects cluster vertically. Games mitigate this by cycling sprite priority each frame, distributing flicker across all objects rather than permanently blanking low-priority sprites.

During the horizontal blank and first few dots of the next scanline (dots 256–320), the PPU fetches tile pattern data for the eight sprites in secondary OAM. Each sprite requires four memory accesses similar to background tiles, but the Y coordinate within the sprite determines which row of tile data is fetched. Sprites can be 8×8 or 8×16 pixels; in 8×16 mode, the tile index selects a pair of vertically adjacent tiles, and the hardware automatically fetches the appropriate half based on the scanline Y offset within the sprite. Fetched sprite pattern data loads into eight pairs of 8-bit shift registers, each pair corresponding to one sprite.

During the active scanline, background and sprite pixel data merge through priority logic. For each dot, the background shift registers produce a 2-bit pixel value, while up to eight sprite shift registers produce candidate sprite pixels. The hardware selects the highest-priority opaque sprite pixel—opaque meaning non-zero after palette lookup—and compares it against the background pixel. If the sprite's priority bit is clear, the sprite pixel wins unless the background pixel is non-zero and the sprite is flagged as behind-background. If the sprite's priority bit is set, the background always wins if it is non-zero. The winning pixel value concatenates with the appropriate palette base to form a 5-bit palette index (0–31), which addresses palette RAM to produce the final color.

Scrolling modifies which portion of the nametable maps to the visible screen area. The PPU exposes two 8-bit scroll registers (written via $2005) for fine X and fine Y scrolling within tiles, plus coarse X and coarse Y components specifying the starting tile. During rendering, the PPU increments the coarse X position every 8 dots (one tile) and increments coarse Y at the end of each scanline. When coarse X or Y overflow their 5-bit ranges, the nametable selection bits toggle, seamlessly transitioning from one nametable to the adjacent one. This mechanism enables scrolling across the full 512×480 pixel space formed by two vertically or horizontally arranged nametables, with wrapping handled automatically by mirroring or cartridge-provided RAM.

The Sega Genesis VDP expands upon this model with richer capabilities and higher resolution. The VDP supports up to 512×512 pixel nametables (64×64 tiles) and dual independent scrolling planes (Plane A and Plane B) plus a fixed window plane for HUD elements. Each plane can scroll horizontally on a per-tile-row basis, enabling parallax effects where distant mountains scroll slower than foreground terrain. The VDP also supports horizontal and vertical scroll tables stored in VRAM, allowing per-line scrolling offsets written by the CPU during vertical blank or via DMA transfer during active display if carefully synchronized.

Genesis tile data resides in VRAM as 4-bit-per-pixel bitmaps, doubling the color depth compared to the NES. Each tile pixel indexes one of 16 colors within a selected palette line, with 4 palette lines of 16 colors each yielding 64 simultaneous colors. Plane tile attributes include horizontal and vertical flip bits, priority, and palette selection, all packed into a 16-bit word alongside the 11-bit tile index. Flipping tiles in hardware reduces VRAM consumption by allowing symmetric objects like trees or platforms to reuse a single tile with different flip states.

Sprite handling on the Genesis supports 80 sprite objects, each with configurable width and height from 8×8 up to 32×32 pixels in 8-pixel increments. Sprites are linked via a next-sprite index, forming a traversable list that the VDP walks each scanline. The sprite structure includes X and Y coordinates, size, tile index, priority, palette, and flip bits. The VDP imposes a per-scanline pixel budget of 320 pixels and a maximum of 20 sprites; exceeding either limit truncates rendering on that line. Unlike the NES, which shows all sprites up to the limit and then flickers, the Genesis simply stops drawing sprites once the budget exhausts, making careful sprite placement and sizing critical for avoiding visual dropouts.

The VDP rasterizes layers in fixed priority order: Plane B low-priority tiles, Sprite low-priority, Plane A low-priority tiles, Window/Plane B high-priority, Sprite high-priority, Plane A high-priority. This six-level depth sorting provides flexibility for foreground foliage in front of characters but behind status bars, or background mountains behind everything. The Window plane is not scrollable and typically overlays the upper or lower screen portion for fixed UI elements, defined by a horizontal split position register.

Direct Memory Access on the Genesis offloads bulk VRAM transfers from the CPU. The 68000 can configure the VDP to DMA from 68000 address space to VRAM, CRAM (color RAM), or VSRAM (vertical scroll RAM) at 16 bits per VDP access cycle. DMA during active display consumes VDP memory bandwidth, potentially disrupting sprite or plane rendering if overused, but DMA during vertical blank is safe and fast, transferring 7 KB in approximately 500 microseconds. DMA fill and copy modes further accelerate clearing or duplicating VRAM regions. Effective Genesis programming relies heavily on DMA scheduling, using horizontal interrupts to queue transfers and vertical blank to execute them atomically.

```
NES PPU Fetch Sequence (per tile, 8 dots):
Dot 0-1: Fetch nametable byte → tile_index
Dot 2-3: Fetch attribute byte → palette_bits
Dot 4-5: Fetch pattern low byte (CHR[tile_index][fine_y][low])
Dot 6-7: Fetch pattern high byte (CHR[tile_index][fine_y][high])

Shift register load (dot 8):
  bg_shift_low |= pattern_low
  bg_shift_high |= pattern_high
  attribute_latch = palette_bits

Genesis VDP DMA Transfer Timing:
68000 bus: 7.67 MHz / 2 = 3.83 MHz effective (wait states)
VDP clock: 53.693 MHz / 8 = 6.71 MHz VRAM access
DMA rate: 1 word per VDP cycle during blanking
VBLANK duration: ~1262 VDP cycles (NTSC)
Max DMA per frame: 2524 bytes (1262 words)
```

Palette RAM organization reflects the separation between background and sprite systems. On the NES, addresses $3F00–$3F0F hold background palette data (four 4-color palettes), while $3F10–$3F1F hold sprite palette data, also four 4-color palettes. Index 0 in each palette is the universal backdrop color, shared across all palettes. Writing to $3F00, $3F04, $3F08, $3F0C, $3F10, $3F14, $3F18, or $3F1C all modify the same physical backdrop color register. The NES master palette contains 64 colors, but not all are distinct; several entries represent the same hue at different brightness levels, and some colors are unstable or produce artifacts on certain television hardware.

The Genesis CRAM holds 64 entries of 9-bit RGB color values, structured as `0000 BBB0 GGG0 RRR0` with each channel providing 8 intensity levels (3 bits). The zero padding in the LSB position reflects the VDP's internal DAC resolution. Palette updates during active display require careful timing; writing CRAM during scanline rendering can produce transient color glitches visible as flicker or incorrect hues for a single scanline. Safe practice restricts CRAM updates to vertical blank or, for per-scanline effects like underwater color gradients, to horizontal blank with precise cycle-counted writes synchronized via horizontal interrupt.

The Game Boy and Game Boy Color represent constrained variations on the tilemap-sprite model. The Game Boy DMG PPU supports a single 256×256 pixel background layer (32×32 tiles) and up to 40 sprite objects (10 per scanline). Tiles are 2-bit-per-pixel monochrome, with four shades mapping to greenish-gray LCD levels via palette registers. The Game Boy Color extends tile attributes with palette selection (8 palettes for backgrounds, 8 for sprites) and VRAM banking, doubling character data capacity to 512 unique tiles. Color palettes provide 32 colors across 8 four-color palettes, with each palette entry selecting from a 15-bit RGB master palette (32768 colors). The GBC's palette system supports mid-frame updates via the HDMA (Horizontal DMA) feature, which transfers 16 bytes per scanline during horizontal blank, enabling effects like per-scanline palette cycling for waterfalls or sunset gradients.

The Super Nintendo Mode 7 represents a radical departure from fixed tilemap rendering. Mode 7 treats the background as a single large 128×128 tile canvas rendered through an affine transformation matrix. The SNES applies a 2D rotation, scaling, and translation matrix to map screen coordinates to tilemap coordinates, enabling rotation and zooming effects that simulate 3D perspective. The transformation matrix is programmable per-scanline via HDMA, allowing the famous pseudo-3D road and horizon effects in F-Zero and Super Mario Kart. The CPU writes matrix coefficients A, B, C, D (for rotation/scale) and origin offsets X₀, Y₀ to PPU registers, and the hardware performs the inverse mapping for each pixel:

```
tilemap_x = A × (screen_x - X₀) + B × (screen_y - Y₀)
tilemap_y = C × (screen_x - X₀) + D × (screen_y - Y₀)
tile_index = nametable[tilemap_x / 8][tilemap_y / 8]
pixel_color = tile_data[tile_index][(tilemap_y % 8)][(tilemap_x % 8)]
```

Calculating matrix coefficients requires trigonometric functions for rotation angles and reciprocal scaling factors, computations that the 65816 CPU performs in software using lookup tables or fixed-point arithmetic. Per-scanline matrix updates via HDMA tables precomputed during vertical blank enable the illusion of continuous rotation and zoom across the frame. The tradeoff is that Mode 7 supports only 256 colors (8-bit pixels) and no transparency, and only a single affine-transformed layer; sprites and other background modes overlay this layer through separate rendering paths.

## 3. High-Performance Optimization & Failure Modes

Optimizing graphics rendering on retro consoles demands precise understanding of hardware fetch cycles, memory bandwidth, and synchronization windows. The NES PPU imposes strict timing on VRAM access; attempting to write nametable or attribute data outside of vertical or horizontal blank while rendering is enabled produces unpredictable corruption. The PPU provides bit 7 of status register $2002 to signal vertical blank entry, but by the time the CPU reads this flag—typically within an NMI interrupt handler—dozens of scanlines into vertical blank have already elapsed. Fast NMI handlers that update large portions of the screen state must count cycles meticulously, deferring non-critical updates to subsequent frames or splitting work across multiple frames using ring buffers of pending changes.

Sprite flickering mitigation requires rotating sprite priorities to distribute the eight-sprite-per-scanline limit fairly across all objects. A common technique writes sprite OAM data in a different order each frame, cycling a base offset through the 64-entry OAM table. For example, on frame N, sprites [0, 1, 2, ..., 63] are written to OAM in order. On frame N+1, sprites [1, 2, 3, ..., 63, 0] are written, effectively rotating the priority queue. This ensures that when vertical crowding causes sprite overflow, different sprites flicker on alternating frames rather than permanently blanking low-priority objects. The cycle count for OAM updates is tight; the 256-byte OAM table can be written via $2004 in 256 × 4 = 1024 cycles if done serially, but DMA via $4014 completes in 513 cycles, making it the preferred method.

Vertical blank duration on NTSC NES spans approximately 2273 CPU cycles (20 scanlines × 113.67 cycles/scanline). Ambitious games like Super Mario Bros. 3 use this window to update scrolling, palette, and tilemap data for two or more separate nametable regions, requiring careful segmentation of workload. Techniques include maintaining dirty flags for nametable tiles that changed since the last frame, processing only the minimal set of updates. For smooth scrolling, pre-computing the nametable column or row entering the screen and writing it as a compressed run-length encoded stream reduces cycle overhead.

Palette animation—cycling palette entries to create animated water, torches, or status indicators—is cheap because palette RAM is small. Writing the 32-byte background+sprite palette via $2006/$2007 requires 32 × 4 = 128 cycles for address setup and data writes. Using DMA or unrolled writes minimizes overhead. Animated palettes in games like Mega Man produce flowing energy effects by rotating palette entries over multiple frames: frame 0 uses colors [blue1, blue2, blue3], frame 1 uses [blue2, blue3, blue1], creating apparent motion without modifying any tile data.

The Genesis VDP's dual-plane scrolling and per-line horizontal scroll enable complex parallax layers but require careful VRAM layout. Horizontal scroll tables reside in VRAM, consuming 2 bytes per scanline per plane (224 scanlines × 2 planes × 2 bytes = 896 bytes). Updating these tables each frame via DMA during vertical blank is essential for smooth parallax. The CPU precomputes scroll offsets for each parallax layer—e.g., foreground scrolls at 1:1 with player velocity, middleground at 0.5:1, background at 0.25:1—and writes the table entries. Vertical scroll is stored in a separate 40-byte VSRAM, supporting per-tile-column vertical offsets for additional parallax depth or split-screen effects.

Genesis sprite rendering budget exhaustion is a common failure mode. Exceeding 20 sprites or 320 pixels per scanline causes the VDP to halt sprite processing, leaving subsequent sprites invisible. Debugging this requires counting sprite pixels per line manually or using emulator debugging overlays. Solutions include reducing sprite sizes, splitting large sprites into smaller tiles, or using plane tiles instead of sprites for static or low-priority objects. The Sonic series uses sprites exclusively for characters and enemies, representing level geometry, rings, and decorative elements through plane tiles to stay within budget.

DMA scheduling on the Genesis requires balancing VRAM throughput against VDP rendering load. DMA during active display (H-blank DMA) can transfer small buffers without visible disruption if constrained to a few words per scanline. Exceeding the VDP's bandwidth budget causes sprite or plane glitches, manifesting as missing pixels or shifted tiles. Safe H-blank DMA limits are approximately 8–16 bytes per line, sufficient for palette fades or per-line effects but insufficient for bulk tilemap updates. Vertical blank DMA handles larger transfers, but the VBLANK window is finite (1262 VDP cycles on NTSC). Games needing extensive per-frame updates use double-buffering: render frame N+1's data during frame N, then atomically flip VRAM pointers during VBLANK.

Horizontal interrupt timing on the Genesis enables mid-frame register changes but demands cycle-accurate synchronization. The H-INT fires at the end of each scanline's active display, providing a narrow window before the next scanline begins. Typical H-INT handlers require 20–40 68000 cycles to execute, leaving limited time for complex logic. Critical updates—like changing scroll registers for raster effects—must execute in a fixed number of cycles to avoid jitter. The Sonic series uses H-INT to split the screen: the status bar at the top uses a fixed plane with no scrolling, while the playfield scrolls independently. The H-INT handler writes the horizontal scroll register at the precise scanline boundary separating these regions.

VRAM tile organization impacts rendering performance through cache locality. Grouping tiles used together in the same nametable regions into contiguous VRAM addresses minimizes VDP fetch latency. The VDP uses burst access patterns, reading sequential VRAM addresses faster than random addresses. Tiles for a platformer level's ground, walls, and props should occupy adjacent VRAM ranges. Sprite tiles benefit from similar grouping; if multiple animation frames of a character occupy consecutive tile indices, the VDP's prefetch logic can pipeline fetches more efficiently. Defragmenting VRAM during load screens or between levels by compacting active tiles and freeing unused ranges prevents fragmentation-induced slowdowns.

The Super Nintendo's Mode 7 affine transformations are computationally expensive in software. Calculating sine and cosine for rotation requires lookup tables or iterative approximations. Fixed-point arithmetic (16.16 or 8.8 format) balances precision against CPU cycle cost. Pre-computing rotation matrices for common angles (every 1° or 2°) reduces runtime math to table lookups and interpolation. Scaling factors require reciprocal division; storing precomputed reciprocals for zoom levels avoids expensive division operations. The F-Zero engine updates Mode 7 matrix coefficients via HDMA tables built from 3D camera position, viewing angle, and road geometry, with the table rebuilt every frame in under 5000 65816 cycles by caching intermediate trigonometric terms.

HDMA on the SNES automatically transfers data from ROM or RAM to PPU registers during horizontal blank, driven by a table structure defining source address, byte count, and scanline triggers. Each HDMA channel can update one or two PPU registers per scanline, enabling wave effects (undulating water surfaces), palette gradients (sunset skies), or window splits (split-screen multiplayer). The HDMA table structure uses indirect addressing for variable-length transfers: a header byte specifies the number of scanlines to repeat the transfer, followed by the transfer data. Careful table construction minimizes RAM footprint and HDMA overhead, which consumes a fixed number of CPU cycles per scanline (8–24 cycles depending on channel count).

Color banding artifacts on the Genesis stem from its 9-bit RGB palette (512 colors) with 3-bit-per-channel resolution. Smooth gradients require dithering: checkerboard or ordered patterns alternating between two adjacent palette entries to simulate intermediate shades. The VDP's raster-based rendering makes spatial dithering straightforward; tiles contain pre-dithered pixel patterns. Temporal dithering—cycling palettes frame-to-frame—produces smoother gradients on CRT displays, where phosphor persistence blends the flickering colors. The Super Mario World sunset effect combines HDMA palette gradients with temporal cycling, writing slightly offset palettes on alternating frames to mask the 3-bit quantization.

Ensuring VRAM coherence between CPU and graphics hardware requires respecting access windows. Writing VRAM while rendering is enabled produces unpredictable results because the PPU or VDP may be reading the same address simultaneously. The NES enforces this strictly; VRAM writes during active display appear as random corruption. The Genesis VDP is more lenient, allowing VRAM writes during active display but with no guarantees of atomicity. Games must track the frame state—whether in VBLANK, HBLANK, or active rendering—and defer writes accordingly. Double-buffering nametables avoids mid-frame updates by preparing the next frame's data in an inactive nametable region and flipping the base address during VBLANK.

Collision detection between sprites and backgrounds often piggybacks on rendering hardware. The NES PPU provides sprite-zero hit detection: bit 6 of status register $2002 sets when sprite zero's opaque pixel overlaps a non-transparent background pixel. Games place sprite zero at a known screen position—like the ground beneath the player—and use the hit flag to trigger events or synchronize scroll updates. This hardware-accelerated collision is single-point only; more complex collision requires CPU-driven bounding box tests using sprite and tile coordinates.

Video timing errors manifest as screen tearing (new frame data appears mid-frame), color flicker (palette writes during active display), or sprite dropout (exceeding per-scanline limits). Debugging requires emulator tools that visualize sprite counts, VRAM bandwidth, and scanline timing. Hardware testing on real consoles reveals timing issues emulators may mask; differences in VBLANK duration, DMA speed, or PPU latch behavior between emulators and hardware cause frame-perfect code to fail. Cycle-accurate emulators like Mesen (NES) or BlastEm (Genesis) expose these edge cases during development, but final validation demands testing on physical hardware with oscilloscope verification of video sync signals.

Compressed graphics formats reduce ROM footprint and VRAM upload time at the cost of CPU decompression overhead. Run-length encoding compresses repetitive tile patterns (sky tiles, blank spaces) into compact streams. Huffman coding or LZ77 compression reduces tilemap data size, decompressed during level load. Decompression must complete within VBLANK if updating VRAM mid-gameplay, or during inter-level loading screens for bulk updates. The Sonic series uses Kosinski and Nemesis compression formats optimized for fast 68000 decompression, achieving 50–70% size reduction on level tile data while decompressing 4–8 KB in under one frame's worth of CPU time.

Tile reuse and mirroring minimize VRAM consumption. Symmetric objects like pillars or trees load a single tile and render it with horizontal or vertical flip flags, halving storage. Palette swapping reuses tile patterns for objects differing only in color: red enemies and blue enemies share tile data but reference different palettes. The NES's 8 KB CHR memory holds 512 tiles; aggressive reuse is mandatory. The Genesis's 64 KB VRAM allows 4096 tiles (4-bit), but careful management still matters; loading only necessary tiles for the current level section and streaming new tiles as the player progresses prevents VRAM exhaustion.

Anti-aliasing and sub-pixel positioning are absent in hardware; all rendering operates on integer pixel coordinates. Smooth motion requires moving sprites by one pixel per frame, which appears jerky at low frame rates. Sub-pixel position tracking in software accumulates fractional movement (e.g., 1.5 pixels per frame) and updates sprite coordinates only when the fractional part exceeds 1.0. This produces smooth apparent motion averaged over multiple frames. The technique requires CPU-maintained position state separate from hardware sprite registers, updated each frame with careful rounding to avoid drift.

The cumulative effect of these hardware constraints and optimizations defines the visual language of retro games: the crisp tile-aligned geometry, limited palette-driven color harmonies, flickering sprites during intense action, and the characteristic CRT scanline and phosphor glow. Mastery of these pipelines transforms constraints into expressive tools, where every byte of VRAM and every scanline cycle contributes to coherent, performant visuals that remain iconic decades after the hardware's obsolescence.
