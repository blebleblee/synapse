# Lesson 2: Memory Hierarchies and Storage

## 1. First-Principles Intuition & Invariants

The architectures that powered the golden age of console gaming emerged from a crucible of brutal economic and physical constraints. Between 1983 and 1996, every byte of RAM, every nanosecond of memory access latency, and every address line on a cartridge connector represented tangible manufacturing cost and engineering tradeoffs that fundamentally shaped what games could achieve. Understanding retro console memory systems requires abandoning modern assumptions about abundant DRAM, multi-level cache hierarchies, and virtual memory paging. Instead, we must internalize the reality that programmers worked within fixed memory envelopes measured in kilobytes, where the boundary between storage and execution memory was often nonexistent, and where clever indirection through bank switching hardware represented the only path to building experiences larger than the address space itself.

The fundamental invariant governing all retro console memory design stems from the economic realities of semiconductor manufacturing in the 1980s and early 1990s. DRAM and SRAM carried substantial per-bit costs, and larger address buses required additional pins, traces, and decoding logic that drove up both silicon area and printed circuit board complexity. The Nintendo Entertainment System shipped with a mere 2 kilobytes of onboard work RAM and 2 kilobytes of video RAM, while the Sega Genesis provided 64 kilobytes of main RAM and 64 kilobytes of VRAM—a generous allocation for 1988 but still microscopic by any modern standard. These capacity limits were not arbitrary; they represented carefully calculated price points where console manufacturers could hit retail targets while maintaining acceptable profit margins. The consequence was an ecosystem where every global variable, every sprite coordinate buffer, and every decompressed audio sample competed for precious bytes in a zero-sum allocation game.

Cartridge-based storage inverted the traditional distinction between read-only program storage and read-write working memory. Unlike floppy disk or CD-based systems where software loaded from slow media into fast RAM before execution, cartridge systems memory-mapped the entire ROM directly into the processor's address space. This architecture eliminated load times and allowed instant random access to any byte of game code or data, but it also meant that ROM contents lived on the far side of a connector that introduced capacitance, inductance, and signal integrity challenges. The electrical characteristics of cartridge edge connectors imposed real constraints on access timing, particularly as clock speeds increased throughout the 16-bit era. Games had to carefully balance the performance benefits of tight inner loops executing from ROM against the bandwidth limitations of fetching data across the cartridge interface.

The address space bottleneck represented the most fundamental constraint of all. An 8-bit processor with a 16-bit address bus can directly reference exactly 64 kilobytes of memory, full stop. The 6502 in the NES, the Z80 in the Sega Master System, and even the 65816 in the Super Nintendo all faced variations of this architectural ceiling. When game designers demanded worlds larger than this limit, hardware engineers responded with bank switching—a technique that divided the address space into fixed windows and provided hardware registers to dynamically remap which physical ROM or RAM banks appeared in those windows at any given moment. Bank switching transformed memory from a flat array into a paged hierarchy, but it introduced profound complexity into the programming model. Code executing in one bank could not directly call subroutines in another bank without carefully orchestrated switching sequences, and data structures could not span bank boundaries without elaborate pointer fixup logic.

The performance characteristics of memory access created a second tier of constraints that shaped programming patterns at the micro-optimization level. RAM, whether static or dynamic, provided symmetric read and write timing, but ROM imposed asymmetric access characteristics determined by the specific flash or mask ROM technology. Early EPROMs required wait states on the first byte access, making sequential reads faster than scattered random access. Video RAM presented even more exotic timing behavior because the video display controller (VDC) continually scanned VRAM to generate the raster display, creating contention windows where CPU access would stall until the next horizontal or vertical blanking interval. Programmers learned to schedule VRAM uploads during the brief microsecond windows of VBLANK and HBLANK, batching changes into tightly packed DMA transfers rather than trickling updates throughout the frame.

Cache mechanics, in the traditional sense of hardware-managed SRAM staging buffers, appeared late in the retro console timeline and only in the most sophisticated systems. The PlayStation and Sega Saturn introduced instruction and data caches measured in kilobytes, but these remained programmer-visible resources requiring explicit management rather than transparent performance accelerators. The absence of automatic caching in earlier consoles meant that memory access latency directly determined instruction throughput, with no hardware layer to hide the cost of cache misses. This reality forced programmers to develop an intimate understanding of hot code paths and data access patterns, manually organizing memory layouts to maximize locality of reference and minimize page-crossing penalties.

Direct Memory Access controllers emerged as the primary mechanism for moving bulk data without burning CPU cycles on byte-by-byte copy loops. DMA hardware could transfer kilobytes of sprite data, audio samples, or decompressed backgrounds from ROM or RAM to VRAM or audio buffers while the processor continued executing game logic. However, DMA operations were not free—they consumed memory bus bandwidth and often imposed blackout periods where the CPU could not access certain memory regions. The Genesis Yamaha YM2612 sound chip included its own DMA controller for streaming PCM samples, but triggering a transfer required carefully timed register writes and awareness of the sound chip's internal buffering state. Mismanaged DMA timing could produce audio glitches, sprite tearing, or complete system lockups if the CPU attempted to access memory mid-transfer.

The interaction between memory architecture and rendering systems created the most visible manifestation of these constraints. Tile-based graphics engines required nametables that mapped screen positions to tile indices, pattern tables containing the actual pixel data for each tile, and palette RAM defining the color mapping for each tile. The NES picture processing unit (PPU) imposed a strict separation between these memory regions, with the nametable and attribute table living in dedicated VRAM and the pattern table residing in either VRAM or cartridge CHR-ROM. Updating even a single tile on screen required writing to multiple memory regions in precise sequence during VBLANK, and exceeding the available blanking time would produce visible tearing artifacts as the electron gun caught up to the CPU's writes. Programmers developed elaborate buffering schemes where they queued updates throughout the frame and then batch-executed them during the next VBLANK window, effectively implementing a software-managed write-combining buffer.

## 2. Core Architecture & Mechanics

The memory map of a retro console defines the foundation upon which all software executes, establishing which address ranges correspond to ROM, RAM, hardware registers, and memory-mapped I/O devices. Consider the canonical NES memory map, which partitions the 6502's 64-kilobyte address space into carefully delineated regions. Addresses $0000 through $07FF contain the 2 kilobytes of internal work RAM, with this region mirrored three additional times through $1FFF to simplify address decoding logic. The PPU registers occupy $2000 through $2007, mirrored every 8 bytes through $3FFF. Controller and APU registers live at $4000 through $4017, followed by cartridge expansion ROM and SRAM from $4020 through $7FFF. The lower program ROM bank occupies $8000 through $BFFF, and the upper program ROM bank spans $C000 through $FFFF, with the interrupt vectors at $FFFA through $FFFF defining the entry points for NMI, reset, and IRQ handlers.

This memory map reveals the architectural philosophy underlying the NES design: minimize onboard memory and push storage responsibility to the cartridge. The CPU cannot execute code from RAM without first copying it from ROM, and the 2-kilobyte RAM envelope forces programmers to maintain ruthlessly compact data structures. Global variables compete with the stack for the same tiny allocation, and stack overflows represent a constant hazard for deep recursion or large automatic variable allocations. The mirroring of RAM and registers throughout the address space reflects the incomplete address decoding used to reduce gate count in the console's discrete logic, but it also creates subtle bugs when programmers accidentally reference mirrored addresses and later port code to systems with different mirroring behavior.

Bank switching hardware transforms this flat memory map into a paged virtual space by introducing mapper chips that intercept address and data lines between the CPU and cartridge ROM. The MMC1 mapper, used in countless NES titles, provides switchable 16-kilobyte program ROM banks and switchable 4-kilobyte or 8-kilobyte character ROM banks. Writing specific bit sequences to designated address ranges triggers bank switches, with the mapper decoding the written values to determine which physical ROM bank to map into the CPU's address space. The MMC3 mapper, deployed in later high-profile releases, extends this model with finer-grained 8-kilobyte program ROM banks, programmable mirroring control, and a scanline counter that can generate IRQ interrupts for mid-frame effects.

The programming model for bank switching requires careful management of code and data placement across banks. Subroutines that must be callable from any bank context live in a fixed bank that remains permanently mapped, typically the last 16-kilobyte bank in the address space. Interrupt handlers must reside in fixed banks because the 6502 fetches the interrupt vector from a fixed address and cannot dynamically remap during the interrupt dispatch sequence. Game code organizes itself into logical modules—one bank for the title screen, another for level 1, another for level 2—with explicit switching code at module boundaries. Data structures spanning multiple banks use bank-relative pointers or indirection tables, accepting the performance penalty of additional dereferences in exchange for breaking the 64-kilobyte barrier.

The Super Nintendo expanded the address space dramatically through its 65816 processor, which supports 24-bit addressing for a 16-megabyte linear address space. However, the architecture retained bank-based organization for backward compatibility with 6502 assembly patterns and to accommodate the diverse mapper configurations found in SNES cartridges. The SNES memory map divides address space into banks of 64 kilobytes each, with banks $00 through $3F and $80 through $BF mapping to system RAM in the lower 8 kilobytes, hardware registers in the next region, and cartridge ROM in the upper 32 kilobytes. Banks $40 through $7F and $C0 through $FF provide contiguous ROM access for large games, while banks $7E and $7F contain the full 128 kilobytes of work RAM without mirroring or windowing.

This expanded address space liberated SNES programmers from the constant bank juggling required on the NES, but it introduced new complexities around addressing modes and register widths. The 65816 supports both 8-bit and 16-bit register modes, switchable via processor status flags, and the size of memory operands changes depending on the current mode. Code must carefully track whether the accumulator and index registers are in 8-bit or 16-bit mode, and mode switches incur cycle penalties. The SNES also introduced DMA channels that could transfer data from ROM or RAM to VRAM, CGRAM (palette RAM), or OAM (sprite attribute memory) without CPU intervention, but each DMA channel required configuration of source address, destination address, transfer size, and addressing mode through a series of hardware registers.

The Sega Genesis presents a heterogeneous memory architecture driven by its dual-processor design. The Motorola 68000 main CPU addresses a flat 16-megabyte space using 24-bit addresses, with 64 kilobytes of RAM mapped at $FF0000 through $FFFFFF and cartridge ROM occupying $000000 through the ROM size limit. The Zilog Z80 coprocessor, inherited from the Sega Master System for backward compatibility, lives in its own 64-kilobyte address space with 8 kilobytes of dedicated RAM and a bank switching window for accessing the 68000's memory map. The video display processor (VDP) maintains separate address space for VRAM (64 kilobytes), CRAM (128 bytes of palette data), and VSRAM (80 bytes of vertical scroll data), all accessible only through indirect register access or DMA.

The Genesis VDP DMA controller operates in three modes, each with distinct use cases and timing characteristics. Memory-to-VRAM DMA transfers data from 68000 ROM or RAM to VRAM at a rate of approximately 16.7 megabytes per second during active display and faster during blanking. VRAM fill mode initializes VRAM regions with a constant value, useful for clearing planes or stamping repeated patterns. VRAM copy mode duplicates VRAM regions internally without involving the 68000 bus, enabling fast tile manipulation. Each mode requires setting up source address, destination address, length, and transfer type through a sequence of VDP register writes, and the programmer must ensure that DMA operations complete before attempting further VDP access to avoid data corruption.

The PlayStation introduced a radically different memory architecture that reflected the transition from ROM cartridges to CD-based storage. The main CPU, a MIPS R3000-derived core, addresses 2 megabytes of main RAM, 1 megabyte of video RAM, and various memory-mapped I/O regions through a 32-bit address space. The absence of directly executable cartridge ROM meant that all game code and data loaded from CD into main RAM, introducing load times but eliminating the bank switching and ROM access penalties that plagued cartridge systems. The MIPS architecture includes a 4-kilobyte instruction cache and a 1-kilobyte data cache, representing the first true hardware-managed cache system in mainstream console gaming.

Cache behavior on the PlayStation requires explicit programmer awareness despite the automatic management. The instruction cache operates as a direct-mapped cache with 256 lines of 16 bytes each, meaning that code addresses mapping to the same cache line will thrash the cache and degrade performance. The data cache provides write-through semantics, ensuring that writes propagate immediately to main RAM, but this eliminates the write-combining benefits of a write-back cache. The CPU provides cache control instructions for invalidating cache lines and managing coherency with DMA operations, and programmers learned to organize hot code paths to minimize cache conflicts and place performance-critical loops within single cache lines.

DMA on the PlayStation extends beyond simple memory-to-memory transfers into a sophisticated infrastructure for feeding the GPU, CD-ROM controller, and audio processor. The GPU DMA channel streams display lists from main RAM to the GPU command FIFO, allowing the CPU to build rendering commands in memory and trigger asynchronous submission. The CD-ROM DMA channel transfers sectors from the CD controller's buffer into main RAM, with the controller automatically generating DMA requests as sectors arrive. The SPU (sound processing unit) DMA channel uploads sample data and reverb parameters to the SPU's 512-kilobyte sound RAM. Each DMA channel includes a control register defining transfer direction, synchronization mode, and chunk size, along with base address and block count registers.

The timing characteristics of DMA operations interact with the overall system bus architecture to create complex performance puzzles. The PlayStation uses a unified memory architecture where the CPU, GPU, CD-ROM controller, and SPU all contend for access to main RAM over a shared bus. A large DMA transfer can starve the CPU of memory bandwidth, causing instruction fetch stalls and performance degradation. The GPU DMA operates in burst mode, transferring an entire display list in one contiguous operation, while the CD-ROM DMA uses slice mode, transferring one sector every few milliseconds as data arrives from the disc. Programmers must balance DMA scheduling to ensure that audio samples upload in time to prevent buffer underruns, that GPU display lists submit before the next frame deadline, and that CD data streams maintain sufficient buffering to hide seek latencies.

The interaction between storage medium and memory hierarchy profoundly influenced game design patterns across console generations. Cartridge systems benefited from instant random access to any byte of ROM, enabling non-linear game structures where players could warp between levels without load penalties. CD-based systems imposed seek times measured in seconds, forcing designers to adopt hub-world structures, hide load times behind cinematic sequences, or carefully preload assets into RAM buffers. The PlayStation's 2-megabyte main RAM became a precious resource for asset caching, with games implementing LRU eviction schemes, predictive preloading based on player movement, and aggressive texture compression to maximize the working set.

## 3. High-Performance Optimization & Failure Modes

Optimizing memory usage on retro consoles demands a holistic understanding of the interplay between code layout, data structure organization, access patterns, and hardware timing. The most fundamental optimization involves ruthlessly minimizing the working set of global variables and stack usage to fit within the tiny RAM allocations. NES programmers adopted a practice called zero-page optimization, where the most frequently accessed variables lived in the first 256 bytes of RAM, enabling the use of shorter, faster zero-page addressing modes that required only one operand byte instead of two. The zero page also served as the target for indirect addressing modes, making it the natural home for pointer variables and index registers during structure traversal.

Bank switching optimization required careful profiling to identify hot code paths and ensure they resided within the same bank or in fixed banks accessible without switching. Excessive bank thrashing could consume dozens of cycles per switch, and the cumulative overhead degraded performance noticeably. Profiling tools remained primitive in the retro era, so programmers developed intuition through cycle counting and manual instrumentation, inserting timing markers that toggled unused PPU registers to generate visible scanline artifacts that revealed execution timing. Modern retro development benefits from cycle-accurate emulators with integrated debuggers that provide instruction-level profiling and memory access heatmaps, enabling quantitative optimization rather than guesswork.

The organization of ROM data to maximize sequential access patterns exploited the burst-read characteristics of some ROM technologies and reduced the addressing complexity of mapper hardware. Graphics data organized into contiguous tile sets allowed the PPU to fetch sequential pattern data without jumping across ROM banks. Level data compressed using run-length encoding or delta encoding reduced ROM footprint while maintaining fast decompression performance, with programmers carefully tuning the compression ratio against the CPU cost of decompression. Some games employed procedural generation techniques to synthesize level geometry from compact seed data, trading ROM space for CPU cycles and accepting the constraint that procedurally generated content must remain reproducible from the same seed.

VRAM management represented one of the most challenging optimization domains because of the strict timing constraints around blanking intervals. The NES PPU provides approximately 2,270 CPU cycles during VBLANK for VRAM updates, and a single tile update requires several register writes and at least two bytes of data transfer. Large-scale screen updates such as scrolling transitions or screen wipes had to spread across multiple frames, with the game logic carefully synchronizing state updates to avoid visual glitches. Programmers developed VRAM buffering systems where game code enqueued update requests into a queue throughout the frame, and a dedicated VBLANK handler dequeued and executed as many updates as time permitted, deferring any overflow to the next frame.

DMA optimization on 16-bit systems required balancing transfer granularity against synchronization overhead. The SNES DMA controller supports eight channels with programmable priority, and setting up a DMA transfer involves writing to multiple registers per channel. For small transfers, the overhead of DMA setup exceeds the time saved versus CPU-driven copying, making direct memory writes faster. The crossover point depends on the specific data and addressing mode, but generally, transfers smaller than 32 bytes favor CPU copying, while larger transfers benefit from DMA. Programmers learned to batch small updates into larger contiguous transfers when possible, reorganizing data structures to improve spatial locality and enable wider DMA operations.

The failure modes associated with memory management on retro consoles range from subtle graphical glitches to catastrophic system crashes. Writing to VRAM outside of blanking intervals produces tearing artifacts as the PPU fetches partially updated data mid-scanline, resulting in corrupted tiles or attribute bytes that persist until the next clean update. Buffer overruns in RAM overwrite adjacent data structures, causing erratic behavior that may not manifest until frames later when the corrupted data influences game logic. Stack overflows silently overwrite global variables or even return addresses, producing crashes that appear to originate from unrelated code due to the corrupted call stack.

Bank switching errors manifest as jumps to incorrect code when a subroutine call crosses a bank boundary without proper switching logic, or as data corruption when code reads from the wrong bank's data region. These bugs prove notoriously difficult to debug because they depend on complex state involving which bank was active when the erroneous access occurred. The lack of memory protection hardware in retro consoles means that wild pointers can write anywhere in the address space, including hardware registers, potentially reconfiguring the PPU, APU, or mapper in ways that produce bizarre symptoms far removed from the root cause.

DMA hazards arise when the CPU attempts to access memory during an active DMA transfer, producing bus contention that can corrupt data or lock up the system. The Genesis VDP DMA requires careful timing to ensure that transfers complete before the next frame starts, and exceeding the VBLANK window can cause the DMA to overlap with active display, resulting in visible artifacts. The PlayStation DMA system includes busy flags and interrupt support to enable safe synchronization, but failing to poll or wait for completion before accessing DMA source or destination buffers introduces race conditions that manifest as intermittent corruption.

Cache coherency bugs on the PlayStation emerge when DMA operations bypass the cache, leaving stale data in the cache that no longer reflects main RAM contents. After a GPU DMA upload, the CPU cache may still contain old copies of the display list data, and subsequent CPU reads return stale values. The correct pattern involves invalidating the data cache region corresponding to the DMA buffer before reading it, using the MIPS cache control instructions. Similarly, after the CPU writes to a buffer destined for GPU DMA, the programmer must ensure cache write-through has completed before initiating the DMA, or the GPU receives incomplete data.

The most sophisticated optimization strategies involved working within the constraints rather than fighting them, designing data structures and algorithms specifically tailored to the memory hierarchy characteristics. Tile-based games naturally aligned with the VRAM structure of retro consoles, and programmers learned to represent game state as tile maps rather than pixel buffers, deferring the translation to pixels to the hardware PPU. Metatiling systems grouped common tile patterns into reusable clusters, reducing the number of individual tile updates required during scrolling or animations. Double buffering techniques maintained multiple copies of critical data structures, allowing the CPU to build the next frame's state in one buffer while hardware scanned the current frame from another buffer, eliminating tearing at the cost of doubled RAM usage.

Compression and decompression algorithms tuned for the specific instruction sets and memory patterns of retro CPUs enabled games to store more data in limited ROM space. Run-length encoding proved ideal for background graphics with large uniform regions, while LZ77-family algorithms compressed diverse data types with reasonable decompression performance. Some games employed lossy compression for graphics and audio, accepting minor quality degradation in exchange for dramatically reduced storage requirements. The SNES's Mode 7 affine transformation hardware enabled fake 3D effects without requiring full 3D model storage, instead rotating and scaling 2D tilemaps to simulate perspective projection.

The memory constraints that defined retro console development ultimately drove innovation in software engineering practices that remain relevant today. Programmers learned to reason precisely about resource consumption, to profile and optimize hot paths, to design data structures with cache behavior in mind, and to build systems that gracefully degraded under resource pressure. These skills, honed in the crucible of kilobyte RAM budgets and microsecond timing windows, represent the embodiment of constrained optimization—extracting maximum expressive power from minimal hardware resources through deep understanding of the underlying architecture.
