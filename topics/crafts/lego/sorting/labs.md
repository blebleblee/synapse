# Operational Verification Labs: Sorting

## Objective & Operational Lab Setup

The operational verification of sorting algorithms through physical Lego construction transforms abstract computational theory into tangible mechanical systems where data movement becomes visible brick displacement, comparisons become structural decision points, and algorithmic complexity manifests as physical build complexity and operational cycle time. This laboratory sequence trains the practitioner to construct, validate, and empirically measure three fundamental sorting mechanisms—bubble sort, selection sort, and merge sort—using Lego Technic components to implement mechanical comparators, indexed storage arrays, and transfer mechanisms that execute algorithmic logic through deterministic physical motion.

The pedagogical foundation rests on a critical insight: sorting algorithms are not merely mathematical abstractions but physical processes constrained by the same principles governing mechanical systems—discrete state transitions, energy expenditure per operation, parallelization limits imposed by actuator count, and failure modes arising from tolerance stack-up and mechanical wear. By constructing sorting machines that manipulate physical tokens through comparison-driven pathways, the practitioner develops intuition for algorithmic efficiency that transcends code execution and extends into hardware design, robotic manipulation, and automated material handling systems.

Your laboratory workstation requires a curated Lego inventory optimized for algorithmic construction. Begin with a baseplate foundation of at least 32×32 studs to provide stable mounting for multi-stage mechanisms. Stock twenty-four 1×8 Technic bricks with through-holes on 1-stud centers to construct indexable storage arrays where each position represents an array element. Acquire eight linear actuators in the form of Technic rack-and-pinion assemblies (part 3743 rack bars driven by 87407 worm gears through 99021 linear actuator housings) to implement bidirectional token transfer. Secure twelve 2×4 liftarms with perpendicular axle holes to fabricate comparison gates and selection mechanisms. Provision thirty-two friction pins and twenty Technic axles in 4-stud and 6-stud lengths to establish pivot points and rotational transfer elements.

The token system representing sortable data elements must encode comparable values through physical attributes while remaining mechanically manipulable. Construct tokens from 2×2 bricks with vertical 1×1 round plates stacked to varying heights encoding integer values from one to eight units. The height differential allows gravity-assisted mechanical comparison through ramp-based height gauges and provides visual confirmation of sorted order. Alternatively, employ color-coded 1×2 Technic bricks with axle holes where color maps to numeric value through a predefined encoding scheme, enabling mechanical comparison through color-sensitive optical barriers constructed from 1×1 transparent round plates acting as light pipes. Establish a modular storage array representing the sortable data structure in memory. Construct a horizontal assembly of eight 1×8 Technic bricks spaced at 3-stud intervals, creating eight discrete positions indexed zero through seven. Establish baseline performance by measuring manual direct-placement sorting time—the duration required to sort eight tokens by hand through visual comparison without mechanical assistance—typically ranging from eight to twelve seconds for trained practitioners. Mechanical sorting implementations exceeding 300% of baseline duration indicate design inefficiency requiring mechanical optimization or algorithmic reconsideration.

## Exercise 1: Foundational Practical Implementation

Construct a functional bubble sort mechanism that physically implements the canonical two-loop comparison algorithm through mechanical token movement across a linear array. Bubble sort's pedagogical value lies in its mechanical simplicity—every comparison produces immediate adjacent-element action without requiring complex indexing or memory structures, making it ideally suited for initial hands-on algorithmic verification despite its quadratic time complexity rendering it impractical for large-scale computational applications.

Begin array construction by establishing an eight-position horizontal track using the modular storage array specification from setup. Orient the array left-to-right with position zero at the left terminus, matching conventional array indexing notation. The bubble sort algorithm executes through repeated passes traversing the array from left to right, comparing each adjacent pair and swapping positions if the left element exceeds the right element. After the first complete pass, the largest element necessarily occupies the rightmost position through successive rightward swaps, analogous to a bubble rising through liquid—hence the algorithm's name. Subsequent passes repeat this process on progressively shorter unsorted subarray lengths, with each pass guaranteeing correct placement of one additional element at the sorted region's boundary.

Construct the comparison-swap module as a mobile assembly that traverses the array executing the pairwise comparison logic. Build a base platform from a 4×10 plate that spans three array positions, with the central position aligned to the current comparison pair. Mount the see-saw comparator mechanism at the platform's center, oriented perpendicular to the array axis. Install input ramps on the left and right sides of the comparator, angled downward toward the comparison junction at 15 degrees to provide gravity-assisted token entry. Fabricate output return chutes that deposit compared tokens back into the array positions, with the critical routing logic implementing the swap condition—if left token exceeds right token, the output chutes cross paths so the heavier token returns to the right position and lighter token to the left position, executing the swap. If left token is less than or equal to right token, chutes return tokens to their original positions, executing the no-swap conditional branch.

Operationally execute the first bubble sort pass through manual actuation following this deterministic protocol. Position the comparison-swap module at array positions zero and one. Extract tokens from both positions using the sliding extraction mechanism and simultaneously place them on the input ramps. The comparator automatically routes tokens according to swap logic, depositing them back into positions zero and one in potentially swapped order. Advance the comparison-swap module one position rightward to compare positions one and two. Repeat the extract-compare-deposit sequence. Continue this process through position pairs two-three, three-four, four-five, five-six, and six-seven, completing the first full pass. The largest-value token now occupies position seven regardless of initial configuration—this invariant provides a critical verification checkpoint confirming correct swap logic implementation.

Execute the second pass identically but terminate at position pair five-six since position seven already holds the maximum element and requires no further comparison. The third pass terminates at four-five. Continue passes of decreasing length until the seventh pass compares only positions zero and one. At this termination point, the array exists in fully sorted ascending order from position zero to position seven.

Measure and document operational metrics for empirical algorithm analysis. Count the total number of comparison operations executed—for an eight-element array, bubble sort performs 7 + 6 + 5 + 4 + 3 + 2 + 1 = 28 comparisons in the worst case (reverse-sorted input) and best case with your current implementation, since the basic bubble sort lacks the optimization detecting already-sorted arrays. Calculate cycle time by measuring elapsed duration from first comparison to final verification. Record mechanical failure events including token jamming in chutes, comparator see-saw sticking in intermediate positions, or token ejection from array positions during transfer. These failure modes reveal tolerance stack-up issues and friction points requiring mechanical refinement.

Conduct three empirical trials with distinct input configurations to validate algorithm correctness across representative data distributions. Trial one employs random input order: position values [5, 2, 8, 1, 7, 3, 6, 4]. Trial two uses reverse-sorted input representing worst-case scenario: [8, 7, 6, 5, 4, 3, 2, 1]. Trial three tests nearly-sorted input with single inversion: [1, 2, 3, 4, 6, 5, 7, 8]. All three trials must produce identical final sorted output [1, 2, 3, 4, 5, 6, 7, 8] despite varying operational behavior during execution. The reverse-sorted trial will execute maximum swap operations as every comparison triggers token exchange, producing maximum mechanical wear on the comparator pivot and maximum cycle duration. The nearly-sorted trial executes only one swap but still performs all 28 comparisons, revealing the algorithm's inability to exploit existing order without optimization modifications.

Implement the early-termination optimization transforming basic bubble sort into an adaptive algorithm. Add a binary state flag mechanism using a 1×2 Technic brick mounted on a vertical axle with two rotational positions—flag-raised indicates "swap occurred this pass" and flag-lowered indicates "no swaps this pass." Reset the flag to lowered position at each pass initiation. During any comparison-swap operation that executes a swap, manually rotate the flag to raised position. At pass completion, inspect flag state: if lowered (no swaps occurred), the array is already sorted and algorithm terminates immediately without executing remaining passes. If raised, reset flag to lowered and continue with next pass. Re-execute trial three with this optimization—the algorithm now terminates after a single pass plus one verification pass, reducing comparison count from 28 to 14 and halving cycle duration, demonstrating the substantial performance impact of algorithm optimization even within the same asymptotic complexity class.

Analyze mechanical efficiency by calculating the ratio of useful work to total mechanical operations. Each comparison operation consumes physical time and mechanical energy (manual actuation effort) but only swaps that correct element ordering constitute progress toward the sorted state. In the random-input trial, count actual swaps executed versus total comparisons performed—typically 12-16 swaps occur among 28 comparisons, yielding 43-57% useful work ratio. The reverse-sorted worst case executes swaps on every comparison except the final pass, achieving 96% useful work ratio despite maximum cycle duration. This counterintuitive result—worst-case input produces highest mechanical efficiency—illustrates the distinction between time complexity and operational efficiency, a critical insight for embedded systems and robotic applications where energy expenditure often dominates performance optimization criteria.

## Exercise 2: Parameter Variation & Empirical Analysis

Construct a selection sort mechanism implementing an alternative algorithmic strategy based on global minimum-finding rather than local pairwise swapping. Selection sort's mechanical implementation requires non-local array access and index tracking, introducing architectural complexity absent from bubble sort's purely local operations, but achieves deterministic comparison count independent of input configuration—a property valuable in real-time systems requiring bounded execution duration.

Selection sort operates through iterative minimum extraction across progressively smaller unsorted subarrays. The algorithm maintains a sorted-unsorted boundary initially positioned at array index zero with all elements unsorted. Each iteration scans the unsorted region identifying the minimum element's index position, then swaps that element with the element at the boundary position, advancing the boundary one position rightward. After n-1 iterations on an n-element array, the boundary reaches the final position and sorting completes, as the last remaining unsorted element must be the maximum value and already occupies its correct position.

Fabricate the minimum-finder module as the core mechanical component executing the scan-and-identify logic. Construct a movable scanning platform from a 6×8 plate that traverses the array accessing each position sequentially. Mount a token holding bracket at the platform's center capable of retaining one token in vertical orientation—this bracket serves as the "current minimum" register. Install a mechanical comparison gate at the platform's front edge using the see-saw comparator design from Exercise 1, but modify the output routing to implement selection logic rather than swap logic. The left input channel receives the current minimum token from the holding bracket. The right input channel receives the scanned array element. If the scanned element is less than the current minimum, the comparator deposits the scanned element into the holding bracket (updating current minimum) and returns the former minimum to the scanned array position. If the scanned element is greater than or equal to current minimum, both tokens return to their original positions.

Execute the first selection sort iteration through this operational protocol. Position the scanning platform at the sorted-unsorted boundary, initially array position zero. Extract the position-zero token and place it in the holding bracket, initializing the current minimum register. Advance the platform to position one and execute the comparison operation between the holding bracket token and the position-one token. The comparator automatically updates the holding bracket if a smaller token is discovered. Advance to position two and repeat comparison. Continue scanning through position seven, at which point the holding bracket contains the global minimum element from the entire array. Extract the token currently at position zero and extract the minimum token from the holding bracket, then swap their physical locations—the minimum now occupies position zero and the former position-zero element occupies the index where minimum was discovered. Advance the sorted boundary one position rightward to position one. The first iteration completes with the absolute minimum element correctly placed.

The second iteration repeats this process starting from the new boundary position one, scanning positions one through seven to find the second-smallest element and swapping it into position one. Subsequent iterations continue with progressively shorter scan ranges until the seventh iteration places the second-largest element in position six, at which point the remaining element in position seven is necessarily the maximum and sorting completes.

Measure operational metrics revealing selection sort's distinct performance characteristics. Count total comparisons across all iterations: 7 + 6 + 5 + 4 + 3 + 2 + 1 = 28 comparisons identical to bubble sort, but note the critical difference—selection sort always executes exactly 28 comparisons regardless of input order, while optimized bubble sort varies from 7 comparisons (already-sorted input) to 28 (reverse-sorted input). Count swap operations separately: selection sort executes exactly 7 swaps (one per iteration) regardless of input configuration, while bubble sort executes 0 to 28 swaps depending on initial order. This deterministic operation count makes selection sort preferable in hard real-time embedded systems despite identical worst-case time complexity.

Conduct comparative empirical trials measuring cycle duration for identical input configurations tested in Exercise 1. Execute selection sort on random input [5, 2, 8, 1, 7, 3, 6, 4], reverse-sorted input [8, 7, 6, 5, 4, 3, 2, 1], and nearly-sorted input [1, 2, 3, 4, 6, 5, 7, 8]. Record cycle duration for each trial and calculate the variance across the three trials. Selection sort typically exhibits lower cycle time variance (standard deviation 5-10% of mean) compared to bubble sort (standard deviation 15-25% of mean) due to its consistent comparison and swap counts, demonstrating the predictability advantage despite marginally longer mean cycle time arising from the additional mechanical complexity of the scanning platform and minimum-register management.

Analyze the mechanical design tradeoffs between bubble sort and selection sort implementations. Bubble sort's comparison-swap module requires simpler construction with fewer moving parts—a single mobile platform traversing adjacent pairs—resulting in lower mechanical complexity and reduced failure rate from component interaction. However, bubble sort's adaptive behavior depending on input order introduces operational unpredictability complicating timing analysis. Selection sort's minimum-finder module requires additional mechanical state (the holding bracket register) and longer traverse distances per iteration (full unsorted-region scans versus single-position increments), increasing mechanical complexity and component count. Yet this complexity purchases deterministic behavior valuable for mission-critical applications where worst-case guarantees outweigh average-case performance.

Extend empirical analysis by testing algorithmic behavior under scaled input sizes. Reconstruct both sorting machines for a sixteen-position array, requiring expanded baseplates and doubled token inventory. Execute bubble sort and selection sort on sixteen-element random input arrays, measuring cycle duration for each algorithm. Bubble sort comparison count scales quadratically: 15 + 14 + 13 + ... + 1 = 120 comparisons for sixteen elements versus 28 for eight elements, representing a 4.3× increase for 2× input size consistent with O(n²) growth. Selection sort scales identically to 120 comparisons. Measure actual cycle durations and observe the scaling relationship—cycle time typically increases super-linearly (greater than 4.3×) due to increased mechanical traverse distances and accumulated friction losses in longer array structures, revealing how physical system constraints compound algorithmic complexity in embodied computation.

Implement a hybrid sorting strategy exploiting both algorithms' strengths. Use selection sort for the first n/2 iterations to deterministically place the smallest half of elements in correct positions with guaranteed operation counts, then switch to optimized bubble sort for the remaining partially-sorted array where early termination optimization can exploit existing order. Measure hybrid algorithm cycle time on the nearly-sorted sixteen-element input where this strategy should outperform either pure algorithm, demonstrating the systems engineering principle that optimal solutions often combine multiple approaches tailored to different operational regimes rather than dogmatically applying a single technique universally.

## Exercise 3: Stress Testing, Boundary Failure & Recovery Protocol

Construct a merge sort implementation representing a fundamentally distinct algorithmic paradigm—divide-and-conquer recursion—that achieves O(n log n) time complexity superior to the quadratic algorithms previously examined. Merge sort's mechanical implementation poses substantial architectural challenges requiring parallel temporary storage, recursive subdivision logic, and the merge operation's complex interleaving of sorted sequences, but the resulting performance advantage becomes empirically measurable at moderate input scales and conceptually illuminates the relationship between algorithmic design and physical system architecture.

Merge sort operates through recursive subdivision of the input array into progressively smaller subarrays until reaching base-case subarrays of length one (trivially sorted), then recursively merging adjacent sorted subarrays into larger sorted subarrays until reconstructing the complete sorted array. The merge operation forms the algorithm's core: given two sorted input sequences, produce a single sorted output sequence by repeatedly comparing the smallest unprocessed element from each input and selecting the lesser element for output advancement. This merge operation executes in linear time proportional to total element count and preserves sortedness through the comparison-driven selection logic.

Architectural design for merge sort demands temporary storage capacity equaling input array size, as merge operations cannot execute in-place without destroying input sequences before merge completion. Construct a dual-plane storage architecture using stacked baseplates separated by 8-stud vertical clearance. The lower plane hosts the primary array storage following the eight-position modular specification. The upper plane provides eight auxiliary positions serving as merge buffers and temporary storage during recursive operations. Install vertical token lifts at each primary position using rack-and-pinion assemblies (3743 rack, 3648 gear) cranked by 4-length axles, enabling controlled token elevation from primary to auxiliary positions and descent from auxiliary to primary positions, implementing the physical equivalent of array copy operations.

Implement merge sort's recursive structure through a manual execution protocol that explicitly manages the recursion stack via physical position markers. Fabricate eight 1×1 colored plates serving as subdivision markers—four red markers indicating "left subarray boundary" and four blue markers indicating "right subarray boundary." The initial state places a red marker at position zero and blue marker at position seven, representing the full array as one unsorted subdivision. Execute the first recursive subdivision by calculating the midpoint (position three), placing a red marker at position four (beginning of right subdivision) and blue marker at position three (end of left subdivision), partitioning the array into positions [0-3] and [4-7]. Recursively subdivide the left partition by placing markers at positions [0-1] and [2-3], then subdivide again to reach base case [0], [1], [2], [3] single-element subarrays. Repeat this subdivision process for the right partition reaching base cases [4], [5], [6], [7]. At maximum recursion depth, eight marker pairs indicate eight single-element subarrays each trivially sorted.

Execute the first merge operation combining base cases [0] and [1] into a sorted subarray spanning positions [0-1]. Position the mobile merge module—a dual-input, single-output comparison mechanism—at positions zero and one. The merge module employs two parallel input channels feeding the standard see-saw comparator, with a single output chute depositing selected tokens sequentially into the auxiliary storage plane at buffer positions corresponding to the output range. Extract tokens from positions zero and one simultaneously into the comparison inputs. The comparator selects the smaller token and deposits it to auxiliary buffer position zero. Extract the remaining token from its primary position and deposit to auxiliary buffer position one—the merge completes with a sorted two-element sequence in the auxiliary buffer. Transfer both tokens from auxiliary buffer back to primary positions zero and one using the vertical lifts, executing the copy-back operation. Repeat this merge process for base pairs [2-3], [4-5], and [6-7], producing four sorted two-element subarrays in the primary plane.

Advance to the second merge level combining sorted two-element subarrays into sorted four-element sequences. Merge operation complexity increases as input sequences exceed single elements, requiring interleaved comparison and selection tracking which input sequence contributes each output element. Position the merge module spanning positions [0-3] to merge sorted subarrays [0-1] and [2-3]. Initialize two index markers (1×1 round plates) at positions zero and two indicating the current unprocessed element in each input subarray. Execute the merge loop: compare elements at the two marked positions, select the smaller element, deposit to the next auxiliary buffer position (initially buffer zero), advance that input's index marker one position. Repeat until one input subarray exhausts (index marker advances beyond subarray boundary), then copy all remaining elements from the non-exhausted input to the output buffer maintaining sequential order. Transfer the merged four-element sorted sequence from auxiliary buffer back to primary positions [0-3]. Repeat for subarray pair [4-7], yielding two sorted four-element sequences.

Execute the final merge operation combining the two sorted four-element subarrays [0-3] and [4-7] into the complete sorted eight-element array. This merge requires the full eight-position auxiliary buffer and executes the longest comparison sequence. Initialize index markers at positions zero and four. Execute the merge loop identically to the four-element merge but across the doubled span, transferring elements through the comparator to auxiliary buffer with index marker advancement. Upon completion, the auxiliary buffer contains the fully sorted array. Transfer all eight elements from auxiliary back to primary positions [0-7], completing the merge sort execution.

Count operational metrics revealing merge sort's efficiency advantage. Total comparison count for eight elements: first merge level executes four two-way merges with 2 comparisons each (8 total), second level executes two four-way merges with 4 comparisons each (8 total), final level executes one eight-way merge with 7 comparisons (7 total), yielding 23 total comparisons versus 28 for bubble sort and selection sort. This comparison count advantage increases dramatically with input size scaling—sixteen elements require approximately 49 comparisons for merge sort versus 120 for quadratic algorithms, empirically demonstrating the O(n log n) versus O(n²) complexity gap. Measure cycle duration noting that merge sort's parallel storage requirements and complex merge logic introduce mechanical overhead offsetting some comparison advantage at small scales—eight-element merge sort typically executes in 90-110% of bubble sort duration despite fewer comparisons, but sixteen-element merge sort completes in 65-75% of bubble sort duration as complexity advantage overcomes mechanical overhead.

Stress test merge sort's boundary conditions by constructing failure scenarios exposing design weaknesses. Execute merge sort on a reverse-sorted sixteen-element input [16, 15, 14, ..., 2, 1] where maximum merge interleaving occurs—each merge operation exhausts both input subarrays simultaneously maximizing comparison count within the n log n bound. This configuration produces maximum mechanical wear on the comparator see-saw mechanism and maximum token transfer count through vertical lifts. ## Operational Reference Guide & Diagnostic Checklist

### Algorithm Selection Decision Matrix

When confronting a sorting task requiring mechanical implementation, algorithm selection depends on multiple constraint dimensions beyond asymptotic time complexity. Evaluate each criterion systematically before committing to implementation architecture.

**Bubble sort optimal conditions:** Input size n ≤ 12 elements where quadratic growth remains manageable. Predictably low swap counts anticipated (nearly-sorted or mostly-ordered inputs) enabling early termination optimization to achieve near-linear performance. Mechanical simplicity prioritized over absolute performance, such as educational demonstrations or resource-constrained environments with limited component budgets. Single-pass streaming constraints where elements arrive sequentially and must be integrated incrementally into sorted order. No auxiliary storage available beyond minimal swap buffers.

**Selection sort optimal conditions:** Hard real-time constraints requiring deterministic worst-case operation counts for timing analysis and deadline guarantees. Input distribution unknown or adversarial where worst-case performance must be assumed. Memory-constrained environments where auxiliary storage beyond single-element registers is unavailable. Write-minimization critical such as EEPROM or flash memory contexts where swap operation counts directly impact hardware lifespan—selection sort's guaranteed n-1 swaps versus bubble sort's potential O(n²) swaps becomes decisive.

**Merge sort optimal conditions:** Input size n ≥ 16 where O(n log n) advantage over quadratic algorithms produces measurable performance gains. Auxiliary storage capacity equal to input size is available through dual-plane architecture or external buffers. Stable sorting required preserving relative order of equal-value elements—merge sort achieves stability naturally through left-input priority during comparisons, while comparison-based quadratic sorts require explicit stability mechanisms. Parallelization opportunities exist allowing concurrent execution of independent merge operations across subtrees, though mechanical Lego implementations typically execute serially due to actuator count limits.

### Comparator Calibration Protocol

The see-saw comparator mechanism represents the critical decision element whose reliability determines overall sorting correctness. Systematic calibration ensures consistent comparison outcomes across the operational envelope.

**Static balance verification:** Remove all tokens from the comparator. Place the see-saw arm in horizontal neutral position. Release gently and observe motion—the arm should remain stationary or oscillate minimally (less than 3-degree deviation) before settling to rest within 2 seconds. Excessive settling time indicates bearing friction requiring lubrication. Consistent deflection toward one side indicates mass imbalance—add 0.5-gram balancing mass (single 1×1 round plate) to the lighter platform side at maximum moment arm to correct.

**Dynamic response testing:** Construct two calibration tokens of maximum height differential (8 units versus 1 unit). Place simultaneously on comparator platforms from identical drop height (6 studs above platform surface) to ensure synchronized loading. Measure elapsed time from token contact to final stable output channel routing—should complete within 1.5 seconds. Repeat ten trials measuring mean response time and standard deviation. Standard deviation exceeding 0.3 seconds indicates inconsistent friction or binding in the pivot mechanism requiring disassembly and cleaning.

**Discrimination threshold measurement:** Construct token pairs with progressively smaller height differentials: 7 units versus 8 units (1-unit differential), 6.5 units versus 7.5 units (achieved through half-plate stacking), down to minimum mechanical resolution. Execute ten trials per differential measuring comparison outcome accuracy. The minimum reliably discriminated differential defines the comparator's resolution limit—typically 0.5 units (one and a half plates height) for friction-pin pivots, improving to 0.33 units (single plate) with bushing-based pivots. Input data encodings must respect this resolution limit maintaining separation exceeding the discrimination threshold between adjacent sortable values.

### Transfer Mechanism Diagnostic Procedures

Token extraction, movement, and insertion operations form the mechanical equivalent of memory access and data movement instructions. Systematic diagnosis isolates failure points in the transfer pathway.

**Extraction jam diagnosis:** If token extraction from array position fails to dislodge token cleanly, measure lateral clearance between token and retaining walls using a Technic axle as feeler gauge—clearance should measure 0.15 to 0.25 studs. Insufficient clearance causes friction binding requiring wall repositioning. Excessive clearance allows token tipping during extraction causing corner catches—install chamfered guide plates (1×2 slopes) at extraction entry forming a funnel geometry reducing tipping probability.

**Chute trajectory verification:** Place a token at chute entrance and release without initial velocity, allowing pure gravity-driven descent. Measure exit position relative to intended target array position—lateral deviation should not exceed 0.5 studs. Excessive deviation indicates chute misalignment or inadequate sidewall containment. Adjust chute angle by inserting plate-height shims under chute mounting points, targeting 20-25 degree descent angle providing optimal balance between gravitational acceleration and controlled descent preventing exit velocity from causing bounce-out ejection.

**Vertical lift binding diagnosis:** Actuate rack-pinion lift mechanism through complete travel range (minimum 8 studs vertical displacement for dual-plane architectures). Measure required crank torque via spring scale attached at 4-stud moment arm from pinion axle center—required force should remain under 100 grams throughout travel. Torque spikes exceeding 150 grams indicate rack misalignment or pinion tooth binding. Inspect rack teeth for debris accumulation or damaged tooth profiles. Verify rack mounting allows 0.1-stud axial float to accommodate manufacturing tolerance variations across the lift stroke.

### Algorithm Execution Checklist

Systematic pre-flight verification prevents operational errors during algorithm execution that corrupt sorting results requiring restart from initial conditions.

**Pre-execution verification sequence:**
1. Confirm token population completeness—all array positions contain valid tokens with no gaps or duplicates.
2. Verify initial array configuration matches intended test input by recording token values position-by-position in laboratory notebook.
3. Inspect all mobile mechanism travel paths for obstructions (stray bricks, displaced components) that could jam motion during execution.
4. Confirm auxiliary buffer positions (merge sort only) are empty and clear.
5. Initialize recursion stack markers (merge sort only) to starting configuration representing full unsorted array.
6. Zero cycle timer and prepare data recording sheet with column headers for comparison count, swap count, elapsed time.

**Intra-execution monitoring protocol:**
Execute algorithm operations at deliberate pace allowing observation of each mechanical action and comparison outcome. After each comparison operation, visually verify both tokens returned to correct positions per algorithm logic before advancing to next operation—caught errors cost less iteration count to correct than propagated errors requiring complete restart. Maintain comparison count tally using physical counter (stack of 1×1 plates where one plate moved per comparison provides tactile tracking) preventing mental count errors during extended operations. Note any anomalous mechanical behavior (unusual friction sounds, token tipping, chute misrouting) in real-time rather than reconstructing from memory post-failure.

**Post-execution verification sequence:**
1. Confirm final array configuration satisfies global sorted order invariant—traverse array recording values confirming monotonic non-decreasing sequence.
2. Verify token set conservation—final array contains identical token set as initial array with no losses or substitutions.
3. Record final operational metrics (comparison count, swap count, cycle duration) in data table.
4. Photograph final sorted configuration for documentation.
5. If verification fails, photograph failed configuration before disturbing array state, then analyze failure mode—incorrect comparison outcomes indicate comparator calibration drift, missing swaps indicate execution protocol errors, extra/missing tokens indicate transfer mechanism failures.

### Failure Mode Analysis and Root Cause Identification

When sorting execution produces incorrect output, systematic diagnosis isolates the failure mechanism enabling targeted correction rather than trial-and-error modification.

**Symptom: Final array contains correct tokens but incorrect order with multiple inversions.** Root cause: Consistent comparator reversal indicating physically inverted output channel routing or see-saw platform orientation 180 degrees rotated from specification. Verify heavier token routes to right output, lighter to left per specification. Measure platform tilt direction under known differential loading confirming proper gravitational response polarity.

**Symptom: Correct order in subsequences but global order violated across subsequences.** Root cause: Merge operation index tracking error (merge sort) or comparison-swap module traversal skipped positions (bubble/selection sort). Verify marker advancement protocol matches algorithm specification—index markers must advance exactly one position per loop iteration without skips or double-increments. Confirm comparison module traverses all required position pairs without omissions.

**Symptom: Tokens missing from final array or duplicates present.** Root cause: Transfer mechanism failure losing tokens through ejection or failing to complete extraction causing double-reads. Inspect array and surrounding baseplate area for ejected tokens confirming loss hypothesis. Review extraction protocol ensuring each token fully clears extraction mechanism before release preventing token ghosting where partial extraction reads same token twice.

**Symptom: Correct sorted order but cycle duration 3× longer than expected.** Root cause: Mechanical friction accumulation or sub-optimal traversal protocol introducing unnecessary operations. Measure individual operation durations isolating bottleneck—comparison operation exceeding 3 seconds indicates comparator pivot friction, transfer operations exceeding 4 seconds indicate chute misalignment or lift binding. Lubricate high-friction components and re-verify calibration per diagnostic procedures.

**Symptom: Sort completes correctly but fails on subsequent execution with identical input.** Root cause: Mechanical wear or tolerance drift from repeated operation causing previously marginal design parameters to exceed operational limits. Inspect pivot pins for widening clearances, rack-pinion gears for tooth wear, and chute trajectories for mounting plate deflection. Replace worn friction pins with new parts, tighten loose axle connections with additional bushing constraint, and reinforce deflecting structures with supplementary bracing liftarms.

### Performance Optimization Strategies

After achieving correct algorithm implementation validated through successful sorted output across representative inputs, optimization focuses on reducing cycle duration and improving mechanical reliability through targeted refinements.

**Reduce comparison operation latency:** Replace gravity-actuated see-saw comparators with spring-biased designs incorporating rubber band tensioners (Technic 63884) providing restoring force that accelerates return to neutral position between comparisons, reducing per-comparison duration from 2.0 seconds to 1.2 seconds yielding 40% throughput improvement on comparison-dominated algorithms.

**Minimize token transfer distances:** Reconfigure array geometry from linear single-row layout to wraparound serpentine pattern where merge sort recursion tree structure maps to physical adjacency—left and right subarrays at each recursion level positioned as physically adjacent segments rather than linearly distant positions, reducing mobile mechanism traverse distances by 35-40% and proportionally decreasing cycle time for traversal-dominated operations.

**Implement parallel actuation:** Merge sort's independent subtree operations enable concurrent execution when multiple actuators are available. Construct duplicate comparison modules enabling simultaneous execution of base-case merges at recursion leaves—four parallel modules reduce first merge level duration from serial 4× unit time to parallel 1× unit time, yielding 25% overall cycle time reduction at the cost of 4× mechanical complexity.

**Optimize token encoding for discrimination speed:** Replace variable-height tokens with mass-based differentiation where heavier tokens (achieved through internal lead weight insertion in hollow 2×2 bricks) tip comparator scales faster than height-based toppling, reducing comparison latency to 0.8 seconds while maintaining discrimination reliability. Mass-based encoding also enables smaller form factor tokens reducing traverse distances and storage footprint.
