# Lesson 1: Platform Architecture Foundations

## 1. First-Principles Intuition & Invariants

Google Vertex AI represents a deliberate departure from the fragmented tooling landscape that characterized machine learning platform engineering in the late 2010s. Before unified platforms emerged, practitioners navigated a labyrinth of disconnected services: training jobs launched through one API, model artifacts stored in another registry, endpoints provisioned via yet another control plane, and monitoring telemetry scattered across multiple dashboards. This architectural fragmentation imposed severe operational friction. A single model deployment pipeline might require orchestrating seven distinct services, each with independent authentication patterns, quota boundaries, and failure domains. The cognitive overhead stalled production velocity and created brittle failure surfaces where inter-service boundary conditions produced silent data corruption or training run aborts.

Vertex AI's foundational design principle anchors on **unified resource lifecycle management**. Every machine learning artifact—whether a Dataset, TrainingPipeline, Model, Endpoint, or BatchPredictionJob—exists as a first-class resource within a single hierarchical namespace rooted in Google Cloud's Resource Manager hierarchy. This is not merely an API convenience layer. The platform implements a formal state machine where each resource transitions through well-defined phases (CREATING, ACTIVE, DELETING, ERROR), and the control plane enforces strict invariants at state boundaries. A Model cannot be deployed to an Endpoint until its underlying artifact storage has reached ACTIVE state and passed cryptographic integrity verification. A TrainingPipeline cannot consume a Dataset until IAM policy evaluation confirms the service account possesses both `aiplatform.datasets.get` and storage bucket read permissions on the backing GCS URIs.

The architectural invariant separating Vertex AI from earlier platforms lies in its **decomposition of orchestration from execution**. The control plane, built atop Google's Spanner-backed control infrastructure, maintains all resource metadata, state machines, and IAM policy evaluation. It never directly executes training workloads or inference requests. Instead, it delegates execution to specialized runtimes: managed training infrastructure provisions ephemeral GPU/TPU clusters, the prediction serving layer routes requests to containerized model servers, and the feature store query engine executes distributed joins across BigQuery and Bigtable. This separation enables the control plane to enforce global invariants—quota enforcement across projects, cross-region replication policies for disaster recovery, audit log compliance for regulated industries—without coupling to the performance characteristics of individual workloads. A training job saturating 512 A100 GPUs generates no backpressure on the control plane's ability to provision new endpoints in parallel.

From a systems architecture perspective, Vertex AI's resource hierarchy mirrors the Google Cloud organization structure but introduces machine-learning-specific containment semantics. A Project forms the isolation boundary for billing, quotas, and IAM inheritance. Within a project, resources are further scoped by Location—either a region like `us-central1` or the multi-region abstraction `us`. Location is not merely a deployment hint; it defines the physical data residency, network latency characteristics, and failure domain boundaries. Training data in `europe-west4` cannot be directly consumed by a TrainingPipeline in `us-central1` without explicit cross-region replication, which introduces both latency penalties and data sovereignty implications for GDPR compliance. The platform enforces location affinity through IAM conditions and Org Policy constraints, enabling enterprises to encode regulatory requirements as machine-readable policy rather than relying on developer discipline.

The abstraction layers within Vertex AI form a clean separation of concerns that maps to distinct operational personas. Data scientists interact primarily with the managed service APIs—submitting AutoML training jobs, tuning hyperparameters via Vizier optimization loops, and querying experiment metrics through the ML Metadata tracking layer. ML engineers engage with the deployment and serving surface—containerizing custom prediction logic, configuring traffic splitting for A/B tests, and defining monitoring policies for drift detection. Platform engineers govern the infrastructure substrate—allocating GPU reservation quotas, configuring VPC Service Controls for network isolation, and establishing Workload Identity bindings between Kubernetes service accounts and Google Cloud IAM principals when bridging to on-premise data sources. Each layer exposes a stable API contract, and the platform's versioning policy guarantees backward compatibility within major API versions, enabling teams to upgrade infrastructure without revalidating training pipelines.

The invariants governing Vertex AI's integration with the broader Google Cloud ecosystem derive from its dependency on foundational platform services. Every API call transits through Google's global load balancer infrastructure, undergoes TLS termination at the nearest Cloud Armor edge node, and routes through Identity-Aware Proxy for zero-trust authentication verification. Resource metadata persists in Spanner, providing serializable isolation and automatic multi-region replication with tunable consistency levels. Training artifacts and model binaries reside in Cloud Storage, inheriting its eleven nines durability guarantee and automatic encryption at rest using Google-managed or customer-supplied KMS keys. Logs flow to Cloud Logging's exabyte-scale ingestion pipeline, where they are indexed by resource labels and made available for real-time streaming through Pub/Sub or batch export to BigQuery for SQL-based analysis. This deep integration eliminates the impedance mismatch that plagued earlier platforms attempting to graft machine learning tooling onto incompatible infrastructure primitives.

Understanding Vertex AI's resource model requires grasping the distinction between **declarative specification and imperative execution**. When a client submits a TrainingPipeline via the REST API or Python SDK, they provide a declarative specification: the container image URI, hardware accelerator requirements, hyperparameter search space, and training data location. The control plane validates this specification against quota limits and IAM policies, persists it as a durable resource in Spanner, and returns immediately with a long-running operation handle. The actual training execution occurs asynchronously. A scheduler component watches the resource state machine, detects the new TrainingPipeline in PENDING state, and provisions the requested infrastructure—allocating GPU VMs from the regional capacity pool, mounting persistent disks for checkpoint storage, and injecting secrets for authenticated access to private datasets. This level-triggered reconciliation loop mirrors Kubernetes' controller pattern but operates at cloud-scale infrastructure granularity rather than container orchestration scope.

The platform's IAM model extends Google Cloud's standard role-based access control (RBAC) with machine-learning-specific predicates. The primitive role `roles/aiplatform.user` grants broad permissions suitable for individual data scientists but violates least-privilege principles in production environments. Predefined roles offer finer granularity: `roles/aiplatform.modelUser` permits deploying existing models to endpoints but prohibits training new models, while `roles/aiplatform.featurestoreDataViewer` allows querying feature values without mutating entity schemas. For defense-in-depth, Org Policy constraints such as `constraints/aiplatform.restrictVpcPeering` enforce network isolation, preventing training jobs from exfiltrating data to unauthorized VPCs. IAM conditions enable temporal constraints—granting `aiplatform.endpoints.predict` only during business hours—or attribute-based policies that restrict access to models tagged with specific sensitivity classifications.

Vertex AI's regional deployment architecture balances latency, availability, and regulatory compliance. Each region operates an independent control plane and execution substrate, eliminating cross-region dependencies that could amplify failure blast radius. Training pipelines launched in `us-central1` never depend on control plane availability in `europe-west4`. However, metadata replication occurs asynchronously for disaster recovery: Model artifact references, endpoint configurations, and experiment tracking data are backed up to a geographically distant region with configurable Recovery Point Objective (RPO) and Recovery Time Objective (RTO) SLAs. This design enables surviving regional failures—if `us-central1` becomes unavailable, endpoints can be reconstructed in `us-west1` from replicated metadata and model binaries stored in dual-region Cloud Storage buckets—but introduces eventual consistency windows where recently created resources may not appear in cross-region disaster recovery snapshots until replication lag drains.

The separation of control plane from data plane manifests physically in network topology and API endpoint structure. All control plane operations—creating datasets, launching training jobs, registering models—target `{region}-aiplatform.googleapis.com` and return resource names containing the full hierarchical path: `projects/{project}/locations/{location}/models/{model}`. These operations are rate-limited by quota policies measuring requests per minute, preventing API abuse but also constraining bulk automation throughput. Prediction requests instead target dedicated serving infrastructure at `{region}-aiplatform.googleapis.com/v1/projects/{project}/locations/{location}/endpoints/{endpoint}:predict`, where the endpoint identifier routes to horizontally scaled prediction servers fronted by Google's global load balancer. Prediction quotas measure queries per second and payload bytes, reflecting the high-throughput nature of inference workloads. This dual-plane architecture enables the platform to independently scale control operations and prediction serving, preventing a traffic surge on inference endpoints from starving the control plane's ability to provision new resources.

## 2. Core Architecture & Mechanics

The internal architecture of Vertex AI decomposes into seven primary subsystems, each implementing a bounded context with well-defined API contracts and failure domain isolation. These subsystems communicate through asynchronous message queues backed by Pub/Sub for loose coupling, enabling independent scaling and fault tolerance. The orchestration layer coordinates multi-step workflows—such as hyperparameter tuning jobs that spawn dozens of parallel training trials—without holding open synchronous connections that could cascade failures.

The **API Gateway** component implements Google's standard API management infrastructure—rate limiting via distributed token bucket algorithms, request logging for audit compliance, and protocol translation between REST/JSON and internal gRPC services. Every API request undergoes a multi-stage validation pipeline. First, the TLS certificate chain is verified against Google Trust Services' root certificate authority. Second, the OAuth2 bearer token or service account JWT is validated, and the associated principal identity is extracted. Third, IAM policy evaluation occurs by querying the Zanzibar-derived authorization database, which represents permissions as a directed acyclic graph of role bindings, group memberships, and Org Policy constraints. This evaluation typically completes in single-digit milliseconds due to aggressive caching and batched policy evaluation, but under extreme load—such as a batch job querying permissions for 10,000 models—the cache miss penalty can escalate to hundreds of milliseconds per request.

Resource state transitions are governed by a finite state machine encoded in protocol buffer definitions and enforced through Spanner's transactional guarantees. When a client calls `create_training_pipeline`, the control plane allocates a unique resource identifier, inserts a row into the `TrainingPipeline` table with state PENDING, and commits the transaction with serializable isolation. A fleet of scheduler workers continuously polls for PENDING resources using change streams—Spanner's built-in change data capture mechanism—and claims work items through optimistic locking. The worker that successfully transitions a TrainingPipeline from PENDING to RUNNING assumes responsibility for provisioning the training infrastructure. It allocates compute resources from the regional capacity pool, configures network routes for VPC peering or Private Service Connect, and launches the training container with environment variables injecting the service account credentials, dataset URIs, and hyperparameter values. If the worker crashes mid-provisioning, a deadlock detection mechanism identifies orphaned resources in transient states and retries the provisioning workflow, ensuring exactly-once execution semantics.

The **Training Runtime** operates as a multi-tenant cluster manager that dynamically provisions heterogeneous accelerator topologies. For standard VM-based training, the runtime allocates Compute Engine instances matching the requested machine type—`n1-standard-16` for CPU-only workloads, `a2-highgpu-8g` for NVIDIA A100 GPU training, or `v3-32` for Cloud TPU pods. Each VM is provisioned with a boot disk containing the training framework preinstalled (TensorFlow, PyTorch, XGBoost, or scikit-learn) and a persistent disk mounted at `/mnt/checkpoints` for periodically saving model weights. The training container receives a GCS FUSE mount providing lazy-loaded access to training datasets without copying multi-terabyte shards to local disk. For distributed training, the runtime provisions a cluster of VMs with high-bandwidth interconnect—either 100 Gbps Ethernet or TPU-specific interconnect fabric—and injects environment variables conforming to the Horovod or TensorFlow distributed training protocols, enabling the framework's parameter server or all-reduce collective communication patterns.

Checkpoint management implements a sophisticated trade-off between durability and performance. Writing gigabyte-scale model checkpoints directly to Cloud Storage on every epoch would saturate network egress bandwidth and introduce multi-second stalls during gradient descent. Instead, checkpoints are first written to local NVMe SSD, then asynchronously streamed to GCS in 32 MB chunks through a background thread pool. The control plane tracks checkpoint versions in ML Metadata, enabling time-travel reconstruction if a training job encounters a transient numerical instability—such as NaN gradients from a learning rate spike—and needs to resume from an earlier checkpoint. For exceptionally large models exceeding single-VM memory capacity, the runtime supports sharded checkpoints where each worker saves only its partition of the parameter tensor, and the control plane stores a manifest describing the sharding layout for correct reassembly during inference.

The **Prediction Serving** subsystem implements a horizontally scaled inference engine fronted by a global load balancer. When a Model is deployed to an Endpoint, the control plane generates a serving configuration specifying the container image (TensorFlow Serving for SavedModel artifacts, TorchServe for PyTorch models, or a custom container for arbitrary prediction logic), resource requests (CPU cores, memory, GPU attachment), and autoscaling policies. This configuration is translated into a Kubernetes Deployment specification and submitted to a regional Google Kubernetes Engine (GKE) cluster dedicated to prediction serving. The GKE cluster operates in Autopilot mode—a fully managed configuration where Google handles node provisioning, security patching, and capacity planning—eliminating operational toil.

Each prediction server pod runs three containers in a sidecar pattern. The primary container executes the model server, loading the model artifact from Cloud Storage into memory and listening on port 8080 for HTTP prediction requests. The sidecar Envoy proxy intercepts inbound traffic, enforcing rate limits, request authentication via IAM token validation, and payload size constraints to prevent denial-of-service attacks from maliciously large inputs. A third logging agent container tails the model server's stdout/stderr streams and ships structured logs to Cloud Logging, enriched with trace context identifiers for distributed request tracing. This sidecar architecture isolates concerns—the model server focuses solely on inference latency, while cross-cutting concerns like observability and security are handled by purpose-built infrastructure components.

Autoscaling behavior for Endpoints follows the Kubernetes Horizontal Pod Autoscaler (HPA) control loop with Vertex-specific enhancements. The HPA controller continuously monitors CPU utilization and custom metrics (such as prediction request queue depth or GPU utilization) scraped from the Envoy proxy's Prometheus metrics endpoint. When average CPU utilization exceeds the target threshold—typically 70% to maintain headroom for traffic bursts—the controller increases the replica count, triggering GKE Autopilot to provision additional nodes if the existing cluster lacks capacity. Vertex AI augments this with predictive autoscaling that analyzes historical traffic patterns using ARIMA time-series forecasting. If traffic exhibits a daily periodicity with a surge at 9 AM UTC, the platform pre-scales the Endpoint at 8:50 AM to avoid cold-start latency when the first requests arrive. Scale-down follows a conservative hysteresis policy, waiting ten minutes of sustained low utilization before terminating pods to prevent thrashing during transient traffic dips.

The **Feature Store** subsystem bridges the impedance mismatch between batch training workflows and online serving requirements. During training, features are typically computed in batch—a daily Dataflow or Spark job aggregates user interactions from the past 90 days into aggregated statistics like click-through rate or average transaction value. These batch features are written to BigQuery, where they are joined with labels during training data preparation. At serving time, the model requires the same features, but recomputing 90-day aggregates on-demand would introduce unacceptable latency. The Feature Store solves this by maintaining two synchronized views: an offline store in BigQuery for training and a low-latency online store in Bigtable for prediction serving.

Feature ingestion into the online store occurs through two pathways. Batch features are bulk-written via a managed pipeline that reads from BigQuery, applies schema validation to ensure type consistency, and writes to Bigtable using batch mutations with automatic retry and exponential backoff. Streaming features—such as a user's last five search queries updated in real-time—are written directly to Bigtable via the Feature Store's write API, which enforces strong consistency within a single entity's feature values but allows eventual consistency across entities for scalability. Point lookups during prediction serving hit Bigtable, which provides single-digit millisecond P99 latency at millions of queries per second through its distributed, SSD-backed architecture. The Feature Store's schema registry, stored in Spanner, maintains versioning metadata enabling the platform to serve multiple feature versions simultaneously—critical during model transitions when the new model requires additional features not consumed by the incumbent model.

ML Metadata (MLMD) implements a graph database specialized for tracking machine learning lineage. Every artifact—datasets, models, training runs, evaluations—is represented as a node, and edges encode relationships like TRAINED_FROM (linking a model to its training dataset) or DEPLOYED_TO (linking a model to its serving endpoint). This graph structure enables compliance queries such as "Which production endpoints are serving models trained on PII-containing datasets subject to GDPR right-to-erasure requests?" or "What is the transitive dependency closure of all datasets contributing to model X's training?" The MLMD backend uses Spanner for ACID transactions and PostgreSQL-compatible query semantics, enabling complex graph traversals expressed as recursive common table expressions (CTEs) without requiring a separate graph database technology stack.

The control plane's quota management system implements hierarchical token buckets with overcommit policies. Each project has quota limits for concurrent training jobs, total GPU hours per month, and prediction queries per second. These quotas are not hard partitions—Google dynamically overcommits capacity when aggregate demand falls below total provisioned infrastructure, allowing projects to burst above their nominal quota if spare capacity exists. However, when contention arises, the scheduler applies prioritization based on quota headroom, preempting lower-priority jobs to reclaim resources. Quota enforcement occurs at multiple layers: the API Gateway rejects requests that would exceed quota limits, the scheduler avoids allocating resources for queued jobs without quota headroom, and the training runtime periodically revalidates that running jobs remain within quota, terminating those that exceed limits due to concurrent launches by other users. This defense-in-depth approach prevents quota exhaustion from cascading into infrastructure instability.

## 3. High-Performance Optimization & Failure Modes

Optimizing Vertex AI workflows requires understanding the latency hierarchy governing machine learning pipelines. The dominant latency contributor in training is typically I/O—loading training data from Cloud Storage saturates network bandwidth before saturating GPU compute. The GCS FUSE connector mitigates this through aggressive prefetching and local caching, but its performance characteristics differ critically from POSIX filesystem semantics. FUSE reads are sequential and blocking; random access patterns—such as shuffling training examples by seeking through a TFRecord file—degrade to worst-case performance where each 256 KB read incurs a separate GCS API call with 50-100 ms latency. The solution involves preprocessing data into optimized formats: TFRecord files with interleaved examples to support sequential streaming, Parquet with rowgroup statistics for predicate pushdown, or sharded datasets where each worker reads a disjoint partition eliminating cross-worker contention.

For distributed training, the communication-to-computation ratio determines scaling efficiency. Data-parallel training using synchronous all-reduce—where each worker computes gradients on a data shard, then all workers average their gradients before applying the update—exhibits linear scaling only when per-worker computation time dominates gradient synchronization time. For ResNet-50 training on ImageNet, a batch size of 32 per GPU keeps each A100 GPU at 85% utilization, and all-reduce across 8 GPUs completes in 15 ms via NVLink interconnect, yielding 98% scaling efficiency. Scaling to 64 GPUs across 8 VMs connected by 100 Gbps Ethernet degrades efficiency to 75% because inter-node gradient synchronization latency escalates to 150 ms, eroding the computation-to-communication overlap. The mitigation involves gradient compression—quantizing 32-bit float gradients to 8-bit integers or applying sparsification to transmit only the top-K largest gradients—reducing synchronization bandwidth by 4× at the cost of slight convergence slowdown requiring 10-15% more training steps.

Hyperparameter tuning jobs using Vertex AI's Vizier service implement Bayesian optimization over the hyperparameter search space, but naive parallelization can introduce sample inefficiency. Vizier maintains a Gaussian process surrogate model predicting validation loss as a function of hyperparameters, and selects the next trial by maximizing expected improvement over the current best. When running 20 parallel trials, the surrogate model trains on only the completed trials, ignoring the in-progress trials whose outcomes are unknown. This causes redundant exploration—multiple trials selecting similar hyperparameter regions before any complete and update the surrogate. The batched acquisition function addresses this by jointly selecting N trial configurations that maximize expected improvement while maintaining diversity through determinantal point processes that penalize configurations too similar to pending trials. Enabling this via the `algorithm: ALGORITHM_BATCH` setting in the StudySpec typically reduces the number of trials required to reach 95% of optimal validation accuracy by 30-40%.

Prediction serving optimization decomposes into two regimes: latency-sensitive and throughput-sensitive. Latency-sensitive applications—such as fraud detection scoring payment transactions in real-time—require P99 latency below 100 ms, necessitating aggressive resource over-provisioning to absorb traffic bursts without queueing delay. Configuring `min_replica_count` high enough to handle peak traffic plus 30% headroom ensures cold-start latency never impacts user-facing requests. Throughput-sensitive batch prediction workloads instead optimize for cost efficiency, trading latency for cheaper spot VMs or packing multiple models onto shared GPU instances. The batch prediction API exploits this by provisioning ephemeral infrastructure only for the job duration, avoiding the hourly cost of continuously running endpoints for infrequent batch inference workloads.

Model artifact size directly impacts cold-start latency, as the prediction server must download the model from Cloud Storage and load it into memory before serving the first request. A 5 GB TensorFlow SavedModel requires 30-40 seconds to download over a 1 Gbps NIC and an additional 15 seconds for TensorFlow Serving to parse the protobuf graph definition and initialize GPU kernels. Quantization reduces model size—converting 32-bit float weights to 8-bit integers shrinks the artifact by 75%—but introduces a 1-2% accuracy degradation that must be validated against task-specific metrics. Model distillation offers a more sophisticated trade-off: training a smaller student model to mimic a larger teacher model's predictions often achieves 80-90% of the teacher's accuracy at 10× smaller size and 5× lower inference latency.

Network topology significantly impacts multi-region deployment patterns. Deploying models in multiple regions for disaster recovery or latency optimization requires replicating both model artifacts and Feature Store data. Cloud Storage supports dual-region buckets—such as `us-central1` and `us-east1`—with synchronous replication ensuring artifact availability survives single-region failures with zero data loss. However, Feature Store data in Bigtable replicates asynchronously, introducing eventual consistency windows of 100-500 ms where a feature update written in one region may not be visible in another. For globally consistent predictions, the application must implement read-after-write consistency by tagging prediction requests with a logical timestamp and ensuring the serving region's Bigtable replica has caught up past that timestamp before processing the request.

IAM policy evaluation latency becomes a bottleneck in high-throughput prediction scenarios. Every prediction request undergoes IAM authorization, verifying the caller possesses `aiplatform.endpoints.predict` permission. This evaluation queries the authorization graph, which under normal load completes in 2-5 ms but can spike to 50+ ms during IAM policy updates—such as adding a user to a group with inherited permissions—because policy cache invalidation triggers a thundering herd of cache refills across the serving fleet. The mitigation involves using long-lived service account tokens instead of OAuth2 user tokens, as service account permissions are evaluated against a smaller policy scope and exhibit more stable cache hit rates. For extremely latency-sensitive workloads, embedding IAM policy evaluation results directly into signed JWTs using workload identity federation eliminates the runtime authorization query entirely, reducing P99 latency by 10-15 ms.

Failure modes in Vertex AI workflows predominantly manifest as partial failures due to the distributed nature of the execution substrate. A training job with 16 workers may experience a single worker crash due to transient network partition or out-of-memory error while the remaining 15 workers continue computing gradients. TensorFlow's distributed runtime implements failure recovery through checkpoint-based restart: when the control plane detects a worker failure via heartbeat timeout, it provisions a replacement worker, restores from the most recent checkpoint, and resumes training. However, this recovery incurs overhead—checkpoint restoration takes 2-5 minutes for multi-GB models, and the restarted worker must replay the data shards already processed by peer workers to maintain synchronization. Frequent restarts indicate either insufficient memory provisioning—increasing `machine_spec.memory_size_gb` by 50%—or code-level issues like memory leaks in custom training loop logic that should be diagnosed via Cloud Profiler's memory allocation flamegraphs.

Prediction serving failures often stem from version skew between training and serving environments. A model trained with TensorFlow 2.12 may fail to load in a TF Serving 2.10 container due to serialization format changes in the SavedModel protobuf schema. The mitigation involves pinning the serving container to match the training framework version by specifying `container_spec.image_uri = "us-docker.pkg.dev/vertex-ai/prediction/tf2-gpu.2-12:latest"` in the DeployModelRequest. For custom containers, embedding the framework version into the Docker image tag and validating compatibility in a staging environment before production deployment prevents runtime deserialization failures that manifest as cryptic "Unsupported SavedModel version" errors with no automatic recovery path.

Quota exhaustion failures require careful capacity planning. Training jobs queued due to insufficient GPU quota remain in PENDING state indefinitely unless the quota is increased via the Google Cloud Console quota request workflow, which typically completes within 24-48 hours but can extend to weeks for large TPU pod requests exceeding regional capacity. Monitoring the `aiplatform.googleapis.com/quota/used` metric and alerting when usage exceeds 80% of allocated quota provides lead time to request increases before hitting hard limits. For bursty workloads, architecting for graceful degradation—such as falling back to smaller models or CPU-based training when GPU quota is exhausted—maintains partial functionality rather than complete service outage.

Data pipeline failures disproportionately impact training reliability. A training job expecting 10,000 TFRecord shards in a GCS bucket will fail catastrophically if even a single shard is missing or corrupted, typically 60-90 minutes into training after successfully processing thousands of earlier shards. Implementing robust data validation before training launch—using Vertex AI's Managed Datasets with built-in schema validation and statistics generation—catches these issues at ingestion time. The validation pipeline computes per-feature histograms, identifies null rates exceeding thresholds, and flags numerical features with suspicious distributions (such as constant values indicating upstream ETL failures). This shifts failure detection left, from expensive multi-hour training crashes to cheap 5-minute validation jobs that fail fast with actionable diagnostic messages identifying the specific malformed data shard and corrupt record offset.
