# Lesson 4: Scaling Laws for Sparse Expert Models

## 1. First-Principles Intuition & Invariants

The fundamental tension in deep learning system design has always been the relationship between model capacity and computational cost. Dense neural networks force us into a Faustian bargain: every additional parameter we introduce contributes to every forward pass computation, creating a strict linear coupling between model size and inference cost. The transformative insight behind Mixture of Experts architectures is the recognition that this coupling is not a fundamental law of neural computation but rather an artifact of dense matrix multiplication primitives. By introducing conditional computation through expert routing, we decouple parameter count from active computation, fundamentally rewriting the scaling equations that govern model performance.

The core invariant of sparse expert models can be expressed through a simple but profound relationship. Consider a traditional dense feedforward layer with parameter matrix $W \in \mathbb{R}^{d \times 4d}$ in a transformer architecture. Every token activates every parameter, yielding a computational cost of $8d^2$ floating-point operations per token. Now consider replacing this layer with a sparse mixture containing $N$ expert networks, each with parameter matrix $W_i \in \mathbb{R}^{d \times 4d}$, where a learned routing function selects only $k$ experts to activate per token. The total parameter count scales as $8Nd^2$, growing linearly with expert count, yet the per-token computational cost remains bounded at $8kd^2$, independent of $N$ for fixed $k$. This fundamental decoupling allows us to scale model capacity far beyond what would be tractable with dense architectures while maintaining constant inference cost per token.

The practical implications of this scaling law manifest across three critical dimensions: parameter efficiency, memory hierarchy utilization, and distributed system topology. Parameter efficiency emerges from the observation that different regions of input space benefit from specialized transformation functions. Natural language exhibits rich statistical structure—syntactic constructions, semantic domains, stylistic registers, and linguistic modalities all present distinct computational demands. A dense model must learn a universal approximation function that handles all these modes simultaneously, necessarily compromising on specialization. Sparse expert models instead learn a decomposition of the input manifold, with each expert specializing in a particular region while the router learns the boundaries between these regions. This specialization yields superior parameter efficiency: empirical studies demonstrate that sparse models with $8× to $64×$ more parameters than dense baselines achieve comparable or superior performance while activating only $12\%$ to $6\%$ of total parameters per forward pass.

The memory hierarchy implications arise from the physical realities of modern accelerator architectures. Contemporary GPUs and TPUs feature deeply hierarchical memory systems: high-bandwidth on-chip SRAM measured in megabytes, device-attached HBM measured in tens of gigabytes, and host DRAM measured in hundreds of gigabytes or terabytes. Matrix multiplication kernels achieve peak throughput only when operands reside in the highest tiers of this hierarchy. For dense models exceeding device memory capacity, we face catastrophic performance degradation as parameters spill to host memory, introducing PCIe bandwidth bottlenecks. Sparse expert models fundamentally change this equation by partitioning parameters into expert shards small enough to fit within favorable memory tiers, even when total model size far exceeds any single device capacity. The routing function becomes a learned memory access pattern, directing computation only to parameters that can be efficiently materialized on-chip.

Model parallelism requirements stem from the distributed system topology necessary to host and execute these massive sparse models. While data parallelism—replicating the full model across devices and partitioning training batches—suffices for dense models that fit within single-accelerator memory, sparse models with billions or trillions of parameters demand expert parallelism strategies. Each accelerator hosts a subset of the expert population, and the routing function implicitly implements a load-balancing network that distributes tokens to appropriate devices. This creates a distributed system where computation follows data, but the "data" in question is not the input tokens but rather the expert parameters themselves. The fundamental challenge becomes managing the capacity and load imbalance inherent in learned routing functions while minimizing cross-device communication overhead.

These three dimensions—parameter efficiency, memory hierarchy, and distributed topology—interact through a complex objective function that production ML systems must optimize. Increasing expert count $N$ improves parameter efficiency but exacerbates memory pressure and complicates parallelism. Increasing top-$k$ routing improves model quality through ensemble effects but linearly increases computational cost and communication volume. The batch size interacts non-trivially with all these factors: larger batches amortize routing overhead and improve expert utilization through better statistical averaging, but they increase memory pressure and introduce latency for interactive workloads. Understanding these tradeoffs requires grounding our analysis in the physical realities of compute graphs, memory systems, and network topologies that underpin production inference infrastructure.

## 2. Core Architecture & Mechanics

The execution flow of a sparse MoE layer unfolds through four distinct computational phases: router scoring, expert selection and token dispatch, expert computation, and result aggregation. Each phase introduces unique performance characteristics and architectural constraints that shape the practical scaling behavior of these systems.

Router scoring begins with the input token representations $X \in \mathbb{R}^{b \times s \times d}$, where $b$ denotes batch size, $s$ sequence length, and $d$ model dimension. The router network—typically a lightweight linear projection $W_r \in \mathbb{R}^{d \times N}$ followed by softmax—produces a logit distribution over $N$ experts for each token. This projection computes $bsd N$ operations, seemingly negligible compared to expert computation itself, but the subsequent softmax introduces a subtle performance trap. Softmax normalization requires computing the exponential of every logit and then normalizing across the expert dimension, a memory-bandwidth-bound operation that cannot be effectively fused with the preceding matrix multiplication on most accelerators. For models with hundreds or thousands of experts, this softmax becomes a non-trivial overhead in the critical path, consuming microseconds that accumulate across the dozens or hundreds of MoE layers in contemporary large models.

The expert selection phase transforms router logits into concrete dispatch decisions through top-$k$ selection. Implementing top-$k$ efficiently on SIMD accelerators presents a subtle algorithmic challenge. The naive approach—sorting all $N$ logits and taking the first $k$ elements—incurs $O(N \log N)$ complexity per token, catastrophic for large expert counts. Production implementations instead use approximate selection algorithms: heap-based selection with $O(N \log k)$ complexity, or radix-select approaches that trade accuracy for speed. The selected expert indices and corresponding router weights then feed into a token dispatch operation that reorganizes the input tensor from shape $[b, s, d]$ into a ragged expert-parallel format where each expert receives only its assigned tokens. This reorganization—essentially a learned scatter operation—introduces memory non-coalesced access patterns that can bottleneck on memory bandwidth if not carefully orchestrated.

The token dispatch mechanics merit detailed examination because they fundamentally determine the system's utilization characteristics. Consider a batch of $B = bs$ total tokens distributed across $N$ experts with top-$k$ routing. In expectation, if the router produces a uniform distribution, each expert receives $kB/N$ tokens. This uniform case represents ideal load balance: all experts perform equal work, and all accelerators in an expert-parallel deployment achieve equal utilization. Reality deviates sharply from this ideal. Learned routers exhibit strong token-expert affinity patterns, with certain experts becoming "specialists" that attract disproportionate token volumes. This specialization drives the model's superior performance, but it creates catastrophic load imbalance in the distributed system. Some experts might receive $5×$ or $10×$ their fair share of tokens while others sit idle, directly translating to proportional underutilization of accelerator capacity.

Capacity constraints introduce an auxiliary mechanism to bound this load imbalance. Each expert declares a maximum capacity $C$, typically set as a multiple of the expected load $C = \alpha kB/N$ where $\alpha$ is a capacity factor in the range $[1.2, 2.0]$. When an expert exceeds capacity, subsequent tokens attempting to route to that expert are either dropped or reassigned to their next-highest-scoring expert. Token dropping represents wasted computation—the router evaluated these tokens but they contribute nothing to the final output—and introduces training instability as the effective loss landscape becomes non-differentiable with respect to router parameters. Expert reassignment ameliorates waste but complicates the routing function's learning dynamics, as tokens no longer flow to their true top-$k$ experts.

The expert computation phase executes the actual feedforward transformation on each expert's assigned token buffer. For a standard MLP expert with hidden dimension $4d$, this involves two matrix multiplications: an up-projection from $d$ to $4d$ and a down-projection back to $d$, interleaved with a nonlinearity. The critical insight is that each expert processes a dynamically-sized batch—the number of tokens it received during dispatch—rather than a fixed batch size. This dynamic batching has profound implications for kernel efficiency. Matrix multiplication achieves peak throughput only when batch dimensions are sufficiently large to saturate the accelerator's arithmetic units and amortize memory latency. Small batches—fewer than 32 or 64 tokens on typical GPUs—leave the accelerator underutilized, achieving only a fraction of peak FLOPS. The load imbalance problem thus manifests not just as idle experts receiving zero tokens, but as partially-utilized experts receiving too few tokens to run efficiently.

Consider a concrete arithmetic example on an NVIDIA A100 GPU with 312 TFLOPS of FP16 compute throughput. An expert with parameters $W_1 \in \mathbb{R}^{4096 \times 16384}$ and $W_2 \in \mathbb{R}^{16384 \times 4096}$ executing on a batch of $B_e$ tokens performs $2 \cdot B_e \cdot 4096 \cdot 16384 = 5.37 \times 10^8 B_e$ FLOPs. At peak efficiency, this computation requires $5.37 B_e / 312 = 1.72 B_e$ microseconds. For $B_e = 1024$ tokens, ideal latency is $1.76$ milliseconds. In practice, actual latency for small batches can exceed $5$ milliseconds, representing $<35\%$ utilization due to kernel launch overhead, memory bottlenecks, and wave quantization effects where the batch size doesn't evenly divide the GPU's streaming multiprocessor count.

Result aggregation recomposes the expert outputs back into the original token sequence order. Each token that routed to $k$ experts now has $k$ corresponding output vectors, weighted by the router's softmax scores. The aggregation performs a weighted sum to produce the final output: $y_i = \sum_{j=1}^k w_{ij} E_{e_{ij}}(x_i)$ where $w_{ij}$ is the router weight for token $i$ routing to expert $e_{ij}$. This operation appears trivial—just $k$ weighted additions per token—but it requires gathering the expert outputs from their scattered expert-parallel format back into sequence order, essentially the inverse of the dispatch scatter. On distributed systems where experts reside on different devices, this aggregation becomes an all-to-all communication primitive, synchronizing results across the expert-parallel dimension before proceeding to subsequent layers.

The memory access patterns throughout this pipeline deserve explicit attention because they determine whether the system is compute-bound or memory-bound. Router scoring reads every input token and writes logits for every token-expert pair, touching $bs(d + N)$ elements. Token dispatch performs irregular gather operations, with cache-unfriendly access patterns. Expert computation—if batch sizes are adequate—achieves compute-bound performance with high arithmetic intensity. Result aggregation performs another irregular scatter-gather. The ratio of compute operations to memory operations, the arithmetic intensity, varies dramatically across these phases. Router and aggregation phases exhibit low intensity, typically $<10$ FLOPs per byte, while expert computation achieves $>100$ FLOPs per byte. Overall system throughput thus depends critically on whether the router and aggregation overheads remain negligible compared to expert computation time.

## 3. High-Performance Optimization & Failure Modes

Optimizing sparse MoE systems for production inference demands reasoning across multiple levels of the system stack: algorithmic choices that shape computational complexity, kernel implementations that maximize accelerator utilization, memory layouts that minimize bandwidth pressure, and distributed system topologies that balance parallelism against communication overhead. Each optimization vector presents distinct tradeoffs that interact in subtle and often counterintuitive ways.

Expert capacity planning emerges as the first critical optimization lever. The capacity factor $\alpha$ directly controls the tradeoff between load balance and token dropping. Setting $\alpha = 1.0$ minimizes memory allocation—each expert buffer is sized exactly to the expected load—but guarantees catastrophic token drops whenever routing exhibits any imbalance. Production systems typically set $\alpha \in [1.25, 1.5]$, accepting $25\%$ to $50\%$ memory overhead to tolerate routing variance. However, this static allocation strategy proves inefficient under varying workload characteristics. A batch of technical tokens might exhibit strong expert affinity, with most tokens routing to a few domain-specific experts, while a batch of diverse conversational tokens distributes more uniformly. Dynamic capacity allocation—where expert buffers are sized based on observed routing distributions in an initial profiling phase—can reduce memory footprint by $30\%$ to $40\%$ compared to pessimistic static allocation, at the cost of introducing a two-phase dispatch mechanism.

Load balancing auxiliary losses represent the standard approach to mitigating inherent routing imbalance. The auxiliary loss penalizes uneven expert utilization by adding a term to the training objective: $\mathcal{L}_{aux} = \alpha \sum_{i=1}^N f_i \cdot P_i$ where $f_i$ is the fraction of tokens routed to expert $i$ and $P_i$ is the average router probability assigned to expert $i$. This formulation encourages the router to distribute tokens uniformly while respecting the learned expert specializations encoded in $P_i$. The coefficient $\alpha$, typically in the range $[0.01, 0.1]$, controls the strength of this regularization. Too small and the loss has negligible effect, leaving severe imbalance; too large and the loss overpowers the primary objective, forcing artificial uniformity that degrades model quality. Tuning this hyperparameter requires extensive experimentation on representative workloads, and the optimal value often varies across layers—early layers benefit from diverse routing to maximize feature extraction, while later layers benefit from specialization for task-specific reasoning.

The mathematical formulation of this auxiliary loss reveals a subtle failure mode. The loss pushes toward uniform $f_i$, but the router learns to game this objective by assigning moderate probabilities to many experts rather than strong probabilities to a few. This "probability smearing" satisfies the auxiliary loss while concentrating actual token routing—determined by the top-$k$ operation—on a subset of experts. The top-$k$ selection is non-differentiable, creating a gradient disconnect between the auxiliary loss and actual dispatch behavior. Advanced formulations introduce gating noise during training, adding Gaussian perturbations to router logits before top-$k$ selection, which provides a stochastic gradient signal that better aligns auxiliary loss optimization with dispatch outcomes.

Kernel fusion optimizations target the memory-bound phases of the MoE pipeline. On GPUs and TPUs, launching separate kernels for router projection, softmax, top-$k$ selection, and token dispatch incurs overhead from kernel launch latency and intermediate memory traffic. Fusing these operations into a single kernel amortizes launch costs and keeps intermediate results in registers or shared memory rather than writing them to device memory. A fused router-dispatch kernel reads input tokens once, computes router logits in registers, performs approximate top-$k$ selection using shared memory, and writes final dispatch indices directly, eliminating three round-trips to global memory. On A100 GPUs with 1.5TB/s HBM bandwidth, each eliminated memory operation saves roughly $0.1$ microseconds per token, accumulating to milliseconds of latency savings across the hundreds of tokens in a typical batch.

Expert batching strategies address the dynamic batch size problem inherent in token dispatch. Since each expert receives a variable number of tokens, the expert computation phase sees widely varying batch sizes, many of which are too small for efficient kernel execution. Expert batching combines tokens from multiple input batches before dispatching to experts, allowing each expert to process a larger aggregate batch. This technique is particularly effective in offline batch inference workloads where latency constraints are relaxed. For example, if each input batch contains $B = 512$ tokens and four input batches are combined before expert dispatch, each expert effectively sees a batch four times larger, substantially improving matrix multiplication efficiency. The cost is increased latency—the first batch must wait for subsequent batches to arrive before processing begins—making this technique unsuitable for interactive inference.

An alternative approach, expert grouping, partitions the $N$ experts into $G$ groups of size $N/G$ and assigns each group to a physical accelerator. Rather than expert-parallel placement where each expert resides on a dedicated device, multiple experts coexist on the same device. Token dispatch then becomes a two-level operation: a cross-device dispatch that routes tokens to appropriate devices based on expert group membership, followed by an intra-device dispatch that routes tokens to specific experts within each group. This topology reduces the number of inter-device communications from $N$ to $G$ at the cost of increased per-device memory pressure, as each device now hosts $N/G$ expert parameter sets. The optimal grouping factor $G$ depends on the network topology's bisection bandwidth relative to device memory capacity—high-bandwidth interconnects like NVLink favor fine-grained expert parallelism with $G \approx N$, while multi-node clusters connected by slower Ethernet or InfiniBand favor coarser grouping with $G \approx$ the number of nodes.

Memory layout optimizations exploit the structure of expert parameters to improve cache locality. Standard implementations allocate each expert's parameters as separate tensors, with $W_{1,i} \in \mathbb{R}^{d \times 4d}$ for expert $i$ residing at a distinct memory address. When the expert computation kernel iterates over multiple experts, each expert's parameters must be loaded from memory, potentially evicting previous experts' data from cache. An alternative blocked layout interleaves expert parameters: the first row of all experts, then the second row of all experts, and so forth. This layout increases cache reuse when multiple experts are processed in sequence, as the cache lines remain valid across expert boundaries. The tradeoff is more complex indexing arithmetic within the kernel and potential loss of alignment guarantees that some matrix multiplication libraries require for peak performance.

Mixed precision and quantization offer orthogonal optimization dimensions. Storing expert parameters in INT8 or even INT4 format reduces memory footprint by $4×$ to $8×$, allowing larger models to fit within device memory and reducing memory bandwidth pressure. Quantization introduces approximation error, but empirical studies demonstrate that expert models tolerate aggressive quantization—particularly for less-frequently-accessed experts—with minimal quality degradation. Per-expert quantization schemes adapt precision to expert importance: frequently-routed experts retain FP16 or even FP32 precision for accuracy, while rarely-accessed experts use INT8 or INT4 to minimize memory cost. Implementing this requires a dynamic precision routing mechanism where the expert dispatch decision jointly determines both which expert to invoke and which precision mode to use, complicating the dispatch logic but yielding substantial memory savings.

The distributed system topology for multi-node expert parallelism introduces network communication as a first-order performance constraint. In a naive implementation, each MoE layer performs an all-to-all communication where every node sends tokens to every other node based on expert assignments. For a cluster of $P$ nodes hosting $N = P \cdot E$ experts with $E$ experts per node, and batch size $B$ tokens, the expected communication volume per layer is $O(kB)$ tokens—every token routes to $k$ experts, potentially on different nodes. Across $L$ layers, total communication is $O(kBL)$. For a model with $L = 64$ MoE layers, $k = 2$, $B = 1024$, $d = 4096$ (half-precision 2 bytes per element), this totals $64 \cdot 2 \cdot 1024 \cdot 4096 \cdot 2 = 1.07$ GB per forward pass. At 100 Gbps network bandwidth, communication alone requires $85$ milliseconds, dominating inference latency if expert computation is efficiently parallelized.

Hierarchical expert placement mitigates this communication bottleneck by exploiting the structure of datacenter network topologies. Modern clusters exhibit hierarchical bandwidth: within a single node, NVLink or similar accelerator interconnects provide $600$ GB/s bidirectional bandwidth; within a rack, InfiniBand or Ethernet provides $200-400$ GB/s; across racks, bisection bandwidth may drop to $50-100$ GB/s. Hierarchical placement assigns experts to nodes such that tokens preferentially route to local experts, falling back to remote experts only when necessary. This requires augmenting the router with topology awareness: rather than learning a distribution over $N$ experts purely based on input content, the router learns a factored distribution that considers both expert suitability and communication cost. The auxiliary loss is extended to penalize cross-rack communications more heavily than intra-rack, encouraging the router to develop locality-aware routing policies.

Pipeline parallelism for MoE layers addresses the latency challenges of deep models with many MoE layers. Sequential layer execution, where layer $\ell$ completes processing all tokens before layer $\ell+1$ begins, leaves most of the cluster idle at any given time—only the nodes hosting experts for the currently-executing layer are active. Pipeline parallelism partitions the input batch into micro-batches and pipelines their execution across layers: while micro-batch $m$ executes at layer $\ell$, micro-batch $m-1$ executes at layer $\ell+1$, and so forth. This increases utilization by overlapping communication and computation across layers. The cost is increased latency for the first token due to pipeline fill time and more complex scheduling logic to manage the pipeline state. For large batch inference, where throughput matters more than first-token latency, pipeline parallelism yields near-linear throughput scaling with the number of layers.

Failure modes in production MoE systems manifest through several characteristic patterns. The first is expert collapse, where routing concentrates on a tiny fraction of experts while the majority remain unused. This occurs when auxiliary loss coefficients are too weak or when training instabilities cause a few experts to dominate early in training, creating a positive feedback loop as those experts receive more gradient updates and become even stronger attractors. Expert collapse degrades model quality by reducing effective capacity and wastes resources on the idle experts. Detection requires monitoring per-expert utilization metrics across batches; mitigation involves increasing auxiliary loss strength, introducing expert dropout that randomly disables experts during training to force routing diversity, or reinitializing collapsed experts with parameters copied from high-utilization experts.

Token dropping under capacity constraints represents a second critical failure mode. When routing imbalance exceeds the capacity factor $\alpha$, tokens are dropped, wasting computation and introducing discrete jumps in the loss landscape that destabilize training. High drop rates—above $5\%$—signal that capacity planning is inadequate for the observed routing distribution. Mitigation strategies include increasing capacity factors at the cost of memory, implementing dynamic capacity with two-phase dispatch, or using expert reassignment policies that route overflowed tokens to their second or third-choice experts rather than dropping them entirely. Monitoring token drop rates per layer provides early warning of capacity issues before they severely impact model quality.

Communication bottlenecks in multi-node deployments manifest as high idle time where accelerators wait for network transfers to complete. Profiling tools like NVIDIA Nsight Systems or custom distributed tracing reveal these bottlenecks through characteristic patterns: compute kernels execute briefly, followed by long gaps waiting on communication collectives. Mitigation requires algorithmic changes—hierarchical placement, locality-aware routing—or infrastructure upgrades to higher-bandwidth networks. In extreme cases, coarsening expert parallelism by increasing expert grouping factor $G$ may reduce communication volume enough to shift the bottleneck back to computation, even though this sacrifices some degree of parallelism.

Numerical instability in router softmax arises when expert count $N$ is very large, causing logit distributions to span many orders of magnitude. Standard softmax implementations compute $\exp(z_i) / \sum_j \exp(z_j)$, which overflows for large positive logits or underflows for large negative logits. Numerically stable implementations subtract the maximum logit before exponentiation: $\exp(z_i - \max_j z_j)$, ensuring the largest exponent is zero. For MoE models with thousands of experts, even this stabilization may prove insufficient if the logit range exceeds the floating-point exponent range. Log-space arithmetic, computing $\log \text{softmax}(z)_i = z_i - \max_j z_j - \log \sum_j \exp(z_j - \max_j z_j)$ and exponentiating only when necessary, provides additional stability at the cost of more expensive logarithm and exponentiation operations.

The ultimate test of a production MoE system is its end-to-end latency-throughput-cost tradeoff. Latency measures time from input to output for a single request, critical for interactive applications. Throughput measures requests processed per second, critical for batch workloads. Cost, measured in accelerator-hours or dollars per million tokens, determines economic viability. These three metrics exist in tension: increasing batch size improves throughput and reduces per-token cost but increases latency; increasing expert parallelism reduces latency but increases cost due to communication overhead and underutilization; increasing model size improves quality but increases all three. The production deployment sweet spot lies at the Pareto frontier where no metric can be improved without degrading another, and this frontier shifts based on workload characteristics, hardware capabilities, and network topology. Navigating this space demands rigorous benchmarking on representative workloads, instrumentation to identify bottlenecks, and principled capacity planning that balances specialization against resource efficiency. The sparse MoE architecture provides the fundamental mechanism to decouple capacity from computation, but realizing this promise in production systems requires mastering every layer of the stack from hardware characteristics through distributed systems protocols to algorithmic refinements of the routing function itself.
