# Lesson 3: Deep Learning Frameworks and Libraries

## 1. First-Principles Intuition & Invariants

A deep learning framework is best understood as a specialized runtime and compiler system for differentiable tensor programs. At its core, a neural network is a composition of affine transformations, nonlinear activations, normalization operations, convolutions, attention mechanisms, and other tensor-valued functions. The framework's job is to represent that composition in a way that is executable on heterogeneous hardware, differentiable with respect to its parameters, and efficient enough to train models containing billions of parameters. For senior engineers and systems architects, the most important mental model is that TensorFlow, PyTorch, and Keras are layered abstractions over the same fundamental substrate: tensors, kernels, memory allocators, schedulers, and communication libraries.

### Invariant 1: Tensor Semantics

A tensor is an N-dimensional array with a shape, a dtype, a device placement, and a memory layout. These four attributes collectively determine every observable behavior of the tensor at the system level.

Shape determines the number of elements and the valid index space. For a rank-3 tensor `T` with shape `(B, H, W)`, the total number of elements is `B * H * W`, and the valid index triple `(i, j, k)` must satisfy `0 <= i < B`, `0 <= j < H`, `0 <= k < W`. Shape mismatches at operation boundaries are the single most common source of silent errors in model code, particularly when broadcasting semantics allow operations to proceed on logically incompatible tensors.

Dtype determines arithmetic precision, numerical range, and hardware routing. The principal dtypes in deep learning are `float32` (the historical default, 32-bit IEEE 754 single precision), `float16` (16-bit IEEE 754 half precision, used in mixed-precision training), `bfloat16` (Brain Float 16, a Google-developed format with the same 8-bit exponent as `float32` but only 7 mantissa bits instead of 10, giving it superior dynamic range over `float16` at the cost of precision), `int8` (8-bit integer, used in post-training quantization and quantization-aware training), and `bool`. The critical distinction between `float16` and `bfloat16` is that `float16` has a maximum representable value of approximately 65504, making it susceptible to overflow during gradient accumulation, whereas `bfloat16` has the same representable range as `float32` and is therefore more numerically stable under automatic mixed precision. Modern accelerators such as the NVIDIA A100 and H100 GPUs have native hardware support for `bfloat16` via their Tensor Cores.

Device placement determines whether the tensor resides in CPU (host) DRAM, GPU (device) VRAM, accelerator memory (e.g., TPU HBM), or a distributed shard. Cross-device operations require explicit data movement through PCIe, NVLink, or the interconnect fabric, and that movement has non-negligible latency and bandwidth cost. Implicit cross-device copies are disabled in most frameworks by default precisely because accidental host-device synchronization is one of the dominant causes of training throughput regression.

Memory layout determines how elements are ordered in physical memory. The two primary layouts are row-major (C-contiguous), where the last axis varies fastest, and column-major (Fortran-contiguous), where the first axis varies fastest. PyTorch and NumPy default to C-contiguous layout. Beyond row vs. column major, strides encode the generalized layout: for a tensor with shape `(d0, d1, d2)`, the stride tuple `(s0, s1, s2)` means that element `T[i, j, k]` is located at element offset `i*s0 + j*s1 + k*s2` from the base pointer; the byte offset is this value multiplied by the element size. A contiguous tensor has strides `(d1*d2, d2, 1)`. A transposed view of that tensor has strides `(1, d2, d2*d1)` without any data movement. Non-contiguous tensors can break kernel assumptions about memory layout and must be explicitly contiguified before passing to libraries such as cuBLAS or cuDNN, which is why `Tensor.contiguous()` appears frequently in PyTorch kernel code.

A framework that violates these invariants produces subtle bugs: silent shape mismatches due to broadcasting, dtype promotion errors that silently upcast or truncate values, device synchronization failures that produce stale reads, and memory corruption from stride-unaware kernels operating on non-contiguous buffers.

### Invariant 2: Differentiability via Reverse-Mode Automatic Differentiation

Modern training relies on reverse-mode automatic differentiation (reverse-mode AD, commonly called backpropagation in the neural network context). The distinction between forward-mode AD and reverse-mode AD is fundamental. Forward-mode AD computes the Jacobian-vector product `J * v` for a tangent vector `v` in a single forward pass, and is efficient when the number of inputs is small relative to the number of outputs. Reverse-mode AD computes the vector-Jacobian product `v^T * J` for a cotangent vector `v` in a single backward pass, and is efficient when the number of outputs is small relative to the number of inputs. Because a neural network loss function maps millions of parameters to a single scalar, reverse-mode AD computes all parameter gradients in a single backward pass, making it the algorithmically correct choice.

Concretely, reverse-mode AD works as follows. During the forward pass, the framework records a directed acyclic graph (DAG) of operations called the computation graph or autograd tape. Each node in the graph corresponds to a tensor-valued operation, and each edge records the data dependency between operations. After the forward pass produces a scalar loss `L`, the backward pass initializes the cotangent of `L` to 1 and propagates it backward through the graph by applying the vector-Jacobian product of each operation's Jacobian. The chain rule ensures that the product of VJPs along any path from `L` to a parameter `theta_i` accumulates the correct partial derivative `dL/d_theta_i`.

In eager systems such as PyTorch, the autograd tape is constructed dynamically as Python code executes. Each `torch.Tensor` with `requires_grad=True` carries a reference to its `grad_fn`, which is the backward function registered at the time the tensor was created. The `grad_fn` stores references to the input tensors (or enough information to recompute them), so that the backward pass can retrieve the activations it needs. This dynamic construction allows arbitrary Python control flow, dynamic shapes, and conditional computation, but it also means that the full graph is not visible until after execution, precluding certain whole-program optimizations.

In graph-based systems such as TensorFlow 1.x (and TensorFlow 2.x with `@tf.function`), the computation graph is traced before execution. `tf.gradients` traverses the static graph and inserts gradient operations as new nodes. This design enables aggressive optimizations: common subexpression elimination, operator fusion, rematerialization (trading computation for memory by recomputing activations during the backward pass rather than storing them), and graph partitioning across devices. The tradeoff is that static graphs are harder to debug, require explicit handling of dynamic shapes via symbolic dimensions, and constrain the Python control flow that can be expressed inside a traced function.

The invariant is that every trainable parameter must lie on a differentiable path from the loss. Non-differentiable operations, such as `argmax`, `round`, or conditional branches that depend on tensor values, break the gradient path. Frameworks handle these in different ways: PyTorch's `torch.no_grad()` context manager explicitly suppresses gradient recording; the straight-through estimator is a common hack that passes gradients through discrete operations as if they were identity functions; and reparameterization tricks (e.g., the reparameterization trick in variational autoencoders) reformulate stochastic operations to push randomness into differentiable parameters.

### Invariant 3: Memory Lifetime and Device Synchronization

Deep learning workloads are among the most memory-intensive computational workloads that exist. A single training step for a large transformer model allocates and frees gigabytes of intermediate activations, gradient buffers, optimizer state tensors, and communication scratch space. The framework must guarantee that no memory is freed while a kernel is still reading it, that memory is not double-freed, and that host-device copies are correctly synchronized.

CUDA execution is asynchronous by default. When PyTorch or TensorFlow enqueues a kernel on a CUDA stream, control returns to the host immediately while the device executes the kernel concurrently. This means that a Python `del tensor` statement does not immediately free GPU memory; the memory can only be freed once all kernels that reference that memory have completed on the device. PyTorch's CUDA allocator manages this through a caching allocator that retains freed blocks in a pool rather than returning them to the OS, and uses CUDA events to track when blocks are safe to reuse. Explicitly calling `torch.cuda.empty_cache()` returns cached blocks to the OS but does not reduce peak memory usage during a training step.

The practical implication for model authors is that memory fragmentation and OOM (out-of-memory) errors are not simply a function of the total tensor sizes; they are also a function of allocation ordering, block size distribution, and the temporal overlap of live tensors. Gradient checkpointing (also called activation recomputation) is the standard technique for trading computation for memory: instead of storing all forward activations for use in the backward pass, the model is divided into segments, and activations at segment boundaries are stored; activations within a segment are recomputed during the backward pass. In PyTorch, this is exposed via `torch.utils.checkpoint.checkpoint`. In TensorFlow, it is exposed via `tf.recompute_grad`.

### Invariant 4: Concurrency and Asynchrony

Training is inherently concurrent across multiple dimensions: CPU threads prepare batches, the GPU executes compute kernels, NIC threads transfer gradients across the network, and storage I/O workers read training data from disk or object storage. The Python Global Interpreter Lock (GIL) prevents multiple Python threads from executing Python bytecode simultaneously, but it does not prevent C++ threads, CUDA kernels, or OS threads from executing concurrently. PyTorch's DataLoader, for example, spawns multiple worker processes (not threads) to work around the GIL, using `multiprocessing.Queue` for inter-process communication. The CUDA driver runs kernels asynchronously on the device regardless of the GIL state.

A correctly designed training system uses CUDA streams to pipeline computation and communication. The default CUDA stream is serialized: operations on the default stream execute in order. Multiple streams can execute concurrently if they do not have data dependencies. A common pattern in distributed training is to issue the all-reduce gradient communication on a separate stream while the backward pass continues on the compute stream, then synchronize the streams before the optimizer step. NCCL (NVIDIA Collective Communications Library) operations are stream-aware and can be interleaved with compute kernels in this way.

Misuse of these mechanisms produces not merely slowness but correctness failures: deadlocks (two operations each waiting for the other on different streams), race conditions (a gradient being read by the optimizer before the all-reduce has completed), and nondeterministic results (from out-of-order atomic accumulation into gradient buffers). CuDNN and cuBLAS both maintain per-stream state, and mixing streams without explicit synchronization is a common source of hard-to-reproduce bugs.

## 2. Framework Landscape: Architecture, Trade-offs, and Positioning

TensorFlow, PyTorch, and Keras occupy different points in the abstraction space, and choosing among them requires a principled understanding of their internal architectures, not merely their surface APIs.

### PyTorch

PyTorch was designed around dynamic, eager execution. Its autograd engine is a C++ library (`torch/csrc/autograd`) that records a DAG of `Function` objects at runtime. Each tensor operation returns a new tensor whose `grad_fn` is set to the backward `Function` for that operation. The backward pass is initiated by calling `.backward()` on the loss scalar, which traverses the DAG in reverse topological order using a queue-based BFS/DFS and calls each `Function`'s `backward` method with the incoming cotangent.

PyTorch's production compilation stack now centers on `torch.compile`, introduced in PyTorch 2.0. Under the hood, `torch.compile` consists of three components: TorchDynamo, TorchInductor, and AOTAutograd. TorchDynamo is a Python bytecode interpreter that captures the computation graph by using CPython's frame evaluation API (`PEP 523`) to intercept the execution of Python functions and trace them into an FX graph without requiring the user to change their code. AOTAutograd (Ahead-of-Time Autograd) uses `functorch`'s function transforms to trace the forward and backward passes together into a joint graph before compilation, enabling cross-pass optimizations. TorchInductor is a code-generating compiler backend that lowers the FX graph to Triton GPU kernels (for CUDA) or C++/OpenMP code (for CPU), performing loop fusion, tiling, and vectorization. The result is that eager PyTorch code, written in an imperative Python style, can be compiled to near-XLA-performance kernels without changing the user-facing API.

PyTorch's distributed training is built on the following primitives: `DistributedDataParallel` (DDP) for data parallelism, `torch.distributed.rpc` for model parallelism and pipeline parallelism, and `FullyShardedDataParallel` (FSDP) for ZeRO-style optimizer state sharding. FSDP shards model parameters, gradients, and optimizer states across data-parallel workers, reducing per-GPU memory consumption proportionally to the number of workers at the cost of all-gather and reduce-scatter communication overhead before and after each layer's forward and backward pass.

### TensorFlow

TensorFlow's historical core design was the static computation graph. In TensorFlow 1.x, users constructed a `tf.Graph` by calling Python API functions that return `tf.Tensor` symbolic handles rather than actual values. The graph was then executed by a `tf.Session`, which compiled and dispatched the graph to available devices. This design enabled XLA (Accelerated Linear Algebra) compilation, which JIT-compiles the entire graph into a single fused kernel sequence, dramatically reducing kernel launch overhead and enabling cross-operation memory optimization.

TensorFlow 2.x made eager execution the default and introduced `tf.function` as the mechanism for opt-in graph tracing. A function decorated with `@tf.function` is traced the first time it is called with a given signature, producing a `ConcreteFunction` backed by a `tf.Graph`. Subsequent calls with compatible signatures dispatch to the cached graph. The tracing process applies AutoGraph, which rewrites Python control flow statements (`if`, `for`, `while`) into equivalent `tf.cond` and `tf.while_loop` graph operations, allowing dynamic-looking Python code to be captured in a static graph.

TensorFlow's deployment story is its strongest differentiator. TensorFlow Lite converts models to a FlatBuffer format for execution on mobile and embedded devices, with support for hardware delegation to device-specific accelerators (e.g., Android NNAPI, Apple Core ML, Hexagon DSP). TensorFlow.js enables model execution in the browser and Node.js. TensorFlow Serving is a production-grade model serving system that manages model versioning, hot-reload, and batching. SavedModel, TensorFlow's serialization format, captures both the graph and the trained weights in a single artifact that can be loaded directly by TF Serving and by TF.js in Node.js, but TFLite and browser-based TF.js require offline conversion to their respective formats.

### Keras

Keras, as of version 3.0, is backend-agnostic. It provides a unified model-building API, `keras.layers`, `keras.Model`, `keras.optimizers`, and `keras.callbacks`, that can run on TensorFlow, JAX, or PyTorch backends.

The backend abstraction in Keras 3.0 is implemented through a strict separation of the frontend API from the backend execution layer. When a user calls `keras.layers.Dense(64, activation='relu')`, the layer's configuration is stored in a backend-agnostic representation. The actual tensor operations—matrix multiplication, bias addition, activation—are dispatched to the configured backend (`tensorflow`, `jax`, or `torch`) through a thin translation layer that maps `keras.ops` primitives to backend-native operations. This enables a single model definition to be trained on JAX (leveraging `jax.jit` and `pmap` for XLA compilation and multi-device parallelism), served with TensorFlow Serving (using the TensorFlow backend for SavedModel export), and fine-tuned on PyTorch (taking advantage of PyTorch's dynamic graph for debugging). The cost of this abstraction is that backend-specific optimizations—custom CUDA kernels, graph surgery, or low-level memory management—require dropping into the native framework. Keras 3.0 models are interoperable: a model trained on the JAX backend can be saved and loaded with the TensorFlow backend, as long as the layer definitions use only the portable `keras.ops` subset.

The evolution from framework-specific ecosystems to backend-agnostic APIs reflects a maturation of the field. TensorFlow's deployment toolchain (TFLite, TF.js, TF Serving) remains unmatched for production systems that span edge devices, browsers, and cloud infrastructure. PyTorch's dynamic execution and research-friendly ergonomics make it the default for rapid prototyping and novel architecture development. JAX's functional programming model and compiler-driven performance make it the framework of choice for large-scale scientific computing and research that requires custom autodiff rules or hardware-specific optimization. The choice of framework is no longer a binding commitment—Keras 3.0 and ONNX allow models to migrate between ecosystems, and the MLIR compiler infrastructure is converging the underlying compilation pipelines. The practitioner's decision now hinges on deployment requirements, team expertise, and the specific performance characteristics of the target workload.
