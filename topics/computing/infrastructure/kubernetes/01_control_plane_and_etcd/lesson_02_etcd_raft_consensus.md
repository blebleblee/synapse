# Lesson 2: Etcd Raft Consensus

## 1. First-Principles Intuition & Invariants

Distributed consensus represents one of the most intellectually demanding challenges in computer science: how do independent processes, each possessing only partial knowledge and subject to arbitrary message delays, agree on a single sequential ordering of state mutations? The problem becomes considerably more acute when we impose the requirement that this agreement must survive network partitions, process crashes, and Byzantine timing failures while maintaining linearizable semantics—meaning every read must reflect the most recent committed write as if all operations occurred atomically on a single logical timeline.

The classical solution to this problem emerged from Leslie Lamport's Paxos algorithm, first published in 1989 in a technical report and later appearing in ACM Transactions on Computer Systems in 1998. Paxos established that consensus could be achieved through a majority quorum mechanism: given N replicas, any write acknowledged by Q = floor(N/2) + 1 replicas becomes durable, because any subsequent quorum of readers must intersect with at least one node that witnessed the write. This mathematical invariant—the quorum intersection property—provides the foundational guarantee that prevents split-brain scenarios where two disjoint subsets of a cluster might independently accept conflicting state transitions.

Despite its theoretical elegance, Paxos proved notoriously difficult to implement correctly. The algorithm's presentation mixed safety properties with liveness optimizations, conflated roles that nodes could assume dynamically, and left critical details like cluster membership changes and log compaction underspecified. Production systems attempting to operationalize Paxos frequently encountered subtle edge cases around leadership flapping, partial log replication during failures, and the complex state machine required to track promises and proposals across multiple rounds of negotiation.

Diego Ongaro and John Ousterhout addressed these implementation challenges in their 2014 USENIX ATC paper introducing the Raft consensus algorithm. Raft deliberately prioritized understandability as a first-class design goal, decomposing the consensus problem into three orthogonal subproblems: leader election, log replication, and safety. Rather than Paxos's symmetrical peer model where any node could simultaneously participate in multiple overlapping consensus rounds, Raft enforces a strong leader model where all client writes flow through a single elected leader that serializes mutations into a replicated log. This architectural constraint simplifies reasoning about system state because at any given term (Raft's logical clock abstraction), at most one leader can exist, and that leader holds the authoritative view of committed state.

The core safety invariant that Raft maintains can be expressed formally: if two logs contain an entry with the same index and term, then the logs are identical in all preceding entries. This property, known as the Log Matching Property, emerges from two mechanisms. First, a leader never overwrites or deletes entries in its own log; it only appends. Second, the AppendEntries RPC that propagates log entries from leader to followers includes the index and term of the immediately preceding entry. A follower only accepts a new entry if its local log contains a matching previous entry, creating an inductive verification chain that detects any inconsistency in log history.

Etcd, the distributed key-value store that serves as Kubernetes's source of truth, implements a production-hardened variant of Raft that extends the academic specification with pragmatic operational features. Every mutation in etcd—whether a Pod creation, ConfigMap update, or Service endpoint modification—translates into a Raft log entry that must achieve quorum replication before the API server acknowledges success to the client. This architecture means that Kubernetes's declarative model, where controllers continuously reconcile observed state toward desired state, rests on a foundation that guarantees linearizable consistency: once the API server confirms a write, that write becomes visible to all subsequent reads across the entire cluster, regardless of which etcd member services the read request.

The quorum mathematics for etcd deployment sizing follow directly from the Q = floor(N/2) + 1 formula. A three-member cluster tolerates one failure because Q = 2, meaning two surviving members can still form a majority. A five-member cluster tolerates two failures with Q = 3. Critically, even-numbered clusters provide no additional fault tolerance: a four-member cluster still only tolerates one failure (requiring three nodes for quorum), wasting resources compared to a three-member deployment. Production Kubernetes control planes standardize on odd-numbered etcd clusters—typically three members for development environments and five members for production systems requiring higher availability—because adding the Nth node to an (N-1)-member cluster where N is even provides redundancy without improving fault tolerance.

The failure model that Raft addresses assumes crash-stop failures where nodes either operate correctly or halt completely, with no Byzantine behavior where nodes might send malicious or corrupted messages. Raft further assumes an asynchronous network model where messages can be delayed, reordered, or dropped, but not corrupted (integrity is delegated to lower layers like TCP checksums and TLS). Under these assumptions, Raft guarantees that the cluster makes progress—meaning clients can successfully write and read data—as long as a majority quorum remains reachable and the network eventually delivers messages within bounded time intervals. The algorithm does not guarantee fairness in the face of sustained asymmetric partitions where a minority remains perpetually isolated, but it does guarantee safety: the isolated minority will never commit writes that conflict with the majority partition's state.

## 2. Core Architecture & Mechanics

Every etcd node exists in exactly one of three states at any moment: follower, candidate, or leader. The state machine begins with all nodes as followers. Time in Raft is divided into terms, each represented by a monotonically increasing integer that acts as a logical clock. Terms provide a mechanism to detect stale information: any message containing a term older than a node's current term gets rejected immediately, and any message containing a newer term causes the recipient to update its local term and revert to follower state if necessary.

Followers remain passive, responding only to RPCs from leaders and candidates. They maintain a randomized election timeout, typically between 150 and 300 milliseconds in etcd's default configuration. This randomization serves a crucial purpose: it breaks symmetry and prevents simultaneous candidacy declarations that would split votes. When a follower's election timeout expires without receiving communication from a valid leader, it transitions to the candidate state and initiates an election.

A candidate increments its current term, votes for itself, and sends RequestVote RPCs in parallel to all other cluster members. Each node can grant at most one vote per term, and it votes for the first candidate that requests its vote, provided the candidate's log is at least as up-to-date as the voter's log. This log comparison uses a two-step process: first compare the term of the last entry in each log, selecting the log with the higher term; if terms are equal, select the longer log. This ordering ensures that any candidate that wins an election possesses all committed entries from previous terms, a property critical to maintaining safety.

Three outcomes are possible during an election. First, the candidate receives votes from a majority of the cluster, transitions to leader state, and begins sending periodic AppendEntries heartbeats to all followers to assert authority and prevent new elections. Second, the candidate receives an AppendEntries RPC from another node claiming to be leader with a term greater than or equal to the candidate's current term, in which case the candidate recognizes the legitimate leader and reverts to follower. Third, the election timeout elapses with no winner because votes were split among multiple candidates. In this case, each candidate that failed to win starts a new election by incrementing its term and sending fresh RequestVote RPCs. The randomized timeout durations make it statistically unlikely that subsequent elections will also split, causing the cluster to converge on a leader within a few rounds.

Once elected, the leader assumes responsibility for all client interactions and log replication. Client write requests arrive at the leader, which appends a new entry to its local log with the current term and index, then replicates this entry to followers via AppendEntries RPCs. Each AppendEntries message carries one or more log entries along with metadata including the leader's term, the index and term of the entry immediately preceding the new entries (prevLogIndex and prevLogTerm), and the leader's commit index—the highest index known to be replicated on a majority of nodes.

A follower receiving an AppendEntries RPC performs several consistency checks. If the message's term is less than the follower's current term, it rejects the request, signaling to the sender that it has stale information. If the follower's log does not contain an entry at prevLogIndex with term matching prevLogTerm, it rejects the request, indicating a log inconsistency. This consistency check enforces the Log Matching Property: the leader will not advance a follower's log until the follower's history aligns with the leader's history at the insertion point. Upon rejection, the leader decrements the nextIndex for that follower and retries with an earlier prevLogIndex, effectively binary searching backward through the log to find the point of divergence. Once the follower accepts an AppendEntries RPC, it appends the new entries (deleting any conflicting entries that follow prevLogIndex) and updates its commit index to the minimum of the leader's commit index and the index of the last newly appended entry.

The leader tracks the highest index replicated on each follower using a nextIndex array. When the leader observes that a log entry has been replicated on a majority of nodes, it advances its commit index to that entry's index. Committed entries are applied to the state machine—in etcd's case, the key-value store—in order. The leader includes its commit index in subsequent AppendEntries RPCs, allowing followers to advance their own commit indexes and apply entries to their state machines. This two-phase protocol—replication followed by commitment—ensures that once an entry is committed, it will never be lost or overwritten, even if leaders change.

Leadership changes introduce the possibility of log inconsistencies. A follower that was partitioned during a previous term may have missing entries, or a follower that was briefly a leader in an aborted term may have extra uncommitted entries. Raft's design guarantees that the new leader's log contains all committed entries from previous terms, so the leader can safely overwrite any conflicting uncommitted entries on followers. The leader never deletes or overwrites entries in its own log; it brings followers into alignment by replaying its log forward from the point of divergence.

Etcd extends the basic Raft protocol with several production-oriented features. Log compaction via snapshotting prevents unbounded log growth: when the log exceeds a configurable threshold (default 10,000 entries), etcd captures a snapshot of the current state machine and discards all log entries up to the snapshot's index. Followers that fall too far behind receive the snapshot via an InstallSnapshot RPC rather than replaying the entire log. Membership changes—adding or removing cluster members—use Raft's joint consensus mechanism, where the cluster transitions through an intermediate configuration that requires majorities in both the old and new configurations before committing to the new configuration exclusively. This approach prevents dangerous scenarios where old and new majorities could elect separate leaders.

Etcd's implementation also includes optimizations for read performance. Pure Raft requires that even reads go through the leader and achieve quorum to guarantee linearizability, a potential bottleneck for read-heavy workloads. Etcd supports several read consistency levels: linearizable reads that contact the leader and wait for heartbeat acknowledgment from a majority; serializable reads that may return slightly stale data from followers; and read-through-leader mode where the leader services reads from its local state after confirming leadership through a recent heartbeat round. Kubernetes primarily uses linearizable reads for control plane operations where consistency is paramount.

The interaction between etcd and Kubernetes's API server deserves special attention. When a client issues a write request—say, creating a new Pod—the API server validates the request, assigns default values, and forwards the resulting object to etcd via a Put operation. This Put becomes a Raft log entry on the leader, replicates to followers, and commits once a majority acknowledges. Only after commitment does the API server return success to the client. Subsequent watch requests from controllers trigger on the committed index, ensuring that controllers observe state changes in the exact order they were committed. This deterministic ordering is what allows Kubernetes's level-triggered controllers to work correctly: each controller processes the committed log of state changes, updating resources and writing status back through the same Raft-replicated path.

Network partitions illustrate Raft's safety guarantees in practice. Consider a five-member etcd cluster that experiences a partition isolating two members from the three-member majority. The three-member partition can elect a leader (requiring two votes plus the leader's self-vote) and continue processing writes, advancing the commit index as entries replicate across the majority. The two-member minority partition cannot elect a leader because neither candidate can obtain three votes. Clients connected to the minority partition will experience timeouts or connection failures, but critically, the minority will not accept any writes or return stale reads for linearizable queries. When the partition heals, the minority members will receive AppendEntries RPCs from the majority's leader, discover their logs are behind, and synchronize by accepting the majority's log entries (potentially discarding uncommitted entries from a short-lived leader in the minority partition before it lost its majority).
