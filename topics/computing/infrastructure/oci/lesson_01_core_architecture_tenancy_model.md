# Lesson 1: Core Architecture, Identity Domains, Tenancy Isolation Model

## 1. First-Principles Intuition & Invariants

Oracle Cloud Infrastructure presents a radical departure from the identity and isolation models pioneered by early public cloud providers. Where legacy platforms anchored their authorization models to flat account hierarchies with bolt-on organizational overlays, OCI architects embedded multi-tenancy isolation, hierarchical resource organization, and federated identity as first-class primitives in the platform's foundational control plane. Understanding OCI's architecture demands we first grasp the invariants governing tenancy isolation, the recursive compartment tree structure, and the policy evaluation engine that enforces authorization through explicit deny-by-default semantics.

At the root of every OCI deployment sits the **tenancy**, a globally unique isolation boundary that represents the apex of an organization's cloud footprint. The tenancy is not merely an administrative convenience or billing construct—it is a cryptographically enforced security domain backed by dedicated key material, isolated control plane state, and physical network segmentation. When you provision a tenancy, OCI allocates a unique Oracle Cloud Identifier (OCID) that serves as the immutable root of all resource namespaces within that isolation boundary. This OCID follows the canonical format `ocid1.<RESOURCE_TYPE>.<REALM>.<REGION>.<UNIQUE_ID>`, embedding geographic realm, regional placement, and cryptographic uniqueness into every resource reference. The invariant here is absolute: no API call, no network packet, and no control plane operation can traverse tenancy boundaries without explicit cross-tenancy peering or federation agreements. This isolation extends from the virtualization layer—where compute instances occupy dedicated hardware enclaves—through the network fabric, where Virtual Cloud Networks (VCNs) exist in non-overlapping IPv4/IPv6 address spaces, and into the control plane, where etcd-backed state machines maintain separate key-value stores per tenancy.

Within the tenancy boundary, OCI introduces the **compartment tree**, a hierarchical namespace that enables fine-grained resource organization and policy inheritance. Unlike flat tagging schemes or project-based grouping, compartments form a directed acyclic graph (DAG) rooted at the tenancy itself, with each compartment acting as a logical container for resources and a policy attachment point. The tree structure enforces a strict parent-child relationship: every compartment except the root must have exactly one parent, and resources placed within a compartment inherit the cumulative policy statements evaluated along the path from that compartment to the root. This recursive evaluation model mirrors the UNIX filesystem permission model but operates on cloud resources rather than inodes. The architectural insight here is profound—by embedding policy inheritance into the compartment DAG, OCI transforms authorization from a flat, resource-scoped decision into a hierarchical, path-dependent evaluation that respects organizational structure. A compute instance placed in a compartment nested three levels deep will have its access governed by policies attached at the root tenancy, the intermediate parent compartments, and the leaf compartment itself, with more specific (deeper) policies overriding or augmenting broader (higher) statements.

The identity layer in OCI decouples authentication sources from authorization targets through a federated architecture centered on **Identity Domains**. Traditional cloud platforms conflate user directories, service accounts, and authorization policies into monolithic Identity and Access Management (IAM) services. OCI instead treats identity as a pluggable abstraction: an Identity Domain is a SAML 2.0 or OpenID Connect (OIDC) compliant directory service that federates authentication requests to external providers—Active Directory, Okta, Azure AD, or any standards-compliant IdP—while maintaining a local shadow directory for authorization mapping. When a user authenticates, OCI receives a signed assertion containing group memberships and attributes, then maps these federated identities to local IAM groups through configurable attribute-based rules. The critical invariant is that authentication and authorization remain orthogonal: the external IdP attests to user identity and group membership, while OCI's policy engine independently evaluates whether those groups possess the necessary grants to perform requested operations. This separation enables zero-trust architectures where authentication strength, session duration, and multi-factor enforcement live in the IdP, while authorization policies remain under strict infrastructure control within OCI.

Policy evaluation in OCI follows an explicit deny-by-default model grounded in predicate logic. Every policy statement consists of a subject (which principals), a verb (what actions), a resource-type (on which resource kinds), a location (in which compartments), and optional conditions (under what constraints). The policy engine evaluates these statements through a three-phase process: identity resolution, resource matching, and condition evaluation. During identity resolution, the engine expands federated group memberships and dynamic group predicates into a set of principal OCIDs. Resource matching then filters applicable policy statements by comparing the target resource's compartment path against the policy's location clause, leveraging the compartment tree's hierarchical structure. Finally, condition evaluation applies runtime predicates—request time, source IP, resource tags, or custom attributes—to determine if the statement grants access. The absence of any matching allow statement results in an implicit deny, and explicit deny statements override all allow grants. This composition of additive grants with explicit denials enables defense-in-depth: broad organizational policies grant baseline permissions, while targeted deny statements enforce compliance boundaries, separation of duties, or incident response controls.

Resource isolation boundaries in OCI extend beyond identity and authorization into the physical and logical networking layers. Every tenancy provisions Virtual Cloud Networks (VCNs) that exist as software-defined Layer 3 networks with RFC 1918 private addressing or provider-assigned IPv6 prefixes. VCNs are compartment-scoped resources, inheriting the policy and organizational structure of their parent compartment while enforcing strict network isolation through stateful security lists and network security groups. The control plane maintains a distributed flow table that programs hardware TCAM (Ternary Content Addressable Memory) entries on the physical network fabric, ensuring that packets sourced from one VCN cannot traverse into another without explicit peering or NAT gateway egress. This hardware-accelerated isolation means that even under control plane failure, the data plane maintains tenancy boundaries through fast-path packet filtering. Inter-tenancy communication requires explicit peering constructs—Local Peering Gateways (LPGs) for intra-region connectivity or Remote Peering Connections (RPCs) for cross-region links—each of which demands mutual consent and cryptographic key exchange between tenancy administrators.

The foundational insight unifying these architectural components is that OCI treats isolation and organization as co-equal design constraints rather than afterthoughts layered atop a flat resource model. The tenancy provides cryptographic and physical isolation, the compartment tree enforces organizational hierarchy and policy inheritance, Identity Domains federate authentication while preserving local authorization control, and the policy engine adjudicates access through explicit, auditable predicate evaluation. This architecture scales from single-team deployments to enterprises with thousands of compartments, millions of resources, and complex federated identity topologies, because the fundamental primitives—hierarchical namespaces, path-dependent evaluation, and explicit deny-by-default semantics—remain invariant across scale.

## 2. Core Architecture & Mechanics

The OCI control plane architecture resembles a distributed state machine where tenancies, compartments, identity domains, and policies exist as strongly consistent, versioned objects stored in a replicated key-value store. At the heart of this system lies a Raft-based consensus layer that maintains quorum across availability domains within each region. When you create a compartment or attach a policy, the API request flows through a regional API gateway that performs initial authentication by validating the request signature against cached public keys. The gateway then forwards the authenticated request to a policy evaluation service that queries the compartment tree, expands group memberships, and executes the policy decision algorithm. Upon authorization success, the request reaches the resource manager service responsible for the target resource type—Identity, Networking, Compute, or Storage—which writes the desired state to the backing store and returns a canonical OCID.

The compartment tree itself exists as a specialized index structure within the control plane's metadata service. Each compartment object contains a parent OCID reference, a name, a description, and a lifecycle state field (ACTIVE, INACTIVE, DELETED). The tree traversal algorithm begins at any compartment and walks parent references until reaching the root tenancy, building a path vector used during policy evaluation. This path vector caching strategy means that policy evaluation for a resource five levels deep requires at most five OCID lookups and a bounded number of policy statement scans proportional to the depth, not the total number of compartments. The control plane maintains inverted indices mapping resource OCIDs to compartment OCIDs, enabling efficient queries like "list all compute instances in compartment X and all descendant compartments."

```
Compartment Tree Structure & Policy Evaluation Path

Tenancy (Root)
 OCID: ocid1.tenancy.oc1..unique_id_root
 Attached Policies: [TenancyAdminPolicy, BaselineAuditPolicy]
   │
   ├── Compartment: Production
   │    OCID: ocid1.compartment.oc1..unique_id_prod
   │    Path: [tenancy, production]
   │    Attached Policies: [ProdNetworkPolicy, ProdStoragePolicy]
   │    │
   │    ├── Compartment: Prod-Frontend
   │    │    OCID: ocid1.compartment.oc1..unique_id_prod_fe
   │    │    Path: [tenancy, production, prod-frontend]
   │    │    Attached Policies: [FrontendComputePolicy]
   │    │
   │    └── Compartment: Prod-Backend
   │         OCID: ocid1.compartment.oc1..unique_id_prod_be
   │         Path: [tenancy, production, prod-backend]
   │         Attached Policies: [BackendDatabasePolicy]
   │
   └── Compartment: Development
        OCID: ocid1.compartment.oc1..unique_id_dev
        Path: [tenancy, development]
        Attached Policies: [DevFullAccessPolicy]

Policy Evaluation for Instance in Prod-Backend:
  1. Resolve principal identity (user or dynamic group)
  2. Build compartment path: [tenancy, production, prod-backend]
  3. Collect policies: TenancyAdminPolicy, BaselineAuditPolicy,
                       ProdNetworkPolicy, ProdStoragePolicy,
                       BackendDatabasePolicy
  4. Evaluate statements in order: root → leaf
  5. Apply condition predicates (time, IP, tags)
  6. Return allow/deny decision
```

Identity Domains introduce a federated directory service that operates as a logically isolated namespace within the tenancy. Each Identity Domain maintains its own user registry, group definitions, OAuth applications, and federation trust relationships, while sharing the tenancy's global policy namespace. When you create a user in an Identity Domain, OCI provisions a local user object with a unique OCID, stores credential material in an encrypted vault, and indexes group memberships for rapid policy evaluation. Federation mappings transform SAML attributes or OIDC claims into group assignments through rule-based transformations. A federation rule might specify: "For all assertions from IdP X where the 'department' attribute equals 'Engineering', assign membership in the local group 'Engineers'." These rules execute during the authentication flow, before policy evaluation begins, ensuring that federated users receive consistent authorization decisions based on their mapped group memberships.

The policy language itself is a domain-specific syntax built atop a formal grammar that compiles to an abstract syntax tree (AST) for evaluation. A canonical policy statement takes the form:

```
Allow group <group_name> to <verb> <resource_type> in <location> where <conditions>
```

The verb specifies an action or action family: `inspect`, `read`, `use`, `manage`. These verbs form a strict hierarchy where `manage` subsumes `use`, which subsumes `read`, which subsumes `inspect`. Resource types map to OCI service namespaces: `instance`, `volume`, `vcn`, `bucket`. The location clause can target the tenancy root, a specific compartment by name or OCID, or a compartment and all descendants using the `compartment <name> and all descendant compartments` syntax. Condition clauses evaluate predicates against request context: `request.user.mfaAuthenticated = 'true'`, `target.resource.tag.environment = 'production'`, `request.networkSource.name = 'CorporateNetworkSource'`. The policy compiler parses these statements into an intermediate representation that indexes by subject and location, enabling efficient lookup during evaluation.

Dynamic groups extend the identity model beyond human users and service accounts to support resource-based identity. A dynamic group defines a matching rule that evaluates resource attributes to determine membership. For example, you might create a dynamic group "ComputeInstancesInProdBackend" with the matching rule: `All {instance.compartment.id = 'ocid1.compartment.oc1..unique_id_prod_be'}`. Any compute instance created in that compartment automatically gains membership in the dynamic group, enabling policies like "Allow dynamic-group ComputeInstancesInProdBackend to read secret-bundle in compartment Prod-Backend." This capability eliminates the need for long-lived service credentials—compute instances authenticate to the OCI API using instance principals, a cryptographic identity derived from the instance metadata service and attested by the virtualization layer. The instance metadata service exposes an OAuth 2.0 token endpoint at `http://169.254.169.254/opc/v2/instance/` that returns short-lived bearer tokens signed by the control plane's certificate authority, embedding the instance OCID and dynamic group memberships in the token claims.

Network isolation boundaries integrate tightly with the compartment and policy model through a combination of Virtual Cloud Networks (VCNs), subnets, security lists, and network security groups. Each VCN exists within a single compartment and defines an RFC 1918 CIDR block such as `10.0.0.0/16`. Subnets partition the VCN's address space into smaller prefixes—`10.0.1.0/24` for a web tier, `10.0.2.0/24` for an application tier—and attach regional or availability-domain-specific routing tables. Security lists act as stateful, subnet-level firewalls that default-deny all inbound traffic and default-allow all outbound traffic. Network security groups provide finer-grained, resource-level security by grouping instances and enforcing rules that reference other security groups rather than raw CIDR blocks. The control plane programs these rules into a distributed flow table that leverages hardware TCAM on physical switches, ensuring line-rate packet filtering without software inspection overhead. The network fabric maintains a per-VCN flow state table that tracks TCP connection tuples and permits return traffic for established flows, implementing true stateful firewalling at scale.

Cross-tenancy communication requires explicit peering constructs that establish mutual trust. A Local Peering Gateway (LPG) connects two VCNs within the same region, requiring that administrators from both tenancies create LPG resources and exchange acceptor/requestor peering relationships. The control plane verifies cryptographic signatures on the peering request, ensuring that both parties possess the necessary `manage vcns` permission in their respective tenancies. Once established, the LPG programs routing table entries that direct traffic destined for the peer VCN's CIDR through the peering link, and the network fabric enforces security list rules on both sides of the connection. For cross-region connectivity, Remote Peering Connections (RPCs) extend this model across OCI's global backbone, leveraging encrypted WAN links that traverse Oracle's private fiber network rather than the public internet. The critical insight is that peering is always bilateral and explicit—no ambient connectivity exists between tenancies or even between VCNs within a tenancy until administrators deliberately construct the network topology.

## 3. High-Performance Optimization & Failure Modes

Optimizing compartment tree design for large-scale deployments demands careful attention to policy evaluation latency and the combinatorial explosion of inheritance paths. A common anti-pattern emerges when organizations create excessively deep compartment hierarchies—eight or ten levels deep—attempting to mirror complex organizational charts. Because policy evaluation walks the compartment path from leaf to root, collecting and evaluating statements at each level, depth directly impacts API latency. A well-architected compartment tree rarely exceeds four levels: tenancy root, business unit or environment, application, and resource tier. This constraint forces architects to leverage tagging and network segmentation rather than compartment proliferation for fine-grained organization. Tagging provides a multi-dimensional classification space that avoids the rigid tree structure—a compute instance can simultaneously carry tags for `environment=production`, `application=webstore`, `costcenter=marketing`, enabling policy conditions and reporting queries that cut across the organizational hierarchy without requiring dedicated compartments.

Policy design at scale requires understanding the evaluation order and specificity rules that govern statement precedence. Policies attached to the root tenancy apply to all resources in all compartments, making them ideal for broad compliance controls like "Deny all users to manage policies in tenancy where request.user.mfaAuthenticated != 'true'." Child compartments inherit these statements and can only further restrict access through additional deny statements or grant additional permissions through allow statements. A critical optimization technique involves minimizing the number of policy objects by consolidating related statements into fewer, larger policies rather than creating many small, single-statement policies. Each policy object imposes a fixed evaluation overhead for parsing and indexing, so a policy containing twenty carefully organized statements evaluates more efficiently than twenty separate policies each containing one statement. However, this consolidation must balance against the operational need for atomic policy updates—modifying a single statement in a large policy requires updating the entire object, triggering a global cache invalidation across the control plane.

Dynamic group matching rules present a subtle performance consideration when formulated carelessly. A poorly constructed matching rule like `Any {resource.type = 'instance'}` evaluates to true for every compute instance in the tenancy, creating a dynamic group with potentially thousands or millions of members. Policy evaluation for such groups requires scanning the entire dynamic group membership set during principal resolution, introducing latency proportional to group size. High-performance dynamic groups leverage specific compartment constraints: `All {instance.compartment.id = 'ocid1.compartment.oc1..specific_id'}` restricts membership to a bounded set of instances, enabling the policy engine to maintain a compact membership index. For deployments with frequent instance churn, consider whether dynamic groups are necessary at all—instance principals already provide resource-based identity without the group membership overhead, and policies can directly target resource types within specific compartments.

Identity Domain federation introduces authentication latency and availability dependencies on external IdPs that demand careful architectural consideration. When a user authenticates through a federated Identity Domain, OCI redirects the authentication request to the external SAML or OIDC provider, waits for a signed assertion, validates the signature against cached certificates, executes federation mapping rules, and caches the resulting group memberships for the session lifetime. This round-trip adds latency proportional to the IdP's response time and introduces a hard dependency—if the external IdP is unreachable, federated authentication fails even when the OCI control plane remains fully operational. High-availability architectures mitigate this risk by provisioning emergency break-glass users directly in OCI's local Identity Domain, bypassing federation entirely. These local users must have sufficiently broad permissions to recover from federation failures and should authenticate using hardware security keys or certificate-based authentication to eliminate credential theft vectors. Session lifetime tuning provides another optimization lever: longer session timeouts reduce authentication round-trips at the cost of delayed revocation propagation when users are removed from IdP groups.

Network security list management at scale requires transitioning from subnet-level security lists to resource-level network security groups (NSGs). Security lists attach to subnets and apply uniformly to all resources within that subnet, forcing architects to create proliferating subnet designs where each combination of security requirements demands a dedicated subnet. This approach exhausts the available address space in a VCN CIDR and creates operational complexity when instances need to move between security contexts. Network security groups instead attach directly to virtual network interface cards (VNICs) and support dynamic membership, enabling a single subnet to host resources with heterogeneous security requirements. NSG rules can reference other NSGs by OCID, expressing policies like "Allow TCP port 443 from NSG-WebTier to NSG-AppTier," eliminating the brittle CIDR dependencies that plague security list designs. The control plane implements NSGs through per-VNIC flow table programming, ensuring that rule complexity scales with the number of resources rather than the number of subnets.

Failure modes in the compartment model center on accidental deletion and lifecycle state propagation. When a compartment enters the DELETING state, all resources within that compartment must first transition to DELETED or be moved to another compartment. This recursive deletion model provides protection against accidental data loss but can trap unwary operators: attempting to delete a compartment with thousands of resources triggers a cascade of API calls that may exhaust rate limits or encounter partial failures, leaving the compartment in an indeterminate state. Production architectures should enforce compartment deletion safeguards through IAM policies that deny `manage compartments` permissions except to a dedicated administrative group, and implement operational runbooks that first enumerate and archive resources before initiating compartment deletion. Tag-based policies offer an additional safeguard: "Deny group Developers to manage compartments in tenancy where target.compartment.tag.protected = 'true'."

Policy evaluation failures manifest as authorization denials that can be opaque without proper logging and observability. The OCI Audit service records every API call, capturing the principal OCID, the target resource, the requested action, and the policy evaluation decision including which policy statements matched. When troubleshooting unexpected denials, query the Audit service for the specific API call, examine the policy evaluation detail, and verify the principal's group memberships at the time of the request. A common pitfall involves stale group membership caches—federated group assignments update during authentication, not in real time as IdP groups change. Users experiencing permission errors after a group membership change must sign out and re-authenticate to refresh their session's cached group memberships. Local Identity Domain group memberships update synchronously, but policy attachments and modifications propagate through the control plane's cache hierarchy with eventual consistency, typically reaching all regional API gateways within seconds but occasionally requiring minutes during control plane load spikes.

Cross-tenancy peering failures typically stem from mismatched routing configurations or asymmetric security list rules. When peering two VCNs via LPG or RPC, both sides must configure routing table entries that direct traffic for the peer CIDR through the peering gateway, and both sides must configure security list or NSG rules permitting the desired traffic patterns. A frequent misconfiguration involves configuring the requestor's routing and security correctly while neglecting the acceptor's configuration, resulting in traffic successfully reaching the peer but return packets being dropped. Packet-level troubleshooting requires leveraging OCI's VCN Flow Logs, which capture NetFlow-style records of all packets traversing VNICs, including drop reasons encoded as metadata fields. Flow logs integrate with OCI Logging Analytics, enabling queries like "show all TCP SYN packets from CIDR 10.0.0.0/16 dropped by security list rules in the last hour." For encrypted RPC links, verify that both tenancies have established the cryptographic handshake by examining the RPC lifecycle state—stuck in PROVISIONING indicates control plane issues, while PEERED confirms active connectivity.

Identity Domain certificate rotation and federation trust failures represent low-frequency but high-impact operational events. SAML and OIDC federation rely on X.509 certificates to validate assertion signatures and establish trust anchors. When an external IdP rotates its signing certificate, OCI's cached certificate must be updated to reflect the new public key; failure to do so results in signature validation failures that block all federated authentication. High-reliability deployments automate certificate monitoring by periodically querying the IdP's metadata endpoint—exposed at the SAML metadata URL or OIDC discovery document—and comparing the advertised certificates against OCI's configured trust anchors. Pre-expiration alerts trigger manual or automated certificate updates, preventing authentication outages. For environments requiring zero-downtime rotation, configure overlapping validity periods where the IdP signs assertions with the new certificate while OCI trusts both old and new certificates during a transition window.

Rate limiting and API throttling introduce another class of failure modes in large-scale compartment and policy operations. OCI enforces per-tenancy and per-region rate limits on control plane API calls, typically expressed as requests per second or requests per minute depending on the service. Bulk operations—creating hundreds of compartments, attaching dozens of policies, or provisioning thousands of compute instances—can exhaust these limits, resulting in HTTP 429 responses. Production automation should implement exponential backoff with jitter when encountering rate limits, retrying failed requests after exponentially increasing delays randomized by a jitter factor to prevent thundering herd effects. For scheduled workloads that predictably generate API load spikes, consider partitioning operations across multiple regions or spreading create requests over time windows using controlled-rate queues. The OCI SDKs and Terraform provider implement automatic retries with backoff for transient failures, but custom automation must explicitly handle rate limiting to achieve reliability at scale.
