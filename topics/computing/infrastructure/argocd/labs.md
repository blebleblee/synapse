# Operational Verification Labs: Argocd

## Objective & Environment Setup

ArgoCD operates as a declarative GitOps continuous delivery controller for Kubernetes, implementing a level-triggered reconciliation loop that continuously observes Git repository state and converges live cluster resources toward declared manifests. The core architecture comprises several tightly coupled subsystems: the `argocd-server` exposes a gRPC API and serves the web UI; the `argocd-repo-server` performs Git clones, Helm template rendering, and Kustomize transformations in isolated ephemeral containers; the `argocd-application-controller` watches Application CRDs and orchestrates the sync loop against target Kubernetes clusters; and the `argocd-dex-server` provides OAuth2/OIDC federation when external authentication is required. Each component maintains persistent connections to etcd-backed Kubernetes API servers, Redis for caching repository metadata and manifests, and optionally external Git repositories over HTTPS or SSH.

Understanding ArgoCD's operational health requires inspecting not just pod restarts and HTTP response codes, but the internal state machines governing application sync phases (OutOfSync, Syncing, Synced, Degraded), resource health assessments derived from custom Lua scripts, and the distributed consistency guarantees between the controller's informer caches and the authoritative etcd keyspace. This lab sequence walks through live subsystem inspection using `kubectl`, network traffic analysis with `tcpdump` and `ss`, performance profiling with `perf`, fault injection to validate resiliency boundaries, and comprehensive diagnostic procedures that mirror production incident response workflows.

Begin by provisioning a Kubernetes cluster with at least three worker nodes to observe distributed behavior under load. Install ArgoCD into the `argocd` namespace using the standard manifest, ensuring that the Redis deployment uses persistent volumes to prevent cache invalidation across pod restarts. Verify that your local workstation has `kubectl` configured with cluster-admin privileges, `tcpdump` for packet capture, `ss` from the `iproute2` suite for socket statistics, `perf` for CPU profiling, and `etcdctl` if your cluster exposes etcd endpoints. The exercises assume a Linux environment with kernel 5.10 or later to access modern eBPF tooling, though core diagnostics remain functional on older kernels through traditional tracing mechanisms.

Install ArgoCD with the following command, which deploys all core components and establishes the necessary RBAC policies for cross-namespace application management:

```bash
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
```

Wait for all pods to reach Running state and verify that the `argocd-application-controller` has successfully listed all namespaces by inspecting its logs for the initial informer synchronization message. Retrieve the initial admin password from the autogenerated Secret and change it immediately to prevent unauthorized access:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
argocd login localhost:8080 --username admin --password <retrieved-password> --insecure
argocd account update-password
```

Expose the `argocd-server` service using a port-forward to localhost, which simplifies network diagnostics by isolating application-layer issues from Ingress or LoadBalancer provisioning delays:

```bash
kubectl port-forward svc/argocd-server -n argocd 8080:443 &
```

With the environment operational, the subsequent exercises dissect ArgoCD's internal state machines, measure reconciliation throughput under synthetic application load, inject controlled failures to validate self-healing behavior, and construct a reusable diagnostic runbook for production troubleshooting.

## Exercise 1: Live State & Internal Subsystem Inspection

ArgoCD's operational correctness depends on the synchronization of multiple asynchronous subsystems, each maintaining its own view of cluster and repository state. The `argocd-application-controller` runs a set of informer goroutines that watch Application CRDs, Deployments, Services, ConfigMaps, and other resource types across all managed namespaces, constructing an in-memory cache that mirrors the authoritative etcd keyspace. When an Application manifest declares a target Git revision and a destination namespace, the controller delegates to the `argocd-repo-server` to clone the repository, render Helm charts or Kustomize overlays, and return a normalized set of Kubernetes manifests. The controller then computes a three-way diff between the desired state (Git), the live state (Kubernetes API), and the last-synced state (stored in the Application's status field), applying changes via strategic merge patches or server-side apply depending on the configured sync options.

Begin by creating a test Application that tracks a public Git repository containing a simple Nginx Deployment and Service. This minimal workload isolates ArgoCD's reconciliation logic from application-specific complexity and provides a stable baseline for observing internal state transitions:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-test
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

Apply this Application and immediately watch the controller logs to observe the reconciliation sequence. The controller emits structured log entries at each phase: fetching the repository manifest, computing the diff, queuing the sync operation, applying resources, and finally assessing health status:

```bash
kubectl apply -f nginx-test-app.yaml
kubectl logs -n argocd deployment/argocd-application-controller --tail=100 -f
```

Within seconds, you will observe log entries indicating that the controller detected the new Application, triggered a repository refresh, computed differences, and initiated a sync. The log lines include the Application name, sync revision SHA, and the specific resources being created or updated. Filter the logs to isolate the reconciliation loop for this specific Application by grepping for its name:

```bash
kubectl logs -n argocd deployment/argocd-application-controller --tail=500 | grep "nginx-test"
```

Now inspect the Application's live status using `kubectl` to examine the custom resource's status subresource, which contains the computed sync state, health assessments for each child resource, and the operation history:

```bash
kubectl get application nginx-test -n argocd -o yaml
```

The `status.sync.status` field will display `Synced` once all resources match the declared Git state, while `status.health.status` reflects the aggregated health of child resources, typically `Healthy` when all Pods are running and passing readiness probes. Drill into the `status.resources` array to see per-resource health and sync states, which ArgoCD derives from custom Lua health assessment scripts shipped with the controller. For a Deployment, the health script checks that `status.replicas`, `status.updatedReplicas`, and `status.availableReplicas` all equal `spec.replicas`, ensuring that the desired rollout has completed without degradation.

Next, examine the network connectivity between the controller and the Kubernetes API server by capturing the gRPC traffic over the in-cluster TLS connection. The controller maintains a watch stream for each informer, translating Kubernetes watch events into cache updates that drive reconciliation. Use `ss` to enumerate all established TCP connections from the controller pod to the API server's ClusterIP:

```bash
CONTROLLER_POD=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-application-controller -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n argocd $CONTROLLER_POD -- ss -tnp | grep :443
```

You will observe multiple connections to the Kubernetes API server's service ClusterIP, each corresponding to a distinct informer watch stream. The output includes the local and remote socket addresses, the TCP state (ESTAB for established), and the associated process ID. To measure the throughput of these watch streams, run `ss` with the `-i` flag to display internal TCP socket information including congestion window size, retransmission counts, and round-trip time:

```bash
kubectl exec -n argocd $CONTROLLER_POD -- ss -tin | grep :443
```

The `cwnd` (congestion window) value indicates how many packets can be in flight simultaneously, while `rtt` (round-trip time) measures the latency to the API server. In a healthy cluster, RTT should remain below 10 milliseconds for in-cluster communication, and retransmissions should be zero. Elevated RTT or non-zero retransmissions suggest network congestion, API server throttling, or node-level packet loss that will degrade ArgoCD's reconciliation responsiveness.

Now inspect the `argocd-repo-server` to understand how Git repository operations and manifest rendering occur. The repo server exposes a gRPC API that the controller invokes to fetch manifests for a given Application. Each request spawns an ephemeral `argocd-repo-server` job that clones the Git repository, checks out the specified revision, and renders Helm templates or Kustomize overlays in an isolated filesystem namespace. This architecture prevents repository state from leaking between Applications but requires careful tuning of resource limits to avoid memory exhaustion under high concurrency.

Retrieve the repo server logs and filter for manifest generation events, which include the repository URL, target revision, and elapsed time:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=200 | grep "GetManifests"
```

Each log entry reveals the execution time for the manifest rendering pipeline, which should complete within a few seconds for typical applications. Prolonged rendering times exceeding 10 seconds indicate either large Helm charts with complex templating logic, slow Git clone operations due to repository size, or CPU throttling from insufficiently provisioned resource limits. Inspect the repo server's resource usage to identify bottlenecks:

```bash
kubectl top pod -n argocd -l app.kubernetes.io/name=argocd-repo-server
```

If CPU usage consistently approaches the configured limit, the repo server will experience throttling, causing manifest generation requests to queue and increasing end-to-end sync latency. To observe this directly, describe the repo server pod and examine the `resources.limits` and `resources.requests` fields, then compare against live usage metrics from `kubectl top`.

Finally, verify the Redis cache hit rate, which ArgoCD uses to memoize rendered manifests and avoid redundant Git clones. The repo server stores the manifest tree indexed by repository URL, target revision, and application path, returning cached results when the Git commit SHA has not changed. Query the Redis instance to inspect cache statistics:

```bash
REDIS_POD=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-redis -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n argocd $REDIS_POD -- redis-cli INFO stats | grep keyspace_hits
kubectl exec -n argocd $REDIS_POD -- redis-cli INFO stats | grep keyspace_misses
```

Calculate the cache hit rate as `hits / (hits + misses)`. A healthy deployment should achieve a hit rate exceeding 80% after the initial warming period, reducing load on the repo server and Git infrastructure. A low hit rate suggests either frequent force-pushes to tracked branches, misconfigured cache TTLs, or Redis persistence failures causing cache invalidation across pod restarts.

This exercise establishes baseline observability into ArgoCD's core control loops, network connectivity, and caching behavior, providing the instrumentation foundation for diagnosing reconciliation delays, sync failures, and resource exhaustion under production load.

## Exercise 2: Benchmarking & Saturation Profiling

Production ArgoCD deployments often manage hundreds or thousands of Applications across multiple clusters, stressing the controller's informer caches, the repo server's concurrency limits, and the API server's watch scalability. Understanding ArgoCD's performance envelope requires synthetic load generation that exercises the full manifest rendering and reconciliation pipeline while instrumenting CPU profiles, memory allocations, and network throughput to identify bottlenecks before they manifest as user-visible latency.

Begin by generating a large number of synthetic Applications, each targeting a distinct namespace to maximize informer cache diversity and stress the controller's watch multiplexing. The following script creates 100 Applications using the same Git repository but varying the target namespace to force unique Deployment objects:

```bash
for i in $(seq 1 100); do
  cat <<EOF | kubectl apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: nginx-load-$i
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: load-test-$i
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
EOF
done
```

Monitor the controller's resource consumption as it processes the new Applications, using `kubectl top` to observe CPU and memory trends over time. The controller will spike CPU usage as it initializes informers for each new namespace, clones the Git repository 100 times (or retrieves cached manifests if Redis is functioning correctly), and applies resources concurrently:

```bash
watch -n 2 'kubectl top pod -n argocd -l app.kubernetes.io/name=argocd-application-controller'
```

Simultaneously, measure the repo server's concurrency by counting the number of active `GetManifests` requests in its logs. The repo server processes requests sequentially per worker goroutine, with concurrency controlled by the `--parallelismlimit` flag, defaulting to 10. Extract the rate of manifest generation requests from the logs and compare against the configured concurrency to determine if the repo server has become a bottleneck:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=1000 | grep "GetManifests" | wc -l
```

If the number of pending requests exceeds the parallelism limit for sustained periods, manifest generation latency will increase linearly, delaying sync operations. To quantify this, enable detailed timing logs by setting the `--loglevel=debug` flag on the repo server and extract the p50, p95, and p99 latencies for `GetManifests` calls using standard command-line tools:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=5000 | grep "GetManifests" | grep "took" | awk '{print $NF}' | sed 's/ms//' | sort -n | awk '
  BEGIN { count=0; sum=0; }
  {
    values[count++] = $1;
    sum += $1;
  }
  END {
    print "Count:", count;
    print "Mean:", sum/count, "ms";
    print "p50:", values[int(count*0.5)], "ms";
    print "p95:", values[int(count*0.95)], "ms";
    print "p99:", values[int(count*0.99)], "ms";
  }
'
```

Typical p50 latencies should remain below 500 milliseconds for small applications, while p99 latencies exceeding 5 seconds indicate resource contention or network issues with the Git remote. To isolate CPU-bound bottlenecks within the controller, capture a CPU profile using `perf` from the host node. First, identify the node hosting the controller pod and the process ID of the controller container:

```bash
CONTROLLER_NODE=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-application-controller -o jsonpath='{.items[0].spec.nodeName}')
CONTROLLER_PID=$(kubectl exec -n argocd $CONTROLLER_POD -- pidof argocd-application-controller)
```

SSH into the node and run `perf record` to sample the controller process at 1000 Hz for 30 seconds, capturing stack traces for all executing goroutines:

```bash
ssh $CONTROLLER_NODE
sudo perf record -F 1000 -p $CONTROLLER_PID -g -- sleep 30
sudo perf report --stdio | head -100
```

The perf report will display the hottest code paths, typically dominated by informer event processing, JSON deserialization, and diff computation. Look for functions related to `pkg/cache`, `pkg/sync`, and `k8s.io/client-go/tools/cache` to identify whether the controller is CPU-bound on cache updates or waiting on API server responses. If `runtime.gcMarkWorker` appears prominently, memory allocation pressure is triggering frequent garbage collection, suggesting the need to increase the controller's memory limit or reduce the number of watched resources.

Next, measure the network throughput between the controller and the API server by capturing packets on the controller's network interface and analyzing the volume of Kubernetes watch events. Use `tcpdump` to write packets to a capture file, then process with `tcpdump` statistics to quantify the byte rate:

```bash
kubectl exec -n argocd $CONTROLLER_POD -- timeout 60 tcpdump -i eth0 -w /tmp/capture.pcap port 443
kubectl cp argocd/$CONTROLLER_POD:/tmp/capture.pcap ./capture.pcap
tcpdump -r capture.pcap -nn | wc -l
tcpdump -r capture.pcap -q | tail -1
```

The packet count and final byte count indicate the aggregate watch stream throughput. In a cluster with thousands of watched resources, the controller may receive hundreds of events per second, each triggering cache updates and reconciliation checks. To determine if watch stream processing has become a bottleneck, compare the event rate against the controller's processing latency by examining the `workqueue_depth` metric exposed via Prometheus, or by directly inspecting the controller's internal queue statistics in debug logs.

Finally, simulate a Redis failure to observe how ArgoCD's caching layer degrades and recovers. Scale the Redis deployment to zero replicas, forcing all manifest generation requests to bypass the cache and clone Git repositories directly:

```bash
kubectl scale deployment argocd-redis -n argocd --replicas=0
```

Immediately observe the repo server logs for increased manifest generation latency and count the number of Git clone operations:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=500 | grep "git clone" | wc -l
```

Without Redis, the repo server clones the repository for every `GetManifests` request, multiplying latency by an order of magnitude and potentially exhausting ephemeral storage on the repo server pod. After capturing sufficient data, restore Redis and verify that the cache repopulates and hit rates recover:

```bash
kubectl scale deployment argocd-redis -n argocd --replicas=1
```

This exercise quantifies ArgoCD's scalability limits, identifies the subsystems that saturate first under load, and demonstrates how caching failures cascade into user-visible latency, equipping operators with the profiling discipline necessary to capacity-plan production deployments.

## Exercise 3: Fault Injection & Recovery Analysis

Distributed systems achieve reliability not through the absence of failures, but through predictable recovery behavior when components fail or degrade. ArgoCD's architecture employs several resiliency mechanisms: the controller's informer caches tolerate transient API server unavailability by continuing to serve stale state; the repo server retries failed Git operations with exponential backoff; and automated sync policies enable self-healing when live cluster state diverges from Git. Validating these properties requires controlled fault injection that exercises failure modes without risking production data, followed by meticulous observation of recovery latency and consistency guarantees.

Begin by simulating a sustained API server disruption that prevents the controller from receiving watch events. The controller's informer cache will continue to serve reads from its last-known state, but write operations (sync, prune, delete) will fail with connection timeouts. Use `iptables` on the controller pod's network namespace to drop all egress traffic to the Kubernetes API server's ClusterIP:

```bash
API_SERVER_IP=$(kubectl get svc kubernetes -o jsonpath='{.spec.clusterIP}')
kubectl exec -n argocd $CONTROLLER_POD -- iptables -A OUTPUT -d $API_SERVER_IP -j DROP
```

With the network path severed, attempt to sync an Application and observe how the controller handles the failure:

```bash
argocd app sync nginx-test --grpc-web
```

The sync operation will hang, eventually timing out after the gRPC client deadline expires. Inspect the controller logs to confirm that it detects the network failure and logs connection errors:

```bash
kubectl logs -n argocd deployment/argocd-application-controller --tail=100 | grep "connection refused"
```

While the network partition persists, modify the Application's target Git revision to point at a different commit and apply the updated Application manifest. The controller will queue the change but cannot fetch the new manifest or apply resources due to API server unreachability. Now restore network connectivity and observe recovery:

```bash
kubectl exec -n argocd $CONTROLLER_POD -- iptables -F OUTPUT
```

Within seconds, the controller's informer watch streams will reconnect, receive the backlog of missed events, and trigger reconciliation for the modified Application. Measure the recovery time by noting the timestamp of the last log entry before the partition and the first successful sync operation afterward:

```bash
kubectl logs -n argocd deployment/argocd-application-controller --tail=500 | grep "nginx-test" | grep "Sync operation completed"
```

Typical recovery latency should remain below 30 seconds, bounded by the informer's resync period and the watch reconnection backoff. If recovery exceeds several minutes, investigate whether the controller's event queue has accumulated a backlog that exceeds its processing capacity, forcing it to reprocess all cached resources.

Next, inject a failure into the repo server by corrupting its ephemeral storage, simulating a scenario where Git clone operations produce malformed manifests due to disk errors or race conditions in the rendering pipeline. Delete the repo server pod to force a fresh clone, then immediately fill its `/tmp` directory with garbage data to exhaust available space:

```bash
REPO_POD=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-repo-server -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n argocd $REPO_POD -- sh -c 'dd if=/dev/zero of=/tmp/fill bs=1M count=1000'
```

Trigger a sync operation and observe how the repo server handles the disk full condition:

```bash
argocd app sync nginx-test --grpc-web
```

The repo server will fail to write the Git clone to disk, returning an error to the controller, which will mark the sync operation as failed and retry after a short delay. Examine the repo server logs for the specific error message:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=100 | grep "no space left"
```

The controller's retry logic employs exponential backoff, initially retrying after a few seconds, then doubling the interval up to a maximum of several minutes. To validate this, observe the sync operation history in the Application status and note the timestamps of successive retry attempts:

```bash
kubectl get application nginx-test -n argocd -o jsonpath='{.status.operationState.finishedAt}' && echo
```

After clearing the `/tmp` directory, the next retry will succeed, demonstrating that transient repo server failures do not require manual intervention:

```bash
kubectl exec -n argocd $REPO_POD -- rm /tmp/fill
```

Now test ArgoCD's self-healing capability by manually deleting a resource managed by an Application configured with automated sync and self-heal enabled. Choose a Deployment managed by the `nginx-test` Application and delete it directly using `kubectl`:

```bash
kubectl delete deployment guestbook-ui -n default
```

The controller's informer will immediately detect the missing resource, compute a diff showing that the live state no longer matches the desired Git state, and trigger an automated sync to recreate the Deployment. Measure the time between deletion and recreation by watching the Deployment's creation timestamp:

```bash
kubectl get deployment guestbook-ui -n default --watch
```

Self-heal latency should remain below 10 seconds in typical deployments, bounded by the controller's reconciliation loop period. If self-heal takes significantly longer, investigate whether the controller is throttling sync operations due to API server rate limits or whether the Application's sync window configuration restricts automated syncs to specific time periods.

Finally, simulate a scenario where Git commits are force-pushed, causing the Application's target revision to point at a non-existent commit SHA. Update the Application's `spec.source.targetRevision` to a random SHA and apply the change:

```bash
kubectl patch application nginx-test -n argocd --type=merge -p '{"spec":{"source":{"targetRevision":"abcd1234nonexistent"}}}'
```

The repo server will fail to fetch the specified revision, returning an error to the controller, which will mark the Application as degraded with a sync status of `ComparisonError`. Inspect the Application status to confirm the error message:

```bash
kubectl get application nginx-test -n argocd -o jsonpath='{.status.conditions[?(@.type=="ComparisonError")].message}'
```

The error message will indicate that the Git commit could not be resolved, providing operators with clear diagnostic information. Restore the Application to a valid commit and verify that it transitions back to Synced status:

```bash
kubectl patch application nginx-test -n argocd --type=merge -p '{"spec":{"source":{"targetRevision":"HEAD"}}}'
```

This exercise validates ArgoCD's fault tolerance boundaries, demonstrates predictable recovery behavior under component failures, and confirms that automated sync policies correctly reconcile divergent cluster state without operator intervention.

## Diagnostic Cheat Sheet & Verification Checklist

Effective ArgoCD operations require a systematic diagnostic workflow that progresses from high-level health indicators to low-level subsystem inspection, narrowing the fault domain through hypothesis-driven investigation. The following cheat sheet consolidates the commands and verification procedures exercised throughout this lab into a reusable runbook for production incident response.

**Controller Health & Reconciliation Loop Inspection:**

Check that the controller pod is running and has not experienced recent restarts, which would indicate crash loops or out-of-memory kills:

```bash
kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-application-controller
```

Retrieve the last 500 log lines and filter for error-level messages, which typically indicate failures to connect to the API server, synchronization errors, or resource conflicts:

```bash
kubectl logs -n argocd deployment/argocd-application-controller --tail=500 | grep "level=error"
```

List all Applications and their sync status to identify which Applications are out of sync or degraded:

```bash
kubectl get applications -n argocd -o custom-columns=NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status
```

For a specific Application showing `OutOfSync` or `Degraded` status, retrieve the detailed status including the resources that are mismatched and the operation history:

```bash
kubectl get application <app-name> -n argocd -o yaml | less
```

**Repo Server Manifest Rendering & Git Operations:**

Verify that the repo server pod is running and inspect its resource utilization to identify CPU or memory bottlenecks:

```bash
kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-repo-server
kubectl top pod -n argocd -l app.kubernetes.io/name=argocd-repo-server
```

Examine repo server logs for manifest generation latency, filtering for `GetManifests` operations and extracting execution times:

```bash
kubectl logs -n argocd deployment/argocd-repo-server --tail=200 | grep "GetManifests"
```

If manifest generation is slow, check whether the repo server is throttled by resource limits or waiting on Git clone operations:

```bash
kubectl describe pod -n argocd -l app.kubernetes.io/name=argocd-repo-server | grep -A 10 "Limits"
kubectl logs -n argocd deployment/argocd-repo-server --tail=200 | grep "git clone"
```

**Redis Cache Performance & Persistence:**

Confirm that the Redis pod is running and has not experienced data loss from pod restarts without persistent volumes:

```bash
kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-redis
kubectl describe pod -n argocd -l app.kubernetes.io/name=argocd-redis | grep -A 5 "Volumes"
```

Calculate the cache hit rate to determine if the repo server is effectively memoizing manifest generation results:

```bash
REDIS_POD=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-redis -o jsonpath='{.items[0].metadata.name}')
HITS=$(kubectl exec -n argocd $REDIS_POD -- redis-cli INFO stats | grep keyspace_hits | cut -d: -f2 | tr -d '\r')
MISSES=$(kubectl exec -n argocd $REDIS_POD -- redis-cli INFO stats | grep keyspace_misses | cut -d: -f2 | tr -d '\r')
echo "Hit Rate: $(echo "scale=2; $HITS / ($HITS + $MISSES) * 100" | bc)%"
```

**Network Connectivity & API Server Communication:**

Enumerate all TCP connections from the controller to the Kubernetes API server, checking for established watch streams and identifying connection failures:

```bash
CONTROLLER_POD=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-application-controller -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n argocd $CONTROLLER_POD -- ss -tn | grep :443
```

Measure round-trip time and retransmission statistics for API server connections to detect network degradation:

```bash
kubectl exec -n argocd $CONTROLLER_POD -- ss -tin | grep :443 | grep rtt
```

Capture packets between the controller and API server to analyze watch event throughput and identify protocol-level issues:

```bash
kubectl exec -n argocd $CONTROLLER_POD -- timeout 30 tcpdump -i eth0 -w /tmp/capture.pcap port 443
kubectl cp argocd/$CONTROLLER_POD:/tmp/capture.pcap ./capture.pcap
tcpdump -r capture.pcap -nn | wc -l
```

**Application-Level Diagnostics & Sync Troubleshooting:**

For an Application stuck in `OutOfSync` status, retrieve the detailed resource diff to identify which fields are mismatched:

```bash
argocd app diff <app-name> --grpc-web
```

If the diff output is empty but the Application remains `OutOfSync`, check whether resource hooks are blocking sync completion or if health assessments are failing:

```bash
kubectl get application <app-name> -n argocd -o jsonpath='{.status.operationState.syncResult.resources[*].hookPhase}' && echo
kubectl get application <app-name> -n argocd -o jsonpath='{.status.resources[*].health}' | jq
```

Manually trigger a sync operation with increased verbosity to observe detailed sync steps and error messages:

```bash
argocd app sync <app-name> --grpc-web --loglevel debug
```

**Performance Profiling & Saturation Analysis:**

Capture a CPU profile of the controller during peak load to identify hot code paths and garbage collection pressure:

```bash
CONTROLLER_NODE=$(kubectl get pod -n argocd -l app.kubernetes.io/name=argocd-application-controller -o jsonpath='{.items[0].spec.nodeName}')
CONTROLLER_PID=$(kubectl exec -n argocd $CONTROLLER_POD -- pidof argocd-application-controller)
ssh $CONTROLLER_NODE "sudo perf record -F 1000 -p $CONTROLLER_PID -g -- sleep 30 && sudo perf report --stdio | head -100"
```

Measure manifest generation latency percentiles to quantify repo server performance under load:


**Verification Checklist:**

Before declaring an ArgoCD deployment production-ready, confirm the following invariants through direct observation:

- All core pods (`argocd-server`, `argocd-repo-server`, `argocd-application-controller`, `argocd-redis`) are running with zero restarts in the last 24 hours.
- The controller maintains at least one established TCP connection to the Kubernetes API server per watched namespace, with RTT below 10 milliseconds.
- Redis cache hit rate exceeds 80% after the initial warming period, indicating effective memoization of manifest rendering.
- Automated sync operations complete within 30 seconds from Git commit to resource convergence for typical applications (10 resources, single namespace).
- Self-heal latency remains below 10 seconds from manual resource deletion to recreation by the controller.
- Repo server manifest generation p95 latency stays below 2 seconds for applications using Helm or Kustomize rendering.
- The controller's memory usage stabilizes after initial informer synchronization and does not grow unbounded, indicating absence of memory leaks in long-running watch streams.
- Applications transition from `OutOfSync` to `Synced` status without operator intervention when Git commits update target revisions, confirming end-to-end GitOps workflow integrity.
