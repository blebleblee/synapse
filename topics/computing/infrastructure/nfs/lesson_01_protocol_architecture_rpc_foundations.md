# Lesson 1: Protocol Architecture, RPC Foundations, Transport Semantics

## 1. First-Principles Intuition & Invariants

The Network File System emerged from a fundamental tension in distributed computing: how to present remote storage as transparently as local filesystem operations while traversing an inherently unreliable network substrate. When Sun Microsystems engineers designed NFS in the mid-1980s, they confronted the reality that POSIX filesystem semantics—built on assumptions of atomic operations, immediate consistency, and trivial latency—cannot be naively projected across network boundaries where packets drop, servers crash mid-operation, and round-trip times dwarf memory access by six orders of magnitude.

At its core, NFS implements a remote procedure call abstraction over filesystem primitives. Rather than sending raw block-level storage commands like iSCSI or presenting an object store interface like S3, NFS exposes operations that mirror the VFS layer: `LOOKUP` to traverse directory entries, `READ` and `WRITE` for data transfer, `GETATTR` to retrieve inode metadata, `CREATE` and `REMOVE` for namespace manipulation. This design choice creates an elegant property: applications making standard POSIX calls through the kernel VFS layer remain entirely unaware that their file handles reference network-mounted filesystems rather than local disk. The operating system's VFS dispatch table routes operations to the NFS client kernel module, which marshals requests into RPC messages, transmits them over TCP or UDP, and blocks the calling process until responses arrive or timeouts expire.

The evolution from NFSv2 through NFSv4.2 traces a progression from radical statelessness to carefully managed stateful sessions, driven by the operational realities of production filesystems at scale. NFSv2, designed when network partitions were common and server reboots frequent, embraced complete statelessness as its founding invariant. The server maintains zero per-client context beyond the filesystem itself. Every request arrives as a self-contained transaction carrying a file handle—an opaque cryptographic token encoding inode number, generation counter, and export identifier—along with all parameters needed to execute the operation atomically. If a server crashes mid-flight, clients simply retransmit. When the server returns, it processes requests identically whether it has seen them before or not, because it never remembered seeing them in the first place.

This stateless model imposes severe constraints. Without tracking which files clients have opened, the server cannot implement byte-range locking, cannot defer writes to optimize disk scheduling, and cannot provide any coherence guarantees beyond the atomicity of individual operations. NFSv2 responses return current file attributes with every reply, allowing clients to implement heuristic cache consistency via timestamp comparison, but these heuristics break under concurrent modification. The protocol achieves correctness through simplicity: every operation either fully succeeds or fully fails, with no partial states visible to clients.

NFSv3 preserved statelessness while extending the protocol to handle larger block sizes, asynchronous writes with commit verification, and improved error granularity. The critical addition of the `COMMIT` operation allowed clients to buffer writes in memory or on local disk, transmit them to the server with `WRITE` requests marked unstable, then issue `COMMIT` to force all buffered data to stable storage. This two-phase approach dramatically improved write throughput by allowing the server to batch disk I/O while maintaining crash consistency guarantees. The client bears responsibility for retransmitting uncommitted writes if the server reboots, but once `COMMIT` returns successfully, data durability is assured.

NFSv4 abandoned statelessness as a dogmatic principle and embraced explicit session state to enable features impossible under pure stateless operation. The protocol introduces open and close semantics with server-generated state identifiers, advisory and mandatory byte-range locks with lease-based expiration, and a compound operation model that bundles multiple filesystem calls into a single RPC round-trip. This stateful architecture requires heartbeat mechanisms—clients must periodically renew their leases or risk having the server reclaim their locks and close their open files. The protocol defines grace periods during which clients can reclaim state after server restarts, and elaborate recovery procedures for handling network partitions.

The shift to statefulness solves real operational problems. With open state, NFSv4 servers can track which clients hold which file handles, enabling proper support for the `close-to-open` consistency model where a client flushing and closing a file guarantees that subsequent opens by any client see the updated content. Byte-range locks allow distributed applications to coordinate access without requiring out-of-band locking services. Compound operations eliminate the cascade of round-trips required to perform common multi-step sequences like "lookup directory entry, retrieve attributes, open file, read first block," reducing latency and improving resilience to packet loss on any individual sub-operation.

Beneath the protocol's semantic layer lies the machinery of Remote Procedure Call marshaling and External Data Representation encoding. RPC defines a request-response transaction model where clients generate unique transaction identifiers (XIDs), package operation parameters into structured messages, and await matching responses keyed by XID. The RPC layer handles transport binding—whether to transmit over UDP datagrams or TCP byte streams—and manages retransmission policies when requests time out. XDR provides the wire format, a canonical big-endian binary representation with explicit length prefixes, fixed-width integers, and recursive encoding of complex structures. Unlike ASN.1 or Protocol Buffers, XDR was designed for machine-to-machine efficiency rather than human readability or schema evolution, trading flexibility for deterministic performance.

The fundamental tension in NFS design revolves around idempotency. Because networks can duplicate packets and clients must retransmit on timeout, servers may receive and execute the same request multiple times. For idempotent operations like `READ`—where executing the same read twice produces identical results—this poses no problem. But non-idempotent operations like `CREATE` present a semantic hazard: if a client issues `CREATE foo`, times out before receiving the response, and retransmits, the server must recognize that the file already exists from the first execution and return success rather than an error. NFSv3 addressed this with duplicate request caching, maintaining a bounded window of recent XIDs and responses. NFSv4's stateful sessions provide sequence numbers that allow servers to detect and suppress true duplicates while distinguishing legitimate retransmissions from new operations.

Transport layer selection between UDP and TCP fundamentally alters failure detection and performance characteristics. UDP grants the NFS layer direct control over retransmission timing and allows the protocol to implement application-level acknowledgments and selective retransmission. When a single packet of a multi-packet read request drops, the client retransmits only the missing fragment rather than the entire transfer. But UDP's 64-kilobyte datagram limit constrains maximum I/O size unless the protocol implements fragmentation, and stateless UDP connections provide no congestion control, risking network collapse under heavy load.

TCP offloads reliability to the transport layer at the cost of head-of-line blocking and protocol complexity. When packet loss occurs mid-transfer, TCP's sliding window stalls all subsequent data delivery until the missing segment arrives and is retransmitted, even if later packets have already reached the receiver. For large sequential I/O workloads over reliable networks, TCP's window scaling and automatic congestion control deliver superior throughput. But TCP connection state requires careful lifecycle management—establishing connections costs round-trips, and half-open connections from client crashes can exhaust server resources unless aggressive keepalives or connection reaping policies are enforced.

NFSv4 mandated TCP and deprecated UDP entirely, recognizing that production environments deploy behind firewalls and NAT devices that break UDP connection tracking, and that modern kernel TCP implementations with tuned window sizes outperform UDP for bulk transfer. The protocol layers an RPC session on top of TCP connections, allowing multiple in-flight operations to pipeline over a single transport while maintaining operation ordering where semantics require it.

The architectural choices embedded in NFS ripple through every layer of a deployment. Stateless NFSv3 requires no server-side coordination during failover—any server in a cluster can service any request, enabling trivial horizontal scaling and load balancing through DNS round-robin or simple request routing. But this comes at the cost of client-side cache coherence complexity and limited locking semantics. Stateful NFSv4 concentrates session state that must be migrated or recreated during failover, requiring cluster file systems like GFS2 or OCFS2 underneath to provide coherent filesystem views, and state replication protocols to synchronize lease tables across server instances. High-availability NFS becomes an exercise in distributed consensus and state machine replication.

## 2. Core Architecture & Mechanics

The RPC/XDR encoding pipeline that underpins NFS transforms high-level filesystem operations into wire-format byte streams through a series of deterministic transformations. Understanding this marshaling process illuminates how protocol efficiency translates directly to client-visible latency and server CPU consumption. Each filesystem call descends through layers: the VFS operation enters the NFS client module, where it maps to one or more NFS procedure numbers; the client assigns an XID from a monotonically increasing counter and constructs an RPC call header; XDR encoding serializes arguments into big-endian binary; the transport layer fragments or streams the message; finally, network transmission occurs.

The RPC message header begins with a 32-bit XID that uniquely identifies the transaction, followed by a message type discriminator (call or reply), RPC protocol version (always 2), program number (100003 for NFS), program version (2, 3, or 4), and procedure number identifying the specific operation. Authentication credentials follow—typically AUTH_UNIX carrying the client's UID, GID, and supplementary group list, or RPCSEC_GSS for Kerberos-authenticated environments. This header structure consumes approximately 80 bytes before any filesystem-specific data appears, a fixed overhead on every operation.

XDR encoding operates recursively on typed data structures. Integers serialize as 4-byte big-endian values regardless of the host platform's native byte order. Variable-length arrays begin with a 4-byte count followed by count elements, each aligned on 4-byte boundaries with zero-padding as needed. Strings encode identically to byte arrays. Discriminated unions include a 4-byte discriminator determining the active variant. File handles—the cryptographic tokens that identify remote filesystem objects—serialize as opaque byte arrays, typically 32 or 64 bytes carrying an encrypted or signed structure containing the inode number, generation counter, filesystem export identifier, and a server-side secret to prevent forgery.

The NFSv3 `READ` operation demonstrates this encoding concretely. The client XDR-encodes a structure containing the file handle, a 64-bit byte offset, and a 32-bit count of bytes to read. The server decodes these parameters, performs security validation against the export's access control list, translates the file handle into an in-kernel inode reference, invokes the underlying filesystem's `read` method to fetch data from the page cache or disk, XDR-encodes a reply containing status, post-operation file attributes, and the actual data bytes, then transmits the response with the matching XID. If the requested read size exceeds the network MTU, the transport layer fragments the reply into multiple packets, each carrying a fragment header that allows the receiver to reassemble the complete message.

```text
NFSv3 READ Request Wire Format:
┌─────────────────────────────────────────┐
│ RPC Header (80 bytes)                   │
│   XID: 0x3fa89201                       │
│   Call type: 0                          │
│   RPC version: 2                        │
│   Program: 100003 (NFS)                 │
│   Version: 3                            │
│   Procedure: 6 (READ)                   │
│   Credentials: AUTH_UNIX                │
│     UID: 1000, GID: 1000, groups: []    │
├─────────────────────────────────────────┤
│ File Handle (32 bytes)                  │
│   [encrypted inode + export + secret]   │
├─────────────────────────────────────────┤
│ Offset: 0x0000000000001000 (4096)       │
├─────────────────────────────────────────┤
│ Count: 0x00010000 (65536)               │
└─────────────────────────────────────────┘

NFSv3 READ Reply Wire Format:
```

The stateless NFSv3 architecture manifests in the protocol's treatment of file handles as opaque capabilities. When a client performs a `LOOKUP` operation to resolve a pathname component, the server returns a file handle encoding all information necessary to access that object in future operations. The client caches this handle in its directory entry cache and uses it directly in subsequent operations without re-traversing the directory hierarchy. The file handle cryptographically binds to a specific inode on a specific export, preventing clients from synthesizing handles or using a handle obtained from one export to access files in another.

Server-side file handle generation typically employs the construction `HMAC-SHA256(inode_number || generation || export_id || server_secret)` where the generation counter increments each time the kernel reuses an inode number after file deletion, preventing handle collisions across file lifetimes. This approach allows the server to validate and decode file handles statelessly—no lookup table maps handles to inodes; instead, the server re-derives the inode number from the handle's plaintext fields and verifies the HMAC using its secret. If the HMAC fails, the handle is rejected as forged. If the current inode's generation counter differs from the handle's embedded generation, the handle is stale—referencing a file that no longer exists.

The duplicate request cache in NFSv3 presents a fascinating exercise in bounded memory consumption under adversarial load. Servers maintain a least-recently-used cache of recent XIDs and their responses, allowing retransmitted requests to return the cached reply without re-executing the operation. The cache must be large enough to span typical client timeout and retransmission windows but cannot grow unbounded as malicious clients could exhaust server memory by generating requests with random XIDs. Production implementations typically cache 1024 to 4096 entries per client transport connection, evicting the oldest entries under memory pressure. The cache only stores responses for non-idempotent operations—`READ` responses are never cached since re-executing a read produces identical results.

NFSv4's compound operation model transforms the request-response paradigm into a transactional sequence. A single compound RPC bundles multiple operations that execute atomically in order, with each operation's results available to subsequent operations in the same compound. The client constructs an array of operation structures, each specifying an operation type and arguments. The server processes operations sequentially, halting on the first failure and returning results for all operations up to and including the failure point.

```text
NFSv4 Compound Structure:
SEQUENCE         → renew lease, provide sequence number
PUTFH (handle)   → set current file handle to directory
LOOKUP ("foo")   → traverse to "foo", new current FH
GETATTR (mask)   → retrieve attributes of "foo"
OPEN (share mode)→ acquire open stateid
READ (offset, n) → read n bytes at offset

All operations share single XID.
Server executes atomically, returns array of per-op results.
Failure at any step aborts compound, returns partial results.
```

This compound model eliminates the client-side complexity of maintaining multiple in-flight RPCs to perform common sequences, reduces round-trips from six to one for the open-read-close pattern, and improves failure atomicity—either the entire sequence succeeds or none of it does, preventing partial state updates that require complex client-side recovery.

NFSv4 sessions introduce explicit connection state negotiated during initial client-server handshake. The client sends a `CREATE_SESSION` operation after establishing a TCP connection, specifying desired maximum request and reply sizes, slot count for operation pipelining, and callback channel configuration for server-to-client notifications. The server responds with a session ID and allocates resources to track that session's state. All subsequent operations include the session ID and a slot sequence number that orders requests within the session.

The slot mechanism implements reliable exactly-once semantics over the unreliable RPC layer. The client maintains a table of slots, each representing one in-flight operation. Before sending a request, the client claims a free slot, assigns a sequence number from that slot's monotonic counter, and transmits the operation. If no response arrives within the timeout, the client retransmits with the same sequence number. The server detects retransmissions by checking if the received sequence number matches the last executed sequence on that slot. If so, it returns the cached reply without re-executing. If the sequence number is higher, the server executes the new operation and caches its reply. This protocol guarantees exactly-once execution semantics across crashes and retransmissions.

Lease-based state management governs all NFSv4 stateful resources—open file state, byte-range locks, delegations. The server grants leases with a timeout period, typically 90 seconds. Clients must renew leases before expiration by sending any operation that includes the `SEQUENCE` operation, which implicitly refreshes the lease. If a client fails to renew within the lease period, the server transitions the client's state into a grace period, eventually reclaiming locks and closing open files. After server restart, clients have one lease period to reclaim their previous state by re-issuing open and lock operations with special reclaim flags.

Transport-level mechanics differ substantially between UDP and TCP bindings. UDP NFS transmits each RPC message as a single datagram or a sequence of fragments governed by RPC's record marking protocol. The client sets a retransmission timeout, typically starting at 1 second and doubling exponentially up to 60 seconds. For each timeout, the client retransmits the entire request. UDP provides no congestion control, so clients must implement their own backoff to avoid overwhelming the network during sustained packet loss.

TCP NFS layers RPC messages over a reliable stream. Each message begins with a 4-byte record mark encoding the message length, allowing the receiver to frame messages within the byte stream. TCP's inherent reliability eliminates the need for application-level retransmission of individual packets, but the client still must timeout entire operations if the server becomes unresponsive. Because TCP provides in-order delivery, packet loss mid-stream stalls all subsequent data delivery until retransmission completes, even if later packets have arrived. This head-of-line blocking can inflate latency for large reads if packet loss occurs early in the transfer.

Modern NFS deployments over TCP benefit from kernel parameter tuning. Increasing `tcp_rmem` and `tcp_wmem` to accommodate large NFS read and write sizes—typically 1 MB—allows the TCP stack to pipeline multiple in-flight NFS operations without blocking. Enabling TCP selective acknowledgment (SACK) improves recovery from packet loss by allowing the receiver to inform the sender which segments arrived successfully, enabling retransmission of only the missing data. Tuning `tcp_congestion_control` to algorithms like CUBIC or BBR optimizes throughput over high-latency or high-bandwidth networks.

## 3. High-Performance Optimization & Failure Modes

Production NFS tuning begins with the client-side attribute cache, the primary mechanism by which Linux masks network latency for metadata-heavy workloads. The kernel VFS layer caches directory entries and inode attributes with configurable time-to-live values, allowing filesystem operations to satisfy `stat`, `readdir`, and pathname resolution from memory without issuing RPCs. The `actimeo` mount option controls both `acregmin`/`acregmax` for file attributes and `acdirmin`/`acdirmax` for directory attributes, specifying minimum and maximum cache lifetimes in seconds.

Aggressive attribute caching—setting `actimeo=600` for 10-minute TTLs—drastically reduces RPC traffic for workloads that frequently stat the same files or traverse directory trees. Compilation farms building large codebases see order-of-magnitude throughput improvements from caching build system metadata checks. But aggressive caching sacrifices cache coherence: if another client modifies a file, cached clients continue seeing stale attributes until their TTL expires. The `noac` mount option disables attribute caching entirely, forcing every operation to query the server, guaranteeing coherence at the cost of devastating metadata performance.

The data cache in the page cache behaves differently. NFSv3's close-to-open consistency guarantees that when a client closes a file, it flushes all dirty pages to the server, and when any client opens a file, it revalidates cached data by comparing timestamps. Between open and close, no coherence protocol runs—concurrent writers on different clients produce undefined interleaving. NFSv4's stateful opens allow the server to grant read or write delegations, explicit tokens permitting a client to cache data aggressively because the server promises to recall the delegation before allowing conflicting access from another client.

Write buffering and commit semantics dominate write-intensive workload performance. By default, NFSv3 clients mark writes as `UNSTABLE`, allowing the server to acknowledge them before persisting to disk. The client accumulates dirty pages in memory until reaching `wsize` boundaries, typically 1 MB, or until a `close`, `fsync`, or write-back timer expires. At commit time, the client issues `WRITE` RPCs for all dirty pages followed by a `COMMIT` RPC. The server must flush its volatile caches to stable storage before acknowledging `COMMIT`, guaranteeing that crashes will not lose data.

This two-phase approach creates a dangerous failure window. If the server crashes after acknowledging `WRITE` but before `COMMIT`, the client retransmits the writes, but the server may have partially written some blocks to disk before the crash. If those blocks contained data from a different, unrelated write that completed before the crash, the retransmitted write overwrites correct data with stale data, causing silent corruption. NFSv3 provides no protection against this scenario; applications requiring write integrity must use `O_SYNC` or `sync` mount options to force synchronous writes at severe performance cost.

NFSv4's mandatory TCP binding and stateful sessions eliminate some failure modes while introducing others. TCP's reliable delivery ensures that successfully acknowledged writes reach the server without client-side retransmission of individual packets. But TCP connection failure—due to firewall timeout, server crash, or network partition—leaves the client uncertain whether in-flight operations completed. The client must either timeout the operation and report error to the application, or wait indefinitely hoping the connection recovers. The `soft` versus `hard` mount option governs this behavior: soft mounts timeout and return EIO after a configured delay; hard mounts retry indefinitely, hanging applications but guaranteeing eventual completion when connectivity restores.

Lock recovery after network partition or server restart reveals the deepest complexity in NFSv4 state management. When a client detects lost connectivity, it must determine whether the server rebooted or merely experienced transient network failure. On reconnection, the client checks the server's reboot epoch counter. If unchanged, the session resumes and outstanding operations retry. If the epoch incremented, the server rebooted and lost all state. The client enters a grace period during which it reclaims previous locks and opens using special reclaim flags. If any reclaim fails—because another client already claimed conflicting locks during grace period—the client must invalidate its cached data and notify applications holding file locks that their locks were lost.

This recovery protocol creates a fundamental tension: long grace periods allow clients ample time to reclaim state after widespread network partitions, reducing spurious lock loss notifications, but delay the server's return to full service and prevent new lock acquisitions until grace period expires. Short grace periods minimize service disruption but risk losing client state if clients cannot reconnect and reclaim within the window. Production servers typically configure 90-second grace periods, matching the default lease timeout.

Delegation recall amplifies the impact of cache coherence breaks. When a server grants a read delegation to a client for a file, that client can service all reads from local cache without contacting the server. If a second client subsequently opens the file for write, the server must recall the read delegation from the first client before granting the write delegation to the second client. The recall involves the server sending a callback RPC to the first client, which must flush cached data and return the delegation. Only after the recall completes can the write proceed.

This callback mechanism requires bidirectional connectivity—clients must accept incoming RPCs from servers. NAT and firewalls often break this assumption, forcing NFSv4.1 to introduce backchannel multiplexing where callbacks flow over the same TCP connection as forward operations, eliminating the need for separate listening sockets on clients. But delegation recall remains a synchronous operation blocking the writer until the recall completes, and if the client holding the delegation is unreachable, the server must timeout the recall, revoke the delegation, and fence that client from future access until it reconnects and reestablishes session state.

Parallel NFS (pNFS) in NFSv4.1+ attempts to eliminate the single-server bottleneck by introducing a metadata-data separation architecture. Clients contact a metadata server for namespace operations—lookups, creates, attribute queries—which returns layout information describing where data physically resides across multiple data servers. Subsequent reads and writes bypass the metadata server and directly access data servers in parallel. This architecture allows metadata and data bandwidth to scale independently, but introduces complexity in handling data server failures, layout revocation, and ensuring layout-driven I/O remains coherent with metadata operations.

The block layout type maps byte ranges of files to block device LUNs, allowing clients to issue SCSI commands directly to storage arrays. File layout maps byte ranges to NFSv4 file handles on data servers. Flex file layout extends file layout with mirroring and redundancy. Each layout type requires client kernel support and imposes different failure handling semantics. Block layouts deliver maximum performance by removing protocol overhead but require shared storage visible to all clients and servers. File layouts maintain filesystem-level abstraction but introduce multi-server consistency challenges.

Monitoring and diagnosing NFS performance requires instrumenting multiple layers. The `/proc/net/rpc/nfs` and `/proc/net/rpc/nfsd` files expose per-operation counters tracking RPC invocations, retransmits, and timeouts. The `nfsstat` command summarizes these counters, revealing operation mix and error rates. Excessive retransmits indicate network packet loss or server overload. High `badcalls` counts suggest authentication failures or protocol mismatches.

Packet captures with `tcpdump` or `tshark` filtered on port 2049 reveal wire-level protocol behavior. Analyzing RPC XIDs across request-response pairs exposes retransmission patterns. Comparing RPC timestamps identifies server processing latency versus network round-trip time. Wireshark's NFS dissector decodes XDR structures, displaying file handles, offsets, and operation parameters in human-readable form.

Server-side tracing illuminates internal behavior. The `rpcdebug` command enables kernel debug logging for RPC and NFS subsystems, writing detailed operation logs to `dmesg`. On Linux, the `nfsdcltrack` and `nfsd4recover` programs log state recovery operations during server restart. The kernel exports NFS server statistics through `/proc/fs/nfsd/`, including per-client connection counts, operation latency histograms, and memory usage.

Advanced deployments use `perf` to profile CPU consumption, revealing whether servers spend cycles in network processing, XDR encoding, filesystem operations, or lock management. Memory profiling with `slabtop` shows kernel slab allocator usage, detecting memory leaks in RPC duplicate caches or excess dentry allocation from attribute cache thrashing.

Failure injection testing validates recovery code paths. Introducing artificial network delays with `tc qdisc` measures timeout and retransmission behavior. Dropping packets with `iptables` rules tests client retry logic. Forcibly killing server processes mid-operation exercises client state recovery and grace period handling. These tests frequently expose edge cases where clients deadlock waiting for server responses that will never arrive, or servers leak state when clients disconnect mid-session.

Security considerations permeate NFS deployments. The AUTH_UNIX credential model trusts clients to report their own UID and GID, allowing any client to impersonate any user by sending forged credentials. Export restrictions based on source IP address provide coarse access control but fail in environments where clients share IP space or use NAT. RPCSEC_GSS with Kerberos provides cryptographic authentication, integrity protection, and optional encryption, but requires functioning Kerberos infrastructure, NFS implementations that correctly handle credential expiration and renewal, and performance overhead from cryptographic operations on every RPC.

The root squashing mitigation maps UID 0 (root) to anonymous UID (typically 65534) on the server, preventing clients running as root from accessing files as root on the server. But this provides no protection against non-root UIDs—a client running as UID 1000 can access and modify any file owned by UID 1000 on the server. Comprehensive security requires either trusted clients in isolated networks, or RPCSEC_GSS with Kerberos and careful export permission configuration.

Looking forward, RDMA transports for NFS over InfiniBand or RoCE networks bypass traditional TCP/IP stack overhead, allowing direct memory access between client and server NICs. The NFS-over-RDMA protocol layers RPC messages over RDMA operations, using RDMA Read and Write for data transfer while reserving RDMA Send/Recv for control messages. This eliminates memory copies and CPU involvement in data transfer, reducing latency to microseconds and scaling throughput to 100+ Gbps on modern fabrics. But RDMA requires specialized hardware, different failure modes around queue pair disconnection, and careful memory registration management to avoid pinning excessive physical memory.
