# Operational Verification Labs: Flux

## Objective & Environment Setup

Flux is a continuous delivery operator that implements GitOps reconciliation for Kubernetes clusters. Unlike imperative deployment pipelines that push changes from CI/CD runners into clusters, Flux inverts the control flow by running controllers inside the cluster that continuously pull desired state from Git repositories and reconcile it against the live cluster state. This architecture eliminates the need to grant external CI systems cluster credentials and establishes Git as the single source of truth for declarative infrastructure. Flux decomposes this responsibility across multiple specialized controllers: **source-controller** fetches artifacts from Git repositories, Helm repositories, and OCI registries; **kustomize-controller** builds Kustomization overlays and applies manifests; **helm-controller** manages Helm release lifecycles; **notification-controller** dispatches events to external systems; and **image-reflector-controller** with **image-automation-controller** scan container registries and commit image tag updates back to Git. Each controller operates as an independent Kubernetes Deployment with its own reconciliation loop, watching Custom Resource Definitions that describe sources, kustomizations, and release specifications.

The operational verification exercises in this guide assume you have provisioned a Kubernetes cluster running version 1.27 or later with at least three worker nodes, each configured with 4 CPU cores and 8 GiB of memory. You must install the Flux CLI binary on your local workstation and bootstrap Flux into the cluster using a Git repository under your control. The bootstrap process installs all Flux controllers into the `flux-system` namespace, creates a GitRepository resource pointing to your repository, and deploys a Kustomization that continuously reconciles the cluster state from the repository's contents. For hands-on diagnostics, ensure your workstation has `kubectl`, `iproute2` utilities including `ss` and `ip`, `tcpdump` for packet capture, `perf` for CPU profiling, `strace` for system call tracing, and `etcdctl` for direct etcd inspection if you have access to the control plane. If running on a managed Kubernetes service like EKS or GKE, you will have limited visibility into etcd and the kubelet's container runtime interface, but all controller-level diagnostics remain fully accessible.

Begin by verifying your Flux installation. Execute `flux check --pre` to confirm that all prerequisite Kubernetes APIs are available, then run `flux check` to validate that all Flux controllers are operational. This command queries each Deployment in the `flux-system` namespace, inspects the readiness status of their Pods, and confirms that the controllers have registered their Custom Resource Definitions with the API server. A healthy Flux installation reports all controllers as ready, with recent reconciliation timestamps visible in the status subresources of GitRepository and Kustomization objects. If any controller is degraded, `flux check` will indicate which Pod is failing and provide guidance on inspecting its logs. The Flux reconciliation model operates on level-triggered state convergence: controllers continuously recompute the desired state from sources, compare it against the observed cluster state, and apply corrective patches to eliminate drift. This differs from edge-triggered systems that react only to explicit change events. Because reconciliation loops run on fixed intervals—defaulting to one minute for GitRepository fetches and five minutes for Kustomization applies—Flux tolerates transient network failures and API server unavailability by automatically retrying operations until they succeed.

To establish a baseline diagnostic environment, clone the Git repository that Flux is monitoring and create a test application manifest. In the repository root, add a directory `apps/podinfo` containing a Deployment, Service, and HorizontalPodAutoscaler for the lightweight `podinfo` HTTP server. Commit this structure and push it to the remote repository. Flux's source-controller will detect the new commit on its next poll interval, fetch the updated revision, and signal kustomize-controller to reconcile the Kustomization. Within two minutes, you should observe the `podinfo` Deployment appearing in your cluster. This end-to-end flow exercises Git polling, artifact caching, manifest rendering, and Kubernetes API patching—the core operational path that every Flux deployment depends on. If the application does not appear, you have discovered a failure point that the subsequent exercises will teach you to diagnose systematically.

The exercises that follow guide you through inspecting live controller state, profiling reconciliation performance under load, and injecting faults to verify recovery behavior. Each exercise builds on the previous one, progressively deepening your operational understanding of Flux's internal subsystems. You will trace HTTP requests from source-controller to Git servers, analyze memory allocation patterns in kustomize-controller during large manifest processing, measure the latency distribution of Kubernetes API PATCH operations, and observe how controllers recover from etcd unavailability and Pod evictions. These are the diagnostic primitives that distinguish operators who can deploy Flux from engineers who can operate it reliably under production failure modes.

## Exercise 1: Live State & Internal Subsystem Inspection

The first operational skill is inspecting the running state of Flux controllers to understand what each component is doing at any given moment. Flux controllers expose their internal state through Kubernetes Custom Resources, Prometheus metrics endpoints, and structured logs. Begin by listing all GitRepository resources: `kubectl get gitrepositories -A`. Each GitRepository represents a remote Git endpoint that source-controller is polling. Examine the status of your primary repository with `kubectl get gitrepository flux-system -n flux-system -o yaml`. The `status.conditions` array shows whether the last fetch succeeded, the `status.artifact` field contains the URL of the cached tarball in source-controller's internal storage, and `status.observedGeneration` confirms that the controller has processed the latest spec changes. If the `Ready` condition is `False`, the `message` field will describe the failure—common causes include SSH key authentication failures, invalid hostkey verification, or network timeouts reaching the Git server.

To observe source-controller's behavior in real time, stream its logs with `kubectl logs -n flux-system deploy/source-controller -f`. Flux controllers use structured logging with `level`, `ts`, `msg`, and contextual fields. When source-controller polls a GitRepository, it logs the repository URL, the commit SHA it fetched, and the time taken to clone and package the artifact. If polling fails, the logs will show the exact error returned by the Git client library, including connection refused errors, TLS certificate validation failures, or repository not found responses. Cross-reference these log entries with the GitRepository's status conditions to distinguish transient failures from persistent misconfigurations. For persistent authentication issues, verify that the SSH private key Secret referenced in the GitRepository's `spec.secretRef` exists and contains a valid `identity` key. Extract the public key from the Secret and confirm it is registered as a deploy key in your Git hosting service.

Next, inspect kustomize-controller's reconciliation state. List all Kustomization resources with `kubectl get kustomizations -A` and select your primary Kustomization: `kubectl get kustomization flux-system -n flux-system -o yaml`. The Kustomization's status reveals which GitRepository artifact it is building from, the last applied revision, and the inventory of resources it has created in the cluster. The `status.inventory` field contains a list of every Kubernetes object—identified by Group, Kind, Name, and Namespace—that the Kustomization owns. This inventory enables Flux to perform garbage collection: when you remove a manifest from Git, kustomize-controller detects that the corresponding object is no longer in the desired state and deletes it from the cluster, provided the object is not shared with another Kustomization. If you delete a Kustomization resource, Flux will remove all objects in its inventory unless you set `spec.prune` to `false`. This behavior is the operational foundation of GitOps: every resource in the cluster is traceable to a specific commit in a Git repository, and removing the commit removes the resource.

To understand how kustomize-controller builds manifests, enable debug logging by patching the Deployment: `kubectl set env -n flux-system deploy/kustomize-controller --containers=manager RUNTIME_LOGS=debug`. This elevates the log verbosity to include the full Kustomize build output, showing which overlays are being applied, which patches are being merged, and the final rendered YAML before submission to the API server. Restart the controller to apply the change, then stream its logs: `kubectl logs -n flux-system deploy/kustomize-controller -f`. Trigger a reconciliation by updating a manifest in your Git repository and pushing the commit. Within the next poll interval, you will observe source-controller fetching the new revision, followed by kustomize-controller downloading the artifact, running `kustomize build`, and diffing the output against the cluster's current state. The logs will show each API PATCH operation with the resource name, namespace, and the patch content. If a patch fails—commonly due to immutable field violations or webhook admission denials—the error appears immediately in the logs with the exact rejection reason from the API server.

Flux controllers expose Prometheus-compatible metrics on port 8080 under the `/metrics` path. These metrics quantify reconciliation loop performance, artifact fetches, and API server interaction latency. Forward the source-controller metrics port to your local machine: `kubectl port-forward -n flux-system deploy/source-controller 8080:8080`. In a separate terminal, fetch the metrics with `curl http://localhost:8080/metrics | grep gotk`. Key metrics include `gotk_reconcile_duration_seconds`, which histograms the time taken to complete a reconciliation loop; `gotk_reconcile_condition`, a gauge indicating the current status of each resource; and `gotk_suspend_status`, which flags suspended resources. For source-controller, observe `gotk_source_artifact_fetch_duration_seconds` to measure Git clone performance, and `gotk_source_artifact_size_bytes` to track artifact size growth over time. Large artifact sizes—typically caused by storing binary assets or node_modules directories in the repository—directly increase the memory footprint of source-controller and the I/O load on the Pod's ephemeral storage.

Repeat the metrics inspection for kustomize-controller: `kubectl port-forward -n flux-system deploy/kustomize-controller 8080:8080` and query `/metrics`. Focus on `gotk_reconcile_duration_seconds` for the Kustomization resource type. If reconciliation duration exceeds several seconds, suspect large manifest counts or complex Kustomize transformations. You can decompose the total duration by inspecting the controller's trace logs: each step—downloading the artifact, running the build, diffing with the cluster, and applying patches—is timed individually. Consistently high durations in the diffing phase indicate that the controller is comparing thousands of resources, which scales linearly with the size of the cluster's existing state. Flux performs server-side dry-run diffs before applying patches to detect immutable field changes and validation errors, and these dry-runs incur the same API server round-trip latency as real applies.

To verify that controllers are processing events from the Kubernetes API server, inspect their cache synchronization state. Flux controllers use the `controller-runtime` library, which maintains a local informer cache of Kubernetes resources that the controller watches. At startup, each controller lists all relevant resources—GitRepositories, Kustomizations, Secrets, ConfigMaps—from the API server and stores them in memory. Subsequent updates arrive via the Watch API, a long-lived HTTP connection over which the API server streams CREATE, UPDATE, and DELETE events. If this Watch connection breaks due to network interruption or API server restart, the controller re-establishes it and resyncs the cache. The reconciliation loop operates entirely against the local cache, only reaching back to the API server when applying patches or fetching additional resources. You can confirm cache liveness by observing the `workqueue_*` metrics: `workqueue_depth` shows how many reconciliation requests are pending, and `workqueue_queue_duration_seconds` measures how long requests wait in the queue before processing. A growing queue depth under steady load signals that the controller cannot keep up with the reconciliation rate, usually due to slow API server responses or expensive Kustomize builds.

Finally, trace the full lifecycle of a single resource from Git commit to cluster creation. Add a new ConfigMap to your Git repository under `apps/podinfo/config.yaml`, commit it, and push. Immediately begin streaming logs from both source-controller and kustomize-controller in separate terminals. Observe the following sequence: source-controller detects the new commit on its next poll, clones the repository, packages the working tree into a tarball, stores it in its artifact cache (a Persistent Volume), and updates the GitRepository's status with the new artifact URL and revision. This status update triggers an event that kustomize-controller receives via its Watch connection. Kustomize-controller reconciles the Kustomization, downloads the artifact tarball from source-controller's HTTP endpoint, extracts it to a temporary directory, runs `kustomize build` over the extracted files, diffs the output manifests against the cluster, and issues a CREATE request for the new ConfigMap. The ConfigMap appears in the cluster, and kustomize-controller updates the Kustomization's inventory to include it. This entire flow typically completes within five to ten seconds, dominated by the Git polling interval. If you need lower latency, configure a webhook receiver using notification-controller to push change events from your Git server directly to Flux, eliminating the polling delay.

## Exercise 2: Benchmarking & Saturation Profiling

Operating Flux at scale requires understanding its performance characteristics under load. Flux's reconciliation throughput is bounded by three primary factors: the rate at which source-controller can fetch and cache artifacts, the CPU and memory available to kustomize-controller for building and diffing manifests, and the Kubernetes API server's capacity to handle PATCH requests. This exercise profiles each subsystem to identify bottlenecks and quantify headroom before saturation.

Begin by measuring Git artifact fetch latency under realistic conditions. Create a synthetic GitRepository pointing to a moderately large repository—at least 100 MiB of YAML manifests or 10,000 files—and configure a short reconciliation interval: `spec.interval: 30s`. Apply this GitRepository and monitor source-controller's behavior with `kubectl logs -n flux-system deploy/source-controller -f` while simultaneously collecting metrics. Forward the metrics port and poll `gotk_source_artifact_fetch_duration_seconds_bucket` repeatedly: `curl -s http://localhost:8080/metrics | grep 'gotk_source_artifact_fetch_duration_seconds_bucket{name="large-repo"'`. The histogram buckets reveal the latency distribution: most fetches should complete in the +1.0 to +2.5 second buckets for a 100 MiB repository over a high-bandwidth network. If latencies spike into the +10.0 bucket, investigate network round-trip time to the Git server with `ping` and `traceroute`, and confirm that source-controller's Pod has sufficient CPU to perform gzip compression of the artifact tarball.

Scale the test by creating multiple GitRepository resources with staggered intervals. Deploy ten GitRepositories, each pointing to a different branch of the same repository, with intervals ranging from 30 seconds to 5 minutes. Source-controller processes reconciliation requests concurrently, up to a default concurrency limit of four. Observe the `workqueue_depth` metric: if the queue depth grows without bound, source-controller is saturated and cannot keep pace with the configured intervals. The symptom of saturation is increasing staleness: the `status.artifact.lastUpdateTime` field in each GitRepository lags further behind the current time. To alleviate saturation, increase the concurrency limit by setting the `--concurrent` flag in source-controller's Deployment args: `kubectl set env -n flux-system deploy/source-controller --containers=manager CONCURRENCY=8`. Restart the controller and observe queue depth stabilizing. The maximum sustainable concurrency depends on the available CPU cores and the I/O bandwidth of the Pod's ephemeral storage. On a node with 4 CPU cores and NVMe-backed storage, source-controller can sustain approximately 12 concurrent Git fetches before I/O wait time dominates.

Next, profile kustomize-controller's manifest building and diffing performance. Create a Kustomization that references a GitRepository artifact containing 500 Kubernetes Deployments, each with 3 replicas, for a total of 1500 Pods worth of declarative state. Set the Kustomization's `spec.interval` to `1m` to force frequent reconciliations. Apply this Kustomization and monitor kustomize-controller's CPU and memory utilization with `kubectl top pod -n flux-system -l app=kustomize-controller`. During the reconciliation loop, CPU usage spikes to near 100% of the Pod's limit as the controller runs `kustomize build` over hundreds of manifests, merges overlays, and serializes the output to YAML. Memory usage grows proportionally to the total size of the rendered manifests, as the controller holds both the desired state (from the artifact) and the observed state (from the API server) in memory to compute the diff. For 1500 Deployments, expect memory usage to approach 1 GiB.

To isolate the diffing overhead, enable CPU profiling with `perf`. First, identify the kustomize-controller Pod's process ID from the node's perspective: `kubectl get pod -n flux-system -l app=kustomize-controller -o jsonpath='{.items[0].spec.nodeName}'` gives you the node name, then SSH to that node and run `crictl ps | grep kustomize-controller` to find the container ID. Obtain the PID with `crictl inspect <container-id> | jq '.info.pid'`. Start a `perf` recording session: `perf record -F 99 -p <pid> -g -o /tmp/kustomize.perf.data -- sleep 30`. This samples the call stack at 99 Hz for 30 seconds, capturing which functions dominate CPU time. Transfer the perf data file to your workstation and generate a flamegraph: `perf script -i kustomize.perf.data | stackcollapse-perf.pl | flamegraph.pl > kustomize-flamegraph.svg`. The flamegraph visualizes the call hierarchy, with wider frames indicating more CPU time. For kustomize-controller, expect significant time in `sigs.k8s.io/kustomize` build functions and in `k8s.io/client-go` API patching functions. If YAML parsing dominates, consider splitting large manifests into smaller files to reduce the per-file parse cost.

Stress-test the Kubernetes API server's PATCH throughput by deploying a Kustomization that manages 2000 ConfigMaps, each 1 KiB in size. Configure `spec.interval: 1m` and observe the reconciliation duration. Flux issues PATCH requests sequentially to maintain apply ordering and ensure dependencies are created before dependents. With 2000 resources, the apply phase alone requires 2000 API server round-trips. On a cluster with an API server latency of 10 ms per request, this totals 20 seconds, dominating the reconciliation time. Query the `gotk_reconcile_duration_seconds` histogram and confirm that the 0.99 quantile exceeds 20 seconds. To reduce latency, enable server-side apply (SSA) by setting `spec.wait: false` in the Kustomization, which allows kustomize-controller to issue PATCH requests concurrently without waiting for each to complete. With SSA, apply time drops to approximately 2 seconds for 2000 resources, bounded by the controller's internal concurrency limit. Verify this by re-measuring the reconciliation duration after enabling SSA.

Memory profiling reveals kustomize-controller's allocation patterns during large builds. Use `pprof` to capture a heap profile: `kubectl port-forward -n flux-system deploy/kustomize-controller 6060:6060`, then `curl http://localhost:6060/debug/pprof/heap > heap.prof`. Analyze the profile with `go tool pprof -http=:8081 heap.prof`. The web UI displays the allocation call graph, with each node sized by total allocated bytes. For large Kustomizations, observe significant allocations in `sigs.k8s.io/kustomize/api/krusty.MakeKustomizer` and `sigs.k8s.io/kustomize/api/resource.Factory`. These allocations are transient: after the build completes, the Go garbage collector reclaims the memory. However, if the build duration exceeds the GC cycle, the Pod's memory usage will spike temporarily. To prevent OOM kills during spikes, set the kustomize-controller Pod's memory request to 1.5× the observed peak usage.

Finally, benchmark end-to-end reconciliation latency from Git commit to cluster update. Instrument your Git repository with a webhook that sends HTTP POST notifications to notification-controller on every push. Configure a Receiver resource in Flux that triggers immediate reconciliation of your GitRepository and Kustomization. Push a commit that updates a single Deployment's image tag and measure the time until the Deployment's Pods are running with the new image. Use `time` to bracket the operation: start the timer when you push, and stop it when `kubectl get deployment <name> -o jsonpath='{.spec.template.spec.containers[0].image}'` shows the new tag. With webhooks enabled, end-to-end latency should be under 10 seconds, dominated by image pull time rather than Flux polling. Without webhooks, latency is bounded below by the GitRepository's poll interval, typically 60 seconds. This measurement quantifies the best-case delivery time for urgent hotfixes, guiding your decision on whether to enable webhook-driven reconciliation in production.

## Exercise 3: Fault Injection & Recovery Analysis

Production Flux deployments must tolerate node failures, network partitions, etcd unavailability, and API server restarts without losing desired state or requiring manual intervention. This exercise systematically injects faults into each subsystem and verifies that Flux's controllers recover automatically through their level-triggered reconciliation loops.

Start with a simple Pod termination. Identify the source-controller Pod and delete it: `kubectl delete pod -n flux-system -l app=source-controller`. Kubernetes immediately schedules a replacement Pod on another node. While the new Pod is starting, source-controller cannot fetch Git artifacts, and any pending reconciliation requests queue in the workqueue. Observe the GitRepository status: the `Ready` condition remains `True` with the last known artifact URL because the status is persisted in etcd and survives Pod restarts. Once the new Pod becomes ready, it loads its informer cache from the API server, discovers all GitRepository resources, and resumes polling on the configured intervals. Within two poll cycles, the controller catches up to the current Git HEAD, and no manual intervention is required. This behavior validates that Flux controllers are stateless: all persistent state resides in Kubernetes Custom Resources, and controllers are freely replaceable.

Inject a network partition between source-controller and the Git server. If running on a cloud provider, simulate this by temporarily revoking the security group rule that permits egress HTTPS traffic from the cluster's VPC. Alternatively, use `iptables` on the source-controller Pod's node to drop outbound packets to the Git server's IP: `iptables -A OUTPUT -d <git-server-ip> -j DROP`. With the partition in place, source-controller's Git fetch attempts timeout after 60 seconds, and the GitRepository's `Ready` condition transitions to `False` with a message indicating connection timeout. The controller logs each failed attempt and backs off exponentially between retries, capping at a 5-minute interval. During the partition, kustomize-controller continues to reconcile using the last successfully fetched artifact, maintaining the cluster's current state. When you restore network connectivity by removing the `iptables` rule, source-controller immediately retries, succeeds, and updates the GitRepository status. Kustomize-controller detects the new artifact and reconciles any changes that accumulated in Git during the partition. This demonstrates Flux's resilience to transient network failures: controllers tolerate arbitrary downtime in upstream dependencies and self-heal when connectivity returns.

Test recovery from etcd unavailability by stopping the etcd process on your control plane node. If using a managed Kubernetes service, simulate this by scaling the API server Deployment to zero replicas temporarily. With etcd unavailable, all `kubectl` commands hang, and Flux controllers lose their Watch connections to the API server. Controllers detect the disconnection within 30 seconds and enter a retry loop, attempting to re-establish the Watch. The controllers' local informer caches retain the last known resource state, but they cannot apply new patches because the API server is unreachable. Observe the workqueue metrics: `workqueue_depth` grows as reconciliation requests accumulate. When you restore etcd and the API server, the Watch connections re-establish, controllers resync their caches, and the queued reconciliation requests drain rapidly as the controllers apply all pending patches. The cluster converges back to the desired state from Git without operator intervention. This validates that Flux does not require persistent connectivity to the API server and can buffer reconciliation work during control plane failures.

Inject a failure in kustomize-controller's build step by committing a syntactically invalid Kustomization overlay to your Git repository. For example, introduce a circular dependency in a `patchesStrategicMerge` directive or reference a nonexistent base. Push this commit and observe kustomize-controller's logs. The controller fetches the artifact, attempts the build, encounters an error in the Kustomize library, and updates the Kustomization's `Ready` condition to `False` with the error message. Crucially, the controller does not apply any changes to the cluster: if the build fails, the entire reconciliation is aborted, preventing partial or corrupted state from being applied. The controller continues to retry the reconciliation on its interval, so the error persists until you push a corrective commit. When you revert the invalid change, the next reconciliation succeeds, and the Kustomization status returns to `Ready=True`. This fail-safe behavior ensures that human errors in Git do not propagate into the cluster's running state.

Simulate a node failure by cordoning and draining the node running kustomize-controller: `kubectl cordon <node-name>`, then `kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data`. The drain operation evicts all Pods, including kustomize-controller, and Kubernetes reschedules them on other nodes. During the eviction window, kustomize-controller is unavailable, and reconciliation pauses. The informer cache is lost, and the new Pod must rebuild it by listing all Kustomizations from the API server. This resync takes several seconds for small clusters and up to 30 seconds for large clusters with thousands of resources. Once the cache is populated, reconciliation resumes. Verify that no Kustomizations were skipped by inspecting their `status.lastAppliedRevision` fields: they should all match the current GitRepository artifact revision. This exercise confirms that Flux tolerates arbitrary Pod rescheduling without losing reconciliation progress.

Test handling of conflicting updates by manually modifying a resource that Flux manages. Select a Deployment managed by a Kustomization and change its replica count directly with `kubectl`: `kubectl scale deployment <name> -n <namespace> --replicas=10`. This creates a drift between the cluster's observed state and the desired state in Git. On the next reconciliation interval, kustomize-controller detects the drift by diffing the rendered manifest against the cluster, determines that the replica count was changed out-of-band, and issues a PATCH to restore the value defined in Git. The Deployment scales back to the replicas specified in the manifest, and the manual change is overwritten. This behavior enforces Git as the single source of truth: any imperative change to a managed resource is automatically reverted. To persist a change, you must commit it to the Git repository. Verify this by observing the Deployment's replica count return to the Git-specified value within the Kustomization's reconciliation interval.

Introduce a deadlock scenario by creating two Kustomizations with circular dependencies. Configure Kustomization A to depend on Kustomization B via `spec.dependsOn`, and Kustomization B to depend on Kustomization A. Apply both resources and observe kustomize-controller's behavior. The controller detects the circular dependency during reconciliation planning and marks both Kustomizations as `Ready=False` with an error message indicating the cycle. Neither Kustomization is reconciled, preventing an infinite loop. This safeguard ensures that misconfigured dependencies do not destabilize the controller. To resolve, remove one of the `dependsOn` entries, push the corrected configuration, and the controller resumes normal reconciliation.

Finally, inject resource exhaustion by deploying a Kustomization that creates thousands of resources, each with a large annotation payload, exceeding the controller's memory limit. Configure a memory limit of 512 MiB on kustomize-controller and apply a Kustomization managing 5000 ConfigMaps, each with 10 KiB annotations. During the build and diff phases, the controller's memory usage climbs to the limit, and the kubelet OOM-kills the Pod. Kubernetes restarts the Pod, and the controller retries the reconciliation, only to hit the limit again. Observe this thrashing behavior in the Pod's restart count: `kubectl get pod -n flux-system -l app=kustomize-controller`. The solution is to either increase the memory limit or split the Kustomization into smaller units. This exercise demonstrates the importance of right-sizing controller resources based on the scale of managed manifests.

## Diagnostic Cheat Sheet & Verification Checklist

Flux operational diagnostics rely on a structured process of inspecting resource status, analyzing logs, querying metrics, and tracing API server interactions. This checklist codifies the diagnostic workflow for common failure modes.

**GitRepository not updating:** Begin by verifying that source-controller is running: `kubectl get pod -n flux-system -l app=source-controller`. Check the GitRepository status: `kubectl get gitrepository <name> -n <namespace> -o yaml` and inspect `status.conditions`. If `Ready=False`, the `message` field contains the error. Common causes include invalid SSH keys (verify the Secret exists and contains `identity` and `known_hosts`), unreachable Git server (test with `git ls-remote <url>` from the cluster), or incorrect branch reference (confirm `spec.ref.branch` matches a real branch). If the status shows `Ready=True` but the artifact revision is stale, check the poll interval: `spec.interval` must be short enough to detect changes within your required latency. Enable webhook notifications to eliminate polling delay.

**Kustomization not applying changes:** Verify that kustomize-controller is running and check the Kustomization status: `kubectl get kustomization <name> -n <namespace> -o yaml`. If `Ready=False`, examine `status.conditions` for the error message. Common issues include invalid Kustomize overlays (test locally with `kustomize build <path>`), missing referenced ConfigMaps or Secrets (verify with `kubectl get`), or API server admission webhook denials (visible in controller logs). If the status shows `Ready=True` but resources are not updated, check the inventory: `kubectl get kustomization <name> -n <namespace> -o jsonpath='{.status.inventory}'`. If the expected resource is missing from the inventory, kustomize-controller did not recognize it in the manifest. Ensure the manifest has correct `apiVersion`, `kind`, `metadata.name`, and `metadata.namespace` fields.

**High reconciliation latency:** Measure the `gotk_reconcile_duration_seconds` metric for the affected resource type. If the 0.99 quantile exceeds 10 seconds, profile the reconciliation loop. For source-controller, check `gotk_source_artifact_fetch_duration_seconds` to isolate Git clone time. For kustomize-controller, inspect logs for the time spent in build vs. diff vs. apply phases. If build dominates, reduce the manifest count per Kustomization. If diff dominates, ensure the cluster has a reasonable resource count—controllers scale linearly with resource count. If apply dominates, enable server-side apply with `spec.wait: false`. Check API server latency with `kubectl get --raw /metrics | grep apiserver_request_duration_seconds` and confirm the 0.99 quantile is under 100 ms.

**Controller OOM killed:** Inspect the Pod's memory usage over time with `kubectl top pod -n flux-system` and correlate spikes with reconciliation events. If kustomize-controller exceeds its memory limit during large builds, increase the limit or split the Kustomization into smaller units. If source-controller OOMs, check artifact sizes with `gotk_source_artifact_size_bytes` and exclude large files from the Git repository using `.sourceignore`. Memory usage grows with the total size of in-flight artifacts and rendered manifests.

**Resources deleted unexpectedly:** Flux performs garbage collection when a resource is removed from a Kustomization's manifests. Check the Kustomization's inventory before and after the deletion: `kubectl get kustomization <name> -n <namespace> -o jsonpath='{.status.inventory}'`. If the resource was in the inventory and is now missing from the rendered manifests, kustomize-controller correctly deleted it. To prevent deletion, set `spec.prune: false` or move the resource to a different Kustomization that will continue managing it.

**Stale metrics or logs:** If metrics are not updating, confirm the Prometheus scrape configuration targets the correct namespace and port (8080). If logs are not appearing, verify that the Pod is writing to stdout: `kubectl logs -n flux-system deploy/<controller> --tail=10`. If logs exist but are not structured, check the `RUNTIME_LOGS` environment variable—default is `info`, set to `debug` for verbose output. If logs are truncated, increase the kubelet's log rotation settings or use a log aggregation system like Fluent Bit to capture all output.

**API server certificate expiration:** If controllers log TLS handshake failures, check the Kubernetes API server's certificate validity: `echo | openssl s_client -connect <api-server>:6443 2>/dev/null | openssl x509 -noout -dates`. If expired, renew the certificate and restart the API server. Controllers automatically reconnect after the TLS error resolves.

**Webhook receiver not triggering:** Verify the Receiver resource exists and has an allocated URL: `kubectl get receiver <name> -n <namespace> -o jsonpath='{.status.webhookPath}'`. Test the webhook endpoint with `curl -X POST <ingress-url><webhook-path>`. If the request succeeds but reconciliation does not trigger, check notification-controller logs: `kubectl logs -n flux-system deploy/notification-controller -f`. **Verification checklist for a healthy Flux deployment:**
1. All controller Pods in `flux-system` namespace are `Running` with 0 restarts in the last hour.
2. `flux check` reports all components as `Ready`.
3. All GitRepository resources have `Ready=True` and `status.artifact.revision` matches the latest Git HEAD.
4. All Kustomization resources have `Ready=True` and `status.lastAppliedRevision` matches the corresponding GitRepository artifact revision.
5. `gotk_reconcile_duration_seconds` p99 latency is under 5 seconds for all resource types.
6. Controller memory usage is stable and below 70% of the configured limit.
7. No `gotk_reconcile_condition{status="False"}` metrics present.
8. Git repository size is under 100 MiB to ensure fast clones.
9. Webhook receivers, if configured, respond with HTTP 200 to test POST requests.
10. All managed resources in the cluster match the desired state in Git, confirmed by comparing `kubectl get` output with rendered manifests.
