# Lesson 4: Advanced Features, High Availability, Stack Architectures

## 1. First-Principles Intuition & Invariants

Modern enterprise switching architectures operate under a fundamental tension between simplicity and resilience. A single physical switch represents a catastrophic single point of failure—loss of power, backplane failure, or software crash takes down every connected endpoint. Yet naive redundancy introduces its own complexity: dual-homing servers to separate switches creates Layer 2 loops unless carefully orchestrated, while maintaining configuration consistency across discrete devices multiplies operational burden. The advanced features covered in this lesson resolve these tensions through elegant protocol state machines and hardware consolidation strategies that preserve deterministic forwarding behavior even as physical components fail.

Link aggregation fundamentally rewrites the economics of bandwidth provisioning by allowing multiple physical links to function as a single logical channel. Rather than choosing between a single 10GbE uplink (sufficient capacity but no redundancy) or two independent 10GbE paths (redundancy but wasted bandwidth when both function), LAG presents both paths as a unified 20GbE pipe that degrades gracefully to 10GbE on single-link failure. This transformation from discrete physical resources to abstract logical capacity emerges from careful coordination between switch ASICs, which must distribute frames across member links without reordering packets within a flow, and between peer devices, which must agree on which links belong to the aggregate and dynamically adjust when members fail.

Quality of Service mechanisms address a different kind of scarcity: buffer space and transmission slots on congested egress ports. Unlike bandwidth, which can be multiplied through parallel links, a single egress port presents a strict serialization bottleneck—only one frame transmits at any instant. When ingress traffic exceeds egress capacity, frames accumulate in output queues until buffers overflow and tail drop occurs. QoS introduces priority differentiation, allowing time-sensitive flows like VoIP or storage replication to claim transmission slots ahead of bulk transfers. This prioritization requires both classification logic to mark frames with priority indicators and scheduling algorithms in the egress pipeline to select the next frame based on queue depth, priority level, and fairness constraints.

Port security operates at the intersection of access control and MAC learning, leveraging the fact that every Ethernet frame carries a source MAC address that identifies the sending station. In unrestricted operation, switches learn MAC addresses promiscuously, populating the forwarding table with any source MAC observed on each port. This openness enables plug-and-play connectivity but permits trivial MAC spoofing attacks: an attacker connects to an access port and transmits frames with arbitrary source addresses, polluting the MAC table or impersonating legitimate devices. Port security constrains this learning process by binding specific MAC addresses to each port, either statically provisioned by the administrator or dynamically learned but locked after initial discovery. Violation policies then determine switch behavior when an unauthorized MAC appears—whether to drop offending frames silently, disable the port entirely, or generate SNMP traps for security monitoring.

Switch stacking and chassis architectures represent two fundamentally different approaches to building multi-port switching fabrics. A stackable switch is an autonomous device with its own control plane, power supply, and forwarding ASIC, but it exposes special high-speed stacking ports that interconnect with similar devices to form a logical unit. The stack elects a master switch that runs the unified control plane while member switches function as remote line cards, forwarding local traffic autonomously but consulting the master for spanning tree decisions, VLAN configurations, and MAC table synchronization. This distributed architecture scales incrementally—each added switch contributes its ports and backplane bandwidth—but introduces synchronization complexity and latency when inter-switch communication is required.

Chassis switches invert this model by consolidating the control plane, backplane, and power distribution into a shared chassis while providing hot-swappable line cards that house the actual Ethernet ports and per-port ASICs. A supervisor module runs the single operating system instance, maintaining a unified forwarding table and control protocol state, while line cards connect through a high-capacity backplane fabric that provides non-blocking switching between any port pair. Failures of individual line cards affect only the ports on that module; the supervisor maintains forwarding state and redistributes traffic through remaining paths. This centralized architecture achieves deterministic performance and simplified management at the cost of higher initial capital expenditure and constrained physical scalability—chassis slot count limits total port density.

Control plane redundancy extends high availability principles to the software layer by duplicating the critical processes that maintain routing tables, run spanning tree, process LACP negotiations, and manage VLAN configurations. Modern switches partition functionality into a control plane that makes forwarding decisions and a data plane that executes those decisions at line rate. A control plane failure—kernel panic, software bug, or memory corruption—should not disrupt packet forwarding for existing flows since the data plane ASIC operates autonomously once programmed. However, the network cannot adapt to topology changes, learn new MAC addresses, or re-converge routing protocols without a functioning control plane. Dual supervisor architectures maintain hot standby processors that synchronize state continuously, allowing subsecond failover when the active supervisor fails.

The invariants governing these advanced features derive from the same forwarding primitives established in earlier lessons. Link aggregation modifies the egress port selection logic but preserves per-flow ordering through consistent hashing algorithms that map flows to specific member links deterministically. QoS inserts priority-aware scheduling between buffer dequeue and transmission, but frames still traverse the same ingress processing, lookup, and egress replication paths. Port security adds MAC address filtering at ingress without altering the fundamental learning and forwarding cycle. Stacking and chassis architectures distribute or centralize the control plane but do not change the ASIC-level primitives for frame forwarding, VLAN tagging, or ACL evaluation. Software-defined switching separates the control plane entirely, running it on external controllers that program forwarding tables through OpenFlow or similar protocols, yet the data plane still executes the same match-action pipeline optimized in silicon.

## 2. Core Architecture & Mechanics

### Link Aggregation Control Protocol State Machine

Link aggregation groups, also called port channels or bonded interfaces, bundle multiple physical links into a single logical interface through careful orchestration of frame distribution and dynamic membership management. The IEEE 802.3ad standard (later incorporated into 802.1AX) defines LACP as the control protocol that negotiates aggregation parameters between peer devices and detects link failures without relying on physical layer signaling alone. Each participating switch transmits LACP PDUs every second (fast mode) or thirty seconds (slow mode) on every potential member port, advertising its system priority, system MAC address, port priority, and operational key that identifies which ports can be aggregated together.

The LACP state machine operates independently on each port, tracking whether the port is selected for aggregation, whether it is synchronized with the partner device, and whether it should actively participate in frame distribution. A port begins in the unselected, out-of-sync state, transmitting LACP PDUs that advertise its parameters but not yet forwarding data frames. When both peers agree on aggregation parameters—matching keys, compatible speeds, and duplex modes—and verify bidirectional LACP PDU exchange, they transition to the selected and synchronized states, enabling data forwarding on that link. The switch ASIC updates its egress hash table to include the newly active port, distributing flows across the expanded member set.

```
LACP Port State Lifecycle
==========================

Port Initialization
        |
        v
   [DETACHED] ──────────────────┐
        |                       │
        | Physical link up      │
        v                       │
  [WAITING] ────────────────────┤
        |                       │
        | Rx LACP PDU           │ Timeout (90s)
        v                       │
  [CURRENT] ─> Partner validates│
        |                       │
        v                       v
  [SELECTED] ──> Add to LAG    Rx timeout ──> [EXPIRED]
        |        hash table              |
        v                                v
  [DISTRIBUTING] ────────────────> [DEFAULTED]
   Forward frames                  Remove from LAG
```

Frame distribution across LAG members relies on hash-based load balancing that maintains per-flow ordering while maximizing bandwidth utilization. The switch extracts fields from each ingress frame—typically source and destination MAC addresses for Layer 2 hashing, or source/destination IP addresses and TCP/UDP ports for Layer 3/4 hashing—and feeds them through a hash function that produces an index into the member port array. This deterministic mapping ensures all frames belonging to a single conversation traverse the same physical link, preserving TCP sequence ordering and avoiding the catastrophic performance degradation that occurs when packets arrive out of order and trigger spurious retransmissions.

The hash distribution algorithm must balance two competing objectives: uniform traffic distribution across all active members and stability under membership changes. Adding or removing a link from the aggregate ideally affects only the flows hashed to that specific member, leaving other flows undisturbed. Many implementations use modulo hashing, computing `hash(flow) % N` where N is the current member count, but this causes massive flow rehashing when N changes—removing one link from a four-member LAG potentially remaps three-quarters of all flows. More sophisticated consistent hashing algorithms use virtual buckets or rendezvous hashing to minimize disruption, ensuring that removing a member only remaps flows that were specifically assigned to that link.

### Quality of Service Classification and Scheduling

Quality of Service mechanisms partition the switch's finite buffer and transmission resources among traffic classes with different performance requirements. Real-time protocols like SIP voice signaling or NVMe-over-TCP storage IO cannot tolerate the unpredictable latency introduced when they queue behind large bulk transfers. QoS addresses this through two complementary mechanisms: classification logic that assigns incoming frames to priority queues, and scheduling algorithms that determine dequeue order when multiple queues compete for transmission slots.

Classification occurs at frame ingress, examining packet headers to extract priority indicators and map them to internal priority values. The IEEE 802.1Q standard defines a 3-bit Priority Code Point (PCP) field in the VLAN tag that directly encodes eight priority levels, with higher values indicating more urgent traffic. IPv4 and IPv6 packets carry their own priority indicators—the Type of Service (ToS) byte in IPv4 headers or the Traffic Class field in IPv6—using either the legacy IP Precedence bits or the Differentiated Services Code Point (DSCP) values that provide finer-grained classification. Switches typically maintain mapping tables that translate external priority markings into internal queue assignments, allowing flexible policy definition independent of the specific marking scheme in use.

Upon classification, the switch enqueues the frame into one of several egress queues associated with the outbound port. Modern switches implement per-port, per-queue buffering with separate counters tracking occupancy for each priority level. This separation prevents lower-priority traffic from starving high-priority flows of buffer space during congestion—a bulk FTP transfer cannot fill all available buffers because the low-priority queue has a finite allocation, leaving buffer headroom for VoIP frames arriving at the high-priority queue. When buffers do exhaust, the switch applies active queue management policies like Weighted Random Early Detection (WRED) that selectively drop frames based on queue depth and priority, providing early congestion signals to TCP senders before tail drop occurs.

Scheduling determines which queue supplies the next frame for transmission when the egress port becomes available. The simplest algorithm, strict priority scheduling, always services the highest-priority non-empty queue first, providing deterministic low latency for urgent traffic but completely starving lower queues during sustained high-priority load. Production networks require fairness guarantees that prevent starvation while still prioritizing latency-sensitive flows, leading to weighted scheduling algorithms that service queues in proportion to configured weights.

Deficit Weighted Round Robin (DWRR) implements fair queuing by maintaining per-queue deficit counters that track "owed" transmission opportunities. Each scheduling round increments each queue's deficit by its configured quantum (proportional to its weight), then services queues in round-robin order, transmitting frames while the deficit remains positive and decrementing the deficit by each frame's length. A high-weight queue receives larger quantum increments, allowing it to transmit more bytes per round, while a low-weight queue gets smaller quanta but still receives guaranteed service. This algorithm prevents both starvation and bandwidth hogging—a queue transmitting large frames cannot monopolize the link because its deficit depletes, forcing the scheduler to service other queues before returning.

Traffic shaping complements scheduling by rate-limiting specific flows or egress ports to prevent them from consuming excessive bandwidth and causing downstream congestion. A token bucket shaper maintains a virtual token counter that increments at the configured rate (e.g., 100 Mbps) and decrements by each transmitted frame's size. When the counter reaches zero, the shaper delays subsequent frames until tokens accumulate, effectively capping the sustained transmission rate. Burst tolerance is implemented through bucket depth—allowing the counter to accumulate tokens up to a maximum value permits short bursts above the configured rate while maintaining long-term average compliance.

### Port Security Learning and Violation Handling

Port security augments the standard MAC learning process with access control policies that restrict which source MAC addresses are permitted on each port. In normal operation, a switch learns source MACs promiscuously: any frame arriving on a port causes the switch to record the source MAC and ingress port association in its forwarding table. This behavior enables zero-configuration networking where devices auto-register simply by transmitting frames, but it provides no defense against MAC spoofing or impersonation attacks.

Static port security requires administrators to manually configure the allowed MAC addresses for each port using the management interface. An access port connecting to a known desktop might be configured with a single allowed MAC, while a trunk port connecting to an IP phone with a daisy-chained PC permits two specific addresses. The switch validates every ingress frame's source MAC against the allowed list for that port, dropping frames from unauthorized MACs immediately without updating the forwarding table.

Dynamic port security automates this process by learning the first N MAC addresses observed on each port and locking them as the allowed set once the limit is reached. This mode balances security and operational simplicity—no manual provisioning required, yet the port remains locked to the initially detected devices. An access port configured for single-MAC learning locks to the first device that transmits, rejecting all subsequent MACs including legitimate devices that connect after a PC replacement. Many implementations support aging timers that expire learned secure MACs after a configured inactivity period, allowing legitimate MAC changes while still preventing rapid MAC table pollution attacks.

Sticky secure MAC addresses combine dynamic learning with persistent storage, writing dynamically learned MACs into the running configuration so they survive switch reboots. This mode provides the convenience of automatic learning during initial deployment while ensuring that a power cycle does not revert the port to permissive mode where an attacker could register their MAC first.

Violation handling defines switch behavior when an unauthorized MAC attempts to transmit on a secured port. Protect mode silently drops frames from violating MACs while continuing to forward traffic from authorized addresses, providing security without disrupting legitimate devices or alerting attackers that their spoofing was detected. Restrict mode drops violating frames and increments a security violation counter visible through SNMP and syslog, enabling security monitoring systems to detect and investigate attacks. Shutdown mode provides the strongest response by error-disabling the port entirely, transitioning it to a non-forwarding state until an administrator manually re-enables it. This mode prevents any malicious traffic but requires operational response to restore service, making it suitable for high-security environments where security violations warrant immediate isolation.

### Switch Stacking Control Plane Synchronization

Switch stacking creates a logical single switch from multiple independent physical devices by electing a master unit that runs the unified control plane while members execute its commands. The stacking protocol establishes this distributed control architecture through a leader election process triggered during initial stack formation or whenever the current master fails.

Election proceeds through a priority comparison where each switch advertises its configured stack priority, MAC address, and current uptime. The device with highest priority wins; ties break on lowest MAC address to ensure deterministic outcomes. The elected master transitions to active state, assuming responsibility for all control plane protocols including spanning tree, LACP negotiations, routing protocol adjacencies, and VLAN management. Member switches transition to standby mode, forwarding their control plane traffic to the master over the stacking links while executing data plane forwarding locally.

The stacking backplane interconnects member switches through dedicated high-speed links—typically 40G or 100G bandwidth—that form a ring topology for redundancy. Traffic ingressing on one member switch can egress on any other member without traversing the master, leveraging the distributed forwarding tables that each member maintains as a synchronized copy of the master's authoritative database. When a frame arrives destined for a MAC address on a different stack member, the local ASIC encapsulates it in a stacking header that identifies the destination switch and egress port, transmits it across the ring, and the receiving switch strips the stacking header and forwards the original frame.

```
Stack Topology and Traffic Flow
================================

        Master (SW-1)
        Stack Priority 15
            |
    Stacking ports 1/Stack1
            |
        [Ring Fabric]
       /     |     \
      /      |      \
SW-2       SW-3      SW-4
Member     Member    Member
  |          |         |
Local      Local     Local
Ports      Ports     Ports

Frame Flow Example:
1. Frame arrives SW-2 port 2/0/1 → DST MAC learned on SW-4
2. SW-2 ASIC adds stacking header: {dest_switch=4, dest_port=0/5}
3. Frame traverses ring SW-2 → SW-3 → SW-4
4. SW-4 strips stacking header, forwards original frame to port 4/0/5
```

MAC table synchronization maintains consistency across stack members by propagating learned addresses through the stacking protocol. When any member learns a new MAC address through normal frame ingress, it notifies the master with the MAC and local port information. The master updates its authoritative table and multicasts the update to all members, which install the entry with the learning switch and port identified. Aging timers run on the master; expired entries generate deletion messages distributed to members. This centralized-but-cached architecture ensures consistent forwarding decisions while allowing distributed lookups—a member switch can resolve most destination MACs through its local copy without querying the master.

Configuration synchronization follows a similar pattern where the master maintains the authoritative running configuration and pushes changes to members through the stacking control protocol. An administrator connects to any stack member's management interface, but the CLI transparently proxies commands to the master for execution. The master validates the configuration change, updates its database, and distributes affected parameters to relevant members. Port-specific configurations like speed, duplex, or PoE settings are pushed only to the switch hosting that port, while global parameters like VLAN definitions or spanning tree settings propagate to all members.

### Chassis Switch Architecture and Supervisor Redundancy

Chassis switches consolidate control plane, backplane fabric, and power distribution into a shared chassis while providing hot-swappable line cards that house Ethernet ports and per-port packet processing ASICs. The supervisor module or route processor runs the unified operating system instance, executing all control plane protocols, maintaining the master forwarding database, and programming line card ASICs through the internal control bus. This centralized architecture eliminates the distributed synchronization complexity inherent in stacked switches at the cost of higher capital expenditure and physical scalability limits imposed by chassis slot count.

The backplane fabric interconnects all line cards through a non-blocking switched mesh that provides dedicated bandwidth between every card pair. Early chassis used shared-bus architectures where all line cards connected to a common electrical bus, creating contention when multiple cards transmitted simultaneously and limiting aggregate throughput to the bus bandwidth. Modern fabrics implement crossbar switches or multi-stage Clos topologies where each line card connects to multiple fabric cards through dedicated links, and the fabric cards perform cell-based switching to route traffic between ingress and egress line cards. A typical implementation uses three to seven fabric cards operating in redundant load-sharing mode; losing a single fabric card reduces aggregate capacity but does not disable any line cards or drop established flows.

Line card architecture partitions packet processing into discrete stages executed by specialized silicon blocks. Ingress frames arrive at the PHY (physical layer interface) which performs signal detection, clock recovery, and deserialization from wire format into parallel data. The MAC block enforces frame boundaries, validates FCS, and filters malformed frames. The packet buffer stage stores the frame in on-card DRAM while the forwarding ASIC performs table lookups: source MAC learning, destination MAC resolution, VLAN membership checks, and ACL evaluation. The ASIC appends an internal fabric header specifying the egress line card and port, then segments the frame into fixed-size cells for transmission across the backplane.

The egress line card receives cells from the fabric, reassembles them into complete frames, and queues them for transmission based on priority and scheduling policy. The egress ASIC applies any required frame modifications: updating TTL fields for routed packets, rewriting VLAN tags, or performing NAT translations. Finally the MAC and PHY blocks serialize the frame and drive it onto the wire.

Supervisor redundancy mitigates the single point of failure introduced by centralizing control plane execution. Chassis designs support dual supervisors operating in active-standby mode with continuous state synchronization between modules. The active supervisor runs all control plane processes—routing daemons, spanning tree, CLI and management protocols—and maintains the authoritative forwarding database. The standby supervisor mirrors this state through real-time synchronization protocols, receiving copies of every configuration change, routing update, and forwarding table modification.

State synchronization mechanisms vary by architecture sophistication. Simple implementations use checkpoint-based synchronization where the active supervisor periodically snapshots its entire state and bulk-transfers it to the standby. This approach minimizes complexity but results in long failover times (tens of seconds) since the standby must re-converge all routing protocols after taking over. Advanced implementations use incremental synchronization with message-level replication: every OSPF LSA received, every BGP route installed, every MAC address learned generates a synchronization message transmitted to the standby, which replays the operation identically. This fine-grained mirroring enables subsecond failover since the standby maintains a fully synchronized routing table and forwarding database continuously.

Failover detection relies on hardware-level heartbeat monitoring between supervisors rather than network reachability checks which might misinterpret control plane congestion as supervisor failure. Dedicated heartbeat links exchange periodic keepalives with aggressive timers—typically 100ms intervals with 300ms timeout—allowing rapid failure detection. Upon detecting active supervisor failure, the standby supervisor asserts control, notifies line cards of the topology change through the control bus, and assumes the active role. Line cards flush any supervisor-specific cached state and re-synchronize their forwarding tables from the new active. In well-implemented systems, data plane forwarding continues uninterrupted during failover; only control plane operations like new MAC learning or routing updates pause briefly during transition.

### Software-Defined Networking Integration

Software-defined networking decouples the switch control plane from the data plane, moving protocol execution and forwarding table computation from individual switches to centralized controllers that program multiple devices through standardized APIs. OpenFlow, the canonical SDN protocol, exposes the switch data plane as a match-action pipeline where the controller installs flow entries specifying matching criteria (source/destination MAC, VLAN, IP addresses, TCP ports) and actions to execute (forward to port, rewrite headers, drop, send to controller).

The OpenFlow switch maintains multiple flow tables arranged in a pipeline where each table performs specialized matching and may include a wildcard entry that sends non-matching packets to the controller. A typical configuration uses Table 0 for MAC-based switching, Table 1 for VLAN filtering, and Table 2 for IP routing, with each table forwarding packets to subsequent stages through explicit GOTO actions. This pipeline structure preserves the conceptual layering of traditional switching while exposing programmability at each stage.

Flow entry installation proceeds through the OpenFlow channel connecting switch to controller. When a packet arrives without a matching flow entry (a table-miss condition), the switch encapsulates it in a PACKET_IN message and sends it to the controller. The controller examines the packet, applies its policy logic—which might include consulting a network-wide topology database, checking access control lists, or implementing custom load balancing—and responds with FLOW_MOD messages that install specific flow entries into the switch tables. Subsequent packets matching those entries are forwarded entirely in the data plane without controller involvement, preserving line-rate performance.

Hardware implementation of OpenFlow pipelines leverages ternary content-addressable memory (TCAM) that performs parallel wildcard matching on all installed flow entries simultaneously. Each TCAM entry stores a match pattern, mask specifying which bits are significant, and priority value for resolving multiple matches. The switch hashes ingress packet headers into a lookup key and presents it to the TCAM; matching entries are prioritized and the highest-priority match supplies the action to execute. TCAM capacity limits the total number of flow entries—typical merchant silicon supports 1K to 32K entries depending on match field width—requiring controllers to carefully manage flow table utilization and employ wildcard entries judiciously.

SDN integration transforms switch management from per-device CLI configuration to programmatic network-wide orchestration. Controllers maintain a synchronized graph model of the entire network topology, discovering switches through LLDP and learning connectivity through packet captures at each device. When an administrator requests a new VLAN or changes access policy, the controller computes the necessary flow entries for every affected switch and installs them atomically through parallel OpenFlow sessions. This centralized visibility enables sophisticated traffic engineering: the controller can reroute flows around congested links, implement dynamic firewall policies that adapt to detected threats, or provide network-wide debugging through flow-level tracing.

## 3. High-Performance Optimization & Failure Modes

### Link Aggregation Capacity Planning and Hash Polarization

Effective LAG deployment requires careful attention to hash distribution characteristics and member link symmetry to achieve uniform load sharing. Hash polarization occurs when multiple LAG bundles in series use identical or correlated hash functions, causing traffic to concentrate on a subset of paths rather than distributing evenly. Consider two spine switches each with a four-member LAG to an access switch: if both spines hash on the same Layer 3 flow tuple, flows that hash to member 1 on the first spine will consistently hash to the same member on the second spine, fully utilizing at most four of the eight total paths while leaving others idle.

Mitigating polarization requires decorrelating hash functions between network tiers through different input field selection or hash seeds. Access switches might hash on Layer 2 source/destination MAC, while spine switches use Layer 3 source/destination IP, ensuring independent distribution decisions at each hop. Alternatively, symmetric hashing employs bidirectional flow definitions where source and destination fields are sorted before hashing—the same hash result applies to both directions of a TCP connection, guaranteeing symmetric path selection for request and response packets.

Member link symmetry profoundly affects achievable bandwidth utilization. A LAG with mixed speeds—combining 10G and 40G links—will distribute flows proportionally to member count rather than capacity, potentially directing four elephant flows to the single 10G link while leaving the 40G links underutilized. All LAG members must negotiate identical speed and duplex settings; a misconfigured link operating half-duplex while others use full-duplex causes catastrophic performance degradation as collisions force exponential backoff on the slow member while other links continue at full rate.

LACP timeout tuning trades failure detection speed against protocol overhead and convergence stability. Fast mode (1-second PDU interval, 3-second timeout) provides rapid failure detection suitable for critical links where even brief outages impact application performance, but generates higher control plane load and may experience false positives from transient congestion. Slow mode (30-second interval, 90-second timeout) reduces overhead but tolerates longer outages before removing failed members and rebalancing traffic. Production deployments typically use fast mode on server-facing ports where rapid failover preserves TCP connections, and slow mode on inter-switch trunks where routing protocols provide faster failure detection through their own keepalive mechanisms.

Flow-based load balancing introduces microbursts when multiple elephant flows hash to the same member link. A LAG distributing traffic across four 10G members provides 40G aggregate capacity but cannot accommodate five simultaneous 10G flows—four links saturate immediately while one flow experiences buffer exhaustion and drops. Monitoring per-member utilization metrics exposes such imbalances; sustained divergence between member link utilization indicates suboptimal hash distribution requiring either additional capacity or application-level flow control.

### QoS Buffer Exhaustion and Microburst Mitigation

Switch buffer dimensioning directly determines the maximum burst size that can be absorbed without drops during transient oversubscription. Packet buffers smooth bursty traffic by queuing excess frames when ingress rate temporarily exceeds egress capacity, allowing brief rate mismatches without packet loss. Merchant switching ASICs typically provision 4MB to 128MB of packet buffer depending on market segment—access switches require less buffering than spine switches aggregating traffic from hundreds of servers.

Buffer allocation strategies partition this finite resource across multiple queues and ports using either static reservation or dynamic sharing. Static allocation guarantees each queue a fixed buffer quota, preventing lower-priority traffic from consuming buffer space needed by high-priority flows but potentially wasting resources when high-priority queues sit idle. Dynamic sharing allows queues to borrow from a shared pool when their dedicated allocation exhausts, maximizing utilization but requiring complex accounting to prevent priority inversion where bulk transfers starve real-time traffic of buffer headroom.

Microburst detection and mitigation addresses a specific failure mode where multiple ingress ports simultaneously transmit toward a single congested egress port for brief intervals (microseconds to milliseconds). Individual port rates appear normal when averaged over typical polling intervals (one second), yet instantaneous oversubscription causes buffer overflow and drops. Hardware-assisted microburst detection captures buffer depth histograms with microsecond granularity, exposing momentary queue buildups invisible to traditional SNMP polling. Mitigation strategies include increasing buffer allocation to the affected queue, implementing stricter rate limiting on ingress flows, or spreading traffic across multiple egress ports through LAG or ECMP routing.

Priority flow control (PFC) provides lossless Ethernet by allowing congested egress ports to send PAUSE frames upstream, temporarily halting transmission from specific traffic classes while preserving flow for others. Unlike traditional IEEE 802.3X PAUSE which stops all traffic on a link, PFC operates per-priority through eight independent pause channels corresponding to 802.1p priority levels. When an egress queue exceeds its configured buffer threshold, the switch transmits PFC PAUSE frames upstream requesting suspension of traffic for that priority class. Upstream switches honor the pause by halting their egress queues for the specified priority, propagating backpressure toward traffic sources.

PFC deployment requires network-wide configuration consistency—all devices in the lossless path must support and enable PFC for the designated traffic classes. Misconfiguration creates deadlocks where downstream devices send pause frames that upstream devices ignore, causing uncontrolled buffer exhaustion and drops. PFC also introduces head-of-line blocking: pausing a single priority class stalls all queues behind it in the pipeline, potentially affecting unrelated traffic. Modern data center fabrics employ explicit congestion notification (ECN) as an alternative, marking packet headers to signal congestion rather than pausing transmission entirely, allowing endpoints to implement application-level rate control without introducing head-of-line blocking.

### Port Security Attack Vectors and Hardening

Port security mitigates MAC flooding attacks where malicious clients transmit frames with randomized source MAC addresses to overflow the switch forwarding table. Commodity switches store learned MACs in hash tables or content-addressable memory with finite capacity—typically 8K to 256K entries. An attacker generating frames with unique source MACs at line rate exhausts this capacity within seconds, causing the switch to enter fail-open mode where unknown destination MACs trigger flooding to all ports. This converts the switched network into a shared collision domain where every device receives all traffic, enabling promiscuous eavesdropping.

Defending against MAC flooding requires rate-limiting MAC learning on untrusted ports through storm control or port security maximum MAC limits. Storm control monitors the rate of unknown unicast frames and throttles traffic once a threshold is exceeded, preventing MAC table exhaustion but still permitting the attack to consume bandwidth. Port security maximum MAC limits definitively bound the number of learned MACs per port—once the limit is reached, further unique source MACs trigger violation handling without installing table entries.

DHCP snooping integrates with port security to validate IP-to-MAC bindings and prevent spoofing attacks. DHCP snooping designates ports as trusted (connecting to legitimate DHCP servers) or untrusted (connecting to clients). The switch intercepts DHCP messages, building a binding table that records IP address, MAC address, VLAN, and ingress port for each successful lease. Dynamic ARP inspection (DAI) leverages this table to validate ARP packets: an ARP reply claiming ownership of an IP address is compared against the DHCP snooping binding; mismatches indicate spoofing and trigger drops. This defense prevents attackers from hijacking IP addresses through gratuitous ARP announcements.

IP Source Guard extends this protection by installing per-port ACLs that permit only traffic matching learned IP-to-MAC bindings. An attacker who compromises a host cannot transmit frames with spoofed source IPs because the switch filters all traffic not explicitly authorized by the DHCP snooping table. This defense operates entirely in hardware using TCAM-based ACLs, maintaining line-rate performance while enforcing strict source validation.

### Stack Split-Brain and Master Failover

Stack split-brain occurs when stacking links fail in a way that partitions the stack into isolated segments, each believing itself to be the complete stack. Consider a four-member ring stack where both stacking links on one switch fail simultaneously: the stack fragments into a three-member segment and an isolated single switch. Each segment independently elects a master based on current priorities and continues operating, but they maintain divergent forwarding tables and respond to the same management IP address. External devices connected to different segments observe inconsistent behavior—MAC addresses learned through one segment remain unknown in the other, and configuration changes applied to one master do not propagate to the isolated partition.

Preventing split-brain requires dual-link stacking topologies where each member connects to both neighbors through independent physical paths. When a single link fails, the ring degrades to a chain but remains connected; both links must fail simultaneously to partition the stack. Even with dual-link topology, implementing stack preemption ensures deterministic master election after partition healing. Non-preemptive mode allows both partitions to retain their elected masters after links restore, requiring administrator intervention to reconcile; preemptive mode forces re-election immediately upon partition healing, with the highest-priority switch across both segments becoming the unified master and the other reverting to member role.

Master failover impacts control plane protocols differently based on their inherent state synchronization mechanisms. Stateless protocols like spanning tree reconverge rapidly—the new master recomputes the spanning tree topology and transmits BPDUs to establish its authority. Stateful protocols like BGP lose session state during failover unless explicitly preserved through graceful restart mechanisms. BGP graceful restart allows routers to maintain forwarding during control plane restarts by advertising their support in the OPEN message and preserving the forwarding table through failovers. When a stack master fails and the standby assumes control, BGP sessions enter graceful restart mode where neighbors continue forwarding based on stale routes while the new master reestablishes sessions and synchronizes routing tables.

### Chassis Fabric Degradation and Oversubscription

Chassis backplane fabrics provide non-blocking switching under specific traffic patterns but may introduce oversubscription when aggregate demand exceeds fabric capacity. A fully populated chassis with twelve 48-port 10G line cards (576 ports total, 5.76 Tbps aggregate) requires a fabric capable of sustaining line-rate bidirectional traffic between any port pair. Achieving true non-blocking operation demands fabric capacity of 2× the total edge bandwidth—11.52 Tbps in this example—because each flow traverses the fabric twice (ingress card to fabric, fabric to egress card).

Fabric oversubscription ratios specify the relationship between edge capacity and backplane bandwidth. A 3:1 oversubscribed chassis with 5.76 Tbps edge capacity might provision only 1.92 Tbps fabric bandwidth, satisfying line-rate forwarding when traffic patterns remain balanced but encountering congestion when traffic concentrates on specific card-to-card paths. Monitoring fabric utilization per chip reveals imbalance: a fabric with seven switching chips operating in load-sharing mode should show roughly equal utilization across all chips; sustained divergence indicates traffic engineering issues or physical fabric failures.

Fabric card failures reduce aggregate capacity but typically do not disable line cards entirely. A chassis with five fabric cards operating in 4+1 redundancy mode tolerates single-card failures by redistributing traffic across remaining fabric chips at reduced capacity—a 20% capacity reduction for one failed card. Line cards detect fabric degradation through increased cell drop counters and dynamically reduce their scheduling rates to prevent overrunning the diminished fabric capacity. Two or more simultaneous fabric failures may disable line cards entirely depending on chassis architecture; some designs isolate line cards into separate non-communicating groups, while others maintain partial connectivity with severely degraded performance.

Supervisor failover time directly correlates with control plane protocol reconvergence delay and thus end-to-end traffic disruption duration. Minimizing downtime requires optimizing state synchronization granularity and avoiding bulk transfers. Checkpointed synchronization—taking full state snapshots every few seconds—results in failover times of ten to thirty seconds as the standby replays accumulated routing updates and rebuilds forwarding tables from scratch. Incremental synchronization with message-level replication achieves subsecond failover by maintaining a continuously synchronized standby that requires only session re-establishment, not full state reconstruction. Advanced implementations preserve even stateful firewall connection tables and NAT bindings through failover by replicating per-flow state incrementally, enabling true transparent failover where established TCP connections survive supervisor failures without reset.
