# Operational Verification Labs: Computer Networking

## Objective & Environment Setup

Network infrastructure forms the foundational substrate upon which all distributed computing systems operate. The ability to diagnose, verify, and troubleshoot network behavior at multiple protocol layers distinguishes competent infrastructure operators from those who merely react to alerts without understanding root causes. These operational verification labs ground networking practice in the Linux kernel's network stack architecture, moving from high-level abstractions down through socket buffers, packet scheduling disciplines, and hardware interrupt processing. The verification methodology progresses through three fundamental stages: first, establishing baseline visibility into live network state and internal kernel subsystems; second, characterizing performance limits through controlled saturation and benchmarking; third, inducing deliberate faults to validate recovery mechanisms and observe cascading failure modes.

The lab environment assumes a contemporary Linux distribution with kernel version 5.10 or later, providing access to modern eBPF infrastructure, enhanced socket statistics via the `ss` utility from the iproute2 suite, and hardware-level diagnostic capabilities through `ethtool`. The practitioner must install the core diagnostic toolchain before proceeding. On Debian-based systems, execute `apt-get install -y iproute2 ethtool tcpdump linux-tools-common linux-tools-generic bpftrace`, while RHEL derivatives require `dnf install -y iproute ethtool tcpdump perf bpftrace`. For containerized workload diagnostics, install `kubectl` following the official Kubernetes documentation for your distribution, and obtain `crictl` from the CNCR releases page to interact directly with the container runtime. Cloud-native environments additionally benefit from `helm` for managing complex application deployments and `etcdctl` for inspecting cluster state coordination.

Network verification differs fundamentally from application-layer debugging because packet flows traverse hardware interrupt handlers, kernel network stacks with multiple queueing disciplines, socket buffer pools, and eventually cross namespace boundaries in containerized environments. Each layer introduces latency, potential packet loss, and state transitions that remain invisible to traditional application monitoring. The exercises that follow systematically expose these layers, teaching operators to correlate symptoms observed at one layer with root causes originating several layers below. A dropped packet may manifest as an application timeout, but the underlying cause could be hardware ring buffer exhaustion, netfilter connection tracking table overflow, or TCP congestion control algorithm state machine mistuning. The verification methodology trains the practitioner to traverse this diagnostic tree efficiently, using precise instrumentation rather than speculation.

The verification environment requires at least two network endpoints for realistic traffic generation and observation. On a single development workstation, leverage network namespaces to create isolated network stacks within the same kernel, providing complete separation of routing tables, iptables rules, and interface configurations. For production-representative scenarios, establish a minimal two-node Kubernetes cluster using kubeadm or a managed service, ensuring that pod-to-pod communication traverses a CNI plugin like Cilium or Calico that implements network policy enforcement and observable service mesh primitives. Throughout these labs, verification commands include their expected output structure, allowing operators to distinguish healthy baseline behavior from anomalous conditions that warrant deeper investigation.

## Exercise 1: Live State & Internal Subsystem Inspection

Network state inspection begins at the physical interface layer, where hardware statistics accumulate packet counters, error conditions, and resource utilization metrics that reveal the ground truth of network health. The `ip` command from iproute2 provides the canonical interface to this layer, exposing both configuration state and runtime statistics through a unified command syntax. Execute `ip -s link show` to enumerate all network interfaces with detailed statistics. The output structure presents each interface with transmit and receive packet counts, byte totals, error counters, and dropped packet indicators. On a healthy interface, the RX and TX packet counts increment monotonically with network activity, while errors and drops remain at zero or grow negligibly relative to total traffic volume.

Consider a typical production interface output: the `eth0` device shows several million received packets with zero errors but exhibits a non-zero drop count in the thousands. This pattern immediately narrows diagnostic focus to receive-side buffer exhaustion or CPU saturation preventing timely packet processing. The dropped packet counter specifically increments when the kernel's network stack cannot dequeue packets from the hardware ring buffer quickly enough, causing the NIC to discard incoming frames. Cross-reference this symptom with CPU interrupt distribution by examining `/proc/interrupts` and filtering for the interface's interrupt queue. Modern multi-queue NICs distribute packet processing across multiple CPU cores through Receive Side Scaling (RSS), but misconfigured IRQ affinity can concentrate interrupt load onto a single core, creating an artificial bottleneck even on an otherwise idle system.

Drill deeper into hardware-level configuration and capabilities using `ethtool`, the canonical utility for querying and modifying NIC parameters. Execute `ethtool eth0` to display link speed, duplex mode, and auto-negotiation status. A production interface must show "Speed: 10000Mb/s" (for 10GbE) or higher, "Duplex: Full", and "Link detected: yes". Any deviation—half-duplex negotiation, reduced speed, or link flapping—indicates physical layer problems or switch port misconfiguration. The command `ethtool -S eth0` exposes vendor-specific hardware counters, including per-queue statistics for multi-queue devices. On Intel ixgbe NICs, observe counters like `rx_queue_0_packets`, `rx_queue_1_packets`, etc., to verify that RSS distributes load evenly across hardware queues. Significant imbalance suggests suboptimal RSS hash key configuration or asymmetric traffic flow patterns.

Ring buffer sizing directly impacts packet loss under burst traffic conditions. Query current settings with `ethtool -g eth0`, which displays maximum supported ring sizes and currently configured values for both RX and TX rings. The kernel default of 256 or 512 slots proves insufficient for high-throughput applications experiencing microsecond-scale traffic bursts. Increase the receive ring to its hardware maximum using `ethtool -G eth0 rx 4096`, allowing the NIC to buffer more incoming packets during temporary CPU scheduling delays. This adjustment trades memory consumption for improved resilience against packet loss, a worthwhile exchange in environments where packet drops translate directly to application-layer retransmissions and degraded user experience.

Transitioning from the hardware interface layer to the kernel's socket subsystem, the `ss` utility replaces the deprecated `netstat` command with vastly superior performance and filtering capabilities. The command `ss -tipm` provides comprehensive socket state inspection: `-t` filters for TCP sockets, `-i` displays internal TCP information including congestion control state, `-p` shows the owning process, and `-m` exposes socket memory allocation. Execute this command and observe the output structure. Each established TCP connection displays its state (ESTABLISHED, TIME_WAIT, etc.), local and peer addresses, send and receive queue depths, and critically, the congestion control algorithm and its current window parameters.

For a representative connection in the ESTABLISHED state, the internal information section reveals metrics like `cwnd:10`, `ssthresh:7`, `bytes_acked:1234567`, and `rtt:1.234/0.567`. The congestion window (`cwnd`) governs how many packets the sender can transmit before requiring an acknowledgment, directly determining throughput on high-latency paths. The slow start threshold (`ssthresh`) marks the boundary between exponential and linear congestion window growth. Round-trip time (`rtt`) and its variance govern retransmission timeout calculation. When troubleshooting slow transfer speeds, compare the congestion window size against the bandwidth-delay product: for a 10 Gbps link with 10ms RTT, the BDP equals (10^10 bits/sec × 0.01 sec) / 8 bits/byte = 12.5 MB, requiring a congestion window of approximately 8500 packets (assuming 1500-byte MTU). If `ss` reports `cwnd:10`, the connection operates at 0.1% of link capacity due to insufficient window scaling.

Socket memory pressure manifests in the receive and send queue depths displayed by `ss`. The output columns `Recv-Q` and `Send-Q` show bytes queued in the kernel socket buffers awaiting application consumption or network transmission. A persistently non-zero `Recv-Q` indicates that the application reads data slower than the network delivers it, potentially due to CPU saturation, blocking I/O operations, or inefficient read patterns. Conversely, a large `Send-Q` suggests network congestion or rate limiting preventing the kernel from draining the send buffer. Cross-reference socket buffer statistics with system-wide limits in `/proc/sys/net/core/rmem_max` and `/proc/sys/net/core/wmem_max`, ensuring that application requirements align with kernel-enforced maximums.

Connection tracking state for netfilter firewalls and NAT operations accumulates in the kernel's `nf_conntrack` subsystem, a frequent source of performance pathology in high-connection-rate environments. Inspect current connection tracking table utilization via `cat /proc/sys/net/netfilter/nf_conntrack_count` and compare against the maximum entries in `/proc/sys/net/netfilter/nf_conntrack_max`. When the count approaches the maximum, new connection attempts fail with "nf_conntrack: table full" kernel messages, causing application-layer connection errors that appear indistinguishable from network outages. The default maximum of 65536 entries proves grossly insufficient for modern microservices architectures where thousands of short-lived connections per second create rapid state table churn. Increase the limit to at least 1048576 using `sysctl -w net.netfilter.nf_conntrack_max=1048576`, and reduce the connection tracking timeout for TIME_WAIT states via `sysctl -w net.netfilter.nf_conntrack_tcp_timeout_time_wait=30` to accelerate state garbage collection.

In containerized environments, network namespaces introduce an additional diagnostic layer. Each pod in Kubernetes operates within its own network namespace, presenting a virtualized network stack isolated from the host and other pods. The container runtime creates a virtual ethernet (veth) pair for each pod, with one end residing in the pod's namespace and the peer anchored in the root namespace or a bridge. To inspect pod network state, first identify the container runtime socket—for containerd, this defaults to `unix:///run/containerd/containerd.sock`. Execute `crictl --runtime-endpoint unix:///run/containerd/containerd.sock pods` to list all pods with their IDs and namespaces. Select a target pod and obtain its network namespace path via `crictl inspect <pod-id> | jq -r '.info.runtimeSpec.linux.namespaces[] | select(.type=="network") | .path'`, typically yielding a path like `/var/run/netns/cni-xxxxxxxx`.

Enter the pod's network namespace using `nsenter --net=/var/run/netns/cni-xxxxxxxx` and execute standard networking commands within the isolated environment. Run `ip addr show` to observe the pod's interface configuration, typically showing a single `eth0` interface with the pod's assigned IP address and a loopback interface. Execute `ip route show` to verify the default gateway configuration, which should point to the CNI bridge or the node's primary interface depending on the network plugin implementation. The command `ss -tuln` within the namespace reveals only the sockets bound by processes in that specific pod, providing isolation verification. Exit the namespace with `exit` and return to the root namespace.

The CNI bridge or overlay network introduces additional packet forwarding mechanisms observable through `iptables` and routing table inspection. On the host namespace, execute `iptables -t nat -L -n -v` to display NAT rules inserted by the CNI plugin for masquerading pod traffic destined for external networks. Kubernetes services implemented via kube-proxy add DNAT rules that redirect ClusterIP traffic to backend pod endpoints. The command `iptables -t nat -L KUBE-SERVICES -n` enumerates all service DNAT rules, showing the virtual IP to real pod IP translation chains. Trace a specific service's packet path by identifying its ClusterIP in `kubectl get svc` output, locating the corresponding KUBE-SVC chain, and following the probability-based load balancing rules that select a backend pod endpoint.

For overlay networks like VXLAN used by Flannel or WireGuard used by Cilium, the encapsulation adds observable overhead and potential failure modes. Capture encapsulated traffic using `tcpdump -i eth0 -nn 'port 4789'` to observe VXLAN frames, or `tcpdump -i eth0 -nn 'port 51820'` for WireGuard. The outer packet headers reveal the underlay routing between Kubernetes nodes, while the inner headers carry the original pod-to-pod communication. Decapsulate and analyze the inner packet by running `tcpdump -i eth0 -nn -w capture.pcap 'port 4789'`, then opening the capture in Wireshark with VXLAN decoding enabled, or use `tcpdump -r capture.pcap -v` with appropriate verbosity to expose the encapsulated layer.

## Exercise 2: Benchmarking & Saturation Profiling

Establishing baseline network performance characteristics requires controlled traffic generation and precise measurement of throughput, latency, and packet loss under varying load conditions. The `iperf3` utility provides the canonical benchmarking framework, implementing both TCP and UDP traffic patterns with detailed statistics reporting. Install `iperf3` on both the source and destination endpoints using your distribution's package manager. On the destination node, launch the server process via `iperf3 -s`, which listens on TCP port 5201 by default. From the source node, initiate a 10-second TCP throughput test using `iperf3 -c <destination-ip> -t 10 -P 4`, where `-P 4` spawns four parallel TCP streams to saturate modern multi-queue network interfaces.

The iperf3 output presents per-second throughput measurements followed by aggregate statistics. A well-tuned 10 GbE link should approach 9.5 Gbps after accounting for Ethernet framing overhead, while a 1 GbE link peaks near 950 Mbps. Throughput significantly below these thresholds indicates bottlenecks in CPU processing, insufficient TCP window scaling, or intermediate network congestion. Observe the retransmission counter in the final statistics block; any non-zero value signals packet loss requiring investigation. Cross-reference iperf3 results with concurrent CPU utilization monitoring via `mpstat -P ALL 1`, watching for soft IRQ (`%soft`) CPU time exceeding 30% on any core, which indicates network stack processing saturation.

TCP throughput naturally adjusts to available bandwidth through congestion control algorithms, but UDP throughput testing exposes the raw packet forwarding capacity of the network path by bypassing congestion avoidance mechanisms. Execute `iperf3 -c <destination-ip> -u -b 10G -t 10` to generate UDP traffic at a target rate of 10 Gbps. The server-side output reports packet loss percentage, which should remain at zero on an uncongested link. Intentionally exceed the link capacity by requesting 20 Gbps on a 10 GbE link using `iperf3 -c <destination-ip> -u -b 20G -t 10` and observe the resulting packet loss. This establishes the hard limit of the physical link and verifies that intermediate devices correctly drop excess packets rather than buffering indefinitely, which would introduce unbounded latency.

Latency measurement requires different instrumentation than bulk throughput testing because latency exists in microsecond to millisecond scales while throughput operates on per-second intervals. The `ping` utility measures round-trip ICMP latency but suffers from coarse millisecond resolution and potential ICMP deprioritization by intermediate devices. For precise latency characterization, use `sockperf` or the TCP/UDP ping modes in `nuttcp`. Alternatively, leverage application-layer request-response timing with `curl` for HTTP endpoints: execute `curl -w "@curl-format.txt" -o /dev/null -s "http://<endpoint>/"` with a format file containing `time_namelookup: %{time_namelookup}\ntime_connect: %{time_connect}\ntime_starttransfer: %{time_starttransfer}\ntime_total: %{time_total}\n`. This decomposes total request time into DNS resolution, TCP handshake, server processing, and data transfer phases, isolating network latency from application processing time.

Under sustained load, observe latency distribution rather than simple averages, as tail latencies reveal queueing behavior and processing variance hidden by mean statistics. Generate sustained background traffic using `iperf3` while simultaneously measuring request latency with periodic `ping` or HTTP requests. On an unloaded network, latency remains stable with minimal variance. Under saturation, observe latency increase and variance spike as packets queue in interface buffers, switch queues, and kernel socket buffers. The difference between minimum and 99th-percentile latency quantifies bufferbloat, the accumulation of excessive buffering that trades latency for minimal packet loss.

Profiling network stack CPU utilization isolates processing bottlenecks between hardware interrupt handling, software interrupt processing (NET_RX softirq), and application-layer processing. The `perf` tool provides comprehensive system-wide profiling with symbol resolution into kernel functions. During an active `iperf3` test, execute `perf record -a -g -- sleep 10` to capture 10 seconds of system-wide stack traces, then analyze with `perf report`. The output displays the top CPU-consuming functions, typically dominated by `__netif_receive_skb_core`, `tcp_v4_rcv`, and `tcp_ack` during receive-heavy workloads. If a significant percentage appears in `copy_user_enhanced_fast_string`, the CPU spends excessive time copying data between kernel and userspace, suggesting opportunities for zero-copy techniques like `MSG_ZEROCOPY` sockets or kernel bypass frameworks.

The `bpftrace` dynamic tracing framework enables surgical observation of specific kernel functions without recompilation or performance overhead from comprehensive profiling. To measure per-packet processing latency through the network stack, create a tracing script that timestamps packets at the NIC driver receive function and again at socket delivery. Write the following script to `net-latency.bt`:

```bpf
kprobe:napi_gro_receive
{
  @start[arg0] = nsecs;
}

kprobe:sock_def_readable
/ @start[arg0] /
{
  $latency = nsecs - @start[arg0];
  @usecs = hist($latency / 1000);
  delete(@start[arg0]);
}

interval:s:5
{
  print(@usecs);
  clear(@usecs);
}
```

Execute `bpftrace net-latency.bt` during traffic generation to observe a histogram of packet processing latencies in microseconds, updated every 5 seconds. The distribution reveals whether processing times cluster tightly around a median value or exhibit a long tail indicating occasional scheduling delays or cache misses.

Container network performance introduces additional layers of abstraction and potential overhead. Compare baseline host-to-host throughput against pod-to-pod throughput across the same physical nodes to quantify CNI plugin overhead. Deploy a simple `netshoot` pod on two different nodes using the manifest:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: netshoot
  namespace: default
spec:
  containers:
  - name: netshoot
    image: nicolaka/netshoot:latest
    command: ["sleep", "3600"]
  nodeSelector:
    kubernetes.io/hostname: <node-name>
```

Create two instances with different `nodeSelector` values targeting distinct nodes. Exec into the first pod with `kubectl exec -it netshoot -- bash` and install `iperf3` via `apk add iperf3`. Launch the iperf3 server, then exec into the second pod and run the client test targeting the first pod's IP. Compare the measured throughput against the host-to-host baseline established earlier. Overlay networks typically introduce 5-15% overhead due to encapsulation and additional routing lookups, while non-overlay implementations like Calico in direct routing mode approach host-level performance.

Service mesh sidecar proxies add another performance dimension. Deploy Envoy or Linkerd and repeat the pod-to-pod throughput test, now traversing the service mesh data plane. The sidecar intercepts both outbound and inbound traffic, applying policy enforcement, telemetry collection, and mutual TLS encryption. Throughput reduction of 20-40% is common, with latency increasing by hundreds of microseconds per request. Profile the sidecar's CPU consumption during the test using `kubectl exec -it <pod> -c istio-proxy -- curl -s localhost:15000/stats` (for Istio/Envoy) to retrieve detailed proxy statistics, including upstream connection pool utilization and request processing latency histograms.

## Exercise 3: Fault Injection & Recovery Analysis

Network fault injection validates system resilience by deliberately introducing failures and observing detection, recovery, and cascading effects. The Linux `tc` (traffic control) utility provides powerful fault injection capabilities including packet loss, latency injection, bandwidth limiting, and packet duplication. These operate at the kernel's queueing discipline layer, affecting all traffic egressing a network interface without requiring application modification. Begin with simple packet loss injection: execute `tc qdisc add dev eth0 root netem loss 5%` to randomly drop 5% of outbound packets. Generate traffic with `ping` or `curl` and observe the immediate impact—ping reports packet loss percentage, while HTTP requests experience increased latency and occasional timeouts as TCP retransmits lost segments.

TCP's reliability mechanisms should mask moderate packet loss from application-visible errors, but observe the throughput impact during an `iperf3` test. The congestion control algorithm interprets packet loss as congestion signals, reducing the congestion window and throttling transmission rate. A 5% loss rate can degrade throughput by 50% or more depending on the RTT and congestion control variant. Increase loss to 10% or 20% to observe the threshold at which TCP's recovery mechanisms become overwhelmed and application-layer timeouts occur. Remove the qdisc with `tc qdisc del dev eth0 root` to restore normal operation before proceeding.

Latency injection simulates WAN conditions or congested intermediate paths. Configure 50ms additional latency with 10ms variance using `tc qdisc add dev eth0 root netem delay 50ms 10ms`. Execute `ping <destination>` and observe the RTT increase by approximately the injected latency value. Launch an `iperf3` TCP test and note the throughput reduction—on high-bandwidth links, throughput becomes latency-limited by the bandwidth-delay product. A 10 Gbps link with 50ms RTT requires a TCP window of (10^10 × 0.05) / 8 = 62.5 MB to sustain full throughput. Default kernel socket buffers and window scaling may prove insufficient, requiring tuning via `sysctl -w net.ipv4.tcp_rmem="4096 131072 134217728"` to increase maximum receive window size.

Bandwidth limiting simulates constrained links or enforces Quality of Service policies. Shape traffic to 100 Mbps using `tc qdisc add dev eth0 root tbf rate 100mbit burst 32kbit latency 400ms`, implementing a token bucket filter that enforces the rate limit while allowing short bursts. Run an `iperf3` test and verify that throughput caps at approximately 100 Mbps regardless of link capacity. This qdisc configuration introduces a trade-off between burst tolerance (the `burst` parameter) and latency (the `latency` parameter)—larger bursts accommodate traffic spikes but increase queueing delay, while smaller bursts minimize latency but drop packets during brief rate excursions.

Combine multiple impairments to simulate realistic adverse conditions: `tc qdisc add dev eth0 root netem delay 100ms 20ms loss 2% rate 500mbit`. This configuration adds 100ms latency with 20ms variance, 2% random packet loss, and a 500 Mbps rate limit. Test application behavior under these conditions, observing timeout configurations, retry logic, and circuit breaker activation. Well-designed distributed systems should degrade gracefully, perhaps increasing request latency but maintaining availability. Brittle systems exhibit cascading failures as timeouts trigger retries that exacerbate congestion, leading to complete service failure despite only moderate network degradation.

Interface flapping simulates cable disconnections or switch port resets. Script a loop that alternates bringing an interface down and up with deliberate timing: `for i in {1..5}; do ip link set dev eth0 down; sleep 2; ip link set dev eth0 up; sleep 5; done`. During the down periods, all traffic through the interface fails immediately. Observe application behavior—properly implemented connection pools should detect failures, mark backends unhealthy, and failover to alternate paths or nodes. Monitor Kubernetes pod events with `kubectl get events -w` during interface flapping on a node hosting application pods; the kubelet should detect the node network failure and potentially mark pods as not ready, triggering service endpoint removal and traffic redirection.

Connection tracking table exhaustion simulates the failure mode where conntrack table filling prevents new connections despite available resources. Reduce the conntrack maximum to a low value like `sysctl -w net.netfilter.nf_conntrack_max=100`, then generate many concurrent connections using `ab` (ApacheBench) or `wrk`: execute `ab -n 10000 -c 100 http://<endpoint>/` to create 100 concurrent connections across 10,000 total requests. Monitor kernel messages with `dmesg -w` and observe "nf_conntrack: table full, dropping packet" errors once the table fills. New connection attempts fail with connection timeout errors. This failure mode proves particularly insidious in microservices architectures where each HTTP request traverses multiple service hops, each consuming conntrack entries on intermediate nodes.

DNS failure injection tests application resilience to name resolution failures, a common operational issue often overlooked during testing. Temporarily break DNS by modifying `/etc/resolv.conf` to point to a non-existent nameserver: `echo "nameserver 192.0.2.1" > /etc/resolv.conf`. Attempt to connect to services by hostname and observe application behavior. Well-implemented clients should timeout quickly, log meaningful error messages, and potentially fallback to cached IP addresses or alternate resolution mechanisms. Poorly implemented clients may hang indefinitely waiting for DNS responses, exhausting connection pools and cascading to downstream service failures.

In Kubernetes, inject network policy violations to validate enforcement. Create a restrictive network policy that denies pod-to-pod communication:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all
  namespace: default
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

Apply with `kubectl apply -f deny-all-netpol.yaml` and attempt pod-to-pod communication via `kubectl exec`. Connections should time out immediately as the CNI plugin enforces the policy at the packet filter layer. Verify enforcement by capturing traffic with `tcpdump` on the node—SYN packets should not appear on the destination pod's veth interface, confirming that filtering occurs before packets reach the pod's network namespace. Delete the policy with `kubectl delete networkpolicy deny-all` to restore connectivity.

Service mesh fault injection leverages higher-layer awareness to inject faults selectively based on request attributes. For Istio, create a VirtualService with fault injection rules:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: fault-injection-test
  namespace: default
spec:
  hosts:
  - httpbin.default.svc.cluster.local
  http:
  - fault:
      delay:
        percentage:
          value: 50
        fixedDelay: 5s
      abort:
        percentage:
          value: 10
        httpStatus: 503
    route:
    - destination:
        host: httpbin.default.svc.cluster.local
```

This configuration injects a 5-second delay into 50% of requests and aborts 10% with HTTP 503 status. Apply the VirtualService and generate requests to the service. Observe client-side timeout behavior, retry logic, and monitoring alert triggering. The service mesh provides request-level observability through distributed tracing, allowing correlation of injected faults with end-user impact in monitoring dashboards.

Recovery analysis requires observing system behavior as faults clear. After injecting a severe fault like interface flapping or conntrack exhaustion, remove the fault condition and measure recovery time—how long until full throughput restores, error rates return to baseline, and connection pools refill. Plot metrics over time to identify slow-recovering components that may accumulate state corruption or require manual intervention. Distributed systems with proper health checking and circuit breakers should recover within seconds to a few minutes, while systems lacking these mechanisms may require pod restarts or even node evacuations to restore full functionality.

## Diagnostic Cheat Sheet & Verification Checklist

The systematic verification of network infrastructure progresses through a structured diagnostic hierarchy, beginning with physical layer validation and ascending through protocol layers to application-level observability. Each layer presents distinct failure modes with characteristic symptoms and targeted diagnostic commands. The following cheat sheet and checklist codify this methodology for rapid troubleshooting and ongoing operational verification.

Physical and link layer verification starts with interface enumeration and statistics review. Execute `ip -s -s link show` for comprehensive interface state including extended statistics beyond the basic single `-s` flag output. Verify that the link state shows "state UP", the MTU matches expected values (typically 1500 for standard Ethernet or 9000 for jumbo frames), and the qdisc (queueing discipline) matches the intended configuration (usually "mq" for multi-queue or "fq_codel" for single-queue with fair queueing and controlled delay). Error and drop counters must remain zero or grow only during confirmed incident windows. Cross-reference with hardware-level statistics via `ethtool -S <interface>` to distinguish packet drops at the NIC hardware from kernel-level drops, indicated by counters like `rx_dropped` versus software drops in `ip -s` output.

Link negotiation failures manifest as reduced throughput or intermittent connectivity. Verify negotiated speed and duplex with `ethtool <interface>`, confirming full-duplex operation at the expected line rate. For 10GbE interfaces, validate flow control configuration with `ethtool -a <interface>`—asymmetric flow control (receive on, transmit off) often provides optimal performance by allowing the switch to signal congestion without the endpoint pausing transmission. Ring buffer sizing impacts burst tolerance; query with `ethtool -g <interface>` and increase to hardware maximums for latency-tolerant, high-throughput applications. Interrupt coalescing settings from `ethtool -c <interface>` balance latency against CPU efficiency—lower coalescing values reduce per-packet latency but increase interrupt rate and CPU overhead.

Network layer diagnostics focus on routing and IP addressing. Verify routing table correctness with `ip route show` and `ip route get <destination-ip>` to simulate route lookup for a specific destination. The output displays the selected route, egress interface, and next-hop gateway. On multi-homed hosts, ensure that policy routing rules (`ip rule show`) do not inadvertently override the main routing table, causing traffic to route through unexpected interfaces. For IPv6, use `ip -6 route show` and verify that SLAAC or DHCPv6 correctly configured addresses via `ip -6 addr show`. The `ping` utility verifies basic reachability, but use `ping -M do -s 1472` to validate path MTU by sending maximum-sized packets with the Don't Fragment bit set, detecting intermediate links with reduced MTU that require fragmentation or path MTU discovery.

Transport layer socket state inspection leverages `ss` with various filters to isolate issues. The command `ss -tan` displays all TCP sockets in numeric format without DNS resolution. To focus on problematic states, filter with `ss -tan state established '( sport = :80 or dport = :80 )'` to show only established connections on port 80. The socket memory fields `Recv-Q` and `Send-Q` reveal backpressure: persistent non-zero `Recv-Q` indicates slow application reads, while non-zero `Send-Q` suggests network congestion or rate limiting. The internal TCP information from `ss -ti` exposes congestion window, RTT, and retransmission statistics. A congestion window (`cwnd`) of 10 or less on a long-lived connection indicates that TCP never exited slow start, suggesting packet loss or receive window limitations.

Connection tracking state for netfilter requires monitoring both current utilization and insertion/deletion rates. Execute `watch -d 'cat /proc/sys/net/netfilter/nf_conntrack_count'` to observe the count update in real-time, highlighting changes. Compare against the maximum from `/proc/sys/net/netfilter/nf_conntrack_max`. For detailed per-connection state, examine `/proc/net/nf_conntrack`, though this proves expensive on systems with hundreds of thousands of connections. Instead, aggregate statistics from `/proc/net/stat/nf_conntrack` provide insertion/deletion rates and dropped connection counts without iterating the entire table. Elevate the maximum well beyond observed peak utilization to provide headroom during traffic spikes, but understand that each entry consumes approximately 350 bytes of unswappable kernel memory, so a limit of 4 million entries requires roughly 1.3 GB of dedicated memory.

Packet capture with `tcpdump` provides ground-truth verification of actual network behavior. Capture all traffic on an interface with `tcpdump -i eth0 -nn -w capture.pcap`, then analyze offline with `tcpdump -r capture.pcap` or Wireshark for protocol dissection. For targeted capture, filter by host and port: `tcpdump -i eth0 -nn 'host 10.0.0.5 and port 80'`. To capture only TCP SYN packets for connection rate analysis, use `tcpdump -i eth0 -nn 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0'`. Capture snaplen can be reduced for header-only analysis with `-s 96` to capture just the IP and TCP headers without payload, reducing storage requirements during high-volume captures. Always capture to a file rather than displaying packets in real-time to avoid dropping packets when display processing cannot keep pace with packet arrival rates.

Container and pod networking diagnostics begin with `kubectl get pods -o wide` to display pod IPs and hosting nodes. For detailed network configuration, use `kubectl describe pod <pod-name>` and examine the annotations section for CNI plugin metadata including assigned IP addresses and network policy associations. Direct container runtime interaction via `crictl` bypasses Kubernetes abstractions; list running containers with `crictl ps` and inspect network configuration with `crictl inspect <container-id>`. The output includes the network namespace path, which can be entered with `nsenter` to execute networking commands within the pod's isolated stack.

Service connectivity troubleshooting requires verifying the entire service chain from ClusterIP to endpoint pod IPs. Execute `kubectl get svc <service-name>` to retrieve the ClusterIP and port, then list backend endpoints with `kubectl get endpoints <service-name>`. The endpoints list must contain at least one pod IP for the service to function. If empty, check pod readiness with `kubectl get pods -l <service-selector>` and examine readiness probe failures. On a cluster node, inspect iptables rules with `iptables -t nat -L KUBE-SERVICES -n | grep <clusterip>` to trace the NAT chain implementing service load balancing. Each service has a KUBE-SVC chain that branches to KUBE-SEP chains, one per endpoint, with probability-based random selection implementing load distribution.

CNI plugin diagnostics vary by implementation, but common failure modes include bridge or tunnel interface misconfiguration and route propagation failures. For bridge-based CNIs like Flannel, verify bridge existence and attached veth interfaces with `ip link show type bridge` and `bridge link show`. For overlay networks, confirm tunnel interfaces exist with `ip link show type vxlan` or `ip link show type wireguard`, and verify that kernel routing directs pod CIDR traffic into the tunnel. The command `ip route show table all` displays all routing tables including CNI-managed tables, which may use policy routing to direct pod traffic. CNI plugin logs typically reside in `/var/log/pods/<namespace>_<pod-name>_<pod-uid>/<container-name>/` or are accessible via `kubectl logs -n kube-system <cni-pod-name>`.

Performance analysis checklist begins with establishing baseline measurements for comparison during troubleshooting. Use `iperf3` to measure host-to-host, pod-to-pod, and pod-to-service throughput, recording values for both TCP and UDP. Execute latency measurements with `ping` or application-level requests, capturing minimum, average, and 99th percentile values. Profile CPU utilization during saturation tests with `perf record` followed by `perf report`, identifying the dominant kernel functions in network processing. The baseline characterization should cover both normal operating conditions and synthetic saturation scenarios, providing reference points that reveal when performance degrades below expected levels.

The verification checklist for each layer ensures systematic coverage:

Physical layer: Link state UP, negotiated speed correct, duplex full, hardware error counters at zero, ring buffers sized for workload, RSS/multi-queue active with balanced interrupt distribution.

Network layer: Routing table correct, default gateway reachable, source IP address assigned, MTU consistent across path, fragmentation not occurring, ARP/ND table populated for active peers.

Transport layer: Socket state appropriate for application phase, congestion window scaling with bandwidth-delay product, retransmission rate below 1%, socket buffer sizes sufficient, connection tracking table below 80% utilization.

Application layer: DNS resolution succeeding, TLS handshake completing, HTTP response codes appropriate, request latency within SLA bounds, connection pool utilization healthy, circuit breakers not tripped.

Container layer: Pod IPs assigned from correct CIDR, DNS resolves cluster.local names, service ClusterIP resolves to endpoint IPs, network policies enforced as configured, CNI plugin pods running, node-to-node connectivity functional.

This diagnostic framework and checklist provide the operational foundation for maintaining robust network infrastructure, enabling rapid fault isolation and informed capacity planning. The practitioner internalizes these commands and verification patterns through repeated application across diverse failure scenarios, building the diagnostic intuition essential for operational excellence in production environments.
