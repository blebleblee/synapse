# Lesson 3: Runtime Engine, Networking Models, Persistent Storage

## 1. First-Principles Intuition & Invariants

Docker's success as a containerization platform rests not on a monolithic daemon architecture but on a carefully decomposed runtime stack that separates policy from mechanism, orchestration from execution, and user intent from kernel-level isolation. At the foundation of this separation lies **containerd**, a standalone daemon that evolved from Docker's internal runtime components into an industry-standard container lifecycle manager governed by the Cloud Native Computing Foundation. Containerd operates as the intermediary layer between high-level Docker CLI commands and the low-level **runc** binary that actually spawns isolated processes using Linux kernel primitives.

The architectural philosophy mirrors the Unix principle of composable tools with clear boundaries. When you execute `docker run`, the Docker daemon (`dockerd`) translates your declarative request—image name, resource limits, network attachments, volume mounts—into containerd's API calls. Containerd then unpacks the container image layers into an overlay filesystem bundle, constructs a runtime specification conforming to the Open Container Initiative (OCI) standard, and invokes runc to create the isolated process tree. This handoff model ensures that the critical security boundary—the transition from trusted daemon to untrusted container code—occurs in a minimal, auditable binary (runc) rather than a large daemon process.

The invariant principle governing container execution is **process substitution with namespace isolation**. Unlike virtual machines that virtualize hardware through a hypervisor, containers virtualize the operating system through kernel-level namespaces. A container is fundamentally a process (or process group) that perceives itself as the only tenant on the machine, unaware of sibling containers or the host's true state. This perception is enforced through six namespace types: **PID** (process ID isolation), **Mount** (filesystem isolation), **Network** (network stack isolation), **IPC** (inter-process communication isolation), **UTS** (hostname isolation), and **User** (UID/GID mapping). Every container begins its life in a dedicated namespace hierarchy, with its init process (PID 1 from the container's perspective) anchored by the pause/infra container that holds the namespace references open for the container's lifetime.

Resource constraints layer atop namespace isolation through **cgroups** (control groups), the kernel's accounting and limiting framework. When you specify `--memory=512m` or `--cpus=2.0`, Docker translates these declarations into cgroup hierarchy entries under `/sys/fs/cgroup/`. The cgroup subsystems—memory, cpu, blkio, pids—enforce hard and soft limits by intercepting system calls and denying resource allocation requests that exceed configured thresholds. This dual mechanism of namespaces (visibility isolation) and cgroups (resource isolation) forms the immutable foundation of container security and performance boundaries.

Docker's networking model confronts a fundamental tension: containers must perceive themselves as isolated network endpoints with unique IP addresses, yet they must communicate efficiently with the external world, sibling containers, and services on the host. Traditional network virtualization through full protocol stack emulation (as in KVM or Xen) imposes unacceptable overhead for lightweight containers. Docker resolves this through **virtual Ethernet pairs** (veth devices) that act as bidirectional pipes connecting container network namespaces to Linux bridges on the host. Each veth pair consists of two endpoints: one anchored inside the container's network namespace (`eth0` from the container's view) and one plugged into a host-side bridge (`docker0` by default). The bridge operates as a software-defined Layer 2 switch, forwarding Ethernet frames between containers and applying NAT (Network Address Translation) rules through iptables to masquerade container traffic as originating from the host's external interface.

The critical insight underpinning Docker's network drivers is that **packet forwarding decisions occur in kernel space**, not user space. When a container sends a packet destined for the internet, the kernel's routing subsystem consults the bridge's forwarding database, determines that the destination lies outside the bridge domain, and routes the packet through the host's default gateway. However, the source IP address belongs to Docker's private subnet (typically `172.17.0.0/16`), which is not globally routable. The kernel's netfilter framework intervenes here: iptables rules installed by Docker in the `nat` table's `POSTROUTING` chain rewrite the source address to the host's external IP through SNAT (Source NAT), allowing the packet to traverse the internet. Return packets undergo reverse translation (DNAT) in the `PREROUTING` chain, restoring the original container IP before forwarding through the bridge.

Persistent storage in containerized environments introduces a layering challenge distinct from virtual machine disk images. Containers inherit Docker's **copy-on-write layered filesystem** model, where each image layer is immutable and shared across all containers instantiated from that image. When a container modifies a file inherited from an image layer, the storage driver (overlay2, devicemapper, btrfs) intercepts the write operation and copies the file into the container's writable top layer before modification. This mechanism—termed **copy-up**—preserves image immutability while allowing container-specific state changes. However, copy-up semantics create an invariant problem for databases, logs, and other write-heavy workloads: the writable layer exists within the container's lifecycle and vanishes when the container is removed.

Docker's **volume** abstraction solves persistence by mounting host directories or named storage objects directly into the container's filesystem namespace, bypassing the copy-on-write layer stack entirely. Volumes exist independently of container lifecycles, managed by Docker's volume plugin system as first-class storage primitives. When you specify `-v /host/data:/container/data` (bind mount) or `-v pgdata:/var/lib/postgresql/data` (named volume), Docker instructs the kernel to perform a **bind mount** operation, making the target path a transparent window into the underlying storage. Writes to mounted paths bypass overlay2's copy-up mechanism, hitting the host filesystem directly with native kernel performance. This architectural separation—ephemeral layers for immutable application code, persistent volumes for mutable state—mirrors the functional programming principle of separating pure computation from side effects.

## 2. Core Architecture & Mechanics

The containerd runtime daemon operates as a gRPC server exposing a comprehensive API surface for container lifecycle management, image distribution, and snapshot coordination. When Docker daemon (`dockerd`) needs to execute a container, it establishes a Unix domain socket connection to containerd's API endpoint (typically `/run/containerd/containerd.sock`) and issues a `Create` RPC request encapsulating the container specification. Containerd's architecture decomposes into three primary subsystems: the **content store** for blob-addressed image layers, the **snapshot service** for managing filesystem layer hierarchies, and the **task service** for runtime execution.

The content store implements a content-addressable storage system where image layer tarballs are stored by their SHA-256 digest. When you pull an image, containerd's image service downloads each layer blob from the registry, verifies its cryptographic hash, and stores it in `/var/lib/containerd/io.containerd.content.v1.content/blobs/sha256/`. This design ensures deduplication: identical layers shared across multiple images consume storage exactly once. The manifest and config JSON documents that reference these layers are similarly stored by digest, forming a Merkle DAG (Directed Acyclic Graph) where every node is cryptographically verifiable by its hash.

Containerd's snapshot service translates this flat content-addressed layer store into a hierarchical filesystem view suitable for container execution. The service supports pluggable **snapshotters**—overlay, btrfs, zfs, devicemapper—each implementing the same interface with storage-driver-specific semantics. The overlay snapshotter, Docker's default for modern kernels, leverages Linux's OverlayFS to construct a unified filesystem view from multiple read-only lower directories (image layers) and a single read-write upper directory (container layer). When containerd prepares a container's root filesystem, it invokes `snapshotter.Prepare()`, which creates a new snapshot inheriting from the image's layer chain. This operation manifests as an OverlayFS mount combining all image layers as `lowerdir` entries and a fresh empty directory as `upperdir`:

```
mount -t overlay overlay \
  -o lowerdir=/layer5:/layer4:/layer3:/layer2:/layer1,\
     upperdir=/container/upper,\
     workdir=/container/work \
  /container/merged
```

The `workdir` serves as OverlayFS's internal scratch space for atomic rename operations during copy-up. When a process inside the container modifies a file in a lower layer, OverlayFS copies the entire file to `upperdir`, then redirects the write operation to the copied version. Subsequent reads resolve to the upper layer copy, shadowing the original lower layer file. This copy-up behavior is transparent to container processes but has profound performance implications: modifying large files inherited from image layers triggers full-file copies, consuming both I/O bandwidth and storage space in the writable layer.

Once the snapshot is prepared, containerd's task service invokes **runc** to create the actual container process. Runc is a minimal OCI runtime—a statically linked binary approximately 10MB in size—that performs exactly one function: spawn a process conforming to an OCI runtime specification JSON document. The specification, written by containerd to `/run/containerd/io.containerd.runtime.v2.task/<container-id>/config.json`, declares every aspect of the container's execution environment: root filesystem path, namespace configuration, cgroup limits, capability sets, seccomp filters, and the command to execute.

Runc's execution flow follows a precise sequence of system calls that transitions from the host's privileged context to the container's isolated environment:

1. **Fork a new process** that will become the container's init process. This child process inherits the host's namespace and security context initially.

2. **Unshare into new namespaces** by invoking `unshare(CLONE_NEWNS | CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWUTS | CLONE_NEWIPC | CLONE_NEWUSER)`. This system call creates fresh namespace instances, isolating the process from the host's view. The PID namespace creates a new process ID hierarchy where the container process becomes PID 1.

3. **Pivot the root filesystem** through `pivot_root()`, replacing the process's perception of `/` with the container's root filesystem snapshot. This operation is more secure than `chroot()` because it fully remounts the root, preventing escape through relative path traversal.

4. **Apply cgroup constraints** by writing the process's PID to cgroup hierarchy files in `/sys/fs/cgroup/`. For a memory limit, runc writes to `memory.limit_in_bytes`; for CPU quotas, it writes to `cpu.cfs_quota_us` and `cpu.cfs_period_us`. These writes must occur before executing the container command, ensuring the process never runs without resource constraints.

5. **Drop capabilities and apply security profiles**. Linux capabilities partition root privileges into granular units (CAP_NET_ADMIN, CAP_SYS_ADMIN, etc.). Runc removes all capabilities except those explicitly allowed in the OCI spec, reducing the attack surface. It then installs a seccomp filter—a Berkeley Packet Filter program running in the kernel—that whitelists allowed system calls and blocks dangerous operations like `reboot()`, `kexec_load()`, or unfiltered `ptrace()`.

6. **Execute the container command** via `execve()`, replacing the runc process with the user-specified binary (e.g., `/bin/sh`, `nginx`, `postgres`). The new process inherits all configured namespaces, cgroups, and security contexts. From this moment, the container is running.

Runc then exits, leaving a detached container process running under containerd's supervision. Containerd's shim process (`containerd-shim-runc-v2`) remains as the container's parent, monitoring for exit signals and maintaining the container's I/O streams (stdin, stdout, stderr) through Unix pipes or FIFOs. This shim architecture allows Docker daemon restarts without killing running containers: containerd re-attaches to existing shims, and they report container state from their maintained file descriptor handles.

Docker's networking subsystem implements multiple network drivers—bridge, host, overlay, macvlan—each optimized for different connectivity patterns. The **bridge driver** constructs a virtual Layer 2 network on the host, mediated by a Linux bridge device. When Docker daemon starts, it creates the `docker0` bridge and assigns it an IP address from a private subnet (`172.17.0.1/16` by default). Each container started with bridge networking receives a dedicated veth pair: one end assigned an IP address from the bridge subnet, the other end plugged into `docker0`.

Container IP address assignment occurs through Docker's embedded IPAM (IP Address Management) component, which maintains a lease database tracking allocated IPs per network. When a container starts, Docker queries IPAM for an available address, configures the container-side veth interface with that IP, sets the default route to the bridge IP, and injects DNS resolver configuration into `/etc/resolv.conf`. The bridge's forwarding table learns MAC-to-port mappings through standard Ethernet learning: when a container sends its first packet, the bridge records the source MAC address and associates it with the veth port.

Inter-container communication within the same bridge network bypasses the host's routing stack entirely. When container A (`172.17.0.2`) sends a packet to container B (`172.17.0.3`), the bridge performs MAC address lookup in its forwarding table and forwards the frame directly to container B's veth interface. The kernel never consults the routing table because both endpoints belong to the same Layer 2 domain. This provides near-native performance for intra-host container communication, limited only by veth pair bandwidth (typically gigabits per second on modern kernels).

External connectivity requires NAT translation through iptables. Docker installs a POSTROUTING rule in the `nat` table that masquerades outbound traffic:

```
iptables -t nat -A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
```

This rule matches packets originating from the Docker subnet that are not destined for the bridge itself, rewriting the source IP to the host's external interface address. The kernel's connection tracking subsystem (`nf_conntrack`) maintains a state table mapping translated connections back to their original container IPs, enabling bidirectional communication. When return packets arrive at the host's external interface, the kernel consults the connection tracking table, performs reverse DNAT, and forwards the packet through the bridge to the correct container.

Port publishing (`-p 8080:80`) introduces a DNAT rule in the PREROUTING chain, intercepting packets destined for the host's external IP on port 8080 and rewriting the destination to the container's IP and port 80:

```
iptables -t nat -A DOCKER ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80
```

The `! -i docker0` condition prevents loops: packets originating from within the bridge network are not subject to DNAT, avoiding double translation. This rule applies before routing decisions, causing the kernel to route the rewritten packet toward the bridge, where it reaches the container transparently. From the container's perspective, it receives a direct connection on port 80, unaware of the NAT translation.

The **host network** driver eliminates all namespace isolation, placing the container process directly in the host's network namespace. This mode provides maximum performance—no veth pair overhead, no bridge forwarding, no NAT translation—at the cost of forfeiting network isolation. Containers in host mode share the host's IP address and can bind to any port without conflict avoidance. This is ideal for performance-critical network services like load balancers or monitoring agents that need direct access to the host's network interfaces.

The **overlay driver** implements multi-host networking through VXLAN (Virtual Extensible LAN) encapsulation. Each host runs a Docker daemon that participates in a distributed key-value store (etcd, Consul, or Docker Swarm's embedded Raft store) maintaining a global view of overlay networks and container placements. When a container joins an overlay network, Docker creates a VXLAN tunnel endpoint (VTEP) on the host, assigns the container an IP from the overlay subnet, and programs forwarding rules into the kernel's FDB (Forwarding Database) and ARP cache.

VXLAN encapsulates Layer 2 Ethernet frames within UDP packets (port 4789) transmitted over the existing Layer 3 network. When container A on host 1 sends a packet to container B on host 2, both on the same overlay network, the kernel encapsulates the Ethernet frame in a UDP packet, routes it to host 2's physical IP, and host 2's VTEP decapsulates the frame before forwarding it to container B. This creates a flat Layer 2 network spanning multiple hosts, enabling containers to communicate as if connected to the same physical switch, regardless of underlying network topology.

Docker's volume plugin system abstracts persistent storage behind a unified API, allowing third-party storage providers (NFS, Ceph, AWS EBS, Azure Disk) to integrate through plugin drivers. The plugin interface defines operations for volume creation, mounting, unmounting, and deletion. When you create a named volume with `docker volume create --driver local mydata`, Docker invokes the plugin's `Create` method, which provisions storage according to driver-specific semantics. The local driver simply creates a directory on the host filesystem under `/var/lib/docker/volumes/mydata/_data`.

Mounting a volume into a container triggers the plugin's `Mount` call, which returns a filesystem path on the host. Docker then instructs runc to bind-mount this path into the container's filesystem namespace at the specified mount point. The bind mount operation—`mount --bind /var/lib/docker/volumes/mydata/_data /container/merged/data`—creates a bidirectional view where both paths reference the same underlying inode tree. Modifications made inside the container at `/data` instantly appear at the host path, and vice versa. This differs fundamentally from copy-on-write layers: bind-mounted volumes bypass the overlay filesystem entirely, interacting directly with the host's native filesystem.

Bind mounts (`-v /host/path:/container/path`) differ from named volumes in lifecycle management and portability. Bind mounts reference explicit host filesystem paths, tightly coupling the container to the host's directory structure. Named volumes are Docker-managed objects with independent lifecycles: they persist after container removal, can be shared across multiple containers simultaneously, and can be backed by remote storage systems through volume plugins. Bind mounts are ideal for development workflows where you want to inject local source code into a container for live editing. Named volumes serve production workloads requiring data durability and storage provider abstraction.

The mount propagation model controls visibility of mount events between namespaces. Docker defaults to **private** propagation, where mounts performed in the container are invisible to the host, and vice versa. This prevents container mount operations from polluting the host's mount table. Shared propagation (`--mount type=bind,source=/host,target=/container,bind-propagation=shared`) enables bidirectional mount event propagation, useful for scenarios like systemd containers that need to observe host mount changes.

## 3. High-Performance Optimization & Failure Modes

Container runtime performance hinges on minimizing the overhead introduced by namespace isolation, copy-on-write filesystem layers, and network virtualization. The first optimization target is **image layer structure**. Because OverlayFS performs copy-up on first write, placing frequently modified files in lower layers forces expensive full-file copies into the writable upper layer. Dockerfile construction should order layers from least-frequently-changing (base OS packages) to most-frequently-changing (application code), and should consolidate related operations into single RUN directives to minimize layer count. Each layer adds indirection to filesystem lookups: the kernel must traverse the layer stack during pathname resolution, consulting each lowerdir before determining the authoritative file version.

The overlay2 storage driver supersedes the legacy overlay driver by supporting multiple lower layers through OverlayFS's `lowerdir` colon-separated syntax. Legacy overlay drivers were limited to a single lower layer plus the upper layer, forcing Docker to merge intermediate layers through expensive mount stacking. Overlay2 eliminates this limitation, allowing images with dozens of layers to be mounted efficiently. However, extremely deep layer stacks (100+ layers) still degrade performance due to increased directory traversal overhead. Image layer consolidation through multi-stage builds (`FROM alpine AS build` followed by `COPY --from=build`) reduces layer depth while preserving build cache granularity.

For write-intensive workloads—databases, log aggregators, build caches—always mount dedicated volumes bypassing the overlay filesystem. A PostgreSQL container storing data in the writable layer suffers catastrophic performance degradation because every write to database pages triggers copy-up from the image layer. A properly configured PostgreSQL container mounts a volume at `/var/lib/postgresql/data`, ensuring all I/O hits the host filesystem's native performance profile without overlay indirection. The performance gap is measurable: database write throughput increases 5-10x when using volumes versus writable layers.

Volume mount performance itself varies by filesystem type. The local driver creates directories on the host's root filesystem, inheriting its characteristics (ext4, xfs, btrfs). XFS provides superior performance for large files and concurrent writes due to its extent-based allocation and delayed allocation optimizations. Btrfs offers copy-on-write snapshots at the filesystem level, enabling efficient volume cloning but with higher CPU overhead. For distributed storage, NFS-backed volumes introduce network latency but enable cross-host volume sharing. Block storage plugins (AWS EBS, Azure Disk) provide POSIX filesystem semantics over remote block devices, trading network latency for durability and replication.

Container networking performance depends critically on packet path length—the number of kernel subsystems a packet traverses between application socket and physical NIC. Bridge networking introduces veth pair traversal, bridge forwarding, and iptables NAT processing. Each stage adds microseconds of latency and consumes CPU cycles. Host networking eliminates all these stages, delivering bare-metal performance but sacrificing isolation. For latency-sensitive services (high-frequency trading, real-time video processing), host networking is mandatory. For standard web services where isolation outweighs microsecond latency improvements, bridge networking suffices.

Overlay networks add VXLAN encapsulation overhead: each packet grows by 50 bytes (VXLAN header + outer IP/UDP headers), and the kernel performs additional encap/decap processing. VXLAN performance degrades on high packet-per-second workloads (DNS servers, network appliances) where the fixed per-packet overhead dominates. For such workloads, macvlan networking—which assigns each container a real MAC address on the physical LAN—eliminates encapsulation at the cost of requiring promiscuous mode on the host NIC and consuming LAN IP addresses.

IPTables rule proliferation becomes a performance bottleneck in environments with hundreds of containers and complex port publishing configurations. Each published port adds a DNAT rule, and the kernel evaluates rules linearly during packet processing. Docker's iptables rule insertion uses a single DOCKER chain in the NAT table, but large deployments can accumulate thousands of rules. The kernel's netfilter connection tracking subsystem, which maintains state for NAT translation, has a finite connection tracking table (`nf_conntrack_max`), typically defaulting to 65536 entries. Exceeding this limit causes dropped packets and connection failures.

Optimizing iptables performance requires two strategies: minimize rule count through network segmentation (use overlay networks for inter-service communication, reducing published ports), and increase connection tracking table size via `sysctl -w net.netfilter.nf_conntrack_max=262144`. For extreme scale (thousands of containers, millions of connections), replacing iptables with nftables or eBPF-based packet processing reduces rule evaluation overhead. However, Docker's native integration with nftables remains limited, requiring custom network plugin development.

Container lifecycle failures manifest through several failure modes tied to resource exhaustion. **OOM (Out-of-Memory) kills** occur when a container exceeds its memory cgroup limit. The kernel's OOM killer selects a process within the cgroup to terminate, often the container's PID 1, causing the entire container to exit. The Docker daemon logs this as exit code 137 (`SIGKILL`). Preventing OOM kills requires careful memory limit sizing based on application profiling. Setting limits too low causes spurious kills; setting too high risks exhausting host memory and triggering host-level OOM.

**CPU throttling** occurs when a container exhausts its CPU quota within a cgroup period. Unlike memory limits (hard constraints enforced through process termination), CPU limits are soft constraints enforced through scheduling delays. The kernel's CFS scheduler assigns CPU time proportional to each cgroup's shares or quota. When a container exhausts its quota (e.g., 100ms of CPU time per 100ms period for `--cpus=1.0`), the scheduler suspends all processes in the cgroup until the next period begins. This manifests as application stalls: HTTP requests timeout, database queries slow down, but the container continues running. Diagnosing CPU throttling requires inspecting cgroup metrics at `/sys/fs/cgroup/cpu/docker/<container-id>/cpu.stat`, where `nr_throttled` and `throttled_time` reveal throttling events.

**Volume mount failures** surface as permission errors or missing directories inside containers. Bind mounts depend on the host filesystem's permission model: if the host path is owned by UID 1000 and the container process runs as UID 33 (www-data), writes fail with `EACCES`. Named volumes managed by Docker are created with root ownership by default, but volume plugin drivers can inject ownership metadata. Resolving permission mismatches requires either matching UIDs between host and container (through `--user` flag or Dockerfile `USER` directive), or mounting volumes with relaxed permissions.

**Network isolation breaches** occur when containers unexpectedly access external networks or other containers despite network policy intentions. Docker's default bridge network has no isolation between containers: any container on `docker0` can communicate with any other. Creating custom bridge networks (`docker network create isolated-net`) enables network-level isolation: containers on different custom bridges cannot communicate unless explicitly connected to both networks. However, all bridge networks share the host's routing table and iptables rules, so containers can still access external networks unless `--internal` flag restricts them.

Diagnosing network failures requires inspecting multiple layers: container network namespace (`docker exec <container> ip addr`, `ip route`), bridge configuration (`ip link show docker0`, `brctl show`), iptables rules (`iptables -t nat -L -n -v`), and connection tracking state (`conntrack -L`). A common failure mode involves stale connection tracking entries preventing new connections after container restart. Flushing the connection tracking table (`conntrack -F`) clears stale state but disrupts all existing connections.

**Filesystem corruption in volumes** occurs when multiple containers mount the same volume with concurrent writes to non-concurrent-safe filesystems or databases. SQLite databases, Berkeley DB files, and similar embedded databases assume exclusive access; concurrent writes from multiple container processes cause database corruption. The solution requires either application-level locking (advisory file locks through `flock()`), or restricting volume mounts to a single writer container while other containers mount read-only (`-v mydata:/data:ro`).

**Image layer cache invalidation** degrades build performance when Dockerfile instructions change frequently. Docker caches each layer by hashing the instruction and its inputs; changing a single instruction invalidates all subsequent layers. Build optimization requires ordering instructions to maximize cache hits: copy dependency manifests (`package.json`, `requirements.txt`) and install dependencies before copying application source code. This ensures dependency installation layers remain cached across source code changes. Multi-stage builds amplify this pattern, allowing intermediate stages to cache independently.

**Containerd resource leaks** manifest as accumulating disk usage in `/var/lib/containerd/` despite removing containers and images. Containerd's content store garbage collection reclaims unused blobs, but orphaned snapshots persist if container removal fails mid-operation. Forced cleanup requires containerd's `ctr` CLI: `ctr -n moby snapshots list` enumerates snapshots, and `ctr -n moby snapshots remove` deletes orphaned entries. The `-n moby` namespace flag targets Docker's containerd namespace, isolating it from other containerd users on the system.

**Runc execution failures** typically surface as `container runtime not found` or `invalid spec` errors. The OCI runtime spec's JSON structure must precisely match kernel capabilities and feature availability: specifying an unsupported namespace type, invalid cgroup controller, or nonexistent device path causes runc to fail before executing the container command. Debugging requires examining the generated config.json in `/run/containerd/` and validating each field against kernel support (check `/proc/self/ns/` for namespace types, `/sys/fs/cgroup/` for cgroup controllers).

**Network plugin failures** in overlay networks often stem from etcd/Consul connectivity issues or firewall rules blocking VXLAN traffic. Overlay networking requires UDP port 4789 open between all Docker hosts. If VXLAN packets are dropped, containers on different hosts cannot communicate despite successful overlay network creation. Diagnosing overlay failures requires checking VXLAN interface state (`ip -d link show`), verifying FDB entries (`bridge fdb show`), and testing UDP reachability between hosts with `nc -u <host-ip> 4789`.

Production resilience demands configuring Docker daemon with appropriate storage drivers, enabling JSON logging drivers with rotation (`--log-driver json-file --log-opt max-size=10m --log-opt max-file=3`), and monitoring containerd metrics through Prometheus exporters. Containerd exposes Prometheus metrics on a configurable port (default 1338) reporting container count, image pull latency, snapshot operations, and runtime execution failures. Grafana dashboards built atop these metrics provide visibility into runtime health, enabling proactive identification of resource exhaustion, storage driver degradation, or network plugin failures before they cascade into outages.
