# Lesson 2: Networking, CNI Plugins, and Service Discovery in EKS

## 1. First-Principles Intuition & Invariants

When Amazon Elastic Kubernetes Service provisions a managed control plane, it does not create an isolated networking domain divorced from your existing Virtual Private Cloud infrastructure. Instead, EKS anchors every pod and service directly into the flat IPv4 address space of your VPC subnets, eliminating the network address translation layers, overlay tunnels, and encapsulation overhead that plague traditional Kubernetes networking models. This architectural decision—routing pod traffic through native VPC constructs rather than synthesizing a parallel software-defined network—transforms the operational surface of cluster networking from an abstract distributed system problem into a concrete exercise in subnet capacity planning, elastic network interface lifecycle management, and AWS Identity and Access Management policy enforcement.

The Container Network Interface specification defines a plugin contract through which Kubernetes delegates IP address assignment, route installation, and namespace network configuration to an external binary. When the kubelet instantiates a new pod sandbox, it invokes the CNI plugin with a JSON payload describing the network namespace, container ID, and requested configuration. The plugin must allocate an IP address, configure the veth pair linking the pod's network namespace to the host, program routing tables, and return the assigned address and gateway to the kubelet. EKS ships with the AWS VPC CNI plugin as the default implementation, but this choice carries profound consequences that ripple through capacity planning, security posture, and operational workflows.

Traditional overlay-based CNI plugins such as Calico or Flannel allocate pod IPs from a private CIDR block divorced from the underlying infrastructure, then encapsulate pod-to-pod traffic in VXLAN or IP-in-IP tunnels that traverse the host network. This indirection simplifies multi-tenancy and enables portable IP addressing across heterogeneous clouds, but introduces latency from encapsulation headers, fragments the network troubleshooting surface between virtual and physical layers, and complicates security group enforcement because the VPC control plane cannot observe encapsulated flows. The AWS VPC CNI plugin inverts this model by attaching multiple elastic network interfaces directly to each EC2 worker node and assigning secondary private IP addresses from your VPC subnets to individual pods. Every pod receives a routable VPC IP address, making pod traffic indistinguishable from EC2 instance traffic at the network layer.

This design imposes a hard constraint on cluster density that operators accustomed to overlay networks frequently underestimate. An EC2 instance's maximum ENI count and secondary IP capacity scale with instance size according to fixed hardware tables published in AWS documentation. A t3.medium instance supports three ENIs with six IPv4 addresses each, yielding a maximum of eighteen pod IPs per node. A c5.4xlarge instance supports eight ENIs with thirty addresses each, providing capacity for two hundred forty pods. When the VPC CNI plugin exhausts the secondary IP pool on an existing ENI, it requests a new interface attachment from the EC2 API, waits for the attachment to complete, and begins allocating addresses from the new interface's secondary IP pool. This elastic scaling mechanism operates transparently during normal pod creation, but the upper bound enforced by instance type limits remains immutable. Operators who provision undersized instances discover this constraint when pod scheduling begins to fail with "insufficient IP address" errors despite abundant CPU and memory headroom.

The security implications of native VPC integration extend beyond simple reachability. Because every pod IP originates from a VPC subnet, security groups—the stateful firewall constructs that govern ingress and egress rules for EC2 resources—can be attached directly to pods rather than applied uniformly at the node level. This capability, delivered through the security groups for pods feature, enables microsegmentation policies that restrict database pods to accept connections only from application tier pods, enforce egress controls that prevent data exfiltration, and satisfy compliance mandates requiring network isolation between workload classifications. The implementation relies on branch ENIs, a specialized ENI type that the VPC CNI plugin provisions dynamically and associates with individual pods through eBPF programs that intercept traffic at the kernel network stack and enforce policy before packets traverse the wire.

Service discovery in Kubernetes operates through two parallel mechanisms: the virtual IP abstraction provided by kube-proxy and the DNS record publication managed by CoreDNS. When you create a Service resource, the Kubernetes control plane allocates a cluster-internal virtual IP from the service CIDR block and programs forwarding rules that distribute incoming connections across the backing pod endpoints. In EKS, kube-proxy runs in iptables mode by default, generating chains of iptables rules that perform destination network address translation and probabilistic load balancing through the statistic module's random distribution. A Service with three healthy endpoints produces iptables rules that select the first endpoint with one-third probability, the second with one-half of the remaining probability, and route all remaining traffic to the third. This stateless load balancing algorithm introduces no per-connection state overhead, but the linear rule chain structure degrades performance as service count grows, because every outbound packet must traverse the entire chain until a match occurs.

DNS resolution for Services follows the standard Kubernetes naming convention, where a Service named postgres in the default namespace becomes resolvable at postgres.default.svc.cluster.local. CoreDNS, the authoritative DNS server embedded in the EKS control plane, watches the Kubernetes API for Service and Endpoint changes, updates its internal cache, and responds to queries from pods with the Service's virtual IP. Pods inherit DNS configuration through the /etc/resolv.conf file that the kubelet injects at startup, which directs queries to the CoreDNS Service IP. This indirection enables service mobility—backend pods can be rescheduled, scaled, or replaced without requiring DNS updates—but introduces a critical dependency on CoreDNS availability and query latency.

The boundary between cluster networking and external connectivity introduces additional complexity layers. EKS clusters deployed in private subnets without direct internet access require NAT gateways or instance-based NAT to enable outbound connections for pod traffic destined to the public internet. The VPC CNI plugin programs default routes in the pod network namespace that direct all non-local traffic through the primary ENI's gateway, where VPC route tables determine next-hop forwarding. Return traffic follows the reverse path, with the VPC routing layer directing responses to the elastic network interface associated with the pod's IP address. Operators must ensure that route table associations, subnet CIDR allocations, and NAT gateway capacity align with pod networking requirements, or risk silent packet drops that manifest as intermittent connection timeouts without clear diagnostic signals.

IP address exhaustion represents the most common operational failure mode in production EKS clusters. When subnet CIDR blocks run dry, the VPC CNI plugin cannot allocate new secondary IPs, pod creation stalls indefinitely, and horizontal pod autoscaling fails silently. The warm pool configuration parameters WARM_ENI_TARGET, WARM_IP_TARGET, and MINIMUM_IP_TARGET control how aggressively the CNI plugin pre-allocates ENIs and secondary IPs before demand materializes. Conservative settings minimize wasted IP addresses but increase pod startup latency when bursts occur. Aggressive settings reduce latency by maintaining excess capacity but accelerate subnet exhaustion. Operators must balance these competing pressures through capacity modeling based on workload churn rates, burst patterns, and subnet size constraints.

Network policy enforcement in EKS requires deliberate activation because the default AWS VPC CNI plugin does not implement the NetworkPolicy API. Calico or Cilium can be installed alongside the VPC CNI plugin to provide policy enforcement through kernel-level filtering, but this introduces operational overhead and potential conflicts between policy engines. The network policies defined through Kubernetes resources specify ingress and egress rules using pod selectors, namespace selectors, and CIDR blocks, but the enforcement logic resides entirely within the chosen policy engine. A misconfigured policy can partition the cluster, prevent DNS resolution, or block kubelet-to-API server communication, requiring emergency intervention through node SSH access and manual iptables inspection.

The abstraction boundary between Kubernetes networking primitives and AWS networking constructs creates a semantic gap that operators must bridge through mental models and diagnostic tooling. When a pod cannot reach a Service, the failure could originate in iptables rule misconfiguration, CoreDNS cache staleness, security group denials, network ACL blocks, route table gaps, or subnet capacity exhaustion. Effective troubleshooting requires tracing the packet path through multiple layers: pod network namespace configuration, veth pair state, iptables chains, ENI attachment status, VPC flow logs, and security group evaluation order. This multi-layer diagnostic surface distinguishes EKS networking from simpler container orchestration platforms and demands deep understanding of both Kubernetes abstractions and AWS networking primitives.


## 2. Core Architecture & Mechanics

The AWS VPC CNI plugin operates as a privileged DaemonSet deployed to every worker node in the cluster, consisting of two primary components: the CNI binary invoked by the kubelet during pod lifecycle events and the ipamd (IP Address Management Daemon) that runs continuously as a long-lived process managing ENI and IP address pools. When the kubelet needs to configure networking for a new pod, it executes the CNI binary at /opt/cni/bin/aws-cni with a CNI_COMMAND=ADD directive. The binary does not directly allocate IP addresses or attach network interfaces. Instead, it communicates with the local ipamd over a Unix domain socket at /var/run/aws-node/ipamd.sock, requesting an IP address from the pre-warmed pool that ipamd maintains through continuous interaction with the EC2 API.

The ipamd process maintains an internal data structure tracking all elastic network interfaces attached to the host and the secondary IP addresses associated with each interface. On startup, ipamd queries the EC2 metadata service to enumerate existing ENIs and their IP allocations, then reconciles this state with the kubelet's pod inventory by querying the Kubernetes API. Any IPs assigned to pods that no longer exist are reclaimed into the available pool. The plugin then evaluates the warm pool configuration parameters to determine whether additional ENIs or IPs should be provisioned. If WARM_ENI_TARGET is set to 1, ipamd will attempt to maintain one entire ENI's worth of free IP addresses above current utilization. If WARM_IP_TARGET is set to 5, ipamd will ensure at least five individual IP addresses remain available regardless of ENI boundaries.

The ENI attachment workflow proceeds through multiple AWS API calls with non-trivial latency. First, ipamd invokes ec2:CreateNetworkInterface with the subnet ID matching the node's primary ENI placement. The API returns an ENI ID but the interface is not immediately usable. Next, ipamd calls ec2:AttachNetworkInterface with the instance ID and ENI ID, specifying a device index that determines the Linux network interface name. The attachment operation can take several seconds to complete, during which the ENI enters an "attaching" state. Once attached, ipamd must invoke ec2:ModifyNetworkInterfaceAttribute to disable source/destination checking, allowing the interface to forward traffic for IP addresses not assigned to the interface itself. Finally, ipamd allocates secondary private IP addresses by calling ec2:AssignPrivateIpAddresses, requesting as many IPs as the interface supports according to instance type limits.

When the CNI binary receives an IP address from ipamd, it configures the pod's network namespace through a sequence of netlink operations and iproute2 commands. The kubelet has already created the network namespace and passed its filesystem path to the CNI plugin. The plugin creates a virtual ethernet pair using the ip link add command, assigning one end to the pod's namespace and leaving the other in the host's root namespace. The host-side veth interface receives a name like eni1234567890abc and is moved into the UP state. The pod-side interface is renamed to eth0, moved into the pod's namespace, assigned the allocated IP address with a /32 prefix length, and brought up. The /32 prefix is critical: it signals that the pod's IP is a host address with no local subnet, forcing all traffic to traverse the default gateway.

The plugin then installs routing rules in both the pod and host namespaces. Inside the pod, a default route is added pointing to the gateway IP address 169.254.1.1, a link-local address that exists only for routing purposes and is not bound to any interface. A static ARP entry is installed mapping this gateway IP to the MAC address of the host-side veth interface, ensuring the pod can send traffic without ARP resolution. In the host namespace, ipamd has already configured policy routing rules that direct traffic from the pod's IP address to the appropriate ENI based on which interface owns the IP in its secondary address pool. This policy routing layer is essential because Linux's default routing behavior would send all traffic out the primary ENI, breaking connectivity for pods assigned to secondary ENIs.

```
# Pod network namespace configuration (simplified view)
# Interface: eth0@if42 (veth pair, pod side)
# IP: 10.0.1.50/32
# Route table:
default via 169.254.1.1 dev eth0
169.254.1.1 dev eth0 scope link

# Host network namespace configuration
# Interface: eni1a2b3c4d (veth pair, host side)
# Policy routing rule:
from 10.0.1.50 lookup 2

# Routing table 2:
default via 10.0.1.1 dev eth1 (secondary ENI gateway)
10.0.1.0/24 dev eth1 scope link
```

Service networking introduces the kube-proxy layer, which operates independently of the CNI plugin but must interoperate seamlessly with pod networking. EKS deploys kube-proxy as a DaemonSet in iptables mode, where it watches the Kubernetes API for Service and Endpoints changes and translates them into iptables rules in the nat table. When a Service named frontend is created with ClusterIP 172.20.0.10 and three backing pods at 10.0.1.50, 10.0.1.51, and 10.0.1.52, kube-proxy generates a KUBE-SERVICES chain entry that matches destination 172.20.0.10 and jumps to a service-specific chain KUBE-SVC-FRONTEND. This chain contains rules using the statistic module to distribute traffic probabilistically across three endpoint chains KUBE-SEP-1, KUBE-SEP-2, and KUBE-SEP-3, each performing DNAT to rewrite the destination address to one of the pod IPs.

The iptables rule structure grows multiplicatively with service and endpoint counts. A cluster with 1000 Services averaging 10 endpoints each generates over 10,000 iptables rules in the nat table. Every outbound packet from every pod must traverse the KUBE-SERVICES chain, comparing destination IPs against every Service ClusterIP until a match occurs. If the destination is not a Service IP, the packet traverses all rules before exiting the chain. This linear search degrades performance as rule counts grow, introducing latency that scales with O(n) where n is the number of Services. The iptables ruleset also requires full reconstruction on every endpoint change, causing transient disruptions during which new connections may fail or route to stale endpoints.

DNS resolution ties the Service abstraction to human-readable names through CoreDNS, which runs as a Deployment in the kube-system namespace and is exposed via a Service with ClusterIP typically in the 172.20.0.10 range. The kubelet injects a /etc/resolv.conf file into every pod container with a nameserver directive pointing to the CoreDNS Service IP and search domains enabling short-name resolution. When a pod process performs a DNS query for postgres, the system resolver library appends the search domains in order—default.svc.cluster.local, svc.cluster.local, cluster.local, and the VPC's DHCP options domain—and issues A record queries for each fully qualified name until a response is received.

CoreDNS processes these queries through a plugin chain defined in its Corefile configuration. The kubernetes plugin watches the Kubernetes API for Services and generates synthetic A records mapping service names to ClusterIPs. The forward plugin delegates queries for external domains to upstream resolvers, typically the VPC resolver at 169.254.169.253 plus any custom DNS servers configured in the cluster. The cache plugin stores responses in memory to reduce API load and query latency. A properly configured CoreDNS instance can handle thousands of queries per second, but the Deployment's replica count and resource limits must scale with cluster size. Undersized CoreDNS deployments manifest as intermittent DNS resolution failures, connection timeouts, and pods that fail liveness probes due to unresolved service names.

Security groups for pods extends the VPC security group model to individual pod granularity through a mechanism called trunk and branch ENIs. When you annotate a pod with vpc.amazonaws.com/security-groups specifying one or more security group IDs, the VPC CNI plugin provisions a branch ENI specifically for that pod and associates the specified security groups with the branch interface. Traffic to and from the pod flows through this dedicated ENI, where the VPC control plane enforces security group rules before packets reach the instance. The trunk ENI, a special interface type that can host multiple branch ENIs, is attached to the worker node during initialization. Each branch ENI consumes one of the instance's ENI slots, reducing the total number of standard ENIs available for IP address pooling.

The packet flow for a pod with custom security groups diverges from the standard path. Outbound traffic from the pod enters a veth interface as usual, but instead of being routed directly to a secondary ENI, it is intercepted by an eBPF program attached to the TC egress hook. This program performs a lookup in a BPF map keyed by pod IP address, retrieves the branch ENI's device index, and redirects the packet to the branch interface. Ingress traffic arrives at the branch ENI after passing through VPC security group evaluation, then is redirected by another eBPF program to the appropriate veth interface based on destination IP. This architecture enables per-pod security group enforcement without modifying the VPC routing layer, but introduces additional latency from the eBPF redirects and limits the number of pods with custom security groups to the instance's maximum branch ENI capacity.

Network policy enforcement through Calico operates at a lower layer than security groups, using iptables and ipset to filter traffic within the host kernel before it reaches the network interface. When you install Calico in policy-only mode alongside the AWS VPC CNI plugin, Calico does not replace the CNI plugin but instead runs as a DaemonSet that watches NetworkPolicy resources and translates them into iptables rules in the filter table. Each NetworkPolicy generates a chain of rules that match traffic based on source pod labels, destination pod labels, and protocol/port combinations. Calico uses ipset to efficiently represent large sets of pod IPs, avoiding the linear rule count explosion that would occur with individual iptables rules per pod.

A NetworkPolicy specifying that pods labeled role=frontend can connect to pods labeled role=backend on port 5432 produces iptables rules that match packets with destination port 5432, check if the source IP belongs to the frontend ipset, check if the destination IP belongs to the backend ipset, and accept the connection if all conditions are met. Packets that do not match any NetworkPolicy rule are subject to the default policy, which is either allow-all or deny-all depending on whether any NetworkPolicy selects the destination pod. This default policy behavior is a frequent source of cluster breakage: creating a NetworkPolicy that selects pods without explicitly allowing DNS traffic will block CoreDNS queries, causing all service discovery to fail.

The interaction between kube-proxy iptables rules and Calico NetworkPolicy rules requires careful ordering in the netfilter packet processing pipeline. Traffic destined for a Service ClusterIP enters the PREROUTING chain in the nat table, where KUBE-SERVICES performs DNAT to rewrite the destination to a pod IP. The packet then traverses the filter table's FORWARD chain, where Calico rules evaluate whether the connection is permitted based on the pod IP, not the original Service IP. NetworkPolicy rules must be written to allow traffic between pod IPs, not Service IPs, because the DNAT occurs before policy evaluation. This semantic gap confuses operators who expect policies to reference Services directly.

Pod-to-pod communication within the same node follows a short-circuit path that does not traverse ENIs or VPC routing. When a pod at 10.0.1.50 sends a packet to another pod at 10.0.1.51 on the same instance, the packet enters the veth pair, arrives in the host namespace, and is immediately forwarded to the destination veth based on the host routing table. This local forwarding path uses the kernel's bridge or routing logic depending on CNI configuration, but in the AWS VPC CNI plugin's default setup, each veth pair is independent and traffic is routed through the host's route table. The packet never touches a physical ENI, does not consume ENI bandwidth, and avoids VPC routing latency. However, security groups for pods still apply because the eBPF redirect logic operates regardless of whether traffic exits the instance.

Pod-to-pod communication across nodes traverses the full VPC routing layer. A packet from 10.0.1.50 on instance A to 10.0.1.51 on instance B is routed out instance A's ENI based on policy routing rules, traverses the VPC fabric, and arrives at instance B's ENI where reverse policy routing directs it to the correct veth interface. The VPC flow logs capture this traffic with the ENI ID of both source and destination interfaces, enabling network forensics and compliance auditing. The latency of this path includes ENI queueing delay, VPC fabric forwarding, and destination instance processing, typically adding several hundred microseconds compared to same-node communication.

```
Packet flow for pod-to-Service communication across nodes:

1. Source pod (10.0.1.50) sends packet to Service ClusterIP (172.20.0.10)
   - Packet exits pod netns via veth pair

2. Host netns PREROUTING/nat table (source node)
   - KUBE-SERVICES chain matches dst 172.20.0.10
   - KUBE-SVC-XYZ chain selects endpoint via statistic module
   - DNAT rewrites dst to pod IP 10.0.2.75

3. Host netns FORWARD/filter table (source node)
   - Calico NetworkPolicy rules evaluate (if installed)
   - Packet accepted if policy allows

4. Host netns POSTROUTING (source node)
   - Policy routing selects ENI based on src IP 10.0.1.50
   - Packet egresses via eth1 (secondary ENI)

5. VPC fabric
   - Routing table directs packet to destination instance ENI
   - Security groups evaluate (if enabled for destination pod)

6. Destination node ENI receives packet
   - Policy routing directs to veth based on dst IP 10.0.2.75

7. Destination pod netns
   - Packet arrives on eth0
   - Application receives connection
```


## 3. High-Performance Optimization & Failure Modes

Subnet capacity planning dominates the operational lifecycle of production EKS clusters, yet most organizations approach this design phase with insufficient rigor, discovering address exhaustion only when pod creation begins to fail during peak traffic events. The fundamental constraint originates from the VPC CNI plugin's requirement that every pod IP must originate from a VPC subnet secondary IP address pool. A /24 subnet provides 256 total addresses, but AWS reserves the first four addresses and the last address in every subnet for network infrastructure, leaving 251 usable IPs. If you deploy twenty m5.xlarge instances with fifteen pods each into this subnet, you require 300 pod IPs plus twenty instance primary IPs, totaling 320 addresses and exceeding capacity by 69 addresses.

The address arithmetic grows more complex when accounting for warm pool overhead. If ipamd is configured with WARM_IP_TARGET=5 on each node, the plugin will pre-allocate five additional IPs per node beyond current pod demand, reserving 100 addresses across twenty nodes for burst capacity. This reservation is invisible to Kubernetes scheduling decisions: the scheduler sees available CPU and memory and places pods accordingly, but the CNI plugin cannot allocate IPs and pod creation stalls. The failure mode presents as pods stuck in ContainerCreating state with events reporting "failed to allocate IP address" or "timed out waiting for pod sandbox". The kubectl describe output shows normal scheduling but no network interface creation, and the aws-node DaemonSet logs contain repeated "insufficient IPs available" warnings.

Correcting subnet exhaustion in a running cluster requires expanding the subnet CIDR range or redistributing pods across additional subnets, neither of which can be performed without disruption. VPC subnet CIDR blocks cannot be modified after creation; you must create a new subnet with a larger block, update the EKS cluster's subnet configuration to include the new subnet, and either taint existing nodes to drain workloads or manually cordon and terminate instances to force pod rescheduling onto nodes launched in the new subnet. This migration introduces cascading complexity: Services with LoadBalancer type must be recreated to update their subnet associations, StatefulSets must be carefully drained to preserve volume attachments, and DNS propagation delays can cause transient connection failures during the transition.

Prefix delegation mode provides an alternative IP allocation strategy that dramatically increases pod density by assigning entire /28 prefix blocks to ENIs rather than individual IP addresses. When you enable prefix delegation by setting ENABLE_PREFIX_DELEGATION=true in the aws-node DaemonSet, ipamd requests prefix allocations from the ec2:AssignPrivateIpAddresses API instead of individual IPs. A /28 prefix contains sixteen addresses, of which fifteen are usable for pods after reserving one for routing purposes. An m5.xlarge instance with four ENIs can support up to four prefixes, yielding sixty usable pod IPs compared to the fourteen IPs available with individual secondary IP allocation. This fivefold capacity increase alleviates subnet pressure but introduces a new tradeoff: prefix blocks are allocated in contiguous chunks, so a node with only three active pods may have an entire fifteen-IP prefix reserved, wasting twelve addresses.

The warm pool configuration parameters interact with prefix delegation in non-obvious ways. WARM_PREFIX_TARGET controls how many unused prefix blocks ipamd maintains, with each prefix representing sixteen addresses. Setting WARM_PREFIX_TARGET=1 reserves sixteen IPs per node regardless of pod count, compared to the five IPs reserved by WARM_IP_TARGET=5 in non-prefix mode. This parameter choice must align with workload autoscaling velocity: applications that scale from ten to one hundred pods within seconds benefit from aggressive warm prefix allocation, while stable workloads waste addresses with excess reservation. The MINIMUM_IP_TARGET parameter sets a floor on total IP availability, overriding warm pool targets when current allocation falls below the threshold.

Security groups for pods introduces a distinct ENI consumption pattern that conflicts with IP address capacity optimization. Each pod with custom security groups requires a dedicated branch ENI, and instance type limits constrain the total ENI count including both standard and branch ENIs. An m5.xlarge instance supports four ENIs total; if you attach two standard ENIs for IP pooling (providing thirty pod IPs with prefix delegation disabled), you can support only two pods with custom security groups before reaching the ENI limit. Exceeding this limit causes pod creation to fail with "maximum ENI capacity reached" errors, even if ample IP addresses remain available in existing ENIs.

The operational pattern for security groups for pods requires reserving ENI capacity explicitly. If your workload requires ten percent of pods to have custom security groups, you must reduce the WARM_ENI_TARGET or manually limit ENI attachment to leave sufficient slots for branch ENIs. The VPC CNI plugin does not automatically balance this allocation; it will happily attach standard ENIs until the limit is reached, then fail to provision branch ENIs for pods requesting custom security groups. Monitoring ENI utilization across the fleet requires correlating CloudWatch metrics for NetworkInterfacesInUse with per-instance type limits, then establishing alerts before the buffer is exhausted.

DNS resolution latency compounds with cluster scale because every pod query for a Service name requires a round-trip to CoreDNS, and CoreDNS must query the Kubernetes API to maintain its record cache. A cluster with 1000 pods each querying DNS ten times per second generates 10,000 queries per second to CoreDNS. If CoreDNS is deployed with two replicas, each replica handles 5000 qps. The default CoreDNS resource requests of 100m CPU and 128Mi memory will saturate under this load, causing query timeouts, cache evictions, and cascading failures as applications retry failed DNS lookups. The symptom manifests as intermittent connection failures with "temporary failure in name resolution" errors or timeouts after five seconds, the default resolver timeout.

Scaling CoreDNS horizontally and vertically addresses the immediate capacity constraint but does not eliminate the architectural bottleneck. The Kubernetes DNS specification requires that all pod DNS queries traverse CoreDNS for both cluster-local and external names, even though external queries are simply forwarded to the VPC resolver after cache misses. A pod querying api.github.com must first query CoreDNS, which checks its cache, finds no entry, forwards the query to 169.254.169.253, waits for the response, caches the result, and returns it to the pod. This double-hop path adds latency and centralizes load on CoreDNS infrastructure. The ndots:5 resolver configuration injected by the kubelet exacerbates this problem by causing the resolver to append search domains to queries before attempting the name as-written, generating five sequential DNS queries for a fully qualified external name before finally resolving correctly on the sixth attempt.

NodeLocal DNSCache deploys a DaemonSet that runs a caching DNS proxy on every node at a link-local IP address, typically 169.254.20.10. The kubelet is configured to inject this address as the primary nameserver in /etc/resolv.conf, directing all pod DNS queries to the local node cache before they traverse the network to CoreDNS. Cache hits are served directly from memory with sub-millisecond latency and zero network overhead. Cache misses are forwarded to the upstream CoreDNS Service over the regular cluster network, but the distribution of misses across all node caches reduces per-replica CoreDNS load proportionally to node count. A 100-node cluster with NodeLocal DNSCache reduces CoreDNS traffic by more than ninety percent for workloads with stable service discovery patterns.

Deploying NodeLocal DNSCache requires modifying the DaemonSet's configuration to handle the idiosyncrasies of EKS networking. The cache must listen on the link-local IP 169.254.20.10 without conflicting with the existing 169.254.1.1 gateway address used by the VPC CNI plugin. The iptables rules must redirect DNS traffic destined for the CoreDNS Service IP to the local cache, but must not intercept queries originating from the cache itself to prevent infinite loops. The configuration must specify the correct upstream CoreDNS Service IP and enable TCP fallback for queries that exceed UDP packet size limits. Misconfiguring any of these parameters results in total DNS failure cluster-wide, requiring emergency rollback and potential node restarts to clear corrupted iptables state.

Iptables rule count optimization becomes critical in clusters with hundreds of Services. The default kube-proxy iptables mode generates over twenty rules per Service endpoint, and the linear chain structure forces every packet to traverse the entire ruleset. Switching kube-proxy to IPVS mode replaces iptables chains with kernel IPVS load balancing, which uses hash tables for O(1) Service lookup regardless of scale. IPVS also provides multiple load balancing algorithms including round-robin, least connection, and source hashing, compared to the stateless random distribution of iptables mode.

Enabling IPVS mode requires installing the ipvsadm package on worker nodes and setting the kube-proxy mode flag to ipvs in the ConfigMap. EKS worker nodes based on Amazon Linux 2 include the necessary kernel modules but not the userspace utilities, so the node AMI must be customized or a bootstrap script must install ipvsadm during node initialization. IPVS uses a dummy interface called kube-ipvs0 to host Service ClusterIPs as local addresses, allowing the kernel to accept traffic for these IPs without generating ICMP unreachable responses. This architectural difference means that ClusterIPs become pingable when using IPVS, changing the network behavior in subtle ways that can confuse diagnostic workflows expecting ClusterIPs to be non-routable.

Network policy enforcement with Calico introduces non-trivial performance overhead from iptables rule evaluation in the filter table FORWARD chain. Every inter-pod packet must traverse the Calico policy chains before forwarding, adding latency that scales with policy complexity. A policy selecting all pods in a namespace with 500 pods generates ipset entries for 500 IPs, and the kernel must perform hash lookups in these sets for every packet. Benchmarks demonstrate that Calico policy enforcement reduces pod-to-pod throughput by five to fifteen percent depending on rule count and packet size, with higher overhead for small packets that spend proportionally more time in kernel rule processing.

Cilium provides an alternative policy enforcement engine based on eBPF rather than iptables, reducing overhead by enforcing policy in the kernel's TC (traffic control) layer before packets enter the netfilter stack. Cilium's eBPF programs perform policy lookups using BPF maps optimized for high-speed packet processing, achieving near-line-rate performance even with complex policies. However, deploying Cilium in EKS requires replacing the default AWS VPC CNI plugin with Cilium's CNI implementation, or running Cilium in policy-only mode with eBPF host routing disabled. The operational complexity of managing Cilium's custom resource definitions, agent configurations, and eBPF program lifecycle exceeds Calico's iptables-based approach, making it appropriate only for clusters with demanding performance requirements or advanced network observability needs.

VPC flow logs provide comprehensive network traffic telemetry by capturing metadata for every ENI-to-ENI flow, including source and destination IPs, ports, protocol, byte count, packet count, and accept/reject status. Enabling flow logs at the VPC level generates log records for all cluster traffic, but the volume scales rapidly with pod density: a 100-node cluster with 1000 pods generating 100 connections each produces 100,000 flow log records per minute. These records are delivered to CloudWatch Logs or S3 with several minutes of latency, making flow logs unsuitable for real-time troubleshooting but invaluable for post-incident forensics and compliance auditing.

Analyzing flow logs for cluster traffic requires understanding how the VPC CNI plugin's IP allocation maps to pod identities. Flow log records contain only ENI IDs and IP addresses, not pod names or namespaces. Correlating a flow log entry showing traffic from 10.0.1.50 to 10.0.2.75 back to specific pods requires querying the Kubernetes API to determine which pod was assigned each IP at the flow timestamp. The aws-node DaemonSet maintains this mapping in memory but does not expose it via API. Custom tooling must poll the Kubernetes API periodically, extract pod IPs from status fields, and build a time-series database correlating IPs to pod identities before flow log analysis becomes practical.

Egress traffic optimization for pods accessing external services requires careful VPC routing configuration to avoid sending traffic through NAT gateways unnecessarily. The VPC CNI plugin installs a default route in each pod's network namespace that directs all non-cluster traffic through the ENI gateway, where VPC route tables determine next-hop forwarding. If the subnet's route table sends all internet-bound traffic through a NAT gateway, every outbound connection from every pod incurs NAT gateway data processing charges and traversal latency. For clusters that make heavy use of AWS service endpoints in the same region, enabling VPC endpoints for S3, DynamoDB, and other services allows traffic to bypass NAT gateways entirely, reducing costs and improving performance.

Cross-availability-zone traffic introduces both latency and data transfer costs that accumulate invisibly until the monthly bill arrives. The Kubernetes scheduler makes pod placement decisions based on resource availability and affinity rules without considering network topology or data transfer pricing. A Service with pods distributed across three availability zones will route client connections to any available pod, causing one-third of traffic to incur inter-AZ transfer charges. The topology-aware routing feature mitigates this by annotating Services with service.kubernetes.io/topology-aware-hints, instructing kube-proxy to prefer endpoints in the same zone as the client pod when possible.

Implementing topology-aware routing requires the topology manager to be enabled on worker nodes and zones to be labeled correctly. EKS automatically applies the topology.kubernetes.io/zone label to nodes based on their EC2 instance placement, and the EndpointSlice controller propagates zone information to endpoint records. Kube-proxy in IPVS or iptables mode reads these hints and weights endpoint selection to favor same-zone targets. However, this optimization degrades gracefully rather than failing hard: if no same-zone endpoints are available, kube-proxy will route to endpoints in other zones, ensuring availability at the cost of increased latency and transfer charges.

MTU (maximum transmission unit) mismatches between pod network interfaces and VPC network paths cause silent packet fragmentation or drops that manifest as degraded throughput and intermittent connection timeouts. The standard Ethernet MTU of 1500 bytes works for most cluster traffic, but jumbo frames with MTU 9001 are supported within VPC networks and can improve throughput for large data transfers. The VPC CNI plugin sets the MTU on pod veth interfaces to match the primary ENI's MTU, which defaults to 9001 on most instance types. If traffic must traverse an internet gateway, VPN connection, or VPC peering link with a lower MTU, packets exceeding the path MTU are fragmented or dropped depending on the DF (Don't Fragment) flag.

Path MTU discovery relies on ICMP Fragmentation Needed messages being propagated back to senders when packets exceed the path MTU, but many networks block ICMP traffic, breaking PMTU discovery and causing connections to hang when attempting to send large packets. The symptom appears as SSH sessions that accept authentication but hang after login, HTTP connections that transfer headers but stall when sending response bodies, or database queries that return small result sets successfully but timeout when fetching large blobs. Diagnosing MTU issues requires tcpdump packet captures showing retransmitted packets with DF flags or ICMP unreachable messages, then manually adjusting MTU settings on pod interfaces or intermediate network devices.

Connection tracking exhaustion in the Linux kernel's netfilter conntrack subsystem represents a capacity limit that appears only under extreme load. Every TCP connection and UDP flow tracked by the kernel consumes an entry in the conntrack table, and the table size is fixed at boot time based on available memory. The default limits accommodate typical workloads, but clusters with hundreds of pods each maintaining thousands of persistent connections can exhaust the table, causing new connections to fail with "nf_conntrack: table full" kernel messages. The failure manifests as sporadic connection refusals or timeouts without clear attribution to any specific component.

Increasing the conntrack table size requires setting the net.netfilter.nf_conntrack_max sysctl parameter at node boot time, along with corresponding adjustments to net.netfilter.nf_conntrack_buckets to maintain hash table performance. EKS worker nodes can be configured with custom bootstrap arguments that set these sysctls via /etc/sysctl.conf before the kubelet starts. However, increasing conntrack capacity consumes additional kernel memory proportional to the table size, potentially reducing memory available for pods. Monitoring conntrack utilization through the /proc/sys/net/netfilter/nf_conntrack_count file and establishing alerts at eighty percent capacity prevents exhaustion before it causes production impact.

The interaction between horizontal pod autoscaling and IP address availability introduces a cascading failure mode where scaling events trigger IP exhaustion, which prevents new pods from starting, which causes continued load pressure, which triggers additional scaling events, creating a feedback loop that can only be resolved by manual intervention. The HPA (Horizontal Pod Autoscaler) queries metrics from the Metrics Server, compares them to target thresholds, and calculates desired replica counts, but it has no visibility into CNI IP address availability. When the HPA requests scaling from fifty to one hundred replicas and only thirty IPs remain available, fifty pods are created but only thirty become running, leaving twenty stuck in ContainerCreating state indefinitely while the HPA continues to observe elevated load and requests additional replicas.

Breaking this failure loop requires either emergency subnet capacity expansion or temporary HPA suspension to allow IP address reclamation from terminated pods. The VPC CNI plugin's IP address garbage collection logic runs on a configurable interval (default thirty seconds) and reclaims IPs from pods that have been deleted for more than sixty seconds. During this window, deleted pod IPs remain reserved and cannot be allocated to new pods. Reducing the garbage collection interval and grace period accelerates IP reclamation but increases the risk of race conditions where an IP is reclaimed while the pod is still shutting down, potentially causing transient connectivity issues during scale-down events.

Observability tooling for cluster networking requires instrumenting multiple layers: pod-level metrics from application instrumentation, node-level metrics from the kubelet and CNI plugin, VPC-level metrics from CloudWatch, and control-plane metrics from EKS API server and CoreDNS. The aws-node DaemonSet exposes Prometheus metrics on port 61678 including IP addresses allocated, ENI count, IPAMD errors, and reconciliation timing. Scraping these metrics into a centralized Prometheus instance enables dashboards showing IP utilization trends, ENI allocation rates, and pod creation latency correlated with CNI plugin behavior.

The VPC CNI plugin's log verbosity can be increased by setting AWS_VPC_K8S_CNI_LOG_LEVEL=DEBUG in the DaemonSet environment, causing detailed logs for every ENI operation, IP allocation, and route installation. These logs are essential for diagnosing intermittent failures where pod creation succeeds on some nodes but fails on others, indicating instance-specific ENI attachment failures or subnet capacity variations. However, debug-level logging generates substantial data volume that can overwhelm CloudWatch Logs and incur unexpected costs, so it should be enabled only during active troubleshooting and disabled once issues are resolved.

Service mesh implementations like Istio or AWS App Mesh introduce additional networking layers that interact with the VPC CNI plugin and kube-proxy in complex ways. Istio deploys an Envoy sidecar into every pod, intercepting all inbound and outbound traffic through iptables REDIRECT rules that route packets through the localhost proxy. These rules operate in the pod's network namespace, after packets have already traversed the veth pair and before they exit to the host namespace, adding multiple user-space context switches and proxy hops to every connection. The latency overhead ranges from single-digit milliseconds for local connections to tens of milliseconds for cross-zone traffic, with higher overhead for small requests that spend proportionally more time in proxy processing.

The interaction between Istio's iptables rules and Calico NetworkPolicy rules requires careful coordination to avoid rule conflicts. Both systems install rules in the pod network namespace and host namespace, and the order of rule evaluation determines whether traffic is permitted or denied. Istio's initialization containers run before Calico's policy enforcement containers, allowing Istio to install its rules first, but changes to NetworkPolicy resources can cause Calico to flush and rebuild rules, potentially overwriting or conflicting with Istio's configuration. Testing policy changes in non-production environments before applying them to production clusters is essential to avoid service disruptions from unexpected rule interactions.

The principle of least privilege applied to EKS networking requires minimizing security group rules, network policy scope, and IAM permissions for the VPC CNI plugin. The aws-node DaemonSet runs with an IAM role that requires ec2:CreateNetworkInterface, ec2:AttachNetworkInterface, ec2:ModifyNetworkInterfaceAttribute, ec2:AssignPrivateIpAddresses, and ec2:DescribeInstances permissions at minimum. Granting these permissions at VPC scope rather than account scope reduces blast radius if the role is compromised. Network policies should default to deny-all and explicitly allow only required connections, forcing operators to document and justify every open network path. Security groups should reference other security groups by ID rather than CIDR blocks when possible, enabling automatic updates when infrastructure changes rather than requiring manual rule modifications.
