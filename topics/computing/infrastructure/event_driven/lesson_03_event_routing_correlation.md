# Lesson 3: Event Routing, Choreography, Orchestration, and Process Correlation

## 1. First-Principles Intuition & Invariants

Event-driven architectures confront a fundamental dilemma that emerges naturally from distributed system design: how do we coordinate multi-step business processes across autonomous services without reintroducing the tight coupling and single points of failure that motivated our migration from monolithic systems in the first place? When a user places an order in an e-commerce platform, that single logical action triggers a cascade of state transitions across inventory reservation, payment processing, warehouse fulfillment, and shipping notification services. Each service operates independently, maintains its own database, and exposes its state changes as domain events. Yet somehow these isolated components must collectively implement complex, stateful workflows that span organizational boundaries and exhibit ACID-like consistency properties despite operating over unreliable networks with arbitrary delays.

The tension between autonomy and coordination surfaces immediately when we attempt to implement even trivial cross-service workflows. Consider a hotel reservation saga that must atomically reserve a room, charge a credit card, and send a confirmation email. In a synchronous, tightly-coupled system, we would wrap these operations in a distributed transaction coordinated by a two-phase commit protocol, sacrificing availability for consistency. In an event-driven architecture, we reject distributed locks and embrace eventual consistency, but we inherit a new problem: how do we track the progress of a multi-step process when each step is triggered by an event that arrives asynchronously, potentially out of order, and may be delivered multiple times due to at-least-once semantics?

This coordination challenge bifurcates into two foundational patterns that represent opposing points on the centralization spectrum: choreography and orchestration. Choreography distributes coordination logic across participating services, where each service listens for specific events, performs its local work, and emits new events that trigger downstream participants. No service has complete visibility into the end-to-end process; instead, the workflow emerges from the collective behavior of autonomous actors responding to domain events according to locally-encoded business rules. Orchestration centralizes coordination within a single orchestrator service or workflow engine that explicitly models the process as a state machine, issues commands to participants, and tracks progress through explicit state transitions. The orchestrator maintains complete visibility into the workflow, can implement complex compensation logic, and serves as the authoritative source of truth for process status.

The choice between these patterns is not merely aesthetic or organizational—it fundamentally shapes the runtime characteristics, failure modes, and operational complexity of distributed systems. Choreography yields systems with no single point of failure, where services remain loosely coupled and can evolve independently, but at the cost of emergent complexity, difficult debugging, and circular dependency risks. Orchestration provides centralized observability, explicit process modeling, and straightforward error handling, but introduces a coordination service that must be highly available and can become a scaling bottleneck. Real-world infrastructure typically employs both patterns strategically: choreography for loosely-coupled inter-domain interactions where services should remain ignorant of each other's existence, and orchestration for tightly-coupled intra-domain workflows where centralized control simplifies reasoning about complex branching logic and compensation requirements.

Regardless of the coordination pattern, all distributed processes require a mechanism to correlate causally-related events across space and time. When a payment processing service emits a PaymentAuthorized event five seconds after receiving a ProcessPayment command, infrastructure must somehow recognize that these messages belong to the same logical workflow instance despite being physically distinct data structures transmitted through separate network sockets. This correlation problem manifests at multiple layers of the system: message brokers must route events to the correct consumer instances, orchestrators must update the appropriate state machine instance, and observability tools must reconstruct end-to-end traces across service boundaries. The solution universally adopted across event-driven architectures is the correlation identifier—a unique token embedded in every message that participates in a workflow, propagated transitively as events trigger commands and commands yield new events, creating an immutable trace of causality through the distributed system.

The correlation identifier serves as a logical thread stitching together physically independent operations into a coherent causal chain. In practice, systems employ multiple layers of correlation: a workflow instance ID that uniquely identifies a specific execution of a business process, a causation ID that points to the immediate event that triggered the current operation, and a distributed trace ID that spans all operations related to a single external request. These identifiers form a hierarchical addressing scheme that enables sophisticated routing topologies, supports advanced debugging scenarios, and provides the foundation for distributed transaction coordination without requiring distributed locks.

At the heart of event routing lies a deceptively simple invariant: messages must be delivered to exactly the consumers that need them, neither more nor fewer, with latency and throughput characteristics that match workload requirements. This seemingly straightforward requirement explodes into a rich taxonomy of routing strategies when we account for the diverse communication patterns that emerge in real infrastructure. Point-to-point routing delivers each message to exactly one consumer, implementing work queue semantics where multiple workers compete to process a backlog of tasks. Publish-subscribe routing multicasts each message to all interested subscribers, enabling reactive systems where independent services respond to the same domain event without coordinating through a central dispatcher. Content-based routing inspects message payloads and applies predicate logic to dynamically determine recipients, allowing declarative routing rules that decouple publishers from topology knowledge. Topic-based routing organizes messages into hierarchical namespaces where consumers subscribe to patterns, providing a middle ground between the flexibility of content routing and the performance of static addressing.

These routing strategies differ fundamentally in their semantics, performance characteristics, and consistency guarantees. Point-to-point queues naturally load-balance work across consumer instances and provide strong ordering guarantees when constrained to a single partition, but they prevent horizontal scaling of pure read operations and complicate broadcast scenarios. Publish-subscribe topics enable fan-out at the broker level, eliminating the need for publishers to maintain recipient lists, but they require careful attention to consumer group semantics to prevent duplicate processing when auto-scaling adds replicas. Content-based routing maximizes decoupling by allowing routing decisions to evolve independently of publisher code, but it imposes computational overhead at the broker and complicates reasoning about message flow through the system. Hybrid topologies that combine these primitives—such as publishing domain events to topics while routing commands through queues—leverage the strengths of each pattern while mitigating their weaknesses.

The infrastructure substrate that implements these routing semantics operates through a combination of broker-side indexing, network-level load balancing, and client-side assignment protocols. Modern message brokers like Apache Kafka organize topics into ordered, immutable logs partitioned across broker nodes, where each partition is an append-only sequence of records identified by monotonically increasing offsets. Consumer groups coordinate through a cluster membership protocol to distribute partition assignments, ensuring that each partition is consumed by exactly one group member while allowing multiple groups to independently consume the same topic. This architecture achieves horizontal scalability by partitioning both write and read workloads, maintains ordering within each partition, and provides fault tolerance through replication at the partition level.

AMQP-based brokers like RabbitMQ employ a different topology centered on exchanges, queues, and bindings. Publishers send messages to exchanges—logical routing endpoints that implement specific forwarding algorithms—which evaluate binding rules to determine which queues should receive copies of each message. Consumers attach to queues and receive messages through push or pull mechanisms. This model provides more flexible routing than Kafka's partition-based approach, supporting sophisticated patterns like topic matching with wildcards and header-based routing, but it sacrifices some throughput and ordering guarantees to achieve that flexibility. Queue-based systems naturally implement competing consumer semantics where multiple workers drain a shared backlog, whereas log-based systems require explicit consumer group coordination to prevent redundant processing.

The choice of routing substrate profoundly impacts the feasibility of different coordination patterns. Choreography thrives on publish-subscribe semantics where domain events naturally fan out to all interested services without requiring publishers to know subscriber identities. Orchestration typically employs command queues where the orchestrator explicitly addresses commands to specific service instances and expects correlated responses. Hybrid approaches might use topic-based event distribution for inter-service notifications while maintaining dedicated command queues for orchestrator-driven workflows, recognizing that different message semantics demand different delivery guarantees and routing behaviors.

## 2. Core Architecture & Mechanics

Event routing infrastructure operates through a carefully orchestrated interplay of client libraries, broker processes, and network protocols that collectively implement message delivery guarantees while maintaining performance under load. Understanding the mechanical details of how messages flow from producer to consumer reveals both the capabilities and constraints that shape coordination pattern design.

At the publisher boundary, client libraries serialize application-level events into wire format—typically JSON, Avro, or Protobuf—and inject metadata including correlation identifiers, causation IDs, message type discriminators, and timestamp information. The serialization layer must balance human readability against compactness and schema evolution flexibility. JSON provides universal tooling support and debugging transparency but wastes bandwidth on repetitive field names and lacks native schema validation. Avro encodes a compact binary format guided by a separate schema document, enabling efficient serialization and robust backward compatibility through schema evolution rules, but it requires schema registry infrastructure and complicates ad-hoc message inspection. Protobuf occupies a middle ground with moderately compact encoding, code generation in multiple languages, and schema-driven compatibility checks, though it shares Avro's opacity without specialized tooling.

Publishers batch messages at the client level to amortize network round-trip costs, trading latency for throughput. A producer accumulating order events might buffer up to 100 messages or 1MB of data—whichever limit is reached first—before transmitting a batch to the broker. This batching occurs transparently within the client library, invisible to application code except through configuration parameters that control batch size, linger time, and compression settings. Compression algorithms like LZ4 or Snappy reduce network bandwidth and broker storage requirements, particularly for JSON payloads with repetitive structure, though they impose CPU overhead at both ends of the transmission.

Once a batch reaches the broker, the routing algorithm consults metadata to determine message placement. In Kafka, the partition key—either explicitly specified by the publisher or derived from the message payload—passes through a hash function that maps it to a specific partition within the target topic. Messages with the same partition key always land on the same partition, guaranteeing ordering for related events such as all state transitions for a particular customer account. The broker appends messages to the selected partition's log, assigns monotonically increasing offsets, and replicates the data to follower replicas according to the topic's replication factor. Only after in-sync replicas acknowledge the write does the broker confirm receipt to the publisher, implementing a quorum-based durability guarantee that tolerates minority replica failures.

RabbitMQ's exchange mechanism implements a more dynamic routing model where binding rules evaluated at message arrival time determine queue placement. A topic exchange interprets each message's routing key as a dot-separated namespace and matches it against wildcard patterns in bindings. An event published with routing key `order.payment.authorized` would match bindings for `order.payment.*`, `order.#`, and `#`, but not `order.payment.authorized.visa` or `inventory.*`. This pattern-matching flexibility enables declarative routing where new consumers subscribe to existing event streams by creating bindings without requiring publisher changes, though it incurs computational overhead that limits throughput compared to Kafka's static partition assignment.

Consumer groups coordinate through a cluster membership protocol that distributes work while preventing duplicate processing. In Kafka, the group coordinator—a broker elected through Raft consensus for each consumer group—manages member registration and partition assignment. When a consumer joins the group, it sends a JoinGroup request to the coordinator, which initiates a rebalance that redistributes partitions across current members. The coordinator selects one member as the group leader, which computes a new partition assignment using a pluggable assignment strategy and reports it back to the coordinator. The coordinator then broadcasts assignments to all members, which begin fetching from their assigned partitions. This protocol ensures that each partition is consumed by exactly one group member, preventing duplicate processing, while allowing multiple consumer groups to independently process the same topic for different use cases.

RabbitMQ implements competing consumer semantics more directly: multiple consumers attach to the same queue, and the broker round-robins messages across them. If a consumer crashes mid-processing, the broker redelivers unacknowledged messages to remaining consumers. This model provides simpler failure recovery than Kafka's rebalance protocol but requires explicit consumer acknowledgments to ensure at-least-once delivery. A consumer that pulls a message from the queue but fails before acknowledgment will cause the message to be redelivered, necessitating idempotent processing logic in the consumer to handle duplicates gracefully.

The acknowledgment protocol sits at the heart of delivery guarantee semantics. At-most-once delivery allows message loss in exchange for maximum throughput: producers fire messages without waiting for broker confirmation, and consumers acknowledge receipt before processing begins. At-least-once delivery guarantees no loss through producer retries and deferred consumer acknowledgments, accepting duplicate deliveries when network timeouts cause retry ambiguity. Exactly-once delivery—more precisely, exactly-once semantics—requires end-to-end coordination between producer, broker, and consumer through idempotence keys, transactional writes, and fencing mechanisms that prevent zombie producers from corrupting state.

Kafka's exactly-once implementation leverages producer IDs and sequence numbers to detect and discard duplicate writes, combined with transactional markers that atomically commit groups of messages across multiple partitions. A producer initializing an idempotent session receives a producer ID from the broker and attaches monotonically increasing sequence numbers to each message. The broker tracks the last sequence number received from each producer and rejects messages with non-consecutive sequences, preventing duplicates from retry storms. Transactions extend this mechanism across partitions: the producer writes messages to a transaction log partition, then commits the transaction by writing a commit marker, which atomically makes all transactional messages visible to consumers. This protocol provides exactly-once semantics within Kafka's boundaries but cannot extend to external systems without additional coordination.

Process correlation infrastructure layers on top of basic message routing to track multi-step workflows across service boundaries. Every message participating in a workflow carries a workflow instance ID—a UUID or ULID generated when the process initiates—that uniquely identifies this specific execution. A hotel reservation saga spawned by an HTTP POST request generates a fresh workflow ID that propagates through every subsequent event and command: ReserveRoom, ChargePayment, SendConfirmation, RoomReserved, PaymentCharged, ConfirmationSent. By indexing messages on workflow ID, infrastructure can reconstruct the complete causal history of a process instance, support queries like "what's the status of reservation XYZ?", and implement timeouts that trigger compensation logic when expected events fail to arrive.

Causation IDs extend correlation to capture immediate cause-and-effect relationships. When a PaymentProcessor service receives a ChargePayment command with workflow ID W and message ID C1, it processes the payment and emits a PaymentCharged event with the same workflow ID but a fresh message ID E1 and causation ID C1, explicitly linking the event back to the command that triggered it. This parent-child relationship enables sophisticated debugging workflows where engineers trace backward from a failure event through the chain of causation to identify the root cause, or forward from a command to discover all downstream effects.

Distributed tracing systems like OpenTelemetry formalize correlation through trace and span identifiers propagated in message headers. A trace represents an entire end-to-end request flow from external client to final response, spanning potentially hundreds of microservices. Each service operation creates a span—a timed segment representing local work—that nests within the trace. As messages flow through the system, instrumentation libraries extract trace context from inbound message headers, create child spans for local processing, and inject trace context into outbound messages. This yields a directed acyclic graph of spans that infrastructure can visualize as a waterfall diagram showing which operations executed in parallel, where latency concentrations occurred, and how errors propagated through the call chain.

Choreography-based coordination emerges from services responding autonomously to domain events without centralized control. When an OrderPlaced event arrives on the order-events topic, the inventory service consumes it, checks stock availability, reserves items, and publishes either ItemsReserved or InsufficientInventory events. The payment service independently consumes ItemsReserved, charges the customer, and publishes PaymentAuthorized or PaymentFailed. The fulfillment service consumes PaymentAuthorized and initiates shipping. At no point does any service command another or maintain awareness of the overall workflow; instead, each service implements local business logic triggered by events it cares about, and the end-to-end process emerges from their collective behavior.

```
OrderService               InventoryService          PaymentService           FulfillmentService
     |                            |                         |                         |
     |--OrderPlaced-------------->|                         |                         |
     |                            |--ItemsReserved--------->|                         |
     |                            |                         |--PaymentAuthorized----->|
     |                            |                         |                         |--ShipmentCreated-->
```

This topology exhibits natural fault tolerance: if the payment service crashes, inventory and fulfillment continue processing unrelated orders without disruption. Services can deploy independently since they couple only through published event schemas, not direct API dependencies. However, choreography introduces emergent complexity that compounds with workflow sophistication. Implementing compensation—say, releasing reserved inventory when payment fails—requires each service to subscribe to failure events and encode rollback logic. Understanding end-to-end system behavior demands tracing event flows across multiple service codebases and message topics. Circular dependencies emerge easily: if fulfillment publishes ShipmentCreated and inventory consumes it to update stock projections, which payment consumes to trigger loyalty points, which order consumes to update status, we've created a feedback loop where reasoning about causality becomes nearly impossible.

Orchestration centralizes workflow logic within a dedicated coordinator that explicitly models the process as a state machine. Instead of publishing events and hoping the right consumers react appropriately, the orchestrator issues commands to specific services and transitions state based on their responses. A saga orchestrator for hotel reservations might be implemented as a finite state machine with states like Initial, RoomReserving, RoomReserved, PaymentProcessing, PaymentAuthorized, ConfirmationSending, and Completed, along with failure states like RoomUnavailable, PaymentFailed, and Cancelled.

```
[Initial]
   |
   |--ReserveRoom(hotelId, dates)-->
   v
[RoomReserving]
   |
   |<--RoomReserved(reservationId)--
   v
[RoomReserved]
   |
   |--ChargePayment(amount, cardToken)-->
   v
[PaymentProcessing]
   |
   |<--PaymentAuthorized(txnId)--
   v
[PaymentAuthorized]
   |
   |--SendConfirmation(email, details)-->
   v
[ConfirmationSending]
   |
   |<--ConfirmationSent()--
   v
[Completed]
```

The orchestrator maintains this state machine instance in durable storage—typically a database table indexed by workflow instance ID—and drives state transitions by sending commands to worker services via point-to-point queues. When RoomReserved arrives, the orchestrator loads the state machine instance, verifies it's in the RoomReserving state, transitions to RoomReserved, persists the new state, and sends the ChargePayment command. If PaymentFailed arrives instead, the orchestrator transitions to compensation, sending a ReleaseRoom command to undo the reservation before moving to Cancelled state.

This centralized coordination provides several operational advantages over choreography. The state machine serves as executable documentation of the business process, making workflow logic explicit and auditable. Compensation is straightforward: the orchestrator knows which forward operations succeeded and can issue compensating commands in reverse order. Observability is trivial: querying the state machine table by workflow ID reveals current process status, which steps completed, and where failures occurred. Timeouts are natural: the orchestrator sets timers when entering waiting states and triggers compensation if responses don't arrive within SLA windows.

However orchestration introduces new failure modes and scaling concerns. The orchestrator becomes a single point of failure that must be highly available, requiring clustering, leader election, and state replication. It couples all participating services to its command schemas and choreography timeline, creating a deployment coordination burden when workflows evolve. The orchestrator can become a performance bottleneck if state machine persistence doesn't scale horizontally, particularly for high-throughput workflows where thousands of instances transition simultaneously.

Real-world infrastructure typically employs both patterns strategically within a single system. Inter-domain interactions use choreography to maintain loose coupling: when the order domain publishes OrderPlaced, it shouldn't need to know that the analytics domain consumes it for reporting, the recommendations domain uses it for model training, and the fraud domain analyzes it for suspicious patterns. Each consuming domain reacts independently without coordinating through a central authority. Intra-domain workflows use orchestration when complex branching logic or compensation requirements justify centralized control: a multi-step payment authorization flow with fraud checks, 3D Secure redirects, and retry logic is easier to reason about as an explicit state machine than as emergent choreography across payment service components.

Saga patterns formalize this coordination into well-defined transaction boundaries with explicit compensation logic. The saga pattern decomposes a distributed transaction into a sequence of local transactions, each publishing an event upon completion. If any local transaction fails, the saga executes compensating transactions to undo preceding operations, achieving eventual consistency without distributed locks. Sagas come in two flavors: choreography-based sagas where services react to events and initiate compensation autonomously, and orchestration-based sagas where a coordinator drives the saga forward and triggers compensation when failures occur.

A choreography-based saga for an e-commerce order might unfold as follows: OrderService creates an order in pending state and publishes OrderPlaced. InventoryService reserves items and publishes ItemsReserved. PaymentService charges the customer and publishes PaymentCharged. FulfillmentService creates a shipment and publishes ShipmentCreated. If payment fails, PaymentService publishes PaymentFailed, which InventoryService consumes to release reserved items and publish ItemsReleased, returning the system to a consistent state. Each service implements both forward and compensating transactions, reacting to events without central coordination.

An orchestration-based saga implements the same workflow through explicit state machine transitions. The saga orchestrator sends ReserveItems to inventory, waits for ItemsReserved, sends ChargePayment to payment, waits for PaymentCharged, then sends CreateShipment to fulfillment. If payment fails, the orchestrator transitions to compensation state and sends ReleaseItems to inventory, tracking compensation completion before transitioning to a terminal failure state. The orchestrator maintains the canonical workflow state and drives all transitions, providing centralized observability and control.

Both approaches must handle idempotency carefully since at-least-once delivery guarantees mean services receive duplicate messages. A payment service that receives ChargePayment twice must recognize the duplicate through the command's message ID or workflow instance ID, skip reprocessing, and return the cached result from the first execution. Idempotency typically requires storing processed message IDs in a database table consulted before executing each command, or using natural idempotency keys from the business domain like order IDs that prevent duplicate charges through unique constraints.

The implementation substrate for orchestration-based sagas ranges from lightweight state machine libraries embedded in service codebases to full-featured workflow engines that run as dedicated infrastructure services. Embedded approaches like Automatiko or Temporal's client libraries model workflows as code—typically as asynchronous functions decorated with durability annotations—that execute within the application process. The library checkpoints execution state to durable storage at each asynchronous boundary, allowing workflow instances to survive process restarts. This approach minimizes operational overhead by avoiding separate infrastructure services but couples workflow definitions to specific programming languages and runtime environments.

Dedicated workflow engines like Apache Airflow, Netflix Conductor, or Temporal Server externalize workflow execution from application services. Workflows are defined declaratively—as DAGs in Airflow, as JSON task definitions in Conductor, or as code that runs in a managed worker pool for Temporal—and submitted to the engine for execution. The engine persists workflow state, schedules tasks, handles retries and timeouts, and provides rich UIs for monitoring and manual intervention. This separation allows workflow definitions to evolve independently of service deployments and provides centralized operational control, but it introduces additional infrastructure complexity and runtime dependencies.

Correlation infrastructure in production systems often layers multiple identifiers to serve different operational needs. A single HTTP request might generate a request ID for API gateway logs, a trace ID for distributed tracing, a workflow instance ID for saga coordination, and business-domain entity IDs like order numbers or customer account IDs. These identifiers serve overlapping but distinct purposes: request IDs facilitate log aggregation across ingress and egress, trace IDs enable end-to-end latency analysis, workflow IDs support process monitoring and timeout handling, and entity IDs allow business-level queries like "show me all operations related to order 12345." Infrastructure must propagate all relevant identifiers through message headers and extract them at service boundaries, storing them in structured log fields and database columns to support efficient querying.

## 3. High-Performance Optimization & Failure Modes

Event routing infrastructure under production load confronts fundamental tensions between throughput, latency, durability, and consistency. Every architectural decision that optimizes one dimension necessarily trades off others, and understanding these trade-offs allows infrastructure engineers to tune systems for specific workload characteristics.

Throughput optimization begins with batching at every layer of the stack. Publishers batch messages before transmission, brokers batch disk writes and replication operations, and consumers batch acknowledgments to reduce round-trip overhead. A Kafka producer configured with `linger.ms=10` and `batch.size=32KB` accumulates up to 32KB of messages or waits 10 milliseconds—whichever comes first—before sending a batch to the broker. This batching can increase throughput by an order of magnitude compared to synchronous per-message transmission, as it amortizes TCP round-trip costs and allows the broker to leverage sequential disk I/O. However, batching increases latency by the linger duration: messages published at the start of a batch wait for the batch to fill or the timer to expire before transmission begins.

Broker-side batching extends this pattern to replication and persistence. Kafka brokers don't fsync log writes after every message; instead they rely on the operating system page cache to batch writes and schedule them according to system-wide I/O priorities. This approach achieves remarkable throughput—modern Kafka clusters sustain millions of messages per second—but it introduces durability risk: if the broker crashes before the OS flushes dirty pages to disk, recent messages vanish. The `min.insync.replicas` setting mitigates this by requiring writes to replicate to at least N follower brokers before acknowledgment, trading throughput for durability. A setting of 2 with replication factor 3 ensures that messages survive any single broker failure, since at least two replicas hold the data, but it reduces throughput compared to `min.insync.replicas=1` by adding network round-trip latency to the critical path.

Consumer throughput scales horizontally by partitioning topics and distributing partition assignments across consumer instances. A topic with 16 partitions can be consumed by up to 16 instances in a consumer group, each processing an independent subset of the event stream. This parallelism is the primary horizontal scaling mechanism in event-driven architectures, but it has limitations. Partitions provide the unit of parallelism: a topic with 4 partitions cannot leverage more than 4 consumer instances, regardless of how much processing capacity is available. Increasing partition count improves parallelism but fragments ordering guarantees—messages across partitions have no defined order—and increases broker-side resource usage, as each partition consumes file handles, memory for indexing, and coordination overhead during rebalancing.

Partition key selection profoundly impacts both performance and correctness. Hashing customer IDs as partition keys ensures all events for a given customer land on the same partition, preserving ordering for that customer's state transitions, but it can create hotspots if certain customers generate disproportionate traffic. A retail system where a single corporate buyer places thousands of orders per hour might overwhelm the partition handling that customer, starving other partitions of processing time. Composite partition keys that combine customer ID with finer-grained discriminators—like `${customerId}:${region}`—can distribute load more evenly, but they fragment ordering guarantees and complicate consumer logic that must now handle a customer's events arriving on multiple partitions.

Latency optimization often requires sacrificing throughput and durability. A producer configured with `acks=1` receives acknowledgment as soon as the partition leader writes the message, without waiting for follower replicas. This reduces write latency by eliminating replication delay but risks data loss if the leader fails before replication completes. Setting `compression.type=none` eliminates CPU overhead from compression, reducing latency at the cost of increased network bandwidth and broker storage. Disabling batching with `linger.ms=0` and `batch.size=1` sends messages immediately upon production, minimizing latency but devastating throughput by forcing a network round-trip per message.

Consumer poll loops must balance latency against processing efficiency. A tight loop that polls for a single message, processes it, acknowledges, and repeats minimizes latency but incurs high overhead from frequent polling. Batched polling that fetches up to 500 messages per poll reduces overhead but increases latency for messages at the end of the batch, which wait in memory while earlier messages process. Auto-commit intervals control acknowledgment batching: frequent commits provide strong progress guarantees—the consumer rarely reprocesses messages after a crash—but impose overhead from coordination traffic to the broker. Infrequent commits reduce overhead but expand the reprocessing window after failures.

Saga orchestration at scale requires careful attention to state machine persistence and locking. A naive implementation that serializes all workflow state transitions through a single database table becomes a bottleneck as concurrency increases. Horizontal scaling requires partitioning workflow instances across multiple database shards, typically by hashing the workflow instance ID to deterministically assign it to a shard. This allows concurrent workflow instances to transition independently without lock contention, but it complicates queries that span workflow instances, like "how many hotel reservations are currently in the PaymentProcessing state?"

Optimistic locking mechanisms allow workflow engines to detect concurrent state modifications without holding exclusive locks. Each state machine row includes a version number that increments on every update. When loading a workflow instance for transition, the engine reads the current version, applies business logic to compute the next state, and attempts an update with a WHERE clause that matches the original version: `UPDATE saga_state SET state='RoomReserved', version=version+1 WHERE workflow_id='abc' AND version=5`. If another thread concurrently modified the workflow, the version condition fails, the update affects zero rows, and the engine retries by reloading current state and recomputing the transition. This approach allows high concurrency for workflows with infrequent contention but degrades under hotspots where many threads compete to transition the same workflow instance.

Temporal's approach to workflow durability leverages event sourcing: instead of persisting workflow state as mutable records, it persists a log of events representing state transitions. A workflow's current state is computed by replaying its event history. This model provides complete audit trails, supports time-travel debugging where engineers replay workflows to specific points in history, and simplifies replication since event logs are append-only. However, it imposes computational overhead from replaying event histories on every workflow wake-up, particularly for long-running workflows with thousands of state transitions. Temporal mitigates this through periodic snapshots that capture workflow state at intervals, allowing replay to start from the most recent snapshot rather than the beginning of time.

Failure modes in event-driven systems often stem from implicit assumptions about delivery order, timing, and completeness. Out-of-order delivery occurs when network delays or retry logic cause messages to arrive in a sequence different from their publication order. A choreographed saga might publish ItemsReserved followed immediately by ItemsReleased (due to a downstream payment failure), but if network jitter delivers them to the fulfillment service in reverse order, the service might process the release before the reservation, creating inconsistent state. Services must be robust to out-of-order delivery through versioning or logical timestamps that allow them to discard stale operations.

Duplicate delivery from retry ambiguity requires idempotent processing at every layer. When a producer sends a message and the broker writes it successfully but the network drops the acknowledgment, the producer times out and retries, causing the broker to receive the message twice. Similarly, when a consumer processes a message successfully but crashes before acknowledging, the broker redelivers the message to another consumer. Every service must recognize duplicates through message IDs or natural idempotency keys and skip reprocessing. This often requires distributed state: a payment service might store processed message IDs in a database table with a TTL-based cleanup policy that retains IDs for longer than the maximum retry window.

Poison messages that repeatedly fail processing can deadlock a consumer if not handled explicitly. A malformed JSON payload that triggers a deserialization exception will fail processing, get rejected, and be redelivered, causing an infinite loop. Consumer implementations must implement retry policies with exponential backoff and dead-letter queues that sequester problematic messages after a threshold number of retries. The dead-letter queue serves as a holding area for manual investigation: operations teams inspect failed messages, fix data quality issues or software bugs, and replay messages once the underlying problem is resolved.

Saga compensation logic confronts fundamental limitations when compensating operations have side effects that cannot be undone. If a saga sends a confirmation email as part of a hotel reservation workflow and later compensates due to payment failure, it cannot unsend the email. The best it can do is send a cancellation email, but the customer has already been notified of a successful reservation. These semantic challenges require careful saga boundary design: operations with irreversible side effects should occur only after all potentially-failing steps complete, positioned at the end of the saga timeline. If that's impossible due to business requirements—perhaps regulatory compliance demands immediate email confirmation—the saga must accept eventual consistency: send the confirmation early, then send a cancellation if later steps fail, relying on customer support to handle edge cases where cancellations arrive delayed or lost.

Timeout configuration in orchestrated sagas must account for worst-case latency plus variance to avoid spurious compensation. If payment processing typically completes in 500ms but occasionally spikes to 10 seconds due to third-party API contention, setting a 2-second timeout causes frequent false failures where the orchestrator compensates a workflow that would have succeeded had it waited slightly longer. Overly generous timeouts delay failure detection, degrading user experience and tying up resources. Adaptive timeout strategies that adjust based on recent latency distributions—perhaps setting timeout to the 99th percentile of the last hour's measurements—provide a middle ground, though they add complexity and can cause oscillations if latency suddenly increases.

Circular event dependencies in choreographed systems create debugging nightmares and potential infinite loops. If service A publishes events consumed by service B, which publishes events consumed by service C, which publishes events consumed by A, we've created a feedback loop where reasoning about causality becomes impossible. Breaking these cycles requires disciplined event taxonomy: distinguish between domain events that represent state changes (OrderPlaced, PaymentAuthorized) and integration events that trigger downstream reactions (NotifyFraudDetection, UpdateRecommendations). Services should consume domain events from upstream boundaries and publish both domain events representing their own state changes and integration events targeting specific downstream consumers. This categorization naturally prevents cycles by establishing a directional event flow through domain boundaries.

Backpressure handling becomes critical when consumers cannot keep pace with producers. If an order service publishes 10,000 OrderPlaced events per second but the inventory service can only process 5,000 per second, the inventory service's consumer lag grows unbounded. Kafka naturally handles this through offset-based consumption: slow consumers fall behind but don't block producers, and the lag is visible through consumer group metrics. However, unbounded lag can cause operational issues: if lag grows to millions of messages, catch-up time after a consumer restart becomes hours or days, and broker disk usage climbs until storage fills. Circuit breaker patterns that detect excessive lag and trigger alerts or shed load can prevent cascading failures, though they necessarily abandon perfect consistency in favor of system availability.

Schema evolution in event-driven systems requires backward and forward compatibility to support rolling deployments. When evolving an OrderPlaced event to include a new shippingClass field, publishers running the new schema must coexist temporarily with consumers running the old schema that doesn't expect the field. Avro and Protobuf support this through schema evolution rules: new fields must have default values so old consumers can safely ignore them, and fields cannot be renamed or removed without breaking compatibility. Schema registries enforce these rules by validating new schema versions against previous versions, rejecting incompatible changes. However, semantic compatibility—ensuring that new field meanings align with how consumers interpret them—remains a human responsibility that requires coordination across teams.

Monitoring event-driven systems demands instrumentation across multiple dimensions. Per-topic throughput and consumer lag reveal whether processing keeps pace with production. End-to-end latency from event publication to consumer acknowledgment exposes routing inefficiencies and processing bottlenecks. Workflow instance metrics like completion rate, mean time to completion, and failure rate by error type provide business-level visibility into saga health. Distributed traces stitching together causally-related operations enable latency waterfall analysis and error propagation debugging. Correlation identifier propagation through structured logging allows reconstructing complete workflow timelines from log aggregation queries. Together, these signals provide the observability necessary to operate complex choreography and orchestration topologies at scale.
