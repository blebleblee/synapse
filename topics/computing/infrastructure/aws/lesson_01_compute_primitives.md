# Lesson 1: Compute Primitives and Instance Lifecycle

## 1. First-Principles Intuition & Invariants

Amazon EC2 represents a sophisticated abstraction layer that transforms physical server hardware—comprising CPUs, memory controllers, storage subsystems, and network interface cards—into virtualized compute units that can be provisioned, destroyed, and reconfigured through API calls in seconds. At its foundation, EC2 operates as a state machine where instances transition through well-defined lifecycle stages, each governed by strict invariants that determine what operations are permissible and what resources are allocated or released.

The fundamental abstraction in EC2 is the instance, which encapsulates a virtual machine running atop either the Xen or Nitro hypervisor depending on the instance generation. Modern EC2 instances leverage the AWS Nitro System, a purpose-built hardware and software architecture that offloads virtualization functions to dedicated silicon. This design decision stems from a critical insight: traditional hypervisors that run on the same CPU as guest workloads consume compute cycles that customers have paid for, creating both performance overhead and security surface area. By migrating the hypervisor control plane, network virtualization, and storage I/O paths to custom ASICs and separate cards, Nitro reclaims nearly 100% of the server's CPU and memory resources for customer workloads while simultaneously hardening the security boundary between tenants.

The instance type nomenclature encodes the resource allocation model through a hierarchical naming scheme. Consider `m6i.2xlarge`: the initial letter denotes the instance family (`m` for general-purpose balanced compute-memory ratio), the digit indicates the generation (`6` representing the sixth iteration with Intel Ice Lake processors), the optional letter suffix specifies the processor vendor or variant (`i` for Intel versus `a` for AMD, `g` for ARM Graviton), and the size multiplier (`2xlarge` providing 8 vCPUs and 32 GiB of memory). This taxonomy reflects underlying physical constraints—larger instance sizes within a family represent allocations of more physical cores, memory channels, and network bandwidth from the same underlying server hardware, up to the point where a bare-metal instance type grants exclusive access to an entire physical machine.

The placement of instances across AWS's physical infrastructure follows deterministic algorithms designed to balance competing objectives: failure isolation, network performance, and resource availability. AWS data centers are organized into Availability Zones (AZs), which are physically separate data center clusters with independent power, cooling, and networking infrastructure. Each region contains multiple AZs connected by low-latency fiber links forming a metropolitan-area network. Within an AZ, servers are arranged in racks sharing power distribution and top-of-rack network switches. EC2's placement engine must map logical instance requests onto this physical topology while honoring customer-specified constraints through placement groups and availability zone selections.

Three fundamental invariants govern instance lifecycle state transitions. First, an instance in the `running` state consumes billable resources including CPU allocation, memory reservation, and network attachment even when idle—AWS bills per-second with a one-minute minimum because the physical resources remain exclusively allocated to that instance ID and cannot be reassigned to other tenants. Second, instance state transitions are not instantaneous; launching an instance requires allocating physical resources, loading the Amazon Machine Image (AMI) root filesystem into attached storage, booting the guest kernel, and initializing the instance metadata service and network stack, a process typically completing in 30-90 seconds depending on AMI size and instance type. Third, certain metadata attributes are immutable after launch—the instance ID, private IP address within its VPC subnet, and the underlying hardware characteristics tied to the instance type cannot be changed without creating a new instance.

The billing model couples directly to the resource allocation architecture. On-Demand instances provide no commitment and bill per-second for running time, but this flexibility comes at maximum cost because AWS must maintain sufficient capacity headroom across all instance types and AZs to satisfy immediate demand spikes. Reserved Instances and Savings Plans amortize discounts (up to 72% compared to On-Demand) across one or three year terms by allowing AWS to perform more accurate capacity planning; customers commit to a consistent baseline of compute usage, enabling AWS to optimize data center build-out and hardware procurement. Spot Instances expose unused capacity at discounts up to 90%, but with the critical caveat that AWS can reclaim these instances with two minutes notice when On-Demand or Reserved capacity requirements rise. This termination model makes Spot suitable only for stateless, fault-tolerant workloads that can checkpoint progress and resume on different instances.

## 2. Core Architecture & Mechanics

The Nitro System architecture decomposes traditional hypervisor responsibilities across specialized hardware components that sit outside the main CPU and memory path. A Nitro card physically installed in each server contains dedicated CPU cores, DRAM, and ASICs that handle four critical domains: the Nitro Hypervisor providing CPU and memory virtualization, the Nitro Security Chip enforcing firmware attestation and configuration lockdown, the Nitro I/O acceleration engines for storage and network virtualization, and the Nitro Controller managing instance lifecycle state transitions. The main server CPUs execute only customer workloads and a minimal stub that communicates with the Nitro card over PCIe.

When an EC2 RunInstances API call arrives, a multi-stage provisioning workflow begins. The EC2 control plane first consults the placement optimizer, which queries current capacity across target availability zones and applies placement constraints. For instances in a cluster placement group, the optimizer attempts co-location on the same rack or even the same physical server to minimize inter-instance latency through shared L3 cache and memory interconnect bandwidth. For spread placement groups, it enforces maximum dispersion across distinct racks to minimize correlated hardware failures. Once a target physical server is selected, the control plane reserves the required vCPU count and memory capacity, preventing other instance launches from over-committing the host's resources.

The Nitro Hypervisor allocates physical memory pages to the instance using second-level address translation tables (Intel EPT or AMD NPT) that map guest physical addresses to host physical addresses. The allocated memory is zero-filled before being exposed to the guest to prevent information leakage from previous tenants—a mandatory security invariant. CPU pinning assigns specific physical cores to the instance's vCPUs using affinity masks, and NUMA-aware allocation attempts to localize memory allocations to the same CPU socket to minimize cross-socket memory access latency. The Nitro I/O subsystem then attaches an Elastic Block Store (EBS) volume or instance store volume as the root device, provisioning the storage through either NVMe-over-TCP to remote EBS servers or direct NVMe attachment for local SSDs.

```
EC2 Instance State Machine:

pending → running → stopping → stopped → terminated
   ↓         ↓                     ↓
 failed    shutting-down    (may restart)

State Transition Rules:
- pending:  Resources allocated, AMI being loaded
- running:  Instance boot complete, billable
- stopping: Shutdown signal sent, EBS volumes flushing
- stopped:  No compute billing, EBS storage billed
- shutting-down: Termination initiated, irreversible
- terminated: All resources released, instance ID retired
```

AMI construction and the boot sequence form a critical path in instance launch latency. An AMI encapsulates three components: a root filesystem snapshot stored as an EBS snapshot, metadata describing the kernel and ramdisk (for paravirtual AMIs) or boot mode (for HVM AMIs using UEFI or legacy BIOS), and block device mappings that specify additional EBS volumes or instance store ephemeral disks to attach at launch. When launching an instance, EC2 creates a new EBS volume from the root snapshot using a lazy-loading mechanism: the volume appears immediately accessible, but blocks are fetched from S3 on-demand as the guest OS reads them during boot. This copy-on-write model means first-access latency for filesystem blocks, which manifests as slower initial boot and application cold-start times compared to subsequent reboots when the volume's local cache is warm.

The instance metadata service (IMDS) provides a critical runtime API accessible at the link-local address `169.254.169.254` that instances query to retrieve their identity, network configuration, and IAM credentials. IMDSv2 introduced a session-oriented protocol requiring a PUT request to obtain a token before subsequent GET requests for metadata will succeed, mitigating server-side request forgery (SSRF) attacks where an application vulnerability could be exploited to exfiltrate IAM credentials. The metadata service runs on the Nitro card itself, not within the instance, so the HTTP endpoint is implemented by the Nitro Controller intercepting packets destined to `169.254.169.254` before they would reach the network interface.

Network attachment follows a deterministic model tied to the VPC subnet and security group configuration specified at launch. Each instance receives a primary elastic network interface (ENI) with a private IPv4 address allocated from the subnet's CIDR block using a subnet-local IPAM allocator. The Nitro I/O acceleration engine implements the virtual network interface by encapsulating instance packets in VXLAN or Geneve tunnels addressed to other instances or VPC gateways, and performing distributed firewall rule evaluation for security groups in hardware. Multi-queue network driver support in modern instances allows parallel packet processing across multiple vCPUs, with each queue assigned to a separate MSI-X interrupt vector for improved throughput under concurrent network flows.

Instance metadata includes a rich set of attributes queryable through the DescribeInstances API or visible in the EC2 console. The instance ID follows the format `i-0123456789abcdef0` and serves as the primary key in EC2's distributed database, remaining stable across stop/start cycles but invalidated upon termination. The hypervisor field indicates `xen` for older instance types or `nitro` for Nitro-based instances, which matters for low-level diagnostics since Nitro instances expose virtualized hardware through full PCI device emulation rather than paravirtualized drivers. The placement object reveals the actual availability zone and placement group membership, while the network interfaces array enumerates all attached ENIs with their MAC addresses, private IPs, security groups, and source/destination check status.

## 3. High-Performance Optimization & Failure Modes

Optimizing instance launch latency requires addressing the AMI loading bottleneck through snapshot pre-warming or fast snapshot restore. Standard EBS volumes built from snapshots load blocks lazily from S3, incurring millisecond-scale latency penalties on first access. The `fio` utility can characterize this behavior by issuing sequential reads across the entire volume and measuring IOPS over time—the first pass through the volume will show degraded performance as blocks are fetched and cached. For latency-sensitive workloads, enabling fast snapshot restore on frequently-used AMIs pre-initializes EBS volumes at launch time by streaming the entire snapshot into the volume before the instance enters the running state, eliminating lazy-loading penalties at the cost of increased launch time (now waiting for full volume hydration) and additional charges.

Resource contention on multi-tenant physical servers, though rare under Nitro's strict allocation model, can still manifest through noisy neighbor effects in shared resources not fully isolated. The L3 cache, memory bandwidth to DRAM, and PCIe lanes to the Nitro card are shared among instances co-located on the same physical server. Workloads with high memory access rates or large working sets that exceed the instance's proportional L3 cache allocation can experience performance variability if another co-located instance begins aggressively thrashing cache lines. The `perf stat` tool on Linux can expose cache miss rates and memory bandwidth saturation by reading performance monitoring counters. For strict performance isolation requirements, bare-metal instance types (`*.metal` variants like `m6i.metal`) provide exclusive access to all physical resources, eliminating multi-tenancy effects entirely.

Placement group strategy selection directly impacts both failure correlation and network performance. Cluster placement groups pack instances together on the same physical network spine, often within a single rack or multi-rack pod, to minimize inter-instance latency and maximize aggregate bandwidth. Measurements with `iperf3` between instances in a cluster placement group typically achieve single-digit microsecond latencies and 25-100 Gbps throughput depending on instance type network limits. However, this tight packing increases failure blast radius—a top-of-rack switch failure, power distribution unit failure, or correlated hardware defects affect all instances in the group simultaneously. Spread placement groups enforce the opposite constraint, distributing instances across distinct racks with independent failure domains, trading reduced network performance for improved fault isolation. Partition placement groups occupy a middle ground, dividing instances into logical partitions that map to separate racks, allowing applications to implement rack-aware replica placement strategies where data is replicated across partitions but compute within a partition can be co-located for performance.

Instance store volumes, when available on the instance type, provide high-performance local NVMe SSDs directly attached to the physical server, offering sub-millisecond latency and millions of IOPS compared to EBS network-attached volumes. However, instance store data is ephemeral—it persists only while the instance remains in the running state. Stopping or terminating the instance, or hardware failures that force instance migration to different physical servers, result in complete data loss. This ephemerality makes instance store suitable only for temporary data, caches, or workloads that replicate data to durable storage. The `/dev/nvme1n1` and subsequent NVMe device names map directly to physical drives without abstraction layers, enabling workloads to leverage advanced NVMe features like I/O determinism commands and namespace management for fine-grained performance tuning.

Handling instance interruptions for Spot Instances requires implementing graceful shutdown handlers that checkpoint application state to durable storage within the two-minute warning window. EC2 delivers interruption notices both through the instance metadata service (a new `/spot/instance-action` endpoint returns termination time and reason) and optionally through EventBridge events that can trigger Lambda functions or SNS notifications. Production-ready Spot workloads typically run batch processing frameworks like AWS Batch or container orchestrators like Kubernetes with cluster-autoscaler configured for Spot instance groups. These systems maintain a queue of pending work, automatically drain tasks from instances receiving termination notices, and replenish capacity by launching replacement Spot instances in different instance types or availability zones where capacity is available. The Spot instance advisor and Spot placement score APIs provide real-time data on interruption rates and capacity availability across instance types, enabling intelligent diversification strategies that balance cost savings against interruption frequency.

Instance recovery and automated replacement mechanisms protect against underlying hardware degradation. EC2 performs continuous health monitoring of physical servers through the Nitro system health telemetry, detecting failing DRAM modules, degraded SSDs, or CPU thermal throttling. When health checks indicate imminent hardware failure, EC2 can trigger automatic instance retirement, sending notifications to instance owners and scheduling mandatory stops within a multi-day window. For instances with simplified instance lifecycle using systems manager or auto-scaling groups, recovery actions can automatically launch replacement instances, reattach EBS volumes, and restore elastic IP associations, minimizing manual intervention. The StatusCheckFailed_System metric in CloudWatch indicates when underlying hardware has failed, distinguishing these infrastructure failures from guest OS crashes (StatusCheckFailed_Instance) and enabling automated recovery policies through CloudWatch alarms that trigger instance reboot or replacement.

Capacity reservation mechanisms provide deterministic instance launch guarantees by pre-allocating physical resources in specified availability zones and instance types. On-Demand Capacity Reservations reserve instances immediately without requiring upfront commitment payments or term lengths, but bill at full On-Demand rates whether instances are running or not. This model suits workloads with predictable scaling events where capacity must be guaranteed—for example, reserving 100 `c6i.2xlarge` instances in a specific AZ to ensure an overnight batch job can scale out reliably. Capacity Reservations can be scoped to specific tenancy models (shared versus dedicated tenancy where instances run on single-tenant physical servers), and can be shared across AWS accounts in the same organization to allow centralized capacity management.

The interplay between instance type selection and workload characteristics determines cost efficiency and performance. Compute-optimized instance families (`c` prefix) provide higher vCPU-to-memory ratios (1:2 GiB per vCPU) suited for CPU-bound tasks like video encoding, high-performance web servers, and scientific modeling. Memory-optimized families (`r` prefix) invert this ratio (1:8 GiB per vCPU or higher) for in-memory databases, caching layers, and big data analytics engines. Storage-optimized families (`i`, `d` prefixes) include high-capacity instance store volumes with NVMe SSDs for data warehousing and distributed filesystems. Graviton-based instances (ARM architecture with `g` suffix like `m6g.xlarge`) deliver price-performance advantages for workloads compiled for ARM64, achieving 20-40% better price-performance than equivalent x86 instance types while consuming less power. Profiling actual workload resource utilization using CloudWatch metrics (CPU utilization, network throughput, disk I/O, memory usage via CloudWatch agent) reveals optimization opportunities—an instance running at 15% CPU utilization likely indicates over-provisioning that could be rightsized to a smaller instance type, recovering cost without sacrificing performance.
