# Operational Verification Labs: Nas

Network-Attached Storage systems represent a critical convergence point in modern infrastructure where block storage protocols, file system semantics, network transport stacks, and distributed consistency mechanisms intersect. A NAS appliance is not merely a file server—it is a specialized storage node that must maintain coherent state across concurrent client access patterns, survive transient network partitions, recover from power failures without data loss, and saturate available network bandwidth while preserving cache-coherent metadata operations. This laboratory guide approaches NAS verification from the perspective of a production infrastructure engineer who must validate storage subsystem behavior under realistic operational stress, diagnose performance anomalies through kernel-level observability, and architect fault-tolerant recovery procedures that align with organizational SLAs.

The pedagogical philosophy underlying these exercises prioritizes hands-on systems verification over abstract storage theory. You will interact directly with the Linux kernel's VFS layer, scrutinize TCP window scaling behavior during bulk transfers, inject controlled I/O faults to validate crash consistency guarantees, and measure filesystem metadata latency distributions under saturating workloads. Each exercise builds a mental model of how NFS protocol state machines, iSCSI block transport, and SMB/CIFS authentication flows materialize as concrete kernel data structures, network packets, and disk I/O patterns observable through production diagnostic tools.

## Objective & Environment Setup

The primary objective of these labs is to develop operational fluency in diagnosing, profiling, and validating Network-Attached Storage systems through kernel-level instrumentation and network protocol analysis. You will verify that a NAS deployment satisfies correctness invariants—crash consistency, cache coherence, access control enforcement—and performance contracts—sustained throughput under concurrent load, bounded metadata operation latency, predictable recovery time objectives. The exercises assume a Linux-based infrastructure environment with access to both NAS server nodes and client mount points, along with privileged access to kernel tracing facilities.

Before beginning the exercises, establish a representative NAS test environment. Deploy a dedicated storage node running either a purpose-built NAS distribution such as TrueNAS SCALE, OpenMediaVault, or a conventional Linux server exporting filesystems via NFS version 4.2, SMB version 3.1.1, or iSCSI block targets. The storage backend should utilize a production-grade filesystem—ZFS for copy-on-write snapshots and end-to-end checksumming, or Btrfs for its integrated volume management and RAID capabilities. Provision at least two client nodes to simulate concurrent access patterns and network partition scenarios. Ensure the network fabric between clients and storage nodes supports jumbo frames (MTU 9000) and verify that network interface cards expose hardware offload capabilities through ethtool.

Install the complete diagnostic toolchain across both server and client nodes. The iproute2 suite provides `ip` for interface configuration and `ss` for socket state inspection. The `ethtool` utility exposes NIC hardware statistics, offload features, and link negotiation parameters. Packet capture and dissection requires `tcpdump` for real-time filtering and `tshark` for protocol-aware parsing of NFS RPC calls and SMB2 command sequences. Performance profiling demands the `perf` subsystem for CPU sampling and hardware event counting, `iotop` for per-process disk I/O attribution, and `bpftool` for deploying eBPF-based storage stack tracing programs. For Kubernetes-integrated storage, install `kubectl` to inspect PersistentVolume bindings and CSI driver logs, and `crictl` to examine container filesystem mounts and overlay metadata.

Validate your environment by mounting an NFS export from the storage node onto a client using NFSv4 with Kerberos authentication. Execute a baseline throughput test by writing a 10 GiB file using `dd` with direct I/O to bypass page cache effects, then measure sustained read bandwidth to verify line-rate performance relative to your network fabric. Capture this baseline transaction with `tcpdump` filtering on port 2049, and inspect the resulting pcap file to confirm that TCP window scaling is active and that the NFS WRITE operations carry payloads matching your configured `wsize` parameter. This initial validation confirms that your toolchain is operational and that the storage and network layers exhibit expected baseline behavior before introducing diagnostic complexity.

## Exercise 1: Live State & Internal Subsystem Inspection

The first category of operational verification focuses on introspecting the runtime state of NAS subsystems without perturbing production workloads. Live state inspection encompasses examining active NFS server RPC queues, enumerating established SMB sessions with their authentication contexts, profiling filesystem metadata cache hit ratios, and correlating network socket buffer occupancy with client-side I/O wait times. These diagnostic techniques rely on procfs and sysfs pseudo-filesystems, kernel tracing infrastructure, and protocol-specific administrative interfaces that expose internal state machines ordinarily hidden behind user-space API abstractions.

Begin by inspecting the NFS server's active RPC state on the storage node. The Linux kernel NFS server maintains per-client state in `/proc/fs/nfsd/clients/`, where each subdirectory corresponds to a connected client identified by its IP address and NFSv4 client ID. Navigate into a client directory and examine the `states` file, which enumerates all currently held open file delegations, byte-range locks, and layout segments issued to that client. Cross-reference the inode numbers listed in this state dump with the actual files on disk by using `find` with the `-inum` predicate. This mapping reveals which files are subject to active client locking, a critical diagnostic when investigating serialization bottlenecks or lock conflicts that manifest as client-side application hangs.

Next, profile the Linux page cache behavior for the exported filesystem using `/proc/meminfo` and the `cachestat` tool from the BCC eBPF toolkit. The page cache serves as the primary mechanism for absorbing write bursts and coalescing read requests, but cache coherence across NFS clients depends on close-to-open consistency semantics enforced through file attribute revalidation. Execute `cachestat 1` to observe per-second page cache hit and miss rates while simultaneously generating a mixed read-write workload from multiple NFS clients using `fio` with the `libaio` engine and a 4 KiB block size. A high miss rate coupled with elevated `GETATTR` RPC counts in `/proc/net/rpc/nfsd` indicates excessive attribute revalidation overhead, suggesting that tuning the `acdirmin` and `acregmin` mount options to lengthen client-side attribute cache lifetimes may reduce metadata round-trips.

For SMB/CIFS exports, introspect active session state using the `smbstatus` utility from the Samba suite. This command enumerates all connected clients, their authenticated user principals, and the specific shares they have mounted. The output includes the SMB protocol dialect negotiated during session setup—verify that clients are negotiating SMB 3.1.1 to ensure encryption and integrity protection are available. Examine the locks section of the `smbstatus` output to identify any conflicting opportunistic locks (oplocks) or SMB2 leases that may be causing client-side application stalls. Correlate these lock holders with the client IP addresses to determine whether a misbehaving application on a specific client is monopolizing file access.

To inspect iSCSI block storage state, use the `tgtadm` utility on the storage node to query target and LUN configuration, then examine initiator session state through `/sys/kernel/scsi_device/`. Each connected iSCSI initiator appears as a SCSI device with its session parameters exposed in sysfs, including negotiated `MaxRecvDataSegmentLength`, `FirstBurstLength`, and the number of active commands queued. On the client side, inspect the iSCSI session using `iscsiadm -m session -P 3` to verify that Immediate Data and Initial R2T parameters are optimized for your workload—disabling Initial R2T reduces protocol round-trips for small writes. Cross-reference the iSCSI session's underlying TCP connection state using `ss -tipm` to observe socket buffer sizes and retransmission counters, which reveal network-layer bottlenecks affecting block I/O latency.

Deploy an eBPF tracing program to capture the full I/O stack latency breakdown from client application system call to storage node disk completion. Using the BCC `biolatency` tool, measure block I/O latency distributions on the storage node while clients perform random read operations. Simultaneously, on a client node, run `funclatency` to trace the latency distribution of the `nfs_file_read` kernel function, which encompasses both network round-trip time and remote filesystem operation latency. Compare these distributions to isolate whether latency variance originates from network jitter, NFS server CPU scheduling delays, or backend disk I/O queuing. If the `biolatency` histogram on the server shows tight clustering around the disk's specified IOPS latency, but `funclatency` on the client reveals a long tail, the variance is attributable to network or NFS protocol overhead rather than storage subsystem performance.

Inspect network interface statistics on both client and server using `ethtool -S <interface>` to enumerate hardware counters for dropped packets, checksum offload errors, and TCP segmentation offload (TSO) events. Large `rx_missed_errors` or `rx_fifo_errors` counters indicate that the NIC's receive ring buffer is undersized relative to incoming packet burst rates, causing kernel network stack packet loss. Increase the ring buffer size using `ethtool -G <interface> rx <size>` and re-run your workload to verify that dropped packet counts no longer increment. Similarly, verify that large receive offload (LRO) and generic receive offload (GRO) are enabled to reduce per-packet processing overhead for bulk data transfers.

Conclude the live state inspection exercise by correlating application-layer metrics with kernel subsystem state. On a client running a database that stores its tablespace on an NFS mount, execute `strace -c <database_process>` to profile system call distributions. High counts of `getdents` and `stat` calls indicate metadata-heavy workloads that may benefit from client-side directory entry caching or server-side filesystem tuning such as enabling directory name lookup caches (dcache). Cross-reference these application system call patterns with the NFS RPC statistics in `/proc/self/mountstats` for the relevant mount point, which breaks down RPC operations by type and reports average round-trip times. This multi-layer correlation between application behavior, NFS protocol activity, and kernel subsystem state is essential for diagnosing performance pathologies that span the full storage I/O path.

## Exercise 2: Benchmarking & Saturation Profiling

Moving beyond passive state observation, the second exercise category involves actively saturating the NAS subsystem to characterize performance limits, identify bottleneck components, and validate that the system meets its design throughput and latency specifications. Saturation profiling requires constructing workloads that stress individual subsystem dimensions in isolation—network bandwidth, disk IOPS, metadata operation rate, CPU cycles consumed by protocol processing—then progressively combining stressors to reveal emergent bottlenecks that only manifest under multi-dimensional load.

Establish a baseline single-client sequential throughput measurement using `fio` configured for large-block direct I/O. On a client node, create an `fio` job file specifying a `filename` pointing to a file on the NFS mount, `ioengine=libaio`, `direct=1` to bypass client page cache, `bs=1M` for 1 MiB block sizes, `iodepth=32` to maintain sufficient I/O queue depth, and `rw=write` for sequential write testing. Run this job for 60 seconds and record the reported bandwidth. This measurement should approach the theoretical network bandwidth minus TCP/IP and NFS protocol overhead—for a 10 GbE link, expect sustained throughput in the range of 1.1 to 1.15 GiB/s. If observed throughput falls significantly below this target, capture a simultaneous packet trace with `tcpdump -i <interface> -w /tmp/nfs-write.pcap` and analyze it using `tshark` to check for TCP window exhaustion, retransmissions, or undersized NFS `wsize` parameters limiting per-RPC payload sizes.

Transition to a multi-client saturation test by launching the same `fio` workload simultaneously from four client nodes, all writing to distinct files within the same NFS export. Monitor the aggregate throughput reported across all clients and compare it to the single-client baseline multiplied by four. If the aggregate throughput does not scale linearly, inspect the storage node's CPU utilization using `perf top` to identify hot kernel functions. High CPU consumption in `nfsd` threads, particularly within functions like `svc_process` or `nfs4_preprocess_stateid`, indicates that NFS server request processing has become CPU-bound. Conversely, if CPU utilization remains low but throughput fails to scale, examine the storage backend using `iostat -x 1` to check whether disk utilization approaches 100%, signaling that the backend storage subsystem has saturated before the network or CPU.

Profile metadata operation performance by constructing a workload that creates and deletes small files at high rates. Use the `mdtest` benchmark from the IOR suite, configuring it to perform directory tree creation with a branching factor of 10 and a depth of 3 across multiple NFS clients. Execute `mdtest -C -d <nfs_mount_point> -n 10000 -i 3 -b 10` and observe the reported file creation rate in operations per second. Metadata operations in NFS require synchronous server-side journaling to ensure crash consistency, so metadata throughput is often limited by the storage backend's synchronous write IOPS capability. On the storage node, use `perf record -e block:block_rq_issue -a -g -- sleep 30` during the `mdtest` run, then analyze the resulting profile with `perf report` to determine whether the bottleneck lies in filesystem transaction commit paths, such as ZFS `zil_commit` or ext4 `jbd2` journal flushing.

Saturate the NFS server's RPC processing capacity by generating a workload with maximum concurrency and minimal per-operation payload. Use `fio` with `bs=4k`, `iodepth=128`, and `numjobs=16` to create 16 parallel I/O streams each maintaining 128 outstanding operations. This configuration generates a high rate of small NFS READ and WRITE RPCs, stressing the server's ability to schedule and dispatch NFS daemon threads. Monitor the server's `/proc/net/rpc/nfsd` statistics, specifically the `th` line which reports thread utilization percentages across histogram buckets. If the histogram shows that all threads frequently operate at 100% utilization, increase the number of NFS server threads by writing a larger value to `/proc/fs/nfsd/threads`. Re-run the saturation test and verify that increasing thread count improves aggregate IOPS, confirming that thread pool exhaustion was the limiting factor.

Introduce network-layer saturation to isolate protocol stack bottlenecks from storage subsystem limitations. Using `iperf3` between a client and the storage node, measure raw TCP throughput to establish the network fabric's baseline capacity independent of NFS protocol overhead. If `iperf3` achieves line-rate performance but NFS workloads fall short, the gap is attributable to NFS protocol processing costs. Deploy the `tcptrace` tool against a packet capture from an NFS write workload to compute effective goodput, accounting for TCP retransmissions and out-of-order delivery. High retransmission rates suggest network path MTU discovery failures or congested switch buffers—verify that jumbo frames are consistently enabled across all intermediate switches and routers using `ping -M do -s 8972 <storage_node_ip>` to test path MTU without fragmentation.

Construct a mixed workload that simultaneously stresses read throughput, write throughput, and metadata operations to identify emergent bottlenecks. Configure `fio` with three job definitions in a single job file: one performing sequential writes at 1 MiB block size, another performing random reads at 4 KiB block size, and a third performing `open/close` file operations. Execute this composite workload while monitoring the storage node with `perf stat -a -e cycles,instructions,LLC-loads,LLC-load-misses` to profile CPU efficiency and cache behavior. A low instructions-per-cycle (IPC) metric coupled with high LLC (last-level cache) miss rates indicates that the CPU is stalling on memory access latency, often caused by cache-incoherent data structures in the NFS server's RPC processing path. This insight may guide architectural tuning such as enabling NUMA-aware NFS thread pinning or adjusting socket buffer memory allocation policies.

Validate QoS and bandwidth limiting enforcement by configuring traffic control policies on the storage node and verifying client-side observed throughput. Use the `tc` command to establish a Hierarchical Token Bucket (HTB) qdisc on the storage node's network interface, limiting NFS traffic to 5 Gbps: `tc qdisc add dev <interface> root handle 1: htb default 10` followed by `tc class add dev <interface> parent 1: classid 1:10 htb rate 5gbit`. Launch a saturation `fio` workload from a client and confirm that observed throughput respects the 5 Gbps limit. Simultaneously capture a packet trace and analyze TCP window behavior using `tshark -r <capture> -T fields -e tcp.window_size_value` to verify that window scaling adapts to the reduced available bandwidth without excessive retransmissions. This validates that rate limiting does not induce pathological TCP behavior such as window collapse or stalled connections.

## Exercise 3: Fault Injection & Recovery Analysis

The third and most critical exercise category focuses on validating NAS system behavior under failure conditions, ensuring that crash consistency guarantees hold, that client failover mechanisms operate correctly, and that recovery time objectives align with service level agreements. Fault injection testing deliberately introduces network partitions, power failures, disk I/O errors, and corrupted protocol state to verify that the NAS subsystem gracefully degrades, preserves data integrity, and recovers to full operational state within bounded time intervals. These exercises require controlled injection frameworks such as `tc netem` for network fault emulation, `dm-flakey` for simulating disk errors, and kernel module instrumentation for introducing RPC processing delays.

Begin by validating NFS client failover behavior under server unavailability. Configure an NFS mount with the `soft,timeo=50,retrans=3` options to establish bounded retry behavior, then initiate a write workload using `dd` to write a 1 GiB file to the mount point. While the write is in progress, induce a network partition by adding a `tc` rule on the storage node to drop all packets from the client's IP address: `tc qdisc add dev <interface> root netem loss 100%`. Observe the client-side behavior—with soft mount semantics, the write operation should fail after the specified timeout and retry count, returning an error to the application. Verify this by checking the `dd` command's exit status and examining kernel log messages with `dmesg | grep -i nfs`. Repeat the test with `hard,intr` mount options, which enforce infinite retries but allow signal interruption, and observe that the write operation blocks indefinitely until you restore network connectivity by removing the `tc` rule. This demonstrates the critical distinction between soft and hard mount semantics in determining application-level failure handling.

Validate crash consistency guarantees by simulating an unclean server shutdown during active write workloads. On the storage node, configure the filesystem with synchronous metadata updates if using ext4 (`mount -o sync,data=journal`) or rely on ZFS's transactional write semantics. From a client, execute a workload that creates a directory tree with 1000 small files while simultaneously writing to a separate large file using `dd`. While both operations are in progress, forcibly terminate the NFS server daemon using `killall -9 nfsd`, then immediately reboot the storage node using `echo b > /proc/sysrq-trigger` to simulate a power failure without allowing clean shutdown. After the storage node recovers and the filesystem is remounted, verify data integrity by checking that either all files in the directory tree are present and complete, or none are present, demonstrating atomic directory operation semantics. Use `fsck` or `zpool scrub` to verify that the filesystem metadata remains consistent and that no orphaned inodes or leaked blocks exist. This confirms that the storage backend's journaling or copy-on-write mechanisms successfully preserved crash consistency.

Inject I/O errors at the block device layer using the device-mapper `dm-flakey` target to simulate transient disk failures. On the storage node, replace the actual block device backing your filesystem with a `dm-flakey` device configured to periodically inject EIO errors: `dmsetup create flakey --table "0 <size> flakey <dev> 0 60 20"`, where the device operates normally for 60 seconds, then injects errors for 20 seconds in a repeating cycle. Initiate a continuous write workload from an NFS client while monitoring the storage node's kernel logs for I/O error messages and observing how the filesystem and NFS server handle these errors. ZFS should detect the checksum failures and attempt to read from a redundant vdev if configured in a mirrored or RAIDZ layout, while ext4 may remount the filesystem read-only if errors exceed the configured threshold. Verify that the NFS client receives appropriate error returns rather than stale or corrupted data, confirming end-to-end error propagation from the block layer through the filesystem and NFS protocol stack to the client application.

Test SMB Transparent Failover by configuring a clustered SMB share using CTDB (Cluster Trivia Database) or the SMB Witness protocol. Establish an SMB 3.0 connection from a Windows client to the clustered share with Persistent Handles enabled, then begin writing to a file. While the write is in progress, initiate a failover by moving the clustered IP address to a different storage node using `ctdb moveip <ip> <new_node>`. The SMB client should transparently reconnect to the new node and resume the write operation without application-level error or data loss. Verify the failover by capturing network traffic and examining the SMB2 Tree Connect and Session Setup sequences that occur during failover—the client should reuse its existing session key and file handle, demonstrating protocol-level resilience.

Introduce protocol-level faults by corrupting NFS RPC messages using `tc netem` packet corruption. On the storage node, configure `tc` to corrupt 1% of packets: `tc qdisc add dev <interface> root netem corrupt 1%`. Initiate an NFS write workload and monitor the client-side RPC statistics in `/proc/self/mountstats` for increases in retransmitted RPCs and bad RPC responses. The NFS client should detect corrupted responses via the RPC XID mismatch or TCP checksum validation, discard the corrupted packets, and retransmit requests. Verify that no corrupted data is written to the server by comparing checksums of files written during the fault injection period with reference checksums from clean writes. This validates that the protocol stack's integrity checks successfully prevent data corruption from propagating to the storage layer.

Validate backup and snapshot recovery workflows by creating a ZFS snapshot of the exported filesystem while a write workload is active, then intentionally corrupting a subset of files. Use `zfs snapshot <pool>/<dataset>@<snapshot_name>` to capture a consistent point-in-time image, then on a client, overwrite several files with garbage data using `dd if=/dev/urandom`. Perform a file-level restore by accessing the snapshot through the `.zfs/snapshot` directory on the NFS mount and copying the original file versions back to the live filesystem. Verify data integrity by comparing checksums of the restored files against reference checksums captured before corruption. This exercise confirms that snapshot-based recovery workflows function correctly over NFS and that snapshot isolation prevents active workloads from interfering with backup consistency.

Conclude the fault injection exercise by testing graceful degradation under resource exhaustion. On the storage node, artificially constrain available memory using cgroups to simulate memory pressure: `cgcreate -g memory:/nfs_limited` followed by `echo 2G > /sys/fs/cgroup/memory/nfs_limited/memory.limit_in_bytes` and `cgclassify -g memory:/nfs_limited $(pgrep nfsd)`. Launch a workload that generates a high rate of unique file accesses to stress the dentry cache and page cache. Monitor the storage node's memory statistics using `vmstat 1` and observe increased page reclaim activity and potential OOM killer invocations. Verify that the NFS server continues to service requests despite memory pressure, albeit with degraded performance, and that clients receive JUKEBOX (NFS4ERR_DELAY) responses during periods of extreme load rather than connection failures. This confirms that the NFS server implements proper backpressure mechanisms and resource management under constrained conditions.

## Diagnostic Cheat Sheet & Verification Checklist

The following reference tables consolidate the essential diagnostic commands and verification procedures introduced across the three exercise categories. These commands form the operational toolkit for rapid NAS subsystem troubleshooting in production environments where minimizing mean time to resolution is critical.

**Live State Inspection Commands**

| Purpose | Command | Key Output Fields |
|---------|---------|-------------------|
| NFS server per-client state | `ls /proc/fs/nfsd/clients/` | Client ID, delegations, locks |
| NFS RPC statistics | `cat /proc/net/rpc/nfsd` | RPC counts by type, queue depth |
| NFS client mount statistics | `cat /proc/self/mountstats` | RPC RTT, retrans, operations/sec |
| SMB active sessions | `smbstatus -b` | Clients, shares, locks, protocol version |
| iSCSI session parameters | `iscsiadm -m session -P 3` | MaxRecvDataSegmentLength, DataDigest |
| Page cache hit rate | `cachestat 1` | Hits, misses, dirties, ratio |
| Network socket state | `ss -tipmn` | Send-Q, Recv-Q, cwnd, rto, rtt |
| NIC hardware counters | `ethtool -S <interface>` | rx_dropped, tx_errors, tso_packets |
| Block I/O latency distribution | `biolatency-bpfcc` | Histogram of I/O completion times |

**Performance Profiling Commands**

| Purpose | Command | Key Metrics |
|---------|---------|-------------|
| Disk I/O statistics | `iostat -x 1` | %util, await, svctm, r/s, w/s |
| Per-process disk I/O | `iotop -oPa` | Total I/O, I/O rate, swap usage |
| CPU profiling with sampling | `perf top -p $(pgrep nfsd)` | Hot functions, CPU%, call graph |
| Hardware event counters | `perf stat -e cycles,instructions,cache-misses` | IPC, cache hit rate |
| Network bandwidth measurement | `iperf3 -c <server> -t 60 -P 4` | Throughput, jitter, loss |
| Filesystem metadata benchmark | `mdtest -C -d <dir> -n 10000` | File creates/sec, stat ops/sec |
| I/O workload generator | `fio --name=test --rw=write --bs=1M --direct=1` | Bandwidth, IOPS, latency percentiles |

**Fault Injection and Recovery Commands**

| Purpose | Command | Effect |
|---------|---------|--------|
| Network partition simulation | `tc qdisc add dev <if> root netem loss 100%` | Drop all packets |
| Packet corruption injection | `tc qdisc add dev <if> root netem corrupt 1%` | Corrupt 1% of packets |
| Block device error injection | `dmsetup create flakey --table "0 <sz> flakey <dev> 0 60 20"` | Periodic I/O errors |
| Memory constraint (cgroup) | `echo 2G > /sys/fs/cgroup/memory/<cg>/memory.limit_in_bytes` | Limit available memory |
| Kill NFS server daemon | `killall -9 nfsd` | Simulate server crash |
| Force kernel panic | `echo b > /proc/sysrq-trigger` | Immediate unclean reboot |
| ZFS snapshot creation | `zfs snapshot <pool>/<dataset>@<name>` | Point-in-time copy |
| Filesystem consistency check | `fsck -fn <device>` (ext4) or `zpool scrub <pool>` (ZFS) | Verify metadata integrity |

**Verification Checklist for NAS Deployment**

Prior to declaring a NAS system production-ready, execute the following verification sequence to validate correctness and performance invariants:

1. **Protocol Connectivity**: Verify that clients can successfully mount exports using all configured protocols (NFSv4, SMB3, iSCSI). Confirm authentication succeeds using Kerberos or NTLM as appropriate. Check `/var/log/messages` on server for successful mount negotiations.

2. **Baseline Throughput**: Measure single-client sequential read and write throughput using `fio` with 1 MiB block sizes and direct I/O. Verify that observed bandwidth reaches at least 90% of theoretical network capacity after accounting for protocol overhead.

3. **Multi-Client Scaling**: Launch concurrent `fio` workloads from four clients writing to distinct files. Confirm aggregate throughput scales linearly or identify CPU/disk saturation using `perf top` and `iostat`.

4. **Metadata Performance**: Execute `mdtest` with 10,000 file creates and verify metadata operation rate meets application requirements (typically >1000 ops/sec for general-purpose workloads).

5. **Crash Consistency**: Simulate unclean shutdown during active writes using `killall -9 nfsd` followed by immediate reboot. Verify filesystem consistency post-recovery using `fsck` or `zpool scrub` with zero errors.

6. **Network Fault Tolerance**: Inject 100% packet loss for 30 seconds using `tc netem` and verify clients with hard mounts resume I/O automatically when connectivity restores. Soft mounts should return timely errors to applications.

7. **Block Device Error Handling**: Use `dm-flakey` to inject I/O errors and confirm that redundant storage configurations (ZFS mirror, RAID) successfully serve data from alternate devices without client-visible corruption.

8. **Resource Exhaustion**: Constrain NFS server memory to 2 GiB using cgroups and verify the server continues servicing requests under memory pressure, issuing NFS4ERR_DELAY rather than crashing.

9. **Backup and Restore**: Create a filesystem snapshot during active I/O, intentionally corrupt files, and perform file-level restore from snapshot. Verify restored files match pre-corruption checksums.

10. **Monitoring Integration**: Confirm that SNMP traps or Prometheus metrics correctly export NFS RPC counts, SMB session statistics, and disk I/O latency percentiles for integration with centralized monitoring systems.

This verification checklist, combined with the diagnostic command reference, provides a systematic framework for validating NAS infrastructure correctness, performance, and resilience in production environments. The exercises and diagnostic workflows presented throughout this lab guide equip infrastructure practitioners with the operational expertise to maintain NAS systems that meet stringent reliability and performance service level objectives.
