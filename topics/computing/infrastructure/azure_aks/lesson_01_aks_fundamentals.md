# Lesson 1: Azure Kubernetes Service Fundamentals

## 1. First-Principles Intuition & Invariants

Azure Kubernetes Service represents Microsoft's fully managed implementation of the open-source Kubernetes orchestration platform, designed to abstract away the operational complexity of maintaining control plane infrastructure while preserving the declarative programming model that defines modern cloud-native systems. At its core, AKS embodies a fundamental architectural principle: the separation of the control plane—responsible for scheduling, state reconciliation, and cluster-wide decision-making—from the data plane, which executes actual workload containers on virtual machine node pools that customers provision and manage.

The economic and operational rationale for AKS emerges from the substantial burden of operating a production Kubernetes cluster. A self-managed cluster requires constant vigilance over etcd quorum health, API server high availability, controller manager state machines, and scheduler performance characteristics. The control plane must survive network partitions, handle certificate rotation, maintain upgrade compatibility across minor versions, and process thousands of API requests per second while preserving linearizable consistency guarantees through etcd's Raft consensus protocol. Microsoft assumes this operational burden in AKS, operating the control plane as a multi-tenant shared service with SLA-backed availability guarantees, while customers retain control over the data plane—the actual compute substrate where their applications execute.

This division of responsibility manifests in a clear cost and management model. The AKS control plane incurs no direct compute charges; Microsoft absorbs the cost of API servers, etcd clusters, controller managers, and schedulers as part of the Azure platform offering. Customers pay exclusively for the virtual machines, managed disks, load balancers, and public IP addresses that constitute their node pools and associated networking infrastructure. This creates an immediate financial incentive to optimize node pool utilization and rightsize VM SKU selections, since compute resources represent the dominant cost vector in any AKS deployment.

The architectural invariants that govern AKS cluster behavior derive from Kubernetes' level-triggered control loop semantics. Unlike event-driven systems that react to discrete state changes, Kubernetes controllers continuously observe the current cluster state, compare it against declared desired state stored in etcd, and execute reconciliation actions to eliminate discrepancies. This design choice provides inherent resilience to transient failures—if a reconciliation action fails due to network partition or node failure, the controller will simply retry on its next iteration, typically within seconds. The entire system converges toward declared state through continuous observation and correction rather than through fragile chains of imperative commands.

Within this control loop framework, AKS manages the control plane components as a shared service across multiple customer clusters, deploying API servers, schedulers, and controller managers in dedicated node pools isolated from customer workloads. Each customer cluster receives its own etcd cluster instance to ensure data isolation and eliminate cross-tenant performance interference. The control plane communicates with customer node pools through the Kubernetes API, with nodes running kubelet agents that register themselves with the API server, report node status, and accept pod scheduling assignments. This creates a hub-and-spoke topology where the control plane acts as the authoritative source of truth, and nodes operate as execution agents that continuously reconcile their local state against control plane directives.

The resource abstractions that Kubernetes and AKS expose build upon Linux kernel primitives—namespaces for isolation and cgroups for resource accounting—but wrap them in higher-level declarative specifications that describe desired outcomes rather than low-level system calls. A Pod, the atomic scheduling unit in Kubernetes, encapsulates one or more containers that share a network namespace, enabling localhost communication between co-located processes. Pods exist as ephemeral, cattle-not-pets entities; they can be terminated, rescheduled, or replaced at any moment based on scheduling constraints, resource availability, or node failures. This ephemeral nature forces application architects to externalize state into durable backing services—databases, object stores, message queues—and treat individual pod instances as fungible computational units with no unique identity beyond transient IP addresses.

Deployments introduce replication and declarative lifecycle management atop the Pod abstraction. A Deployment specifies a desired replica count, container images, resource requests, and update strategies, then delegates to a ReplicaSet controller that continuously ensures the specified number of pod replicas exist and match the declared template. This indirection through ReplicaSets enables sophisticated rolling update semantics—gradually replacing old pod versions with new ones while maintaining minimum available capacity—without requiring imperative orchestration scripts. The Deployment controller calculates optimal ReplicaSet transitions, the ReplicaSet controller manages pod lifecycle, and the scheduler places pods onto nodes, creating a layered hierarchy of control loops that compose to deliver higher-level guarantees from simpler building blocks.

Services provide stable network endpoints for ephemeral pod collections, solving the fundamental challenge that pods receive unpredictable IP addresses and can be rescheduled at any moment. A Service defines a selector that matches pods based on labels, then provisions either a cluster-internal virtual IP or an Azure Load Balancer external IP that distributes traffic across all matching pods. The kube-proxy component on each node programs iptables or IPVS rules to implement this load balancing, transforming virtual service IPs into concrete pod IPs through kernel packet filter rules. This creates a stable addressing contract—clients connect to a service IP that never changes, while the underlying pod fleet scales, upgrades, and heals dynamically.

The AKS abstraction layer adds Azure-specific integrations atop these core Kubernetes primitives. When you provision an AKS cluster, Azure Resource Manager creates a dedicated resource group containing the virtual machine scale sets, network security groups, and load balancers that constitute the node pools, while hiding the control plane infrastructure entirely. The cluster identity—a managed identity or service principal—receives delegated permissions to create Azure resources on your behalf, enabling Kubernetes controllers to provision load balancers, persistent disks, and virtual network integrations through Azure APIs. This tight integration means that when you declare a Service of type LoadBalancer in Kubernetes, the cloud controller manager detects this declaration and invokes Azure APIs to provision an Azure Load Balancer with appropriate frontend IP configurations and backend pool memberships, bridging the declarative Kubernetes specification to imperative Azure resource creation.

## 2. Core Architecture & Mechanics

The AKS architecture decomposes into three primary layers: the managed control plane, the customer-provisioned node pools, and the network fabric that connects them. Understanding the precise boundaries and communication patterns across these layers proves essential for diagnosing failures, optimizing performance, and reasoning about security boundaries.

The managed control plane consists of Kubernetes core components that Microsoft operates in a multi-tenant shared infrastructure. The API server acts as the central coordination point, exposing the Kubernetes REST API over HTTPS on a public or private endpoint that customers configure during cluster creation. This API server authenticates requests using Azure Active Directory integration, certificate-based authentication, or bearer tokens, then authorizes them against role-based access control policies stored in etcd. The API server itself maintains no state; it reads from and writes to etcd exclusively, functioning as a stateless gateway that validates, transforms, and persists resource declarations into the cluster's source of truth.

The etcd cluster stores all Kubernetes resources as JSON or Protocol Buffer serialized objects indexed by resource type and namespace, maintaining a monotonically increasing revision number for every write operation. This revision forms the foundation for watch mechanisms—clients establish HTTP long-polling connections to the API server specifying a resource type and optional selector, and the API server streams updates whenever objects matching the watch criteria change. Controllers leverage these watch streams to detect state changes and trigger reconciliation loops without polling, creating an efficient event notification system that scales to clusters with thousands of resources.

The scheduler runs as a leader-elected singleton that observes unscheduled pods—those with `spec.nodeName` unset—and attempts to assign them to nodes based on resource availability, affinity rules, taints, and tolerations. The scheduling algorithm operates in two phases: filtering eliminates nodes that cannot satisfy pod requirements (insufficient CPU, failing health checks, missing labels), then scoring ranks remaining nodes to prefer those with better resource balance, locality, or spread characteristics. Once the scheduler selects a node, it updates the pod's `spec.nodeName` field through the API server, which persists the binding to etcd. The kubelet on the target node observes this binding through its watch stream and begins pulling container images and starting containers.

The controller manager bundles multiple control loops into a single binary, including the ReplicaSet controller, Deployment controller, Service controller, and dozens of others. Each controller establishes watch streams for relevant resource types, maintains local caches synchronized with API server state, and executes reconciliation logic when changes occur. The Deployment controller detects changes to Deployment resources, calculates desired ReplicaSet configurations, and creates or updates ReplicaSets accordingly. The ReplicaSet controller observes ReplicaSets and their associated pods, creating new pods when replica counts fall short and deleting excess pods when counts exceed desired levels. This controller hierarchy decomposes complex behaviors into simple, composable control loops that operate independently yet coordinate through shared state in etcd.

Customer node pools manifest as Azure Virtual Machine Scale Sets (VMSS), providing horizontal scaling capabilities and automatic replacement of failed instances. Each scale set references a specific VM SKU—defining CPU cores, memory, disk throughput, and network bandwidth—and deploys VMs into a designated subnet within the cluster's virtual network. The VMs run a hardened Linux image maintained by Microsoft, containing the kubelet agent, container runtime (containerd by default), and necessary kernel modules for container isolation. During node bootstrap, the kubelet retrieves cluster credentials from Azure Instance Metadata Service, registers itself with the API server, and begins reporting node capacity and allocatable resources.

The kubelet implements the node-side execution contract, continuously synchronizing pod state on its node with desired state declared in the API server. It establishes a watch on pods assigned to its node, then invokes the container runtime to create, start, stop, and delete containers as needed. The kubelet also reports node conditions—disk pressure, memory pressure, PID pressure—and pod status updates back to the API server, enabling scheduler decisions and triggering pod evictions when resources become constrained. This bidirectional communication between kubelet and API server maintains consistency between declared intent and runtime reality across potentially thousands of nodes.

Network connectivity in AKS builds upon Azure Virtual Network (VNet) primitives, with two primary models: kubenet and Azure CNI. The kubenet model assigns pods IP addresses from a separate address space than node VMs, using bridge networking and SNAT (source network address translation) to enable pod-to-pod and pod-to-internet communication. This approach minimizes IP address consumption—only nodes consume VNet IPs—but introduces NAT overhead and complicates network policy enforcement. Azure CNI, the recommended production model, assigns pods IP addresses directly from the VNet subnet, eliminating NAT hops and enabling direct integration with Azure network security groups and user-defined routes. Each node receives a pre-allocated block of IPs from the subnet, with block size determined by the maximum pods per node setting (default 30, configurable up to 250).

The kube-proxy component on each node implements Kubernetes Service networking by programming packet filter rules that intercept traffic destined for Service virtual IPs and redirect it to pod IPs. In iptables mode, kube-proxy generates a chain of iptables rules for each Service, with random probability branching to distribute connections across backend pods. In IPVS mode, kube-proxy programs kernel-level load balancing that avoids iptables traversal overhead and provides more sophisticated scheduling algorithms—round-robin, least-connection, source hashing. Both modes leverage the Linux kernel's connection tracking (`conntrack`) subsystem to maintain session affinity and NAT state for established connections.

Azure load balancer integration exemplifies the cloud controller manager pattern. When you create a Kubernetes Service with `type: LoadBalancer`, the Azure cloud controller manager detects this resource through its watch stream, allocates a public IP address from Azure, provisions an Azure Load Balancer with a frontend IP configuration pointing to that public IP, creates a backend pool containing all cluster node IPs, and configures health probes and load balancing rules that distribute incoming traffic across nodes. The kube-proxy on each node then receives this traffic on a NodePort and redirects it to pods using the same iptables or IPVS mechanisms used for ClusterIP services. This two-layer load balancing—Azure Load Balancer distributing to nodes, then kube-proxy distributing to pods—creates redundancy but introduces additional latency hops.

Persistent storage in AKS leverages Azure Managed Disks and Azure Files through the Container Storage Interface (CSI) driver model. When you create a PersistentVolumeClaim requesting storage, the Azure Disk CSI controller provisions an Azure Managed Disk with specified size, performance tier (Standard HDD, Standard SSD, Premium SSD, Ultra Disk), and redundancy level (locally redundant or zone redundant). The controller creates a PersistentVolume representing this disk, binds it to the claim, and updates the PV with Azure-specific volume attributes like disk URI and resource group. When a pod referencing this PVC gets scheduled, the CSI node plugin on the target node invokes Azure APIs to attach the managed disk to the VM, waits for kernel block device detection, formats the disk if necessary, and mounts it into the pod's filesystem namespace at the specified path. This attachment process requires exclusive access—an Azure Managed Disk can only attach to one VM at a time—enforcing single-writer semantics for block storage.

## 3. High-Performance Optimization & Failure Modes

Optimizing AKS deployments requires understanding the resource allocation and scheduling mechanics that govern pod placement and cluster utilization. The scheduler makes decisions based on two resource dimensions: requests and limits. A request represents the guaranteed resources a pod requires; the scheduler only places pods on nodes with sufficient unreserved capacity to satisfy all requests. A limit represents the maximum resources a pod may consume; the kubelet enforces limits through cgroups, throttling CPU usage when pods exceed CPU limits and killing pods that exceed memory limits. This distinction enables overcommitment—scheduling pods such that the sum of limits exceeds node capacity—while guaranteeing that requested resources remain available.

Effective resource requests require measuring actual application utilization under representative load. Undersized requests waste cluster capacity by forcing the scheduler to distribute pods across more nodes than necessary, increasing costs. Oversized requests cause pod scheduling failures when clusters lack nodes with sufficient unreserved capacity, even when actual utilization remains low. The Vertical Pod Autoscaler (VPA) analyzes historical resource usage and recommends request values that balance utilization and reliability, though applying these recommendations requires pod restarts. The Horizontal Pod Autoscaler (HPA) complements VPA by scaling replica counts based on observed metrics—CPU utilization, memory usage, or custom metrics—adjusting the number of pod instances to meet demand while VPA adjusts per-pod resource allocations.

Node pool architecture choices significantly impact cluster economics and failure domain isolation. A single large node pool containing high-CPU VMs may prove cost-effective for CPU-bound workloads but wastes resources when pods require high memory-to-CPU ratios. Multiple specialized node pools—one for CPU-intensive workloads using compute-optimized VMs, another for memory-intensive workloads using memory-optimized VMs, and a third for GPU workloads—enable precise SKU matching to workload characteristics. Node selectors and taints/tolerations direct pods to appropriate node pools, preventing memory-intensive pods from consuming valuable CPU capacity on compute-optimized nodes.

Autoscaling node pools through the Cluster Autoscaler automates capacity management by observing pending pods—those unschedulable due to insufficient cluster resources—and provisioning additional nodes from the underlying VMSS. The autoscaler evaluates scale-up requirements every 10 seconds by default, selecting the node pool and VM count that satisfies pending pods while minimizing cost. Scale-down occurs more conservatively, only removing nodes that have run below 50% utilization for at least 10 minutes and contain only pods that can be rescheduled elsewhere. This asymmetric timing prevents thrashing while ensuring rapid response to demand spikes. The autoscaler respects pod disruption budgets and node affinity constraints, refusing to scale down nodes if doing so would violate availability guarantees or break pod scheduling requirements.

Network performance optimization depends on minimizing hops between communicating pods and leveraging high-throughput VM SKUs. Azure CNI with pod IP addresses from the VNet enables direct pod-to-pod communication without NAT, reducing latency and eliminating conntrack state overhead. Placing frequently communicating pods on the same node through pod affinity rules eliminates network hops entirely, leveraging kernel-local loopback or shared memory communication paths. For workloads requiring sustained high throughput—streaming data pipelines, distributed databases—selecting accelerated networking-capable VM SKUs offloads packet processing to FPGA-based SmartNICs, bypassing the hypervisor networking stack and achieving line-rate bandwidth with single-digit microsecond latency.

Persistent volume performance tuning requires matching disk performance tiers to I/O patterns. Standard SSD provides 500-6000 IOPS depending on disk size, suitable for general-purpose workloads with moderate I/O requirements. Premium SSD scales from 120-20000 IOPS based on disk size, with lower latency characteristics ideal for databases and transaction processing systems. Ultra Disk enables independent specification of disk size, IOPS (up to 160,000), and throughput (up to 4 GB/s), allowing precise matching to application requirements without overprovisioning capacity. Monitoring disk throttling metrics through Azure Monitor reveals when applications exceed provisioned IOPS or throughput limits, indicating opportunities to upgrade to higher-performance tiers or implement application-level caching.

Control plane reliability depends on proper API rate limiting and efficient watch semantics. The API server enforces per-client request rate limits to prevent individual clients from monopolizing control plane capacity. Controllers and operators that list all resources of a type periodically—instead of maintaining long-running watch connections—impose disproportionate load on the API server and etcd. Informers, the client library abstraction that implements watch-based caching, establish a single watch connection and maintain an in-process cache synchronized with API server state, dramatically reducing API load for applications that query resources frequently. Custom controllers should always use informers rather than polling to minimize control plane impact.

Node failure recovery proceeds automatically through multiple mechanisms. The node controller detects when nodes stop reporting heartbeats (default 40-second timeout), marks them as `NotReady`, and after five minutes begins evicting pods from the unresponsive node. The VMSS health probe detects failed VM instances and automatically replaces them, while the kubelet on the replacement node registers with the control plane and becomes eligible for pod scheduling. Pods evicted from failed nodes get rescheduled by their ReplicaSet or StatefulSet controllers onto healthy nodes, with startup time determined by image pull duration and application initialization logic. Minimizing this recovery time requires preloading container images across nodes and implementing fast startup paths in application code.

Cluster upgrade failures typically stem from version skew incompatibilities or custom resource definition conflicts. AKS supports N-1 version skew between control plane and node pools—if the control plane runs 1.28, node pools may run 1.27 or 1.28—but not N-2 skew. Attempting to upgrade nodes more than one minor version behind the control plane fails validation. Incremental upgrades, advancing one minor version at a time, avoid this failure mode. Custom resources defined by operators and extensions require API version compatibility; upgrading Kubernetes may deprecate API versions that existing CRDs target, causing application controllers to crash during startup. Auditing deprecated API usage through tools like Pluto or kubectl-convert identifies these incompatibilities before upgrades.

Network policy enforcement failures often arise from CNI and policy plugin misconfigurations. Azure CNI requires enabling network policy support during cluster creation—retrofitting network policies onto existing clusters without this setting requires cluster recreation. The Calico and Azure policy plugins interpret identical NetworkPolicy resources differently in edge cases, particularly around default deny behavior and namespace selectors. Testing network policies in isolated namespaces and validating blocked connections through curl probes or dedicated test pods verifies policy correctness before applying them to production workloads.

Disk attachment timeouts during pod startup typically indicate either VMSS overscaling—attempting to attach more disks than a VM SKU supports—or Azure API throttling during burst disk creation. Each VM SKU imposes a maximum data disk count: Standard_D2s_v3 supports 4 disks, while Standard_D64s_v3 supports 32. Exceeding these limits causes attachment operations to fail. Reducing pod density per node or using larger VM SKUs with higher disk limits resolves this failure mode. Azure Disk CSI driver logs contain detailed error messages and retry attempts that diagnose attachment failures and API throttling responses.

Image pull errors represent one of the most common pod startup failures, caused by network timeouts, registry authentication issues, or missing images. AKS nodes pull images from container registries over public internet unless private link integration is configured, making them susceptible to transient network failures. Integrating Azure Container Registry with AKS through managed identity authentication eliminates credential management overhead and enables seamless private registry access. Configuring image pull secrets for third-party registries requires distributing credentials to every namespace where pods reference those registries, introducing operational complexity that private registries with integrated authentication avoid.

Resource exhaustion at the node level manifests through kubelet eviction events. When disk usage exceeds 85% of total capacity, the kubelet marks the node as `DiskPressure` and begins evicting pods, prioritizing those consuming the most disk space. Memory pressure triggers similar evictions when available memory drops below 100MB, killing pods with the highest memory usage relative to their requests. These evictions cause application disruptions that proper resource requests and limits prevent. Monitoring node allocatable resources and maintaining headroom for system daemons and kernel buffers ensures consistent pod scheduling without triggering emergency evictions.

Cluster autoscaler unschedulable pod states require investigating whether pending pods specify resource requests that no available node pool can satisfy, reference node selectors or taints that no nodes match, or violate pod affinity/anti-affinity constraints. The autoscaler logs detail why it cannot satisfy particular pods, typically indicating either that maximum node pool size has been reached or that no expansion would schedule the pending pod due to incompatible requirements. Adjusting pod specifications to relax constraints or creating specialized node pools with appropriate labels and taints resolves these scheduling deadlocks.
