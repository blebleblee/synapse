# Lesson 3: Intermediate Code Generation and Optimization

## 1. First-Principles Intuition & Invariants

The journey from source code to executable machine instructions passes through a crucial intermediate phase where abstraction and architecture collide. After the compiler frontend has parsed the source program, performed semantic analysis, and validated types, it must translate the high-level abstract syntax tree into a form amenable to machine-independent optimization and subsequent code generation. This intermediate representation sits at the heart of every modern optimizing compiler, serving as the bridge between language semantics and hardware execution.

The fundamental challenge lies in reconciling two competing forces. On one hand, we require an intermediate representation that faithfully preserves the semantics of the source program, capturing control flow, data dependencies, and side effects with sufficient fidelity that no legal program behavior is altered. On the other hand, we demand a representation that exposes optimization opportunities, making data flow explicit, control structure transparent, and redundancy visible. The tension between these requirements has driven decades of compiler research, from the early days of FORTRAN optimization through the sophisticated middle-ends of LLVM and GCC.

Three-address code emerged as the dominant intermediate representation precisely because it strikes this balance with elegant simplicity. Each instruction in three-address code performs at most one operation, storing the result in a destination while reading from at most two operands. This constraint forces the decomposition of complex expressions into sequences of simple operations, each with explicit temporary storage. The representation mirrors the register-based architecture of modern processors while remaining sufficiently abstract that machine-specific details like register allocation, instruction scheduling, and calling conventions can be deferred to later compilation phases.

Consider the high-level expression `a = b * c + d * e`. In three-address form, this explodes into a sequence of primitive operations: first `t1 = b * c`, then `t2 = d * e`, and finally `a = t1 + t2`. Each temporary variable `t1` and `t2` represents an abstract storage location that will eventually map to either a register or a memory location. This decomposition exposes the internal parallelism within the expression, revealing that the two multiplication operations have no data dependencies and could potentially execute concurrently on a superscalar processor. The explicit temporaries also make data flow transparent, allowing optimization passes to track where values are produced, where they are consumed, and when they become dead.

The control flow graph provides the structural scaffold upon which optimization algorithms operate. By representing the program as a directed graph where nodes correspond to basic blocks and edges represent control flow transitions, we transform the linear sequence of instructions into a topology that exposes dominance relationships, loop structures, and irreducible control flow. A basic block is a maximal sequence of instructions with a single entry point at the beginning and a single exit point at the end, guaranteeing that if the first instruction executes, all subsequent instructions in the block execute in sequence without branching or external entry. This property is fundamental because it allows optimization algorithms to reason about instruction sequences as atomic units, applying transformations that preserve semantics within the block while delegating inter-block concerns to graph-level analysis.

Data flow analysis provides the semantic foundation for optimization by computing what properties hold at each program point. Unlike control flow analysis, which concerns itself solely with the topology of execution paths, data flow analysis propagates semantic facts through the program, answering questions like: Which variables are live at this program point? Which definitions reach this use? Which expressions have already been computed along all paths? These questions cannot be answered by examining individual instructions or even individual basic blocks in isolation. Instead, they require iterative fixed-point computation over the control flow graph, propagating information forward or backward until no further changes occur.

The mathematical structure underlying data flow analysis is that of a lattice with a monotone transfer function. Each program point is associated with a lattice element representing the semantic property of interest, and each instruction applies a transfer function that transforms input lattice elements to output lattice elements. The join operation at control flow merge points combines information from multiple predecessors, and the entire computation proceeds by iteratively applying transfer functions and joins until the lattice values stabilize. The termination and correctness of this process follow from the finite height of the lattice and the monotonicity of the transfer functions, guarantees that hold regardless of the complexity of the program's control flow.

Optimization transforms leverage these foundational analyses to improve program performance without altering semantics. Local optimizations operate within single basic blocks, exploiting the simple control flow to apply algebraic simplifications, constant folding, and strength reduction. Global optimizations operate across basic blocks, using data flow information to eliminate redundant computations, move loop-invariant code, and propagate constants through conditional branches. The distinction between local and global is not merely one of scope but reflects fundamentally different algorithmic approaches: local optimizations typically involve pattern matching and greedy rewriting, while global optimizations require sophisticated fixed-point computation and may need to iterate multiple times before reaching a stable optimized form.

The correctness invariant that governs all optimization is semantic preservation: the optimized program must exhibit the same observable behavior as the original program for all valid inputs. This constraint is both simpler and more subtle than it appears. It is simpler because we need not preserve the internal execution trace, only the externally visible effects such as output, termination behavior, and observable side effects to memory or I/O. It is more subtle because modern languages provide escape hatches like volatile variables, atomic operations, and inline assembly that expose low-level execution details, constraining what transformations remain valid. A compiler bug that introduces miscompilation is catastrophic precisely because it violates this fundamental contract, potentially causing silent data corruption or exploitable security vulnerabilities in production systems.

Performance considerations drive the engineering tradeoffs in optimization pass ordering and aggressiveness. Optimization is fundamentally a compile-time investment that pays dividends at runtime, but the return on investment exhibits diminishing returns. Early optimization passes often expose opportunities for subsequent passes, creating positive feedback where redundancy elimination enables constant propagation which enables dead code elimination. However, this virtuous cycle has limits: beyond a certain point, additional optimization iterations yield marginal performance improvements while dramatically increasing compile time. Production compilers therefore implement optimization levels that trade off compilation speed against runtime performance, from `-O0` which performs minimal optimization for fast compilation and debuggability, through `-O2` which enables most profitable optimizations, to `-O3` which aggressively optimizes even at the cost of code size and compilation time.

## 2. Core Architecture & Mechanics

Three-address code forms the operational substrate of the intermediate representation. Each quadruple consists of an operator, up to two source operands, and a destination. The general form `x = y op z` captures binary operations, while unary operations take the form `x = op y`, and copy operations simplify to `x = y`. Control flow instructions break this pattern, introducing conditional jumps `if x relop y goto L` and unconditional jumps `goto L` that alter the program counter rather than computing values. Function calls require special three-address forms that handle argument passing, the call itself, and return value retrieval.

The translation from abstract syntax tree to three-address code proceeds through syntax-directed translation, where each grammar production is associated with semantic actions that emit intermediate code. For an expression like `a + b * c`, the parser constructs a tree with the addition at the root and the multiplication as the right child. The code generation traversal visits this tree in post-order, ensuring that operands are evaluated before operators. When visiting the multiplication node, the code generator allocates a fresh temporary `t1` and emits `t1 = b * c`. When visiting the addition node, it allocates another temporary `t2` and emits `t2 = a + t1`. The final result resides in `t2`, which becomes the operand for any enclosing expression or the right-hand side of an assignment.

Array accesses and pointer dereferences require address computation instructions that make memory access explicit. A reference to `a[i]` translates to an address computation `t1 = addr(a) + i * sizeof(element)` followed by a dereference `t2 = *t1`. Multi-dimensional arrays require nested address calculations, with each dimension contributing a multiplicative factor. This explicit representation of address arithmetic exposes opportunities for strength reduction, where multiplications can be converted to additions within loops, and for bounds check elimination, where static or dynamic analysis proves that array indices remain within valid ranges.

Control flow translation transforms structured control constructs into explicit jumps and labels. An if-statement `if (condition) then S1 else S2` translates to a conditional jump that evaluates the condition, jumps to the else-label if false, executes S1, jumps unconditionally to the end-label, places the else-label, executes S2, and finally places the end-label. While-loops `while (condition) do S` translate to a begin-label, evaluation of the condition, a conditional jump to the end-label if false, execution of S, an unconditional jump back to the begin-label, and finally the end-label. This translation makes control flow explicit through labels and jumps, preparing the code for control flow graph construction.

The control flow graph emerges from partitioning the linear three-address code into basic blocks. The algorithm identifies leader instructions that begin basic blocks: the first instruction in the program, any target of a jump, and any instruction immediately following a jump. Each basic block extends from its leader to the instruction immediately before the next leader. Edges connect basic blocks according to control flow: a conditional jump creates edges to both the fall-through successor and the jump target, an unconditional jump creates a single edge to the target, and sequential flow creates an edge to the immediately following block. Function calls typically create edges both to the call target and to the return continuation, though intraprocedural analysis may treat calls as single instructions.

```
Original Code:
  1: x = 0
  2: y = 1
  3: if x < 10 goto 8
  4: y = y * 2
  5: x = x + 1
  6: if y < 100 goto 10
  7: goto 11
  8: x = x + 5
  9: goto 3
 10: y = y + 3
 11: return y

Basic Blocks:
  B1: [1, 2, 3]         Entry block
  B2: [4, 5, 6]         True branch of outer if
  B3: [8, 9]            False branch of outer if
  B4: [10]              True branch of inner if
  B5: [11]              Exit block (implicit 7 lands here)

Control Flow Graph:
  B1 → B2 (true), B1 → B3 (false)
  B2 → B4 (true), B2 → B5 (false)
  B3 → B1 (back edge)
  B4 → B5
  B5 → exit
```

Data flow analysis for live variables proceeds backward through the control flow graph, computing which variables are live at the exit of each basic block. A variable is live at a program point if there exists a path from that point to a use of the variable that does not pass through a definition. The backward data flow equations capture this intuition: the live-out set of a block equals the union of the live-in sets of all successors, and the live-in set equals the union of the live-out set minus definitions plus uses within the block. Symbolically, `in[B] = use[B] ∪ (out[B] - def[B])` and `out[B] = ∪_{S ∈ succ[B]} in[S]`.

The iterative algorithm initializes all in and out sets to empty, then repeatedly applies the data flow equations until no changes occur. Each iteration examines every basic block, recomputing its in and out sets based on current information from successors and the block's use and def sets. Convergence is guaranteed because the sets can only grow, never shrink, and are bounded by the finite set of program variables. In practice, visiting blocks in reverse post-order relative to the control flow graph accelerates convergence by propagating information backward along likely execution paths first.

Reaching definitions analysis proceeds forward through the control flow graph, computing which assignments could possibly reach each program point without an intervening reassignment. A definition `x = ...` at program point p reaches point q if there exists a path from p to q along which x is not redefined. The forward data flow equations mirror the structure of live variables: the out set of a block equals the union of the block's generated definitions plus the in set minus killed definitions, `out[B] = gen[B] ∪ (in[B] - kill[B])`, while the in set equals the union of out sets of all predecessors, `in[B] = ∪_{P ∈ pred[B]} out[P]`.

Available expressions analysis determines which expressions have been computed along all paths reaching a program point and have not been invalidated by subsequent assignments. An expression `x + y` is available at point p if every path from the entry to p evaluates `x + y` and neither x nor y is subsequently reassigned. This analysis enables common subexpression elimination by identifying redundant computations. The data flow equations use intersection rather than union at merge points because an expression is available only if it is available along all incoming paths: `in[B] = ∩_{P ∈ pred[B]} out[P]` and `out[B] = gen[B] ∪ (in[B] - kill[B])`.

Local optimization within basic blocks exploits the absence of control flow to apply transformations greedily. Constant folding evaluates expressions with known constant operands at compile time, replacing `t1 = 2 + 3` with `t1 = 5`. Algebraic simplification applies identities like `x + 0 = x`, `x * 1 = x`, `x * 0 = 0`, and `x - x = 0`. Strength reduction replaces expensive operations with cheaper equivalents, converting `x * 2` to `x + x` or `x << 1`, and `x / 8` to `x >> 3` when x is unsigned. Copy propagation replaces uses of a variable with the source of a copy, transforming the sequence `t1 = x; t2 = t1 + y` into `t2 = x + y`, eliminating the temporary.

Peephole optimization examines small sliding windows of consecutive instructions, applying pattern-based transformations. A peephole window typically spans two to four instructions, searching for inefficiency patterns like redundant loads and stores, unnecessary jumps to jumps, or algebraic simplifications that span multiple instructions. The optimization replaces matched patterns with improved instruction sequences, then slides the window forward. The process continues until no further matches occur within any window.

Dead code elimination removes instructions whose results are never used. An assignment `x = ...` is dead if x is not live at that point. Within a basic block, dead code elimination works backward from the end, maintaining a set of live variables. When encountering an assignment to a dead variable, the instruction is deleted. When encountering a use of a variable, that variable is added to the live set. This local analysis extends naturally to global dead code elimination by first computing live variable information for the entire procedure, then removing assignments to variables that are not live-out from their defining blocks.

Common subexpression elimination leverages available expressions analysis to identify redundant computations. When encountering an expression `x + y` where that expression is available, the compiler knows some earlier block computed the same expression into a temporary, say `t1 = x + y`. The current computation can be replaced with a copy `t2 = t1`, eliminating the redundant arithmetic. Global common subexpression elimination requires careful handling of control flow merge points, inserting copy instructions along paths where the expression was not previously computed to ensure the optimized program remains semantically equivalent.

Loop invariant code motion identifies computations within loops whose operands do not change across iterations, hoisting such computations to the loop preheader. A loop preheader is a basic block that dominates all loop entries and is executed exactly once before the loop begins. Code motion proceeds by identifying the natural loops in the control flow graph through dominator analysis, constructing preheaders if they do not exist, then examining each instruction within the loop to determine whether its operands are invariant. An operand is invariant if it is defined outside the loop or is itself the result of a loop-invariant computation. Hoisting an invariant computation is safe only if the instruction dominates all loop exits, ensuring it would have executed on all iteration paths regardless of early exit.

Induction variable analysis identifies variables that vary systematically with loop iterations, forming arithmetic progressions. The canonical induction variable is the loop counter itself, incremented by a constant stride on each iteration. Derived induction variables are computed as linear functions of basic induction variables, such as array index calculations. Recognizing induction variables enables strength reduction within loops, replacing multiplications with additions by maintaining the derived variable incrementally. For example, if `i` is a basic induction variable incremented by 1 and the loop computes `a[i]`, the address calculation `t = base + i * sizeof(element)` can be strength-reduced to incrementing `t` by `sizeof(element)` on each iteration.

Loop unrolling replicates the loop body multiple times, reducing loop overhead and exposing additional optimization opportunities. Unrolling by a factor of four transforms a loop with a single statement `S` into a loop containing `S; S; S; S` with the iteration count divided by four and a cleanup loop handling the remainder. The replicated statements become distinct in the intermediate representation, allowing instruction scheduling to interleave operations from different iterations and breaking false dependencies. Unrolling trades increased code size for reduced branch overhead, better instruction-level parallelism, and improved register allocation through software pipelining.

Scalar replacement of aggregates converts structure field accesses into scalar temporaries when the structure does not escape the function. If a local structure `s` has fields `x` and `y` accessed repeatedly within a function, and the address of `s` is never taken, the compiler can allocate scalar temporaries `s_x` and `s_y` to hold the field values, replacing field accesses with scalar operations. This transformation eliminates memory traffic, exposing the values to register allocation and enabling further optimization through data flow analysis that would otherwise be obscured by memory aliasing.

Function inlining replaces a call site with a copy of the called function's body, eliminating call overhead and exposing interprocedural optimization opportunities. Inlining proceeds by copying the callee's intermediate representation into the caller at the call site, renaming local variables to avoid conflicts, replacing formal parameters with actual arguments, and adjusting return statements to branch to the continuation point. Aggressive inlining can dramatically improve performance by enabling constant propagation, dead code elimination, and specialization based on calling context. However, it increases code size and compile time, and excessive inlining can degrade instruction cache performance. Modern compilers use heuristics based on function size, call frequency profiling, and optimization level to guide inlining decisions.

Constant propagation tracks constant values through data flow, replacing variable uses with their known constant values. Sparse conditional constant propagation extends this by simultaneously tracking control flow reachability, recognizing that some branches are never taken when conditions are constant. The algorithm maintains a worklist of basic blocks and variable-value pairs, propagating constants through assignments and evaluating branch conditions to prune unreachable code. When a variable is assigned different constants along different paths, it is marked as non-constant. The result is a maximally precise constant propagation that eliminates unreachable code exposed by constant conditions.

## 3. High-Performance Optimization & Failure Modes

The compilation pipeline architecture determines how optimization passes compose and interact. Modern compilers organize passes into phases: early optimizations operate on high-level intermediate representation preserving language semantics and enabling further lowering; middle-end optimizations perform the majority of machine-independent transformations; and late optimizations work on low-level representations close to machine code, incorporating target-specific knowledge. Within each phase, pass ordering matters significantly. Running constant propagation before dead code elimination exposes more dead code because propagating constants can reduce conditional branches to unconditional jumps, making entire basic blocks unreachable. Running dead code elimination before common subexpression elimination can enable further CSE because removing dead stores may cause more expressions to become available.

The fixed-point iteration strategy governs when optimization converges. Some transformations enable others in cascading fashion: inlining exposes context-specific constant arguments, constant propagation enables constant folding, constant folding enables dead branch elimination, and dead branch elimination enables further inlining of previously unknown call targets. Compilers typically iterate optimization passes multiple times, either running individual passes to fixed-point or executing entire pass sequences multiple times. LLVM implements a pass manager that reruns passes when profitability heuristics suggest further improvement is likely, while GCC uses a fixed sequence of pass repetitions tuned through empirical benchmarking.

Alias analysis fundamentally constrains optimization aggressiveness by determining whether two memory references may overlap. A conservative alias analysis assumes all pointers may alias, preventing code motion across any memory operation. Precise alias analysis enables aggressive optimization but requires sophisticated interprocedural analysis and may still resort to conservative assumptions in the presence of unsafe casts or external code. Type-based alias analysis leverages language type systems to prove that pointers to incompatible types cannot alias, a sound assumption in C and C++ when strict aliasing rules are followed. Flow-sensitive alias analysis tracks pointer relationships through the control flow graph, computing may-alias and must-alias sets at each program point.

Optimization for cache performance addresses the memory hierarchy explicitly, transforming code to improve spatial and temporal locality. Loop tiling partitions iteration spaces into blocks that fit in cache, ensuring that once data is loaded into cache it is reused maximally before eviction. Loop fusion combines adjacent loops operating on the same data to improve temporal locality, while loop distribution splits loops to reduce register pressure or enable vectorization. Array padding adjusts data structure layouts to avoid cache conflicts where independent data structures map to the same cache sets, causing unnecessary evictions.

Profile-guided optimization leverages runtime profiling data to guide compilation decisions. A profile-guided compilation workflow first compiles the program with instrumentation that records branch frequencies, function call counts, and value distributions. The instrumented binary runs on representative workloads, writing profile data to disk. The compiler then recompiles the program using the profile data to guide inlining decisions, optimize hot loops aggressively while leaving cold code unoptimized, and perform trace scheduling that linearizes frequently executed paths. Profile data enables optimistic optimizations that assume common-case behavior, with fallback paths handling rare cases.

Vectorization transforms scalar code into SIMD instructions that operate on multiple data elements simultaneously. Automatic vectorization for loops requires proving that iterations are independent, determining alignment properties of memory accesses, and handling loop bounds that are not multiples of the vector length. The vectorizer replaces scalar operations with vector equivalents, generating vector loads, arithmetic operations, and stores. Peeling iterations from loop beginnings or endings may be necessary to achieve alignment or handle remainder iterations. Modern compilers leverage SIMD instruction sets like SSE, AVX, and NEON, selecting instruction variants based on target architecture capabilities and optimization settings.

Optimization failure modes arise from incorrect alias analysis, inadequate profiling data, or transformations that degrade performance on specific microarchitectures. Aggressive loop unrolling can overflow instruction caches, causing performance degradation that outweighs reduced loop overhead. Inlining every small function can bloat code size to the point where the working set no longer fits in instruction cache. Speculative code motion can introduce computations on paths where they would not previously execute, slowing cold paths. Optimization bugs arise from incorrect data flow analysis, improper handling of aliasing or volatile variables, or failure to preserve exception semantics or memory ordering constraints.

Debugging optimized code presents unique challenges because the relationship between source code and generated code becomes obscured. Variables may be optimized away entirely, residing only in registers or being recomputed on demand. Control flow transformations like inlining, tail call optimization, and code motion scramble the execution trace. Modern compilers emit debug information that maps machine code back to source locations and tracks variable locations through register allocation and code motion, but this debug information is necessarily approximate. Disabling optimization for debugging sacrifices performance and may mask timing-dependent bugs, while debugging optimized code requires understanding the transformations the compiler applied.

Compilation time scalability limits the complexity of optimization algorithms that can be deployed in production compilers. While theoretically optimal algorithms exist for certain optimization problems, they often have exponential worst-case complexity. Production compilers therefore use heuristics and approximations that run in polynomial time. Data flow analysis typically runs in time proportional to the product of the number of basic blocks and the number of variables, which remains tractable for functions of reasonable size. Register allocation via graph coloring is NP-complete, so compilers use greedy heuristics or iterative improvement. Instruction scheduling is also NP-complete, leading to list scheduling algorithms with polynomial complexity and good empirical results.

Interprocedural optimization extends analysis and transformation across function boundaries, enabling context-sensitive constant propagation, cross-function inlining, and whole-program dead code elimination. Summary-based interprocedural analysis computes concise summaries of each function's behavior, such as which global variables it may modify or which parameters it reads, then uses these summaries when analyzing callers. Call graph construction identifies all possible call targets, handling direct calls easily but requiring complex analysis for indirect calls through function pointers or virtual dispatch. Whole-program optimization requires link-time visibility of all code, an assumption violated by dynamic linking and separate compilation, leading to link-time optimization frameworks that defer final optimization until all object files are available.

The phase ordering problem reflects the fundamental tension between local and global decision-making in optimization. Each pass makes locally optimal decisions based on the current program state, but the optimal sequence and configuration of passes depends on complex interactions that are difficult to predict statically. Machine learning approaches have been applied to learn optimization pass orderings from large corpora of programs and performance measurements, though traditional hand-tuned pass sequences remain competitive. The problem is exacerbated by the exponential search space of possible pass orderings and configurations, making exhaustive search infeasible even for moderate-sized programs.

Security implications of compiler optimization arise when transformations eliminate code that developers intended for security purposes. Zeroing sensitive memory after use may be optimized away as a dead store if the memory is never subsequently read, leaving secrets in memory longer than intended. Timing-sensitive code for cryptographic constant-time operations can be disrupted by instruction scheduling or code motion. Volatile qualifiers and memory barriers provide mechanisms to constrain optimization, but require careful use and compiler support. Modern compilers implement options like `-fno-delete-null-pointer-checks` and `-fno-strict-overflow` to disable optimizations that could introduce security vulnerabilities when code violates language rules the compiler assumes hold.

The intermediate representation design space offers numerous alternatives beyond three-address code. Static single assignment form ensures each variable is assigned exactly once, simplifying data flow analysis by making def-use chains explicit through φ-functions at control flow merge points. Continuation-passing style makes control flow explicit by representing every function call as a tail call passing a continuation. Sea-of-nodes representations eliminate instruction ordering within basic blocks, representing only data dependencies and allowing instruction scheduling maximal freedom. The choice of intermediate representation profoundly affects which optimizations are easy to implement, how compilation time scales, and what semantic properties are preserved or exposed.

Production compiler implementations like LLVM and GCC embody decades of optimization research translated into robust engineering practice. LLVM's intermediate representation is a low-level typed assembly language with SSA form, explicit control flow, and rich type information. The LLVM pass infrastructure enables modular optimization passes that register dependencies and can be composed flexibly. GCC's GIMPLE representation similarly uses SSA form and provides multiple intermediate language levels from high-level GIMPLE close to source code through to low-level GIMPLE near machine code. Both compilers implement hundreds of optimization passes, carefully ordered and tuned through extensive benchmarking on standard benchmark suites like SPEC CPU and real-world applications.

The correctness verification of compiler optimizations remains an active research challenge, with formal methods providing mathematical proofs that transformations preserve semantics. Translation validation proves that specific compilation runs preserve semantics by constructing logical formulas relating source and target programs, then using SMT solvers to verify equivalence. Compiler verification proves once that the compiler implementation itself is correct, as exemplified by the CompCert verified C compiler. However, the tension between verification cost and optimization aggressiveness means most production compilers prioritize performance and compilation speed over formal correctness guarantees, relying instead on extensive testing and differential testing against multiple compilers.
