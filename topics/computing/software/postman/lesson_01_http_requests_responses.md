# Lesson 1: HTTP Requests, Responses, and Request Building Mechanics

## 1. First-Principles Intuition & Invariants

HTTP is a stateless, application-layer protocol built on a request-response model so simple in concept and so consequential in practice that understanding it deeply separates engineers who debug APIs quickly from those who guess. Before Postman can be understood as a tool, HTTP must be understood as a contract. That contract is defined by a series of RFCs, the most authoritative being RFC 9110 (HTTP Semantics, 2022), which superseded RFC 7231 and established the canonical definitions for methods, status codes, and content negotiation that every conforming client and server must honor.

The fundamental invariant of HTTP is this: a client sends a request message, and a server returns a response message. These messages share a common wire format. Each consists of a start-line, zero or more header fields organized as name-value pairs delimited by CRLF (`\r\n`), a mandatory blank line marking the end of the header section, and an optional message body. This grammar does not change between HTTP/1.1, HTTP/2, and HTTP/3; what changes is the framing and transport layer underneath. HTTP/1.1 transmits messages as human-readable text over a persistent TCP connection. HTTP/2 encodes the same semantic structure into binary frames multiplexed over a single TLS stream, eliminating head-of-line blocking at the application layer. HTTP/3 replaces TCP entirely with QUIC, a UDP-based transport that bakes TLS 1.3 into the handshake and eliminates TCP's stream-level head-of-line blocking at the transport layer. When you issue a request in Postman, it speaks HTTP/1.1 or HTTP/2 depending on the server's negotiated ALPN extension, but the semantics you configure in the UI map directly to the RFC wire format regardless of which version carries the message.

The request method is the most load-bearing field in the start-line. RFC 9110 defines methods not merely as strings, but as properties with formal behavioral constraints: safety, idempotency, and cacheability. A method is **safe** if it is defined to have no observable side effects on server state, meaning the client bears no responsibility for initiating it. `GET`, `HEAD`, `OPTIONS`, and `TRACE` are safe. A method is **idempotent** if identical repeated requests produce the same server-side effect as a single request. All safe methods are idempotent, but `PUT` and `DELETE` are idempotent without being safe: a `PUT` to `/users/42` with the same payload twice results in the same resource state as doing it once, but the first call does change state. `POST` is neither safe nor idempotent, which is why submitting an order form twice creates two orders. `PATCH` is neither safe nor idempotent in the general case, though a well-designed patch document using JSON Merge Patch (RFC 7396) can be made idempotent in practice by the application.

These properties are not merely academic taxonomy. They govern proxy behavior, CDN edge caching, browser retry logic, and load balancer health check semantics. When a network proxy retries a timed-out request, it may only do so safely if the method is idempotent. Postman's retry and test-runner behaviors respect these distinctions implicitly, and an engineer who understands them will design collections and test suites that model reality instead of fighting it.

Headers encode the metadata that governs how the message body is to be interpreted, what formats the client can accept, what credentials are being presented, and how the connection should be managed. The `Content-Type` header on a request body is not a hint; it is a contract declaration. If you send `Content-Type: application/json` and your body is malformed JSON, the server is entitled to return `400 Bad Request` without inspecting the payload further, and many production frameworks do exactly that. The `Accept` header on the request is the client's negotiation bid: it tells the server which media types are acceptable for the response, expressed as a prioritized list using quality values (`q=`). `Accept: application/json, text/html;q=0.9, */*;q=0.5` means the client prefers JSON, will accept HTML with slightly lower preference, and will accept anything else as a last resort. `Content-Negotiation` is the server's corresponding obligation to honor that preference, and when it fails to do so, debugging the resulting content mismatch without understanding this invariant is effectively impossible.

The URL anatomy deserves equal precision. A fully specified URL contains a scheme (`https`), an authority (`api.example.com:443`), a path (`/v2/users`), an optional query string (`?page=2&limit=50`), and an optional fragment (`#section`). The fragment is never sent to the server; it is a purely client-side navigation construct that HTTP does not transmit. Query parameters are percent-encoded by convention (RFC 3986), meaning any character outside the unreserved character set must be encoded as `%XX` where `XX` is the character's hexadecimal octet value. A space becomes `%20`, a `+` in a query string is historically interpreted as a space in `application/x-www-form-urlencoded` encoding but means a literal `+` in path segments. These distinctions matter when debugging authentication signatures, HMAC payloads, and OAuth 1.0a request canonicalization.

## 2. Core Architecture & Mechanics

Postman models the HTTP request-response cycle as a first-class data structure it calls a **Request**. This is not just a UI convenience; it is a serializable document format. When you save a request to a Collection, Postman persists it as a JSON object conforming to the Collection Format v2.1 schema, a specification maintained by Postman that defines the complete structural grammar of a request, including its method, URL object, header array, body configuration, pre-request scripts, and test scripts. Understanding this schema is what allows engineers to generate requests programmatically, version them in Git, and import or export them across teams without touching the UI.

The URL is decomposed into a structured object rather than stored as a flat string. It retains the raw string for display, but also stores the parsed components separately: `protocol`, `host` (as an array of domain labels), `path` (as an array of path segments), and `query` (as an array of key-value objects). This decomposition is what enables Postman's path variable and query parameter editing to work independently of the raw URL bar.

The request body in Postman is typed, not free-form. The `body` object in the request schema carries a `mode` discriminant that selects exactly one of five content representations:

`raw` mode stores the body as a string with an associated language hint (`json`, `text`, `html`, `xml`, `javascript`). This hint sets the `Content-Type` header automatically when the language is selected, though the header can always be overridden manually. The raw body editor provides syntax highlighting and JSON validation feedback in the UI.

`urlencoded` mode models the body as an array of key-value pairs that Postman serializes as `application/x-www-form-urlencoded`, the same encoding a browser uses when submitting an HTML form without a file upload. Each key and value is percent-encoded, and pairs are joined with `&`.

`formdata` mode models the body as a multipart form (`multipart/form-data`), where each part is a key-value pair that may carry either a string value or a file reference. When a file part is present, Postman reads the file from the local filesystem and streams it into the multipart body. The `Content-Type` header for the outer request is set to `multipart/form-data; boundary=<generated_boundary>`, where the boundary token is a unique string that cannot appear in any part's body.

`file` mode streams a raw binary file as the entire request body, which is appropriate for endpoints that accept binary payloads directly, such as a blob storage upload endpoint that expects `Content-Type: image/png` and the raw PNG bytes in the body.

`graphql` mode is a specialized sub-case of `raw/json` that structures the body as a JSON object with `query` and `variables` fields, matching the GraphQL over HTTP specification.

Variable substitution is the mechanism that makes Collections reusable across environments. Before serializing the wire-format request, Postman performs a string substitution pass over the method, URL, all header values, and the raw body, replacing any `{{variable_name}}` token with the value resolved from the active scope chain. That scope chain has a defined resolution order: request-local variables override collection variables, which override environment variables, which override global variables, which override Postman Vault secrets. This is not arbitrary. It mirrors the precedence semantics of environment variable resolution in Unix shells and configuration systems like Kubernetes: narrowest scope wins. When a `{{authToken}}` reference resolves to an empty string in production but to a valid JWT in development, the cause is almost always a missing or stale value at the wrong scope level.

Postman executes pre-request and test scripts inside a sandboxed Node.js V8 context. The sandbox exposes the `pm` API object, which provides programmatic access to the request being built (`pm.request`), the response received (`pm.response`), all variable scopes (`pm.environment`, `pm.collectionVariables`, `pm.globals`), and the test assertion framework (`pm.test`, `pm.expect`). The sandbox does not have access to the Node.js filesystem or network modules directly. Any HTTP requests from scripts must go through `pm.sendRequest`, which routes through Postman's own request pipeline and inherits proxy and certificate settings from the application configuration.

The response object Postman constructs from the wire is a parsed representation. `pm.response.json()` deserializes the body string as JSON and returns a JavaScript object. `pm.response.text()` returns the raw body string. `pm.response.code` returns the integer status code. `pm.response.responseTime` returns the elapsed time in milliseconds from the moment the request was sent to the moment the last byte of the response body was received, which corresponds to the total round-trip time including server processing. The Headers collection is exposed as `pm.response.headers.get("Content-Type")`, with case-insensitive lookup honoring RFC 9110's requirement that header field names are case-insensitive.

Status codes deserve the same mechanical precision as methods. The five classes defined by RFC 9110 are not interchangeable. `2xx` signals that the server understood the request and acted on it. The distinction between `200 OK`, `201 Created`, `202 Accepted`, and `204 No Content` is semantically significant: `201` mandates the presence of a `Location` header pointing to the newly created resource; `202` signals asynchronous processing where the action has been queued but not completed; `204` explicitly carries no body, and a client must not wait for one. `3xx` codes indicate that the client must take additional action to satisfy the request, almost always a redirect. `301 Moved Permanently` allows the client to cache the redirect indefinitely; `302 Found` does not. `307 Temporary Redirect` preserves the original method on redirect, which `302` historically does not on many clients. `4xx` codes place the fault at the client. `400 Bad Request` means malformed syntax; `401 Unauthorized` means missing or invalid credentials (the name is a historical misnomer; it means unauthenticated); `403 Forbidden` means authenticated but not authorized; `404 Not Found` means the resource does not exist at that URI; `422 Unprocessable Content` means the syntax was valid but the semantic validation failed. `5xx` codes place the fault at the server. The difference between `502 Bad Gateway` (the upstream the server is proxying to returned an invalid response) and `503 Service Unavailable` (the server itself cannot handle the request, often due to overload) is critical for incident triage.

## 3. High-Performance Optimization & Failure Modes

The most consequential workflow optimization in Postman is systematic environment architecture. Engineers who maintain a single set of hardcoded URLs and tokens in a Collection develop a brittle artifact that cannot be promoted across environments without manual editing. The correct architecture separates the invariant request structure from the variant configuration. A `baseUrl` environment variable pointing to `http://localhost:3000` in a Development environment, `https://staging.api.example.com` in Staging, and `https://api.example.com` in Production means that every request in the collection works correctly in every environment with nothing more than an environment switch in the top-right dropdown.

Authorization configuration should be set at the Collection level and inherited by all requests using the `Inherit auth from parent` setting. This creates a single point of control for the authentication strategy. If the API uses Bearer tokens, set `Authorization: Bearer {{accessToken}}` at the collection root, and store the token value in the active environment. When the token expires, updating a single environment variable re-authenticates every request in the collection simultaneously. For APIs that use OAuth 2.0, Postman has a built-in OAuth 2.0 helper that can perform the full authorization code or client credentials flow, store the resulting access token, and refresh it automatically before it expires. The token refresh mechanism executes a pre-request script that checks token expiry and conditionally calls the token endpoint, a pattern that eliminates the most common source of intermittent 401 failures in long-running test suites.

Pre-request scripts are the right place to generate dynamic data that must be fresh for each request: timestamps for HMAC signatures, nonce values, request IDs, and computed authorization headers. The `crypto-js` library is bundled in the Postman sandbox and provides SHA-256, SHA-512, HMAC, AES, and Base64 primitives without any import statement. Building an AWS Signature Version 4 canonical request, for example, can be done entirely in a Postman pre-request script using `CryptoJS.HmacSHA256` to sign the canonical string and `CryptoJS.enc.Hex.stringify` to produce the hexadecimal signature. This eliminates the need for external signing proxies or scripted cURL wrappers in many debugging workflows.

A failure mode that consistently surprises engineers is the difference between a network error and an HTTP error response. Postman distinguishes these clearly in its response panel. A `Connection refused` or `ECONNREFUSED` error means no TCP connection was established; the request never reached an HTTP handler, so there is no status code and no response headers. A `502 Bad Gateway` is an HTTP response with a body that happened to signal an upstream failure. The former requires network-level diagnosis (is the service running, are there firewall rules, is the hostname resolving?), while the latter requires application-level diagnosis (what did the upstream return, what does the gateway log say?). Engineers who treat these as the same class of error waste significant time looking in the wrong layer of the stack.

TLS certificate validation is another frequent friction point in development environments. When working against a service using a self-signed certificate or an internal PKI that is not in the system trust store, Postman will refuse the connection and show a certificate error. The correct remediation for a development workflow is to add the CA certificate to Postman's certificate manager under Settings → Certificates → CA Certificates, which scopes the trust to Postman without modifying the system trust store. Disabling SSL certificate verification globally (the "SSL certificate verification" toggle in Settings) is a common shortcut that introduces real security risk in production testing workflows because it silently bypasses all certificate validation, including for public endpoints. Per-host certificate configuration is the right approach.

Request timing data surfaces a category of performance bugs that are invisible from code review. Postman decomposes response time into DNS lookup, TCP connect, TLS handshake, time to first byte (TTFB), and content transfer duration. TTFB is the most diagnostic of these: it represents the time the server spent processing the request after the connection was established. A large TTFB against an endpoint that should be fast points to a slow database query, a lock contention issue, or a synchronous external call in the request path. A large TLS handshake time on the first request that drops to near-zero on subsequent requests indicates TLS session resumption is working correctly. If TLS handshake times remain high on every request, the server may not be supporting session tickets or session IDs, and the connection is re-negotiating full TLS on every request, adding a full round-trip penalty each time.

The Postman Console, opened with `Cmd+Alt+C` on macOS or `Ctrl+Alt+C` on Windows and Linux, shows the actual wire-format request and response with headers, the resolved variable values after substitution, and any script execution logs from `console.log` calls in pre-request or test scripts. It is the single most effective debugging surface available, and the most underused. Any discrepancy between what you configured in the UI and what actually appears in the Console's raw request output indicates a variable resolution failure, an encoding mismatch, or a script mutation of the request object. The Console shows what was actually sent; the UI shows the template that generated it. When these differ, the Console is ground truth.

Duplicate header keys are a failure mode that the HTTP specification technically permits but that most server implementations handle inconsistently. RFC 9110 specifies that multiple header fields with the same name are equivalent to a single header field containing a comma-separated list of their values, except for `Set-Cookie`, which is explicitly exempted. In practice, some servers take the first value, some take the last, and some concatenate all values. If Postman is configured with a header value at the request level and the same header is also injected by a collection-level pre-request script, both values will appear on the wire. The resolution is to audit the Console output when debugging unexpected authentication or content-type failures: duplicated `Authorization` or `Content-Type` headers are a frequent root cause.

Postman's collection runner executes requests sequentially by default, honoring the order defined in the collection tree. Each request runs in the context of the shared environment, meaning a test script on request N can write `pm.environment.set("createdId", pm.response.json().id)` and request N+1 can reference `{{createdId}}` in its URL path. This sequential dependency chain is the idiomatic way to model multi-step API workflows: create a resource, retrieve it, mutate it, and delete it, with each step consuming the output of the previous one. The failure mode here is test order dependency: a collection designed with implicit state dependencies between requests cannot be safely parallelized or run out of order. Keeping dependencies explicit and documented, and ensuring the collection can be re-run from a clean state, is the discipline that separates a maintainable API test suite from a fragile one.
