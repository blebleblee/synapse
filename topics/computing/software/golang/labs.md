# Operational Verification Labs: Golang

## Objective & Toolchain Setup

Modern software engineering demands systematic verification workflows that extend beyond unit testing into the domains of performance characterization, memory safety validation, and concurrency correctness. This laboratory guide establishes a comprehensive operational verification methodology for Go programs, grounded in the toolchain primitives that the Go runtime and compiler expose. Unlike interpreted languages or managed runtimes that obscure low-level behavior, Go provides direct access to compilation artifacts, runtime instrumentation, and execution profiling that enable engineers to reason about program behavior from first principles.

The Go toolchain architecture comprises several layers of abstraction. Source code written in Go undergoes lexical analysis and parsing into an abstract syntax tree, which the compiler then lowers through a series of intermediate representations before emitting machine code. The `go build` command orchestrates this pipeline, invoking the compiler (`compile`), assembler (`asm`), and linker (`link`) in sequence. The runtime layer provides garbage collection, goroutine scheduling, and memory management, all of which introduce performance characteristics that require systematic measurement and analysis. Understanding these layers enables engineers to diagnose issues that manifest only under production workloads or specific hardware configurations.

Verification workflows in Go leverage three primary diagnostic domains: static analysis and compilation artifacts, dynamic performance profiling, and runtime safety instrumentation. Static analysis tools such as `go vet` and the escape analysis report (`-gcflags=-m`) expose compiler decisions about heap allocation and inlining that directly impact performance. Dynamic profiling through `pprof` captures CPU samples, memory allocation traces, mutex contention, and goroutine blocking behavior, providing quantitative insight into runtime bottlenecks. Safety instrumentation via the race detector and memory sanitizers identifies undefined behavior and concurrency bugs that deterministic testing often fails to surface.

The `-gcflags` flag passes directives to the Go compiler, where `-N` disables optimizations and `-l` disables inlining. The Go execution model introduces several runtime components that influence verification methodology. The garbage collector operates concurrently with application goroutines, introducing non-deterministic pause times that manifest as latency tail events. The scheduler multiplexes goroutines onto operating system threads using a work-stealing algorithm, where contention for shared scheduler state can create unexpected performance cliffs. Memory allocation follows a size-class hierarchy with thread-local caches, where allocation patterns that thrash these caches exhibit dramatically different performance than patterns that align with cache boundaries. Systematic verification requires measuring these runtime interactions under realistic workloads, not merely synthetic microbenchmarks.

Prepare a reference program that exercises the domains covered in subsequent exercises. This program implements a concurrent hash table with lock-free reads and synchronized writes, exposing common pitfalls in memory ordering, cache coherence, and goroutine synchronization. The implementation deliberately contains several categories of issues—inefficient memory allocation, data race conditions, and suboptimal cache utilization—that the verification workflows will systematically expose and remediate.

```go
// File: labs/reference/concurrent_map.go
package main

import (
	"hash/fnv"
	"sync"
	"sync/atomic"
)

type ConcurrentMap struct {
	buckets  []bucket
	size     int
	rehashing atomic.Bool
}

type bucket struct {
	mu    sync.RWMutex
	items []item
}

type item struct {
	key   string
	value interface{}
}

func NewConcurrentMap(size int) *ConcurrentMap {
	cm := &ConcurrentMap{
		buckets: make([]bucket, size),
		size:    size,
	}
	for i := range cm.buckets {
		cm.buckets[i].items = make([]item, 0, 4)
	}
	return cm
}

func (cm *ConcurrentMap) hash(key string) uint32 {
	h := fnv.New32a()
	h.Write([]byte(key))
	return h.Sum32()
}

func (cm *ConcurrentMap) Get(key string) (interface{}, bool) {
	idx := cm.hash(key) % uint32(cm.size)
	b := &cm.buckets[idx]
	
	// Deliberately racy read to expose data race detector
	for i := range b.items {
		if b.items[i].key == key {
			return b.items[i].value, true
		}
	}
	return nil, false
}

func (cm *ConcurrentMap) Put(key string, value interface{}) {
	idx := cm.hash(key) % uint32(cm.size)
	b := &cm.buckets[idx]
	
	b.mu.Lock()
	defer b.mu.Unlock()
	
	for i := range b.items {
		if b.items[i].key == key {
			b.items[i].value = value
			return
		}
	}
	
	// Inefficient append that triggers allocation on every insert
	b.items = append(b.items, item{key: key, value: value})
}

func (cm *ConcurrentMap) Iterate(fn func(string, interface{})) {
	for i := range cm.buckets {
		b := &cm.buckets[i]
		b.mu.RLock()
		for j := range b.items {
			fn(b.items[j].key, b.items[j].value)
		}
		b.mu.RUnlock()
	}
}
```

This reference implementation contains three distinct categories of verification targets. First, the `Get` method omits lock acquisition, creating a data race with concurrent `Put` operations that the race detector will flag. Second, the unbounded `append` in `Put` triggers heap allocations on every insertion rather than amortizing allocations across multiple operations, a pattern that profiling will expose as a memory throughput bottleneck. Third, the linear scan in `Get` exhibits poor cache locality when bucket sizes grow, manifesting as increased cache miss rates under load. Subsequent exercises will systematically identify and remediate each category of issue through toolchain-driven verification.

## Exercise 1: AST, IR & Disassembly Analysis

Understanding how the Go compiler transforms source code into machine instructions provides essential insight into performance characteristics and optimization opportunities. The compilation pipeline proceeds through several intermediate representations: the abstract syntax tree captures syntactic structure, the static single assignment form enables dataflow analysis and optimization, and the final assembly listing exposes the actual instructions executed by the processor. Analyzing these artifacts reveals compiler decisions about inlining, escape analysis, and register allocation that directly determine runtime performance.

The Go compiler exposes intermediate representations through the `-S` flag, which emits assembly output annotated with source line numbers and optimization decisions. This listing uses a platform-independent assembly syntax that abstracts over differences between x86-64, ARM, and other architectures, enabling cross-platform analysis while preserving essential details about instruction selection and register usage. Engineers examining assembly output can identify optimization failures, unexpected function calls that should have been inlined, and memory access patterns that cause cache misses or false sharing.

Begin by analyzing the compilation artifacts for the `ConcurrentMap.Get` method. This analysis exposes how the compiler handles the unsynchronized read of the `items` slice, revealing the memory access pattern that creates the data race. Compile the reference program with assembly output and search for the `Get` method's implementation, noting the instructions used for slice indexing and field access.

```bash
cd ~/go-verification-labs/asm-analysis
cp ../reference/concurrent_map.go .

# Generate assembly listing with optimization disabled
go build -gcflags='-S -N -l' concurrent_map.go 2>&1 | tee asm_unoptimized.txt

# Extract the Get method assembly
grep -A 50 '"".(*ConcurrentMap).Get' asm_unoptimized.txt > get_method_unopt.asm

# Generate assembly listing with optimizations enabled
go build -gcflags='-S' concurrent_map.go 2>&1 | tee asm_optimized.txt
grep -A 50 '"".(*ConcurrentMap).Get' asm_optimized.txt > get_method_opt.asm

# Compare instruction counts
echo "Unoptimized instruction count:"
grep -E '^\s+0x' get_method_unopt.asm | wc -l
echo "Optimized instruction count:"
grep -E '^\s+0x' get_method_opt.asm | wc -l
```

The assembly listings reveal the fundamental structure of slice operations in Go. Each slice comprises three words: a pointer to the backing array, a length, and a capacity. Accessing `b.items[i]` requires loading the pointer, performing bounds checking against the length, computing the offset `i * sizeof(item)`, and dereferencing the resulting address. Without proper synchronization, concurrent writers can modify the pointer or length while the reader is in the middle of this operation, creating torn reads that violate memory safety. The race detector instruments exactly these operations to detect concurrent conflicting accesses.

Escape analysis determines whether variables can be allocated on the stack or must escape to the heap. Variables that escape incur garbage collection overhead and additional memory latency due to pointer indirection. The Go compiler emits escape analysis decisions when invoked with `-gcflags=-m`, producing a diagnostic report that explains why each variable escapes. This report guides optimization efforts by identifying allocation hot paths that would benefit from value-type semantics or object pooling.

```bash
# Generate escape analysis report
go build -gcflags='-m -m' concurrent_map.go 2>&1 | tee escape_analysis.txt

# Filter for heap allocation decisions
grep 'escapes to heap' escape_analysis.txt

# Analyze specific method escape behavior
grep -A 5 'ConcurrentMap.Put' escape_analysis.txt
```

The escape analysis report for `Put` reveals that the `item{key: key, value: value}` composite literal escapes to the heap. This occurs because the `append` operation may reallocate the backing array, and the Go compiler conservatively assumes that the appended item's lifetime extends beyond the function's stack frame. This allocation pattern, repeated for every insertion, creates garbage collection pressure that profiling will quantify. Remediation strategies include pre-allocating the slice with sufficient capacity or using a free list to recycle item allocations.

The inlining budget determines which function calls the compiler replaces with inline code, eliminating call overhead and enabling additional optimizations across the inlined boundary. The Go compiler uses a cost model that assigns points to each statement and control flow construct, inlining functions whose total cost falls below a threshold. The `-gcflags=-m` output annotates each function with its inlining cost and explains why functions exceed the budget or contain constructs that prevent inlining.

```bash
# Analyze inlining decisions
grep 'can inline\|cannot inline\|inlining call' escape_analysis.txt > inlining_decisions.txt

# Examine why ConcurrentMap.hash was not inlined
grep -A 3 'ConcurrentMap.hash' inlining_decisions.txt
```

The `hash` method's inlining decision depends on its complexity and the calling context. Small methods that perform simple arithmetic operations inline readily, while methods containing loops, defer statements, or function calls often exceed the inlining budget. Inlining profoundly affects performance because it eliminates function call overhead, enables constant propagation across the call boundary, and allows the compiler to optimize the combined code sequence as a single unit. Engineers targeting performance-critical paths should structure code to maximize inlining opportunities, factoring complex logic into separate functions called from thin inline wrappers.

The Go compiler's intermediate representation, accessible through `-S -N -l`, preserves variable names and source line mappings that enable detailed analysis of optimization failures. Examine the unoptimized assembly for the `Get` method to understand the exact sequence of memory accesses performed during slice iteration. Each iteration loads the slice pointer and length, performs bounds checking, computes the element address, and loads the `key` field for comparison. This memory access pattern determines cache behavior and exposes the data race vulnerability.

```go
// File: labs/asm-analysis/bounds_check_analysis.go
package main

import "fmt"

func sumSlice(data []int) int {
	sum := 0
	for i := 0; i < len(data); i++ {
		sum += data[i]
	}
	return sum
}

func sumSliceOptimized(data []int) int {
	sum := 0
	for i := range data {
		sum += data[i]
	}
	return sum
}

func main() {
	data := []int{1, 2, 3, 4, 5}
	fmt.Println(sumSlice(data))
	fmt.Println(sumSliceOptimized(data))
}
```

Compile this example with bounds check instrumentation to observe how the compiler generates conditional branches for slice bounds validation. The traditional index-based loop requires a bounds check on every iteration, while the range-based loop allows the compiler to prove that the index always remains within bounds, eliminating redundant checks. This optimization, visible in the assembly output, directly reduces the instruction count in tight loops.

```bash
# Compile with bounds check elimination reporting
go build -gcflags='-d=ssa/check_bce/debug=1' bounds_check_analysis.go 2>&1 | tee bce_report.txt

# Compare assembly for both functions
go build -gcflags='-S' bounds_check_analysis.go 2>&1 | grep -A 30 'sumSlice\|sumSliceOptimized' > bounds_check_comparison.asm

# Count bounds check instructions (PCDATA annotations)
grep 'PCDATA.*checkbounds' bounds_check_comparison.asm | wc -l
```

The bounds check elimination report annotates each array or slice access with the compiler's proof obligation. When the compiler can statically prove that an index lies within bounds, it omits the runtime check, reducing both instruction count and branch misprediction penalties. This optimization interacts with loop structure, induction variable analysis, and range assertions, demonstrating how high-level code patterns enable low-level performance improvements.

Practical verification workflows combine assembly analysis with objdump and disassembler tools to correlate source code, compiler IR, and final machine code. Use `go tool objdump` to disassemble compiled binaries, examining how the linker resolves function calls and structures the final executable. This analysis reveals whether the runtime or standard library introduces unexpected overhead through interface dispatch, reflection, or garbage collection write barriers.

```bash
# Compile binary for disassembly
go build -o concurrent_map concurrent_map.go

# Disassemble specific functions
go tool objdump -s 'main.(*ConcurrentMap).Get' concurrent_map > get_objdump.txt
go tool objdump -s 'main.(*ConcurrentMap).Put' concurrent_map > put_objdump.txt

# Analyze call graph and external dependencies
go tool objdump -s 'main.main' concurrent_map | grep CALL > main_calls.txt

# Examine runtime function calls
cat main_calls.txt | grep runtime
```

The objdump output exposes runtime function calls that the compiler inserts for garbage collection coordination, goroutine scheduling, and memory allocation. Each `runtime.newobject` call represents a heap allocation, `runtime.writeBarrier` appears at pointer writes that may create cross-generational references, and `runtime.morestack` handles stack growth for goroutines that exceed their initial stack allocation. Identifying these runtime interactions enables engineers to predict performance characteristics under different workload patterns and optimize allocation-heavy code paths.

## Exercise 2: Cache Miss & Throughput Profiling

Performance optimization grounded in measurement requires systematic profiling to identify bottlenecks, quantify resource consumption, and validate that optimizations produce measurable improvements. The Go runtime provides comprehensive profiling facilities that capture CPU samples, memory allocations, mutex contention, and goroutine blocking events without requiring code instrumentation or external tools. These profiles, analyzed through the `pprof` visualization tool, expose performance characteristics at multiple granularities from individual functions to system-wide resource utilization patterns.

CPU profiling operates through statistical sampling, where the runtime periodically records the program counter and call stack during execution. This sampling approach introduces minimal overhead, typically one to five percent, enabling production use without significantly perturbing the measured system. The resulting profile aggregates samples into a call graph that attributes execution time to functions and call sites, revealing hot paths that dominate execution time. Engineers analyze these profiles to identify optimization opportunities, validate that performance-critical code receives appropriate optimization attention, and detect unexpected inefficiencies introduced by algorithmic choices or library usage.

Begin by instrumenting the reference `ConcurrentMap` program with benchmark workloads that exercise different access patterns. The Go testing package provides a standardized benchmarking framework that runs functions repeatedly while measuring execution time and memory allocations. These benchmarks serve as reproducible performance tests that detect regressions when combined with statistical analysis via `benchstat`.

```go

import (
	"fmt"
	"math/rand"

func BenchmarkConcurrentMapPut(b *testing.B) {
```

## Exercise 3: Data Race Stress Testing & Leak Sanitizer Diagnostics

Concurrency correctness represents one of the most challenging aspects of systems programming, where subtle race conditions manifest non-deterministically and often evade conventional testing. The Go race detector instruments memory accesses at compile time, tracking read and write operations to detect conflicting unsynchronized accesses that constitute data races. This dynamic analysis tool provides deterministic detection of race conditions that would otherwise require extensive stress testing or manifest as production failures, enabling engineers to verify concurrency correctness with high confidence.

The race detector operates by maintaining shadow memory that records the most recent access to each memory location, including the goroutine ID, access timestamp, and access type. On each memory access, the instrumentation checks whether a previous conflicting access occurred in a different goroutine without intervening synchronization. When the detector identifies a race, it reports both access locations with complete stack traces, enabling precise diagnosis of the synchronization failure. This instrumentation introduces significant overhead, typically five to ten times slowdown and ten times memory increase, limiting its use to testing environments rather than production deployments.

Enable the race detector by passing the `-race` flag to the Go toolchain during compilation and test execution. Run the benchmark workload with race detection enabled, which will either report detected races or complete successfully if no races occur. The reference `ConcurrentMap` implementation contains a deliberate race in the `Get` method, which the detector will identify during concurrent execution.


The race detector output identifies the conflicting accesses with source file locations and complete goroutine stack traces. For the `ConcurrentMap` implementation, the detector reports a race between the `Get` method's read of `b.items` and the `Put` method's write via `append`. This race occurs because `Get` accesses the slice without acquiring the lock, allowing concurrent `Put` operations to reallocate the backing array while `Get` iterates over it. The fix requires acquiring the read lock before accessing `b.items`.

```go
// File: labs/race-detection/concurrent_map_fixed.go
package main

import (
	"hash/fnv"
	"sync"
	"sync/atomic"
)

type ConcurrentMap struct {
	buckets  []bucket
	size     int
	rehashing atomic.Bool
}

type bucket struct {
	mu    sync.RWMutex
	items []item
}

type item struct {
	key   string
	value interface{}
}

func NewConcurrentMap(size int) *ConcurrentMap {
	cm := &ConcurrentMap{
		buckets: make([]bucket, size),
		size:    size,
	}
	for i := range cm.buckets {
		cm.buckets[i].items = make([]item, 0, 16) // Pre-allocate capacity
	}
	return cm
}

func (cm *ConcurrentMap) hash(key string) uint32 {
	h := fnv.New32a()
	h.Write([]byte(key))
	return h.Sum32()
}

func (cm *ConcurrentMap) Get(key string) (interface{}, bool) {
	idx := cm.hash(key) % uint32(cm.size)
	b := &cm.buckets[idx]
	
	b.mu.RLock() // Fix: acquire read lock
	defer b.mu.RUnlock()
	
	for i := range b.items {
		if b.items[i].key == key {
			return b.items[i].value, true
		}
	}
	return nil, false
}

func (cm *ConcurrentMap) Put(key string, value interface{}) {
	idx := cm.hash(key) % uint32(cm.size)
	b := &cm.buckets[idx]
	
	b.mu.Lock()
	defer b.mu.Unlock()
	
	for i := range b.items {
		if b.items[i].key == key {
			b.items[i].value = value
			return
		}
	}
	
	b.items = append(b.items, item{key: key, value: value})
}

func (cm *ConcurrentMap) Iterate(fn func(string, interface{})) {
	for i := range cm.buckets {
		b := &cm.buckets[i]
		b.mu.RLock()
		for j := range b.items {
			fn(b.items[j].key, b.items[j].value)
		}
		b.mu.RUnlock()
	}
}
```

However, introducing locking in `Get` may significantly impact performance under read-heavy workloads, motivating alternative concurrency strategies such as lock-free data structures or copy-on-write schemes.

Stress testing with the race detector requires generating high-concurrency workloads that maximize the probability of exposing races. The Go testing package's `RunParallel` method spawns goroutines proportional to `GOMAXPROCS`, executing the benchmark body concurrently across multiple CPUs. This pattern creates the scheduling interleavings necessary to trigger race conditions that sequential execution would never expose.

```go
// File: labs/race-detection/race_stress_test.go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"testing"
	"time"
)

func TestConcurrentMapRaceStress(t *testing.T) {
	cm := NewConcurrentMap(128)
	
	const numGoroutines = 100
	const numOperations = 10000
	
	var wg sync.WaitGroup
	wg.Add(numGoroutines)
	
	// Start readers
	for i := 0; i < numGoroutines/2; i++ {
		go func(id int) {
			defer wg.Done()
			for j := 0; j < numOperations; j++ {
				key := fmt.Sprintf("key_%d", rand.Intn(1000))
				cm.Get(key)
			}
		}(i)
	}
	
	// Start writers
	for i := 0; i < numGoroutines/2; i++ {
		go func(id int) {
			defer wg.Done()
			for j := 0; j < numOperations; j++ {
				key := fmt.Sprintf("key_%d", rand.Intn(1000))
				cm.Put(key, j)
				time.Sleep(time.Microsecond) // Encourage interleaving
			}
		}(i)
	}
	
	wg.Wait()
}

func TestConcurrentMapIterateRace(t *testing.T) {
	cm := NewConcurrentMap(64)
	
	// Pre-populate
	for i := 0; i < 1000; i++ {
		cm.Put(fmt.Sprintf("key_%d", i), i)
	}
	
	var wg sync.WaitGroup
	wg.Add(3)
	
	// Iterator
	go func() {
		defer wg.Done()
		for i := 0; i < 100; i++ {
			cm.Iterate(func(k string, v interface{}) {
				_ = k
				_ = v
			})
		}
	}()
	
	// Writer
	go func() {
		defer wg.Done()
		for i := 0; i < 1000; i++ {
			cm.Put(fmt.Sprintf("key_%d", rand.Intn(2000)), i)
		}
	}()
	
	// Reader
	go func() {
		defer wg.Done()
		for i := 0; i < 1000; i++ {
			cm.Get(fmt.Sprintf("key_%d", rand.Intn(2000)))
		}
	}()
	
	wg.Wait()
}
```

Execute the stress tests with the race detector enabled, observing whether races occur under high-concurrency conditions. These tests generate scheduling interleavings that sequential execution or low-concurrency benchmarks miss, exposing subtle race conditions that manifest only under production load patterns. The race detector's deterministic detection ensures that even rare races that occur in only one out of thousands of executions will be flagged and reported.

Beyond the race detector, memory sanitizers detect other categories of undefined behavior such as use-after-free, double-free, and buffer overflows. While Go's memory safety guarantees prevent these issues in pure Go code, programs using `cgo` to interface with C libraries can introduce these vulnerabilities. The Go toolchain supports AddressSanitizer integration for detecting memory errors in C code called via `cgo`.

```go
// File: labs/race-detection/cgo_example.go
// +build cgo

package main

/*
#include <stdlib.h>
#include <string.h>

char* unsafe_concat(const char* a, const char* b) {
    // Deliberately unsafe: buffer overflow vulnerability
    char* result = (char*)malloc(10);
    strcpy(result, a);
    strcat(result, b);
    return result;
}

void unsafe_free(char* ptr) {
    free(ptr);
    free(ptr); // Deliberate double-free
}
*/
import "C"
import (
	"fmt"
	"unsafe"
)

func UnsafeConcat(a, b string) string {
	ca := C.CString(a)
	cb := C.CString(b)
	defer C.free(unsafe.Pointer(ca))
	defer C.free(unsafe.Pointer(cb))
	
	result := C.unsafe_concat(ca, cb)
	goResult := C.GoString(result)
	C.unsafe_free(result)
	
	return goResult
}

func main() {
	result := UnsafeConcat("Hello, ", "World!")
	fmt.Println(result)
}
```

Compile and run the `cgo` example with AddressSanitizer enabled to detect the buffer overflow and double-free errors. The sanitizer instruments memory allocations and accesses in C code, reporting violations with stack traces that identify the source of undefined behavior. This integration extends Go's safety guarantees to mixed Go and C codebases, enabling systematic verification of foreign function interfaces.


Goroutine leak detection identifies goroutines that fail to terminate, creating resource leaks that accumulate over time and eventually exhaust system resources. While Go provides garbage collection for memory, goroutines themselves are not garbage collected and must explicitly terminate. Use goroutine profiling to capture the number and stack traces of running goroutines, comparing snapshots before and after operations to detect leaks.

```go
// File: labs/race-detection/goroutine_leak_test.go
package main

import (
	"context"
	"runtime"
	"testing"
	"time"
)

func leakyOperation(ctx context.Context) {
	// Deliberately leaks goroutine: missing context cancellation check
	go func() {
		ticker := time.NewTicker(100 * time.Millisecond)
		defer ticker.Stop()
		
		for {
			select {
			case <-ticker.C:
				// Perform work but never check ctx.Done()
				_ = time.Now()
			}
		}
	}()
}

func TestGoroutineLeak(t *testing.T) {
	initialGoroutines := runtime.NumGoroutine()
	
	ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)
	defer cancel()
	
	// Spawn leaky operations
	for i := 0; i < 10; i++ {
		leakyOperation(ctx)
	}
	
	// Wait for context timeout
	<-ctx.Done()
	time.Sleep(100 * time.Millisecond) // Allow goroutines to exit if properly implemented
	
	finalGoroutines := runtime.NumGoroutine()
	leakedGoroutines := finalGoroutines - initialGoroutines
	
	t.Logf("Initial goroutines: %d", initialGoroutines)
	t.Logf("Final goroutines: %d", finalGoroutines)
	t.Logf("Leaked goroutines: %d", leakedGoroutines)
	
	if leakedGoroutines > 0 {
		t.Errorf("Detected %d leaked goroutines", leakedGoroutines)
	}
}
```

Execute the goroutine leak test and capture a goroutine profile to examine the stack traces of leaked goroutines. The profile reveals which goroutines failed to terminate and identifies the source locations where they were spawned, guiding remediation efforts to add proper context cancellation or shutdown signaling.

```bash
# Run leak detection test
go test -v -run=TestGoroutineLeak

# Capture goroutine profile during execution
go test -run=TestGoroutineLeak -goroutineprofile=goroutine.prof

# (pprof) traces
```

The goroutine profile displays all running goroutines with their stack traces, grouped by common call paths. Leaked goroutines appear as stacks that remain active after the expected termination point, often blocked on channel receives, timer ticks, or other synchronization operations that never complete. The fix requires propagating cancellation signals through context objects or explicit shutdown channels, ensuring that all spawned goroutines can terminate gracefully.

Deadlock detection identifies circular wait conditions where goroutines block indefinitely waiting for each other to release resources. The Go runtime automatically detects global deadlocks, where all goroutines are blocked with no possibility of progress, and panics with a diagnostic message listing all goroutine states. This detection occurs only for global deadlocks; partial deadlocks involving a subset of goroutines do not trigger automatic detection and require explicit timeout mechanisms or distributed deadlock detection algorithms.

```go
// File: labs/race-detection/deadlock_example.go
package main

import (
	"fmt"
	"sync"
)

func deadlockExample() {
	var mu1, mu2 sync.Mutex
	
	// Goroutine 1: locks mu1 then mu2
	go func() {
		mu1.Lock()
		defer mu1.Unlock()
		
		// Simulate work
		fmt.Println("Goroutine 1 acquired mu1")
		
		mu2.Lock()
		defer mu2.Unlock()
		fmt.Println("Goroutine 1 acquired mu2")
	}()
	
	// Goroutine 2: locks mu2 then mu1
	go func() {
		mu2.Lock()
		defer mu2.Unlock()
		
		fmt.Println("Goroutine 2 acquired mu2")
		
		mu1.Lock()
		defer mu1.Unlock()
		fmt.Println("Goroutine 2 acquired mu1")
	}()
	
	// Wait indefinitely
	select {}
}

func main() {
	deadlockExample()
}
```

Run the deadlock example and observe the runtime's detection and panic message. The runtime reports all goroutine states at the deadlock point, revealing the circular dependency between lock acquisition orders. The fix requires establishing a consistent lock ordering across all code paths, ensuring that all goroutines acquire locks in the same sequence to prevent circular waits.

```bash
# Run deadlock example
go run deadlock_example.go 2>&1 | tee deadlock_report.txt

# Runtime will panic with:
# fatal error: all goroutines are asleep - deadlock!
# Followed by goroutine states showing blocking points
```

2. Analyze with `pprof -alloc_space` to find allocation hot paths
