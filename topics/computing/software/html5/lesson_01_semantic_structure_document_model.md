# Lesson 1: Semantic Structure, Document Object Model, Parsing Rules

## 1. First-Principles Intuition & Invariants

HTML5 represents a radical departure from the brittle, schema-driven parsing models of XHTML and XML. Where XHTML demanded well-formedness and failed catastrophically on malformed input, HTML5 embraces the messy reality of the web: a billion documents written by hand, generated by broken templates, and mutilated by content management systems. The HTML5 specification formalizes what browsers have done for decades through ad-hoc error recovery into a deterministic, implementable parsing algorithm. This algorithm is not a simple recursive descent parser or a clean context-free grammar. It is a dual-stage state machine consisting of a tokenizer operating on a byte stream and a tree constructor that consumes tokens while maintaining a stack of open elements, a list of active formatting elements, and a complex set of insertion modes that govern where each token is inserted into the growing Document Object Model tree.

The core invariant of HTML5 parsing is **error tolerance with deterministic recovery**. Given identical input bytes, every conforming HTML5 parser must produce an identical DOM tree, even when the input violates syntactic rules. This determinism is critical for web interoperability: server-side rendering, client-side frameworks, search engine crawlers, screen readers, and security scanners must all agree on what a document means. The specification achieves this by enumerating every possible error condition and prescribing exact recovery behavior. When a parser encounters a closing tag with no matching open element, it does not throw an exception or halt; it applies a specific rule from the adoption agency algorithm or foster parenting rules and continues.

HTML5 introduces a formal content model hierarchy that governs which elements may contain which others. At the root of this taxonomy lies the distinction between flow content, phrasing content, and embedded content. Flow content represents block-level structural elements like paragraphs, headings, and lists. Phrasing content corresponds to inline text-level semantics: spans, emphasis, links, and inline code. Embedded content brings in external resources through images, video, audio, and iframes. Unlike the simplistic block versus inline dichotomy of HTML4, the HTML5 content model is multidimensional: a single element may belong to multiple categories, and containment rules vary by context. The `<a>` anchor element, for instance, is phrasing content but may contain flow content if it wraps entire paragraphs or headings, provided it does not nest another interactive element.

Semantic structure in HTML5 emerges from the sectioning content model and the outline algorithm. Sectioning elements—`<article>`, `<section>`, `<nav>`, `<aside>`—establish new sectioning contexts, creating a nested hierarchy of document regions each with its own heading rank. The outline algorithm computes an implicit document structure by analyzing heading elements (`<h1>` through `<h6>`) within each sectioning context, allowing multiple `<h1>` elements without ambiguity. A blog post containing nested articles can use `<h1>` for both the main post title and comment titles, with the outline algorithm understanding that comment headings are subordinate because they appear within nested `<article>` elements. While the outline algorithm has not been widely implemented in assistive technologies, the semantic distinctions remain valuable for document processing pipelines, content extraction, and machine learning systems that analyze page structure.

The Document Object Model is not merely a convenient API abstraction; it is the fundamental in-memory representation of an HTML document within the browser runtime. The DOM tree is a directed acyclic graph of node objects where each element, text fragment, comment, and document type declaration exists as a first-class object with identity, attributes, and parent-child relationships. The tree structure enables efficient queries through CSS selectors and XPath expressions, supports incremental updates via DOM mutation observers, and provides a stable contract between the rendering engine and JavaScript execution environment. Understanding DOM construction is essential for performance optimization: deeply nested trees increase query complexity, excessive text nodes fragment memory, and frequent mutations trigger expensive layout recalculations and style revalidation.

Void elements represent a subtle but important parsing distinction. Elements like `<img>`, `<br>`, `<input>`, and `<meta>` cannot have children and must not have closing tags in the HTML syntax. When the parser encounters `<img>`, it immediately inserts an element node and pops it from the stack of open elements without waiting for a closing tag. Attempting to write `<img></img>` produces two separate `<img>` nodes because the parser interprets the closing tag as a malformed token and applies error recovery. This behavior differs from self-closing XML syntax: writing `<img />` in HTML5 is functionally identical to `<img>` because the trailing slash is ignored for non-foreign elements. Understanding void elements prevents common bugs in template generation systems that emit closing tags for void elements, producing unintended DOM structures.

The parsing algorithm maintains several critical data structures that determine insertion behavior. The stack of open elements tracks which elements are currently open and governs where new nodes are inserted. The list of active formatting elements implements the adoption agency algorithm, which handles misnested formatting tags like `<b><i></b></i>` by reparenting elements to maintain valid nesting. The insertion mode is a state variable that determines how each token is processed: initial mode handles DOCTYPE declarations, before HTML mode consumes tokens until the root element appears, in body mode processes the document content, and specialized modes handle tables, framsets, and templates. Mode transitions occur based on specific tokens and context conditions, creating a complex but fully specified control flow.

## 2. Core Architecture & Mechanics

The HTML5 parsing process begins with byte stream decoding, where raw bytes are transformed into Unicode code points according to a character encoding declaration. The parser first performs a prescan of the first 1024 bytes searching for a `<meta charset>` declaration or byte order mark to determine encoding. If no declaration is found, the parser applies a confidence-based heuristic or defaults to UTF-8. Once the encoding is established, the byte stream is decoded into a stream of Unicode code points that feed into the tokenizer.

The tokenizer is a finite state machine with over eighty distinct states governing character consumption and token emission. The machine begins in the data state, consuming characters and emitting them as character tokens until it encounters a `<` character, which transitions to the tag open state. The tag open state examines the next character: if it is an ASCII letter, the machine transitions to tag name state and begins accumulating tag name characters; if it is `!`, the machine transitions to markup declaration open state to handle comments and DOCTYPE declarations; if it is `/`, the machine enters end tag open state. Each state specifies explicit transitions for every possible input character, including EOF, with defined error handling for unexpected inputs.

```text
Tokenizer State Machine (Simplified Core States):

Data State:
  '<'           → Tag Open State
  '&'           → Character Reference State
  NULL          → ERROR: emit U+FFFD
  EOF           → emit EOF token
  [other]       → emit character token

Tag Open State:
  '!'           → Markup Declaration Open State
  '/'           → End Tag Open State
  [A-Za-z]      → Tag Name State (create start tag)
  '?'           → ERROR: Bogus Comment State
  EOF           → ERROR: emit '<' character

Tag Name State:
  ' ' '\t' '\n' → Before Attribute Name State
  '/'           → Self-Closing Start Tag State
  '>'           → emit current tag token
  [A-Z]         → append lowercase to tag name
  NULL          → ERROR: append U+FFFD
  [other]       → append to tag name

Attribute States:
  Before Attribute Name → Attribute Name → After Attribute Name
      → Before Attribute Value → Attribute Value (Quoted/Unquoted)
```

When the tokenizer emits a tag token, the tree constructor consumes it according to the current insertion mode. The tree constructor maintains the stack of open elements as a dynamic array of element pointers, with the current node at the top of the stack. For a start tag token in the "in body" insertion mode, the constructor first checks if the tag name matches a special element category that requires specific handling. Ordinary flow content elements like `<div>` or `<p>` are simply instantiated as new element nodes, appended to the current node as a child, and pushed onto the open element stack. Phrasing content elements follow similar logic but may trigger reconstruction of active formatting elements if previous formatting context was interrupted.

The adoption agency algorithm handles misnested formatting elements by maintaining a separate list of active formatting elements—a bounded list of up to three markers and associated formatting elements like `<b>`, `<i>`, `<strong>`, `<em>`. When the parser encounters a closing tag for a formatting element, it searches the active formatting list backwards for a matching element. If found, it performs a complex reparenting procedure that reconstructs proper nesting by cloning formatting elements and adjusting parent-child relationships. Consider the input `<b>bold <i>italic</b> still italic</i>`. When the parser encounters `</b>`, the `<i>` element is still open. The adoption agency algorithm clones the `<i>` node, closes the original `<i>` before the `</b>`, closes the `<b>`, then reopens the cloned `<i>` to contain "still italic", producing a DOM equivalent to `<b>bold <i>italic</i></b><i> still italic</i>`.

Table parsing represents the most complex insertion mode due to foster parenting rules. Tables have strict content models: a `<table>` element must contain only `<caption>`, `<colgroup>`, `<thead>`, `<tbody>`, `<tfoot>`, and `<tr>` elements, never raw text or other flow content. When the parser encounters unexpected content inside a table—a common occurrence with malformed markup—it invokes foster parenting, which moves the unexpected content before the table in the DOM tree. This behavior prevents content loss but can produce surprising structures. Consider `<table><div>text</div><tr><td>cell</td></tr></table>`. The parser foster-parents the `<div>` before the table, resulting in a DOM where the div is a sibling preceding the table, not a child.

```text
Simplified Tree Construction Algorithm:

function processToken(token, insertionMode):
  switch insertionMode:
    case IN_BODY:
      if token is StartTag:
        if token.name in SPECIAL_ELEMENTS:
          # Close implied end tags
          while stack.top in IMPLIED_END_TAG_EXCLUDE:
            stack.pop()
        
        node = createElement(token.name, token.attributes)
        stack.top.appendChild(node)
        
        if token.name not in VOID_ELEMENTS:
          stack.push(node)
        
        if token.name in FORMATTING_ELEMENTS:
          activeFormattingElements.push(node)
      
      else if token is EndTag:
        if token.name in FORMATTING_ELEMENTS:
```

Template elements introduce a unique parsing context through the template contents owner document. A `<template>` element contains a DocumentFragment as its content property, representing inert markup that does not execute scripts or load resources. When the parser encounters a `<template>` start tag, it pushes a template insertion mode onto the mode stack and creates a new DocumentFragment. All subsequent content until the matching `</template>` is parsed into this fragment rather than the main document tree. This isolation enables template cloning for web components and client-side rendering frameworks without polluting the main DOM with inert structure.

Foreign content handling manages the integration of SVG and MathML namespaces within HTML documents. When the parser encounters an `<svg>` or `<math>` element, it transitions to a specialized parsing mode that adjusts tokenization rules to match XML case sensitivity and self-closing tag behavior. Within SVG context, element and attribute names preserve their case, and `<rect />` is correctly interpreted as self-closing rather than emitting a separate end tag token. The foreign content mode maintains a second stack tracking namespace context, ensuring that elements are created in the correct namespace URI and that transitions back to HTML content occur at appropriate boundary elements like `</svg>`.

## 3. High-Performance Optimization & Failure Modes

DOM construction performance directly impacts page load latency and user experience. Modern browser engines employ speculative parsing, where a secondary thread scans ahead in the token stream to discover external resources like stylesheets, scripts, and images while the main thread builds the DOM tree. This lookahead enables earlier resource fetching but depends on predictable document structure. Inline scripts that use `document.write()` break speculative parsing by injecting tokens into the stream, forcing the speculative parser to discard its work and resynchronize. Performance-conscious applications avoid `document.write()` entirely, using declarative HTML or deferred script execution to maintain speculative parsing efficiency.

Deep nesting creates quadratic complexity in certain DOM operations. CSS selector matching with descendant combinators must walk ancestor chains, and deeply nested trees increase walk distance. Similarly, event bubbling traverses from target to document root, and excessive depth extends this path. Tree structures exceeding one thousand levels trigger browser warnings and may cause stack overflow in recursive algorithms. Template generation systems that nest components without bound—common in recursive comment threads or hierarchical navigation—must implement depth limits or iterative flattening to prevent pathological DOM structures.

Script execution during parsing blocks tree construction unless marked with `async` or `defer` attributes. When the parser encounters a `<script>` tag without asynchronous attributes, it pauses tokenization, executes the script, then resumes. This synchronous execution allows scripts to call `document.write()` to inject content into the parsing stream, but it prevents parallel resource loading and delays rendering. The `defer` attribute allows scripts to load asynchronously while preserving execution order, executing after DOM construction completes but before the DOMContentLoaded event. The `async` attribute enables complete parallelism, executing scripts immediately upon load without ordering guarantees. Performance optimization strategies place scripts at document end or use `defer` for initialization logic and `async` for independent analytics or advertisement code.

Parse errors represent a significant correctness concern despite error recovery guarantees. While the HTML5 algorithm produces a valid DOM tree from any input, the resulting structure may not match author intent. A missing closing tag for a `<div>` causes subsequent content to nest inside when the author expected sibling elements. Browser developer tools report parse errors in the console, but many developers ignore these warnings, shipping documents with hundreds of errors. Automated validation through the W3C validator or Nu Html Checker should be integrated into continuous integration pipelines to catch structural errors before deployment. Server-side rendering frameworks should emit valid HTML by construction, escaping user content and using typed template systems that prevent unclosed tags.

Content Security Policy interacts with DOM construction through inline script and style restrictions. A strict CSP that disables `'unsafe-inline'` prevents execution of inline event handlers like `onclick` attributes and inline `<script>` blocks. This security posture forces separation of behavior from structure, requiring external JavaScript files with nonce or hash validation. Template systems that generate inline handlers from user input create injection vulnerabilities; CSP failures in production indicate potential XSS attack vectors. Modern frameworks like React and Vue automatically sanitize content and use event delegation rather than inline handlers, aligning with strict CSP requirements.

Memory consumption grows with DOM tree size, impacting both heap usage and garbage collection pressure. Each element node consumes several hundred bytes for the object header, attribute map, child list, and internal engine bookkeeping. A document with one hundred thousand nodes may consume tens of megabytes of heap memory. Single-page applications that accumulate DOM nodes without cleanup—adding list items or table rows indefinitely—eventually exhaust memory and trigger browser tab crashes. Virtual scrolling techniques render only visible elements, destroying off-screen nodes and reconstructing them on demand. This approach maintains constant DOM size regardless of data set cardinality, trading CPU for memory and enabling million-row tables in browser environments.

Mutation observers provide performant change notification but require careful batching to avoid performance degradation. A mutation observer callback receives all mutations that occurred since the last callback invocation as a batch, enabling efficient processing of multiple changes. However, mutations triggered by observer callbacks themselves are delivered synchronously if the observer is configured with `attributeOldValue` or `characterDataOldValue`, potentially creating recursive callback cycles. High-frequency DOM mutations from animation loops or real-time data feeds should batch changes using `requestAnimationFrame` or microtask scheduling to minimize observer callback frequency.

Character encoding misdetection corrupts document content, producing mojibake where multi-byte characters render as garbage. The most common failure mode occurs when UTF-8 documents lack explicit encoding declarations and servers send incorrect `Content-Type` headers. The parser's prescan examines only the first kilobyte, so late `<meta charset>` declarations are ignored, requiring a reparse with the correct encoding. Best practice mandates UTF-8 for all HTML5 documents with explicit declaration in both HTTP headers (`Content-Type: text/html; charset=utf-8`) and meta tags (`<meta charset="utf-8">`) within the first 1024 bytes. Legacy encoding declarations using the `http-equiv` form (`<meta http-equiv="Content-Type" content="text/html; charset=utf-8">`) are supported but unnecessarily verbose.

The template element enables zero-cost abstraction for client-side rendering by storing inert DOM structures that clone efficiently. Unlike hidden divs, template contents never execute scripts, load images, or trigger resource fetches during initial parse. Cloning a template creates a deep copy of its DocumentFragment in a single operation, faster than parsing equivalent HTML strings with `innerHTML`. Frameworks that compile templates to JavaScript functions during build time achieve even better performance by eliminating runtime parsing entirely, but the template element provides a standards-based fallback with reasonable performance characteristics for dynamic content.

Sanitization of user-generated content requires parser-aware filtering to prevent tag injection and attribute-based XSS. Naively stripping `<script>` tags is insufficient because malicious payloads exploit event handlers (`<img onerror="...">`), javascript: URLs (`<a href="javascript:...">`), and CSS expression injection in legacy browsers. The DOMPurify library implements a comprehensive whitelist-based sanitizer that parses untrusted HTML, walks the resulting DOM tree, and removes disallowed elements and attributes according to a configurable policy. This approach leverages the browser's own parser to handle encoding complexities and edge cases, avoiding the brittle regex-based filters that attackers routinely bypass.

Accessible document structure depends on proper semantic element usage and heading hierarchy. Screen readers construct document outlines from heading elements and sectioning content, enabling users to navigate by heading level or landmark region. Skipping heading levels (`<h1>` followed by `<h3>`) creates gaps in the outline and confuses assistive technology. Presentational heading use—choosing `<h3>` for size rather than structural meaning—breaks outline coherence. The `<article>`, `<section>`, `<nav>`, and `<aside>` elements provide machine-readable semantic markers that ARIA landmarks expose to assistive technology. Modern HTML5 documents should use semantic elements rather than generic `<div>` containers with class names, enabling better accessibility, search engine optimization, and reader mode extraction in browsers.
