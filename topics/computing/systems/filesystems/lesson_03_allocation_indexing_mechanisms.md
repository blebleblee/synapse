# Lesson 3: Allocation and Indexing Mechanisms

## 1. First-Principles Intuition & Invariants

When a user process writes data to a file through the filesystem abstraction, a cascade of mechanical decisions must unfold at the block device boundary. The filesystem must answer three fundamental questions in microseconds: where should the new data physically reside on disk, how should the system remember that location for future retrieval, and how can these decisions minimize both spatial fragmentation and temporal latency across millions of operations? These allocation and indexing mechanisms form the bedrock contract between logical file abstractions and physical storage geometry, transforming high-level POSIX write semantics into concrete sector addresses on spinning platters or flash translation layer mappings on solid-state drives.

The allocation problem emerges from a fundamental constraint: physical storage devices expose a finite, contiguous address space of fixed-size blocks, typically 4096 bytes in modern systems, yet filesystems must multiplex this space across tens of thousands of files with wildly varying lifetimes and access patterns. A naive sequential allocation strategy would quickly lead to external fragmentation as files are deleted, leaving scattered holes too small for new allocations. Conversely, a purely randomized allocation strategy would destroy spatial locality, forcing disk heads to perform expensive seeks or SSDs to scatter reads across multiple NAND dies. The engineering tension between fragmentation minimization and allocation speed defines every production filesystem's design philosophy.

Block allocation strategies fundamentally partition into two mechanical approaches: bitmap-based tracking and free-list structures. A bitmap represents each allocatable block as a single bit in a densely packed array, where zero indicates free and one indicates allocated. This encoding achieves maximum space efficiency, requiring only $\frac{N}{8}$ bytes to track $N$ blocks, but imposes sequential scanning costs when searching for contiguous free regions. Free-list approaches instead maintain explicit linked structures of available blocks, enabling $O(1)$ allocation at the cost of metadata overhead and potential fragmentation as the free space becomes scattered. Modern filesystems hybridize these techniques, employing bitmaps for dense regions and extent-based tracking for large contiguous spans.

The indexing problem operates at a different layer of the storage hierarchy: given a logical file offset presented by a user-space read or write operation, how does the filesystem translate that byte offset into a physical block address with minimal indirection overhead? The canonical Unix solution employs a multi-level indexing tree embedded within each file's inode structure. Direct blocks store the first dozen or so block addresses inline, providing single-level lookup for small files that dominate real-world workloads. When files exceed this threshold, indirect blocks introduce additional layers of pointer traversal, trading increased latency for unbounded file size support. Each additional level of indirection multiplies the potential file size by the fan-out factor—typically 1024 pointers per 4KB block on 64-bit systems—but also multiplies the I/O operations required for random access patterns.

Extent-based indexing emerged as a modern alternative to the classic block-by-block indirection model, particularly suited to large sequential allocations characteristic of multimedia workloads and database files. An extent descriptor encodes both a starting block address and a length, collapsing hundreds of consecutive block pointers into a single compact tuple. When a 100MB video file can be represented by a handful of extent descriptors rather than 25,600 individual block pointers, the metadata overhead and traversal cost collapse dramatically. The ext4 filesystem's extent trees, for instance, embed up to four extent descriptors directly in the inode structure, with overflow cases triggering B-tree indexing for larger files. This design achieves $O(\log n)$ lookup complexity while maintaining cache-friendly metadata layout.

Fragmentation manifests in two distinct forms, each with different performance implications and mitigation strategies. Internal fragmentation occurs when the filesystem's fixed block size forces partial block waste—a 100-byte file still consumes a full 4096-byte block, wasting 97.5% of the allocated space. This tax is unavoidable in block-oriented storage but can be partially mitigated through tail packing techniques that store multiple small file tails within shared blocks, as employed by ReiserFS and modern extent-based designs. External fragmentation emerges from allocation patterns over time: as files are created, extended, and deleted, the free space fractures into non-contiguous regions, forcing new allocations into suboptimal locations that destroy sequential access locality and inflate seek times on rotational media.

The performance implications of allocation and indexing decisions ripple through every layer of the I/O stack, from application-level throughput to hardware-level command queue depth utilization. Sequential writes to a well-allocated file enable the block layer to merge adjacent I/O requests, maximizing transfer efficiency and allowing Native Command Queuing on SATA drives or NVMe queue depth exploitation on modern SSDs. Conversely, fragmented allocations force the elevator scheduler to reorder requests to minimize seek penalties, introducing latency variance and reducing sustained throughput. The distinction between logical and physical locality becomes critical: even if a filesystem maintains sequential logical block numbers, poor allocation decisions can scatter those blocks across distant physical locations, negating any performance benefit from the logical ordering.

## 2. Core Architecture & Mechanics

Block allocation in the ext2/ext3/ext4 lineage employs a hierarchical bitmap structure divided into block groups, each covering a fixed number of consecutive blocks on the underlying device. A typical block group on a 1TB ext4 filesystem spans 128MB of disk space, containing 32,768 blocks when using 4KB block size. Each block group maintains its own allocation bitmap, superblock backup, group descriptor, inode table, and data blocks, creating a self-contained allocation domain that enables parallel allocation decisions and limits the blast radius of corruption events. The block group descriptor cache, typically pinned in kernel memory, stores metadata about free block counts and directory entry concentrations, allowing the allocator to make informed placement decisions without scanning every bitmap.

When the kernel's page cache writeback daemon flushes dirty pages to disk, the ext4 block allocator consults the mount-time allocation policy and current free space maps to select target block groups. The multiblock allocator attempts to reserve contiguous regions for each file, maintaining per-inode preallocation windows that reduce fragmentation for streaming writes. The allocator's goal function balances multiple competing objectives: minimize distance between a file's inode and its data blocks to reduce seek time, pack related files from the same directory into nearby block groups to exploit locality of access, and avoid concentrating allocations in any single group to maintain balanced free space distribution. These heuristics encode decades of empirical filesystem research into a few hundred lines of kernel code in `fs/ext4/mballoc.c`.

The actual allocation decision unfolds through a buddy allocator variant adapted for persistent storage management. The kernel maintains multiple freelists for each block group, organized by order: order-0 lists contain individual free blocks, order-1 lists contain pairs of contiguous blocks, order-2 lists contain four-block runs, and so forth up to order-10 covering megabyte-scale contiguous regions. When an allocation request arrives for $n$ blocks, the allocator searches the appropriate order-$k$ freelist where $2^k \geq n$, splitting larger chunks if necessary and coalescing freed blocks during deallocation to reconstruct higher-order runs. This data structure ensures $O(\log N)$ allocation complexity while naturally maintaining extent-friendly contiguous allocations when free space permits.

The bitmap scanning operation represents the innermost loop of the allocation path, executed millions of times during heavy write workloads. Modern implementations leverage processor-specific bit manipulation instructions to accelerate the search for zero bits indicating free blocks. On x86-64 systems, the `BSF` (bit scan forward) and `POPCNT` (population count) instructions enable scanning 64 bits in a single CPU cycle, while ARM platforms employ `CLZ` (count leading zeros) for equivalent functionality. The kernel typically loads bitmap blocks into cache-hot memory regions and scans them in 64-byte cacheline-aligned chunks to maximize throughput. When no suitable free region exists within the current block group, the allocator falls back to a global scan across all groups, potentially triggering expensive disk I/O to read bitmap blocks not currently resident in memory.

Inode-based indexing in traditional Unix filesystems revolves around a fixed-size structure, typically 128 or 256 bytes, embedded directly in the inode table at a predetermined disk location computed from the inode number. The ext4 inode structure dedicates 60 bytes to the `i_block` array, which ext2/ext3 interpreted as fifteen 32-bit block pointers but ext4 repurposed for extent tree storage. The classical interpretation assigned the first twelve entries as direct block pointers, the thirteenth as a singly-indirect pointer referencing a block containing 1024 additional pointers, the fourteenth as doubly-indirect covering $1024^2$ blocks, and the fifteenth as triply-indirect extending to $1024^3$ blocks. This exponential addressing scheme enabled files up to approximately 2TB on 32-bit systems with 4KB blocks, though the three levels of indirection for large file access imposed severe performance penalties.

The data structures for indirect block traversal form a sparse tree where most branches remain unpopulated for typical files. A 100KB file requires only the twelve direct pointers plus a single indirect block holding 13 additional pointers, leaving the doubly and triply indirect branches completely unallocated. The filesystem must read each indirect block from disk during traversal, though the buffer cache aggressively pins frequently accessed indirect blocks to minimize I/O overhead. For sequential access patterns, the kernel's readahead logic prefetches subsequent indirect blocks before the application explicitly requests them, overlapping I/O latency with computation. Random access patterns, conversely, thrash the indirect block cache and force synchronous reads for each level of indirection, amplifying latency by factors of three to four relative to direct pointer access.

Extent-based indexing in ext4 replaces the indirect block tree with a compact B-tree variant optimized for range queries. Each extent header occupies 12 bytes, encoding a 32-bit logical block number, 48-bit physical block number, and 16-bit length field allowing spans up to 32,768 contiguous blocks (128MB at 4KB block size). The inode's `i_block` region stores an extent tree header followed by up to four inline extent entries, sufficient for files with up to four distinct contiguous regions totaling arbitrary size. When a file's allocation pattern requires more than four extents, the filesystem constructs an index node containing up to 340 child pointers (given 12-byte extent entries and 60-byte available space). The tree grows depth-first, maintaining sorted order by logical block number to enable binary search during lookups.

```
Extent Tree Structure (conceptual layout):

Inode (256 bytes)
├── Standard metadata (inode number, permissions, timestamps)
└── i_block[60 bytes]:
    ├── Extent header (12 bytes): magic=0xF30A, entries=3, max=4, depth=0
    ├── Extent 0: logical=0, physical=1048576, length=8192 blocks (32MB)
    ├── Extent 1: logical=8192, physical=2097152, length=4096 blocks (16MB)
    └── Extent 2: logical=12288, physical=3145728, length=2048 blocks (8MB)

For deeper trees with depth > 0:
├── Index node (4096-byte block):
│   ├── Extent index header: entries=340, depth=1
│   ├── Index 0: logical=0 → block 4194304 (leaf node)
│   ├── Index 1: logical=32768 → block 4198400 (leaf node)
│   └── ...
```

The extent allocation path integrates tightly with the multiblock allocator to maintain contiguous allocations. When extending a file, the kernel first attempts to expand the final extent if physically adjacent free blocks are available. The allocator consults the block group's buddy lists to check for contiguous free space immediately following the last allocated block, enabling extent growth without tree modification. If no adjacent space exists, the allocator searches nearby block groups for a suitably large contiguous region, creating a new extent entry and potentially triggering tree reorganization if the inline extent array overflows. This design naturally produces well-packed extent trees for sequential write patterns while gracefully degrading to fragmented layouts only when free space geometry forces it.

The translation from file offset to physical block address during read operations proceeds through a binary search over the extent tree. The kernel extracts the target logical block number by dividing the byte offset by the block size, then descends the extent tree comparing logical block ranges at each level. Modern implementations leverage CPU branch prediction by organizing extent tree nodes in sorted order and employing prefetch hints to load child nodes into cache before comparison completes. For cache-resident extent trees, the lookup completes in hundreds of nanoseconds; for tree nodes resident only on disk, each level of indirection adds 5-10 milliseconds on rotational media or 50-100 microseconds on NVMe SSDs. The extent tree depth rarely exceeds three levels even for terabyte-scale files with fragmented allocations, providing logarithmic lookup complexity with manageable constant factors.

XFS takes extent-based allocation further through its B+tree file fork structure, maintaining separate trees for data extents and extended attributes. The XFS inode format, typically 512 bytes, embeds a 100-byte data fork region that can hold either inline data for tiny files, a small extent list, or a B+tree root. The extent list format stores extent records sorted by file offset, each encoding a 54-bit starting block number, 52-bit logical offset, and 21-bit length, enabling files up to 8 exabytes with extent runs spanning 8TB. When the inline extent list exhausts its capacity, XFS converts the fork to a B+tree format, allocating separate filesystem blocks for tree nodes and linking them through a classic B+tree pointer structure. This design achieves optimal space utilization for small files while scaling efficiently to massive sparse files common in database and virtualization workloads.

The XFS allocator operates through allocation groups similar to ext4's block groups but with more sophisticated free space indexing. Each allocation group maintains two B+trees tracking free space: one indexed by starting block number for address-ordered allocation and another indexed by extent length for best-fit allocation. When the allocator searches for $n$ contiguous free blocks, it queries the length-indexed tree to find the smallest available extent satisfying the request, minimizing fragmentation by avoiding waste of larger free regions. The dual-tree design imposes bookkeeping overhead—each free space change requires updates to both trees—but enables precise allocation decisions that measurably reduce fragmentation over filesystem lifetime compared to simpler bitmap approaches.

```c
/* Simplified XFS extent record structure */
typedef struct xfs_bmbt_rec {
    __be64 l0;  /* Packed: logical offset (52 bits) + extent flag (1 bit) */
    __be64 l1;  /* Packed: start block (52 bits) + block count (21 bits) */
} xfs_bmbt_rec_t;

/* Unpacking logical offset from extent record */
static inline xfs_fileoff_t xfs_bmbt_get_startoff(xfs_bmbt_rec_t *r) {
    return be64_to_cpu(r->l0) >> 9;
}

/* Unpacking physical block address */
static inline xfs_fsblock_t xfs_bmbt_get_startblock(xfs_bmbt_rec_t *r) {
    return (be64_to_cpu(r->l1) >> 21) & 0x000FFFFFFFFFFFFF;
}

/* Unpacking extent length */
static inline xfs_filblks_t xfs_bmbt_get_blockcount(xfs_bmbt_rec_t *r) {
    return be64_to_cpu(r->l1) & 0x1FFFFF;
}
```

Delayed allocation represents a critical optimization enabled by modern extent-based architectures, deferring the physical block assignment decision until page writeback time rather than at initial write system call. When a process writes to a file through buffered I/O, the kernel immediately copies data into the page cache but marks the pages as delalloc—delayed allocation—without consulting the block allocator. Only when the writeback daemon flushes dirty pages to disk, potentially seconds or minutes later, does the filesystem commit to physical block assignments. This temporal decoupling provides enormous allocation flexibility: the allocator can observe the entire pending write pattern across all files, make globally optimal placement decisions, and create large contiguous extents by batching small writes that arrived sequentially in time even if separated by other I/O operations.

The delayed allocation state requires careful accounting to prevent overcommit disasters. The filesystem maintains per-inode reservations tracking the maximum space that could be required if all delalloc pages were flushed simultaneously with worst-case fragmentation. When the total reserved space approaches the filesystem's free space limit, new write operations receive ENOSPC errors even though actual block allocation has not yet occurred. This conservative accounting prevents the pathological scenario where the filesystem runs out of space mid-writeback, forcing data loss or inconsistency. The reservation overhead imposes additional bookkeeping in the page cache layer—each delalloc page carries metadata noting its reservation status—but the allocation quality improvements typically outweigh the memory cost, particularly for workloads dominated by small buffered writes like log file appends or database transaction logs.

## 3. High-Performance Optimization & Failure Modes

Allocation performance tuning begins with block group selection heuristics that minimize long-term fragmentation while maximizing short-term allocation speed. The ext4 `orlov` allocator, named after its original author, employs a randomized load-balancing approach for directory allocations: when creating a new directory, the kernel selects a block group with above-average free space and below-average directory concentration, spreading directory trees across the disk to prevent hotspots. For regular files, the allocator prefers the block group containing the parent directory's inode, exploiting the empirical observation that files in the same directory often get accessed together. These heuristics encode implicit assumptions about access patterns—assumptions that break down for certain workloads like object storage systems with uniform access distributions, but prove remarkably robust across decades of filesystem evolution.

Preallocation mechanisms give applications explicit control over physical layout when standard heuristics prove insufficient. The `fallocate` system call with `FALLOC_FL_KEEP_SIZE` flag instructs the filesystem to reserve contiguous disk space without initializing it or updating the file size, enabling applications to preallocate entire files before writing data. Database systems exploit this capability to create large sparse files for tablespace allocation, ensuring contiguous physical layout that minimizes seek overhead during random access workloads. The kernel's implementation differs across filesystems: ext4 allocates uninitialized extents marked with a special flag that triggers zeroing on first read, while XFS employs speculative preallocation that automatically discards unused regions during file close or truncation.

Online defragmentation tools address fragmentation accumulation in aging filesystems, though their effectiveness depends heavily on filesystem architecture and workload characteristics. The `e4defrag` utility for ext4 employs a donor file technique: it allocates a temporary contiguous extent, copies the fragmented file's data into the new location using kernel assistance to maintain atomicity, then swaps the extent trees in a single transaction. This approach requires double the file's space temporarily and performs poorly on near-full filesystems where contiguous free space is scarce. XFS's `xfs_fsr` (filesystem reorganizer) operates opportunistically during idle periods, incrementally relocating fragmented files to improve layout without requiring atomic swaps, but achieving optimal layout may require multiple passes over the filesystem spanning hours or days.

Extent tree depth profoundly impacts random access performance, particularly for highly fragmented large files. A file with 1000 non-contiguous extent ranges forces the kernel to maintain a 1000-entry extent tree, potentially spanning multiple levels and requiring multiple disk I/O operations per random read. The performance cliff emerges around the point where extent trees exceed CPU cache capacity: an extent tree resident in L3 cache enables sub-microsecond lookups, while a tree spanning multiple disk blocks forces millisecond-scale latencies on each access. Production monitoring should track per-file extent counts through filesystem-specific tools like `filefrag` on Linux, alerting when critical files exceed vendor-recommended thresholds—typically 30-50 extents for database files where random access dominates.

```bash
# Examine extent fragmentation for critical database file
filefrag -v /var/lib/postgres/data/base/16384/relation_12345
```

Free space fragmentation requires different mitigation strategies than file fragmentation, as the allocator cannot simply relocate free blocks without touching allocated data. The reserve pool mechanism employed by many filesystems dedicates 5-10% of total capacity as allocator-only space, hidden from user-visible free space counts. This reserve enables the allocator to always find contiguous regions for critical metadata operations and large sequential writes even when user-visible free space fragments badly. The reserve threshold typically triggers emergency cleanup behaviors: the kernel may defer deletion operations, compact small free regions into larger spans through aggressive defragmentation passes, or even refuse new allocations for non-privileged users while allowing root operations to complete. These behaviors prevent complete filesystem deadlock but can surprise administrators who observe ENOSPC errors while `df` reports gigabytes of available space.

Tail packing optimizations exploit the observation that most files are small—file size distributions follow a long-tail Pareto distribution where the median file is tens of kilobytes while the mean is orders of magnitude larger. Rather than waste most of a 4KB block for a 100-byte file, tail packing filesystems store multiple small file tails within shared blocks, often dedicating special block groups for tail storage. ReiserFS pioneered this technique with its balanced tree structure that stored file tails as internal tree nodes, while modern implementations like bcachefs employ more conventional approaches with dedicated tail blocks. The space savings can reach 30-40% on workloads dominated by configuration files and small scripts, but complexity increases significantly: the allocator must maintain reference counts on shared blocks, handle cases where tail files grow beyond tail block capacity, and ensure atomic updates when multiple files share tail storage.

The copy-on-write allocation strategy employed by Btrfs and ZFS inverts the traditional update-in-place model, treating all writes as allocations of new blocks rather than overwrites of existing ones. When an application modifies a 4KB region in the middle of a file, the filesystem allocates a fresh block, writes the new data, updates the extent tree to point to the new location, then marks the old block as free—all within a transaction that maintains crash consistency. This design provides atomic snapshot semantics almost for free, as snapshots merely increment reference counts on existing extents, but imposes allocation overhead on every write operation. Workloads dominated by random overwrites suffer worst-case performance as each small write fragments the free space and increases extent tree complexity, while sequential write patterns remain relatively unaffected.

Write amplification emerges as the dominant performance concern in copy-on-write architectures, particularly when combined with SSDs where write endurance matters. A single 4KB application write may trigger a cascade of metadata updates: the extent tree leaf node must be rewritten, its parent index node must be rewritten to point to the new leaf, and eventually the filesystem root must be updated. In pathological cases, a 4KB write can amplify to 20-30KB of physical I/O when accounting for indirect metadata updates. Modern CoW filesystems mitigate this through batching and delayed metadata updates, aggregating many small logical writes into fewer physical operations, but the fundamental amplification remains. Production deployments must carefully tune snapshot frequency and retention policies to balance the convenience of point-in-time recovery against the steady accumulation of write amplification overhead.

Alignment considerations grow increasingly critical as storage devices expose complex internal geometries. SSDs employ pages (typically 4KB or 8KB), erase blocks (256KB to 4MB), and channels spanning multiple dies, with optimal performance requiring writes aligned to erase block boundaries. Shingled Magnetic Recording (SMR) drives organize tracks into zones requiring sequential write patterns, with random writes forcing expensive track rewrites. The filesystem can observe these characteristics through the block device topology interface, which exposes alignment offsets, optimal I/O sizes, and discard granularity. Filesystems that respect these hints can achieve 2-3× performance improvements on modern hardware, but many legacy systems default to conservative 4KB block alignment that leaves performance on the table.

```bash
# Query block device topology for alignment optimization
cat /sys/block/nvme0n1/queue/optimal_io_size      # Optimal write size in bytes
cat /sys/block/nvme0n1/queue/physical_block_size   # Minimum atomic write unit
cat /sys/block/nvme0n1/alignment_offset            # Partition alignment offset
cat /sys/block/nvme0n1/queue/minimum_io_size       # Minimum recommended I/O size

# Example output interpretation for NVMe SSD:
# optimal_io_size: 0 (no preference, device handles all sizes well)
# physical_block_size: 4096
# alignment_offset: 0 (partition starts at device boundary)
# minimum_io_size: 4096
#
# Configure filesystem with matching geometry:
mkfs.ext4 -b 4096 -E stride=16,stripe_width=64 /dev/nvme0n1p1
# stride=16: RAID stripe unit in blocks (64KB / 4KB = 16)
# stripe_width=64: full stripe size across all disks (256KB / 4KB = 64)
```

The discard operation, exposed through `TRIM` on SATA SSDs and `UNMAP` on NVMe devices, notifies the storage controller when filesystem blocks transition to free state, enabling garbage collection and wear leveling optimizations. The kernel can issue discards synchronously during block deallocation, batched periodically through `fstrim` invocations, or continuously through the `discard` mount option. Synchronous discard imposes latency penalties on delete operations, sometimes adding tens of milliseconds per freed extent, but ensures the SSD's free block pool remains maximally populated. Batched discard amortizes overhead by accumulating free regions over time and issuing bulk discard commands during idle periods, striking a balance between SSD performance and filesystem delete latency. Production systems typically employ weekly `fstrim` cron jobs combined with filesystem aging monitoring to trigger emergency discard passes when SSD performance degradation becomes measurable.

Failure modes in allocation subsystems often manifest as silent performance degradation rather than catastrophic errors. The allocator's failure to find contiguous free space forces fallback to fragmented layouts, incrementally increasing average I/O latency from microseconds to milliseconds as extent counts grow. Applications rarely detect this degradation through return codes—write operations succeed but subsequent read performance mysteriously degrades. Proactive monitoring requires instrumenting extent counts, average extent sizes, and free space fragmentation metrics, establishing baseline performance expectations, and alerting when key metrics drift beyond acceptable thresholds. The challenge lies in distinguishing expected aging from pathological fragmentation requiring intervention, typically through statistical analysis of per-file extent distributions compared against filesystem-wide population statistics.

Corruption in allocation metadata—flipped bits in bitmaps or extent trees due to hardware errors or software bugs—triggers Byzantine failure modes that confound debugging. A corrupted bitmap might mark allocated blocks as free, enabling the allocator to double-allocate blocks to different files, leading to cross-file data corruption that only manifests when applications read those specific blocks. Extent tree corruption can cause kernel panics during file access as the filesystem attempts to read block addresses that fall outside device boundaries. Modern filesystems employ metadata checksumming to detect corruption at access time: ext4's metadata checksums cover bitmaps, extent trees, and directory entries, enabling detection of corruption before it propagates into data corruption. The recovery path typically involves running `fsck` in repair mode, though the tool must make heuristic decisions about which metadata structures to trust when multiple checksums fail, sometimes discarding user data to preserve filesystem consistency.

The interaction between filesystem allocation and upper layers like LVM or software RAID introduces subtle performance pathologies when alignment assumptions break. A filesystem with 64KB stripe width optimized for RAID-5 performance will suffer dramatically if the underlying LVM physical extent size misaligns with stripe boundaries, forcing every logical stripe to span multiple physical RAID stripes and doubling the I/O overhead. These misalignments rarely cause functional failures but can reduce throughput by 50-70%, manifesting as mysterious underperformance relative to expected hardware capabilities. Diagnostic validation requires examining the complete storage stack from filesystem mount options through device mapper table entries down to physical device geometry, verifying consistent alignment at every layer.
