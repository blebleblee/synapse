# Lesson 4: I/O Redirection, Pipes, Here-Documents, Built-in Commands

## 1. First-Principles Intuition & Invariants

At the heart of Unix process execution lies a deceptively simple abstraction: the file descriptor table. When the kernel creates a new process through the `fork()` system call, it duplicates the parent's file descriptor table into the child's address space, establishing an inheritance chain that forms the foundation of all shell I/O manipulation. Each entry in this table is fundamentally a pointer into the kernel's global open file table, which itself maintains offset positions, access modes, and reference counts to underlying inodes in the virtual filesystem layer.

The shell's primary responsibility during command execution is to surgically manipulate this file descriptor table before invoking `execve()`, which replaces the process image while preserving the descriptor state. This preservation property creates a powerful invariant: any redirection established by the shell persists across the `exec` boundary into the executed program, appearing to that program as if the file descriptors were opened directly by its own code. The program remains blissfully unaware that descriptor 1 (standard output) might point to a file rather than a terminal, or that descriptor 0 (standard input) is reading from a pipe rather than keyboard input.

The canonical file descriptor trinity—0 for standard input, 1 for standard output, and 2 for standard error—represents a convention rather than a kernel mandate. The POSIX specification reserves descriptors 0 through 2 for this purpose, but the kernel imposes no semantic meaning on these numbers. They are simply indices into the process's descriptor array, a flat table typically sized to 1024 entries by default (the `RLIMIT_NOFILE` soft limit), though modern systems support dynamic expansion into the millions. When Bash prepares to execute a command, it operates on a cloned descriptor table inherited from its own shell process, using low-level `dup2()` system calls to atomically replace entries before the final `execve()`.

The semantics of I/O redirection rest on a critical ordering invariant: redirections are evaluated strictly left-to-right within a command line, with later redirections potentially overwriting earlier ones. This left-to-right evaluation order, combined with the atomic nature of `dup2()`, ensures predictable descriptor manipulation even in complex chains. Consider the expression `command >file 2>&1`, which first redirects descriptor 1 to `file`, then duplicates that file-backed descriptor into slot 2, causing both stdout and stderr to write to the same underlying file offset. Reversing this order to `command 2>&1 >file` produces fundamentally different semantics: descriptor 2 first captures wherever descriptor 1 currently points (typically the terminal), then descriptor 1 gets redirected to `file`, leaving stdout and stderr diverged.

Pipelines introduce a second foundational mechanism: the anonymous pipe, a kernel-managed circular buffer of fixed size (historically 4096 bytes, modernized to 65536 bytes on Linux since kernel 2.6.11, and further increased to 1048576 bytes in recent versions). When Bash encounters the pipe operator `|`, it invokes the `pipe()` system call to create a unidirectional communication channel represented by two file descriptors: a read end and a write end. The shell then forks two child processes, connecting the write end of the pipe to descriptor 1 of the left command and the read end to descriptor 0 of the right command. Both processes execute concurrently, with the kernel mediating flow control through buffer management: writes block when the pipe is full, reads block when the pipe is empty, and the read end receives EOF when the write end closes.

This concurrent execution model creates subtle but critical invariants regarding data visibility and atomicity. Pipe writes smaller than `PIPE_BUF` (guaranteed by POSIX to be at least 512 bytes, typically 4096 on Linux) are atomic—the kernel will not interleave bytes from concurrent writers. Beyond this threshold, writes may be fragmented, and multiple processes writing to the same pipe can produce intermingled output. Similarly, the pipe buffer acts as a decoupling mechanism between producer and consumer rates, but once filled, backpressure propagates to the writer through blocking, creating a natural pacing mechanism that prevents unbounded memory consumption.

Here-documents represent a third major mechanism, syntactically distinct but mechanically implemented through temporary file descriptors. When Bash encounters a here-document construct `<<EOF`, it doesn't create a physical disk file (in typical interactive usage). Instead, it buffers the document content in memory and presents it to the command through a pipe or a `/dev/fd/` descriptor, depending on shell implementation and available kernel features. The crucial distinction from standard input redirection is timing: here-document content is captured and processed during command parsing, allowing variable expansion, command substitution, and quote removal before execution begins. This preprocessing phase means that constructs like `cat <<EOF\n$HOME\nEOF` expand the `$HOME` variable at parse time, embedding the result into the buffered content.

Built-in commands operate under a fundamentally different execution model than external programs. When Bash recognizes a built-in like `read` or `printf`, it bypasses the entire `fork`-`exec` sequence, executing the command within the shell's own process context. This has profound implications for I/O redirection: redirections applied to built-ins modify the shell's own descriptor table, and Bash must meticulously save and restore the original descriptors after built-in completion to maintain shell state integrity. The `exec` built-in exploits this same mechanism in reverse—it allows permanent modification of the shell's descriptors without launching a subprocess, enabling constructs like `exec 3>file` to open a persistent file descriptor that remains available across multiple commands.

The mathematical foundation of descriptor manipulation reduces to a few atomic operations: `open()` to allocate new descriptors from the lowest available index, `close()` to deallocate and return indices to the pool, `dup2(oldfd, newfd)` to atomically close `newfd` and make it an alias for `oldfd`, and `fcntl()` with `F_DUPFD` to duplicate descriptors with index constraints. Bash orchestrates these primitives through a state machine that tracks which descriptors are user-visible (the standard 0-2 trinity), which are internally allocated for pipe coordination, and which represent saved versions for restoration after built-in execution. This state machine must handle edge cases like descriptor number exhaustion, EMFILE errors when the process limit is reached, and ENFILE when the system-wide open file table overflows.

## 2. Core Architecture & Mechanics

The redirection operators form a compact but complete algebra for descriptor manipulation. The fundamental form `>file` implements output redirection by opening `file` in write mode (with `O_WRONLY | O_CREAT | O_TRUNC` flags) and duplicating the resulting descriptor into slot 1. The noclobber shell option (`set -C`) modifies this behavior to use `O_EXCL`, causing redirection to fail atomically if the file already exists, preventing accidental overwrites in scripts that handle sensitive data. The append form `>>file` substitutes `O_APPEND` for `O_TRUNC`, positioning writes at the file's end regardless of concurrent modifications by other processes—a critical property for log accumulation in multi-process systems.

Input redirection `<file` mirrors the output mechanism, opening the file in read-only mode and duplicating into descriptor 0. The symmetry extends to numeric forms: `3>file` redirects an arbitrary descriptor number, enabling sophisticated descriptor juggling. The here-string `<<<string` provides syntactic sugar for simple input substitution, mechanically equivalent to `echo string | command` but implemented without a subprocess or pipe overhead. Bash expands the string, appends a newline, and presents it through a temporary descriptor, making it ideal for feeding single-line input to commands like `read` or `grep`.

Descriptor duplication takes two forms: `>&` for output duplication and `<&` for input. The expression `2>&1` duplicates descriptor 1 into slot 2, creating an alias where both descriptors point to the same open file table entry, sharing file offset and flags. This sharing has a subtle consequence: writes to either descriptor interleave atomically at the kernel level, but applications that alternate between stdout and stderr may produce garbled output if they assume independent buffering. The close operator `>&-` closes the specified descriptor, implemented through `close()`, which decrements the open file table reference count and deallocates the descriptor index. Closing stdin with `<&-` or stdout with `>&-` leaves programs in a precarious state—many will crash on the next I/O attempt with EBADF (bad file descriptor), while others silently ignore errors, creating debugging nightmares.

Here-documents introduce delimiter parsing and expansion semantics. The construct takes the form:

```bash
command <<[-]DELIMITER
content line 1
content line 2
DELIMITER
```

The optional hyphen after `<<` activates tab-stripping mode, removing leading tab characters (not spaces) from each line, allowing indented here-documents in structured scripts without embedding that indentation in the data. The delimiter itself undergoes quote removal but no other expansion—quoting any character in the delimiter (e.g., `<<'EOF'` or `<<E\OF`) disables all expansion within the document body, treating content as literal text. Without quoting, the document undergoes full parameter expansion (`$var`), command substitution (`` `cmd` `` or `$(cmd)`), and arithmetic expansion (`$((expr))`), but not pathname expansion (globbing) or brace expansion.

The expansion timing creates an important distinction from runtime input: here-document expansion occurs during command parsing, before the command executes. This means that variables referenced in the here-document reflect their values at parse time, not at execution time. For most scripts, this distinction is invisible, but in complex scenarios involving traps or signal handlers that modify variables, the parse-time snapshot behavior can produce unexpected results. The shell buffers the entire expanded content before launching the command, removing any opportunity for the command to influence expansion through side effects.

Pipelines chain commands through a graph of anonymous pipes, with Bash orchestrating a precisely timed sequence of forks and descriptor manipulations. Consider the three-stage pipeline `cmd1 | cmd2 | cmd3`. Bash executes the following orchestration:

```
1. pipe() → [fd_a_read, fd_a_write]  (connects cmd1 to cmd2)
2. pipe() → [fd_b_read, fd_b_write]  (connects cmd2 to cmd3)
3. fork() → child_1:
     close(fd_a_read)
     dup2(fd_a_write, 1)
     close(fd_a_write)
     close(fd_b_read, fd_b_write)
     exec(cmd1)
4. fork() → child_2:
     dup2(fd_a_read, 0)
     close(fd_a_read)
     close(fd_a_write)
     dup2(fd_b_write, 1)
     close(fd_b_write)
     close(fd_b_read)
     exec(cmd2)
5. fork() → child_3:
     close(fd_a_read, fd_a_write)
     dup2(fd_b_read, 0)
     close(fd_b_read)
     close(fd_b_write)
     exec(cmd3)
6. Parent closes all pipe descriptors and waits
```

This descriptor choreography ensures that each command receives exactly the descriptors it needs while closing all others, preventing descriptor leaks and ensuring proper EOF propagation. When `cmd1` terminates and its process descriptor table is deallocated, the kernel closes all open descriptors, including the write end of pipe A. This closure decrements the reference count on the pipe's write end to zero (since `cmd2` already closed its copy), causing the kernel to signal EOF on the read end, which `cmd2` observes as a zero-byte `read()` return. The same EOF cascade propagates through `cmd2` to `cmd3`.

Process substitution `<(command)` and `>(command)` provide a powerful generalization of pipelines, exposing the pipe endpoints as pseudo-filenames that can be passed to commands expecting file arguments. On Linux, Bash implements this through `/dev/fd/` entries (which are symlinks to `/proc/self/fd/`) backed by anonymous pipes. When the shell encounters `<(cmd)`, it creates a pipe, forks a subprocess to run `cmd` with stdout redirected to the write end, and synthesizes a filename like `/dev/fd/63` that represents the read end. The command receiving this filename can open it normally, unaware that reads are actually pulling data from the pipe. This mechanism enables elegant transformations like `diff <(sort file1) <(sort file2)`, which compares sorted versions of two files without creating temporary disk files.

The `read` built-in implements the shell's fundamental input tokenization mechanism, consuming data from stdin (or a specified descriptor via `read -u N`) and splitting it into shell variables. The splitting algorithm respects the `IFS` (Internal Field Separator) variable, which defaults to space, tab, and newline. The command `read a b c` reads a line, splits it on IFS characters, assigns the first field to `a`, the second to `b`, and all remaining fields (including any embedded separators) to `c`. The `-r` flag disables backslash escape processing, treating backslashes as literal characters rather than escape sequences—a critical option when reading arbitrary data that might contain backslash-newline continuations or escape codes.

The `printf` built-in provides formatted output with semantics derived from C's `printf()` but adapted for shell string handling. Unlike `echo`, whose behavior varies across implementations (especially regarding backslash interpretation and newline appending), `printf` offers standardized, predictable output formatting. The format string accepts the full repertoire of conversion specifiers: `%s` for strings, `%d` for signed integers, `%u` for unsigned, `%x` and `%X` for hexadecimal, `%o` for octal, `%f` for floating-point, and `%b` for backslash-escaped strings. Width and precision modifiers work as in C, and the command automatically repeats the format string to consume all arguments, a unique shell extension that simplifies loops.

The `exec` built-in serves dual purposes: replacing the shell process with a new program (the traditional `exec` behavior) or manipulating the shell's own descriptor table without replacement. When invoked without a command, as in `exec 3>file`, it opens the file and assigns descriptor 3 in the shell's process, making it available to all subsequent commands until explicitly closed with `exec 3>&-`. This pattern enables long-lived file handles in scripts, avoiding the overhead of repeated open/close cycles. The command `exec > file` redirects the shell's own stdout permanently, affecting all subsequent commands in the script—a technique sometimes used for log file redirection but fraught with risk, as it breaks interactive output and complicates error handling.

Trap handlers, registered with the `trap` built-in, execute within the shell's process context when signals arrive or when special pseudo-signals like `EXIT`, `ERR`, or `DEBUG` trigger. The handler inherits the shell's descriptor state at the moment of invocation, meaning that descriptors opened by earlier commands or `exec` remain accessible. This property enables sophisticated error logging patterns where `trap` handlers redirect output to dedicated log descriptors. The `trap - SIGNAME` form removes a handler, restoring default signal disposition, while `trap '' SIGNAME` sets an ignore handler, useful for preventing `SIGINT` (Ctrl-C) from interrupting critical sections.

Coprocesses, a bash-specific extension invoked with `coproc`, create a persistent bidirectional communication channel with a background command. The syntax `coproc cmd` launches `cmd` with stdin and stdout connected to pipes, which Bash exposes through array variables `${COPROC[0]}` (stdout read end) and `${COPROC[1]}` (stdin write end). Named coprocesses take the form `coproc NAME { cmd; }`, populating `${NAME[0]}` and `${NAME[1]}`. This mechanism enables stateful dialog with long-running processes, such as database CLIs or interactive tools, without launching a new process per interaction. The coprocess model differs from process substitution in persistence: the subprocess remains running across multiple read/write cycles, maintaining state between interactions.

## 3. High-Performance Optimization & Failure Modes

The performance characteristics of I/O redirection and pipelines hinge on kernel buffering strategies and process scheduling latency. Pipes implement finite-length circular buffers in kernel space, sized at 65536 bytes by default on modern Linux (retrievable via `fcntl(fd, F_GETPIPE_SZ)`). This buffer size creates a critical performance inflection point: pipelines with data volumes below the pipe capacity operate at near-memory speeds, while larger volumes incur blocking write overhead as the producer waits for the consumer to drain the buffer. The blocking behavior serializes pipeline stages, preventing runaway memory consumption but potentially underutilizing CPU if the consumer runs slower than the producer.

Optimizing pipeline throughput requires understanding this producer-consumer dynamic. When the producer generates data faster than the consumer processes it, the pipe buffer fills, blocking the producer in the kernel's wait queue. The consumer's `read()` drains the buffer, unblocking the producer, which then races to refill the buffer before blocking again. This cycle creates a sawtooth pattern in memory usage and CPU utilization, with frequent context switches between blocked and runnable states. Tools like `pv` (pipe viewer) or `mbuffer` can interpose between stages to provide larger intermediate buffers in userspace, smoothing out bursts and reducing context switch frequency at the cost of increased memory consumption.

File descriptor exhaustion represents a common failure mode in complex scripts that open many files or pipelines without closing them. The process limit (`ulimit -n`) defaults to 1024 open files on many systems, a seemingly large number until considering that each pipe consumes two descriptors, each pipeline stage multiplies descriptor consumption, and network sockets or database connections also allocate from the same pool. Scripts that dynamically construct pipelines in loops must explicitly close descriptors with `exec {fd}>&-` or risk hitting EMFILE (too many open files in process), which manifests as cryptic failures when `open()` or `pipe()` return -1. The system-wide limit (`/proc/sys/fs/file-max`) also imposes a cap, triggerable in high-concurrency scenarios where many processes open files simultaneously.

Here-document size limitations stem from memory buffering constraints. Since Bash buffers the entire expanded here-document content before executing the command, extremely large documents (megabytes to gigabytes) can cause memory exhaustion, especially in memory-constrained containers or embedded systems. The buffering approach also prevents streaming large datasets through here-documents—the shell must finish expanding the entire document before the command starts reading. For large data volumes, external files or process substitution offer superior memory profiles, as they stream data incrementally rather than buffering completely.

Redirection order bugs rank among the most insidious script defects because they produce silent misbehavior rather than explicit errors. The classic mistake `command 2>&1 >file` intends to redirect both stdout and stderr to `file` but actually sends stderr to the terminal and only stdout to the file. The error arises from left-to-right evaluation: `2>&1` first duplicates descriptor 1 (still pointing to the terminal) into descriptor 2, then `>file` redirects descriptor 1 to the file, leaving descriptor 2 orphaned on the terminal. The correct order `command >file 2>&1` first redirects stdout to the file, then duplicates that file-backed descriptor into stderr, unifying both streams.

Race conditions in pipeline exit status checking emerge from Bash's `wait()` semantics. In a pipeline `cmd1 | cmd2 | cmd3`, the special variable `$?` captures only the exit status of `cmd3`, the rightmost command. The `PIPESTATUS` array provides individual exit codes for each stage, but only if read immediately—subsequent commands overwrite the array. The bash option `set -o pipefail` alters this behavior, causing the pipeline to report a non-zero exit status if any stage fails, but it reports the rightmost non-zero status, not necessarily the first failure. Scripts requiring precise failure diagnosis must capture `PIPESTATUS` immediately after the pipeline and inspect each element, a pattern often wrapped in a helper function for reusability.

Buffering artifacts cause unexpected behavior when mixing stdio-based and descriptor-based I/O. When a program writes to stdout via `printf()` or `puts()`, the C standard library buffers the output in userspace (4096 bytes by default) before issuing `write()` system calls. If the program then directly writes to descriptor 1 via `write()`, that output bypasses the buffer and interleaves with buffered content in unpredictable order. Similarly, when a script redirects stdout of a buffered program, the buffer mode may change from line-buffered (for terminals) to fully-buffered (for files or pipes), causing output to appear delayed or reordered. The `stdbuf` utility or `setvbuf()` within programs can force buffering modes, but scripts often can't control external programs' buffering policies.

Signal handling during blocked I/O operations introduces subtle failure modes. When a process blocks in `read()` on a pipe and receives a signal, the kernel interrupts the `read()`, causing it to return -1 with `errno` set to `EINTR` (interrupted system call). Well-written programs retry the `read()`, but many scripts and tools fail to handle `EINTR`, treating it as a fatal error. Bash itself handles `EINTR` transparently during built-in operations, but external commands may misbehave. Pipelines compound this issue: if a signal interrupts one stage, EOF propagates to downstream stages, which may terminate prematurely, leaving upstream stages blocked on writes to a broken pipe, eventually receiving `SIGPIPE` and terminating with status 141.

The broken pipe scenario manifests when a pipe reader terminates before the writer finishes. The writer's next `write()` call triggers a `SIGPIPE` signal, which by default terminates the process. Many scripts inadvertently create this condition through constructs like `cat large_file | head -10`, where `head` reads 10 lines and exits, closing its stdin. The `cat` process, still writing, receives `SIGPIPE` and terminates with exit code 141 (128 + 13, where 13 is `SIGPIPE`'s signal number). While benign in interactive use, this can break scripts that check exit codes strictly. The bash option `set -o pipefail` propagates this non-zero status to the pipeline's overall exit code, potentially triggering error handlers. Defensive scripts either ignore `SIGPIPE` with `trap '' PIPE` (risky, as it prevents normal termination) or accept 141 as a success code in specific contexts.

Descriptor leaks across `exec` boundaries pose security and resource risks. When a script opens a descriptor with `exec 3>file` and then launches a subprocess via a function or command substitution, that subprocess inherits descriptor 3 unless explicitly closed. If the subprocess is untrusted or unaware of the descriptor, it might inadvertently read or write to the file, creating information disclosure or corruption vectors. The `close-on-exec` flag (`O_CLOEXEC`, set via `fcntl(fd, F_SETFD, FD_CLOEXEC)`) instructs the kernel to close the descriptor automatically during `execve()`, preventing inheritance. Bash doesn't expose `O_CLOEXEC` directly, so scripts must manually close descriptors before subshells or use `{fd}>&-` patterns judiciously.

Performance tuning for here-documents involves minimizing expansion overhead. A here-document with extensive command substitutions like `$(expensive_command)` delays command execution while the shell forks subprocesses to evaluate each substitution. For large documents with many substitutions, preprocessing the content into a temporary file or using process substitution can parallelize expansion work. However, for typical use cases with modest documents and simple variable substitutions, the overhead is negligible, and here-documents offer superior readability compared to echo chains or external files.

Coprocess deadlocks occur when the coprocess fills its output pipe buffer, blocking on write, while the parent script blocks reading from stdin or waiting for unrelated I/O, creating a circular wait. Since pipe writes block when the buffer fills, a coprocess that produces more than 64KB of output without the parent reading will halt. Similarly, if the parent writes more than 64KB to the coprocess's stdin without the coprocess reading, the parent blocks. Defensive coprocess interactions use non-blocking I/O (difficult in pure bash) or separate reader threads (impossible in bash), so practical solutions involve careful message sizing, flushing output explicitly, or using line-based protocols where each request-response cycle fits within the pipe buffer.

Resource limits (`ulimit`) cap various aspects of process resource consumption, including core dump size (`-c`), data segment size (`-d`), file size (`-f`), locked memory (`-l`), open files (`-n`), pipe size (`-p`), stack size (`-s`), CPU time (`-t`), and virtual memory (`-v`). Scripts running under restrictive limits may encounter silent failures when attempting to open files beyond the descriptor limit or create pipes in excess of the pipe size limit. The `ulimit` built-in allows querying and setting these limits within the shell session, but only within the bounds of hard limits inherited from the parent process or set by PAM (Pluggable Authentication Modules) at login. Exceeding hard limits requires privileged system reconfiguration, typically via `/etc/security/limits.conf` or systemd unit file directives.

Atomic operations on file descriptors are crucial for concurrent script safety. The `dup2()` system call atomically closes the target descriptor and duplicates the source in a single operation, preventing race windows where another thread or signal handler might observe the descriptor in an inconsistent state. In contrast, a sequence of `close(newfd); dup(oldfd)` is non-atomic—a signal arriving between the two calls could cause descriptor leakage or incorrect duplication. Bash's redirection operators leverage `dup2()` internally, ensuring atomic descriptor manipulation even when redirections chain. Scripts using `exec` to manually manipulate descriptors inherit this atomicity, but must remain aware that signals or traps executing concurrently can observe intermediate states between commands.

The final optimization frontier involves minimizing subprocess creation. Pipelines require forking one process per stage, each incurring scheduling overhead and memory duplication (even with copy-on-write). For simple transformations, bash's string manipulation operators (`${var//pattern/replacement}`, `${var##pattern}`, `${var%pattern}`) or arithmetic expansion `$(( ))` eliminate subprocess calls entirely. A pipeline like `echo "$var" | sed 's/foo/bar/'` forks two processes (one for `echo`, one for `sed`), while the pure-bash equivalent `${var//foo/bar}` runs in-process. Similarly, `$(( i + 1 ))` outperforms `$(expr $i + 1)`, avoiding the `expr` fork. These micro-optimizations accumulate in loops processing thousands of iterations, where fork overhead dominates runtime. However, excessive string manipulation in bash can itself become slow due to quadratic-time string concatenation in certain scenarios, so profiling remains essential to identify actual bottlenecks rather than premature optimization.
