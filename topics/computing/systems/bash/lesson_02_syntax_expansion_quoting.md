# Lesson 2: Syntax, Parameter Expansion, Quoting, Word Splitting

## 1. First-Principles Intuition & Invariants

The Bash shell operates as a staged compiler pipeline that transforms human-readable command lines into executable process graphs. At its core lies a deterministic tokenization and expansion engine that processes input text through seven distinct phases, each phase applying transformations according to invariant precedence rules established by POSIX.1-2017 and extended by Bash-specific grammar. Understanding this pipeline is not merely academic—it forms the mechanical foundation that determines whether your shell scripts exhibit correct, predictable behavior or degenerate into injection vulnerabilities, silent data corruption, and nondeterministic failures in production systems.

The fundamental insight is that the shell does not interpret commands as atomic strings. Instead, it parses input into tokens, applies recursive expansions to those tokens according to a fixed evaluation order, and only then executes the resulting command vector. This staged evaluation model means that a seemingly simple command like `cp $file "$dest"` actually invokes at least four distinct transformation phases before the `cp` binary ever receives its arguments. Each phase operates on the output of the previous phase, and crucially, later phases cannot retroactively affect earlier ones. This determinism is both a strength and a source of subtle bugs—once the shell has performed word splitting on an unquoted variable expansion, no amount of subsequent quoting can reassemble the original value.

The pipeline begins with lexical analysis, where the shell tokenizer identifies metacharacters (space, tab, newline, pipe, semicolon, ampersand, parentheses, angle brackets, dollar signs, backticks, and quotes) and partitions the input stream into words. This initial tokenization phase respects quoting boundaries—a space inside double quotes is not a word delimiter—but does not yet perform expansions. The result is a token stream that preserves the syntactic structure of the command line while deferring all semantic interpretation.

Following tokenization, the shell enters the expansion cascade, a sequence of seven ordered transformations that progressively rewrite tokens from their initial form into their final executable representation. The invariant ordering is: brace expansion, tilde expansion, parameter and variable expansion (including command substitution and arithmetic expansion, which nest recursively), word splitting, pathname expansion (globbing), quote removal, and finally redirection processing. This ordering is not arbitrary—it reflects careful language design choices that balance expressiveness with predictability. Brace expansion must precede parameter expansion because `{$var}` should expand the variable first, not attempt to generate brace sequences from the variable's value. Word splitting must follow parameter expansion because the shell needs the fully expanded text before determining where to insert field separators. Pathname expansion must follow word splitting because glob patterns should match against filenames, not against intermediate expansion artifacts.

The quoting mechanisms—single quotes, double quotes, and backslash escaping—serve as expansion suppressors that selectively disable phases of the pipeline. Single quotes impose a total blackout: no expansions of any kind occur within single-quoted strings, and every character retains its literal value except for the single quote itself. Double quotes permit a limited subset of expansions—parameter expansion, command substitution, arithmetic expansion, and backslash escaping for specific metacharacters—but critically disable word splitting and pathname expansion. This asymmetry is the key to writing robust shell scripts: double-quoting variable expansions prevents the shell from reinterpreting spaces, newlines, and glob characters embedded in variable values.

The Internal Field Separator variable `IFS` governs word splitting behavior and stands as one of the most misunderstood mechanisms in shell programming. By default, `IFS` contains space, tab, and newline, meaning the shell splits unquoted expansion results at any sequence of these whitespace characters. Modifying `IFS` changes the splitting behavior for the duration of the current shell or subshell, allowing scripts to parse structured data formats. However, `IFS` does not affect the initial tokenization phase—it only applies to the word-splitting phase that follows parameter and command substitution. This distinction is critical: setting `IFS` to a comma does not magically make commas into command separators at the syntax level.

A fundamental invariant that governs all expansion behavior is that the shell never re-parses expanded text as syntax. When a variable contains a pipe character, the shell does not interpret that pipe as a command separator during parameter expansion—it remains a literal character unless explicitly evaluated by `eval` or passed to a subshell. This property is both a security feature and a source of confusion. It prevents trivial command injection attacks where an attacker-controlled variable might contain `; rm -rf /`, but it also means that storing complex command pipelines in variables and expecting them to execute correctly will fail unless you explicitly invoke secondary evaluation.

The shell's treatment of empty and unset variables introduces another layer of invariant behavior that affects script correctness. An unset variable expands to nothing, producing zero words, while an empty variable (one set to the null string) expands to a single empty word. This distinction becomes observable during word splitting: `$unset` disappears entirely from the command line, while `$empty` contributes an argument consisting of the empty string. Quoting changes the outcome: `"$unset"` produces one empty-string argument (because double quotes preserve the expansion even when it's empty), while `"$empty"` also produces one empty-string argument. This behavior explains why `rm $file` is catastrophically dangerous when `$file` is unset or empty—it expands to `rm` with no arguments, or worse, `rm ""`, neither of which does what the author intended.

## 2. Core Architecture & Mechanics

The shell parser operates as a multi-stage finite automaton that consumes input characters and produces an abstract syntax tree representing the command structure. The parser's first responsibility is lexical scanning, which partitions the input stream into tokens. During this phase, the scanner maintains a state machine that tracks whether it is currently inside single quotes, double quotes, or unquoted context. Whitespace characters (space, tab, newline) serve as token delimiters in unquoted contexts but become literal characters within quotes. Metacharacters such as `|`, `&`, `;`, `(`, `)`, `<`, and `>` always trigger token boundaries in unquoted contexts, but they lose their syntactic meaning inside quotes.

The tokenization phase also handles backslash escaping, where a backslash preceding any character suppresses that character's special meaning for exactly one character position. This mechanism operates at the lexical level, before expansions occur. A construct like `echo \$HOME` reaches the tokenizer as four tokens: `echo`, a literal dollar sign (because the backslash removed its special meaning), and then `HOME` as separate text. The shell never sees this as a parameter expansion because the dollar sign lost its metacharacter status during tokenization.

Once tokenization completes, the shell enters the expansion cascade. The first phase is brace expansion, a Bash-specific feature (not mandated by POSIX) that generates multiple words from a single token containing brace patterns. The shell scans for patterns matching `{a,b,c}` or `{x..y}` and expands them into separate words before any variables are substituted. Brace expansion is strictly lexical—it does not interpret the contents of braces as expressions or commands. A construct like `echo {1..$n}` will not work as intended because parameter expansion has not yet occurred when the shell processes braces. The shell sees `{1..$n}` as a malformed range (since `$n` is not a number at this stage) and leaves it unexpanded.

Following brace expansion, the shell performs tilde expansion, which converts leading tilde characters into home directory paths. The expansion applies only to tokens that begin with an unquoted tilde. The shell checks if the tilde is followed by a username; if not, it expands to `$HOME`. If a username follows (as in `~alice`), the shell queries the system password database to retrieve that user's home directory. Tilde expansion is unique in that it only triggers at word boundaries—a tilde appearing mid-word, as in `foo~bar`, remains literal.

Parameter expansion constitutes the most complex phase of the pipeline, encompassing variable substitution, command substitution, and arithmetic expansion. The shell scans tokens for unquoted dollar signs and initiates recursive descent parsing to determine the expansion's extent. Parameter expansion supports several syntactic forms, each with distinct semantics. The simplest form, `$var`, expands to the value of the variable `var`. The braced form, `${var}`, allows disambiguation when the variable name is followed by characters that could be part of an identifier. For example, `$varname` expands the variable `varname`, while `${var}name` expands `var` and concatenates the literal string `name`.

The shell provides substring and pattern-matching operators within parameter expansion syntax, enabling inline text transformation without invoking external utilities. The substring extraction operator `${var:offset:length}` returns a portion of the variable's value, using zero-based indexing. Negative offsets count from the end of the string, requiring a space or parenthesis to disambiguate from the `${var:-default}` default-value syntax. Pattern removal operators `${var#pattern}`, `${var##pattern}`, `${var%pattern}`, and `${var%%pattern}` delete the shortest or longest match of `pattern` from the beginning or end of the variable's value. These operators perform glob-style pattern matching, not regular expressions, meaning `*` matches any sequence of characters while `?` matches exactly one character.

Search-and-replace expansion, written `${var/pattern/replacement}` or `${var//pattern/replacement}`, scans the variable's value for occurrences of `pattern` and substitutes `replacement`. The single-slash form replaces only the first match, while the double-slash form replaces all matches. The replacement string can reference the matched text using `&`, though this is less commonly needed than in `sed` or `awk`. Crucially, both the pattern and replacement undergo further expansion—if `replacement` contains `$x`, the shell will expand `$x` before performing the substitution. This nesting can lead to subtle bugs when the replacement itself contains dollar signs intended as literals.

Command substitution, denoted by `$(command)` or the archaic backtick form `` `command` ``, executes a subshell and captures its standard output, inserting the result into the expansion context. The shell forks a child process, redirects its standard output to a pipe, executes the command, and reads the pipe until EOF. Trailing newlines in the captured output are removed—a single trailing newline disappears, as do multiple trailing newlines, but newlines within the output are preserved. This behavior means that `$(echo)` expands to an empty string, while `$(echo ""; echo "")` expands to a single newline (the second echo's newline survives). Command substitution nests with other expansions: `$(echo $HOME)` first expands `$HOME` inside the subshell, then captures the output.

Arithmetic expansion, written `$((expression))`, evaluates integer expressions using C-style operator precedence. The shell parses the expression as a series of arithmetic operations, performing variable expansion recursively within the arithmetic context. Variables can be referenced with or without the dollar sign—both `$((x + 1))` and `$(($x + 1))` are valid, though the latter is more explicit. The shell treats all operands as signed long integers (typically 64-bit on modern systems), performing two's complement arithmetic. Division by zero triggers an error that terminates the expansion, though it does not necessarily halt script execution unless `set -e` is active.

After all expansion types complete, the shell enters the word-splitting phase, which partitions expansion results into separate arguments based on the `IFS` variable. This phase only applies to unquoted expansions—text within double quotes bypasses word splitting entirely. The shell scans each expanded token for characters present in `IFS`, splitting the token at each occurrence. Consecutive `IFS` characters collapse into a single split point if they are `IFS` whitespace (space, tab, or newline by default), but non-whitespace `IFS` characters produce empty fields. This distinction means that with `IFS=:`, the string `a::b` splits into three fields: `a`, an empty string, and `b`. With default `IFS`, multiple spaces produce only a single split.

The interaction between word splitting and empty expansions creates a subtle invariant: an unquoted expansion that produces an empty string vanishes entirely from the argument list, while a quoted expansion that produces an empty string contributes an empty-string argument. Consider the difference between `command $var` and `command "$var"` when `var` is empty. The unquoted form expands to `command` with no arguments, while the quoted form expands to `command ""`, passing an empty string as the first argument. This behavior is often counterintuitive—programmers expect that an empty variable should produce an empty argument, but the shell's word-splitting rules dictate otherwise.

Pathname expansion (globbing) follows word splitting and applies to any words containing unquoted glob metacharacters: `*`, `?`, and `[...]`. The shell scans each word for these patterns and attempts to match them against filenames in the current or specified directory. If matches are found, the shell replaces the pattern with the sorted list of matching filenames. If no matches are found, the behavior depends on shell options: by default, the pattern is left unchanged as a literal string. Setting `nullglob` causes unmatched patterns to expand to nothing (contributing zero words), while `failglob` causes the shell to report an error and abort the command.

The glob matching algorithm uses filesystem syscalls to enumerate directory entries and filters them against the pattern. The `*` metacharacter matches any sequence of characters except for leading dots (unless `dotglob` is set), while `?` matches exactly one character. Character classes `[abc]` match any single character within the brackets, and ranges `[a-z]` match any character within the range. Bracket expressions also support negation: `[!abc]` matches any character except `a`, `b`, or `c`. Extended glob patterns, enabled by `shopt -s extglob`, introduce additional constructs like `@(pattern-list)` for matching one of several alternatives and `*(pattern-list)` for matching zero or more occurrences.

Quote removal is the final syntactic transformation before command execution. At this stage, the shell strips quote characters that were not themselves escaped or quoted. Single quotes and double quotes disappear, but the text they enclosed remains. This phase is distinct from the quoting mechanisms that suppressed expansions earlier—it is purely cosmetic cleanup that removes the syntactic scaffolding after all semantic processing completes. An important consequence is that quotes are not preserved in variable assignments: `x="hello world"` stores the string `hello world` (without quotes) in `x`, and later expanding `$x` without quotes will subject it to word splitting.

The interaction between quoting and expansion phases creates a precise contract: single quotes disable all expansions, double quotes disable word splitting and globbing but permit parameter/command/arithmetic expansion, and backslash escaping disables special meaning for exactly one character. These rules compose: inside double quotes, a backslash only escapes dollar signs, backticks, double quotes, backslashes, and newlines—other characters following a backslash retain the backslash as a literal. The construct `"\$HOME"` produces the literal string `$HOME` (because the backslash escapes the dollar sign), while `"\nHOME"` produces `\nHOME` (because `\n` is not an escape sequence recognized inside double quotes; for actual newlines, you need `$'\n'` syntax).

ANSI-C quoting, written `$'...'`, provides a third quoting mechanism that interprets backslash escape sequences like `\n` (newline), `\t` (tab), `\x##` (hexadecimal byte), and `\u####` (Unicode codepoint). This syntax is a Bash extension not present in POSIX shells. It is particularly useful for embedding literal control characters in scripts without requiring actual control character bytes in the source file. The construct `echo $'line1\nline2'` prints two lines, while `echo 'line1\nline2'` prints the literal string `line1\nline2` (because single quotes suppress interpretation of backslashes).

The shell maintains a distinction between special parameters and ordinary variables. Special parameters include `$0` (script name), `$1` through `$9` (positional parameters), `$#` (argument count), `$*` (all arguments as a single word when quoted), `$@` (all arguments as separate words when quoted), `$$` (current shell PID), `$!` (background job PID), `$?` (exit status), and `$_` (last argument of previous command). The parameter `$*` and `$@` exhibit different behavior when quoted: `"$*"` expands to a single word containing all arguments separated by the first character of `IFS`, while `"$@"` expands to separate words, one per argument, preserving empty arguments. This distinction is critical for writing functions that correctly forward arguments: `"$@"` is the only form that preserves argument boundaries and empty strings.

Array variables in Bash extend the parameter expansion syntax to support indexed and associative collections. Indexed arrays use integer subscripts, with `arr[0]` accessing the first element. Array expansion `${arr[@]}` produces all elements as separate words (when quoted), while `${arr[*]}` concatenates them. The syntax `${!arr[@]}` expands to the list of defined indices, not the values, allowing iteration over sparse arrays. Associative arrays, declared with `declare -A`, use string keys instead of integer indices. The key-value iteration pattern `for key in "${!assoc[@]}"; do echo "${assoc[$key]}"; done` is the standard idiom for walking associative arrays.

## 3. High-Performance Optimization & Failure Modes

The shell's expansion pipeline incurs measurable overhead that becomes significant in tight loops or deeply nested command substitutions. Each command substitution forks a subshell, which requires duplicating the parent shell's memory image (though modern kernels use copy-on-write), setting up pipes, and performing context switches. In a loop that invokes `$(command)` thousands of times, the fork overhead dominates execution time. The optimization is to restructure the code to minimize subshell invocations—batch operations using arrays, leverage the shell's built-in string manipulation operators instead of spawning `sed` or `awk`, and prefer parameter expansion over external utilities when feasible.

Glob expansion can trigger expensive filesystem traversals when patterns match large directory trees. A pattern like `**/*.txt` with `globstar` enabled recursively descends the directory hierarchy, invoking `readdir()` syscalls for every subdirectory. On network filesystems or directories containing millions of files, this traversal can take seconds or minutes. The failure mode manifests as apparent hangs where the shell becomes unresponsive while the kernel fills page cache with directory metadata. Mitigating this requires constraining glob patterns to specific subtrees, using `find` with `-maxdepth` to control recursion, or switching to database-backed file indices for large-scale file discovery.

Word splitting interacts catastrophically with unquoted variable expansions containing embedded spaces, newlines, or glob metacharacters. The classic failure pattern is `rm $files`, where `$files` contains multiple filenames separated by spaces. If any filename contains a space, word splitting will fragment it into separate arguments, causing `rm` to delete the wrong files or report that files don't exist. The fix is trivial—`rm "$files"` if `$files` is a single filename, or iteration over an array if `$files` represents multiple files. Yet this pattern remains one of the most common sources of bugs in shell scripts because the failure mode is silent until it strikes production data.

The `IFS` variable introduces state-dependent behavior that violates the principle of lexical scoping. Modifying `IFS` in a function or script alters word-splitting behavior globally for the shell process, affecting subsequent commands even after the function returns. The standard mitigation is to save the original `IFS` value, modify it locally, and restore it: `old_IFS=$IFS; IFS=,; ...; IFS=$old_IFS`. However, this pattern itself is fragile—if the script exits or returns prematurely (due to `set -e` triggering on an error), the restoration never occurs. The robust solution is to encapsulate `IFS` changes within subshells: `(IFS=,; command)` ensures that the modification is confined to the subshell's scope and automatically reverted when the subshell exits.

Empty and unset variables create ambiguous boundary conditions that propagate through function call chains and command pipelines. The expansion `${var:-default}` provides a default value if `var` is unset or empty, but it does not distinguish between these cases. To detect unset versus empty, use `${var-default}` (without the colon), which only provides a default if the variable is unset, not if it's empty. The test `[ -z "$var" ]` checks for empty, while `[ -v var ]` checks if the variable is set (regardless of value). Mixing these constructs incorrectly leads to functions that behave differently when passed an empty string versus when passed no argument at all.

Command substitution captures trailing newlines inconsistently, which breaks assumptions about round-tripping data through variables. The idiom `content=$(cat file); echo "$content"` loses the file's final newline if one exists, because command substitution strips trailing newlines. To preserve them, append a sentinel character before capture and remove it afterward: `content=$(cat file; echo x); content=${content%x}`. This pattern is cumbersome, highlighting a fundamental impedance mismatch between the shell's text-processing model and applications that require byte-accurate data handling. For binary data or precise text preservation, the shell is the wrong tool—use `read -r -d ''` to read entire files into variables while preserving all whitespace, or avoid the shell entirely and move to Python or Perl.

Quoting failures in `eval` constructs open severe injection vulnerabilities. The `eval` built-in re-parses and executes its arguments as shell syntax, meaning that any unquoted user-controlled data can inject arbitrary commands. A construct like `eval echo $user_input` allows an attacker to supply `user_input='; rm -rf /'` and execute destructive commands. Even with quoting, `eval` is hazardous because it requires double-escaping: `eval "echo \"$var\""` quotes `$var` correctly, but forgetting the inner quotes allows word splitting and globbing within the `eval` context. The safe approach is to avoid `eval` entirely or use arrays and indirect references (`${!varname}`) to achieve dynamic variable access without textual re-parsing.

Glob patterns interacting with user-controlled filenames enable denial-of-service attacks through quadratic pattern-matching complexity. A pattern like `**/*` recursively expands, but if an attacker creates deeply nested directories (e.g., 10,000 levels deep), the glob traversal becomes computationally prohibitive. The shell lacks mechanisms to limit recursion depth or match count, so the only defense is to avoid glob expansion on untrusted input paths. Use explicit directory traversal with `find` and process filenames via piped loops or arrays rather than expanding them into the argument vector.

The split between `$*` and `$@` becomes a source of subtle bugs in functions that forward arguments. Using `"$*"` when `"$@"` is intended collapses arguments into a single word, breaking commands that expect separate arguments. The canonical example is a wrapper function: `run_cmd() { command "$*"; }` versus `run_cmd() { command "$@"; }`. The first form converts `run_cmd a b c` into `command "a b c"` (single argument), while the second preserves it as `command a b c` (three arguments). This distinction is invisible until a wrapped command requires precise argument boundaries, such as `cp`, which expects source and destination as separate arguments.

Parameter expansion's pattern matching operators use glob patterns, not regular expressions, which limits their expressive power and creates subtle mismatches with user expectations. The pattern `${var#*.}` removes the shortest match of `*.` from the beginning of `$var`, which for `foo.bar.baz` yields `bar.baz`. However, users familiar with regular expressions might expect this to remove everything up to the first dot, not the entire prefix including the dot. The mismatch arises because glob `*` is greedy and matches as much as possible, while the `#` operator searches for the shortest match. Using `##` (longest match) would change the behavior again, removing up to the last dot.

The shell's arithmetic expansion uses signed 64-bit integers on most modern systems, but older systems or 32-bit architectures use signed 32-bit integers, creating portability hazards around overflow. The expression `$((2**63))` overflows on 64-bit systems, wrapping to negative values. Bash does not trap overflow or provide arbitrary-precision arithmetic—calculations that exceed native integer width silently produce incorrect results. For large-integer arithmetic, shell scripts must invoke external tools like `bc` or `dc`, which themselves introduce overhead and require careful handling of input quoting and output parsing.

The race conditions inherent in shell scripts stem from the time-of-check-to-time-of-use (TOCTOU) gap between testing a condition and acting on it. A classic example is `[ -f "$file" ] && rm "$file"`, which checks if a file exists and then deletes it. Between the test and the removal, another process could delete the file or replace it with a symlink, causing the `rm` to delete an unintended target. The shell provides no atomic file operations, so the only defense is to structure scripts to tolerate races (e.g., use `rm -f` and ignore errors) or move critical sections to languages with proper file locking primitives.

Subshell semantics introduce surprising behavior when scripts modify variables inside command substitutions or pipelines. Variables assigned in a subshell do not persist in the parent shell, meaning `$(x=5)` has no effect on the outer environment. Similarly, `echo data | while read line; do sum=$((sum + line)); done; echo $sum` prints an empty or uninitialized value for `$sum` because the `while` loop runs in a subshell (the right-hand side of a pipe), and its modifications to `$sum` vanish when the subshell exits. The fix is to restructure code to avoid pipelines into loops, using process substitution or here-documents instead: `while read line; do sum=$((sum + line)); done < <(echo data)` executes the loop in the parent shell, preserving variable assignments.
