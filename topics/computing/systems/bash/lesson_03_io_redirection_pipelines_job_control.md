# Lesson 3: I/O Redirection, Pipelines, Job Control, Signals

## 1. First-Principles Intuition & Invariants

The Unix philosophy rests on a deceptively simple abstraction: *everything is a file*. This design decision, inherited from Multics and crystallized in the early 1970s by Ken Thompson and Dennis Ritchie, means that data streams flowing into and out of processes are not special-cased constructs but ordinary file descriptors referencing open file descriptions in the kernel's file table. When you launch a process, the kernel creates three standard streams—`stdin` (file descriptor 0), `stdout` (file descriptor 1), and `stderr` (file descriptor 2)—by default pointing to the controlling terminal device. These descriptors are not hardwired constants but entries in the process's per-process file descriptor table, a dynamically managed array of pointers into the system-wide open file table maintained by the kernel. This indirection layer is what makes I/O redirection possible: by manipulating file descriptor entries before or during process execution, the shell can transparently rewire data flows without the running program ever knowing its standard streams have been redirected.

File descriptors are small non-negative integers serving as indices into this per-process table. When a process calls `read(0, buf, count)`, the kernel translates file descriptor `0` into a pointer to an open file description structure containing the current file offset, access mode flags, and a reference to the underlying inode or device driver. The kernel then invokes the appropriate read method—whether that points to a disk-backed file, a pipe, a socket, or a pseudo-terminal—and advances the file offset accordingly. The crucial invariant here is that file descriptors provide location-transparent addressing: the process does not care whether descriptor 1 points to `/dev/pts/3`, a regular file `/tmp/output.log`, or the write end of a pipe connected to another process. This abstraction enables the shell to compose arbitrary data flows by duplicating, closing, and reassigning descriptors using the `dup2()` system call, which atomically closes the target descriptor if open and makes it an alias for the source descriptor.

Pipelines extend this model into multi-process communication channels. When the shell encounters `cmd1 | cmd2`, it creates an anonymous pipe using the `pipe()` system call, which returns two file descriptors: a read end and a write end backed by a kernel-resident ring buffer (historically 4KB on early Unix, now typically 64KB or larger on modern Linux). The shell then forks two child processes. In the first child, it closes the read end of the pipe, duplicates the write end onto descriptor 1 (stdout), and execs `cmd1`. In the second child, it closes the write end, duplicates the read end onto descriptor 0 (stdin), and execs `cmd2`. The parent shell closes both ends of the pipe in its own descriptor table and waits for the children to complete. This choreography ensures that data written by `cmd1` flows through the kernel-managed pipe buffer directly into `cmd2` without intermediate disk I/O or copying through user space. The pipe buffer itself is a circular queue with read and write pointers maintained by the kernel, providing blocking semantics: writes block when the buffer is full, reads block when empty, and the kernel wakes sleeping processes via the scheduler's wait queue mechanism when data becomes available or space opens up.

Job control introduces a layer of process group management necessary for interactive shells to handle background execution, suspend-and-resume, and terminal signal distribution. Every process belongs to a process group identified by a process group ID (PGID), and every terminal has a foreground process group that receives keyboard-generated signals like `SIGINT` (Ctrl-C) and `SIGTSTP` (Ctrl-Z). When you launch a command with an ampersand suffix (`cmd &`), the shell places it in a new process group and does not wait for termination, instead returning control to the user immediately. The kernel delivers terminal-generated signals only to the foreground group, which is why background jobs do not respond to Ctrl-C. The shell itself acts as the session leader, managing process groups through `setpgid()` and controlling terminal ownership through `tcsetpgrp()`. This architecture enables shells to implement features like `fg`, `bg`, and job tables while preventing background processes from interfering with interactive input.

Signals represent asynchronous event notification at the kernel level, a mechanism predating POSIX but formalized into a standardized interface. When an event occurs—a timer expires, a child process terminates, a hardware exception is raised, or another process invokes `kill()`—the kernel marks a pending signal in the target process's signal bitmask. Before returning to user mode from any system call or interrupt, the kernel checks for pending signals and, if the signal is not blocked or ignored, invokes the registered signal handler by manipulating the process's stack frame to simulate a function call. Signal handlers run in user space but are invoked by kernel machinery, creating a race-prone execution context where only async-signal-safe functions may be called. The default disposition for most signals is termination, but processes can override this with `sigaction()` to install custom handlers. The shell leverages signals extensively: it installs handlers for `SIGCHLD` to reap terminated children, uses `SIGINT` and `SIGQUIT` for interactive cancellation, and exposes signal trapping to scripts through the `trap` builtin, allowing cleanup code to run even when the script is interrupted or receives a termination signal.

Understanding these primitives requires recognizing their invariants. File descriptors are process-local; duplication creates aliasing, not copying. Pipes are unidirectional and half-duplex; bidirectional communication requires two pipes. Signals are asynchronous and non-queueing; multiple deliveries of the same signal may coalesce into one. Job control relies on terminal driver state; non-interactive shells do not receive keyboard signals. These invariants constrain what is possible and shape how robust shell scripts must be constructed. A script that redirects output to a file must handle the case where the file cannot be opened. A pipeline must account for partial failures when intermediate commands terminate prematurely. A signal handler must not call non-reentrant functions like `malloc()` or `printf()`. Mastery of shell programming means reasoning about these kernel-level mechanics and building resilient compositions atop them.

## 2. Core Architecture & Mechanics

The file descriptor table is the foundational data structure enabling I/O redirection. Each process maintains a private table of file descriptor entries, indexed by integers starting from zero. An entry is either vacant or contains a pointer to an open file description in the system-wide open file table. The open file description, in turn, holds the current file offset (a 64-bit byte position), status flags (read-only, write-only, read-write, append mode, non-blocking mode), and a reference to the underlying vnode or inode representing the actual file, device, or IPC object. When you duplicate a descriptor with `dup2(oldfd, newfd)`, the kernel does not copy the underlying file; instead, it makes `newfd` point to the same open file description as `oldfd`, incrementing its reference count. Both descriptors now share the same file offset, so a read or write through either will advance the position seen by the other. This sharing is critical for redirection: when the shell execs a child process after redirecting stdout to a file, the exec preserves the descriptor table but replaces the process image, so the new program inherits the redirected descriptor without any awareness that its stdout is not a terminal.

Redirection operators in the shell syntax map directly to sequences of system calls. The simple output redirection `cmd > file` causes the shell to fork, then in the child process open `file` with flags `O_WRONLY | O_CREAT | O_TRUNC`, which creates the file if absent or truncates it to zero bytes if present, and returns a new descriptor, say 3. The shell then calls `dup2(3, 1)`, which atomically closes descriptor 1 if open and makes it point to the same open file description as descriptor 3. The shell closes descriptor 3 since it is no longer needed and execs the command. The newly loaded program sees descriptor 1 pointing to the file, and all writes to stdout land in the file rather than the terminal. The append redirection `cmd >> file` differs only in using `O_APPEND` instead of `O_TRUNC`, ensuring writes occur at the end of the file regardless of prior seeks. Input redirection `cmd < file` follows an analogous path, opening the file read-only and duplicating it onto descriptor 0.

The here-document syntax `cmd << EOF` is syntactic sugar for creating an anonymous temporary data source. When the shell parses a here-document, it reads lines from the script or terminal until it encounters the delimiter `EOF` on a line by itself. The collected text is written to a temporary pipe (or in some implementations, a temporary file in `/tmp`), and the read end of that pipe is duplicated onto the command's stdin. This is equivalent to embedding the data inline but more convenient for multi-line inputs. Here-strings `cmd <<< "text"` are a compact variant that pass a single string as stdin, implemented by the shell writing the string to a pipe and attaching the read end. Process substitution `cmd <(subcmd)` takes this further by creating a named pipe or `/dev/fd/N` descriptor that appears as a filename argument, allowing commands that expect file paths to consume the output of another command as if reading a file. The shell spawns `subcmd` with its stdout connected to the anonymous pipe, then passes `/dev/fd/N` or a named FIFO path to `cmd` as an argument. When `cmd` opens that path, it is actually opening the read end of the pipe, and data flows from `subcmd` through the kernel buffer into `cmd`.

Pipelines are orchestrated through a sequence of fork, pipe, dup2, close, and exec operations. Consider the pipeline `cmd1 | cmd2 | cmd3`. The shell begins by creating two anonymous pipes, yielding four descriptors: `pipe1[0]` (read end of pipe 1), `pipe1[1]` (write end of pipe 1), `pipe2[0]` (read end of pipe 2), and `pipe2[1]` (write end of pipe 2). The shell then forks three child processes. In the first child, the shell closes `pipe1[0]`, `pipe2[0]`, and `pipe2[1]`, duplicates `pipe1[1]` onto descriptor 1, closes `pipe1[1]`, and execs `cmd1`. This child now has stdout connected to the write end of pipe 1. In the second child, the shell closes `pipe1[1]`, `pipe2[0]`, duplicates `pipe1[0]` onto descriptor 0, duplicates `pipe2[1]` onto descriptor 1, closes `pipe1[0]` and `pipe2[1]`, and execs `cmd2`. This child reads from pipe 1 and writes to pipe 2. In the third child, the shell closes `pipe1[0]`, `pipe1[1]`, `pipe2[1]`, duplicates `pipe2[0]` onto descriptor 0, closes `pipe2[0]`, and execs `cmd3`. This child reads from pipe 2 with stdout still connected to the original terminal. The parent shell closes all pipe descriptors in its own table to ensure the only references remain in the children, then waits for all three processes to terminate. This design ensures that when `cmd1` terminates and closes its write end of pipe 1, the kernel delivers `SIGPIPE` to any subsequent writes, and when all write ends are closed, `cmd2` reading from pipe 1 receives EOF. The symmetric property holds for pipe 2 between `cmd2` and `cmd3`.

The kernel's pipe implementation is a ring buffer residing in kernel memory. On Linux, the default capacity is 65536 bytes (64 KB), tunable via `fcntl(F_SETPIPE_SZ)`. The buffer maintains read and write offsets, both initially zero. When a process writes to the write end, the kernel copies data from user space into the buffer, advancing the write offset modulo the buffer size. If the buffer is full, the write call blocks, adding the process to the pipe's wait queue until a reader consumes data and wakes the writer. Symmetrically, a read from the read end copies data to user space and advances the read offset, blocking if the buffer is empty. When the last write end is closed, subsequent reads return zero bytes (EOF). When the last read end is closed, subsequent writes receive `SIGPIPE` and return `EPIPE`. This blocking behavior provides flow control: a slow reader naturally throttles a fast writer, preventing unbounded memory consumption. The kernel must also handle partial writes atomically up to `PIPE_BUF` bytes (typically 4096) to prevent interleaving from concurrent writers, a guarantee crucial when multiple processes write to the same pipe.

Job control is built atop the process group and session abstractions. Every process has a process ID (PID), a parent process ID (PPID), and a process group ID (PGID). Processes in the same pipeline are placed in the same process group by the shell calling `setpgid()` for each child before exec. The shell itself is the session leader, and the terminal driver maintains a foreground process group ID. Keyboard signals like `SIGINT` and `SIGTSTP` are sent by the kernel to all processes in the foreground group. When you type Ctrl-C, the terminal driver's line discipline detects the interrupt character, and the kernel invokes `kill(-pgrp, SIGINT)` where `pgrp` is the foreground PGID, delivering the signal to every process in that group. If a process is in a background group, it does not receive the signal and continues running. To bring a stopped job back to the foreground, the shell calls `tcsetpgrp(tty_fd, job_pgid)` to designate the job's process group as the foreground group, then sends `SIGCONT` to resume execution. Background jobs attempting to read from the terminal receive `SIGTTIN`, which by default stops the process, preventing background jobs from stealing input.

The shell maintains a job table mapping job IDs (small integers like `%1`, `%2`) to process groups. When you launch `cmd &`, the shell assigns a job ID, records the PGID, and prints the job number and first PID. The shell does not wait on background jobs immediately; instead, it installs a `SIGCHLD` handler that reaps terminated children asynchronously or checks for terminated children when printing the next prompt. The `jobs` builtin iterates the job table and reports the status of each, querying via `waitpid(-pgid, &status, WNOHANG | WUNTRACED)` to detect termination or suspension without blocking. The `fg` builtin moves a job to the foreground by reassigning terminal control and sending `SIGCONT`, then waits synchronously for the job to complete. The `bg` builtin sends `SIGCONT` to a stopped background job without changing terminal ownership, allowing it to resume in the background. This model requires cooperation from the terminal driver, process group management system calls, and signal delivery machinery.

Signals are delivered via the kernel's signal mechanism, which checks for pending signals on every return from kernel mode to user mode. The kernel maintains a per-process bitmask of pending signals and another bitmask of blocked signals. When a signal is raised, the kernel sets the corresponding bit in the pending mask unless the signal is already pending and the signal does not queue (most signals do not; real-time signals do). Before resuming user-mode execution, the kernel checks if any signals are both pending and unblocked. If so, it selects one (POSIX does not specify the order, but traditionally signals are processed in ascending numerical order), clears the pending bit, and checks the signal disposition. If the disposition is `SIG_DFL` (default), the kernel performs the default action, typically terminating the process, generating a core dump for certain signals, or ignoring the signal. If the disposition is `SIG_IGN`, the signal is discarded. If the disposition is a function pointer registered via `sigaction()`, the kernel constructs a signal frame on the process's user-mode stack, saves the current register state, modifies the instruction pointer to point to the signal handler, and returns to user mode, effectively "calling" the handler. When the handler returns (via a special sigreturn system call), the kernel restores the saved registers and resumes execution where it was interrupted. This design means signal handlers can run at almost any point in the program's execution, creating race conditions if the handler accesses global data or calls non-reentrant functions.

The `trap` builtin in the shell allows scripts to intercept signals and execute cleanup code. The syntax `trap 'commands' SIGNAL` installs a handler for the specified signal, replacing the default disposition. When the signal is delivered, the shell suspends its current execution, runs the specified commands, and resumes. This is commonly used for cleanup on exit: `trap 'rm -f "$tempfile"' EXIT` ensures temporary files are removed even if the script is interrupted by Ctrl-C (which generates `SIGINT`). The special pseudo-signal `EXIT` is not a real signal but a shell construct that executes the trap action whenever the shell exits, regardless of reason. Traps can also be used to reload configuration: a daemon script might install `trap 'reload_config' SIGHUP` so sending `SIGHUP` to the process triggers a configuration reload without termination. The shell preserves traps across function calls but resets them on exec, since the new program replaces the entire process image.

File descriptor management becomes intricate when combining redirection with pipelines and error handling. Consider `cmd 2>&1 | grep error`. The `2>&1` redirection duplicates stderr (descriptor 2) onto stdout (descriptor 1), so both streams merge and flow into the pipeline. The order matters: `cmd | grep error 2>&1` redirects stderr to stdout *after* the pipeline is established, meaning stderr of `grep` goes to the terminal, not into the pipeline. The shell evaluates redirections left to right, applying each in sequence. The descriptor `&1` syntax tells the shell to duplicate the current descriptor 1 rather than opening a file named `1`. This distinction is critical: `cmd > file 2>&1` sends both stdout and stderr to the file, but `cmd 2>&1 > file` redirects stderr to the original stdout (likely the terminal) and then redirects stdout to the file, leaving stderr unchanged. Mastery requires internalizing the evaluation order and the difference between duplication and redirection.

Advanced redirection includes opening descriptors for both reading and writing with `<>`, often used for locking or bidirectional communication with devices. The syntax `exec 3<> file` opens `file` on descriptor 3 in read-write mode, allowing subsequent commands to read from and write to descriptor 3 without reopening the file. The `exec` builtin without a command applies redirections to the current shell rather than a child process, useful for persistent redirection: `exec > logfile` redirects all subsequent output of the shell script itself to the logfile. Closing descriptors explicitly with `exec 3>&-` removes the entry from the descriptor table, releasing the underlying file description if no other descriptors reference it. These techniques enable sophisticated patterns like creating lockfiles via descriptor holding, managing multiple log streams, or interacting with coprocesses.

## 3. High-Performance Optimization & Failure Modes

Pipeline performance is dominated by the interplay between kernel buffering, process scheduling, and I/O latency. The 64 KB pipe buffer means that a fast producer can fill the buffer and block until the consumer reads, introducing stalls. If the producer generates data in large bursts, the consumer may starve the CPU of useful work between bursts. Optimal throughput occurs when the producer and consumer run concurrently with the buffer approximately half-full, a state the kernel's scheduler attempts to achieve by waking both processes opportunistically. However, if the consumer is CPU-bound, the buffer fills and the producer blocks, serializing the pipeline. Conversely, if the producer is I/O-bound (e.g., reading from a slow disk), the consumer blocks waiting for data. The pipe buffer size can be adjusted via `fcntl(F_SETPIPE_SZ)`, but increasing it beyond memory cache sizes may degrade performance by inducing cache misses.

The `SIGPIPE` signal is a critical failure mode in pipelines. When a reader terminates prematurely—perhaps due to finding a match early in a large dataset—it closes the read end of the pipe. The writer, unaware, continues writing and receives `SIGPIPE` on the next write call. By default, `SIGPIPE` terminates the process immediately without executing any signal handler. This behavior is desirable for simple filters but problematic for scripts that need to clean up resources. Ignoring `SIGPIPE` with `trap '' PIPE` or `signal(SIGPIPE, SIG_IGN)` causes the write to return `EPIPE` instead of terminating, allowing the program to detect the broken pipe and exit gracefully. In shell scripts, this is typically unnecessary since the shell handles `SIGPIPE` transparently, but in C programs or daemon scripts, explicit handling is essential.

Race conditions in signal handlers are a perennial source of bugs. Signal handlers run asynchronously and can interrupt any non-atomic operation. If a signal handler and the main program both access a shared variable without synchronization, data corruption or inconsistent state can result. The only safe operations in a signal handler are assignments to variables of type `volatile sig_atomic_t` and calls to async-signal-safe functions, a restricted subset of libc functions documented in POSIX (`write()`, `_exit()`, `sigaction()`, etc.). Non-safe functions like `malloc()`, `printf()`, and most of the standard library must not be called from a signal handler. A common pattern is to set a flag in the handler and check the flag in the main loop, deferring actual work to safe contexts. For example, a `SIGCHLD` handler might set `child_exited = 1`, and the main loop checks this flag and calls `waitpid()` when set, ensuring the blocking system call does not occur in the signal context.

Job control introduces subtleties in terminal handling and signal distribution. If a background job attempts to read from stdin, it receives `SIGTTIN`, which by default stops the process. The shell detects the stopped state via `SIGCHLD` and marks the job as stopped. If the user then brings the job to the foreground with `fg`, the shell sends `SIGCONT` and the job resumes. However, if the script uses `read` in a background job without redirecting stdin, the job stops immediately, often confusing users who expect background jobs to run independently. To prevent this, background commands should redirect stdin from `/dev/null` or a file: `cmd < /dev/null &`. Similarly, background jobs that write to stdout or stderr can interfere with the terminal if the user is typing commands, producing garbled output. Redirecting output is essential for clean background execution.

Process substitution has inherent race conditions when the substituted command terminates before the consuming command opens the FIFO or descriptor. If `cmd <(subcmd)` is used and `subcmd` exits immediately, the FIFO may be closed before `cmd` opens it, resulting in an immediate EOF. This is usually harmless but can cause issues if `cmd` expects a persistent data source. On the other hand, if `subcmd` blocks waiting for a reader and `cmd` never reads (perhaps due to an error), both processes deadlock. Properly written commands should handle EOF gracefully and avoid blocking indefinitely on input.

File descriptor leakage occurs when a script opens descriptors with `exec 3> file` but never closes them. While the kernel automatically closes all descriptors on process termination, long-running shell scripts can accumulate open descriptors, eventually hitting the per-process limit (typically 1024 or higher, tunable via `ulimit -n`). Explicitly closing descriptors with `exec 3>&-` when no longer needed prevents leakage. Some shells automatically close high-numbered descriptors when execing commands, but this behavior is not portable.

Here-documents processed by the shell undergo variable expansion, command substitution, and escape sequence interpretation unless the delimiter is quoted. The syntax `<< 'EOF'` disables expansion, treating the here-document as literal text, useful for embedding code or data that contains dollar signs or backticks. If expansion is enabled, special characters must be escaped: `\$` to produce a literal dollar sign. Misunderstanding expansion rules leads to subtle bugs where the generated text differs from the intended content.

Error handling in pipelines is complicated by the pipeline's exit status semantics. By default, the shell reports the exit status of the last command in the pipeline. If `cmd1 | cmd2 | cmd3` runs and `cmd1` fails but `cmd2` and `cmd3` succeed, the pipeline's exit status is zero (success), even though the first command failed. To detect intermediate failures, Bash provides the `PIPESTATUS` array, which records the exit status of each command in the last pipeline: `"${PIPESTATUS[@]}"` expands to the statuses of all commands. Checking `PIPESTATUS` after critical pipelines is essential for robust scripts. Alternatively, enabling `set -o pipefail` causes the pipeline to return the exit status of the rightmost failing command, making failures visible without manual status inspection.

The `nohup` command and `disown` builtin address session termination. When you log out of an interactive shell, the kernel sends `SIGHUP` to all processes in the session, typically terminating them. Commands launched with `nohup cmd &` run with `SIGHUP` ignored, so they survive logout. The shell also redirects stdout and stderr to `nohup.out` if they are terminals, preventing output loss. The `disown` builtin removes a job from the shell's job table, preventing the shell from sending `SIGHUP` when it exits. This is useful for long-running background processes that should outlive the shell session, but it also means the shell no longer tracks or manages the job.

Concurrency with file redirection requires awareness of kernel-level atomicity guarantees. Multiple processes writing to the same file with `>>` (append mode) are safe at the byte level due to the `O_APPEND` flag, which causes the kernel to atomically seek to the end and write, preventing interleaved writes at wrong offsets. However, individual writes larger than the filesystem's atomic write size (often page-sized, 4 KB) may still be interleaved at the byte level if multiple processes write simultaneously. Using flock or other locking mechanisms ensures exclusive access when coordinating multiple writers. Reading from shared files is inherently racy if other processes are writing; the reader may observe partial writes or inconsistent state unless the writer uses atomic rename (`mv tempfile finalfile`) to publish completed data.

Signal masking with `sigprocmask()` allows critical sections to run without interruption. A script or program can block signals during sensitive operations, ensuring that signal handlers do not run until the block is lifted. In shell scripts, this is less common, but in C programs, it is standard practice. For example, a program might block `SIGCHLD` while modifying a shared data structure accessed by the `SIGCHLD` handler, preventing races. After unblocking, any pending signals are delivered immediately. This technique is essential for writing reentrant-safe code in multi-threaded or signal-intensive environments.

The interaction between signal handling and blocking system calls is governed by the `SA_RESTART` flag in `sigaction()`. If a system call like `read()` or `sleep()` is interrupted by a signal and `SA_RESTART` is set, the kernel automatically restarts the system call after the signal handler returns, making the signal transparent to the program. If `SA_RESTART` is not set, the system call returns `EINTR`, and the program must check for this error and decide whether to retry. Shell scripts rarely encounter this directly, as the shell handles it internally, but when writing signal-aware daemons or long-running processes, correctly handling `EINTR` is mandatory to avoid spurious failures.

Finally, understanding the kernel's implementation of `wait()` and process reaping is crucial for job control and signal handling. When a child process terminates, it enters the zombie state, where the kernel retains minimal information (PID, exit status, resource usage) until the parent calls `wait()` or `waitpid()` to reap it. If the parent never reaps zombies, they accumulate, eventually exhausting the PID space. The `SIGCHLD` signal notifies the parent of child termination, allowing asynchronous reaping. Installing a `SIGCHLD` handler that calls `waitpid(-1, NULL, WNOHANG)` in a loop ensures all terminated children are reaped without blocking. Shells implement this internally to maintain job tables, but long-running scripts that fork child processes must explicitly handle zombie reaping to avoid resource leaks.

In summary, mastering I/O redirection, pipelines, job control, and signals requires deep understanding of the kernel's process model, signal delivery machinery, and file descriptor mechanics. These primitives compose into powerful idioms but also introduce subtle failure modes and race conditions. Robust shell programming demands reasoning about asynchronous signal delivery, blocking semantics, process group management, and error propagation through pipelines, always grounded in the kernel-level invariants that govern process interaction.
