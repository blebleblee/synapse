# Lesson 1: Signal Fundamentals, Delivery Semantics, Dispositions

## 1. First-Principles Intuition & Invariants

Unix signals represent the kernel's fundamental mechanism for asynchronous notification delivery to user-space processes. At their core, signals embody a deeply counterintuitive architectural decision: the operating system can interrupt a process at nearly any instruction boundary, inject an execution context switch into ring 3 user space, and force the process to handle an event before resuming normal flow. This design creates a miniature scheduler within each process, where the kernel acts as an external interrupt controller that can preempt not just between threads but within a single thread's instruction stream.

The foundational invariant underlying all signal semantics is **asynchronous delivery with no guaranteed ordering**. When the kernel decides to deliver a signal, it does not wait for the process to reach a "safe point" in its execution. Instead, it interrupts the process between any two instructions that do not form an atomic hardware sequence, saves the current register state onto the process's kernel stack, and either invokes a user-registered signal handler or applies a default disposition. This interruption occurs regardless of whether the process is executing application logic, traversing kernel space during a system call, or blocked waiting for I/O. The kernel's signal delivery machinery operates orthogonally to the process's own control flow, creating race conditions that require explicit synchronization primitives like `sigprocmask()` to manage safely.

Signals originate from three distinct sources, each with different generation semantics. Hardware exceptions such as division by zero, invalid memory access (segmentation faults), or illegal instructions generate synchronous signals like `SIGFPE`, `SIGSEGV`, and `SIGILL`. These signals are inherently synchronous because they arise directly from instruction execution and are delivered to the specific thread that caused the exception. The kernel's trap handler detects the hardware fault, translates it into a signal number, and queues the signal for immediate delivery. In contrast, process-generated signals arise from explicit system calls like `kill()`, `raise()`, or `pthread_kill()`, allowing one process or thread to send arbitrary signals to another, subject to permission checks based on real and effective user IDs. Finally, kernel-generated signals emerge from system-level events such as terminal control characters (Ctrl-C generating `SIGINT`), resource limit violations (`SIGXCPU` for CPU time, `SIGXFSZ` for file size), or child process termination (`SIGCHLD`). Each source imposes different delivery constraints: hardware exceptions deliver synchronously to the faulting thread, process signals may target any thread in a multi-threaded process, and kernel signals follow complex routing rules through process groups and sessions.

The signal delivery path within the kernel follows a deterministic state machine, though its execution appears unpredictable from user space. When a signal is generated, the kernel sets a bit in the target process's pending signal mask, a per-process or per-thread bitmap tracking which signals await delivery. Before returning from any system call or timer interrupt, the kernel checks this pending mask against the process's signal blocking mask, maintained via `sigprocmask()`. If a pending signal is not blocked, the kernel removes it from the pending set and delivers it by examining the process's signal disposition table—a per-process array indexed by signal number, storing either `SIG_DFL` (default), `SIG_IGN` (ignore), or a function pointer to a user-registered handler. For default dispositions, the kernel applies hardcoded behavior: termination, termination with core dump, stopping the process, or ignoring the signal. For registered handlers, the kernel performs a complex context switch: it saves the current user-space register state, builds a signal frame on the user stack containing this saved context, modifies the program counter to jump to the handler function, and resumes execution in user mode. When the handler returns via the `sigreturn()` system call, the kernel restores the original register state, allowing the process to continue as if the signal handler was never invoked.

The **async-signal-safety** constraint represents the most critical invariant governing signal handler implementation. Because a signal can arrive at any instruction boundary, a handler might interrupt a non-reentrant function mid-execution, such as `malloc()` holding internal heap locks, `printf()` manipulating `FILE` stream buffers, or `getpwnam()` accessing shared static storage. If the signal handler then calls the same non-reentrant function, the result is undefined behavior: deadlocks on internal locks, corrupted data structures, or memory corruption. POSIX defines a narrow whitelist of async-signal-safe functions—approximately 130 system calls and library routines—that guarantee safe invocation from signal handlers. This whitelist includes low-level system calls like `write()`, `read()`, `_exit()`, `sigaction()`, and `sigprocmask()`, but excludes nearly all standard C library functions that manipulate global state. The restriction extends beyond library calls to fundamental operations: modifying global variables without atomic operations creates data races, and accessing thread-local storage may observe stale or corrupted values if the signal interrupted a TLS update.

Signal handler execution inherits the interrupted context's stack, a design choice that creates subtle overflow vulnerabilities. When the kernel delivers a signal, it pushes the signal frame onto the process's current stack, whether that stack is the main thread's stack, an alternate signal stack registered via `sigaltstack()`, or a custom thread stack allocated with `pthread_create()`. If the process was deeply recursed or near stack exhaustion when the signal arrived, the signal frame itself—typically several kilobytes on x86-64 to hold register state, floating-point context, and return trampolines—can overflow the stack, generating a `SIGSEGV` during signal delivery. This secondary fault creates a nested signal scenario that typically terminates the process because the kernel refuses to deliver a second `SIGSEGV` while handling the first. The `sigaltstack()` system call provides protection by allocating a separate, kernel-managed stack exclusively for signal handlers, ensuring that stack overflow in the main thread cannot prevent signal delivery. However, alternate stacks introduce new failure modes: if multiple signals arrive in rapid succession, handlers can overflow the alternate stack itself, and thread-local alternate stacks require careful setup with `pthread_sigmask()` to avoid races during thread creation.

The interrupted system call problem exposes a fundamental tension between signal delivery and blocking I/O semantics. When a signal arrives while a process blocks in a slow system call—`read()` on a socket, `wait()` for child termination, `select()` waiting for file descriptor readiness—the kernel faces a decision: should it deliver the signal and abort the system call, or should it defer delivery until the call completes? Early Unix variants chose immediate delivery, causing system calls to fail with `EINTR` (interrupted system call) and forcing application developers to manually restart every blocking operation in a loop. Modern POSIX provides the `SA_RESTART` flag to `sigaction()`, instructing the kernel to automatically restart certain system calls after signal handler completion. However, restart semantics apply inconsistently: `read()` and `write()` on regular files restart unconditionally, blocking I/O on sockets restarts only with `SA_RESTART`, and `sleep()` and `nanosleep()` never restart, instead returning the remaining time in an output parameter. This semantic complexity creates portability hazards, where code that works on Linux with `SA_RESTART` fails on BSD variants with subtly different restart rules. The only truly portable solution wraps every blocking system call in an `EINTR` retry loop, even when using `SA_RESTART`, because signal handlers might modify global state that invalidates the operation's preconditions.

Signal delivery guarantees expose inherent unreliability in the signal mechanism. Standard signals, numbered 1 through 31 on most Unix variants, are **non-queuing**: if a signal is already pending when another instance is generated, the kernel discards the second occurrence, leaving only one pending bit set. A process that receives 1000 `SIGUSR1` signals while blocking the signal will observe only a single delivery when unblocking. This behavior makes standard signals unsuitable for counting events or tracking the number of occurrences. Real-time signals, introduced in POSIX.1b and numbered 32 through 64 on Linux, provide **queuing semantics**: each signal instance is enqueued separately in a kernel-managed queue with an accompanying integer or pointer payload delivered via `sigqueue()`. Real-time signals deliver in strict order within each signal number, allowing reliable event counting and data passing. However, real-time signal queues are bounded by `RLIMIT_SIGPENDING`, typically 64,000 signals per user, and queue exhaustion causes `sigqueue()` to fail with `EAGAIN`, silently dropping events unless the application implements explicit backpressure.

The signal disposition table exhibits process-wide scope with thread-specific overrides, creating a hybrid inheritance model that surprises developers unfamiliar with POSIX threading semantics. When a process calls `fork()`, the child inherits an exact copy of the parent's signal dispositions, pending signals, and blocking masks. However, `execve()` resets all signal handlers to `SIG_DFL`, preserving only the signal blocking mask, ensuring that newly executed programs start with predictable signal behavior. In multi-threaded processes, signal disposition is process-wide: any thread calling `sigaction()` modifies the shared disposition table visible to all threads. Yet the signal blocking mask is thread-local: each thread maintains its own mask set via `pthread_sigmask()`, allowing fine-grained control over which threads can receive which signals. Process-directed signals like those sent via `kill()` are delivered to an arbitrary thread that does not block the signal, chosen by the kernel's internal scheduling heuristics. Thread-directed signals sent via `pthread_kill()` target a specific thread, queuing exclusively to that thread regardless of blocking masks. This split delivery model forces developers to carefully design signal handling in multi-threaded programs: blocking all signals in worker threads except a dedicated signal handling thread, or using `signalfd()` to convert asynchronous signal delivery into synchronous file descriptor polling compatible with event loops like `epoll`.

## 2. Core Architecture & Mechanics

The kernel's signal data structures form a hierarchical system spanning per-process global state, per-thread local state, and per-signal metadata. At the process level, the `task_struct` in Linux maintains a `sighand` pointer to a shared `sighand_struct`, which contains the disposition table (`k_sigaction` array indexed by signal number), a spin lock protecting concurrent modifications, and a reference count enabling copy-on-write semantics during `fork()`. This shared structure means all threads in a process observe the same signal handlers, though they can register thread-local dispositions by copying the structure on first modification. The per-thread `task_struct` holds a `blocked` signal mask (64-bit bitmask for standard signals), a `real_blocked` mask used during `sigsuspend()` to temporarily override blocking, and a `saved_sigmask` for restartable blocking operations. The pending signal queue exists in two forms: a per-process shared queue for process-directed signals like those from `kill()`, and per-thread private queues for synchronous signals and those sent via `pthread_kill()`. Each queue entry contains the signal number, sender's PID and UID (for security checks), and for real-time signals, a `siginfo_t` structure carrying payload data.

The signal delivery decision path within the kernel follows a priority-based scan that executes on every return from kernel mode to user mode, triggered by system call completion, timer interrupts, or page faults. The kernel invokes `do_signal()` or its architecture-specific variant, which first checks the per-thread private pending queue, then the shared per-process queue, scanning for unblocked signals. The search prioritizes lower-numbered signals, ensuring that `SIGKILL` (9) and `SIGSTOP` (19) preempt all others, though this priority is implicit in numeric ordering rather than an explicit preemption mechanism. Upon finding a deliverable signal, the kernel examines the disposition table. For `SIG_IGN`, it simply dequeues the signal and continues scanning. For `SIG_DFL`, it invokes hardcoded behavior based on signal number: `SIGTERM`, `SIGINT`, and `SIGKILL` terminate the process, `SIGQUIT` and `SIGILL` terminate with a core dump, `SIGSTOP` and `SIGTSTP` stop execution, and `SIGCHLD` and `SIGURG` are ignored by default. For registered handlers, the kernel initiates the complex signal frame construction process.

Signal frame construction represents one of the kernel's most intricate user-space context manipulations. The kernel must transition from ring 0 kernel space back to ring 3 user space, but instead of returning to the interrupted instruction, it must first execute the signal handler, then restore the original context. To achieve this, the kernel modifies the saved register state on the kernel stack before returning to user mode. On x86-64, the kernel allocates space on the user stack for a `ucontext_t` structure, which embeds the full register state (`mcontext_t`), the signal mask to restore after handler completion, a pointer to the stack itself (for `sigaltstack()` state), and flags controlling restart behavior. The kernel writes the interrupted `RIP` (instruction pointer), `RSP` (stack pointer), `RFLAGS`, and all general-purpose registers into this structure, along with the full x87 FPU and SSE/AVX state captured via `XSAVE` instructions. It then pushes a return address pointing to a kernel-provided code stub called the signal trampoline (historically the `__restore_rt` function in the vDSO), sets the user-space `RIP` to the handler function address, and places the signal number, a pointer to a `siginfo_t` structure, and a pointer to the `ucontext_t` as the handler's first three arguments (following the System V AMD64 ABI). When the kernel returns to user mode, execution resumes at the handler with a pristine call frame, appearing as if the kernel invoked the handler as a normal function call.

The signal return path via `sigreturn()` reverses this process through a carefully crafted system call stub. When the signal handler executes a `return` statement, control flows to the signal trampoline code that the kernel pushed onto the stack. This trampoline consists of just two instructions: loading `RAX` with the system call number for `rt_sigreturn()` (139 on x86-64) and invoking `syscall`. The kernel's `sys_rt_sigreturn()` handler reads the `ucontext_t` structure from the user stack, validates that the signal frame is intact (checking magic numbers and stack alignment), restores the saved signal mask via `set_current_blocked()`, and copies the saved register state back into the kernel's `pt_regs` structure. It then returns to user space using the standard system call exit path, but because the kernel overwrote the saved `RIP` and `RSP`, execution resumes at the exact instruction that was interrupted when the signal arrived, with all registers restored to their pre-signal state. This return-through-kernel design prevents user space from directly manipulating the signal stack frame, which would create severe security vulnerabilities allowing privilege escalation through register state forgery.

The signal blocking mask operates through bitwise operations on a 64-bit unsigned long on most 64-bit architectures, with higher signal numbers stored in adjacent words for systems supporting more than 64 signals. The `sigprocmask()` system call accepts three operations: `SIG_BLOCK` performs bitwise OR with the current mask, adding signals to the blocked set; `SIG_UNBLOCK` performs bitwise AND with the complement, removing signals from the blocked set; and `SIG_SETMASK` replaces the mask entirely. The kernel represents the mask as a `sigset_t` structure, which on Linux is a struct containing an array of unsigned longs, allowing efficient atomic operations on signal groups. Special signals `SIGKILL` (9) and `SIGSTOP` (19) are hardcoded in the kernel to ignore any blocking attempts: even if user space sets the corresponding bits in the blocking mask, the kernel's `sigmask()` and `sigismember()` macros forcibly clear these bits before checking deliverability. This invariant ensures that the system administrator can always terminate runaway processes and that job control always functions, but it means these two signals cannot be caught or blocked under any circumstances.

The interaction between signal delivery and system call execution follows architecture-specific conventions that vary between BSD-derived systems and Linux. When a blocking system call like `read()` on a pipe or `accept()` on a listening socket is interrupted by signal delivery, the kernel must decide whether to restart the call after the handler completes or return `EINTR` to user space. On Linux with the `SA_RESTART` flag set, the kernel stores the system call number and arguments in the task's `restart_block` structure before delivering the signal. After the handler returns and the kernel restores the user context, it checks the `restart_block` and, if the system call is restartable, modifies the saved `RIP` to point to the `syscall` instruction that initiated the call, decrements `RIP` by 2 bytes (the length of the `syscall` instruction on x86-64), and returns to user space. The process re-executes the `syscall` instruction with the original arguments still in registers, transparently restarting the operation without user-space intervention. However, certain system calls are explicitly marked non-restartable: `poll()`, `select()`, and their variants always return `EINTR` to allow user space to recalculate timeouts, and `sleep()` and `nanosleep()` fill an output parameter with the remaining sleep time instead of restarting.

Thread-directed signal delivery in multi-threaded programs introduces routing complexity that most developers underestimate. When a process-directed signal arrives via `kill()`, the kernel iterates through the process's thread group, looking for a thread that does not block the signal. The selection algorithm checks the per-thread `blocked` mask, and if multiple threads can receive the signal, the kernel chooses one based on internal scheduling state—typically the thread that most recently entered kernel mode, though this is an implementation detail that varies across kernel versions. If all threads block the signal, it remains pending in the shared process queue until at least one thread unblocks it. For synchronous signals like `SIGSEGV` or `SIGFPE`, the kernel always delivers to the thread that caused the exception, overriding the blocking mask because blocking a synchronous signal represents a programming error. Thread-directed signals sent via `pthread_kill()` bypass the routing logic entirely, enqueuing directly to the target thread's private pending queue. If the target thread has exited but its `pthread_t` handle remains valid, `pthread_kill()` returns `ESRCH`, but the kernel's signal delivery code does not distinguish between non-existent threads and threads that have not yet started, creating a race condition during thread creation where signals can be lost.

The `signalfd()` mechanism, introduced in Linux 2.6.22, provides a file descriptor interface to signal delivery, allowing integration with event-driven I/O multiplexing via `epoll()` or `select()`. When a process creates a signal file descriptor via `signalfd()` and blocks the corresponding signals with `sigprocmask()`, the kernel redirects signal delivery from the asynchronous handler path to a synchronous read interface. Each `read()` on the signal file descriptor consumes one pending signal and returns a `signalfd_siginfo` structure containing the same information as `siginfo_t`: signal number, sender PID and UID, and real-time signal payload. This design eliminates the async-signal-safety constraint because signal processing occurs in normal application code flow, but it introduces new failure modes: if the application does not read the signal file descriptor frequently enough, the kernel's signal queues fill, and for real-time signals, new occurrences are dropped once the queue reaches `RLIMIT_SIGPENDING`. The `signalfd()` approach also changes signal semantics for multi-threaded programs: signals delivered via the file descriptor are consumed by whichever thread calls `read()`, rather than the kernel's routing algorithm, allowing centralized signal handling in a dedicated thread without complex mask manipulation.

## 3. High-Performance Optimization & Failure Modes

Minimizing signal handler latency requires careful attention to stack locality and cache behavior. Signal frame construction incurs hundreds of nanoseconds of overhead on modern x86-64 processors due to cache misses when the kernel writes the full FPU/SSE state into the user stack. On processors with AVX-512 support, the `ucontext_t` structure exceeds 2 KB due to the 512-bit vector registers, causing the signal frame to span multiple cache lines and evict useful data from the L1 cache. Developers can reduce this overhead by registering handlers with the `SA_NODEFER` flag, which prevents the kernel from blocking the delivered signal during handler execution, eliminating the need to save and restore the signal mask. However, `SA_NODEFER` creates reentrancy hazards: if the handler is slow and another instance of the same signal arrives, the kernel interrupts the first handler, pushing a second signal frame onto the stack. Without careful reentrancy guards using atomic variables or thread-local counters, nested handler invocations can corrupt shared state or overflow the stack. The alternate signal stack registered via `sigaltstack()` should be sized generously—at least 64 KB—to accommodate nested handlers and large signal frames, and it should be aligned to page boundaries to optimize TLB usage.

Real-time signal queues require explicit backpressure management to prevent event loss when generation rate exceeds processing rate. The kernel's `RLIMIT_SIGPENDING` limit is a per-user limit, not per-process, meaning that a misbehaving process can exhaust the quota for the entire user, causing `sigqueue()` to fail with `EAGAIN` for unrelated processes. Application servers that accept real-time signals as IPC must monitor queue depth by periodically reading `/proc/[pid]/status` and checking the `SigQ` field, which reports pending signals versus the limit. When the queue approaches 80% capacity, the application should implement rate limiting on the signal source or switch to a different IPC mechanism like Unix domain sockets or shared memory with futex-based notification. For high-frequency event notification, developers should consider consolidating multiple events into a single real-time signal with a bitmask payload, or abandoning signals entirely in favor of `eventfd()`, which provides a lightweight counter-based notification mechanism compatible with `epoll()` edge-triggered mode, avoiding the kernel's signal routing overhead entirely.

Interrupted system call handling requires defensive coding even with `SA_RESTART` enabled, because restart semantics do not apply uniformly across all operations. The canonical pattern wraps every blocking system call in a loop that retries on `EINTR`, explicitly checking for termination conditions after each retry. Consider a network server calling `accept()` in a loop: if a `SIGCHLD` signal arrives to notify of child process termination, the kernel may restart `accept()` transparently, but the application must also check for and reap zombie children to prevent accumulation. Failing to handle `SIGCHLD` properly causes the process table to fill with zombie entries, eventually hitting `RLIMIT_NPROC` and preventing `fork()`. The correct pattern combines `accept()` in a loop with periodic `waitpid(-1, NULL, WNOHANG)` to harvest all terminated children without blocking. For time-sensitive operations like `poll()` with a timeout, the application must recalculate the remaining timeout after each `EINTR` interruption, typically by recording the start time with `clock_gettime(CLOCK_MONOTONIC)` and subtracting elapsed time from the original timeout on each retry. The `ppoll()` and `pselect()` variants provide atomic signal mask manipulation during blocking, preventing race conditions where a signal arrives between unblocking the signal and entering the blocking call, though these primitives are not universally available on legacy Unix variants.

Signal-based interprocess communication scales poorly beyond simple notification use cases. The combination of non-queuing standard signals, bounded real-time signal queues, and signal routing non-determinism in multi-threaded programs makes signals unsuitable for high-throughput message passing. In production systems, signals are best reserved for exceptional control flow: shutdown requests (`SIGTERM`), configuration reloads (`SIGHUP`), immediate termination (`SIGKILL` sent by external monitors), and asynchronous I/O notification (`SIGIO` for legacy applications, though modern code should use `epoll()` with `EPOLLET`). For reliable message passing between processes, Unix domain sockets provide guaranteed delivery, message boundaries, and control message passing for file descriptor transfer. For latency-sensitive notification between threads, atomic operations combined with futex-based `pthread_cond_wait()` deliver microsecond-scale wakeups with predictable memory ordering semantics, whereas signal delivery incurs kernel scheduler overhead and unpredictable routing delays in multi-threaded processes.

The interaction between signals and thread cancellation in POSIX threads creates subtle cancellation safety hazards. When a thread blocked in a cancellation point like `read()` or `pthread_cond_wait()` receives a cancellation request via `pthread_cancel()`, the kernel delivers the internal `SIGCANCEL` signal (or equivalent mechanism), unwinding the stack through registered cleanup handlers. If a signal handler is active when cancellation occurs, the kernel must decide whether to cancel immediately or defer until the handler returns. POSIX specifies deferred cancellation for signal handlers registered with `sigaction()`, meaning the handler completes before cancellation takes effect, but cleanup handlers registered with `pthread_cleanup_push()` do not nest with signal handlers predictably across implementations. The safest pattern disables cancellation during signal handler execution via `pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, NULL)` at handler entry, re-enabling it before return, though this requires thread-local storage to track the previous cancellation state. For complex applications mixing signals and thread cancellation, the simplest solution is to avoid cancellation entirely, using explicit termination flags checked at loop boundaries combined with condition variable notifications to wake blocked threads.

Memory barriers and atomic operations require special consideration in signal handlers due to the kernel's signal delivery model. When a signal handler executes, the kernel flushes store buffers and issues a full memory barrier to ensure that the handler observes all prior writes from the interrupted context. However, writes performed within the signal handler are not automatically visible to the interrupted context until a subsequent memory barrier. A common error pattern sets a `volatile sig_atomic_t` flag in a signal handler and polls this flag in a busy loop in the main thread, assuming that the handler's write becomes visible immediately. Without an explicit memory barrier in the polling loop, the compiler or CPU may cache the flag value in a register, preventing the loop from ever observing the signal handler's modification. The correct pattern uses atomic variables with `_Atomic` type qualifier (C11) or GCC's `__sync_*` builtins, which enforce acquire-release semantics: the signal handler performs an atomic store with release semantics, and the polling loop performs an atomic load with acquire semantics, guaranteeing that all writes preceding the store are visible after the load completes. For maximum portability across legacy compilers, wrapping the flag variable access in a function call that the compiler cannot inline serves as a crude memory barrier, forcing a register reload on each poll iteration, though this technique relies on optimization heuristics rather than language guarantees.

Signal handler reentrancy problems extend beyond async-signal-safety to include logical reentrancy within application-specific state machines. A signal handler that modifies a linked list, hash table, or red-black tree must either use lock-free data structures with atomic compare-and-swap operations, or block all signals during data structure manipulation in non-handler code. The latter approach employs `sigprocmask(SIG_BLOCK, &all_signals, &old_mask)` before entering critical sections and `sigprocmask(SIG_SETMASK, &old_mask, NULL)` after exiting, creating non-preemptible regions analogous to kernel interrupt disabling. However, frequent signal masking introduces measurable overhead—approximately 200 nanoseconds per `sigprocmask()` call on modern Linux—due to TLB flushes and signal routing table updates. For hot paths that update shared state at high frequency, a better design moves signal handling logic into a dedicated thread that blocks all signals except those it explicitly handles, while worker threads block all signals permanently. This signal thread model eliminates reentrancy entirely: signals deliver to the dedicated thread, which processes them synchronously in a loop that reads from a `signalfd()` file descriptor, updating shared state via conventional mutexes or atomics that do not require async-signal-safety.

Core dump generation triggered by signals like `SIGQUIT`, `SIGILL`, and `SIGSEGV` creates forensic challenges in production environments running with restrictive file system permissions or inside containers. The kernel writes core dumps to the current working directory by default, which may be read-only in containerized deployments or lack sufficient disk space for large process images. The `/proc/sys/kernel/core_pattern` sysctl controls core dump naming and piping to external programs, allowing administrators to pipe core dumps to `systemd-coredump` or custom archival scripts that compress and upload dumps to centralized storage. However, piped core dumps are truncated if the receiving process cannot consume data fast enough, and the kernel's core dump code holds the mmap semaphore for the entire dump duration, blocking all memory allocation and page faults in other threads. In multi-gigabyte processes, core dump generation can freeze the entire application for tens of seconds, causing cascading failures in distributed systems with aggressive health check timeouts. The `RLIMIT_CORE` resource limit provides crude control over core dump size, but setting it to 0 disables core dumps entirely, eliminating post-mortem debugging capability. A production-hardened approach configures `core_pattern` to pipe dumps to a rate-limited external collector that immediately writes a truncated dump to disk and schedules full dump generation in a background process, allowing the application to resume quickly while preserving forensic data for later analysis.
