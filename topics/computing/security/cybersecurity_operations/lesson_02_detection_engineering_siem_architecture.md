# Lesson 2: Detection Engineering, SIEM Architecture, Log Management

## 1. First-Principles Intuition & Invariants

Detection engineering exists at the intersection of adversarial reasoning and statistical inference. At its core, the discipline seeks to transform raw telemetry streams into actionable threat intelligence by constructing formal decision boundaries that distinguish malicious behavior from benign operational noise. Unlike traditional software engineering, where correctness is measured against deterministic specifications, detection engineering operates in a fundamentally adversarial environment where attackers continuously adapt to evade instrumentation. This evolutionary pressure creates an epistemic feedback loop: every detection rule published becomes obsolete the moment adversaries incorporate countermeasures, forcing defenders to reason about attacker capabilities, operational constraints, and the economic calculus of detection evasion.

The foundational invariant governing all detection systems is the tradeoff between sensitivity and specificity, expressed formally through Receiver Operating Characteristic (ROC) curves. Every detection rule partitions the event space into positive and negative classifications, producing four outcomes: true positives (legitimate threats correctly identified), false positives (benign activity misclassified as malicious), true negatives (benign activity correctly ignored), and false negatives (threats that evade detection). The precision-recall curve quantifies this boundary, where precision measures the proportion of alerts that represent genuine threats, and recall measures the proportion of actual threats successfully detected. In production security operations, false positive rates dominate operational cost because human analysts possess finite attention bandwidth. A rule generating one hundred alerts per day with 99% false positive rate consumes analyst time investigating ninety-nine irrelevant events, creating alert fatigue that degrades overall detection efficacy and increases the probability that genuine threats are dismissed as noise.

Detection methodologies bifurcate into two fundamental paradigms: signature-based detection and anomaly-based detection, each with distinct failure modes and operational characteristics. Signature-based detection encodes known attack patterns as explicit matching rules, analogous to hash-based malware signatures or YARA rules. These rules operate deterministically: when an event's attributes match the signature's predicate logic, an alert fires. The computational model resembles finite automaton matching, where events transition through state machines until a terminal accept state triggers detection. Signature-based systems exhibit high precision because rules encode specific threat indicators validated through prior incident analysis, but they suffer from zero-day blindness—they cannot detect novel attack techniques absent from the signature corpus. This creates an asymmetric advantage for attackers, who need only innovate beyond the documented threat landscape to achieve complete evasion.

Anomaly-based detection inverts this paradigm by constructing baseline models of normal behavior and flagging deviations exceeding statistical thresholds. Rather than enumerating malicious patterns, anomaly detectors learn the distribution of benign activity and signal when observations fall outside expected confidence intervals. This approach provides theoretical coverage against zero-day threats because novel attacks, by definition, deviate from historical baselines. However, anomaly detection introduces fundamental challenges rooted in the curse of dimensionality and concept drift. High-dimensional feature spaces make it computationally intractable to model every behavioral axis, forcing practitioners to project telemetry onto lower-dimensional manifolds that preserve discriminative power while remaining tractable. Concept drift describes the temporal non-stationarity of baselines: user behavior patterns shift across business cycles, infrastructure topology evolves, and organizational processes change, causing yesterday's normal to become today's anomaly. Adaptive learning systems must continuously retrain models to track distribution shifts without catastrophically forgetting historical attack patterns.

Modern detection engineering synthesizes these paradigms through layered defense architectures that compose multiple detection modalities at different abstraction layers. Network intrusion detection systems analyze packet headers and payloads for protocol violations and malicious signatures. Endpoint detection and response platforms instrument operating system telemetry—process creation events, registry modifications, file system writes, network connections—constructing behavioral graphs that model process lineage and inter-process relationships. User and entity behavior analytics systems aggregate authentication logs, database queries, and API access patterns to detect credential compromise, insider threats, and lateral movement. Each layer generates event streams that feed upstream correlation engines, which apply temporal logic to detect multi-stage attack campaigns spanning minutes or weeks.

The Security Information and Event Management (SIEM) architecture emerged as the canonical framework for centralizing heterogeneous telemetry and operationalizing detection logic at scale. A SIEM functions as a distributed data warehouse optimized for write-heavy ingest, full-text search across semi-structured logs, and real-time alerting on streaming events. Conceptually, it implements a pipeline architecture with five fundamental stages: collection, normalization, enrichment, correlation, and alerting. Collection agents deployed across infrastructure forward logs via syslog, HTTP APIs, or proprietary protocols. Normalization parsers transform vendor-specific log formats into a unified schema, extracting structured fields from unstructured text through regular expressions, key-value parsing, or JSON deserialization. Enrichment stages append contextual metadata—geolocation data for IP addresses, asset inventory tags, threat intelligence feeds—transforming sparse events into information-dense records. Correlation engines evaluate detection rules against event streams, maintaining stateful windows to detect sequential patterns. Alerting mechanisms route triggered detections to analyst queues, ticketing systems, or automated response orchestrators.

The architectural invariant governing SIEM performance is the write amplification factor introduced by indexing overhead. Every ingested event undergoes parsing, field extraction, enrichment, and indexing before becoming queryable. Modern SIEMs index events into inverted indices optimized for full-text search, where each unique term generates posting lists mapping to document identifiers. This indexing overhead imposes a storage multiplier: a one-kilobyte raw log may consume five kilobytes of indexed storage after accounting for inverted indices, columnar projections, and metadata overhead. At scale, this amplification drives storage costs to dominate total cost of ownership, forcing practitioners to implement tiered retention strategies where high-resolution indices expire after days while compressed archives persist for regulatory compliance periods measured in years.

Log aggregation pipelines function as the circulatory system of detection infrastructure, shuttling telemetry from distributed sources to centralized analytics platforms. Unlike batch ETL pipelines that process data at rest, log aggregation operates on unbounded streams with latency requirements measured in seconds. The canonical architecture employs a message queue as a decoupling buffer between log producers and consumers, providing backpressure absorption when downstream processing lags behind ingestion rates. Apache Kafka has emerged as the de facto standard for log aggregation, implementing a distributed commit log with partitioning semantics that enable horizontal scaling. Producers append events to topic partitions, and consumers maintain offset pointers tracking read positions, enabling replay semantics for recovery from processing failures.

The fundamental theorem of log aggregation is the CAP theorem applied to telemetry pipelines: under network partitions, systems must choose between consistency (all consumers see events in identical order) and availability (the pipeline continues accepting writes). Production log pipelines invariably prioritize availability over strict ordering because detection systems tolerate minor reordering but cannot tolerate log loss. This design choice manifests in at-least-once delivery semantics, where duplicate events may propagate through the pipeline following network retries or consumer restarts. Detection rules must be idempotent with respect to duplicate events, typically by tracking unique event identifiers or using sliding time windows that absorb reordered arrivals.

Normalization transforms the Tower of Babel problem inherent in heterogeneous log sources into a unified semantic model. A Windows Security Event Log entry describing a process creation event contains fundamentally the same information as a Linux auditd log entry, but they employ incompatible schemas, field names, and timestamp formats. Normalization parsers apply vendor-specific transformations to extract common fields—timestamp, source IP, destination IP, process name, user principal—mapping them to a canonical schema like the Elastic Common Schema (ECS) or the Open Cybersecurity Schema Framework (OCSF). This schema unification enables detection rules to operate across heterogeneous infrastructure without encoding vendor-specific logic.

The parser implementation strategy bifurcates into rule-based and machine learning approaches. Rule-based parsers employ regular expressions, Grok patterns, or parsing expression grammars to extract structured fields from unstructured text. These parsers exhibit deterministic behavior and interpretable failure modes but require manual maintenance as log formats evolve. Machine learning parsers train sequence-to-sequence models on labeled log samples, learning to extract fields through statistical pattern recognition. These models generalize to minor format variations but introduce opacity that complicates debugging and may hallucinate fields in adversarial inputs.

Retention strategies encode the economic tradeoff between forensic depth and storage cost. Regulatory frameworks like GDPR, HIPAA, and PCI-DSS mandate minimum retention periods ranging from months to years, but retaining high-cardinality telemetry at full fidelity for extended periods becomes prohibitively expensive. Tiered storage architectures partition data by access frequency: hot storage hosts recent, frequently queried data on high-performance SSDs with millisecond query latencies; warm storage archives older data on cost-optimized object stores with second-scale query latencies; cold storage preserves compliance data on tape or glacier-class storage with minute-to-hour retrieval times. The boundary between tiers is determined by the investigative time horizon—most incident response investigations query telemetry from the past thirty days, making this a natural hot tier boundary.

Alerting mechanisms transform detected threats from database entries into actionable analyst tasks. The alerting pipeline must solve several challenges: deduplication to collapse repeated firings of the same rule into single incidents, severity scoring to prioritize analyst attention, context enrichment to accelerate investigation, and routing logic to assign alerts to appropriate teams. Deduplication algorithms employ temporal grouping windows that merge alerts firing within configurable intervals, typically five to fifteen minutes, preventing alert storms where a single root cause generates thousands of individual firings. Severity scoring systems synthesize multiple signals—rule criticality, asset value, threat intelligence context, user risk scores—into a composite priority metric that orders the analyst queue. Context enrichment appends investigative pivots to alerts: recent authentication history for the affected user, network flow records for suspicious connections, file hashes for malicious executables, enabling analysts to triage incidents without manually correlating data sources.

## 2. Core Architecture & Mechanics

The SIEM architecture implements a distributed pipeline processing unbounded event streams through a directed acyclic graph of transformation stages. Understanding this architecture requires dissecting the data flow from raw log emission through final alert presentation, examining the internal data structures and algorithms at each stage.

The collection layer deploys lightweight forwarding agents on every log-producing system: servers, workstations, network appliances, cloud control planes. These agents tail log files, subscribe to Windows Event Log channels, or receive syslog streams, batching events into compressed payloads transmitted to upstream aggregation endpoints. The batching algorithm trades latency for throughput, accumulating events until a configurable time window elapses or a size threshold triggers transmission. A typical configuration might batch for five seconds or one megabyte, whichever arrives first. This batching reduces network overhead and allows TCP connection reuse, but introduces delivery latency that creates a fundamental lower bound on detection speed.

Agent protocols must handle network failures gracefully through persistent local queues that buffer events during upstream unavailability. The canonical implementation maintains a disk-backed ring buffer with configurable capacity, typically several gigabytes. When the buffer reaches capacity, the agent must choose between blocking further log writes (potentially destabilizing the host application) or dropping oldest events. Production deployments universally choose to drop events, accepting bounded log loss over host instability. This design decision places an upper bound on tolerable network partition duration: if connectivity remains severed longer than the buffer capacity divided by the ingestion rate, log loss becomes inevitable.

The network transport layer typically employs TLS-encrypted HTTPS POST requests with gzip content encoding, achieving compression ratios between three-to-one and ten-to-one depending on log entropy. Authentication occurs via pre-shared API keys, mutual TLS certificates, or ephemeral tokens issued through an identity federation service. The protocol must handle backpressure signaling through HTTP 429 rate limit responses or 503 service unavailable errors, triggering exponential backoff with jitter to prevent thundering herd effects when services recover.

Upon arrival at the SIEM ingestion boundary, events enter a distributed message queue that decouples collection from processing. The queue partitioning strategy critically impacts downstream parallelism and ordering guarantees. A common approach partitions by source IP address or hostname, ensuring all events from a single host traverse the same partition and are processed by the same consumer, preserving temporal ordering within a host. This partitioning enables stateful correlation rules that track per-host state without requiring distributed coordination.

The normalization stage consumes events from the queue and applies parsing rules to extract structured fields. The parser selection logic uses metadata embedded by collection agents—source type, log format identifier—to route events to appropriate parsing pipelines. A syslog parser extracts RFC5424 structured data elements, a JSON parser deserializes nested objects into flat field hierarchies, and vendor-specific parsers apply custom logic for proprietary formats.

Parsing failures introduce a critical failure mode: when an event does not match any parser's expected format, the SIEM must choose between discarding the event or forwarding it unparsed. Production systems forward unparsed events to a catchall index, preserving the raw data for manual investigation while marking the event as unparseable. This ensures that novel log formats or corrupted events remain available for forensic analysis rather than vanishing silently.

Field extraction employs named capture groups in regular expressions or structured parsing libraries. Consider a parsing rule for an SSH authentication failure log:

```
Failed password for invalid user admin from 203.0.113.45 port 54321 ssh2
```

The parser applies a regular expression with named groups:

```
^Failed password for invalid user (?<username>\S+) from (?<source_ip>\d+\.\d+\.\d+\.\d+) port (?<source_port>\d+)
```

Extracting fields `username=admin`, `source_ip=203.0.113.45`, `source_port=54321`. These fields are mapped to the normalized schema, producing a structured event:

```json
{
  "timestamp": "2025-02-15T14:23:17Z",
  "event.category": "authentication",
  "event.outcome": "failure",
  "user.name": "admin",
  "source.ip": "203.0.113.45",
  "source.port": 54321,
  "event.original": "Failed password for invalid user admin from 203.0.113.45 port 54321 ssh2"
}
```

The enrichment stage appends contextual metadata by performing lookups against external data sources. A geolocation enrichment service queries a MaxMind GeoIP database to append country, city, and autonomous system number for the source IP. A threat intelligence enrichment service checks the IP against reputation feeds, appending threat actor attribution, malware family associations, or abuse confidence scores. An asset inventory service queries a CMDB to append system criticality, business owner, and compliance scope tags. These enrichments transform sparse events into information-dense records that accelerate analyst triage.

Enrichment services introduce latency and failure modes that must be carefully managed. A synchronous enrichment architecture blocks event processing on external service responses, causing head-of-line blocking when services experience latency spikes. An asynchronous architecture decouples enrichment from the critical path by emitting partially enriched events immediately and applying enrichments as background writes. This trades consistency for availability, allowing detection rules to fire on unenriched events if downstream services fail.

The correlation engine evaluates detection rules against enriched event streams. Rules are expressed in domain-specific languages optimized for temporal pattern matching over streaming data. Splunk Processing Language (SPL), Elasticsearch Query DSL, and Sigma rules represent different points in the expressiveness-performance tradeoff space. The correlation engine maintains stateful sliding windows that buffer recent events, enabling rules to detect sequences spanning multiple events.

A correlation rule detecting brute-force authentication attacks might specify: "Alert if more than five failed authentication attempts occur from the same source IP against the same target system within a five-minute window, followed by a successful authentication from that IP within one minute." Implementing this rule requires maintaining per-IP, per-target state that counts recent failures and watches for subsequent successes.

The state management strategy determines whether the correlation engine can scale horizontally. A naive implementation stores state in memory within a single-threaded process, limiting throughput to a single CPU core and introducing catastrophic data loss on process restart. A distributed implementation partitions state across multiple workers using consistent hashing, allowing horizontal scaling but introducing coordination overhead. A persistent implementation checkpoints state to durable storage periodically, enabling recovery from failures at the cost of recovery time objectives measured in seconds or minutes.

The correlation engine must handle late-arriving events that violate temporal ordering assumptions. Network delays, clock skew, or batch processing can cause events to arrive out of timestamp order. A correlation rule expecting events in strict temporal sequence may fail to detect attack patterns if events arrive reordered. Watermarking strategies bound the maximum tolerable out-of-order delay, buffering events until a watermark timestamp advances, then processing all buffered events up to that watermark. This introduces bounded latency but provides ordering guarantees within the watermark window.

Detection rule logic encodes the core intellectual property of a security operations program. Rules evolve through a lifecycle: initial authoring based on threat intelligence, tuning to reduce false positives, promotion from testing to production, and eventual deprecation as attack techniques evolve. Rule authoring requires balancing specificity against evasion resilience. Overly specific rules matching exact command-line syntax or file paths are trivially evaded through minor modifications. Robust rules match semantic behavior invariants that remain stable across evasion attempts.

Consider a rule detecting credential dumping via the Windows LSASS process. A naive rule might match exact process names:

```
process.name == "mimikatz.exe"
```

An attacker evades this by renaming the binary. A more robust rule matches process access patterns:

```
process.name != "lsass.exe" AND
process.accessed_memory_region(target="lsass.exe") AND
process.access_rights CONTAINS "PROCESS_VM_READ"
```

This rule detects any non-LSASS process reading LSASS memory, a behavioral invariant required for credential dumping regardless of tool names. However, this rule generates false positives from legitimate security tools and debuggers, requiring further tuning through allowlist exceptions.

The alerting stage consumes triggered detection rules and transforms them into analyst-actionable tasks. Alert documents aggregate all relevant context: the matched events, enrichment metadata, rule description, recommended response procedures, and links to related alerts. Alert deduplication logic groups temporally proximate alerts matching the same rule against the same entity, collapsing what might be hundreds of individual firings into a single incident.

Severity scoring algorithms synthesize multiple risk dimensions into a composite priority score. A rule's base severity reflects the inherent criticality of the detected technique—privilege escalation warrants higher severity than reconnaissance. Asset criticality modulates severity based on the affected system's business impact—an alert on a production database outweighs the same alert on a test system. User risk scores derived from behavioral analytics further adjust severity—activity from a user with historical anomalies receives elevated priority. Threat intelligence context amplifies severity when the detected technique matches active threat campaigns.

The alert routing engine assigns alerts to analyst queues based on organizational structure, on-call schedules, and expertise requirements. A simple implementation routes based on alert category: network alerts to the network security team, endpoint alerts to the host security team, cloud alerts to the cloud security team. Advanced implementations employ machine learning to predict which analyst is most likely to efficiently resolve each alert type based on historical resolution patterns.

Alert fatigue represents the dominant operational challenge in production security operations centers. A SIEM generating thousands of daily alerts overwhelms analyst capacity, forcing triage heuristics that inevitably miss genuine threats buried in noise. Effective alert tuning requires iterative refinement: analysts investigate alerts, identify false positive patterns, and implement suppressions or rule modifications. This feedback loop transforms detection rules from their initial high-sensitivity, low-specificity state toward the optimal balance point on the precision-recall curve.

The storage layer implements a hybrid architecture balancing query performance against cost efficiency. Hot indices store recent data in column-oriented formats optimized for analytical queries. Each field is stored in a separate column, enabling selective field retrieval without deserializing entire documents. Columnar storage achieves superior compression ratios compared to row-oriented formats because values within a column exhibit high correlation, enabling dictionary encoding, run-length encoding, or delta encoding.

Inverted indices accelerate full-text search by maintaining term-to-document posting lists. The indexing process tokenizes text fields into terms, applies stemming or lemmatization to normalize variations, and builds posting lists mapping each unique term to the document identifiers containing that term. Search queries are decomposed into Boolean expressions over terms, and the engine intersects or unions the corresponding posting lists to identify matching documents. This data structure transforms substring search from a linear scan over all documents—intractable at scale—into posting list intersection, which exhibits logarithmic complexity with respect to vocabulary size.

The retention management system migrates aging data through storage tiers based on access patterns and compliance requirements. A typical tier migration schedule moves data from hot SSDs to warm object storage after thirty days, then to cold archive storage after ninety days, finally deleting data after the regulatory retention period expires. Migration occurs through background reindexing jobs that read documents from the source tier, apply format transformations (e.g., removing inverted indices for cold data), and write to the destination tier.

## 3. High-Performance Optimization & Failure Modes

Scaling SIEM infrastructure to handle enterprise telemetry volumes requires careful attention to bottlenecks across the ingestion, processing, and query planes. A typical enterprise generates terabytes of daily logs, translating to sustained ingestion rates of tens of thousands of events per second with spikes reaching hundreds of thousands during business peak hours. Meeting these throughput requirements while maintaining sub-minute detection latencies demands optimization across multiple architectural layers.

The ingestion bottleneck often manifests at the collection agent layer when agents contend with application workloads for CPU and disk I/O. Efficient agents employ memory-mapped I/O to tail log files, avoiding the syscall overhead of traditional read operations. Batching and compression occur in separate threads to prevent blocking the log tailing loop. Agents must implement adaptive rate limiting to prevent overwhelming upstream services during spike events like mass deployments or application restarts that generate log bursts.

Network bandwidth consumption becomes problematic in distributed environments with thousands of endpoints forwarding logs to centralized collectors. Compression provides the first line of defense, reducing bandwidth by 70-90% depending on log entropy. Protocol-level optimizations include connection pooling to amortize TCP handshake overhead, HTTP pipelining to reduce round-trip latencies, and adaptive batch sizing that increases batch sizes during high-volume periods to improve throughput at the cost of latency.

The message queue forms the central coordination point where ingestion and processing rates decouple. Queue capacity planning must accommodate burst traffic without overflowing, requiring provisioning for peak rates rather than averages. A common sizing heuristic provisions capacity for the 99th percentile ingestion rate sustained for fifteen minutes, providing buffer against transient processing slowdowns. Queue monitoring exposes partition lag metrics—the delta between producer write offsets and consumer read offsets—that quantify processing delays and trigger autoscaling responses.

Parser performance directly impacts processing throughput because parsing is CPU-bound and must occur serially for each event. Regular expression engines employing backtracking algorithms exhibit pathological performance on crafted inputs, potentially degrading to exponential time complexity. Production parsers employ possessive quantifiers and atomic groups to disable backtracking, ensuring linear time complexity with respect to input length. Alternatively, deterministic finite automaton-based parsers provide bounded performance guarantees at the cost of expressiveness limitations.

Parser failure handling must prevent malformed events from wedging the processing pipeline. A defensive parsing strategy wraps each parser invocation in a timeout that kills parsing attempts exceeding a threshold, typically one hundred milliseconds. Events that timeout are forwarded unparsed to preserve data rather than blocking the pipeline. Persistent parser failures on specific event types trigger circuit breakers that bypass problematic parsers after consecutive failure thresholds, preventing cascading failures.

Enrichment services introduce external dependencies that become availability bottlenecks under failure scenarios. A synchronous enrichment architecture where event processing blocks on enrichment responses inherits the availability of all enrichment dependencies, creating a multiplicative failure probability. If each enrichment service maintains 99% uptime, a pipeline dependent on five enrichment services achieves only 95% uptime through the chain rule of independent failures. An asynchronous enrichment architecture with default fallback values maintains processing throughput during enrichment service outages, degrading gracefully by emitting less-enriched events rather than blocking entirely.

Correlation engine scaling requires careful state partitioning to enable horizontal parallelism. A stateful correlation rule tracking failed authentication attempts per source IP must route all events from a given IP to the same worker to maintain consistent state. The partitioning function applies consistent hashing to the IP address, mapping it deterministically to a worker index. This approach scales linearly by adding workers and repartitioning state, but introduces rebalancing overhead when the worker pool changes size, temporarily stalling processing during state migration.

Memory-resident state stores enable low-latency correlation at the cost of capacity limits and durability risks. A correlation engine maintaining five-minute sliding windows over authentication events buffers recent events in memory, sizing buffers to accommodate peak event rates. A system processing ten thousand authentication events per second must buffer three million events, consuming approximately three gigabytes of memory at one kilobyte per event. Periodic state checkpointing to persistent storage enables recovery from worker failures but introduces write amplification that can saturate storage I/O.

Query performance optimization centers on minimizing data scanned during searches. Partition pruning filters out entire index partitions that cannot contain matching documents based on query predicates. A query searching for events in a specific time range only scans partitions intersecting that range, potentially eliminating 90% of data from consideration. Schema-level optimizations include separating high-cardinality, rarely queried fields into separate indices to reduce index sizes for common queries.

Alert storm prevention mechanisms detect and suppress runaway alert generation before overwhelming analyst queues. Rate limiting logic tracks alert firing rates per rule, automatically disabling rules exceeding configured thresholds until manual review occurs. A typical threshold might allow one hundred alerts per five-minute interval before triggering suppression. Anomaly detection over alert volumes identifies unusual spikes that indicate rule misconfiguration or infrastructure failures, automatically creating meta-alerts that notify SIEM administrators.

False positive reduction represents the most critical operational optimization because analyst attention is the scarce resource constraining detection capacity. The iterative tuning process begins by collecting false positive samples during initial rule deployment, identifying common patterns across false positives, and implementing suppressions targeting those patterns. Allowlist-based suppressions exempt specific entities, such as known security tools or administrative service accounts, from triggering rules. Context-based suppressions add additional predicates that distinguish true attacks from false positives, such as requiring unusual parent processes or unexpected user accounts.

Detection rule testing frameworks prevent regressions during tuning by maintaining test suites of historical true positive and true negative events. Each rule modification is validated against these test suites to ensure true positives remain detected while false positive rates decline. The test framework replays historical event datasets through the correlation engine with candidate rule modifications, measuring precision and recall changes. Automated canary deployment strategies promote rule changes through environments—testing, staging, production—requiring passing acceptance criteria before advancing.

Compliance retention requirements create tension between storage costs and legal obligations. Data minimization strategies reduce retention costs by filtering unnecessary log sources, reducing field cardinality, and sampling high-volume, low-signal event types. Network flow logs, which may constitute 80% of ingestion volume, can be sampled at 1:100 ratios for commodity internet traffic while retaining 100% of flows involving critical assets. Field projection drops high-cardinality fields like unique session identifiers that provide minimal forensic value, reducing storage footprint by 30-50%.

Encryption at rest protects archived logs from storage media theft or unauthorized access. Block-level encryption using AES-256 in XTS mode provides transparent encryption with minimal performance overhead, typically under 5% CPU utilization. Key management architectures employ envelope encryption where data encryption keys are themselves encrypted by key encryption keys stored in hardware security modules. Key rotation strategies periodically rekey data by rewriting encrypted blocks with new keys, limiting cryptographic exposure per key to bounded time windows.

Disaster recovery strategies must account for the write-heavy, high-volume characteristics of log data. Traditional backup approaches copying entire datasets to secondary storage become prohibitively expensive at petabyte scale. Incremental backup strategies leverage immutable log properties—logs are write-once and never modified—to backup only newly ingested data. Replication to geographically distributed regions provides resilience against regional failures while introducing cross-region bandwidth costs proportional to ingestion rates.

Chain-of-custody requirements for forensic investigations demand tamper-evident logging that cryptographically proves log integrity. Write-ahead logging systems append events to immutable logs while computing rolling Merkle trees over log segments. Each tree node contains a cryptographic hash of its children, with the root hash published to an external timestamping service or blockchain. This construction enables verification that no historical log entry has been modified or deleted without detection, satisfying evidentiary requirements for legal proceedings.

The ultimate failure mode in detection engineering is adversarial evasion, where attackers deliberately craft attack techniques that exploit blind spots in detection coverage. Defenders combat evasion through defense-in-depth strategies that layer multiple detection modalities, ensuring that evasion of one layer exposes attackers to detection at another. Network-level detections capture external reconnaissance, endpoint detections identify post-exploitation activity, and cloud API detections reveal lateral movement, collectively covering the full attack lifecycle. Continuous threat intelligence integration updates detection rules to address emerging techniques documented in frameworks like MITRE ATT&CK, closing evasion gaps as adversaries innovate. The arms race between attacker innovation and defender adaptation forms the fundamental dynamic driving detection engineering evolution, ensuring that detection systems remain permanently under development rather than ever reaching a final, complete state.
