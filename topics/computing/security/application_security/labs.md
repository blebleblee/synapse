# Operational Verification Labs: Application Security

## Objective & Lab Bench Setup

Application security extends beyond software-level vulnerability analysis into the physical hardware substrate that executes code, stores cryptographic secrets, and enforces isolation boundaries. Modern embedded systems, IoT devices, mobile platforms, and even server-class hardware implement security primitives in firmware, bootloaders, Trusted Execution Environments (TEEs), and hardware security modules (HSMs). These implementations are opaque to traditional software testing but become transparent under hardware-level probing, bus analysis, and fault injection. This laboratory guide grounds application security verification in the physical realities of silicon, signal timing, and electromagnetic emanation, bridging the gap between abstract vulnerability research and the concrete diagnostic protocols required to validate security claims in production hardware.

The laboratory bench for hardware-assisted application security verification requires a curated set of physical instruments and software toolchains that operate at the boundary between digital logic and radio-frequency signal propagation. At the core sits a USB logic analyzer capable of sampling digital buses at 100 MHz or higher, with sufficient channel count to simultaneously capture multi-wire protocols such as SPI, I²C, JTAG, and UART. The Saleae Logic series, DreamSourceLab DSLogic, or Sigrok-compatible Cypress FX2LP-based analyzers provide the necessary bandwidth and protocol decoder integration. Complementing the logic analyzer is a USB-to-UART bridge supporting 3.3V and 1.8V signaling levels, essential for intercepting serial console output and bootloader debugging messages that often leak memory addresses, build versions, and security configuration flags. The FTDI FT232H or CP2102 modules serve this role reliably, with the FT232H offering additional MPSSE (Multi-Protocol Synchronous Serial Engine) modes for SPI and I²C bit-banging.

For memory extraction and firmware manipulation, a dedicated SPI/I²C flash programmer such as the Shikra or Bus Pirate enables non-invasive reading and writing of external NOR flash chips, bypassing software-enforced read protection. The CH341A programmer provides a low-cost alternative for 25-series SPI flash chips commonly found in routers, IoT devices, and embedded controllers. JTAG and SWD (Serial Wire Debug) access requires an OpenOCD-compatible debug probe such as the ST-Link V2, J-Link EDU, or CMSIS-DAP adapter, allowing direct CPU halting, register inspection, and memory manipulation on ARM Cortex-M and Cortex-A cores. For power analysis and fault injection experiments, a Chipwhisperer Lite or Pro captures power traces synchronized with cryptographic operations, enabling differential power analysis (DPA) and clock glitching attacks that reveal AES key bytes or bypass secure boot verification.

The software diagnostic suite integrates protocol decoders, disassemblers, and binary analysis frameworks into a unified verification workflow. Sigrok-cli provides command-line access to logic analyzer captures with built-in protocol decoders for SPI, I²C, UART, JTAG, 1-Wire, CAN, and dozens of other embedded buses, exporting decoded packets to JSON or VCD (Value Change Dump) format for correlation with firmware execution traces. OpenOCD bridges JTAG/SWD hardware to GDB, enabling source-level debugging of ARM, MIPS, RISC-V, and x86 targets through standardized remote serial protocol commands. Flashrom abstracts flash chip programming across dozens of hardware interfaces, supporting parallel, LPC, FWH, SPI, and I²C flash topologies with automatic chip identification and protection status queries. Binwalk automates firmware image analysis, extracting compressed filesystems, bootloader headers, and embedded certificates from raw flash dumps through entropy analysis and magic byte signature matching. Radare2 provides interactive disassembly, emulation, and binary diffing capabilities, with r2pipe integration allowing Python-scripted vulnerability pattern matching across firmware revisions.

The physical lab bench layout prioritizes signal integrity and electromagnetic isolation. The target device under test (DUT) sits on an anti-static mat with all ground connections referenced to a common star-point ground rail, minimizing ground loops that introduce noise into sub-millivolt analog measurements. Logic analyzer probe grounds connect directly to DUT ground test points or exposed via plane, with probe tips using spring-loaded pogo pins or micro-grabber clips to ensure reliable contact on 0.1-inch and 0.05-inch pitch headers. For BGA (Ball Grid Array) and QFN (Quad Flat No-Lead) packages without exposed test pads, hot-air rework stations and UV-curing conductive epoxy enable temporary breakout of internal signals to measurement points. Power supplies must provide clean, ripple-free voltage rails with current limiting and oscilloscope-grade precision, as voltage droops during flash programming or CPU clock glitching can corrupt firmware or damage silicon. A benchtop oscilloscope with 200 MHz bandwidth and 1 GSa/s sampling complements the logic analyzer for analog signal characterization, particularly when analyzing power rail transients during cryptographic operations or measuring SPI clock jitter that might indicate counterfeit components.

Software installation on the analysis workstation requires a Debian-based Linux distribution for optimal driver support and package availability. The core toolchain installation proceeds as follows: `sudo apt-get update && sudo apt-get install -y sigrok-cli openocd flashrom binwalk radare2 gdb-multiarch minicom picocom screen python3-pip python3-dev libusb-1.0-0-dev libftdi1-dev`. Sigrok requires udev rules to grant non-root USB access: `sudo usermod -aG plugdev $USER` followed by `sudo wget https://sigrok.org/gitweb/?p=libsigrok.git;a=blob_plain;f=contrib/60-libsigrok.rules -O /etc/udev/rules.d/60-libsigrok.rules && sudo udevadm control --reload-rules`. OpenOCD similarly needs udev permissions for JTAG adapters: `sudo wget https://github.com/openocd-org/openocd/raw/master/contrib/60-openocd.rules -O /etc/udev/rules.d/60-openocd.rules`. Python-based binary analysis tools install via pip: `pip3 install --user binwalk r2pipe keystone-engine capstone unicorn`. For Chipwhisperer integration, the official repository provides pre-compiled packages: `pip3 install --user chipwhisperer`. After installation, verify toolchain accessibility with `sigrok-cli --version`, `openocd --version`, `flashrom --version`, and `radare2 -v`, confirming version numbers match current stable releases to avoid protocol decoder regressions or hardware compatibility issues.

Target selection for these laboratories emphasizes commercially available development boards and consumer electronics that expose standard debug interfaces without requiring invasive silicon decapsulation or wafer-level probing. The STM32F103C8T6 "Blue Pill" board provides an ARM Cortex-M3 microcontroller with SWD debug header, SPI flash expansion socket, and UART console, making it ideal for bootloader security and firmware extraction exercises. For embedded Linux targets, the Raspberry Pi Zero W exposes UART on GPIO14/GPIO15 and offers SD card boot with observable U-Boot and kernel initialization sequences. Router hardware such as the TP-Link TL-WR841N contains an Atheros MIPS SoC with UART console and external SPI flash, demonstrating real-world firmware update attack surfaces. IoT devices like the ESP8266 and ESP32 modules feature integrated Wi-Fi with exposed bootloader UART and downloadable flash contents via esptool, illustrating over-the-air (OTA) update vulnerabilities and certificate storage weaknesses.

## Exercise 1: Live Hardware Probing & Signal Capture

The first operational verification exercise establishes baseline signal capture capabilities by probing a live UART console during device boot, capturing bootloader output, and correlating serial timing with CPU execution states. UART (Universal Asynchronous Receiver-Transmitter) represents the most ubiquitous debug interface in embedded systems, often left enabled in production firmware despite transmitting sensitive information such as memory maps, hardware revision strings, and failed authentication attempts. Unlike JTAG or SWD, UART requires no cryptographic handshake or debug authentication, making it the primary reconnaissance vector for hardware-level application security assessment.

Begin by identifying UART test points on the target device. On PCBs with silkscreen labels, look for "TX", "RX", "GND", and sometimes "VCC" markings near unpopulated header footprints or test vias. The TX (transmit) pin outputs serial data from the device to the analyzer, while RX (receive) accepts commands sent to the device. Ground provides the voltage reference for signal detection, and VCC indicates the logic level voltage (typically 3.3V or 1.8V). When silkscreen is absent, multimeter continuity mode traces suspected UART pins back to the main SoC, or oscilloscope probing during boot reveals characteristic asynchronous square waves on TX pins. UART baud rates commonly default to 115200, 57600, 38400, or 9600 bits per second, with 8 data bits, no parity, and 1 stop bit (8N1 configuration).

Connect the logic analyzer to the identified UART pins using the following mapping: logic analyzer Channel 0 to device TX, Channel 1 to device RX, and logic analyzer ground to device ground. Do not connect logic analyzer VCC to device VCC, as this creates a voltage rail conflict; the logic analyzer derives its threshold detection from ground-referenced signal swings and does not source power to the target. Power the target device from its normal supply (USB, barrel jack, or battery), ensuring voltage regulators have stabilized before initiating capture. Launch sigrok-cli with UART protocol decoder and trigger on TX activity: `sigrok-cli --driver fx2lafw --config samplerate=24M --channels D0=TX,D1=RX --triggers TX=r --protocol-decoders uart:baudrate=115200:format=ascii --output-format ascii --continuous`. This command configures a Cypress FX2LP-based logic analyzer to sample at 24 MHz, assigns channel names, triggers on a rising edge (device boot assertion), decodes UART at 115200 baud, and outputs human-readable ASCII text directly to the terminal.

Press the target device reset button or cycle power while the capture is running. Within milliseconds, the bootloader emits its identification string, typically containing vendor name, version number, build date, and sometimes the base memory address where execution begins. A representative U-Boot capture from a MIPS router might display: `U-Boot 1.1.3 (Aug 15 2017 - 14:23:45) Board: AP121 reference board DRAM: 32 MB Flash: 4 MB Using default environment In: serial Out: serial Err: serial Net: ag7240_enet_initialize... eth0: 00:03:7f:09:0b:ad eth0 up eth1: 00:03:7f:09:0b:ac eth1 up Hit any key to stop autoboot: 0`. This output reveals critical reconnaissance data: the bootloader version (U-Boot 1.1.3, known to contain CVE-2018-18439 and CVE-2019-11059 vulnerabilities), DRAM size (32 MB, limiting exploit payload space), flash size (4 MB, indicating the entire firmware image fits within flashrom extraction range), default Ethernet MAC addresses (useful for identifying cloned hardware or supply chain substitution), and the autoboot interrupt window (3 seconds, during which sending any character via UART RX drops into the U-Boot command shell).

To interact with the bootloader, establish a bidirectional UART session using minicom or picocom. The FT232H USB-to-UART adapter connects with TX to device RX, RX to device TX, and ground to ground (note the crossover: analyzer TX transmits to device RX input). Configure minicom with `minicom -D /dev/ttyUSB0 -b 115200`, disabling hardware flow control in the settings menu (`Ctrl-A Z`, then `O` for configure, select "Serial port setup", set "Hardware Flow Control" to "No"). Power-cycle the device and press the spacebar during the autoboot countdown. The U-Boot prompt `ar7240>` appears, granting access to memory manipulation commands (`md` for memory display, `mm` for memory modify, `cp` for copy, `erase` and `protect` for flash management). Issue `printenv` to dump environment variables, which often contain root filesystem locations, kernel command-line arguments, and default login credentials stored in plaintext. Execute `md 0xbf000000 0x100` to display the first 256 bytes of NOR flash at physical address 0xbf000000, revealing the flash chip's manufacturer ID and device ID bytes that flashrom uses for automatic detection.

For devices without an exposed UART header, solder a 4-pin 0.1-inch header directly to TX, RX, GND test points using 30-gauge Kynar wire wrap wire and a temperature-controlled soldering iron at 315°C with a conical tip. Flux-cored 63/37 tin-lead solder provides superior wetting compared to lead-free alloys, critical for reliable contact on small SMD pads. When soldering to BGAs or QFN ground pads, use low-temperature Chip Quik alloy to temporarily lower the melting point, preventing thermal damage to adjacent components. After header installation, apply conformal coating or hot glue strain relief to prevent mechanical stress from repeatedly plugging and unplugging the UART cable during iterative testing.

Capture timing analysis reveals CPU execution bottlenecks and authentication bypass opportunities. Use the logic analyzer's measurement cursors to quantify the duration between bootloader initialization and kernel decompression, identifying the window available for UART-based exploit delivery. Modern bootloaders implement secure boot verification through HMAC-SHA256 or RSA-2048 signature checks on kernel images, operations that consume 50-200 milliseconds depending on image size and cryptographic accelerator availability. During this verification window, the CPU is unresponsive to UART input, but immediately after verification completes, the bootloader may process environment variable overrides or command-line parameters that can redirect execution. Measure the pulse width of the "Verifying kernel..." message and the subsequent "Starting kernel..." transition to determine the exact timing of the attestation gap.

Advanced signal capture extends to SPI flash read operations during boot, where the bootloader fetches kernel and filesystem images from external NOR flash. Connect logic analyzer channels to SPI bus pins: CS (chip select), CLK (clock), MOSI (master out slave in), and MISO (master in slave out). Configure sigrok-cli with SPI decoder: `sigrok-cli --driver fx2lafw --config samplerate=24M --channels D0=CLK,D1=MOSI,D2=MISO,D3=CS --protocol-decoders spi:clk=CLK:mosi=MOSI:miso=MISO:cs=CS --output-format ascii`. During boot, the capture reveals SPI command sequences such as `0x03` (Read Data) followed by a 24-bit address and subsequent data bytes streaming from the flash chip. Cross-reference captured addresses with the U-Boot `printenv` output to identify where kernel, rootfs, and configuration partitions reside in the flash memory map. This information guides targeted flashrom extraction of sensitive partitions without dumping the entire 4 MB flash, reducing analysis time and minimizing device downtime.

Document all captured signals, decoded protocols, and timing measurements in a structured lab notebook, correlating oscilloscope screenshots with corresponding sigrok-cli log files. Create a signal reference table mapping physical pin numbers to logical functions, noting voltage levels, baud rates, and clock frequencies. This baseline characterization serves as the ground truth for subsequent exercises involving memory extraction and fault injection, where deviations from expected timing indicate successful exploitation or unintended hardware malfunction.

## Exercise 2: Bus Sniffing, Register Inspection & Memory Dumping

The second operational verification exercise transitions from passive signal observation to active memory extraction, leveraging JTAG/SWD debug interfaces and SPI flash programming to obtain complete firmware images for offline analysis. Modern application processors and microcontrollers implement hardware debug ports standardized by ARM's CoreSight architecture or MIPS EJTAG specification, exposing CPU registers, memory-mapped peripherals, and on-chip flash contents to external debuggers. Production devices often disable these interfaces through eFuse programming or debug authentication protocols, but development boards, pre-production hardware, and cost-reduced consumer electronics frequently ship with full debug access enabled, creating an expansive attack surface for firmware reverse engineering and vulnerability discovery.

Begin with SWD (Serial Wire Debug) access on an ARM Cortex-M target such as the STM32F103 "Blue Pill" board. SWD reduces the traditional 4-wire JTAG interface (TCK, TMS, TDI, TDO) to a 2-wire protocol (SWDIO, SWCLK) plus ground and optional RESET, conserving PCB routing resources while maintaining full debug functionality. Locate the SWD header on the target board, typically a 4-pin or 10-pin connector with pinout documented in the schematic or silkscreen. Connect an ST-Link V2 debug probe: ST-Link GND to target GND, ST-Link SWDIO to target SWDIO, ST-Link SWCLK to target SWCLK, and optionally ST-Link RESET to target NRST for hardware reset control. Power the target from USB or an external 3.3V supply, not from the ST-Link's VCC pin, which sources only 100 mA and may brownout under flash programming current spikes.

Launch OpenOCD to establish a debug session: `openocd -f interface/stlink.cfg -f target/stm32f1x.cfg`. OpenOCD initializes the ST-Link adapter, scans the SWD bus for connected devices, identifies the STM32F103C8T6 by its 32-bit IDCODE (0x1BA01477 for Cortex-M3 core), and halts CPU execution at the current program counter. The OpenOCD telnet interface on port 4444 provides interactive debug commands. In a separate terminal, connect via `telnet localhost 4444` and issue `reset halt` to stop execution at the reset vector, typically address 0x08000000 where the ARM Cortex-M vector table resides. Execute `mdw 0x08000000 16` to dump the first 16 words (64 bytes) of flash, revealing the initial stack pointer value at offset 0x00 and the reset handler address at offset 0x04. These values must point to valid SRAM (0x20000000-0x20005000 range) and flash (0x08000000-0x08010000 range) respectively, or the bootloader has been corrupted or debug access is reading uninitialized flash.

Extract the complete flash contents using OpenOCD's `dump_image` command: `dump_image firmware.bin 0x08000000 0x10000`. This reads 64 KB (0x10000 bytes) starting from flash base address 0x08000000 and writes the raw binary to `firmware.bin` on the host filesystem. Verify the dump integrity by calculating its SHA256 hash and comparing against a known-good firmware image, if available: `sha256sum firmware.bin`. Transfer the firmware image to the analysis workstation and invoke binwalk to identify embedded artifacts: `binwalk -e firmware.bin`. Binwalk's entropy analysis detects compressed sections (high entropy) versus plaintext strings (low entropy), automatically extracting LZMA-compressed kernel images, SquashFS root filesystems, and ARM Thumb-2 executable code segments. The extracted filesystem reveals configuration files, shell scripts, password hashes, TLS certificates, and hardcoded API keys that constitute the application security threat model.

For targets with external SPI NOR flash, such as routers and IoT devices storing their root filesystem off-chip, flashrom provides direct chip access without CPU involvement, bypassing software-enforced read protection. Identify the flash chip part number by visual inspection or probing the SPI bus during boot with a logic analyzer, noting the JEDEC manufacturer ID and device ID bytes transmitted during the `0x9F` (Read JEDEC ID) command. Common flash chips include Winbond W25Q32 (4 MB), Macronix MX25L64 (8 MB), and GigaDevice GD25Q127 (16 MB), all supporting standard SPI commands at 3.3V logic levels. Connect the FT232H USB-to-SPI adapter: FT232H D0 (TCK/SCK) to flash CLK, D1 (TDI/MOSI) to flash DI/MOSI, D2 (TDO/MISO) to flash DO/MISO, D3 (TMS/CS) to flash CS, and FT232H GND to flash GND. Decouple the target CPU from the SPI bus by either desoldering the flash chip and socketing it on a breakout board, or forcing the CPU into reset/low-power mode where its SPI controller tristates, releasing bus control.

Execute flashrom with FT232H programmer: `flashrom -p ft2232_spi:type=232H --read flash_dump.bin`. Flashrom auto-detects the flash chip, queries its status register for write protection flags, and performs a full read at maximum supported SPI clock frequency (typically 12-30 MHz). The operation completes in 10-60 seconds depending on flash size and USB bandwidth. Verify the dump integrity by reading twice and comparing hashes: `flashrom -p ft2232_spi:type=232H --read flash_dump2.bin && sha256sum flash_dump.bin flash_dump2.bin`. Mismatches indicate flaky electrical connections (poor probe contact, insufficient ground), SPI bus contention (CPU not fully isolated), or flash chip hardware failure (worn sectors, radiation upset). Repair connections and retry until consecutive reads produce identical hashes.

Analyze the flash dump with binwalk: `binwalk -e flash_dump.bin`. The output identifies bootloader boundaries (U-Boot at offset 0x00000, typically 128-256 KB), kernel image locations (Linux zImage or uImage at offset 0x20000-0x40000), root filesystem formats (SquashFS, JFFS2, YAFFS2), and configuration partitions storing Wi-Fi credentials, SSH keys, and firmware update URLs. Extract the root filesystem: `cd _flash_dump.bin.extracted/ && unsquashfs *.squashfs`. Navigate the extracted filesystem and grep for hardcoded secrets: `grep -r "password\|secret\|api_key\|token" etc/ usr/bin/ www/`. Common findings include default administrator passwords in `/etc/passwd` or `/etc/shadow`, cloud API tokens in `/etc/config/cloud.conf`, WPA2-PSK passphrases in `/etc/config/wireless`, and TLS private keys in `/etc/ssl/private/` lacking proper filesystem encryption.

Register inspection via JTAG exposes peripheral configuration and cryptographic accelerator state during runtime. Connect to the target via OpenOCD and halt execution mid-operation: `reset halt`. Read the SPI controller's configuration registers to determine clock divider, mode (CPOL/CPHA), and chip select behavior: `mdw 0x40013000 16` for STM32F1's SPI1 peripheral base address. Cryptographic accelerators, when present, store AES round keys and HMAC intermediate states in memory-mapped registers accessible via debug interfaces. On STM32L4 devices with AES hardware, read the key registers: `mdw 0x50060010 8` exposes the 256-bit AES key loaded for encryption operations. This demonstrates that JTAG-enabled devices leak cryptographic material regardless of software-level key zeroization routines, as hardware debug bypasses CPU execution and directly samples register flip-flops.

For devices implementing debug authentication (ARM TrustZone, Secure Boot with debug locks), attempt known bypass techniques before resorting to invasive silicon attacks. Check if the debug lock is a software flag in flash rather than a hardware eFuse: dump the flash image and search for debug control structures, often stored in the first or last sector with specific magic bytes (`0xDEADBEEF`, `0x5EC00000`). Modify the debug enable bit, rewrite the flash, and retry OpenOCD connection. If eFuse-locked, consider fault injection (covered in Exercise 3) or purchasing factory-fresh chips from distributors, which universally ship with debug enabled until the OEM firmware runs its provisioning sequence.

Document the memory map, register values, and extracted firmware in a structured analysis report. Create a memory layout diagram showing bootloader, kernel, filesystem, and free space boundaries, annotating each region with access permissions (read, write, execute) and encryption status (plaintext, AES-encrypted). Calculate the firmware attack surface: count the number of network-exposed services, SUID binaries, and world-writable files, providing quantitative metrics for vulnerability prioritization. This report feeds into the final exercise, where identified weaknesses are validated through fault injection and exploitation.

## Exercise 3: Fault Simulation & Exploit Verification

The third operational verification exercise validates application security vulnerabilities through controlled fault injection and exploit chaining, bridging the gap between theoretical attack vectors identified during static analysis and confirmed exploitability against live hardware. Fault injection encompasses voltage glitching (momentary VCC/GND droops), clock glitching (transient frequency injection), electromagnetic pulse injection (localized EM field disruption), and laser fault injection (photoelectric current injection via focused laser). These techniques induce CPU instruction skip, memory read corruption, conditional branch inversion, and cryptographic computation errors, enabling security bypass even when software mitigations are correctly implemented. Hardware fault injection represents the ultimate physical attack surface, as it operates below the software abstraction layer where traditional security controls reside.

Voltage glitching exploits the relationship between supply voltage, transistor switching speed, and CPU timing margins. Modern CMOS logic requires minimum voltage thresholds to reliably propagate signals through combinational paths within a clock cycle. By momentarily dropping VCC below this threshold during a critical instruction (secure boot signature verification, password comparison, privilege check), the CPU may skip the instruction entirely, invert a conditional branch, or corrupt a register value, creating an exploitable inconsistency between architectural intent and silicon behavior. The Chipwhisperer platform provides a programmable glitch generator synchronized to cryptographic operations via power analysis triggers or external GPIO timing signals.

Establish a voltage glitching setup on an STM32F103 target executing a secure boot routine that verifies firmware signatures before jumping to the application. Connect the Chipwhisperer-Lite glitch output to the target's VCC rail via a 10 Ω current-limiting resistor, with the Chipwhisperer ground referenced to target ground. The resistor prevents excessive current draw from damaging the glitch MOSFET while allowing sufficient voltage droop to induce faults. Install the target firmware, a minimal bootloader that reads a signature from flash offset 0x0800F000, computes an HMAC-SHA256 over the application region (0x08000000-0x0800EFFF), and compares the result with the stored signature, halting execution on mismatch. Instrument the bootloader to toggle a GPIO pin high during the signature comparison, providing an external trigger for glitch synchronization.

Configure the Chipwhisperer glitch parameters: glitch width (duration in nanoseconds), glitch offset (delay from trigger in clock cycles), and repeat count (number of consecutive glitches). Begin with a coarse parameter sweep: width from 5% to 50% of the CPU clock period (at 72 MHz, one cycle is 13.9 ns, so 5% is approximately 1 ns), offset from -10 to +10 cycles relative to the GPIO trigger edge, and repeat count from 1 to 5 glitches. The Python script controlling the Chipwhisperer iterates through this parameter space, triggering a target reset, waiting for the GPIO edge, injecting the glitch, and observing whether the bootloader halts (verification succeeded) or continues execution into the unsigned application region (verification bypassed). Use OpenOCD to monitor the program counter: if PC advances beyond the expected halt address (e.g., 0x08000100), the glitch succeeded.

A successful glitch campaign reveals parameter combinations that bypass signature verification with reproducibility above 10%, sufficient for practical exploitation. Typical successful parameters on ARM Cortex-M3 at 72 MHz and 3.3V supply: glitch width 20-30 ns, offset +2 to +5 cycles from trigger, repeat count 2-3 glitches. These parameters induce instruction skip on the conditional branch following the HMAC comparison (`BNE halt_label`), causing the CPU to execute the fall-through path as if the signature matched. Log successful glitch parameters and corresponding power traces, analyzing the correlation between glitch timing and CPU pipeline state using Chipwhisperer's built-in waveform viewer.

Clock glitching injects transient high-frequency pulses into the CPU clock input, violating setup and hold time constraints at sequential logic elements (flip-flops, latches). When a flip-flop samples its input while the clock signal is metastable or during a glitch-induced extra clock edge, the stored value may differ from the intended data, corrupting register contents or instruction opcodes mid-execution. Clock glitching targets bootloaders, cryptographic operations, and privilege checks, particularly on older devices lacking clock integrity monitors or glitch detection circuits.

Construct a clock glitching setup using a Chipwhisperer or custom FPGA-based glitch generator. Identify the target's crystal oscillator or external clock input pin, typically a 8-40 MHz signal feeding the CPU's PLL (Phase-Locked Loop). Desolder the crystal or cut the clock trace, inserting a glitch injection point where the Chipwhisperer's clock output replaces the original clock source. Configure the target CPU to run from the external clock without engaging the PLL multiplier, simplifying glitch synchronization. Load a test firmware that increments a counter in a tight loop, writing the counter value to a GPIO-driven LED or UART output each iteration, providing visual feedback of glitch success (unexpected counter jumps).

Sweep clock glitch parameters: base frequency (matching the original crystal), glitch frequency (2x to 10x the base), glitch duration (1-10 base clock cycles), and glitch offset (position within the target's execution loop). Monitor the counter output for anomalies: if the counter skips values or resets unexpectedly, a glitch corrupted the increment instruction or loop condition. Narrow the parameter range around successful glitches, increasing repeat count to achieve >50% success rate. Apply clock glitching to the secure boot firmware from the voltage glitching exercise, comparing success rates and parameter sensitivities between the two fault injection modalities. Clock glitching often achieves finer temporal resolution than voltage glitching, as clock edges are nanosecond-precise, whereas voltage droops propagate through PCB capacitance with microsecond time constants.

Electromagnetic fault injection (EMFI) uses localized magnetic fields to induce currents in silicon interconnects, flipping bits in SRAM, CPU registers, or peripheral data buses without physical contact with the chip. EMFI requires a high-voltage pulse generator driving a small electromagnetic coil (2-5 mm diameter) positioned micrometers above the target die, accessible only after removing plastic IC packaging or using X-ray imaging to locate sensitive structures beneath the package. Consumer-grade EMFI setups such as the ChipShouter inject kilovolt pulses into handwound coils, generating localized field strengths sufficient to corrupt memory in ARM Cortex-M and Cortex-A devices.

Construct an EMFI probe from 30 AWG magnet wire wrapped 10-20 turns around a ferrite core or 3D-printed coil former, soldered to a BNC connector. Connect the coil to a ChipShouter or laboratory pulse generator capable of delivering 5 kV, 10 ns pulses at 10-100 Hz repetition rate. Position the coil above the target IC using a micromanipulator or 3D-printed jig, maintaining coil-to-die spacing below 5 mm for effective field coupling. Trigger the pulse generator synchronously with the target's cryptographic operation or security check, sweeping the coil position in a 2D grid over the chip surface. Monitor the target's UART output or GPIO flags for fault indicators: corrupted AES ciphertext, skipped signature verification, or unauthorized privilege escalation.

EMFI parameter optimization requires iterative refinement: adjust pulse voltage (2-10 kV), pulse width (5-50 ns), coil position (XY grid scan in 0.5 mm steps), and coil angle (normal incidence versus 30° tilt to penetrate package underfill). Successful EMFI on cryptographic accelerators produces bit-flips in AES round keys or intermediate cipher states, detectable through differential fault analysis (DFA). Collect faulted ciphertext outputs, comparing them with fault-free reference encryptions to identify the round and byte position of the injected fault, extracting the AES key through algebraic analysis (DFA on AES-128 typically requires 2-10 faulted ciphertexts to recover the full 128-bit key).

Exploit verification chains hardware fault injection with software vulnerability exploitation to demonstrate end-to-end attack feasibility. Consider a scenario where voltage glitching bypasses secure boot, loading an unsigned firmware image that contains a stack buffer overflow in the network configuration parser. The exploit chain proceeds as follows: power-cycle the device while injecting the optimized glitch parameters from the voltage glitching exercise, causing the bootloader to skip signature verification and execute the attacker-supplied firmware. The malicious firmware image includes a patched network daemon with a deliberate buffer overflow in the SSID parsing function, accessible via a crafted Wi-Fi beacon frame. Transmit the beacon using a software-defined radio (HackRF, LimeSDR) or modified Wi-Fi adapter (ath9k-based card with patched driver), triggering the overflow and executing a reverse shell payload that connects back to the attacker's C2 server. Validate the exploit by observing the reverse shell connection and issuing commands to read `/etc/shadow`, extract TLS private keys, or pivot to adjacent network devices.

Document the complete exploit chain in a structured penetration test report, including fault injection parameters, firmware modifications, network packet captures, and post-exploitation artifacts. Quantify the attack cost: hardware budget (Chipwhisperer $300, logic analyzer $50, USB-UART $10), time investment (glitch parameter tuning 4-8 hours, firmware analysis 2-4 hours, exploit development 1-2 hours), and required expertise (hardware hacking proficiency, ARM assembly familiarity, network protocol knowledge). Compare this cost against the deployed asset value and threat model, providing risk-prioritized recommendations for hardware security mitigations: enable debug authentication, implement glitch detection circuits, use secure enclaves (TrustZone, SGX), and deploy cryptographic attestation for firmware integrity.

## Hardware Security Checklist & Diagnostic Cheat Sheet

This checklist consolidates operational verification procedures into a rapid-assessment framework for evaluating hardware application security posture during penetration tests, product security reviews, or supply chain audits. Each category maps to observable hardware characteristics, diagnostic commands, and risk severity thresholds, enabling consistent scoring across diverse device types and threat models.

**Debug Interface Exposure Assessment** begins with visual PCB inspection under magnification. Populated JTAG, SWD, or UART headers indicate debug access was intentionally preserved for development or field service, suggesting relaxed security policy. Unpopulated headers with visible solder pads or vias warrant continuity testing with a multimeter to confirm pin functionality. Probe suspected UART pins during boot, capturing serial output with `sigrok-cli --driver fx2lafw --config samplerate=24M --channels D0=TX --protocol-decoders uart:baudrate=115200 --output-format ascii --continuous`. Bootloader messages containing memory maps, build timestamps, or command prompts constitute high-severity findings, as they enable reconnaissance and interaction without authentication. Test JTAG/SWD access via OpenOCD: `openocd -f interface/stlink.cfg -f target/stm32f1x.cfg`, noting whether the debug port responds with IDCODE or halts execution. Successful connection without password prompts indicates critical debug interface vulnerability.

**Flash Memory Protection Verification** extracts firmware via hardware interfaces, comparing the obtained image against manufacturer-published hashes or signed update packages to detect unauthorized modifications. Execute `flashrom -p ft2232_spi:type=232H --read firmware.bin`, measuring extraction time and success rate across multiple attempts. Flash chips lacking status register protection (WP# pin floating, status register bits unset) permit arbitrary firmware rewriting, enabling persistent implant installation. Verify protection status: `flashrom -p ft2232_spi:type=232H --wp-status`, expecting block protection bits (BP0, BP1, BP2) set to protect bootloader regions. Use binwalk to analyze firmware structure: `binwalk -e firmware.bin`, confirming bootloader and kernel signatures, filesystem encryption, and absence of plaintext credentials. Critical finding: unencrypted root filesystem containing `/etc/shadow` with weak password hashes (MD5, single-round SHA-256) or hardcoded SSH private keys in `/etc/dropbear/`.

**Cryptographic Key Storage Audit** requires memory dumping during runtime to capture transient key material loaded from flash or provisioned via external secure elements. Halt the target mid-execution via JTAG: `reset halt`, then dump SRAM: `dump_image sram.bin 0x20000000 0x5000`. Search the SRAM dump for AES key schedules (44 consecutive 32-bit words with high entropy) or RSA private keys (ASN.1 DER-encoded structures starting with `0x30 0x82`). Extract entropy statistics: `ent sram.bin`, confirming entropy above 7.9 bits/byte in key regions. Cross-reference with firmware strings: `strings firmware.bin | grep -i "key\|token\|secret"`, identifying hardcoded API tokens or TLS private keys. High-severity finding: cryptographic keys stored in plaintext flash or RAM without hardware-backed secure storage (TrustZone secure world, HSM, TPM).

**Secure Boot Integrity Validation** tests cryptographic verification routines through glitch-based bypass attempts. Configure voltage glitching parameters from Exercise 3, targeting the signature comparison instruction during boot. Success rate above 1% indicates exploitable secure boot weakness, as nation-state adversaries or well-funded criminal groups can iterate attacks until bypass succeeds. Verify the presence of rollback protection: extract firmware version numbers from multiple samples (factory-fresh, field-updated), confirming that older firmware cannot be flashed onto updated devices. Check for debug backdoors: decompile the bootloader using Ghidra or radare2, searching for conditional branches that skip verification based on GPIO pin states, magic flash values, or timing-based conditions. Critical finding: secure boot disabled entirely, verification routine stubbed out, or bypassable via hardware fault injection with >10% success rate.

**Power Analysis Susceptibility** captures side-channel leakage during cryptographic operations, assessing differential power analysis (DPA) resistance. Connect a Chipwhisperer to the target's VCC rail via a 1 Ω shunt resistor, sampling power consumption at 500 MS/s during AES encryption. Trigger captures synchronously with plaintext input transmission via UART or SPI, collecting 1000-10000 traces with fixed key and varying plaintexts. Import traces into Chipwhisperer Analyzer, computing correlation traces for each AES key byte hypothesis using Hamming weight model. Correlation peaks above 0.3 indicate exploitable leakage, enabling key recovery from 200-2000 traces depending on noise floor. Modern microcontrollers implementing AES-NI hardware acceleration or masking countermeasures should resist DPA with >50,000 traces required for key recovery, indicating robust side-channel protection.

**Diagnostic Command Reference** provides ready-to-execute shell commands for rapid triage during time-constrained engagements. Scan for USB-connected logic analyzers and debug probes: `sigrok-cli --scan && lsusb | grep -i "ftdi\|stlink\|cmsis"`, confirming hardware detection and driver binding. Identify UART baud rates when documentation is unavailable: `minicom -D /dev/ttyUSB0 -b 115200 && minicom -D /dev/ttyUSB0 -b 57600 && minicom -D /dev/ttyUSB0 -b 38400`, cycling through common rates until recognizable ASCII text appears. Dump OpenOCD-accessible memory regions: `echo "dump_image sram.bin 0x20000000 0x5000; exit" | nc localhost 4444`, automating extraction during scripted vulnerability scans. Extract firmware from USB DFU (Device Firmware Update) mode: `dfu-util -l && dfu-util -a 0 -s 0x08000000 -U firmware.bin`, bypassing SPI flash desoldering when DFU is enabled. Compute firmware entropy: `binwalk -E firmware.bin`, plotting entropy curve to identify compressed/encrypted regions versus plaintext configuration blocks.

**Risk Scoring Framework** quantifies hardware security posture through weighted metrics. Assign point values: exposed debug interface without authentication (10 points), unprotected SPI flash (8 points), plaintext cryptographic keys (10 points), bypassable secure boot (9 points), high DPA correlation (7 points), default credentials in firmware (6 points). Sum scores across categories: 0-10 points (low risk, defense-in-depth deployed), 11-25 points (medium risk, single-layer security), 26+ points (high risk, multiple critical vulnerabilities). Map scores to remediation priorities: high-risk findings require immediate patching (eFuse debug locks, flash protection, key migration to secure storage), medium-risk findings addressed in next firmware release (credential randomization, secure boot hardening), low-risk findings tracked for future architecture reviews (side-channel countermeasures, supply chain validation).

This operational verification framework equips penetration testers and hardware security engineers with systematic procedures for assessing application security at the silicon and PCB level, uncovering vulnerabilities invisible to software-only testing methodologies. By integrating signal capture, memory extraction, fault injection, and exploit validation into a cohesive laboratory workflow, practitioners gain empirical confirmation of security design effectiveness, informing evidence-based risk mitigation strategies and secure development lifecycle improvements.
