# Lesson 4: Operational Model, Policy Management

## 1. First-Principles Intuition & Invariants

Security-Enhanced Linux operates as a stateful labeling machine that enforces mandatory access control through a policy decision point embedded within the kernel's Linux Security Module framework. Unlike discretionary access control systems where resource owners dictate permissions, SELinux implements a reference monitor that intercepts every security-sensitive operation—file access, process creation, network binding, IPC communication—and evaluates each request against a precompiled policy database loaded into kernel memory. This architectural separation between policy definition and policy enforcement creates a fundamental invariant: no userspace process, not even root, can modify access decisions without first altering the policy source, recompiling it through the policy toolchain, and loading the resulting binary module into the kernel's policy store.

The operational model centers on three distinct phases that form the policy lifecycle. First, human-readable policy source files written in a domain-specific language define the relationships between security contexts, the permissions granted to specific domain types, and the boolean switches that enable runtime policy adjustments without recompilation. Second, the compilation phase transforms these source declarations into a binary policy database through a multi-stage toolchain involving `checkmodule` for syntax validation and module compilation, followed by `semodule_package` for module packaging, and finally `semodule` for integration into the active policy store with dependency resolution and priority handling. Third, the enforcement phase occurs entirely within kernel space where the security server evaluates access vector cache lookups, computes policy decisions through type enforcement rules, and generates audit events for both allowed and denied operations based on configured audit rules.

The transition from policy source to enforced behavior introduces several critical invariants that govern system state consistency. When the kernel loads a policy module, it constructs an in-memory access vector cache that serves as a deterministic finite automaton for rapid permission decisions—each cache entry maps a source context, target context, and object class tuple to a permission bitmap computed from the complete policy ruleset. This cache operates as a write-through store where modifications to the policy database immediately invalidate affected entries, forcing recomputation on subsequent access attempts. The security server maintains strict monotonicity guarantees: once a policy decision denies access, no amount of cache manipulation or timing variation can bypass that denial without an explicit policy change, and every access decision produces an auditable trail that records the precise security contexts involved, the requested permissions, and the policy rule that triggered the decision.

Boolean toggles represent a carefully designed escape hatch that permits limited runtime policy flexibility without sacrificing the integrity of the compiled policy database. Each boolean declaration in the policy source defines a named switch that conditionally enables or disables entire blocks of policy rules through preprocessor-style conditional compilation. When administrators toggle a boolean at runtime using `setsebool`, the security server does not recompile policy source—instead, it re-evaluates the conditional branches within the already-loaded binary policy, recomputes affected access vector cache entries, and atomically updates the policy decision tables. This mechanism preserves the fundamental invariant that all policy logic remains statically defined at compile time while permitting operational teams to adjust enforcement boundaries for specific service profiles, network configurations, or administrative workflows without triggering a full policy rebuild and system-wide policy reload.

The relationship between confined domains and unconfined operations forms another essential invariant in the operational model. A confined domain represents a process security context subject to comprehensive type enforcement rules that explicitly enumerate every permitted interaction with system resources—file types, network ports, IPC mechanisms, capability sets, and inter-process transitions. The policy defines these domains through `type` declarations paired with extensive `allow` rules that whitelist specific access vectors, creating a default-deny security posture where any operation not explicitly permitted triggers an access denial. In contrast, unconfined domains receive broad permission grants through policy macros like `unconfined_domain` that effectively bypass type enforcement for administrative contexts, permitting root processes to operate with near-traditional discretionary access control behavior while still maintaining context labels for audit purposes and potential future confinement.

## 2. Core Architecture & Mechanics

The policy compilation pipeline transforms human-readable policy source into kernel-loadable binary modules through a three-stage transformation process that validates syntax, resolves dependencies, and generates optimized access decision structures. Policy source files typically live in modular form under `/etc/selinux/targeted/policy/` or within package-specific directories like `/usr/share/selinux/packages/`, where each module declares its type definitions, access rules, role associations, and boolean switches in files with `.te` (type enforcement), `.if` (interface definitions), and `.fc` (file context) extensions. The type enforcement file contains the core access control logic, declaring security types through `type` statements, defining domain transitions via `domain_auto_trans` or explicit `type_transition` rules, and granting permissions through `allow` statements that specify source type, target type, object class, and permission set.

When an administrator invokes `checkmodule -M -m -o custom.mod custom.te`, the compiler performs lexical analysis and syntax validation against the policy language grammar, then generates an intermediate binary representation that encodes type definitions, access vectors, conditional expressions, and constraint rules into a platform-independent module format. This intermediate representation preserves the logical structure of policy rules while normalizing identifiers into numeric indices that reference the global policy symbol table. The `-M` flag instructs the compiler to produce a policy module rather than a monolithic base policy, while `-m` enables MLS (Multi-Level Security) extensions even if the module does not explicitly use sensitivity labels. The resulting `.mod` file contains a serialized abstract syntax tree annotated with version metadata, dependency declarations, and optional sections for role definitions and user mappings.

The second transformation stage involves `semodule_package` which wraps the compiled module with file context specifications and optional installation scripts into a bundled policy package with the `.pp` extension. This packaging step merges the binary module from `checkmodule` with file context rules from the corresponding `.fc` file, generating a self-contained artifact that declares both the runtime access control rules and the filesystem labeling directives required to establish correct security contexts for files created or managed by the confined service. The file context specifications use extended regular expressions to match filesystem paths, associating each pattern with a security context template that defines the user, role, type, and sensitivity labels that should apply to matching files during initial labeling or relabeling operations performed by `restorecon` or `setfiles`.

Integration into the active policy occurs through `semodule`, the policy module manager that maintains a versioned policy store under `/etc/selinux/targeted/modules/` with transactional semantics for module installation, upgrade, and removal operations. When executing `semodule -i custom.pp`, the tool performs dependency analysis to verify that all required types, attributes, and interfaces referenced by the new module exist either in the base policy or in previously installed modules. The dependency resolver constructs a directed acyclic graph of module relationships where edges represent symbol dependencies, then performs a topological sort to determine the correct load order. If dependency resolution succeeds, `semodule` merges the new module into the policy store, increments the policy version counter, and triggers a policy rebuild that concatenates all active modules into a unified binary policy database optimized for kernel consumption.

The policy rebuild process invoked by `semodule` generates a monolithic binary policy file at `/etc/selinux/targeted/policy/policy.XX` where `XX` represents the policy version number, typically 31 or 33 corresponding to the maximum policy format version supported by the running kernel. This binary database contains several critical data structures that enable efficient runtime enforcement. The type enforcement table encodes all `allow` rules as a sparse matrix mapping (source_type, target_type, class) tuples to permission bitmasks, using hash tables or compressed bitmap representations to minimize memory footprint while preserving constant-time lookup characteristics. The role-based access control table defines which roles can assume which types, enforcing the intermediate layer between user identities and process domains. The conditional policy table stores boolean switch states alongside the rule sets they conditionally enable, permitting runtime toggling without policy recompilation.

Boolean toggle management operates through a distinct code path that modifies policy state without triggering full recompilation. When an administrator executes `setsebool httpd_can_network_connect on`, the command communicates with the policy management daemon or directly updates the boolean state file under `/sys/fs/selinux/booleans/httpd_can_network_connect`, writing the new value into the kernel's policy state table. The security server responds by invalidating all access vector cache entries that depend on conditional rules guarded by that boolean, forcing the next access check to re-evaluate the conditional expression with the updated boolean value. The policy database stores conditional rules in a branching structure where each boolean switch acts as a predicate controlling whether a subtree of `allow` rules contributes to the final permission decision, implemented through lazy evaluation that skips disabled branches during access vector computation.

To make boolean changes persistent across reboots, administrators must either use `setsebool -P` which writes the boolean state to disk at `/etc/selinux/targeted/modules/active/booleans.local`, or manually edit that file and reload the policy with `semodule -B` to rebuild the policy database with the updated boolean defaults. The persistent storage mechanism maintains a simple key-value mapping of boolean identifiers to their enabled/disabled state, which the policy loader reads during system initialization to establish initial boolean values before the security server begins processing access requests. This separation between runtime boolean state and the compiled policy binary ensures that boolean toggles remain fast and atomic while preserving the ability to reset to known-good configurations by removing local boolean overrides and reloading the distribution-provided policy defaults.

Audit log interpretation requires understanding the structured format of AVC (Access Vector Cache) denial messages that the kernel emits through the audit subsystem whenever SELinux blocks an operation. Each denial event records a comprehensive trace of the security decision including the process security context that attempted the operation, the target object's security context, the object class (file, socket, process, etc.), the specific permissions that were denied, and additional metadata like process ID, executable path, and capability flags. A typical AVC denial appears in `/var/log/audit/audit.log` as a single-line record with key-value pairs: `type=AVC msg=audit(1234567890.123:456): avc: denied { read write } for pid=1234 comm="httpd" name="data.db" dev="sda1" ino=789012 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:user_home_t:s0 tclass=file permissive=0`.

The audit record structure encodes several layers of information essential for policy debugging. The `scontext` field identifies the source domain—the security context of the process that attempted the access—revealing the type enforcement domain (`httpd_t`), the role (`system_r`), and the user identity (`system_u`) of the acting process. The `tcontext` field specifies the target object's security context, showing which type label (`user_home_t`) applies to the resource being accessed and therefore which type enforcement rules govern that access. The `tclass` field names the object class (`file`, `tcp_socket`, `process`, `capability`, etc.) which determines the permission vocabulary available for that class—file objects support permissions like `read`, `write`, `execute`, while socket objects define `bind`, `connect`, `listen`, and other network-specific operations. The denied permission set, shown in curly braces, lists the specific access rights that the policy did not grant, enabling precise identification of which `allow` rule must be added to permit the operation.

Confined domains represent the operational manifestation of least-privilege enforcement where SELinux restricts a process to only those operations explicitly required for its legitimate function. When a service like Apache HTTPd launches under the `httpd_t` domain, the kernel enforces type enforcement rules that permit the process to bind TCP sockets on ports 80 and 443, read files labeled `httpd_sys_content_t`, write to log files labeled `httpd_log_t`, and execute scripts labeled `httpd_sys_script_exec_t`, while denying access to user home directories, system configuration files outside the httpd namespace, and privileged operations like loading kernel modules or modifying system time. This confinement occurs through a whitelist model where the policy explicitly enumerates allowed interactions—any operation not granted by an `allow` rule results in denial, even if traditional Unix permissions would permit the access.

Domain transitions form the mechanism by which confined processes spawn child processes in different security contexts, enabling a parent process to delegate specific tasks to more tightly confined or differently privileged security domains. When an `httpd_t` process executes a CGI script, the policy can specify an automatic domain transition that relabels the child process to `httpd_sys_script_t`, a domain with restricted file access and limited network permissions appropriate for executing untrusted web application code. The transition occurs through a combination of `type_transition` rules that declare default domains for specific execution scenarios and `allow` rules that explicitly permit the transition, creating a transactional sequence where the kernel verifies that the source domain has `transition` permission for the target domain, the target domain has `entrypoint` permission for the executable file's type, and the executable type has `execute` permission granted to the source domain.

Unconfined operations represent a pragmatic compromise where administrative contexts receive broad policy grants that approximate traditional root privileges while maintaining context labels for audit trails and future confinement possibilities. When a user logs in through an unconfined user mapping, their shell spawns in an unconfined domain like `unconfined_t` which benefits from policy macros that grant sweeping permissions across most object classes and types. These domains can transition into confined domains when launching system services but can also bypass type enforcement for administrative tasks like direct filesystem manipulation, arbitrary network operations, and capability exercises. The policy achieves this through `unconfined_domain` interface calls that generate hundreds of `allow` rules covering common administrative operations, combined with domain transition rules that permit unconfined domains to enter any confined domain through appropriate executable entrypoints.

## 3. High-Performance Optimization & Failure Modes

Policy debugging methodology centers on transforming audit denial logs into actionable policy modifications through a systematic analysis workflow that identifies the security contexts involved, determines whether the denied operation represents legitimate behavior or a genuine security violation, and generates appropriate policy rules or file context adjustments to resolve the issue. The `audit2why` tool provides immediate diagnostic analysis by reading AVC denials from the audit log and correlating them against the active policy database to explain why each denial occurred—whether a missing `allow` rule, a boolean that needs toggling, a file context mismatch, or a constraint violation. Running `audit2why -a` processes all denials in the audit log and produces human-readable explanations that identify the specific policy gap causing each denial, often suggesting the exact `setsebool` command or policy module that would resolve the issue.

When audit2why identifies missing `allow` rules rather than simple boolean misconfigurations, `audit2allow` generates policy source code that would permit the denied operations. Executing `audit2allow -a` analyzes all denials in the audit log and outputs type enforcement source code containing `allow` rules for each distinct denial pattern, aggregating multiple denials of the same source-target-class tuple into single rules with combined permission sets. This tool serves as a rapid policy prototyping mechanism during application integration where administrators observe actual application behavior under SELinux, collect denial logs during functional testing, and automatically generate a draft policy module that whitelists the observed access patterns. The workflow typically involves `audit2allow -a -M myapp` which not only generates the type enforcement source but also compiles it into a policy module and produces installation instructions, creating an end-to-end automation path from denial observation to policy remediation.

Critical evaluation of audit2allow output prevents the creation of overly permissive policies that undermine confinement. Automatically generated rules require manual review to verify that each granted permission represents legitimate application behavior rather than attack artifacts, misconfigurations, or unnecessary privileged operations. A denial indicating that a web server process attempted to write to `/etc/shadow` should not automatically translate into a policy rule permitting that access—instead, it signals a security incident or misconfiguration requiring investigation and remediation rather than policy relaxation. Best practice involves running applications in permissive mode during initial integration to observe all denied operations without blocking functionality, analyzing the complete denial set to understand the application's actual security requirements, manually crafting a minimal policy that grants only essential permissions, and then switching to enforcing mode to validate that the tailored policy provides sufficient access without over-permitting.

File context restoration guarantees system-wide security label consistency after file creation, package installation, or filesystem relabeling operations through two complementary mechanisms: policy-defined default contexts that automatically label newly created files, and explicit relabeling tools that reset contexts to policy specifications. When a confined process creates a file, the kernel applies type transition rules from the policy database that specify the default security context for files created by that domain in that directory, typically inheriting the parent directory's type or transitioning to a domain-specific content type. For example, when `httpd_t` creates a file in a directory labeled `httpd_sys_rw_content_t`, the policy might specify a type transition that labels the new file as `httpd_sys_rw_content_t`, ensuring automatic consistency without manual relabeling.

Explicit relabeling becomes necessary after package installations that deploy files without SELinux awareness, after filesystem corruption that damages extended attributes storing security contexts, or when policy updates change file context specifications for existing paths. The `restorecon` utility reads file context specifications from the compiled policy database and recursively applies correct labels to specified files or directories, using the regular expression patterns from `.fc` policy files to match filesystem paths against their intended contexts. Running `restorecon -Rv /var/www/html` walks the web server document root, compares each file's current security context against the policy specification for its path, and updates any mismatched labels while logging all changes for audit purposes. The `-R` flag enables recursive directory traversal while `-v` produces verbose output showing each relabeling operation, providing visibility into which files required context corrections.

The `setfiles` command provides system-wide relabeling capabilities during recovery scenarios or after major policy updates, reading file context specifications and applying them across entire filesystems. Unlike `restorecon` which assumes generally correct labeling and corrects deviations, `setfiles` performs exhaustive relabeling suitable for disaster recovery or initial system labeling during OS installation. Administrators typically invoke `setfiles -v /etc/selinux/targeted/contexts/files/file_contexts /` to relabel the entire root filesystem according to the active policy's file context database, a operation that touches every file's extended attributes and can require significant time on large filesystems. Best practice restricts `setfiles` usage to offline relabeling scenarios during system recovery or controlled maintenance windows, while `restorecon` handles routine context corrections during normal operations.

Troubleshooting methodology for persistent policy issues follows a structured diagnostic approach that isolates whether denials stem from missing policy rules, incorrect file contexts, boolean configurations, or architectural mismatches between application behavior and policy design. The first diagnostic step involves verifying that all required policy modules are installed and enabled using `semodule -l` to list active modules and `semodule -e modulename` to enable any disabled modules required by the confined application. Module installation failures often trace to missing dependencies that the application's policy module references but that are not available in the policy store, resolved by identifying the missing module through dependency analysis and installing it from distribution repositories or building it from source.

File context mismatches represent a common failure mode where files possess incorrect security labels due to improper initial labeling, filesystem operations that bypass SELinux awareness, or policy updates that changed context specifications without subsequent relabeling. Diagnosing these issues involves `ls -Z` to display current file contexts, `matchpathcon` to show what contexts the policy specifies for given paths, and comparing the two to identify discrepancies. When `matchpathcon /var/www/html/index.html` returns `system_u:object_r:httpd_sys_content_t:s0` but `ls -Z` shows `unconfined_u:object_r:user_home_t:s0`, the mismatch explains why httpd denials occur—the web server's policy grants access to `httpd_sys_content_t` but not `user_home_t`, requiring `restorecon` to fix the label or policy modifications to permit the current context.

Boolean enumeration and verification ensures that runtime policy toggles match operational requirements through `getsebool -a` which lists all policy booleans and their current states, enabling administrators to verify that network-related booleans, database connection permissions, or shared filesystem access switches align with application deployment architecture. Many common denial scenarios resolve through boolean adjustments rather than policy modifications—`httpd_can_network_connect`, `httpd_can_network_connect_db`, `httpd_use_nfs`, `httpd_enable_cgi` each control major capability domains that affect web server confinement. Systematically enabling relevant booleans and retesting often resolves denials faster than writing custom policy modules, with the advantage that boolean toggles represent supported configuration paths maintained by distribution policy maintainers.

Permissive domain testing provides surgical enforcement relaxation for specific domains under development without system-wide permissive mode, enabling administrators to debug policy issues for one service while maintaining enforcement for all other confined domains. The `semanage permissive -a httpd_t` command places the `httpd_t` domain into permissive mode where the kernel logs all denials that would occur under enforcement but allows the operations to proceed, generating comprehensive denial logs that capture the complete set of access patterns required by the application. This approach proves invaluable during initial policy development where exhaustive testing in permissive mode produces a complete picture of application security requirements before committing to enforcing mode. Once all denials are addressed through policy rules or confirmed as non-issues, `semanage permissive -d httpd_t` removes permissive status and enables full enforcement.

Advanced policy debugging leverages `sesearch` to query the compiled policy database for specific rules, types, or transitions, enabling administrators to verify that expected policy rules actually exist in the active policy or to understand complex policy interactions. Querying with `sesearch --allow -s httpd_t -t httpd_sys_content_t -c file -p read` searches for `allow` rules that grant the `httpd_t` domain read permission on files labeled `httpd_sys_content_t`, displaying the exact policy rules that permit or deny specific operations. This capability supports root-cause analysis when audit logs show denials but `audit2why` provides unclear explanations—directly querying the policy database reveals whether the expected rules exist, whether they apply to different but related types, or whether conditional statements guard the rules behind boolean switches.

Performance optimization of policy enforcement focuses on minimizing access vector cache churn and reducing policy database size through efficient type hierarchies and attribute-based rules. Large policies with thousands of individual type declarations and hundreds of thousands of `allow` rules can degrade enforcement performance due to cache pressure and lookup overhead. Policy architects address this through attribute definitions that group related types under common attributes, then write `allow` rules that reference attributes rather than individual types—a single rule `allow domain file_type:file read;` grants read permission to all domains on all file types, replacing potentially thousands of individual type-to-type rules. The policy compiler optimizes attribute-based rules by expanding them into type-specific rules at compile time but stores them efficiently in the binary policy database using compressed representations that reduce memory footprint and cache pollution.

Context validation tools prevent policy deployment errors by verifying that file context specifications, type declarations, and role definitions maintain consistency across the policy database before compilation. The `semanage fcontext -l` command enumerates all file context specifications currently registered in the policy store, enabling administrators to audit which path patterns map to which contexts and identify conflicts where overlapping regular expressions assign different contexts to the same filesystem paths. Similarly, `semanage port -l` displays network port context mappings, verifying that the policy associates specific ports with appropriate socket types that confined domains can bind, critical for network service confinement where port binding denials often trace to missing port context definitions rather than missing `allow` rules.

Disaster recovery procedures for catastrophic policy failures ensure system bootability even when broken policy modules prevent normal operation. The kernel command line parameter `enforcing=0` disables SELinux enforcement at boot time without disabling the entire SELinux subsystem, permitting administrators to access a broken system, analyze audit logs, and repair policy issues while the kernel continues labeling operations and collecting audit data. More severe failures may require `selinux=0` to completely disable the SELinux subsystem during boot, though this prevents all labeling and audit collection, making subsequent policy debugging more difficult. Once booted into a recovery state, administrators can use `semodule -R` to rebuild the policy database from installed modules, `semodule -r modulename` to remove broken modules causing load failures, or manually restore policy backups from `/etc/selinux/targeted/modules/previous/` where the policy store maintains previous configurations for rollback scenarios.
