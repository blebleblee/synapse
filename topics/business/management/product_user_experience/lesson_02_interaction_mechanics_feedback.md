# Lesson 2: Interaction Mechanics, Feedback Loops, Error States

## 1. First-Principles Intuition & Invariants

Every interface is a negotiation between human intent and machine capability. The user arrives with a goal encoded in neural pathways shaped by decades of physical manipulation—reaching for door handles, turning pages, pressing buttons—and the system responds through pixels, haptic pulses, or audio cues that must travel back through sensory channels, be decoded, and trigger the next action. This continuous loop of stimulus, perception, decision, and motor response constitutes the fundamental interaction cycle, and every millisecond of latency, every pixel of visual ambiguity, and every unexpected state transition imposes a cognitive tax that accumulates across thousands of micro-interactions throughout a user session.

The classical models that govern these mechanics emerged not from digital design but from human factors research in aviation, industrial control systems, and military targeting. Fitts's Law, derived from Shannon's information theory and formalized by Paul Fitts in 1954 through experiments with stylus-tapping tasks, describes the time required to move to a target as a logarithmic function of the distance-to-size ratio. The predictive formula $T = a + b \log_2\left(\frac{D}{W} + 1\right)$ encodes a profound invariant: doubling the distance or halving the width does not double the acquisition time but increases it logarithmically. This relationship persists across modalities—mouse cursors, touch targets, eye gaze systems—because it reflects fundamental biomechanical constraints in the human motor system, specifically the speed-accuracy tradeoff governed by ballistic muscle movements and corrective microfixations.

Hick's Law operates at a different layer of the stack, governing not motor execution but decisional overhead. William Edmund Hick and Ray Hyman demonstrated in the 1950s that reaction time grows logarithmically with the number of equally probable choices: $RT = b \log_2(n + 1)$. This is not merely perceptual filtering but cognitive load management. When confronted with ten navigation options of equal salience, the user must serially or hierarchically evaluate each possibility, constructing and rejecting mental models of outcome states until a satisfactory match emerges. The logarithmic relationship again reflects information-theoretic principles—each binary decision halves the solution space—but the constant $b$ varies wildly based on familiarity, visual hierarchy, and semantic chunking. A well-designed navigation taxonomy that groups related functions can collapse perceived option count from ten to three-plus-three-plus-four, dramatically reducing the effective $n$ in Hick's formula.

Interaction cost, a synthesis of these mechanics, quantifies the total effort expenditure for a user to achieve an outcome. Don Norman's gulf of execution describes the gap between user intent and the system's input affordances: the user wants to "archive all emails from this sender," but the interface offers only "select message, click More, choose Filter, configure rule, apply retroactively." Each step imposes a Fitts acquisition cost, a Hick decision cost, a working memory load to maintain state across the sequence, and a visual search cost to locate each successive control. The gulf of evaluation measures the inverse journey: after executing the command, can the user confirm that the system state now matches their intent? If archived messages vanish without trace or confirmation, the user must navigate to the Archive folder, visually scan for the expected messages, and cognitively reconcile the result with their initial goal. Both gulfs widen catastrophically when designers assume expert mental models or omit intermediate feedback.

State transitions form the skeletal structure beneath every interaction. A button exists in discrete states—default, hover, focus, active, disabled, loading—and each transition must be instantaneous, deterministic, and visually unambiguous. When a user clicks "Submit Payment," the system enters a loading state; if this transition is delayed by 200 milliseconds while the JavaScript event handler processes, the user may click again, triggering duplicate submissions. If the loading state displays no progress indicator, the user cannot distinguish between a frozen interface and a long-running transaction. If the terminal success state is a subtle color change rather than a modal confirmation, the user may miss the feedback entirely and repeat the action. These micro-failures cascade into support tickets, transaction reversals, and user abandonment.

Feedback timing requirements are not negotiable; they are psychophysical thresholds. At 100 milliseconds, causality feels instantaneous—the system is an extension of the user's body. At 100 to 300 milliseconds, the delay is perceptible but tolerable; users maintain flow state. At 300 to 1000 milliseconds, the interface feels sluggish, and users begin to doubt whether their action registered. Beyond one second, attention fractures; users will click again, navigate away, or abandon the task entirely. These thresholds derive from the human perceptual system's temporal integration window and have been validated across decades of HCI research. Mobile interfaces compound the problem: touch targets must provide immediate visual depression feedback within 100 milliseconds even if the actual operation takes seconds, requiring optimistic UI updates and asynchronous state reconciliation.

Error prevention and error recovery represent divergent architectural philosophies. Prevention prioritizes constraint-based design: disable the "Submit" button until all required fields validate, use input masks that prevent invalid formats, offer autocomplete that guides users toward valid choices. Recovery architectures assume errors are inevitable and focus on graceful degradation: provide inline validation messages that appear immediately upon field blur, allow incremental correction without losing partial progress, offer undo mechanisms with sufficient history depth. The optimal balance depends on task criticality and user expertise. Financial transactions and medical records systems tilt heavily toward prevention because a single error can have catastrophic consequences. Creative tools and exploratory interfaces favor recovery because excessive constraints stifle experimentation and impose cognitive overhead that disrupts flow.

The deep invariant across all these mechanics is that human cognition operates on a limited-capacity parallel architecture with serial bottlenecks. Visual processing is massively parallel—we perceive an entire screen layout in a single fixation—but deliberate attention and working memory are brutally serial and capacity-limited. George Miller's famous "seven plus or minus two" has been revised downward to three to five chunks in modern cognitive load research. Every interaction that requires holding intermediate state—"remember which tab I was on, then navigate here, then return"—burns working memory slots that could be used for domain problem-solving. Expert users develop procedural memory that bypasses these bottlenecks, converting deliberate multi-step sequences into automatic motor programs, but this expertise requires hundreds of repetitions and collapses instantly when interfaces change unpredictably.

## 2. Core Architecture & Mechanics

The interaction state machine defines the permissible paths a user can traverse through the system. At the lowest level, every interactive element exists as a node in a directed graph where edges represent valid transitions triggered by user actions or system events. A form submission button begins in a `pristine-disabled` state because required fields are empty. As the user completes fields, validation logic evaluates on each `blur` or `input` event, and when all constraints satisfy, the button transitions to `pristine-enabled`. On click, it moves to `submitting`, which displays a spinner and disables the button to prevent double-submission. Upon receiving a server response, the system transitions to either `success` or `error`. Success might navigate to a confirmation page or display an inline success message and reset to `pristine-disabled`. Error states display inline feedback and return to `enabled`, allowing the user to correct and retry.

This state machine must be deterministic and complete. Every state must define behavior for every possible event, even if the behavior is "ignore." If the user clicks "Submit" during the `submitting` state, the event must be explicitly suppressed rather than implicitly undefined, because undefined behavior creates race conditions where rapid clicks queue multiple asynchronous operations. Similarly, if the server response times out, the system must transition to an explicit `timeout` state rather than leaving the interface frozen in `submitting`. Timeout handling itself requires careful calibration: a five-second timeout might be too aggressive for complex queries but absurdly long for simple lookups. Progressive feedback—"Still processing... this is taking longer than usual"—maintains user confidence during extended operations.

Fitts's Law optimization translates directly into quantitative design specifications. Consider a primary action button in a web application. The formula $T = a + b \log_2\left(\frac{D}{W} + 1\right)$ suggests that acquisition time depends on both distance $D$ from the user's current cursor position and target width $W$. The constant $a$ represents the reaction time and initiatory motor program (typically 50 to 200 milliseconds), and $b$ captures the speed-accuracy coefficient (typically 100 to 200 milliseconds per bit). For a button 600 pixels away and 120 pixels wide, the index of difficulty $ID = \log_2\left(\frac{600}{120} + 1\right) = \log_2(6) \approx 2.58$ bits. With $a = 100$ ms and $b = 150$ ms/bit, predicted acquisition time is approximately $100 + 150 \times 2.58 = 487$ milliseconds.

To reduce acquisition time, designers have three levers: decrease distance, increase width, or relocate the button to a zero-distance location such as the current cursor position or screen edges. Desktop operating systems place critical functions at screen edges—the infinitely tall "target" of the menu bar, the corners for window controls—because edges provide a physical barrier that eliminates the need for deceleration and precision correction. Mobile interfaces cannot exploit edges but instead use thumb-reachable zones: primary actions cluster in the bottom third of the screen where the thumb naturally rests when holding a phone one-handed. Secondary actions and destructive operations move to the top or require two-handed reach, imposing a Fitts cost that serves as a natural confirmation mechanism.

Hick's Law decomposition requires taxonomic analysis of the option space. A navigation menu with twelve undifferentiated items imposes $\log_2(13) \approx 3.7$ bits of decisional load. Grouping those items into four categories of three items each reduces the first decision to $\log_2(5) \approx 2.3$ bits, and the second decision to $\log_2(4) = 2$ bits, for a total of 4.3 bits. This appears worse until we account for the fact that visual grouping and semantic categorization allow parallel processing: the user can eliminate entire categories in a single perceptual fixation rather than serially evaluating twelve items. The effective decisional load is closer to the first-level decision alone—2.3 bits—because the second level operates on a pre-filtered set within working memory.

Progressive disclosure further collapses Hick complexity by deferring infrequent choices until contextually triggered. Microsoft Word's ribbon interface hides 90% of formatting options behind contextual tabs that appear only when relevant objects are selected. The base state presents perhaps twenty common operations, but selecting a table reveals table-specific tools, and selecting an image reveals image-specific tools. This context-sensitive filtering reduces $n$ dynamically based on user intent inferred from selection state. The tradeoff is discoverability: users must know that additional options exist and will appear upon selection, which requires either learned expertise or onboarding tooltips.

Feedback architecture operates on multiple parallel channels with different latency requirements. Visual feedback is immediate and persistent: button depression animations, progress bars, inline validation messages. Auditory feedback is optional but powerful for confirming non-visual state changes: a subtle click sound when a toggle switches, a chime when a file upload completes. Haptic feedback on mobile devices provides tactile confirmation that bridges the perceptual gap between glass touch and mechanical button depression. These channels must be synchronized; a button that plays a click sound 200 milliseconds after visual depression feels broken because human perception integrates multisensory input within a narrow temporal window.

```
[User Action] → [Input Event] → [State Transition] → [Feedback Rendering]
      ↓              ↓                  ↓                     ↓
   Click         onClick()         pristine → submitting    Spinner appears
      ↓              ↓                  ↓                     ↓
   (100ms)       (validation)        (async API call)      (optimistic UI)
      ↓              ↓                  ↓                     ↓
   [Response] ← [Server]          submitting → success    Confirmation modal
      ↓              ↓                  ↓                     ↓
   (500ms)       (processing)        (state sync)         (toast notification)
```

Optimistic UI updates decouple feedback from server latency by immediately rendering the expected success state before the operation completes. When a user clicks "Like" on a social post, the heart icon fills and the count increments instantly, while an asynchronous request propagates to the backend. If the request fails, the system must gracefully roll back the optimistic change and display an error, but in the 99% success case, the user experiences zero-latency feedback. This pattern is essential for mobile applications where network latency can exceed one second but is dangerous for non-idempotent operations like financial transactions where optimistic confirmation could mislead the user.

Error state taxonomy distinguishes between four failure classes: input validation errors, system constraint violations, transient infrastructure failures, and unrecoverable logic errors. Input validation errors—malformed email addresses, passwords that don't meet complexity requirements—should be caught client-side with immediate inline feedback adjacent to the offending field. The error message must specify the constraint: "Password must contain at least one uppercase letter, one number, and be at least 8 characters long" rather than "Invalid password." System constraint violations—attempting to book a sold-out event, exceeding an account quota—require server validation and should display contextual explanations with recovery actions: "This event is sold out. Join the waitlist or browse similar events."

Transient infrastructure failures—network timeouts, rate limiting, temporary service degradation—demand retry mechanisms with exponential backoff and user-facing messaging that distinguishes between "still trying" and "requires intervention." A robust implementation attempts automatic retries with backoff intervals of 1, 2, 4, 8 seconds, displays a non-blocking notification that retries are occurring, and escalates to a user-actionable error only after exhausting retries. Unrecoverable logic errors—null pointer exceptions, database constraint violations—should never surface raw error messages to users; instead, they trigger graceful degradation, log detailed diagnostics to monitoring systems, and display a generic "Something went wrong" message with a support reference ID.

## 3. High-Performance Optimization & Failure Modes

Interaction latency optimization begins with critical path analysis. Every user action triggers a chain of operations: event capture, validation, state mutation, API request, server processing, response parsing, state reconciliation, and UI re-render. The cumulative latency determines perceived responsiveness. Modern web applications target a 60 frames-per-second render budget, which allocates approximately 16 milliseconds per frame. A single synchronous JavaScript operation that blocks the main thread for 50 milliseconds causes three dropped frames and perceptible jank. React's concurrent rendering, Vue's asynchronous component updates, and Web Workers for offloading expensive computations all serve to keep the main thread responsive.

Animation performance for feedback mechanisms requires understanding the browser rendering pipeline. CSS transforms and opacity changes are GPU-accelerated and bypass layout and paint stages, completing in 1 to 2 milliseconds. Changes to width, height, or position trigger layout recalculation and repaint, potentially taking 10 to 20 milliseconds for complex DOM trees. Animating margin or padding on a parent element with many descendants can trigger recursive layout—the catastrophic performance failure mode where a single property change cascades through thousands of nodes. High-performance interaction feedback uses `transform: scale()` for size changes, `transform: translate()` for position changes, and `opacity` for visibility transitions, reserving layout-triggering properties for static initial render.

Fitts's Law exploitation extends beyond button sizing to interaction target prediction. If a user is editing a document and repeatedly clicking a toolbar button, the system can reduce effective distance by keeping the toolbar in a fixed position rather than allowing scroll to hide it. Sticky headers implement this principle. More sophisticated implementations predict the user's next action—after clicking "Bold," the user is statistically likely to click "Italic" or return to the text editor—and can preemptively render those targets or optimize their positioning. Autocomplete dropdowns that position predicted options near the current text cursor reduce acquisition distance to near-zero for keyboard-heavy users.

Hick's Law optimization through adaptive interfaces adjusts option count based on user expertise. Gmail's default compose window shows essential formatting options—bold, italic, link—but hides advanced features behind a disclosure arrow. After a user invokes an advanced feature, the system could permanently expand that section for that user, reducing decisional load on future compositions by elevating frequently used options to top-level visibility. This requires usage analytics and per-user preference state but can dramatically reduce interaction cost for power users without overwhelming novices.

Failure mode analysis for interaction mechanics must account for asynchronous state reconciliation. When a user submits a form, the client transitions to a loading state and awaits a server response. If the network connection drops, the request may silently fail, leaving the interface frozen. Robust implementations use request timeout handlers, typically 10 to 30 seconds depending on expected operation duration, and display explicit error states with retry buttons. Even more dangerous is the scenario where the request succeeds but the response is lost—the server processes the payment, but the client never receives confirmation. Idempotency tokens attached to each request allow the client to safely retry without causing duplicate processing, and server-side deduplication logic prevents double-charging even if the client retries a completed operation.

Error recovery architecture for complex multi-step workflows requires maintaining sufficient state to allow users to resume after interruption. A loan application spanning ten screens should persist progress after each screen submission rather than holding all state in memory. If the browser crashes or the user navigates away, the next session should resume at the last completed step. LocalStorage or IndexedDB provide client-side persistence for web applications; mobile apps use SQLite or platform-specific key-value stores. The recovery mechanism must handle partial state—if the user completed half of step 5 and abandoned—by either allowing continuation from that exact point or gracefully falling back to the last fully completed step with minimal data loss.

Accessibility considerations for interaction mechanics are non-negotiable. Keyboard navigation must provide equivalent interaction paths to mouse-based workflows, with visible focus indicators and logical tab order. Screen readers require semantic HTML—`<button>` rather than `<div onclick>`—and ARIA labels that describe state: "Submit button, disabled" or "Loading, please wait." Error messages must be programmatically associated with their fields using `aria-describedby` so assistive technologies can announce them. Timing-based interactions—hover menus that appear after 500 milliseconds—must provide alternative access methods because motor-impaired users may not be able to maintain cursor stability.

Performance monitoring for interaction responsiveness requires instrumenting the event pipeline. Time-to-interactive (TTI) measures the delay between page load and the moment when the interface is fully responsive to input. First input delay (FID) captures the latency between the user's first interaction and the browser's response, directly quantifying the Fitts acquisition time penalty imposed by main thread congestion. Custom event timing instrumentation can track the duration of specific interactions—form submission latency, search result rendering time, navigation transition duration—and alert when they exceed thresholds. Real user monitoring (RUM) aggregates these metrics across diverse devices and network conditions, revealing performance variance that synthetic testing misses.

Stress testing interaction state machines involves fuzzing the event space. Automated tools rapidly fire random event sequences—clicking buttons during loading states, submitting forms with partially filled fields, navigating away and returning mid-operation—to expose unhandled state transitions. This reveals edge cases like: what happens if the user clicks "Save" twice within 10 milliseconds? Does the double-click event get suppressed, or do two API calls fire? What if the server responds to the second request before the first? Race condition handling requires either serializing async operations with a request queue or implementing server-side deduplication based on idempotency tokens.

The ultimate optimization is eliminating interactions entirely through intelligent defaults and contextual inference. If 80% of users select the same shipping option, make it the default and allow override rather than forcing an explicit choice. If the user is viewing a product detail page, the "Add to Cart" button should pre-populate with that product rather than requiring the user to re-specify. If the user always exports reports in PDF format, remember that preference and skip the format selection dialog. Every decision point removed, every form field pre-filled, every confirmation dialog eliminated by making actions safely reversible—these are the compound interest of interaction design, saving seconds per session that accumulate into hours across a user's lifetime with the product.
