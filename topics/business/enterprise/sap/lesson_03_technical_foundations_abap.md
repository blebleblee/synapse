# Lesson 3: Technical Foundations with ABAP

## 1. First-Principles Intuition & Invariants

The Advanced Business Application Programming language represents SAP's proprietary fourth-generation language, designed in the 1980s to shield business logic from the volatility of underlying database schemas and hardware architectures. Unlike general-purpose languages optimized for algorithmic efficiency or systems programming, ABAP emerged from a singular constraint: enterprise applications must remain stable across decades while the data structures they manipulate evolve continuously through mergers, regulatory changes, and business model transformations. This architectural philosophy produced a language where database tables are first-class citizens, where every variable carries metadata about its business semantics, and where the compiler enforces referential integrity at compile-time rather than relegating these concerns to runtime validation.

The ABAP runtime operates within the NetWeaver Application Server, a multi-tenant execution environment that manages memory isolation, work process scheduling, and database connection pooling for thousands of concurrent users. Each user request spawns within a dialog work process, a stateless execution container that retrieves its context from shared memory structures and database-backed session state. This architectural choice stems from mainframe heritage: when SAP R/2 ran on IBM System/370 hardware in the 1970s, memory was the scarcest resource, and stateless processes allowed aggressive multiplexing of expensive hardware. Modern ABAP systems inherit this constraint, which manifests as the prohibition against background threads, the absence of function pointers, and the reliance on synchronous Remote Function Calls for inter-system communication.

The Data Dictionary serves as the central metadata repository, a concept borrowed from relational database theory but extended to encompass not just table schemas but also the business semantics of every field. When a developer defines a table field as referencing domain `MATNR`, the system automatically inherits field length, data type, input validation rules, search helps, and even text labels in forty languages. This metadata-driven architecture enables SAP's promise of zero-code internationalization: a sales order form developed in German automatically renders in Mandarin or Arabic because the labels flow from the Data Dictionary rather than being hard-coded in presentation logic. The price of this flexibility appears in runtime overhead—every field access triggers metadata lookups—but for enterprises operating across regulatory jurisdictions and linguistic boundaries, the trade-off proves economically rational.

Transport management reflects SAP's acknowledgment that enterprise software changes represent financial risk quantifiable in millions of dollars per incident. The Change and Transport System treats every modification—whether a table structure change, a custom report, or a configuration setting—as an atomic unit that must traverse a promotion pipeline from development to quality assurance to production. Each transport request carries a cryptographic signature linking it to a specific developer, timestamp, and change approval. This traceability becomes legally mandatory in regulated industries: pharmaceutical manufacturers must demonstrate to FDA auditors that every system change followed documented procedures, and financial institutions must prove to regulators that configuration changes received appropriate risk committee approval. The transport system transforms these compliance requirements from manual documentation exercises into automated audit trails embedded in the software delivery process itself.

The ABAP Repository stores all development artifacts—programs, function modules, table definitions, screens—in database tables rather than the filesystem, a design choice that predates modern version control systems but offers unique advantages for distributed development. When a developer in Singapore modifies a function module, the change commits atomically to the database, visible immediately to developers in Frankfurt and São Paulo without file synchronization protocols. The repository's versioning system maintains every historical state, enabling regulatory auditors to reconstruct the exact code that processed a financial transaction three years prior. This database-centric approach collides with contemporary DevOps practices that assume Git repositories and CI/CD pipelines, forcing enterprises into complex bridging architectures where ABAP code must be extracted, versioned externally, and re-imported—a friction point that reveals deep incompatibilities between SAP's architectural assumptions and modern software engineering practices.

## 2. Core Architecture & Mechanics

The ABAP programming model distinguishes between executable programs, function modules, and classes, each serving distinct architectural roles in the three-tier landscape. An executable program—designated by the `REPORT` keyword—represents the original programming model from the R/2 era, where a single monolithic codebase handled screen rendering, business logic, and database access. Modern ABAP development relegates reports to analytical output generation, using them as thin orchestration layers that invoke reusable function modules for business logic and classes for object-oriented abstractions. This layering reflects the gradual evolution from procedural to object-oriented paradigms without breaking backward compatibility: a Z-program written in 1995 still executes unchanged on a 2025 S/4HANA system because the ABAP kernel maintains interpreter semantics across thirty years of platform evolution.

Function modules encapsulate business logic in stateless, remotely callable units, the ABAP equivalent of microservices before that architectural pattern gained its current nomenclature. A function module declares its interface through importing, exporting, changing, and table parameters, each carrying type information from the Data Dictionary. When a function module is flagged as remote-enabled, the SAP Gateway automatically generates RFC stubs that serialize parameters, transmit them over TCP/IP using the proprietary RFC protocol, and deserialize them in the target system. This mechanism enables the classic distributed SAP landscape where a sales order created in the CRM system triggers an RFC to the ERP system for ATP (Available-to-Promise) checks, which in turn invokes an RFC to the Supply Chain Management system for inventory allocation—all appearing to the end user as a single atomic transaction despite spanning multiple database instances across continents.

The Data Dictionary's type system extends SQL's primitive types with business-centric abstractions. A domain defines not just storage characteristics but also semantic constraints: the `MATNR` domain specifies an 18-character material number, but it also encodes that leading zeros must be preserved, that the field participates in material master search helps, and that conversion exits must handle external format transformations. Data elements layer business semantics atop domains: the data element `MATNR` references the domain `MATNR` but adds field labels, documentation, and parameter IDs for screen field memory. This multi-layer type system enables the Data Dictionary to serve as a single source of truth: when a regulatory change mandates extending material numbers to 40 characters, modifying the domain propagates automatically to every table, structure, function parameter, and screen field that references it—a change that would require invasive refactoring in traditional RDBMS schemas.

Transparent tables represent the primary data persistence mechanism, mapping one-to-one to database tables while allowing the ABAP runtime to inject client field partitioning, buffering hints, and change document triggers. The client field—typically the first column of every table—implements SAP's multi-tenancy model at the data level: a single database instance stores data for multiple legal entities, differentiated by a three-character client code. Every Open SQL statement implicitly filters by the current session's client, preventing cross-contamination of subsidiary data. This architecture emerged from SAP's origins serving multi-national conglomerates where each country subsidiary required logical data separation but shared a common code base. The client mechanism's persistence as a core architectural invariant—even as modern cloud platforms offer superior tenant isolation—demonstrates path dependency in enterprise architecture: migrating away would invalidate decades of custom code that assumes client-based partitioning.

Table buffering exposes the NetWeaver Application Server's multi-level caching hierarchy to developers through Data Dictionary metadata. Marking a table as fully buffered instructs the application server to load its entire contents into shared memory at startup, satisfying read requests without database round trips. Single-record buffering loads individual keys on demand, maintaining an LRU cache in the application server's shared memory. Generic buffering caches all records matching a specified key prefix, optimizing for range scans that occur in foreign key validation. These buffering modes operate transparently to application code—Open SQL statements automatically check buffer before querying the database—but developers must understand invalidation semantics: when a buffered table receives an INSERT, UPDATE, or DELETE on any application server in the cluster, SAP Gateway broadcasts an invalidation message to all servers, causing them to refresh from the database on next access. Incorrect buffering configuration produces Heisenbugs where users see stale data depending on which application server handled their request, failures that manifest only in high-concurrency production environments.

Internal tables represent ABAP's in-memory data structure, analogous to arrays or lists in conventional languages but carrying database-like semantics. A standard internal table maintains insertion order and allows duplicate keys, suitable for read-heavy operations. A sorted internal table maintains entries in key order via binary tree insertion, providing logarithmic search performance at the cost of linear insertion time. A hashed internal table implements a hash map, offering constant-time key lookups but prohibiting sequential processing. The runtime enforces memory limits—typically 2GB per work process—causing a `TSV_TNEW_PAGE_ALLOC_FAILED` short dump when an internal table exhausts the address space. This constraint forces developers to adopt streaming algorithms for large datasets: rather than loading a million-row table into memory, production code iterates with `SELECT ... PACKAGE SIZE 5000` cursors, processing records in fixed-size batches to maintain bounded memory consumption.

Field symbols and data references introduce pointer semantics into a language originally designed without them. A field symbol, declared with `FIELD-SYMBOLS <fs> TYPE ty`, acts as a typed alias to another variable, enabling generic programming patterns. The `ASSIGN` statement binds a field symbol to a target, allowing subsequent modifications to transparently update the underlying data. This mechanism proves essential in framework code that manipulates structures of unknown type at runtime, such as ALV grid components that render arbitrary tables without compile-time knowledge of their columns. Data references—created with `CREATE DATA` and dereferenced with `dref->*`—enable dynamic memory allocation and polymorphic data structures, though their use remains constrained by ABAP's prohibition against circular references and the absence of a generational garbage collector.

Open SQL provides a vendor-neutral database abstraction layer, translating ABAP statements into native SQL dialects for Oracle, DB2, SQL Server, HANA, and other supported databases. The syntax intentionally restricts itself to the common subset of SQL-92: no vendor-specific functions, no outer joins (until recent releases), no subqueries in the SELECT list. This conservatism enables code portability but frustrates developers accustomed to modern SQL expressiveness. The ABAP kernel's SQL preprocessor injects client filters, applies table buffering logic, and rewrites queries for performance—transparently converting `SELECT SINGLE` into indexed lookups and `FOR ALL ENTRIES` into parameterized bulk selects. However, the abstraction leaks under load: a query that performs well on HANA's columnar engine may timeout on Oracle's row-based storage, forcing developers into native SQL escape hatches that sacrifice portability for performance.

The work process lifecycle governs resource allocation and transaction boundaries. When a user executes a transaction, the dispatcher allocates an available dialog work process, loading the user's session context from the database into the work process's roll area. The ABAP program executes synchronously within this process until hitting a screen display statement, at which point the work process serializes its context back to the database and returns to the free pool. The next user action may execute in a different work process, requiring context restoration from the database. This stateless model enables massive horizontal scaling—an SAP system with 500 concurrent users might run only 50 dialog work processes—but imposes strict limits on execution time. Dialog work processes abort after 300 seconds of CPU time or 600 seconds of wall-clock time by default, preventing runaway programs from monopolizing resources. Long-running operations must execute in background work processes, which lack time limits but cannot perform screen I/O.

Logical database abstraction represents an early attempt at data access layer separation, predating modern ORM frameworks by two decades. A logical database defines a hierarchical data model—for example, customers, their sales orders, and order line items—along with selection screens and authorization checks. Programs declare their attachment to a logical database in their attributes, automatically inheriting its selection parameters and read authorization logic. The runtime invokes callback methods in the program—`GET customer`, `GET order`, `GET item`—passing each record as the hierarchy traverses. This pattern enabled reusable authorization and selection logic but fell out of favor as object-oriented design patterns matured, though thousands of legacy reports still depend on logical databases for their authorization enforcement.

## 3. High-Performance Optimization & Failure Modes

ALV reporting frameworks abstract the complexity of grid rendering, sorting, filtering, and Excel export behind declarative field catalogs. The classic ALV—function module `REUSE_ALV_GRID_DISPLAY`—accepts an internal table and a field catalog structure defining each column's name, type, and rendering hints. The Object-Oriented ALV—class `CL_SALV_TABLE`—provides a fluent API for programmatic customization: adding hyperlinks, conditional formatting, and custom toolbar buttons. Both variants delegate rendering to the SAP GUI's grid control, which implements virtual scrolling to handle million-row result sets without loading all data into client memory. The performance boundary appears when developers attempt client-side aggregations on large datasets: the ALV transmits all matching rows to the GUI before applying user-initiated filters, causing network saturation. Production-grade reports must implement database-level filtering and aggregation, using the ALV purely for final presentation of pre-computed results.

BAPI function modules expose SAP's standard business objects through stable, documented interfaces insulated from internal table structure changes. The BAPI `BAPI_SALESORDER_CREATEFROMDAT2` creates a sales order by accepting header data, line items, partners, and text specifications as table parameters, performing all validation, pricing, and ATP checks before committing. Unlike direct table updates—which bypass business logic and corrupt data integrity—BAPI calls enforce the same validation as interactive transactions. The BAPI interface contract promises backward compatibility: SAP guarantees that upgrading to a new release will not break BAPI signatures, though new optional parameters may appear. This stability enables external systems to integrate via RFC without brittle dependencies on internal implementation details. However, BAPIs impose performance penalties: a BAPI that creates a sales order with 1000 line items executes the same validation logic 1000 times, whereas direct table updates could batch-validate. High-throughput scenarios require IDoc processing or direct ALE interfaces that amortize validation costs across larger batches.

Remote Function Calls implement SAP's distributed object protocol, predating SOAP and REST but serving similar architectural purposes. An RFC-enabled function module becomes callable across system boundaries through the `CALL FUNCTION ... DESTINATION` syntax, where the destination references a connection configuration stored in transaction `SM59`. Synchronous RFC blocks the caller until the remote system responds, suitable for interactive queries like ATP checks. Asynchronous RFC queues the call for background processing, returning immediately to the caller—essential for decoupling systems with different availability requirements. Transactional RFC guarantees exactly-once execution semantics through a persistent queue and automatic retry mechanism, preventing duplicate postings when network failures occur mid-transaction. Queued RFC extends tRFC with serialization: calls to the same queue name execute in order, critical for maintaining causality in distributed workflows. The RFC protocol's proprietary nature—it operates over TCP port 3300 with a binary serialization format—complicates firewall traversal and integration with non-SAP systems, driving adoption of SOAP and REST wrappers for external connectivity.

Enhancement frameworks provide structured modification points in SAP-delivered code without altering the original source. Implicit enhancement points appear automatically at the end of every form routine, method, and function module, allowing customers to inject code without touching SAP's code. Explicit enhancement points—marked by `ENHANCEMENT-POINT` statements—indicate locations where SAP anticipates frequent customization, such as adding fields to a sales order screen or extending pricing logic. The enhancement implementation stores in a separate repository object, transported independently of the base code. During an SAP upgrade, the base code updates while enhancements remain intact, though SAP provides no guarantee that enhancements will continue functioning if the surrounding code's semantics change. This tension between extensibility and upgradability forces enterprises into costly regression testing after every SAP patch, validating that thousands of enhancements still operate correctly in the modified runtime environment.

Modification Assistant tolerates direct changes to SAP-delivered code by tracking every altered line in a modification log. When upgrading, the system detects conflicts between customer modifications and new SAP code, presenting a three-way merge interface where developers manually reconcile differences. This mechanism enabled customers to adapt SAP software before enhancement frameworks matured, but creates permanent technical debt: every modification must be revalidated and potentially reimplemented with each upgrade. Modern best practice prohibits modifications except in crisis scenarios, favoring enhancements, BAdIs, and custom wrapper programs that preserve a clean separation between SAP-delivered and customer-developed code.

Transport management orchestrates code promotion across the three-system landscape: development, quality assurance, and production. Every change begins in a development system where developers create a transport request, a container for related changes. The request status—modifiable, released, imported—governs who can add changes and whether the request can promote to subsequent systems. Releasing a request locks all contained objects, exports their content to operating system files, and increments version numbers in the repository. The transport files—cofiles containing metadata and data files containing serialized repository objects—transfer to the quality system via operating system commands or the Transport Management System's RFC-based distribution. Import in the quality system validates dependencies, applies changes to the database, and generates activation logs detailing any errors. Successful quality validation triggers promotion to production using identical import procedures, ensuring that production receives byte-identical code to what quality tested.

Transport routes define the promotion topology using a hierarchical domain architecture. A development system designates itself as the domain controller, with quality and production systems as targets in a delivery chain. Three-tiered landscapes typically configure a single development system delivering to both quality and production, while more complex architectures support multiple development systems consolidating changes through integration systems before reaching production. The Consolidation route moves transports from development to quality, while Delivery routes propagate from quality to production. This separation enables parallel development streams: one team's changes can remain in quality while another team's changes promote to production, provided they affect non-overlapping objects. Transport layer assignment determines which changes a transport request can contain: a transport in the customizing layer carries only configuration tables, while a workbench transport holds repository objects like programs and function modules.

Debugging in ABAP operates through an interpreter-level breakpoint mechanism integrated into the kernel. The `/h` command in the SAP GUI command field activates the debugger for the next screen interaction, halting execution at the first ABAP statement. Classical debugger presents a text-based interface with separate tabs for variables, internal tables, and call stack. New debugger—available since NetWeaver 7.0—provides a graphical interface with syntax-highlighted source, watch expressions, and conditional breakpoints. Both debuggers support watchpoints that pause execution when a specified variable changes value, essential for diagnosing data corruption bugs in complex business logic. The debugger's session isolation allows production debugging: an activated debugger affects only the specific user session, leaving other users' transactions unaffected. However, debugging incurs severe performance degradation—interpreted execution can run 100x slower than optimized compiled code—making it unsuitable for load testing or performance analysis.

SQL trace, activated in transaction `ST05`, captures every database operation executed during a transaction, recording table names, access paths, row counts, and execution times. Post-execution analysis reveals full table scans, missing indexes, and redundant queries. The trace distinguishes between identical queries executed in a loop—a symptom of inefficient code—and legitimate multiple accesses to different keys. HANA SQL trace extends this capability with visualization of columnar engine operations, showing whether queries utilize column store optimizations or fall back to row engine processing. Production trace analysis requires `S_DEVELOP` authorization and generates database load through its instrumentation overhead, limiting its use to specific user sessions rather than system-wide profiling.

Runtime analysis, invoked through transaction `SE30` or the newer `SAT`, measures CPU and wall-clock time consumption at statement granularity. The profiler instruments ABAP code with timing probes, recording how many microseconds each line consumes across the traced transaction. Call hierarchy views expose which subroutines and methods dominate execution time, while hit lists identify hot loops. The analysis distinguishes database time—spent waiting for SQL responses—from ABAP time spent in computational logic. A report showing 80% database time indicates I/O-bound performance requiring query optimization, while 80% ABAP time suggests algorithmic inefficiency in business logic. The profiler's 10% instrumentation overhead restricts its use to development and quality systems, though limited production sampling sometimes proves necessary when performance issues manifest only under realistic data volumes.

Memory Inspector, transaction `S_MEMORY_INSPECTOR`, diagnoses memory leaks and excessive heap consumption by tracking object allocations and internal table sizes. The tool captures heap snapshots at developer-specified points, comparing them to identify objects that grow unexpectedly. Memory leaks in ABAP typically manifest as internal tables that accumulate records without bounds or persistent data references that never dereference. The inspector highlights the largest memory consumers, drilling down to show which program lines allocated the memory. A classic memory leak pattern appears when a program caches data in static variables across multiple user requests in a stateful scenario—stateful RFC or web service calls—without clearing the cache, causing linear memory growth until the work process exhausts its 2GB address space and terminates with a short dump.

Code Inspector, transaction `SCI`, automates code quality checks through configurable rulesets. SAP ships standard variants for performance, security, and syntax checking. Performance checks flag inefficient patterns: `SELECT` statements inside loops, missing `FOR ALL ENTRIES` optimizations, string concatenations in loops without pre-allocated buffers. Security checks identify SQL injection vulnerabilities, authorization check bypasses, and hard-coded passwords. Extended program checks enforce naming conventions, documentation requirements, and Unicode compliance. Enterprise-grade development shops embed Code Inspector execution in transport release procedures, blocking promotion of code that violates critical rules. The inspector generates problem counts by severity—error, warning, information—with errors typically mandating remediation before production deployment.

Unicode compliance represents a fundamental character encoding constraint in modern SAP systems. Non-Unicode systems store characters as single-byte ISO 8859-1, limiting text fields to Western European languages. Unicode systems allocate two bytes per character using UTF-16 encoding, supporting all languages but requiring explicit length handling in ABAP code. The `STRLEN()` function returns character counts, not byte lengths, while `XSTRLEN()` returns byte counts. Bit-level operations—shifting, masking—become illegal on character fields, requiring explicit conversion to hexadecimal fields. Unicode-incompatible code fails at runtime with a `SYNTAX_ERROR` short dump when attempting invalid operations. Migration from non-Unicode to Unicode represents a multi-year program requiring validation of every custom program, particularly those performing byte-level file parsing or legacy interface communication.

Short dumps—ABAP's exception mechanism for unhandled runtime errors—terminate the current transaction and log diagnostic information in transaction `ST22`. Each dump captures the call stack, variable contents, and database cursor state at the moment of failure. Common dump types include `DBIF_RSQL_SQL_ERROR` for database errors, `TSV_TNEW_PAGE_ALLOC_FAILED` for memory exhaustion, and `SYSTEM_CORE_DUMPED` for kernel-level crashes. The dump analysis view shows the exact source line that triggered the failure and the chain of calls leading to it. Production monitoring systems integrate with `ST22` to alert on new dump types, as recurring dumps indicate systematic bugs requiring code fixes. Dump frequency tracking identifies problematic transactions: a transaction generating 100 dumps daily likely contains logic errors that manifest only under specific data conditions encountered in production but not in test systems with sanitized data.

Performance bottlenecks in ABAP programs typically fall into four categories: inefficient database access, excessive memory allocation, algorithmic complexity, and RFC latency. Database inefficiency manifests as full table scans caused by missing indexes or non-selective WHERE clauses. The solution involves creating secondary indexes on frequently filtered fields, though each index imposes insert/update overhead that must be balanced against read performance gains. Memory bottlenecks appear when programs load entire tables into internal tables rather than processing incrementally. Refactoring to cursor-based processing with bounded batch sizes eliminates these issues at the cost of increased code complexity. Algorithmic inefficiency often stems from nested loops with quadratic or cubic complexity—reading a header table and, for each header, looping through a detail table. Replacing nested loops with hashed internal tables reduces complexity from O(n²) to O(n). RFC latency accumulates when a program makes dozens of remote calls in a loop rather than batching data and making a single bulk call. Aggregating 100 RFC calls into one reduces network round trips and latency by two orders of magnitude.

The Open SQL optimizer's query rewriting capabilities offer significant performance leverage when properly exploited. The `FOR ALL ENTRIES` clause transforms a filter set into a bulk operation: instead of executing a `SELECT` inside a loop with varying WHERE conditions, the program loads filter values into an internal table and passes the entire table to a single `SELECT FOR ALL ENTRIES`. The database executes this as a parameterized bulk query, amortizing parsing and plan optimization costs. However, the clause carries subtle constraints: the filter table must not be empty—causing the query to return all rows—and large filter tables (>10,000 entries) should be split into chunks to avoid exceeding database parameter limits. The `PACKAGE SIZE` addition to `SELECT` enables streaming large result sets in fixed-size batches, processing each batch before fetching the next. This pattern prevents memory exhaustion when query results exceed available heap space.

Native SQL escape hatches—embedded SQL between `EXEC SQL` and `ENDEXEC` statements—bypass Open SQL abstraction to access database-specific features. HANA-specific queries can exploit columnar operations, full-text search, and spatial functions unavailable in Open SQL. The cost appears in portability: native SQL code becomes database-dependent, failing if the system migrates to a different database platform. This tradeoff proves acceptable when performance requirements exceed what Open SQL can deliver—a common scenario in analytical reporting on multi-billion-row tables where HANA's in-memory columnar engine provides orders-of-magnitude speedups over traditional row-based processing. Native SQL also enables stored procedure invocation, allowing complex multi-statement transformations to execute entirely within the database, minimizing data transfer to the application server.

Authorization trace, activated via transaction `ST01`, records every authority check a transaction performs, showing which authorization objects it tested and whether the user's profile granted access. This diagnostic tool proves essential for custom transaction authorization troubleshooting: when a user reports access denial, the trace reveals which missing authorization caused the failure. Security architects use trace analysis to construct minimal privilege profiles: run a transaction with full authorization while tracing, then create a role containing only the exact authorizations the trace recorded as checked. This approach implements least-privilege principles systematically rather than through trial-and-error authorization assignment. However, authorization trace generates enormous logs—hundreds of checks per transaction—requiring post-processing scripts to filter relevant failures from successful checks.

Table logging, configured in the Data Dictionary technical settings, records every INSERT, UPDATE, and DELETE operation to change document tables. The log captures the user ID, timestamp, transaction code, and before/after values of changed fields. Regulatory compliance in financial and pharmaceutical industries mandates table logging for audit-critical tables like accounting documents, material master data, and manufacturing batch records. The log tables grow linearly with transaction volume—a high-throughput system may accumulate billions of log entries annually—requiring archiving strategies to prevent unbounded database growth. Log analysis tools query these change documents to reconstruct data lineage: identifying who modified a customer credit limit, when a material batch status changed from quality inspection to released, or which transaction updated a cost center assignment.

Custom table partitioning on HANA exploits the database's native range and hash partitioning to distribute large tables across multiple storage nodes. A sales order table partitioned by fiscal year places each year's data in a separate partition, enabling partition pruning: queries filtering on year 2023 read only that partition's segments. Partitioning improves query parallelism and simplifies archiving—dropping a partition removes all its rows in milliseconds versus hours for row-by-row deletion. However, partition key choice requires careful analysis: partitioning by a field not used in WHERE clauses provides no performance benefit, while partitioning by high-cardinality fields like document number creates excessive partitions that overwhelm metadata structures. The optimal partition key exhibits medium cardinality (dozens to hundreds of distinct values) and appears frequently in query predicates.
