# Lesson 1: PLC Architecture, Scan Cycles, Ladder Logic Semantics

## 1. First-Principles Intuition & Invariants

The programmable logic controller emerged in the late 1960s as a direct replacement for hardwired relay panels in automotive manufacturing plants. General Motors, frustrated by the cost and inflexibility of rewiring relay cabinets for every model year change, issued a specification demanding a solid-state control system that production electricians could program using familiar ladder diagram notation. Richard Morley's Modicon 084, introduced in 1969, answered this challenge by encoding relay logic semantics into semiconductor memory and executing them in a deterministic, cyclical fashion. This architectural decision—embedding discrete control logic into a repeating scan cycle with guaranteed worst-case execution time—established the foundational invariant that distinguishes PLCs from general-purpose computers: bounded, predictable real-time operation.

Unlike general-purpose microprocessors running preemptive multitasking operating systems with stochastic scheduling jitter, a PLC executes a single monolithic control program from beginning to end, then immediately repeats. This scan cycle architecture eliminates context switching overhead and priority inversion hazards. Every input is sampled once per cycle into an input image table, the entire ladder logic program executes against this frozen snapshot, and computed outputs are written simultaneously to an output image table at cycle conclusion. This triple-phase model—input acquisition, logic solve, output update—creates deterministic causality: an input transition cannot affect outputs until the next scan cycle begins, establishing a minimum propagation delay equal to one full scan time.

The physical manifestation of this control philosophy appears in the PLC's modular hardware architecture. A backplane connects a central processing unit module, discrete and analog input/output modules, communication interface modules, and specialty function modules into a unified system. Each I/O module contains its own microprocessor handling signal conditioning, isolation, and conversion, offloading these tasks from the main CPU. A discrete input module might implement optoisolator circuits providing 2500VAC galvanic isolation, threshold detection with hysteresis for noise immunity, and status indication LEDs—all transparent to the ladder logic programmer, who interacts with these circuits through symbolic addresses in the data table.

This abstraction between physical I/O and program logic constitutes the PLC's primary value proposition. When a proximity sensor on conveyor line three detects a part, the electrical transition propagates through a shielded twisted-pair cable to terminal block position seven on input module two, where an optoisolator circuit converts the 24VDC sensor signal into a logic-level pulse. The input module's local processor debounces this signal over several microseconds, then writes the stable state into a specific bit location within the input image table during the next scan cycle's input acquisition phase. The ladder logic program references this bit not by its physical address but by a symbolic tag like `Conveyor_3_Part_Detected`. This symbolic abstraction allows plant engineers to replace a failed sensor with a different model using a different voltage level—requiring only input module reconfiguration, not program modification.

The scan cycle's deterministic nature imposes fundamental constraints on control system response time. Consider a safety interlock requiring that a press cannot actuate unless both guard doors read closed. If the scan time measures 10 milliseconds and an operator opens a door halfway through the current scan, the input image table retains the stale "closed" state for the remainder of that cycle. The door-open condition propagates to the ladder logic only when the next scan's input acquisition phase reads fresh values. The press output, computed during that second scan's logic solve phase, updates the physical output only at that scan's conclusion. Total worst-case latency from physical event to output response spans two full scan cycles plus input/output module propagation delays—typically 20 to 30 milliseconds for a 10ms scan.

This latency characteristic fundamentally shapes PLC application domains. Processes with mechanical time constants measured in seconds or minutes—batch reactors, HVAC systems, conveyor coordination—tolerate scan cycle delays without issue. High-speed servo positioning or nanosecond-precision timing applications exceed PLC architectural capabilities, requiring specialized motion controllers or FPGA-based systems. The PLC occupies the middle ground: deterministic enough for safety-critical interlocks and sequential machine control, yet flexible enough for complex Boolean logic, timer/counter operations, and arithmetic computations that would require hundreds of discrete relay components.

Memory organization within the PLC reflects its relay replacement heritage while incorporating modern data structure concepts. The data table partitions into discrete regions: input image bits corresponding to physical input terminals, output image bits driving physical output terminals, internal bit storage for intermediate logic states, timer/counter structures containing preset values and accumulated counts, and numeric registers holding analog measurements or setpoint values. Early PLCs implemented this memory as battery-backed SRAM with addresses exposed directly to the programmer—`I:0/7` referenced input module zero, terminal seven; `O:2/3` controlled output module two, terminal three. Contemporary PLCs abstract these hardware addresses behind tag-based symbolic names while maintaining the underlying partitioned memory model for deterministic access patterns.

The ladder logic programming paradigm encodes Boolean control equations using graphical symbols derived from electromechanical relay diagrams. A normally-open contact symbol represents an AND operation: the rung conducts logic continuity only when the referenced bit reads true. A normally-closed contact inverts this logic, conducting when the bit reads false. Series-connected contacts implement logical AND; parallel branches implement OR. The rightmost position of each rung contains an output instruction—typically a coil symbol—that writes computed rung continuity to a specific bit or executes a function block. This graphical notation allows electricians and technicians familiar with relay panel schematics to program complex Boolean logic without learning text-based programming languages, fulfilling General Motors' original 1968 specification requirement.

Execution semantics for ladder logic differ critically from relay panel operation. In a hardwired relay panel, all coils and contacts react simultaneously to input changes, with propagation delays measured in milliseconds as electromagnetic fields collapse and rebuild. The PLC serializes this parallel logic into sequential rung-by-rung evaluation within the scan cycle. The processor evaluates rung one from left to right, computes output states, then proceeds to rung two. This top-to-bottom, left-to-right evaluation order creates subtle semantic differences from true parallel relay operation. If rung five writes a bit and rung seven reads that same bit, rung seven observes the updated value within the same scan. If rung seven writes and rung five reads, rung five retains the previous scan's value—the updated value propagates only on the next scan cycle. This sequential execution model requires programmers to understand data dependencies and carefully order rungs to achieve intended control behavior.

## 2. Core Architecture & Mechanics

The physical construction of a modular PLC system begins with the backplane—a printed circuit board containing parallel data, address, and control buses connecting multiple I/O module slots. This backplane implements a memory-mapped I/O architecture: each installed module responds to a specific range of memory addresses on the shared bus. When the CPU executes an instruction reading input address `0x0800`, the backplane's address decoding logic activates the chip-select line for input module slot zero, which drives its current input states onto the data bus. This direct memory access model eliminates protocol overhead—no packets, no handshaking, just synchronous read/write cycles completing in predictable clock edge counts.

Power distribution through the backplane follows multiple isolated rails. A 120VAC or 24VDC field power connection feeds input and output modules directly, maintaining galvanic isolation from the logic power rails supplying the CPU and communication modules. This isolation topology ensures that ground loops in field wiring or voltage transients from motor starters cannot inject noise into the processor's digital circuits. Each I/O module contains its own isolated DC-DC converter or linear regulator stepping field power down to the 3.3V or 5V logic levels required by its local microcontroller and signal conditioning circuits.

Input modules implement sophisticated signal conditioning to convert raw field signals into clean logic levels suitable for data table storage. A typical discrete input module designed for 24VDC industrial sensors contains optoisolator circuits providing 1500 to 2500VAC isolation between field wiring and backplane logic. The field-side circuitry includes current-limiting resistors setting input impedance around 3 to 5 kilohms, voltage threshold detectors with hysteresis bands preventing chatter on slowly transitioning signals, and LED indicators driven from the field side showing terminal energization status independent of processor operation. After optical isolation, the logic-side circuitry presents stable Boolean states to a local microcontroller, which implements digital filtering—typically requiring a consistent state for 1 to 10 milliseconds before updating the input image table to suppress electromagnetic interference spikes.

The temporal behavior of this input conditioning chain determines minimum detectable pulse width. If a sensor produces a 500-microsecond pulse but the input module requires 2 milliseconds of stable state before registering a transition, the pulse disappears—filtered out as noise. High-speed counter modules designed for encoder interfaces bypass this filtering, implementing dedicated hardware counters that increment on every edge transition regardless of scan cycle timing. These specialty modules contain their own local processors and memory, accumulating counts asynchronously and presenting accumulated totals to the main CPU as memory-mapped registers read during the scan cycle.

Output modules perform the inverse transformation: accepting Boolean states from the output image table and converting them into field-side switching actions. A relay output module contains electromechanical relays rated for 2 to 10 ampere resistive loads, providing complete isolation but limited to 10 to 20Hz switching frequencies due to mechanical contact bounce and coil inductance. Transistor output modules employ MOSFETs or BJTs for solid-state switching at kilohertz rates, suitable for driving solenoid valves, indicator lamps, or SSR control inputs, but requiring attention to inductive kickback suppression and current ratings. Triac output modules switch AC loads directly, integrating zero-crossing detection to minimize electromagnetic interference by transitioning only when line voltage crosses through zero.

The output image table update mechanism determines precise timing of field-side transitions. During the scan cycle's output update phase, the CPU writes the entire computed output image to each output module simultaneously via backplane broadcast writes. Each module latches these new values and updates its physical output terminals within microseconds, constrained only by the switching time of its output devices—10 milliseconds for relay contacts, 10 microseconds for transistors. This simultaneous update behavior ensures that multiple outputs change state synchronously, critical for applications like coordinated motor direction control where enabling forward and reverse simultaneously would create a short-circuit fault.

Analog I/O modules introduce quantization and conversion time considerations absent from discrete I/O. A 12-bit analog input module with a 0-10VDC range quantizes continuous voltages into 4096 discrete levels, yielding approximately 2.4mV resolution. The successive-approximation ADC within the module requires 10 to 50 microseconds to perform each conversion, limiting simultaneous sampling rates. To maximize scan cycle determinism, most analog modules convert all channels during the input acquisition phase, storing digitized values in local registers that the CPU bulk-reads as a contiguous memory block. This architecture ensures that all analog readings presented to the ladder logic program represent simultaneous samples, not values captured at staggered times throughout the scan.

The scan cycle's internal structure partitions into five distinct phases executed sequentially. The housekeeping phase validates system integrity: the CPU verifies memory checksums, monitors supply voltages, checks I/O module health via backplane communication, and services the watchdog timer—a hardware circuit that resets the processor if not periodically strobed, providing fail-safe protection against infinite loops. The input acquisition phase bulk-reads all input modules in a single backplane transaction, copying physical input states into the input image table. The program execution phase evaluates every rung of the ladder logic program sequentially from top to bottom, performing Boolean logic, arithmetic operations, timer/counter updates, and function block executions. The output update phase bulk-writes the computed output image table to all output modules. Finally, the communication phase services network messages, HMI requests, and programming terminal connections before immediately beginning the next scan.

```
┌─────────────────────────────────────────────────────────┐
│                    SCAN CYCLE PHASES                     │
├─────────────────────────────────────────────────────────┤
│ 1. HOUSEKEEPING (0.1-0.5 ms)                            │
│    - Watchdog timer reset                                │
│    - Memory integrity check                              │
│    - I/O module health diagnostics                       │
├─────────────────────────────────────────────────────────┤
│ 2. INPUT ACQUISITION (0.2-1.0 ms)                       │
│    - Bulk read all input modules → Input Image Table    │
│    - Analog conversions complete                         │
│    - High-speed counter snapshot                         │
├─────────────────────────────────────────────────────────┤
│ 3. PROGRAM EXECUTION (2-20 ms typical)                  │
│    - Evaluate ladder logic rung-by-rung                  │
│    - Execute function blocks                             │
│    - Update timers/counters                              │
│    - Compute outputs → Output Image Table                │
├─────────────────────────────────────────────────────────┤
│ 4. OUTPUT UPDATE (0.2-1.0 ms)                           │
│    - Bulk write Output Image Table → all output modules  │
│    - Synchronous physical output transitions             │
├─────────────────────────────────────────────────────────┤
│ 5. COMMUNICATION SERVICE (0.5-5.0 ms)                   │
│    - HMI data exchange                                   │
│    - Network message processing                          │
│    - Programming terminal service                        │
└─────────────────────────────────────────────────────────┘
         ↓ Loop immediately to phase 1
```

This five-phase model produces total scan times ranging from 3 milliseconds for simple programs with minimal I/O to 100 milliseconds for complex applications with thousands of ladder rungs and extensive communication requirements. The processor vendor specifies worst-case execution times for each instruction type: a simple contact examination might consume 0.5 microseconds, a timer instruction 2 microseconds, a floating-point mathematical operation 10 microseconds. Programmers multiply instruction counts by these timing specifications to compute worst-case scan time, ensuring the system meets real-time deadlines.

Ladder logic semantics derive directly from electromechanical relay operation but diverge in critical ways due to sequential evaluation. Consider a self-holding or "seal-in" circuit: a momentary pushbutton energizes a motor contactor, and an auxiliary contact on that contactor provides a parallel holding path around the pushbutton so the motor continues running after button release. In relay hardware, this happens instantaneously—the contactor's auxiliary contact closes within milliseconds of coil energization. In ladder logic, the equivalent circuit places a normally-open contact in parallel with the pushbutton contact, both feeding the motor output coil. When the pushbutton contact closes, the rung evaluates true, energizing the motor output. On the very same scan cycle, when evaluation reaches the parallel holding contact referencing that motor output bit, the processor reads the just-written true state from the output image table. The holding logic activates immediately, within the same 10-millisecond scan that initiated motor start—functionally equivalent to relay operation despite sequential evaluation.

Data dependency hazards arise when rungs reference bits written by later rungs in the program. Suppose rung 50 implements an alarm condition that sets an `Alarm_Active` bit, and rung 10 uses a normally-closed `Alarm_Active` contact to enable production mode. During scan execution, rung 10 evaluates before the alarm logic on rung 50 has updated the `Alarm_Active` bit. If an alarm condition develops, rung 10 observes the stale false state throughout the current scan and permits continued production operation. Only on the next scan cycle, after rung 50 has set the alarm bit, does rung 10 observe the true state and inhibit production. This one-scan delay typically proves inconsequential for alarm annunciation but could violate safety requirements if used for critical interlocks. Best practice dictates placing safety-critical logic at the top of the program so that it evaluates immediately after input acquisition, minimizing latency between input transition and output response.

Timer instructions encapsulate more complex behavior than simple Boolean contacts and coils. A TON (Timer On-Delay) instruction contains three components: a preset value specifying target elapsed time, an accumulated value tracking current elapsed time, and enable/done output bits indicating timer state. When the timer's input rung evaluates true, the accumulated value increments by the elapsed time since the previous scan—typically the scan time itself measured in milliseconds. When accumulated time reaches or exceeds the preset, the done bit energizes. If the input rung goes false before timeout completion, the accumulated value resets to zero. This behavior models an electromagnetic time-delay relay where the coil must remain continuously energized for the full preset duration before contacts transition.

Counter instructions implement similar accumulation semantics but respond to discrete count-up events rather than continuous time. A CTU (Count-Up) instruction increments its accumulated value on each false-to-true transition of its count input. The processor detects transitions by comparing the current scan's input state against the previous scan's state stored in a shadow bit. When the current state reads true and the previous state reads false, a transition occurred, incrementing the accumulator. This edge-detection mechanism allows counters to respond to input events shorter than the scan cycle, provided those events remain stable long enough for input filtering to register them. A 1-millisecond pulse filtered to 2 milliseconds produces one clean edge per occurrence; a 0.1-millisecond pulse disappears entirely.

The data table organization supporting these instructions varies by PLC family but follows common principles. Allen-Bradley CompactLogix systems employ a tag-based architecture where programmers define symbolic names with associated data types: `BOOL` for single bits, `DINT` for 32-bit signed integers, `REAL` for IEEE-754 floating-point values, or complex structures like `TIMER` containing preset, accumulated, enable, and done members. These tags map to physical memory addresses transparently—the programmer references `Motor_Start_Button` without knowing whether it occupies byte 0x2400 bit 5 or byte 0x3C00 bit 2. Siemens S7 systems organize memory into discrete blocks: I (input image), Q (output image), M (memory bits), T (timers), C (counters), and DB (data blocks for structured data). Modicon systems use register-based addressing with explicit numeric addresses: `%I0.0.7` references input module 0 slot 0 terminal 7, while `%MW100` references memory word 100.

Program execution flow control extends beyond simple rung-by-rung sequential evaluation through jump, subroutine call, and conditional execution constructs. A JMP (Jump) instruction with an associated LBL (Label) allows the processor to skip rung evaluation between the jump source and label destination when the jump's input conditions evaluate true. This provides conditional execution: entire program sections activate only when specific mode bits enable them. Subroutine instructions partition large programs into manageable functional units: a main program calls subroutines passing parameters, the subroutine executes its ladder logic, then returns control to the main program. This modular structure improves program organization and enables code reuse across similar machine sections.

Immediate I/O instructions bypass the scan cycle's synchronized input acquisition and output update phases, reading or writing physical I/O terminals directly during program execution. An IIM (Immediate Input with Mask) instruction forces the processor to execute an unscheduled backplane read transaction, copying specified input module terminals into the input image table mid-scan. An IOM (Immediate Output with Mask) writes specific output bits directly to physical terminals without waiting for the output update phase. These instructions sacrifice determinism for reduced latency: a critical stop input can halt machine motion within microseconds of assertion rather than waiting 20 milliseconds for the next scan's input acquisition. Overuse of immediate I/O fragments the deterministic scan model, introducing variable execution times and complicating program verification.

## 3. High-Performance Optimization & Failure Modes

Scan time optimization begins with instruction selection and ordering. Boolean contact examinations execute in 0.5 microseconds; complex mathematical functions consume 50 microseconds. A program performing trigonometric calculations every scan to compute servo position trajectories wastes processing bandwidth if those calculations need updating only when the operator adjusts setpoints. Conditional execution structures surrounding computationally expensive operations—evaluating them only when input data changes—reduce average scan time significantly. Similarly, ordering frequently false rungs early in parallel branches allows the processor to short-circuit evaluation: if the first parallel branch evaluates true, subsequent parallel branches never execute, saving time.

Memory access patterns influence performance in subtle ways. Although PLCs lack cache hierarchies like general-purpose processors, localized data references exhibit better performance than scattered accesses due to memory controller burst-mode behavior. Structuring programs to process related I/O points and data table elements contiguously—handling all conveyor one logic before jumping to conveyor two—exploits these microarchitectural efficiencies. The effect measures only microseconds per scan but accumulates over thousands of rung evaluations.

Scan time determinism requirements constrain communication bandwidth allocation. The communication service phase budgets fixed time regardless of actual network traffic: if Ethernet/IP messages arrive faster than the allocated service window can process them, incoming packets queue in the module's receive buffer. Under extreme network load, these buffers overflow, causing message loss and HMI timeout faults. Proper network design segregates time-critical I/O traffic from bulk data transfers: dedicated device-level networks using producer-consumer models handle real-time I/O updates, while slower plant-level networks transport HMI data, recipes, and historical trends. This layered architecture prevents high-volume SCADA polling from disrupting deterministic control loop execution.

Watchdog timer configuration balances safety against false-trip risk. Setting the watchdog timeout to 50 milliseconds provides tight protection against processor lockup but may false-trip if a legitimate computational burst momentarily extends scan time beyond 50ms. Setting it to 500 milliseconds tolerates occasional scan time spikes but delays fault detection. Best practice involves measuring worst-case scan time under all foreseeable conditions—maximum I/O count, heaviest computational load, peak communication traffic—then setting the watchdog timeout to 150% of this measured maximum. This margin accommodates statistical variation while ensuring rapid fault detection if the processor truly hangs.

Input signal conditioning failures manifest as intermittent or erratic input states. A proximity sensor with failing output transistors may produce pulses that straddle the input module's voltage threshold, causing rapid true/false oscillations as the module's hysteresis band interprets noise as legitimate transitions. Software debouncing mitigates this: requiring an input to maintain consistent state for 3 to 5 consecutive scans (30 to 50 milliseconds) before accepting the transition filters out noise bursts while still responding adequately to legitimate process events. This technique proves especially valuable for mechanical limit switches exhibiting contact bounce, which can generate dozens of transitions over 10 to 20 milliseconds during physical actuation.

Output module failure modes depend on switching technology. Relay outputs fail shorted or open: shorted contacts weld together from arc erosion, continuously energizing the output regardless of program state; open circuits result from coil burnout or mechanical fracture, preventing output energization. Transistor outputs typically fail shorted due to MOSFET junction breakdown from inductive voltage spikes. Proper load suppression—flyback diodes across inductive loads for DC circuits, snubbers across AC loads—extends output module lifespan dramatically. Under-specifying output current ratings accelerates failures: continuous operation at 90% of rated current generates excessive heat, degrading semiconductor junctions and reducing mean time between failures from years to months.

Memory corruption risks arise primarily during program downloads or online edits. If the programming terminal loses connection mid-download, the processor's program memory may contain incomplete logic structures—rungs referencing timer structures that were never created, jump instructions targeting non-existent labels. Most modern PLCs implement transactional program download protocols: the new program uploads entirely into shadow memory, checksum validation confirms integrity, then a single atomic operation switches the processor to execute from the new memory space. This transactional model prevents partially corrupted programs from executing, but processors running legacy protocols may require manual validation after every program modification.

Battery-backed SRAM used in older PLC models introduces data retention hazards. When backup battery voltage drops below threshold—typically after 3 to 5 years—the processor issues low-battery warnings but continues operating. If power fails before battery replacement, all program memory and data table contents vanish. Best practice involves scheduling preventive battery replacements every 2 years and maintaining backup copies of program and data table contents on the programming terminal. Contemporary PLCs employ flash memory for program storage and capacitor-backed SRAM or FRAM for data table retention, eliminating battery maintenance requirements entirely while providing weeks of data retention during power outages.

Scan time overruns trigger system faults requiring careful diagnosis. If scan time exceeds watchdog timeout, the processor faults, halts output updates, and enters a safe state. Intermittent overruns—occurring only when specific process conditions combine—prove particularly troublesome. Diagnostic techniques include instrumenting the program with timestamp markers: setting an output bit at the start of suspect program sections, clearing it at completion, and monitoring output energization duration with an oscilloscope reveals which program sections consume excessive time. Alternatively, enabling the processor's built-in performance monitoring logs captures per-rung execution times, identifying computational hotspots demanding optimization or offloading to specialty function modules.

Deterministic real-time constraints impose fundamental limits on PLC application domains. Motion control applications requiring sub-millisecond position loop update rates exceed standard PLC capabilities. Although specialty motion modules containing dedicated processors and FPGA position loop controllers integrate into PLC backplanes, the core scan-cycle-based control architecture cannot directly servo motor commutation or interpolated path planning at kilohertz rates. Similarly, high-speed data acquisition sampling analog inputs at 100kHz requires dedicated data acquisition modules with local memory buffers; the main PLC processor retrieves stored waveforms as bulk transfers during the scan cycle rather than processing individual samples in real time.

Network-distributed I/O topologies extend physical I/O capacity beyond backplane limitations but introduce network transmission latency into the control loop. Ethernet/IP or Profinet I/O networks update remote I/O modules synchronously with the scan cycle: during input acquisition, the processor broadcasts a request to all network-attached input modules, collects responses, then proceeds to program execution. Network propagation delays, switch forwarding latency, and module response time accumulate to 1 to 5 milliseconds depending on network loading and topology. This latency adds directly to scan time, potentially doubling total loop delay compared to backplane-mounted I/O. Compensating for this delay requires either accepting increased response time or migrating time-critical I/O to local backplane slots while leaving less critical I/O distributed across the network.

Safety-rated PLC systems implement redundancy and fault detection mechanisms beyond standard control processors. Dual-channel architectures execute identical programs on two independent processors, continuously cross-comparing outputs to detect discrepancies indicating hardware faults. Discrepancy detection triggers immediate transition to a safe state—de-energizing all outputs—within one scan cycle. These safety controllers employ specialized I/O modules with dual input circuits monitoring each sensor through independent optoisolators and requiring both channels to agree before presenting an input as valid. Output modules implement force-guided relay contacts: mechanical linkage ensures that if the normally-open contact welds shut, the normally-closed contact cannot close, providing hardware verification that fail-safe circuit states remain achievable. Programming these systems requires adherence to IEC 61131-3 safety extensions and third-party certification to SIL 2 or SIL 3 integrity levels, imposing formal verification and testing disciplines absent from standard PLC development workflows.
