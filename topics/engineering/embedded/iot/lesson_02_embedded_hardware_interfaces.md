# Lesson 2: Embedded Hardware Interfaces

## 1. First-Principles Intuition & Invariants

The boundary between a microcontroller and the external world is where embedded systems become tangible. A sensor wire, a relay coil, a display pixel—these are not abstractions. They are electrical phenomena measured in volts, currents flowing in amperes, timing measured in nanoseconds. The embedded engineer's craft is to translate the digital abstraction of a CPU—ones and zeros strobing through silicon at gigahertz frequencies—into meaningful interaction with analog phenomena, mechanical devices, and data streams that operate at vastly different timescales and voltage levels.

This translation problem defines the entire discipline of hardware interfaces. At its core, an embedded system must accomplish three fundamental tasks: it must sense the external world through analog-to-digital conversion and serial protocols; it must compute decisions based on that sensed state; and it must actuate changes to the external world through digital outputs, pulse-width modulation, or serial communication back to actuators and displays. The quality of an embedded product—whether a medical device, an industrial controller, or an IoT sensor node—is determined almost entirely by how well the engineer understands and implements these three layers of interface.

The CPU itself knows nothing about the real world. At the silicon level, a processor executes instructions that manipulate register contents and memory locations. To interface with external hardware, the processor uses a technique called memory-mapped input/output (MMIO). Every peripheral—whether a UART controller, an SPI master, a GPIO block, or an ADC—occupies a reserved range of addresses in the processor's address space. When firmware writes to a specific memory address, instead of updating RAM, the write operation is intercepted by the peripheral's control logic. Similarly, reads from certain addresses return the current state of external pins or sensor readings rather than memory contents. This unified address space approach, inherited from the design of early minicomputers in the 1960s, remains the dominant paradigm in microcontroller design because it is conceptually simple and requires minimal additional instruction set complexity.

The real challenge in embedded hardware interfaces emerges from the mismatch between the CPU's capabilities and the constraints of the physical world. A microcontroller might execute instructions every 10 nanoseconds (for a 100 MHz ARM Cortex-M4), yet a mechanical button press creates electrical noise that settles over hundreds of milliseconds. An ADC might have 12 bits of resolution, implying precision to one part in 4096, yet real-world sensors have temperature drift, nonlinearity, and noise that often dominate the quantization error. A serial communication link must synchronize data between two independent clock domains—a synchronization problem that has no perfect solution, only careful engineering approximations. These mismatches demand that the embedded engineer develop intuition about electrical constraints, timing budgets, noise margins, and failure modes.

The invariants that govern hardware interfaces are rooted in physics and information theory. First, every signal transition takes time. No pin voltage changes instantaneously. A GPIO output cannot drive unlimited current—it has a maximum source and sink capability specified in the datasheet. Second, all real-world signals contain noise. A sensor reading is never "the true value"; it is the true value plus thermal noise, quantization noise, and systematic error. Third, timing is expensive in embedded systems. Every microsecond spent blocking on I/O is a microsecond not spent servicing other tasks. Fourth, power is always finite. A battery-powered IoT device might have only milliampere-hours of capacity; every interaction with the physical world—sensing, communication, actuation—consumes energy that must be accounted for in the system power budget.

These invariants shape every design decision. The choice between polling and interrupts, the selection of ADC resolution and sampling rate, the decision to use DMA or CPU-driven transfers, the configuration of I/O voltage levels and termination resistances—all of these arise from the tension between the CPU's capabilities and the physical world's constraints. Understanding hardware interfaces means internalizing these tradeoffs and learning to navigate them systematically.

## 2. Core Architecture & Mechanics

### GPIO and Digital I/O Foundations

The simplest hardware interface on any microcontroller is the General-Purpose Input/Output pin. A GPIO pin is a bidirectional electrical contact that can be configured to sense external voltages (input mode) or drive voltage onto a wire (output mode). At the silicon level, a GPIO pin is implemented as a multiplexer that selects between the core logic (for output) and external pin state (for input), combined with protection logic and drive strength configuration.

Consider the architecture of a typical GPIO block on an ARM Cortex-M microcontroller such as the STM32H7 series. Each GPIO port contains 16 pins, labeled PA0 through PA15 (or PB0–PB15 for port B, etc.). The hardware is controlled through a set of memory-mapped registers, each 32 bits wide. The Mode Register (MODER) contains two bits per pin, selecting whether that pin is input (00), output (01), alternate function (10), or analog (11). For output pins, the Output Type Register (OTYPER) selects between push-pull (0) and open-drain (1) output. The Output Speed Register (OSPEEDR) controls the slew rate—how fast the output voltage transitions. This seemingly redundant feature exists because controlling transition speed reduces electromagnetic interference (EMI) emissions and allows the circuit designer to tune high-speed signals.

The key registers for GPIO operation are the Input Data Register (IDR), which samples the current electrical state of all pins on the port, and the Output Data Register (ODR), which directly controls output pins in push-pull mode. However, direct read-modify-write of the ODR is problematic in real-time systems. If an interrupt fires between the read and the write, another task might modify the ODR, causing a race condition. For this reason, most microcontrollers provide atomic bit-manipulation registers. The STM32H7, for instance, provides the BSRR (Bit Set/Reset Register), which allows setting or clearing individual bits in a single atomic write operation. Writing to bits [15:0] of BSRR sets the corresponding ODR bits, while writing to bits [31:16] clears them. This eliminates race conditions in interrupt-driven GPIO manipulation.

The output drive strength, controlled through the OSPEEDR register and related analog output control registers, is not merely an optimization; it directly affects circuit behavior. When a GPIO pin transitions from low to high, it charges the parasitic capacitance of the PCB trace and any external load. A faster slew rate delivers more current during the transition, charging the capacitance more quickly. However, faster transitions also radiate more electromagnetic energy, potentially interfering with sensitive analog circuits or radio receivers operating nearby. Furthermore, high slew rates require larger internal transistors in the output stage, consuming more silicon area and increasing leakage power. The embedded engineer must balance these considerations based on system requirements.

Input pins present their own subtleties. When sampling a GPIO input, the read operation captures the instantaneous voltage on the pin and converts it to a digital bit—typically using a comparator that transitions at the midpoint between the valid low voltage (0 V to 0.8 V for most microcontrollers) and the valid high voltage (2.0 V to 3.3 V). However, if the voltage is transitioning between these states at the instant of sampling—a condition called metastability—the result is undefined. More practically, real-world signals are noisy. A mechanical button press, for instance, produces electrical oscillation or "bounce" as the mechanical contacts separate and reconnect over a period of 10–20 milliseconds. A GPIO input sampled during this bouncing period will read as alternating 0s and 1s even though the user intended a single button press. To solve this problem, firmware must implement debouncing, typically by sampling the input multiple times over a period longer than the expected bounce duration, confirming that the signal has stabilized before treating the input as valid.

### Serial Communication Protocols: UART, SPI, and I2C

Embedded systems rarely operate in isolation. They must communicate with sensors, actuators, displays, and other microcontrollers. The three most common serial communication protocols are UART, SPI, and I2C, each designed for different use cases and tradeoffs.

UART (Universal Asynchronous Receiver-Transmitter) is the oldest and simplest. It transmits data serially, one bit at a time, over a single wire (plus ground return). The protocol is asynchronous, meaning there is no shared clock signal between the transmitter and receiver; instead, both sides agree on a baud rate (such as 9600 or 115200 bits per second), and timing is maintained by each side's independent oscillator. This independence makes UART robust for communication over long distances where distributed clocks would be impractical, and it historically enabled terminal communication between computers and peripherals. However, the requirement for independent timing creates a tradeoff: both sides must operate their oscillators to very close tolerance, typically within 5% of the nominal rate, or communication fails.

The UART framing format encapsulates each byte of data within start, stop, and optional parity bits. A low-to-high transition on the data line signals the start of a byte; the transmitter then sends eight data bits (least-significant bit first), optionally a parity bit for error detection, and one or more stop bits (high). The receiver detects the falling edge of the start bit, waits 1.5 bit times (allowing the start bit to settle), and then samples the data line every bit period thereafter. This timing is maintained by an internal timer running at a multiple of the desired baud rate, typically 16 times the baud rate to allow sampling in the middle of each bit period. If the timing drifts, successive bits are sampled later in their transmission windows, and after eight bits, the error has accumulated enough to cause misalignment.

UART is asynchronous and therefore cannot sustain high data rates over long distances without careful clock design. For applications requiring higher bandwidth or better clock tolerance, SPI (Serial Peripheral Interface) provides a synchronous alternative. SPI uses four signals: a clock (SCK) generated by the master device, chip select (CS) to activate a particular slave, and two data lines (MOSI for master-to-slave, MISO for slave-to-master). Because the clock is generated and transmitted along with the data, there is no requirement for clock synchronization; the slave simply samples the data line on clock edges. SPI is inherently faster than UART—it can operate at 10 MHz, 50 MHz, or even higher—and the protocol is extremely simple. On each clock pulse, one bit is transmitted and one bit is received; full-duplex communication is possible.

However, SPI's simplicity comes with a tradeoff: there is no addressing mechanism. Every SPI slave requires a dedicated chip-select line from the master. If a system needs to communicate with ten different SPI devices, the master needs ten separate CS outputs. This limitation makes SPI unsuitable for multi-device networks. The protocol also requires a dedicated clock line, consuming an additional GPIO or PCB trace. Furthermore, SPI has multiple modes defined by the clock polarity (CPOL) and clock phase (CPHA). In mode 0 (CPOL=0, CPHA=0), the clock is normally low, and data is sampled on the rising edge. In mode 2 (CPOL=1, CPHA=1), the clock is normally high, and data is sampled on the falling edge. If the master and slave are configured with mismatched modes, data corruption results. This flexibility, intended to accommodate different device designs, often becomes a source of subtle bugs in real-world systems.

I2C (Inter-Integrated Circuit) addresses SPI's multi-device limitation through a different architectural approach. I2C uses only two wires—a clock line (SCL) and a data line (SDA)—shared among all devices on the bus. All drivers use open-drain output stages; this means they can only pull the line low, not drive it high. A pull-up resistor (typically 4.7 kΩ) on each line holds it at the bus voltage (3.3 V or 5 V) when no device is driving it low. This wired-AND logic allows multiple devices to coexist on the same two wires. Communication proceeds through a structured protocol: the master generates START and STOP conditions by manipulating the SDA line while SCL is high (conditions that violate the normal bit timing and are recognized as protocol markers). After START, the master sends a seven-bit slave address followed by a read/write bit. All slaves listen to the address; the one whose address matches pulls SDA low during the ACK bit period, confirming its presence. Data bytes then flow between master and slave, each followed by an ACK from the receiver.

I2C's shared-bus architecture makes it ideal for systems with multiple sensors and peripheral ICs. Its two-wire simplicity requires minimal PCB routing. However, this simplicity comes at a cost: speed. I2C typically operates at 100 kbit/s (standard mode) or 400 kbit/s (fast mode), compared to SPI's multi-megabit rates. The reason is that I2C's timing relies on capacitive charging of the bus lines through pull-up resistors. When a device releases the bus, the pull-up resistor charges the capacitance of the PCB trace and all connected devices; the time constant is determined by the product of the pull-up resistance and the bus capacitance. To operate at faster rates requires smaller pull-up resistances, which then cause excessive current draw when the bus is held low, generating heat and consuming power. At 100 kbit/s, I2C is practical for most embedded systems. At faster rates, signal integrity degrades rapidly, making reliable communication difficult without careful PCB layout and termination.

### Analog-to-Digital and Digital-to-Analog Conversion

The boundary between the analog and digital worlds is mediated by converters. An ADC (Analog-to-Digital Converter) transforms a continuous analog voltage into a discrete digital number; a DAC (Digital-to-Analog Converter) performs the inverse transformation. These components are fundamental to any embedded system that must interface with analog sensors or actuators.

An ideal ADC with N bits of resolution divides the input voltage range into 2^N discrete levels. For a 12-bit ADC with a 3.3 V reference, each discrete level corresponds to 3.3 V ÷ 4096 ≈ 0.81 mV. The ADC samples the input voltage at a specific instant and outputs the index of the nearest quantization level. The difference between the actual analog voltage and the nearest quantization level is called quantization error; it is uniformly distributed between −0.5 LSB and +0.5 LSB (where LSB is the Least Significant Bit, the voltage corresponding to one digital count). For a 12-bit 3.3 V converter, this corresponds to ±0.4 mV of quantization uncertainty. If the analog input is a noisy signal, the quantization error combines with the signal noise in a complex way; generally, if the signal noise is larger than the quantization step, the quantization error becomes less visible and the effective resolution is limited by the signal noise, not the ADC resolution.

The most common ADC architecture in microcontrollers is the successive approximation register (SAR) converter. A SAR-ADC operates like a binary search algorithm. It contains a comparator that compares the input voltage against a reference voltage generated by a digital-to-analog converter (DAC). The SAR control logic starts with a guess in the middle of the reference range (digital output = 2^(N-1)); if the input is higher, the DAC output is lowered and the control logic guesses higher; if the input is lower, the DAC output is raised and the control logic guesses lower. This process repeats, halving the search space at each iteration, until the exact digital value is found. Crucially, this search process requires N clock cycles for an N-bit converter. A 12-bit SAR-ADC requires 12 clock cycles per conversion. If the ADC clock runs at 10 MHz, a single 12-bit conversion takes 1.2 microseconds, allowing approximately 833,000 conversions per second maximum.

However, this theoretical maximum assumes continuous conversions with no dead time. In practice, real ADCs include an acquisition time—a delay required for the input to settle after the previous conversion, while the sample-and-hold capacitor charges to the input voltage. This acquisition time depends on the source impedance of the analog circuit driving the ADC input. If a 10 kΩ resistor drives the ADC input, the source impedance is 10 kΩ. The time for the input to settle to within one LSB is approximately 7 times the RC time constant (R × C_ADC), where C_ADC is the ADC's internal sampling capacitor (typically 10–100 pF). A well-designed analog interface includes a buffer amplifier with very low output impedance, reducing acquisition time to microseconds or less. Without buffering, acquisition time dominates the conversion cycle, limiting practical sampling rates.

Digital-to-Analog conversion is simpler in principle but faces different tradeoffs. A DAC outputs a voltage proportional to the digital input code. The simplest DAC is a resistor ladder network, where each bit position is represented by a resistor scaled by powers of two. Summing resistors combine the contributions of all bits, producing an output proportional to the digital input. However, resistor-ladder DACs require extremely precise resistor matching; a 1% error in a resistor dedicated to the most significant bit causes a 1% error in the output. This sensitivity to component tolerances limits the practical resolution of resistor-ladder DACs to about 8 bits without expensive precision components.

Modern microcontroller DACs typically use charge-redistribution or current-steering architectures. These convert the digital code into a capacitor charge or current source proportional to the digital value. A charge-redistribution DAC uses binary-weighted capacitors; successive approximation switches connect each capacitor or a divided version to the output node to build up the desired voltage. These methods are more tolerant of component matching errors because matching is easier to achieve than absolute accuracy. Modern DACs integrated into microcontrollers typically achieve 8–12 bits of resolution and can output microvolts of noise, sufficient for most embedded applications.

A critical consideration for both ADCs and DACs is the reference voltage. The ADC and DAC use this reference to define the meaning of each digital code. For a 12-bit ADC with a 3.3 V reference, a digital output of 2048 corresponds to approximately 1.65 V input. If the reference voltage drifts due to temperature changes or power supply noise, the ADC and DAC outputs drift correspondingly. High-precision systems often employ a dedicated voltage reference IC with temperature stability better than 50 ppm/°C (parts per million per degree Celsius) and noise filtering to minimize sensitivity to power supply ripple.

### Interrupt Handling and Real-Time Constraints

The CPU executes instructions sequentially, one per clock cycle (approximately—pipelining complicates this picture, but the sequential model holds conceptually). If the CPU were forced to continuously poll an external device to check for new data or status changes, the CPU would waste vast amounts of time on non-productive polling. For instance, a UART might receive a new byte every 100 microseconds at 9600 baud, but the CPU is executing instruction cycles in nanoseconds. Polling would require checking the UART status register millions of times between actual data arrivals, consuming CPU cycles without achieving anything.

Interrupts solve this problem by inverting the control flow. Instead of the CPU polling peripherals, peripherals notify the CPU when an event occurs—a new byte has arrived on the UART, an ADC conversion is complete, a GPIO pin has changed state. When an interrupt occurs, the CPU immediately suspends its current execution, saves the processor state, and branches to an interrupt handler routine (also called an Interrupt Service Routine or ISR). When the ISR completes, the saved state is restored and normal execution resumes.

The mechanism for interrupt handling is defined by the CPU architecture. In ARM Cortex-M microcontrollers, interrupts are prioritized using the Nested Vectored Interrupt Controller (NVIC). Each interrupt source has a priority level, typically represented as an integer from 0 (highest priority) to 255 (lowest priority). When multiple interrupts are pending simultaneously, the NVIC prioritizes them and services the highest-priority interrupt first. Critically, a higher-priority interrupt can interrupt a lower-priority ISR that is currently executing. This nesting allows responsive handling of high-priority real-time events.

The NVIC is configured through memory-mapped registers in the microcontroller's system control space. To enable an interrupt, the firmware sets a bit in the Interrupt Set-Enable Register (ISER); to disable an interrupt, it sets a bit in the Interrupt Clear-Enable Register (ICER). The interrupt priority is set in the Interrupt Priority Registers (IPR). For example, enabling the UART0 receive interrupt on an STM32L4 series microcontroller involves writing to the appropriate ISER register and then configuring the UART0 peripheral to generate an interrupt when a byte is received.

However, interrupts introduce significant complexity into embedded software design. The ISR executes asynchronously with respect to the main program flow; it can interrupt execution at any point in the main code. Any data structure accessed by both the main code and an ISR must be protected against race conditions. If the main code reads a multi-byte variable (such as a 16-bit integer on an 8-bit processor) and an ISR modifies that variable between the reads of its high and low bytes, the main code observes a corrupted value. The standard solution is to disable interrupts during access to shared data, though this introduces latency and complicates the code.

A more insidious problem is priority inversion. Suppose a high-priority ISR requires access to a shared resource (a buffer or a state variable) that is currently locked by lower-priority code running in the main program. The high-priority ISR must wait for the lower-priority code to release the lock, effectively reducing the high-priority ISR to the priority of the lower-priority code. If multiple lower-priority activities are also waiting for the resource, the high-priority ISR might not run for several milliseconds, violating the real-time constraint that demanded high priority in the first place. Solutions include priority inheritance (temporarily elevating the priority of the code holding the lock) or careful architectural design to minimize contention for shared resources.

The total time from when an interrupt occurs to when the ISR begins executing is called interrupt latency. The latency includes the time for the current instruction to complete, the time to save processor state (push registers onto the stack), and the time to fetch the first instruction of the ISR. On modern ARM Cortex-M processors, interrupt latency is typically 12–24 clock cycles, corresponding to 120–240 nanoseconds on a 100 MHz processor. However, if the current instruction is a long operation (such as a multi-cycle multiply or a memory access that misses the cache), latency can be longer.

Interrupt latency can be further extended by interrupt masking, where the processor disables interrupts globally or selectively disables certain priority levels during critical sections. If the main program disables interrupts for an extended period to protect a large critical section, even a high-priority interrupt cannot preempt execution until the critical section completes. This trades determinism in the critical section for unpredictability in interrupt response time. Modern architectures mitigate this through nested vectored interrupt controllers (NVIC) that support priority grouping and preemption, allowing higher-priority interrupts to preempt lower-priority ISRs without disabling all interrupts. The practical consequence is that ISR design must account not only for its own execution time but also for the worst-case latency introduced by all higher-priority or equal-priority interrupts that could delay its execution. In systems with multiple interrupt sources, the engineer must construct a timing analysis that accounts for interrupt nesting, preemption, and blocking to guarantee that all real-time deadlines are met under worst-case conditions.

Effective interrupt-driven embedded systems require disciplined architectural decisions: minimize ISR duration by deferring non-urgent work to the main loop or a task scheduler, protect shared data with atomic operations or brief critical sections, analyze interrupt frequencies and execution times to verify that the processor has sufficient bandwidth, and validate the system under worst-case interrupt load to confirm that latency requirements are satisfied. When designing hardware interfaces, choose peripherals that offer hardware buffering (such as FIFOs in UARTs or DMA controllers) to reduce interrupt frequency and relax timing constraints. When implementing ISRs, measure their execution time on the target hardware using GPIO toggling or logic analyzers, and verify that the sum of all interrupt processing time plus main-loop execution time remains below the processor's capacity. The result is a system that responds to external events with predictable latency and maintains correctness under all operating conditions.
