# Operational Verification Labs: Firmware Engineering

## Objective & Operational Lab Setup

Firmware engineering demands rigorous operational verification protocols that bridge the gap between hardware constraints and software correctness. Unlike application-layer software development, where abstraction layers provide safety nets, firmware operates in a regime of strict determinism: a single missed interrupt, an incorrectly configured clock domain, or a misaligned DMA transfer can render an entire embedded system inoperable. This laboratory guide establishes a comprehensive verification methodology rooted in the physical realities of microcontroller execution—register-level state machines, timing-critical peripheral interactions, and memory-constrained real-time operating environments.

The operational verification workflow presented here proceeds from foundational firmware primitives through parametric boundary analysis and culminates in stress testing under adversarial conditions. Each exercise grounds theoretical firmware concepts in tangible hardware behavior, requiring practitioners to physically observe execution artifacts through JTAG debug probes, logic analyzers, and oscilloscope measurements. This approach mirrors the engineering reality that firmware correctness cannot be proven solely through simulation; it must be validated against the electrical characteristics of silicon, the propagation delays of communication buses, and the interrupt latency profiles of real microcontroller architectures.

The laboratory environment centers on the ARM Cortex-M4 microcontroller architecture, specifically the STM32F407VGT6 reference platform, which provides representative peripheral complexity, memory-mapped I/O structures, and nested vectored interrupt controller (NVIC) behavior found across industrial embedded systems. Practitioners must provision a hardware workbench comprising the STM32F4 Discovery board with on-board ST-LINK/V2 debug interface, a Saleae Logic Pro 8 or equivalent multi-channel logic analyzer capable of 100 MS/s sampling, a Rigol DS1054Z oscilloscope with at least 50 MHz analog bandwidth for observing edge transitions and clock signal integrity, and a UART-to-USB bridge adapter for protocol-level communication verification. Software tooling consists of the ARM GNU embedded toolchain (arm-none-eabi-gcc version 12.2 or later), OpenOCD for JTAG/SWD interfacing, GDB with ARM Cortex-M extensions, and STM32CubeMX for peripheral initialization code generation. All firmware artifacts produced in these exercises compile to bare-metal ELF binaries with full symbol tables enabled, permitting cycle-accurate debugging and memory inspection at arbitrary execution points.

The verification methodology adheres to a three-layer validation hierarchy. At the lowest layer, register-level correctness confirms that peripheral configuration registers contain expected bitfield values after initialization sequences, detected through GDB memory examination or live register dumps. The intermediate layer establishes timing compliance, where oscilloscope measurements verify that GPIO toggle rates, UART baud rate generation, and SPI clock frequencies conform to datasheet specifications within tolerance bands. The highest layer validates functional integration, confirming that multi-peripheral interactions—such as ADC-triggered DMA transfers writing to UART transmission buffers—execute atomically without race conditions or priority inversion anomalies. Each exercise documents expected waveforms, register states, and quantitative metrics, providing practitioners with falsifiable verification criteria that distinguish correct firmware behavior from subtle malfunctions.

The analytical framework for firmware verification extends beyond functional correctness to encompass resource utilization boundaries. Flash memory consumption, SRAM allocation patterns, stack depth profiling under worst-case interrupt nesting, and CPU cycle budgets for critical interrupt service routines all constitute measurable operational parameters. These exercises employ empirical instrumentation techniques: inserting GPIO toggle instructions at ISR entry and exit points to measure execution duration on an oscilloscope, analyzing MAP files generated by the linker to identify memory fragmentation, and using ARM CoreSight debug infrastructure to capture instruction trace streams during exception handling. The practitioner emerges from this laboratory sequence with a systematic methodology for characterizing firmware performance under quantifiable constraints, enabling evidence-based optimization decisions rooted in physical measurement rather than speculative tuning.

## Exercise 1: Foundational Practical Implementation

The foundational firmware implementation exercise establishes a complete bare-metal execution environment from first principles, bypassing vendor-provided Hardware Abstraction Layers (HALs) to expose the raw register-level mechanisms governing microcontroller operation. This approach constructs a minimal viable firmware image that configures the system clock tree, initializes a single GPIO peripheral for visual confirmation, and implements a polled delay loop calibrated against the processor's clock frequency. The objective is to produce a blinking LED firmware artifact while simultaneously verifying each hardware configuration step through direct register inspection, thereby cementing the practitioner's understanding of the Cortex-M4 startup sequence, memory-mapped peripheral access patterns, and clock distribution architecture.

Begin by establishing the STM32F407 linker script, which defines the physical memory layout governing firmware execution. Create a file named `stm32f407vg.ld` with the following content, specifying the Flash ROM starting at address 0x08000000 with 1 MB capacity and SRAM starting at 0x20000000 with 128 KB capacity. The linker script must define the vector table placement at the Flash origin, ensuring the ARM Cortex-M4 boot sequence correctly loads the initial stack pointer and reset vector.

```ld
MEMORY
{
    FLASH (rx) : ORIGIN = 0x08000000, LENGTH = 1024K
    SRAM (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

ENTRY(Reset_Handler)

SECTIONS
{
    .isr_vector :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))
        . = ALIGN(4);
    } >FLASH

    .text :
    {
        . = ALIGN(4);
        *(.text)
        *(.text*)
        *(.rodata)
        *(.rodata*)
        . = ALIGN(4);
        _etext = .;
    } >FLASH

    .data :
    {
        . = ALIGN(4);
        _sdata = .;
        *(.data)
        *(.data*)
        . = ALIGN(4);
        _edata = .;
    } >SRAM AT>FLASH

    _sidata = LOADADDR(.data);

    .bss :
    {
        . = ALIGN(4);
        _sbss = .;
        *(.bss)
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } >SRAM

    . = ALIGN(8);
    _end = .;
}
```

The linker script's `.isr_vector` section ensures the vector table occupies the first memory region, a hardware requirement since the Cortex-M4 fetches the initial stack pointer from address 0x00000000 (aliased to 0x08000000 in Flash via the BOOT0 pin configuration) and the reset handler address from 0x00000004. The `.data` section configuration employs the `AT>FLASH` directive, instructing the linker to store initialized variable contents in Flash while reserving SRAM space, requiring the startup code to copy this data during boot. This arrangement reflects the physical reality that SRAM loses state during power cycles, necessitating initialization from non-volatile Flash storage.

Construct the vector table and startup code in `startup.c`, implementing the minimal Cortex-M4 boot sequence. The vector table must populate the initial stack pointer with the end of SRAM and define handler addresses for the Reset exception and all peripheral interrupts, even if unused handlers simply spin in infinite loops.

```c
#include <stdint.h>

extern uint32_t _estack;
extern uint32_t _sdata;
extern uint32_t _edata;
extern uint32_t _sidata;
extern uint32_t _sbss;
extern uint32_t _ebss;

void Reset_Handler(void);
void Default_Handler(void);

void NMI_Handler(void) __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
void MemManage_Handler(void) __attribute__((weak, alias("Default_Handler")));
void BusFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
void UsageFault_Handler(void) __attribute__((weak, alias("Default_Handler")));
void SVC_Handler(void) __attribute__((weak, alias("Default_Handler")));
void DebugMon_Handler(void) __attribute__((weak, alias("Default_Handler")));
void PendSV_Handler(void) __attribute__((weak, alias("Default_Handler")));
void SysTick_Handler(void) __attribute__((weak, alias("Default_Handler")));

__attribute__((section(".isr_vector")))
uint32_t vector_table[] = {
    (uint32_t)&_estack,
    (uint32_t)Reset_Handler,
    (uint32_t)NMI_Handler,
    (uint32_t)HardFault_Handler,
    (uint32_t)MemManage_Handler,
    (uint32_t)BusFault_Handler,
    (uint32_t)UsageFault_Handler,
    0,
    0,
    0,
    0,
    (uint32_t)SVC_Handler,
    (uint32_t)DebugMon_Handler,
    0,
    (uint32_t)PendSV_Handler,
    (uint32_t)SysTick_Handler,
};

void Reset_Handler(void) {
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;
    
    while (dst < &_edata) {
        *dst++ = *src++;
    }
    
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }
    
    extern int main(void);
    main();
    
    while (1);
}

void Default_Handler(void) {
    while (1);
}
```

The Reset_Handler implements the critical data initialization sequence that copies the `.data` section from Flash to SRAM and zero-initializes the `.bss` section. This sequence executes before the C runtime environment becomes valid, establishing the invariant that all global variables contain their initialized values before `main()` executes. The weak alias mechanism for exception handlers provides default implementations that trap into infinite loops, facilitating debug-time fault detection when unexpected exceptions fire.

Implement the main firmware logic in `main.c`, configuring the system clock to operate at 168 MHz from the external 8 MHz HSE crystal and initializing GPIO pin PD12 (the green LED on the STM32F4 Discovery board) for output operation. The clock configuration sequence involves enabling the HSE, configuring PLL multiplication and division factors to achieve 168 MHz, switching the system clock source to the PLL output, and setting appropriate Flash latency wait states for the increased clock frequency.

```c
#include <stdint.h>

#define RCC_BASE        0x40023800
#define RCC_CR          (*(volatile uint32_t *)(RCC_BASE + 0x00))
#define RCC_PLLCFGR     (*(volatile uint32_t *)(RCC_BASE + 0x04))
#define RCC_CFGR        (*(volatile uint32_t *)(RCC_BASE + 0x08))
#define RCC_AHB1ENR     (*(volatile uint32_t *)(RCC_BASE + 0x30))

#define FLASH_BASE      0x40023C00
#define FLASH_ACR       (*(volatile uint32_t *)(FLASH_BASE + 0x00))

#define GPIOD_BASE      0x40020C00
#define GPIOD_MODER     (*(volatile uint32_t *)(GPIOD_BASE + 0x00))
#define GPIOD_ODR       (*(volatile uint32_t *)(GPIOD_BASE + 0x14))

#define HSE_STARTUP_TIMEOUT 0x5000

static void SystemClock_Config(void) {
    RCC_CR |= (1 << 16);
    
    uint32_t timeout = HSE_STARTUP_TIMEOUT;
    while (!(RCC_CR & (1 << 17)) && timeout--);
    
    if (!(RCC_CR & (1 << 17))) {
        while (1);
    }
    
    FLASH_ACR = (1 << 10) | (1 << 9) | (1 << 8) | 5;
    
    RCC_PLLCFGR = (1 << 22) | (0 << 16) | (336 << 6) | (8 << 0);
    
    RCC_CR |= (1 << 24);
    while (!(RCC_CR & (1 << 25)));
    
    RCC_CFGR = (RCC_CFGR & ~0x3) | 0x2;
    while ((RCC_CFGR & 0xC) != 0x8);
}

static void GPIO_Init(void) {
    RCC_AHB1ENR |= (1 << 3);
    
    GPIOD_MODER &= ~(3 << (12 * 2));
    GPIOD_MODER |= (1 << (12 * 2));
}

static void delay_cycles(uint32_t cycles) {
    for (uint32_t i = 0; i < cycles; i++) {
        __asm__ volatile ("nop");
    }
}

int main(void) {
    SystemClock_Config();
    GPIO_Init();
    
    while (1) {
        GPIOD_ODR ^= (1 << 12);
        delay_cycles(8400000);
    }
    
    return 0;
}
```

The SystemClock_Config function implements a precise PLL configuration sequence targeting 168 MHz operation. The HSE oscillator requires startup time after enabling, necessitating the timeout-based polling loop that monitors the HSERDY bit in RCC_CR. The PLL configuration register employs specific multiplication and division ratios: the 8 MHz HSE input divides by 8 (PLLM field) to produce a 1 MHz PLL input, multiplies by 336 (PLLN field) to yield 336 MHz VCO frequency, then divides by 2 (PLLP field implied by bit 16 clear) to generate the final 168 MHz system clock. The Flash memory interface requires five wait states at 168 MHz operation in the 2.7-3.6V voltage range, configured through FLASH_ACR alongside enabling instruction and data caching. The GPIOD initialization enables the AHB1 peripheral clock gate for GPIO port D and configures pin 12 as a general-purpose output through the MODER register's two-bit field.

Compile the firmware using the ARM GNU embedded toolchain with explicit optimization and architecture flags that target the Cortex-M4 with hardware floating-point unit. Execute the following compilation sequence, generating both the ELF executable with full debug symbols and a binary image suitable for Flash programming:

```bash
arm-none-eabi-gcc -c -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -O2 -g3 -Wall -ffunction-sections -fdata-sections startup.c -o startup.o

arm-none-eabi-gcc -c -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -O2 -g3 -Wall -ffunction-sections -fdata-sections main.c -o main.o

arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 -T stm32f407vg.ld -Wl,--gc-sections -Wl,-Map=firmware.map startup.o main.o -o firmware.elf

arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
```

The compilation flags merit detailed examination. The `-mcpu=cortex-m4` directive selects the Cortex-M4 instruction set architecture, while `-mthumb` enforces Thumb-2 instruction encoding, the mandatory operating mode for Cortex-M processors. The floating-point ABI configuration `-mfloat-abi=hard -mfpu=fpv4-sp-d16` instructs the compiler to generate hardware FPU instructions using the FPv4-SP single-precision floating-point unit, passing floating-point arguments in FPU registers rather than emulating through software. The `-ffunction-sections -fdata-sections` flags combined with the linker's `--gc-sections` option enable dead code elimination, removing unused functions and data from the final image to minimize Flash consumption. The MAP file produced during linking documents precise symbol addresses and section sizes, essential for analyzing memory utilization.

Flash the firmware to the target using OpenOCD, which interfaces with the ST-LINK/V2 debug probe over USB and communicates with the STM32F407 via the Serial Wire Debug protocol. Create an OpenOCD configuration file named `stm32f4_discovery.cfg` with interface and target specifications:


Launch OpenOCD in a terminal, which initializes the debug connection and exposes a GDB server on TCP port 3333:


In a separate terminal, invoke GDB with the firmware ELF file and connect to the OpenOCD server, then halt the processor, erase Flash, program the new image, verify programming correctness, reset the processor, and resume execution:

```bash

```

The `compare-sections` command verifies that the Flash memory contents match the ELF file sections exactly, detecting programming errors caused by voltage instability or communication noise. Upon resuming execution, the green LED on GPIO PD12 should toggle at approximately 1 Hz, the rate determined by the delay_cycles function's iteration count scaled by the 168 MHz clock frequency.

Verify the clock configuration through direct register inspection. Halt the processor at an arbitrary point and examine the RCC and Flash controller registers to confirm correct PLL lock and wait state configuration:

```bash
(gdb) monitor halt
(gdb) x/1wx 0x40023800
0x40023800: 0x03038201

(gdb) x/1wx 0x40023808
0x40023808: 0x00000008

(gdb) x/1wx 0x40023C00
0x40023C00: 0x00000705
```

The RCC_CR value 0x03038201 confirms HSEON (bit 16), HSERDY (bit 17), PLLON (bit 24), and PLLRDY (bit 25) are all set, indicating successful HSE startup and PLL lock. The RCC_CFGR value 0x00000008 shows SWS bits 2-3 equal to binary 10, confirming the system clock source switched to PLL output. The FLASH_ACR value 0x00000705 verifies five wait states (bits 0-2) and enabled instruction cache (bit 9), data cache (bit 10), and prefetch (bit 8).

Measure the actual LED toggle frequency using an oscilloscope connected to GPIO PD12. Configure the oscilloscope for edge triggering on a rising edge with a timebase of 500 ms/division. The waveform should exhibit clean square-wave transitions with a measured period between 1.9 and 2.1 seconds, accounting for the imprecise delay_cycles implementation that experiences variation due to interrupt latency and branch prediction effects. Calculate the precise delay cycle count required for exactly 1 Hz operation by measuring the observed period and applying the correction factor: if the measured period is T seconds, the corrected cycle count equals 8400000 × (1.0 / T). Update the delay_cycles argument with this calibrated value and reprogram the firmware to achieve tighter frequency tolerance.

Extend the verification by inserting a breakpoint in the main loop and single-stepping through GPIO register writes while monitoring the logic analyzer. Connect a logic analyzer probe to GPIO PD12 and configure the capture for digital input with a 10 MS/s sample rate. In GDB, set a breakpoint on the ODR write instruction and step through execution:

```bash
(gdb) break *main+82
(gdb) continue
(gdb) stepi
```

After each `stepi` command, the logic analyzer trace should show the corresponding GPIO state transition occurring within nanoseconds of the instruction execution, confirming zero latency between the register write and the physical pin state change for memory-mapped I/O operations.

This foundational exercise establishes the complete bare-metal firmware development and verification workflow: linker script construction defining memory layout, startup code implementing the ARM Cortex-M4 boot sequence, register-level peripheral configuration, compilation with architecture-specific flags, Flash programming through debug probes, runtime register inspection via GDB, and physical signal measurement through oscilloscope and logic analyzer instrumentation. The practitioner now possesses the empirical methodology to validate every stage of firmware execution against hardware specifications, forming the foundation for advanced verification techniques in subsequent exercises.

## Exercise 2: Parameter Variation & Empirical Analysis

The second exercise transitions from foundational validation to systematic parameter variation, exploring how firmware behavior responds to clock frequency scaling, interrupt priority reconfiguration, and peripheral timing adjustments. This empirical analysis quantifies the operational boundaries of firmware timing constraints, characterizing the relationship between system clock frequency and achievable interrupt latency, measuring the impact of DMA transfer widths on memory bandwidth utilization, and establishing the maximum sustainable UART baud rates under varying CPU loading conditions. The verification methodology employs instrumented measurement techniques, inserting GPIO toggle sequences at strategic execution points to capture timing characteristics on an oscilloscope, while simultaneously analyzing memory transaction patterns through the ARM CoreSight debug infrastructure.

Construct a firmware testbench that implements a timer-triggered interrupt service routine (ISR) performing analog-to-digital conversion, transferring results via DMA, and transmitting formatted data over UART. This multi-peripheral integration scenario exposes timing interactions between DMA arbitration, interrupt nesting, and bus contention effects. Begin by extending the previous exercise's codebase with Timer 2 configuration for periodic interrupts at 1 kHz, ADC1 configuration for single-ended conversion on channel 0 (PA0), DMA2 stream 0 configuration for memory-to-memory ADC result transfer, and USART2 configuration for 115200 baud asynchronous serial transmission.

Implement the timer configuration in a dedicated initialization function that sets Timer 2 to generate update interrupts at precisely 1 kHz given the 168 MHz system clock with APB1 timer clock running at 84 MHz. The timer prescaler and auto-reload register values derive from the clock frequency division required to achieve the target interrupt rate:

```c
#define TIM2_BASE       0x40000000
#define TIM2_CR1        (*(volatile uint32_t *)(TIM2_BASE + 0x00))
#define TIM2_DIER       (*(volatile uint32_t *)(TIM2_BASE + 0x0C))
#define TIM2_SR         (*(volatile uint32_t *)(TIM2_BASE + 0x10))
#define TIM2_CNT        (*(volatile uint32_t *)(TIM2_BASE + 0x24))
#define TIM2_PSC        (*(volatile uint32_t *)(TIM2_BASE + 0x28))
#define TIM2_ARR        (*(volatile uint32_t *)(TIM2_BASE + 0x2C))

#define NVIC_ISER0      (*(volatile uint32_t *)0xE000E100)

#define RCC_APB1ENR     (*(volatile uint32_t *)(RCC_BASE + 0x40))

static void Timer2_Init(void) {
    RCC_APB1ENR |= (1 << 0);
    
    TIM2_PSC = 83;
    TIM2_ARR = 999;
    
    TIM2_DIER |= (1 << 0);
    
    NVIC_ISER0 |= (1 << 28);
    
    TIM2_CR1 |= (1 << 0);
}
```

The Timer 2 configuration employs a prescaler value of 83, which divides the 84 MHz APB1 timer clock by 84 (prescaler register value plus one), producing a 1 MHz timer clock. The auto-reload register value of 999 causes the timer to overflow after 1000 counts, generating an update interrupt at exactly 1 kHz. The update interrupt enable bit in TIM2_DIER arms the interrupt source, while setting bit 28 in NVIC_ISER0 enables the Timer 2 global interrupt in the Nested Vectored Interrupt Controller, corresponding to interrupt request number 28 in the STM32F407 vector table.

Configure ADC1 for single conversion mode triggered by software, sampling analog input channel 0 connected to GPIO PA0. The ADC configuration sequence enables the ADC peripheral clock, sets the common clock prescaler, configures conversion resolution, sampling time, and regular channel sequence:

```c
#define ADC1_BASE       0x40012000
#define ADC1_SR         (*(volatile uint32_t *)(ADC1_BASE + 0x00))
#define ADC1_CR1        (*(volatile uint32_t *)(ADC1_BASE + 0x04))
#define ADC1_CR2        (*(volatile uint32_t *)(ADC1_BASE + 0x08))
#define ADC1_SMPR2      (*(volatile uint32_t *)(ADC1_BASE + 0x10))
#define ADC1_SQR3       (*(volatile uint32_t *)(ADC1_BASE + 0x34))
#define ADC1_DR         (*(volatile uint32_t *)(ADC1_BASE + 0x4C))

#define ADC_CCR         (*(volatile uint32_t *)0x40012304)

#define RCC_APB2ENR     (*(volatile uint32_t *)(RCC_BASE + 0x44))

#define GPIOA_MODER     (*(volatile uint32_t *)0x40020000)

static void ADC_Init(void) {
    RCC_APB2ENR |= (1 << 8);
    RCC_AHB1ENR |= (1 << 0);
    
    GPIOA_MODER |= (3 << (0 * 2));
    
    ADC_CCR = (1 << 16);
    
    ADC1_CR1 = (0 << 24);
    
    ADC1_CR2 = (1 << 10);
    
    ADC1_SMPR2 = (3 << (0 * 3));
    
    ADC1_SQR3 = 0;
    
    ADC1_CR2 |= (1 << 0);
}
```

The ADC common clock register (ADC_CCR) configures the ADC clock prescaler to divide the APB2 clock by 4, producing a 42 MHz ADC clock from the 168 MHz APB2 bus. GPIO PA0 switches to analog mode through the MODER register configuration, disabling digital input buffers. The sampling time for channel 0 uses 56 cycles, providing adequate acquisition time for high-impedance sources while maintaining conversion throughput. The end-of-conversion polarity bit (EOCS) in CR2 configures the end-of-conversion flag to set after each individual conversion completes rather than after an entire sequence, simplifying single-conversion polling logic.

Implement DMA2 stream 0 configuration for transferring ADC conversion results from the ADC1 data register to a SRAM buffer. The DMA controller requires precise configuration of source and destination addresses, transfer direction, data width, and memory increment modes:

```c
#define DMA2_BASE       0x40026400
#define DMA2_S0CR       (*(volatile uint32_t *)(DMA2_BASE + 0x10))
#define DMA2_S0NDTR     (*(volatile uint32_t *)(DMA2_BASE + 0x14))
#define DMA2_S0PAR      (*(volatile uint32_t *)(DMA2_BASE + 0x18))
#define DMA2_S0M0AR     (*(volatile uint32_t *)(DMA2_BASE + 0x1C))

#define RCC_AHB1ENR     (*(volatile uint32_t *)(RCC_BASE + 0x30))

static volatile uint16_t adc_buffer[8];

static void DMA_Init(void) {
    RCC_AHB1ENR |= (1 << 22);
    
    DMA2_S0CR = 0;
    while (DMA2_S0CR & (1 << 0));
    
    DMA2_S0PAR = (uint32_t)&ADC1_DR;
    DMA2_S0M0AR = (uint32_t)adc_buffer;
    
    DMA2_S0NDTR = 8;
    
    DMA2_S0CR = (0 << 25) | (1 << 10) | (1 << 9) |
                (1 << 8) | (0 << 6);
    
    ADC1_CR2 |= (1 << 8);
}
```

The DMA configuration establishes peripheral-to-memory transfer direction with the peripheral address register pointing to ADC1_DR and memory address pointing to the adc_buffer array in SRAM. Both peripheral and memory data widths configure to 16-bit halfword transfers matching the ADC's 12-bit resolution stored in a 16-bit register. Memory increment mode enables automatic address advancement after each transfer, while peripheral address remains fixed since ADC1_DR represents a single register location. The DMA enable bit in ADC1_CR2 connects the ADC's DMA request output to DMA2 stream 0, causing the ADC to generate DMA requests upon conversion completion.

Configure USART2 for 115200 baud asynchronous transmission with 8 data bits, no parity, and 1 stop bit. The baud rate derives from the APB1 peripheral clock frequency divided by a mantissa and fractional divider stored in the baud rate register:

```c
#define USART2_BASE     0x40004400
#define USART2_SR       (*(volatile uint32_t *)(USART2_BASE + 0x00))
#define USART2_DR       (*(volatile uint32_t *)(USART2_BASE + 0x04))
#define USART2_BRR      (*(volatile uint32_t *)(USART2_BASE + 0x08))
#define USART2_CR1      (*(volatile uint32_t *)(USART2_BASE + 0x0C))

#define GPIOA_MODER     (*(volatile uint32_t *)0x40020000)
#define GPIOA_AFRL      (*(volatile uint32_t *)0x40020020)

static void USART_Init(void) {
    RCC_APB1ENR |= (1 << 17);
    
    GPIOA_MODER &= ~((3 << (2 * 2)) | (3 << (3 * 2)));
    GPIOA_MODER |= (2 << (2 * 2)) | (2 << (3 * 2));
    
    GPIOA_AFRL &= ~((0xF << (2 * 4)) | (0xF << (3 * 4)));
    GPIOA_AFRL |= (7 << (2 * 4)) | (7 << (3 * 4));
    
    uint32_t apb1_clk = 42000000;
    uint32_t baud = 115200;
    uint32_t usartdiv = (apb1_clk + (baud / 2)) / baud;
    
    USART2_BRR = usartdiv;
    
    USART2_CR1 = (1 << 13) | (1 << 3);
}

static void USART_SendByte(uint8_t byte) {
    while (!(USART2_SR & (1 << 7)));
    USART2_DR = byte;
}

static void USART_SendString(const char *str) {
    while (*str) {
        USART_SendByte(*str++);
    }
}
```

The USART baud rate calculation employs rounding division to minimize quantization error when the APB1 clock frequency does not divide evenly by the target baud rate. GPIO pins PA2 and PA3 configure as alternate function mode with AF7 selection, connecting them to USART2_TX and USART2_RX signals respectively. The USART enable bit (UE) and transmitter enable bit (TE) in CR1 activate the USART peripheral and transmission circuitry.

Implement the Timer 2 interrupt service routine that performs ADC sampling, waits for DMA completion, formats the results, and transmits via USART. Insert GPIO toggle instructions at ISR entry and exit to permit oscilloscope measurement of interrupt latency and execution duration:

```c
#define GPIOD_ODR       (*(volatile uint32_t *)(GPIOD_BASE + 0x14))

void TIM2_IRQHandler(void) {
    GPIOD_ODR |= (1 << 15);
    
    if (TIM2_SR & (1 << 0)) {
        TIM2_SR &= ~(1 << 0);
        
        DMA2_S0CR &= ~(1 << 0);
        while (DMA2_S0CR & (1 << 0));
        
        DMA2_S0NDTR = 8;
        DMA2_S0M0AR = (uint32_t)adc_buffer;
        DMA2_S0CR |= (1 << 0);
        
        for (int i = 0; i < 8; i++) {
            ADC1_CR2 |= (1 << 30);
            while (!(ADC1_SR & (1 << 1)));
        }
        
        DMA2_S0CR &= ~(1 << 0);
        
        USART_SendString("ADC: ");
        for (int i = 0; i < 8; i++) {
            char buf[8];
            uint16_t val = adc_buffer[i];
            int idx = 0;
            
            if (val == 0) {
                buf[idx++] = '0';
            } else {
                char temp[8];
                int temp_idx = 0;
                while (val > 0) {
```

```c

#define FAULT_LOG_SIZE 64

typedef enum {
    FAULT_NONE = 0,
    FAULT_HARD,
    FAULT_MEM_MANAGE,
    FAULT_BUS_FAULT,
    FAULT_USAGE_FAULT,
    FAULT_STACK_OVERFLOW,
    FAULT_WATCHDOG,
    FAULT_ADC_OVERRUN,
    FAULT_DMA_ERROR,
    FAULT_UART_OVERRUN

typedef struct {
    uint32_t timestamp;
    FaultType_t type;
    uint32_t pc;
    uint32_t sp;
    uint32_t lr;
    uint32_t psr;
    uint32_t peripheral_state[4];
} FaultEntry_t;

static volatile FaultEntry_t fault_log[FAULT_LOG_SIZE];
static volatile uint32_t fault_head = 0;
static volatile uint32_t fault_count = 0;

static uint32_t get_timestamp(void) {
    return TIM2_CNT;
}

static void log_fault(FaultType_t type, uint32_t pc, uint32_t sp, 
                      uint32_t lr, uint32_t psr) {
```

## Operational Reference Guide & Diagnostic Checklist

The operational reference guide consolidates the verification methodologies, measurement techniques, and diagnostic procedures employed throughout the laboratory exercises into a systematic checklist format. This reference enables practitioners to execute firmware verification campaigns independently, providing standardized procedures for register validation, timing measurement, peripheral functionality confirmation, and fault condition detection. Each checklist entry specifies the verification objective, required instrumentation, acceptance criteria, and diagnostic interpretation for common failure modes.

### Register Configuration Verification

Register verification confirms that peripheral initialization sequences correctly configure hardware control registers to enable desired operational modes. The systematic approach reads each relevant control register through GDB memory examination and compares bitfield values against datasheet specifications.

**Clock Configuration Validation:**
1. Halt processor execution at arbitrary point after SystemClock_Config returns
2. Read RCC_CR register at address 0x40023800: `x/1wx 0x40023800`
3. Verify HSEON (bit 16) = 1, HSERDY (bit 17) = 1, PLLON (bit 24) = 1, PLLRDY (bit 25) = 1
4. Read RCC_PLLCFGR at 0x40023804: expected value 0x20402A08 for 168 MHz configuration
5. Read RCC_CFGR at 0x40023808: verify SWS field (bits 2-3) = 0b10 indicating PLL source
6. Read FLASH_ACR at 0x40023C00: verify LATENCY field (bits 0-2) = 5 wait states
7. **Failure diagnosis:** If PLLRDY = 0, PLL failed to lock; check HSE crystal connections. If SWS ≠ 0b10, clock source switch failed; examine RCC_CFGR SW field for attempted source selection.

**GPIO Configuration Validation:**
1. Read GPIOD_MODER at 0x40020C00 after GPIO initialization
2. Extract bits 24-25 for pin 12: expected value 0b01 for output mode
3. Read GPIOD_OTYPER at 0x40020C04, bit 12: expected 0 for push-pull output
4. Read GPIOD_OSPEEDR at 0x40020C08, bits 24-25: verify speed configuration
5. Toggle GPIO output through GDB: `set *(uint32_t*)0x40020C14 = (1 << 12)`
6. Verify physical pin state change using logic analyzer or oscilloscope
7. **Failure diagnosis:** If MODE field incorrect, GPIO clock gate may be disabled; verify RCC_AHB1ENR bit 3. If physical pin does not toggle, check for alternate function configuration overriding GPIO mode.

**Timer Configuration Validation:**
1. Read TIM2_CR1 at 0x40000000: verify CEN (bit 0) = 1 for counter enabled
2. Read TIM2_PSC at 0x40000028: expected value 83 for 1 MHz timer clock
3. Read TIM2_ARR at 0x4000002C: expected value 999 for 1 kHz update rate
4. Read TIM2_CNT at 0x40000024 twice with 1 ms delay between reads
5. Calculate count difference: expected ~1000 counts per millisecond
6. Read TIM2_DIER at 0x4000000C: verify UIE (bit 0) = 1 for update interrupt enabled
7. Read NVIC_ISER0 at 0xE000E100: verify bit 28 = 1 for Timer 2 interrupt enabled
8. **Failure diagnosis:** If CNT not incrementing, timer clock may be disabled; check RCC_APB1ENR bit 0. If interrupts not firing, verify NVIC priority registers and ensure interrupts globally enabled via PRIMASK.

### Timing and Signal Integrity Measurement

Timing measurements quantify firmware execution characteristics and verify peripheral timing specifications through oscilloscope and logic analyzer instrumentation. The measurement protocol establishes standardized probe placement, trigger configuration, and statistical analysis procedures.

**Interrupt Latency Measurement:**
1. Configure Timer 2 output compare channel to toggle GPIO PA5 on update events
2. Connect oscilloscope channel 1 to GPIO PA5, channel 2 to ISR timing pin (PD15)
3. Set oscilloscope trigger on channel 1 rising edge, timebase 500 ns/division
4. Measure time from PA5 edge to PD15 edge using cursor delta measurement
5. Capture 1000 traces using oscilloscope histogram function
6. Calculate mean, standard deviation, minimum, and maximum latency values
7. **Acceptance criteria:** Mean latency < 2 µs, standard deviation < 500 ns at idle system
8. **Failure diagnosis:** Latency > 5 µs suggests Flash wait states misconfigured or branch predictor disabled. High variance indicates interrupt priority inversion or bus arbitration conflicts.

**GPIO Toggle Rate Verification:**
1. Implement tight loop toggling GPIO pin: `while(1) { GPIOD_ODR ^= (1<<12); }`
2. Connect logic analyzer to target GPIO with 100 MS/s sample rate
3. Measure toggle period using logic analyzer timing markers
4. Calculate toggle frequency: F = 1 / (2 × period) due to complementary edges
5. Compare measured frequency against theoretical maximum from clock frequency
6. **Expected results:** At 168 MHz with zero optimization, ~20 MHz toggle rate achievable
7. **Failure diagnosis:** Toggle rate < 10 MHz suggests excessive instruction overhead; examine disassembly for unnecessary memory barriers or volatile keyword side effects.

**UART Baud Rate Accuracy:**
1. Configure USART for 115200 baud transmission
2. Transmit continuous 0x55 pattern (alternating 1/0 bits) through UART
3. Connect logic analyzer to UART TX pin, configure UART protocol decoder for 115200 baud
4. Capture 1000 byte transmission sequence and analyze baud rate accuracy
5. Calculate measured baud rate from bit timing: baud = 1 / (bit_period)
6. **Acceptance criteria:** Baud rate error < ±2.5% (112,320 to 118,080 baud)
7. **Failure diagnosis:** Baud rate error > 3% suggests incorrect APB clock frequency or USART_BRR miscalculation. Use `(APB_CLK / desired_baud)` formula to recalculate.

### Functional Integration Testing

Functional tests validate end-to-end peripheral interactions including DMA transfers, interrupt-driven communication, and multi-step state machine execution. The testing methodology injects known input patterns and verifies output correctness through data comparison and checksum validation.

**ADC-DMA Transfer Validation:**
1. Apply known analog voltage to ADC input channel using function generator
2. Configure function generator for 1.65V DC output (mid-scale of 3.3V range)
3. Trigger ADC-DMA transfer sequence and capture resulting buffer contents through GDB
4. Read buffer array: `print adc_buffer` or `x/8xh &adc_buffer`
5. Calculate expected ADC value: (1.65 / 3.3) × 4095 ≈ 2048 (0x800)
6. **Acceptance criteria:** All buffer elements within ±50 counts of expected value
7. **Failure diagnosis:** Readings at 0 or 4095 suggest ADC reference voltage incorrect. Readings with high variance indicate inadequate sampling time or noisy analog ground.

**UART Transmission Integrity:**
1. Configure USB-to-UART adapter for 115200 baud, 8N1, hardware flow control disabled
2. Execute firmware transmitting known test pattern: "ABCDEFGH\r\n" repeated
3. Capture 1000 consecutive transmissions in serial terminal or log file
4. Calculate character error rate: errors / (1000 × 10 characters)
5. Verify start bit, stop bit, and parity (if enabled) through logic analyzer
6. **Acceptance criteria:** Zero character errors over 1000 transmissions
7. **Failure diagnosis:** Sporadic errors suggest electrical noise; add series termination resistor. Consistent errors at specific character positions indicate timing drift; verify baud rate accuracy.

**Interrupt Nesting Behavior:**
1. Configure multiple interrupt sources with different priorities
2. Insert GPIO toggle markers at entry/exit of each ISR
3. Connect logic analyzer with sufficient channels to capture all ISR markers simultaneously
4. Trigger lower-priority interrupt, then higher-priority interrupt during ISR execution
5. Verify logic analyzer trace shows higher-priority ISR preempting lower-priority ISR
6. Measure ISR prologue/epilogue overhead from toggle timing
7. **Acceptance criteria:** Higher priority ISR executes within 12 cycles of assertion
8. **Failure diagnosis:** Preemption not occurring suggests interrupt priorities configured identically or NVIC PRIMASK/FAULTMASK incorrectly set.

### Fault Detection and Recovery Verification

Fault verification deliberately injects error conditions and confirms firmware detection mechanisms, logging infrastructure, and recovery procedures execute correctly. The verification protocol measures detection latency, recovery success rates, and system stability metrics post-recovery.

**Watchdog Timer Functionality:**
1. Configure IWDG for 2-second timeout period
2. Execute firmware main loop without watchdog reload for 3 seconds
3. Monitor system reset through debug probe connection loss and reconnection
4. Verify reset source register RCC_CSR bit 29 (IWDGRSTF) = 1 after reboot
5. Implement watchdog reload in main loop and verify no resets occur
6. **Acceptance criteria:** Reset occurs 2.0 ± 0.2 seconds after last reload
7. **Failure diagnosis:** No reset occurring suggests IWDG not started; verify IWDG_KR unlock sequence. Premature reset indicates RLR value miscalculated for desired timeout.

**Stack Overflow Detection:**
1. Implement recursive function with no termination condition
2. Insert stack depth check calling log_fault when usage exceeds threshold
3. Execute recursive function and verify fault log entry generated
4. Read fault log through GDB: `print fault_log[0]`
5. Verify fault type = FAULT_STACK_OVERFLOW and SP value near stack base
6. **Acceptance criteria:** Fault detected before stack-heap collision occurs
7. **Failure diagnosis:** Collision occurring without detection suggests threshold too conservative; reduce threshold or implement stack canary pattern checking.

**Hard Fault Recovery:**
1. Execute instruction causing hard fault (e.g., read from invalid address `*(volatile uint32_t*)0x1FFFFFFF`)
2. Verify hard fault handler executes through GPIO LED assertion
3. Read fault log and verify PC value corresponds to faulting instruction
4. Examine Configurable Fault Status Registers (CFSR) at 0xE000ED28
5. Decode CFSR fields to identify fault cause (MemManage, BusFault, UsageFault)
6. Verify system reset executed after fault logging
7. **Acceptance criteria:** Fault detected within 1 µs, log entry valid, reset within 100 ms
8. **Failure diagnosis:** If handler not executing, verify vector table placement and weak alias declarations. If CFSR shows unexpected fault type, examine MPU configuration or bus matrix settings.

### Performance Boundary Characterization

Performance characterization establishes quantitative limits on firmware throughput, latency, and resource consumption through systematic load testing and parametric sweeps. The characterization data informs real-time scheduling analysis and resource allocation decisions.

**Maximum Sustainable Interrupt Rate:**
1. Configure timer for variable interrupt rate starting at 1 kHz
2. Insert ISR execution time measurement via GPIO toggle
3. Incrementally increase interrupt rate in 1 kHz steps
4. At each rate, measure ISR execution time and verify no ISR overlap
5. Continue until measured ISR period exceeds interrupt period (indicating overflow)
6. Record maximum rate where ISR completion precedes next interrupt assertion
7. **Expected results:** 10-50 kHz typical for ISR with moderate peripheral I/O
8. **Failure interpretation:** Maximum rate defines hard real-time scheduling bound; tasks requiring higher rate must use DMA or hardware acceleration.

**Memory Bandwidth Saturation:**
1. Configure DMA for maximum-rate memory-to-memory transfer (32-bit width, no wait states)
2. Measure transfer time for 64 KB block using TIM2_CNT timestamps
3. Calculate bandwidth: bytes / (time × clock_period)
4. Compare against theoretical AHB bus bandwidth (168 MHz × 4 bytes = 672 MB/s)
5. Vary DMA priority and measure impact on concurrent CPU execution
6. **Typical results:** 400-500 MB/s achievable with CPU concurrent execution
7. **Failure interpretation:** Bandwidth < 300 MB/s suggests bus arbitration contention; examine concurrent peripheral DMA activity and AHB bus matrix priority configuration.

**Flash Memory Endurance Verification:**
1. Implement Flash erase/write cycle loop targeting single sector
2. Execute 1000 erase/write cycles while monitoring for write failures
3. Verify data integrity after each write using CRC32 checksum
4. Read Flash status register (FLASH_SR) after each operation for error flags
5. Log cumulative error count and failure cycle number
6. **Acceptance criteria:** Zero errors over 1000 cycles (far below datasheet 10K endurance)
7. **Failure diagnosis:** Errors occurring suggest VDD voltage instability during write or inadequate erase pulse duration; verify power supply bypass capacitors and Flash timing registers.

The operational reference guide provides practitioners with standardized verification procedures encompassing register validation, timing measurement, functional integration testing, fault detection, and performance characterization. Each checklist entry specifies concrete acceptance criteria and failure diagnosis procedures, enabling systematic firmware verification campaigns that produce quantitative evidence of correctness and operational boundary limits. This methodology transforms firmware validation from subjective code review to objective measurement-based verification, establishing engineering rigor equivalent to hardware circuit testing disciplines.
