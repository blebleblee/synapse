# Lesson 6: System Interconnects

## 1. First-Principles Intuition & Invariants

The modern computer system is fundamentally a collection of autonomous agents—processor cores, memory controllers, I/O peripherals, accelerators, security coprocessors—each operating at different latencies, bandwidth requirements, and synchronization domains. The central architectural challenge is routing data, commands, and control signals between these agents with minimal latency, maximum throughput, and predictable behavior under contention. This challenge is the domain of system interconnects.

At its most primitive level, a system interconnect is a collection of wires and switching logic that enforces a protocol for bus arbitration, address decoding, and transaction sequencing. But this minimalist view obscures the profound complexity lurking beneath. Early monolithic buses—the Motorola 68000 bus, the Intel FSB (Front Side Bus)—operated on a simple principle: one master, many slaves, strictly serialized transactions. A CPU held the bus for one clock cycle, drove an address onto shared wires, waited for a slave to respond, then released the bus for the next transaction. Contention was resolved by priority arbitration: the CPU always won, peripherals took turns. Latency was predictable but bandwidth was throttled by the slowest agent and the bus clock frequency.

The critical invariant that emerges from this historical context is the **latency-bandwidth tradeoff**. Wider buses (more parallel wires) increase per-cycle throughput but demand tighter timing closure and greater pin counts. Faster clocks reduce per-transaction latency but intensify power dissipation and electromagnetic interference. Deeper pipelining hides latency but introduces pipeline bubbles and branch misprediction penalties. No single configuration optimizes all metrics simultaneously.

Contemporary systems have abandoned monolithic buses in favor of hierarchical, packet-switched interconnects. The NVIDIA NVLink, Intel QPI (QuickPath Interconnect, now replaced by UPI), and AMD Infinity Fabric exemplify this departure. These interconnects serialize transactions into variable-length packets, route them asynchronously through crossbar switches or mesh networks, and allow multiple independent transactions to be in flight simultaneously. A CPU can issue a memory read, then immediately issue a write to a different address without blocking. The interconnect decouples transaction initiation from completion, enabling **out-of-order transaction completion**.

The fundamental property that governs modern interconnect design is **transaction-level parallelism**. Unlike the monolithic bus where only one transaction occupied the wires at any instant, modern interconnects maintain multiple in-flight transactions across different physical paths. This parallelism cascades through the system: if a CPU can issue 16 independent memory transactions before any response arrives, and each transaction takes 200 nanoseconds to complete, the CPU can sustain nearly continuous load on the memory system instead of stalling after each transaction. The interconnect must therefore provide not just shared wires but independent **virtual channels** or **message queues** that allow multiple transactions to coexist without deadlock.

Deadlock is the silent killer of packet-switched interconnects. Imagine a circular wait: transaction A occupies buffer space in switch X and waits for space in switch Y; transaction B occupies space in Y and waits for space in X. Neither transaction can proceed; both are frozen indefinitely. This is not a performance degradation—it is a hard system failure. The architectural invariant that prevents deadlock is the **partial order on resources**. Every buffer, every virtual channel, every switch must be assigned a rank, and transactions can only move from lower-ranked resources to higher-ranked resources. No cycles in the resource dependency graph means no circular waits, hence no deadlock. This constraint shapes every detail of interconnect topology and flow control.

Another foundational invariant is **coherence preservation**. In a multi-core system, multiple cores may have cached copies of the same memory location. If one core modifies its cached copy, the system must ensure that all other cores either invalidate their stale copies or obtain the updated value. The interconnect must provide a **coherence protocol** that coordinates these updates, typically through broadcast invalidation (MESI protocol) or directory-based tracking (MOESI protocol). This coherence traffic can consume 30–50% of total interconnect bandwidth in some workloads, so the interconnect must be designed with coherence transactions as first-class citizens, not afterthoughts.

Finally, the invariant of **isolation and priority** emerges in systems requiring quality-of-service (QoS) guarantees. In a cloud server or automotive SoC, different tasks (real-time control loops, best-effort workloads) share the same interconnect. Without isolation, a single greedy task can saturate the interconnect and starve other tasks. The interconnect must provide **traffic shaping**, **rate limiting**, and **priority arbitration** that guarantee latency bounds for high-priority transactions even under worst-case contention. This requirement fundamentally changes the arbitration logic and buffer provisioning throughout the interconnect hierarchy.

## 2. Core Architecture & Mechanics

### Hierarchical Bus Organization

The simplest interconnect remains the hierarchical bus, found in microcontrollers and entry-level SoCs. A typical ARM Cortex-M4 microcontroller organizes its interconnect as a two-level hierarchy: a fast core bus (AHB, AMBA High-Performance Bus) connecting the CPU, instruction cache, data cache, and on-chip SRAM at the CPU clock frequency; and a slower peripheral bus (APB, AMBA Peripheral Bus) connecting UART, SPI, GPIO, and timers at a divided clock frequency (often CPU clock / 2 or / 4). Between these buses sits a bridge that translates transactions from the fast bus to the slow bus, inserting wait cycles when necessary.

The ARM AMBA AHB protocol exemplifies this hierarchy. A transaction on the AHB bus consists of an address phase and a data phase, both synchronized to the rising edge of the system clock. The master (CPU or DMA controller) drives the address, write/read control signals, and data (for writes) on clock edge N. The slave (memory controller or peripheral) observes these signals, decodes the address, accesses its internal storage, and drives the read data back onto the bus by clock edge N+1 or later, depending on latency. A slave can assert a HREADY signal to indicate it is ready; if HREADY is low, the transaction is stalled and repeats on the next clock cycle.

```
Clock    |  1  |  2  |  3  |  4  |  5  |  6  |
---------|-----|-----|-----|-----|-----|-----|
Master   | Addr| Addr| Addr| Addr| Addr| Addr|
         | Ctrl| Ctrl| Ctrl| Ctrl| Ctrl| Ctrl|
         | Wr0 | Wr0 | Wr1 | Wr1 | Wr2 | Wr2 |
---------|-----|-----|-----|-----|-----|-----|
Slave    |     | Rdy0| Rdy0| Rdy1| Rdy1| Rdy2|
HREADY   |     |  1  |  0  |  1  |  1  |  1  |
---------|-----|-----|-----|-----|-----|-----|
```

In this timing diagram, the master issues a write to address A at clock 1. The slave is ready (HREADY=1) at clock 2, so the write completes. The master immediately issues a write to address B at clock 2. The slave is not ready (HREADY=0) at clock 3, so the transaction stalls—the address and data remain on the bus, and the slave does not latch them. At clock 4, the slave becomes ready again, and the transaction finally completes. This synchronous, pipelined handshake is simple to implement but introduces **bus turnaround cycles** and **pipeline stalls** that degrade throughput when slaves have variable latency.

The fundamental limitation of hierarchical buses is **serialization under contention**. If two masters (a CPU and a DMA controller) both attempt to access the same bus segment simultaneously, an arbiter grants access to one and stalls the other. The losers wait in a queue, unable to proceed until the winner releases the bus. In a system with N masters contending for a single bus, only one can make progress at any given moment. Throughput is bounded by the bus clock frequency and the number of transactions that fit in each clock cycle—typically one transaction every 4–6 cycles including address, data, and control phases. For a system with 8 cores on a 2 GHz bus, the aggregate theoretical throughput is roughly 8 bytes per core per 6 cycles, or 2.67 bytes per core per nanosecond. Contention for a single bus quickly becomes the bottleneck.

### Crossbar Switches and Point-to-Point Interconnects

The crossbar switch architecture addresses the serialization bottleneck by providing independent paths between every master-slave pair. Conceptually, a crossbar is an N×M matrix of switches where N is the number of master ports and M is the number of slave ports. Each switch cell in the matrix can be opened or closed to route a transaction from master i to slave j. In the simplest implementation, only one transaction can traverse any given switch cell at a time, but multiple transactions can flow through different cells simultaneously. A CPU can access the L3 cache while a DMA controller simultaneously accesses main memory, and an I/O coprocessor reads from a peripheral, all on distinct paths through the crossbar.

The arbitration complexity of a crossbar scales poorly. An N×M crossbar requires N×M switch cells and O(N×M) arbitration logic to resolve conflicts when multiple masters request the same slave port simultaneously. For a 16-core system with 32 slave ports, this is 512 switch cells and correspondingly complex arbitration. Real systems mitigate this by using **hierarchical crossbars**: first-level crossbars connect clusters of 4 cores each, second-level crossbars connect clusters to memory controllers, and so forth. This hierarchical decomposition reduces arbitration complexity from O(N²) to O(N log N).

A concrete example is the NVIDIA Tegra X1 SoC, which uses a hierarchical crossbar with multiple arbitration stages. The four ARM Cortex-A53 cores share a first-level crossbar that connects to an L2 cache and a main interconnect. The main interconnect is itself a crossbar that arbitrates between the L2 cache, three memory controllers, the GPU, and various I/O controllers. When a core issues a memory read, the transaction traverses the first-level crossbar to reach the main interconnect, then traverses a second-level crossbar to reach the memory controller. If multiple cores issue simultaneous reads, the first-level arbitration may serialize some of them, but the survivors that make it to the main interconnect can proceed in parallel if they target different memory controllers.

The transaction packet format in a crossbar is more elaborate than monolithic bus signals. Each transaction is encapsulated in a **request packet** that contains the transaction ID (to match responses with requests), address, read/write control, data (for writes), and various metadata (priority level, cache coherence attributes, security realm). The request packet is routed through the crossbar by address decoding logic that examines the address bits and opens the appropriate switch cell. Once the transaction reaches the slave, the slave performs the requested operation—a memory read from DRAM, a peripheral register access, a cache tag lookup—and returns a **response packet** containing the transaction ID, read data (for reads), and any error status. The response packet traverses a separate return path through the crossbar back to the master. Separating request and response paths prevents head-of-line blocking where a slow response would stall all subsequent requests behind it.

### Network-on-Chip (NoC) Topologies

As systems scale to 100+ cores (as in modern GPU dies and data center accelerators), crossbars become prohibitively expensive. The area required for a crossbar grows as O(N²), and the power dissipation from arbitration logic and long interconnect wires becomes dominant. The solution is a **Network-on-Chip** (NoC) topology that treats the interconnect as a communication network with routers, links, and flow control similar to packet networks like Ethernet or TCP/IP, but optimized for low latency and deterministic behavior.

The simplest NoC topology is a **mesh grid**. Imagine a 4×4 grid of router nodes, with each node connected to its four neighbors (north, south, east, west). A transaction originating from a core in the top-left corner that targets a memory controller in the bottom-right corner is routed through intermediate routers using a routing algorithm (typically dimension-ordered routing: move east 3 hops, then south 3 hops). The transaction occupies one link at a time as it traverses the mesh. Other transactions can simultaneously use different links, enabling massive transaction-level parallelism.

```
    [M0]  [M1]  [M2]  [M3]
     |     |     |     |
    [R]--[R]--[R]--[R]
     |     |     |     |
    [R]--[R]--[R]--[R]
     |     |     |     |
    [R]--[R]--[R]--[R]
     |     |     |     |
    [R]--[R]--[R]--[MC]
```

In this 4×4 mesh, [M0] through [M3] are processor cores or I/O agents, [R] are router nodes, and [MC] is a memory controller. A transaction from M0 (top-left) to MC (bottom-right) is routed along the path: M0 → R → R → R → R → R → R → R → MC. This path requires 8 hops, each taking approximately 1–2 clock cycles (depending on router pipeline depth and link width). Assuming 2 cycles per hop, the transaction takes 16 cycles to reach the memory controller, plus the memory access time (e.g., 50 cycles for DRAM), plus 16 cycles to return the response, for a total round-trip latency of ~82 cycles. Meanwhile, other transactions can be routed through other links simultaneously.

The trade-off is **diameter latency vs. aggregate throughput**. A mesh with many hops has high per-transaction latency due to router pipeline stages and link traversal. An alternative topology like a **torus** (mesh with wraparound links connecting edges) or a **hypercube** (N-dimensional binary grid) can reduce diameter and latency but add complexity and wiring cost. A **tree topology** (transaction tree with roots at memory controllers) provides low latency for memory-bound traffic but creates bottlenecks at internal nodes when multiple cores access memory simultaneously. The topology choice depends on the target application: scientific computing benefits from low latency (small diameter mesh or hypercube), data center workloads benefit from high bisection bandwidth (fat tree or mesh with multiple parallel links between regions).

Flow control in a NoC prevents buffer overflow and manages credit-based transmission. Each router maintains input buffers for incoming packets and tracks the occupancy of downstream output buffers using **credit counters**. When a router has credits (available buffer space in the next router), it can transmit a packet. When credits run out, it stalls and waits for the downstream router to consume packets and return credits. This credit-based flow control guarantees that no packet is dropped due to buffer overflow—all packets either make progress or are stalled predictably.

Virtual channels further enhance NoC capacity. Instead of a single FIFO buffer at each input port of a router, we maintain K independent buffers (virtual channels). A packet arriving at an input port is assigned to one of the K channels based on its priority, coherence class, or other attributes. Each virtual channel has its own credit counter and routing state. This decoupling prevents low-priority traffic from blocking high-priority traffic and can prevent certain classes of deadlocks.

### DMA Controllers and Out-of-Order Transaction Completion

Direct Memory Access (DMA) controllers are autonomous agents that can initiate memory transactions without intervention from the CPU. A typical use case is transferring data from a peripheral (e.g., network interface card receiving Ethernet packets) to main memory. Without DMA, the CPU would execute a tight loop: read a byte from the NIC register, write it to memory, repeat. This wastes CPU cycles and creates cache pollution. With DMA, the CPU programs the DMA controller with a starting address, byte count, and source/destination selectors, then goes idle. The DMA controller reads from the NIC and writes to memory at its own pace, potentially at much higher throughput than the CPU could achieve. When the transfer completes, the DMA controller asserts an interrupt, waking the CPU.

A key architectural detail is that DMA transactions are not ordered with respect to CPU transactions unless explicit synchronization is performed. The CPU might issue a store to memory address X, then the DMA controller might read address X, but the DMA read might arrive at the memory controller before the CPU store due to different path latencies through the interconnect. If this race is uncontrolled, the DMA read returns stale data, corrupting the transfer. The mitigation is to use **memory barriers** or **synchronization fences**: the CPU executes a special instruction (e.g., `SFENCE` on x86-64, `DMB` on ARM64) that stalls the CPU until all pending stores have reached the memory controller and received acknowledgment. Only after the fence completes can the CPU safely trigger the DMA transfer.

Modern DMA controllers support **scatter-gather** mode, where instead of a single contiguous source and destination, the controller follows a linked list of descriptors, each specifying a source buffer, destination buffer, and byte count. The CPU populates this descriptor list with pointers to non-contiguous pages in memory, and the DMA controller follows the chain, performing multiple transfers. This capability is crucial for I/O virtualization and network packet processing, where buffers are often scattered across multiple pages.

The interconnect must support multiple outstanding DMA transactions simultaneously. If a DMA controller can only issue one transaction and wait for completion before issuing the next, throughput is limited by the round-trip latency. Modern controllers maintain a queue of pending transactions and can issue the next transaction as soon as the previous one is in flight (not yet completed). The interconnect must therefore provide **transaction tags** (unique IDs) that allow responses to be matched with requests out of order. When DMA transaction #3 completes before transaction #1, the DMA controller's response handler knows which transaction is completing because the response packet contains the transaction ID.

### Memory Controllers and DRAM Timing

The memory controller is the interface between the system interconnect and DRAM. It must translate logical addresses (virtual addresses translated to physical addresses by an MMU) into DRAM commands: activate a row, read/write a column, precharge the row. DRAM has complex timing constraints: after issuing an activate command to row R, the controller must wait at least 15 nanoseconds (tRCD, Row-to-Column Delay) before issuing a read or write command to a column in that row. After issuing a read command, data appears on the DRAM pins after tCAC (Column Access Time), typically 12–14 nanoseconds. Precharging a row (returning the sense amplifiers to neutral) requires tRP (Precharge Time), typically 12–15 nanoseconds.

The memory controller maintains multiple **banks** of DRAM, each capable of independent row activation. While bank 0 is precharging its current row, bank 1 can activate a different row and commence column reads. This bank-level parallelism allows the memory controller to hide some latency through **command interleaving**. A request to address A (in bank 0) triggers an activate command; before the row-to-column delay expires, a request to address B (in bank 1) can trigger an activate in a different bank, then both can proceed to column accesses in parallel.

The interconnect's role is to present a stream of read and write requests to the memory controller, and the memory controller's role is to schedule these requests to maximize throughput and minimize latency. Optimal scheduling is NP-hard (the problem is equivalent to minimizing total weighted flow time with precedence constraints), so practical controllers use heuristics:

**Row-hit prioritization** examines all pending requests and prioritizes those that hit an open row. If the current row of bank 0 is A and multiple requests to addresses in row A are pending, the controller issues these column reads first before precharging. This amortizes the activate and precharge latency over multiple accesses to the same row.

**Read-first scheduling** prioritizes reads over writes because reads block dependent instructions in the CPU pipeline, while writes can often be buffered and retired asynchronously. A write buffer in the CPU caches pending writes; after a write completes at the memory controller, the buffer is decremented, freeing the CPU to continue execution. A read, conversely, must complete before dependent instructions can proceed, so minimizing read latency improves CPU performance more than minimizing write latency.

**Write combining** buffers multiple small writes to adjacent locations and issues them as a single write burst to DRAM. Instead of issuing four separate column write commands to addresses A, A+8, A+16, A+24, the controller buffers them in a write combine buffer and issues a single burst write command that places all four values on the bus in parallel.

The interconnect must present these requests in an order compatible with the memory controller's scheduling algorithm. If the interconnect reorders requests arbitrarily, the memory controller cannot apply row-hit prioritization effectively. Many systems mitigate this through a **transaction reordering window**: the interconnect can reorder transactions within a window (e.g., up to 32 pending transactions), but transactions older than the window are not reordered. This provides the memory controller with some freedom for optimization while preserving program order for old transactions, reducing the risk of stale data hazards.

### Interrupt Handling and Control Flow

Peripherals (UART, network interface, storage controller, sensors) generate interrupts when events occur: a byte arrives on the UART, a network packet is received, a disk operation completes. Without a sophisticated interconnect, the interrupt signal is wired directly from the peripheral to the CPU's interrupt pin. The CPU periodically samples this pin, and when it transitions from low to high, the CPU suspends execution of the current instruction, saves the program counter and processor flags, and jumps to an interrupt handler routine.

This simple model breaks down in a multi-core system. If a peripheral asserts an interrupt, which core should service it? Sending it to all cores wastes resources; sending it to one core requires additional logic to choose the target. The solution is an **interrupt controller** (such as the ARM NVIC or GIC—Generic Interrupt Controller) that acts as an intermediary between peripherals and cores. Peripherals assert interrupt signals to the interrupt controller, which maintains a priority queue of pending interrupts. The controller decides which interrupt to send to which core based on priority and load balancing. When a high-priority interrupt arrives, the controller may preempt a lower-priority interrupt being serviced on a core and switch that core to the new interrupt handler.

In ARM systems with a GIC, interrupt handling proceeds as follows: a peripheral asserts an interrupt signal to the GIC's input port. The GIC latches the interrupt and sets a pending bit in an internal register. The GIC compares the interrupt's priority with the current execution priority of each core (stored in the CPU Priority Register, GICC_CTLR). If the new interrupt has higher priority and a target core is available, the GIC signals that core's interrupt pin. The core recognizes the interrupt, enters exception mode, and executes an instruction that queries the GIC to learn the interrupt number (Interrupt Acknowledge Register, GICC_IAR).

The core then services the interrupt, and upon completion, writes the interrupt number back to the GIC's End of Interrupt Register (GICC_EOIR), signaling that the interrupt has been handled. The GIC clears the pending bit, re-evaluates its priority queue, and may immediately signal another pending interrupt if one exists. This protocol ensures that interrupts are prioritized, load-balanced across cores, and that no interrupt is lost or duplicated. Modern interrupt controllers also support interrupt affinity (routing specific interrupts to specific cores) and message-signaled interrupts (MSI), where peripherals write to a special memory-mapped address to trigger an interrupt rather than asserting a dedicated wire. MSI is especially important in PCIe systems, where the number of physical interrupt lines is limited but the number of devices is large. By virtualizing interrupts as memory writes, MSI allows thousands of independent interrupt sources to coexist without physical wiring constraints, and it integrates seamlessly with cache-coherent interconnects since interrupt delivery becomes just another memory transaction.

The evolution from simple point-to-point buses to sophisticated multi-layer fabrics reflects the relentless demand for bandwidth, latency, and efficiency as system complexity grows. Every architectural choice—bus width, arbitration policy, cache coherence protocol, quality-of-service mechanism, interrupt routing—must be justified by measurement against workload requirements. A system interconnect is not an abstract diagram; it is a physical circuit with finite wire count, power budget, and signal integrity constraints. The engineer's task is to navigate these constraints while meeting throughput, latency, and coherence guarantees, ensuring that the interconnect never becomes the bottleneck that strangles an otherwise capable system.

|---------------------------|------------------------|------------------------|------------------|
| **Bus arbitration** | Only one master may drive the bus at a time; arbitration grants exclusive access | Measure arbitration latency (cycles from request to grant); verify no simultaneous grants via logic analyzer | Simultaneous grants → bus contention → data corruption; starvation → unbounded latency for low-priority masters |
| **Cache coherence (MESI/MOESI)** | All cores must observe a single, consistent view of memory; invalidate-on-write or update-on-write maintains invariant | Trace cache line state transitions; verify no dirty data exists in multiple caches simultaneously; check snoop hit rate | Stale reads (incorrect data), lost writes (data inconsistency), false sharing (ping-ponging cache lines → bandwidth waste) |
