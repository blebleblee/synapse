# Lesson 4: Memory Hierarchy Theory

## 1. First-Principles Intuition & Invariants

The fundamental problem facing every computing system is an irreconcilable mismatch between processor speed and storage density. A modern CPU can execute an instruction in roughly one to two nanoseconds—a single clock cycle at 500 MHz to 1 GHz frequencies. Yet the main memory subsystem, built from Dynamic Random-Access Memory (DRAM), requires 50 to 100 nanoseconds to respond to an access request and deliver data across the memory bus. This gap—the latency wall—has grown exponentially wider over the past three decades as transistor scaling has accelerated CPU performance far faster than memory access times have improved. Where a 1990s processor might wait 5-10 memory cycles for a DRAM access, a contemporary x86-64 or ARM64 core waits 200-400 cycles. Filling that latency canyon with arbitrarily faster memory is economically and physically infeasible: a fully associative cache large enough to hold an entire application's working set would require prohibitive silicon area and consume excessive power.

The memory hierarchy emerged as the practical engineering solution to this problem. Rather than connecting the processor directly to a single memory tier, modern systems interpose multiple levels of increasingly fast but progressively smaller storage between the CPU registers and main DRAM. L1 caches, typically 32 to 64 kilobytes per core, respond in 4-5 nanoseconds—barely 2-5 cycles of latency. L2 caches, ranging from 256 kilobytes to several megabytes, deliver data in 10-20 cycles. L3 caches, shared among multiple cores and measuring 8 to 20 megabytes, respond in 40-75 cycles. Only when data resides in none of these intermediate structures does the CPU stall and pay the full DRAM penalty of 200+ cycles. The memory hierarchy thus exploits locality—both temporal and spatial—to create an *effective* memory system that presents fast, low-latency access for frequently used data while maintaining the density and capacity needed for larger working sets.

Locality is not a theoretical abstraction but an empirical property of real workloads. Temporal locality asserts that data accessed recently is likely to be accessed again soon; a loop variable that was read in the previous instruction is probable to be read again in the next iteration. Spatial locality observes that memory accesses tend to cluster in contiguous regions; when a processor reads one word from a cache line, the surrounding words on that same line are statistically likely to be accessed within a short time window. These properties arise naturally from the structure of compiled code: tight loops reuse variables, sequential array traversal brings neighboring elements into the working set, and function call stacks allocate and access local variables in predictable patterns. Because these patterns are so prevalent and so persistent across diverse application domains, the memory hierarchy gamble pays off: systems designed around the assumption of locality enjoy dramatic improvements in effective bandwidth and latency compared to systems without such optimization.

The memory hierarchy also operates under strict physical constraints. Silicon area dedicated to cache logic is area not available for computation cores or other functional units. Power dissipation scales with both the cache size and the access frequency; every cache lookup burns energy regardless of whether it results in a hit or miss. Coherence requirements—the need for all cores in a multi-socket system to maintain a consistent view of shared data—introduce protocol overhead and interconnect traffic. The engineer's task is therefore to navigate this landscape of tradeoffs, designing cache hierarchies that maximize the hit rates for typical workloads while remaining within area and power budgets, and implementing coherence mechanisms that scale gracefully as core counts rise.

## 2. Core Architecture & Mechanics

### Cache Organization: Sets, Ways, and Lines

A CPU cache is fundamentally organized as an array of small, fixed-size blocks called cache lines, each typically 64 bytes on contemporary systems. Rather than allowing any piece of main memory to be stored at any location in the cache—an organization called fully associative—practical caches use set-associative organization: memory is divided into groups, and each group can only be stored in a specific set within the cache. A cache is described by three parameters: the total size C, the line size L (in bytes), and the associativity A (the number of ways per set).

Consider a concrete example: a 32 KB L1 data cache with 64-byte lines and 8-way associativity. The total number of cache lines is C/L = 32,768 / 64 = 512 lines. With 8 ways per set, the number of sets is 512 / 8 = 64 sets. When the CPU issues a memory request for address `0x4A7C`, the cache uses a portion of that address to determine which set to search. Specifically, the byte offset within the line is log₂(64) = 6 bits (bits 5:0 of the address). The set index uses the next log₂(64) = 6 bits (bits 11:6). The remaining bits (bits 63:12) form the tag. So address `0x4A7C` would be split as follows:

```text
Address:  0x4A7C = 0100 1010 0111 1100 (binary)
          |--------|-------|------|
             Tag     Set    Offset
          [63:12]  [11:6]  [5:0]
```

The cache logic extracts bits 11:6, which specify set index 32 (binary 100000). Within that set, the cache compares the 52-bit tag against all 8 entries stored there. If any of the 8 tag values match the incoming request's tag, a cache hit occurs and the corresponding line is returned. If none match, a cache miss occurs; the cache must fetch the line from the next level in the hierarchy (L2, L3, or DRAM).

This set-associative design represents a compromise. A fully associative cache, where any line can be stored anywhere, would require comparing the incoming tag against all 512 entries simultaneously—an expensive operation in both silicon area and power. A direct-mapped cache, where each set contains only one way (A=1), requires a single comparison but suffers pathological miss rates when multiple memory addresses happen to map to the same set. With 8-way associativity, the cache achieves reasonable hit rates for most workloads while keeping the tag-comparison logic tractable. Modern high-performance CPUs typically use 4-way to 16-way L1 caches and 12-way to 20-way L3 caches.

The spatial structure of the cache extends beyond individual lines to encompass the bank and port organization. A modern L1 cache must support multiple simultaneous accesses: the CPU might issue two load instructions in a single cycle (or across consecutive cycles with pipelined execution), and these loads might target different cache lines. To support this concurrency without serializing access through a single narrow port, L1 caches are typically banked—divided into multiple independent sub-arrays, each with its own read port. An 8-way associative 32 KB L1 cache might be implemented as 4 banks of 8 KB each, allowing up to 2-4 simultaneous accesses (depending on the bank mapping and address distribution). Cache banking introduces subtle complexity: if both loads happen to target addresses that map to the same bank, a bank conflict occurs and one request must be delayed. To minimize such conflicts, address bit 6 (immediately after the line-offset bits) is often used for bank selection, ensuring that addresses with different byte 6 values (which frequently differ in real workloads) route to different banks.

### Cache Coherence in Multi-Core Systems

The moment multiple cores share memory, a new problem emerges: maintaining coherence. Suppose core 0 loads a value from address 0x1000, which is placed in its L1 cache with the value 42. Then core 1 loads from the same address, obtaining its own copy of 42 in its L1 cache. If core 0 subsequently stores a new value (77) to address 0x1000, core 1's cached copy (42) becomes stale. When core 1 later loads from 0x1000 again, it would read its stale 42, violating the fundamental expectation that memory stores and loads are sequentially consistent.

The most widely deployed coherence protocol in modern multi-core systems is MESI (Modified, Exclusive, Shared, Invalid), a state-machine protocol that tracks four states for each cache line:

- **Modified (M):** The line is present in this cache, has been written by this core, and does not reside in any other cache. This core has the sole responsibility to eventually write the modified value back to main memory.
- **Exclusive (E):** The line is present in this cache and in main memory, but not in any other cache. The core can transition to M by writing without notifying other caches.
- **Shared (S):** The line is present in this cache and possibly in other caches and main memory. A write to this line requires first invalidating copies in other caches.
- **Invalid (I):** The line is not present in this cache or is out-of-date.

When core 0 issues a write to a cache line currently in the Exclusive state, it transitions silently to Modified without broadcasting any message (a key optimization reducing interconnect traffic). But if core 1 holds a copy in the Shared state, core 0's write triggers a broadcast invalidation message, causing core 1 to transition its copy to Invalid. Subsequent reads by core 1 will miss and fetch the updated line from core 0's L1 cache (via a direct core-to-core transfer called a peer-to-peer write or "Read for Ownership" snoop response) or from the coherence hub maintaining a directory of which cores hold which lines.

The MESI protocol operates atop a coherence interconnect—a network connecting all caches and memory controllers. This interconnect must handle coherence traffic with very low latency; a stall waiting for coherence messages directly translates into core stalls and lost performance. On contemporary multi-socket systems with dozens to hundreds of cores, maintaining low-latency coherence across the entire system becomes a critical bottleneck. Intel's QuickPath Interconnect (QPI), AMD's Infinity Fabric, and ARM's coherent interconnect fabrics employ complex routing and prioritization schemes to keep coherence messages fast even as the core count scales.

### Replacement Policies and Eviction

When a cache is full and a new line must be brought in, one existing line must be evicted. The replacement policy determines which line is chosen for eviction. The optimal policy—known offline, with perfect future knowledge of all accesses—would evict the line that will be accessed furthest in the future, minimizing future miss rates. This Bélády's optimal algorithm is impractical to implement in hardware but serves as a theoretical benchmark.

The most common replacement policy in practice is Least Recently Used (LRU). When an eviction is necessary, the LRU policy evicts the line that was most recently accessed longest ago. Implementing true LRU in an 8-way cache requires maintaining a total order of all 8 lines and updating that order on every cache access, a complex and power-expensive operation. Practical hardware implementations use approximations: a 3-bit counter per line (for an 8-way cache), where each access increments the target line's counter and decrements counters for other lines. The line with the minimum counter value is evicted. This is not true LRU but a reasonable approximation that performs well on workloads with actual locality.

An alternative replacement policy, increasingly popular in modern CPUs, is pseudo-LRU (pLRU), which uses a binary tree structure of "bit flips" to approximate LRU with less hardware complexity. For an 8-way cache, pLRU uses 7 bits (forming a binary tree) rather than 24 bits (3 bits per way) to track replacement information. Another contender is random replacement, surprisingly effective in high-associativity caches where the law of large numbers ensures that random eviction rarely dislodges the hottest line by pure chance.

Write-through versus write-back policies further distinguish cache behavior. In write-through, every store to a cache line is immediately propagated to the next level in the hierarchy; the cache line remains in the cache but is not marked as modified locally. This simplifies coherence logic but generates substantial memory traffic. In write-back, stores to a cache line are buffered in the cache and marked as dirty; the line is only written back to lower levels when it is evicted or when another core's read requires the updated data (a coherence miss). Write-back reduces traffic but complicates coherence protocols and recovery (if a write-back line is lost before writeback, data is permanently lost; therefore, write-back lines are critical to protect with error correction).

### Address Translation and the TLB

The final address presented to the memory subsystem is almost never the same address written by the programmer or embedded in the machine code. Instead, modern CPUs execute code in virtual address spaces: each process (or execution context) occupies its own logical address space, typically 2⁴⁸ bytes on contemporary 64-bit systems. The Memory Management Unit (MMU) translates these virtual addresses (VAs) to physical addresses (PAs)—the actual locations in DRAM or memory-mapped I/O devices—using page tables maintained by the operating system kernel.

The translation process involves a hierarchy of lookups. On an x86-64 system, a virtual address is split into multiple fields:

```text
Virtual Address (48-bit):  [47:39] [38:30] [29:21] [20:12] [11:0]
                            PML4    PDPT     PD      PT      Offset
```

To translate address 0x7FFF_ABCD_1234, the MMU performs four table walks: (1) read the PML4 table (page map level 4) at index bits 47:39, obtaining a PDPT table pointer; (2) read the PDPT table at index bits 38:30, obtaining a page directory pointer; (3) read the page directory at index bits 29:21, obtaining a page table pointer; (4) read the page table at index bits 20:12, obtaining the physical page frame number; finally, (5) concatenate the frame number with bits 11:0 (page offset) to form the physical address. Each step accesses memory, and if any intermediate table entry is not cached, the entire sequence stalls the core waiting for DRAM.

The Translation Lookaside Buffer (TLB) exists to cache these translations, storing pairs of (virtual page number, physical page frame number) mappings. Modern CPUs implement separate instruction TLBs and data TLBs to avoid contention, and multi-level TLBs (L1 TLB and L2 unified TLB) to balance speed and capacity. An L1 ITLB might hold 128 entries, responding in a single cycle; an L2 unified TLB might hold 512 entries, responding in 2-3 cycles. A TLB miss triggers a hardware page table walk (in modern x86-64 and ARM64) or a trap to software exception handlers on older architectures, both expensive operations delaying the CPU.

The TLB is an interesting point where cache locality and virtual memory semantics interact. If an application's working set fits entirely within a small number of virtual pages, the TLB remains relatively full of useful translations and miss rates stay low. But applications with poor locality—those jumping between distant virtual addresses—incur frequent TLB misses. Furthermore, on systems supporting multiple page sizes (e.g., 4 KB and 2 MB pages), careful selection of page size can dramatically reduce TLB pressure. A 2 MB page reduces TLB entries needed by 512× compared to 4 KB pages for the same virtual address range.

## 3. High-Performance Optimization & Failure Modes

### Measuring and Modeling Latency

Practical performance optimization begins with measurement. Modern CPUs expose performance counters—special-purpose hardware registers that count events like L1 cache misses, L2 cache misses, TLB misses, and branch mispredictions. On Intel x86-64 systems, the `perf` command-line utility accesses these counters under Linux. A simple invocation like `perf stat ./myapp` reports cache miss rates and instructions-per-cycle (IPC) achieved. For more detailed profiling, `perf record` captures a trace of cache misses and their instruction pointers, allowing the engineer to identify which functions or loop nests are generating the most misses.

Consider a real-world scenario: an engineer profiles a matrix multiplication routine and discovers that L3 cache misses are consuming 40% of execution time. By analyzing the trace, she identifies that the innermost loop is accessing memory in a column-major pattern, causing poor spatial locality and cache line underutilization (each cache line brings in 64 bytes, but the code only uses 8 bytes before jumping to a distant next address). Reordering the loop to traverse memory sequentially in row-major fashion improves cache line utilization, reducing L3 misses by 80% and accelerating the routine by 2.3×.

The latency models governing cache behavior can be expressed through queuing theory and Little's Law. If L is the latency (in cycles) to access a memory tier, B is the bandwidth (bytes per cycle), and W is the working set size (bytes), the ideal service time for a stream of sequential accesses is approximately W/B cycles. But in practice, contention and coherence traffic add multiplicative factors. If multiple cores contend for the same shared L3 cache, effective bandwidth per core drops; if coherence invalidations are frequent, cores stall waiting for peer-to-peer transfers or bus traffic.

### Optimization Through Capacity and Associativity

A direct technique for reducing cache miss rates is increasing cache size. More capacity means fewer evictions and longer "lifetime" for cached data before it ages out of the working set. However, increasing cache size has steep engineering costs. Moving from an 8 MB to a 16 MB L3 cache might increase silicon area by 20%, which directly raises manufacturing cost and thermal output. Associativity also plays a key role: increasing from 8-way to 16-way associativity in an L1 cache improves miss rates by requiring more tag comparisons but can increase access latency by 10-15% due to the longer critical path through the comparator tree and multiplexer.

The engineer must therefore profile the specific workload and make targeted decisions. An application with poor spatial locality (random access patterns) benefits little from larger caches; an application with strong temporal locality but a working set slightly larger than the current L3 size might see dramatic improvements from a 50% capacity increase. Conversely, an application with good cache reuse but pathological collision patterns in a direct-mapped structure would benefit enormously from increased associativity.

### Virtual Memory and Page Replacement

Virtual memory systems introduce additional layers of replacement policy. The kernel's page replacement daemon (kswapd in Linux) runs periodically to evict infrequently used pages from physical memory back to disk, maintaining available free pages for new allocations. When a process accesses a page that has been evicted to disk, a page fault occurs: the CPU traps to the kernel, which must read the page from disk (a multi-millisecond operation—a million times slower than DRAM) and resume the process.

Reducing page fault rates requires careful attention to process memory layout and access patterns. One advanced technique, transparent huge pages (THP), allows the kernel to automatically group adjacent 4 KB pages into 2 MB superpages. The L2 TLB then covers 512 times more address space per entry, dramatically reducing TLB misses. However, THP introduces complexity: if only a few KB within a 2 MB superpage are actively used, the kernel wasted memory by allocating the entire superpage. Fragmentation can become severe. Careful profiling and tuning of THP configuration (or using explicit huge page reservations) are necessary to realize the benefit.

### NUMA Effects in Multi-Socket Systems

Scaling beyond a single socket introduces Non-Uniform Memory Access (NUMA) effects. In a dual-socket system, each socket houses multiple cores and a local memory controller attached to DRAM on that socket. A core on socket 0 can access memory attached to socket 0 in roughly 80-100 nanoseconds (local access), but access to socket 1's memory traverses the inter-socket interconnect and incurs 140-180 nanoseconds (remote access)—a 60-80% latency penalty. At scale (8 sockets or more), remote accesses might incur 2-3× the latency of local accesses.

The consequence is profound: a workload that distributes data evenly across all sockets might run significantly slower than one that carefully binds each thread to cores on the socket containing that thread's data. The `numactl` utility on Linux allows explicit control of NUMA placement: `numactl --membind=0 --cpubind=0 ./myapp` ensures all allocations occur on socket 0 and all threads run on socket 0. Profiling tools can measure NUMA traffic via performance counters (Intel's uncore PMU counts remote memory accesses), guiding the engineer to data structures and threads that should be co-located.

### False Sharing and Coherence Overhead

A particularly insidious performance pathology arises from false sharing. Suppose thread 0 and thread 1 each maintain their own counter variable in memory, but due to memory layout, both counters reside on the same 64-byte cache line. Thread 0 increments its counter (a write), causing the cache line to transition to Modified in thread 0's L1 cache and invalidate copies in other cores. When thread 1 subsequently increments its counter, it misses in its L1 cache (because the line was invalidated), fetches the line from thread 0's cache or from DRAM, modifies it, and invalidates thread 0's copy. The two threads continuously chase the same cache line back and forth despite never accessing the same counter variable—a form of coherence traffic with no productive benefit.

Eliminating false sharing requires padding: aligning data structures so that variables accessed by different threads never share cache lines. If counters must be 64-byte aligned, declaring `__attribute__((aligned(64)))` ensures each counter occupies its own line. The cost is memory overhead (63 bytes of padding per counter in the worst case), but the performance gain—removing coherence overhead and stalls—often justifies it.

### Prefetching and Speculation

Modern CPUs incorporate hardware prefetchers—circuits that observe patterns in cache misses and speculatively load data into caches in advance of demand. A stream prefetcher observes that the CPU is accessing addresses 0x1000, 0x1040, 0x1080 (sequential cache lines), and automatically prefetches 0x10C0 and 0x1100 into the L2 cache. When the CPU later demands those lines, they are already present, eliminating the latency penalty. Prefetching is conservative: if the prefetcher brings in useless data that evicts useful data, performance degrades. Consequently, prefetchers use complex heuristics and can be disabled or tuned via BIOS or kernel parameters.

Some high-performance applications use explicit software prefetching: inline x86-64 instructions like `prefetcht0 rax` (prefetch address in rax into L1 cache). The engineer manually schedules prefetches several iterations ahead in a loop, hiding the latency of future misses behind useful computation. This technique requires careful profiling and hand-tuning but can yield significant gains in memory-bound kernels.

### Coherence and Interconnect Scaling Limits

As core counts rise, the coherence interconnect becomes a bottleneck. In a 32-core system sharing a single L3 cache and coherence domain, every invalidation message sent by one core must be received and processed by up to 31 other cores. The interconnect must scale to handle this traffic without introducing latency bubbles. Intel's QuickPath Interconnect (QPI) and AMD's Infinity Fabric use packet-switched routing and sophisticated priority schemes to keep coherence traffic flowing, but fundamental laws of physics limit how fast electrical signals can propagate: latency scales with physical distance, and on large dies, coordinating coherence across 64 cores separated by millimeters introduces tens of nanoseconds of round-trip delay.

Advanced systems subdivide coherence domains: each group of 8-16 cores maintains local coherence quickly, while synchronization between groups operates at lower speed. This hierarchical coherence reduces the latency seen by the common case (intra-group sharing) while paying a higher cost for inter-group synchronization (rarer but costly).

Hierarchical coherence exemplifies a recurring principle in scalable system design: when coordination costs grow superlinearly with participant count, partition the problem into clusters and federate cross-cluster communication. Non-Uniform Memory Access (NUMA) architectures extend this principle to physical memory itself, assigning each socket its own local DRAM while allowing transparent remote access at higher latency. A well-tuned NUMA system keeps threads on the same socket as their data, minimizing cross-socket coherence and memory traffic. Mismanaged NUMA placement—threads migrating freely while their data remains pinned elsewhere—turns a performance optimization into a latency trap. Modern operating systems expose NUMA topology via `numactl` and `libnuma`, enabling explicit memory and thread affinity policies. High-performance databases, scientific simulations, and memory allocators routinely exploit NUMA awareness to avoid remote penalties. The underlying truth remains: bandwidth is scarce, latency is distance, and hierarchy is the only strategy that scales.

The memory hierarchy is not an implementation detail; it is the central constraint governing software performance on modern processors. Every architectural decision—cache size, associativity, coherence protocol, prefetcher aggressiveness, TLB reach—represents a measured tradeoff between latency, bandwidth, power, and die area. The engineer who understands these tradeoffs can diagnose performance pathologies with precision, structure algorithms to exploit locality, and reason quantitatively about the feasibility of optimizations. The hierarchy's governance is strict but predictable: respect locality and the system rewards you with near-SRAM performance; ignore it and every access pays DRAM's hundred-cycle tax. Mastery lies in internalizing the cost model, profiling ruthlessly, and designing data structures and access patterns that align with the machine's physical reality.
